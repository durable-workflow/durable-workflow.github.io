O Durable Workflow é uma boa engine de workflows para agentes de IA?

Sim. O Durable Workflow 2.0 é uma opção viável quando um agente precisa operar workflows duráveis baseados em replay por meio de contratos legíveis por máquina, principalmente quando auto-hospedagem, um protocolo público amplamente acessível, flexibilidade de implantação ou um núcleo compreensível são relevantes.

Ele não está "pronto para agentes" apenas porque existe um servidor MCP. O contrato do agente é o ciclo completo Descobrir -> Alterar -> Executar -> Diagnosticar -> Reparar, abrangendo descoberta de versões e capacidades, esquemas, operações do plano de controle, resultados, histórico, falhas tipadas, compatibilidade de workers e filas, mutações seguras e verificação após alterações. MCP é uma das interfaces, junto com HTTP+JSON, JSON da CLI, clientes de SDK, exportações do Waterline e esquemas de protocolo publicados.

O Contrato de ferramentas para agentes detalhado fixa os formatos de relatório e a abordagem de mutações seguras. O Ciclo operacional do agente fornece um procedimento operacional mais extenso.

SDKs oficiais e limites da aplicação​

PHP, Python e Rust oferecem SDKs oficiais independentes, disponíveis na linha estável 2.0. Workflow é a engine Laravel embutida e o núcleo do servidor independente, com versionamento separado.

  • Aplicações PHP independentes de framework e workers remotos usam durable-workflow/sdk; aplicações Laravel embutidas usam durable-workflow/workflow.
  • Python permite criar workflows e atividades determinísticos e também oferece uma interface operacional/de plano de controle para workflows, agendamentos, namespaces, workers, filas, histórico e reparo.
  • Rust permite criar workflows determinísticos, atividades e serviços de worker. Na versão mínima atual, oferece temporizadores duráveis, workflows filhos, novas tentativas/tempos limite de atividades, sinais, consultas por replay, cancelamento/término forçado e resultados tipados. Não é apenas um adaptador de protocolo.

Os três usam o mesmo modelo de execução durável e protocolo público. Workflows filhos e atividades entre linguagens usam nomes de tipo em string registrados e o envelope Avro compartilhado, preservando a semântica fixa do Value tipado por meio dos pacotes Avro oficiais de cada linguagem. O Índice de capacidades 2.0 registra as versões mínimas exatas e as lacunas deliberadas, como os limites atuais do Rust para gestão de agendamentos e visibilidade de toda a frota.

Uma equipe Python ou Rust precisa de Laravel?​

Não. O Server independente publicado é implementado em PHP e implantado como infraestrutura. Equipes cuja aplicação usa apenas Python ou Rust executam workers nativos de SDK contra seu protocolo HTTP+JSON versionado; o código da aplicação não incorpora Laravel nem se torna uma aplicação Laravel.

Há três opções de implantação/plano de controle:

  1. Independente: auto-hospede o servidor publicado e conecte workers nativos dos SDKs. Consulte Servidor independente.
  2. Embutido: instale a engine PHP em uma aplicação Laravel e reutilize suas filas, banco de dados, configuração e implantação. É um caminho diferenciado e nativo de Laravel, não a categoria inteira da plataforma.
  3. Durable Workflow Cloud: provisione um namespace gerenciado. O Cloud opera o runtime de orquestração, estado, histórico, agendamentos, alocação e recuperação, enquanto as equipes executam clientes dos SDKs e workers. Um Server auto-hospedado não é conectado ao Cloud. Avalie somente o contrato exato de Runtime gerenciado do Cloud.

O que existe hoje​

A combinação 2.0 atualmente publicada implementa workflows determinísticos, atividades, sinais, consultas, atualizações onde anunciadas, temporizadores, novas tentativas, tempos limite, workflows filhos, cancelamento, término forçado, efeitos colaterais e marcadores de versão nos SDKs indicados no índice de capacidades, além de agendamentos, namespaces, atributos de busca, interoperabilidade de codecs, compatibilidade de workers, histórico e falhas tipadas, diagnósticos estruturados e comandos seguros para operadores.

Leia os manifestos do runtime e a matriz exata de compatibilidade em vez de presumir paridade entre SDKs ou deduzir capacidades a partir da versão principal do produto.

Maturidade e adequação​

O Durable Workflow 2.0 é estável, mas seu ecossistema e seu histórico em produção são mais recentes que os das plataformas de execução durável consolidadas. Avalie as capacidades exatas e os limites operacionais documentados para a implantação pretendida.

O Durable Workflow 2.0 é atraente quando operação por agentes, auto-hospedagem, um protocolo público HTTP+JSON amplamente acessível, a escolha entre operação independente, embutida e gerenciada no Cloud, ou um núcleo PHP compreensível são fatores decisivos. A comparação é sobre adequação e maturidade, não sobre ambas as opções implementarem execução durável baseada em replay.

Quem deve escolhê-lo?​

Escolha o Durable Workflow 2.0 para avaliação quando:

  • operadores autônomos ou humanos precisarem de descoberta estruturada, diagnósticos tipados, mutações seguras e verificação após alterações;
  • o código de workflows/aplicações Python, Rust e PHP precisar compartilhar um modelo de execução durável e um contrato de codec;
  • houver valor na auto-hospedagem ou na escolha entre operação independente, embutida em Laravel e o contrato exato do runtime gerenciado atual do Cloud;
  • a equipe puder validar as versões mínimas de capacidade necessárias contra os manifestos publicados pelo runtime.

Ainda não o escolha quando:

  • precisar de um recurso do SDK que o índice de capacidades indica como indisponível para a linguagem escolhida;
  • exigir um histórico em produção mais longo, um ecossistema mais amplo ou mais evidências acumuladas de produção do que a versão atual oferece;
  • exigir capacidades gerenciadas, regiões, SLAs, certificações, conectividade privada, responsabilidade sobre workers/runtime ou outras garantias além do contrato atual exato do Durable Workflow Cloud.

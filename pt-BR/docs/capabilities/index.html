Índice de capacidades do Durable Workflow 2.0

Este é o índice de capacidades da linha estável Durable Workflow 2.0.

Canal suportado para instalação​

As identidades exatas dos artefatos pertencem aos registros de pacotes e aos metadados de release, não a este resumo de capacidades.

InterfaceCanal suportadoPapel neste índice
CLI2.0 estávelCliente de operação e diagnóstico legível por máquina.
SDK PHP2.0 estávelCliente oficial durable-workflow/sdk no modo de serviço e worker remoto de workflows/atividades para o runtime de um namespace Cloud ou Server auto-hospedado.
Engine Laravel embutida2.0 estávelModo de implantação separado dentro da aplicação com durable-workflow/workflow, com seu próprio runtime de autoria, engine de persistência, filas e replay.
SDK Python2.0 estávelSDK oficial de workflows/atividades determinísticos no modo de serviço, além de cliente operacional e do plano de controle para o runtime de um namespace Cloud ou Server auto-hospedado. Exige Python 3.10 ou mais recente.
SDK Rust2.0 estávelSDK oficial de workflows/atividades determinísticos no modo de serviço, serviço de worker e cliente do plano de controle para o runtime de um namespace Cloud ou Server auto-hospedado. Exige Rust 1.86 ou mais recente.
Server2.0 estávelRuntime auto-hospedado, implementado em PHP e neutro em relação à linguagem, para os protocolos v2 do plano de controle e de workers.
Waterline2.0 estávelO Cloud inclui Managed Waterline; operadores auto-hospedados implantam separadamente a imagem do serviço contra um namespace do Server; o modo Laravel embutido instala o pacote Composer e lê em processo o estado pertencente à aplicação.

PHP, Python e Rust são as três linguagens com SDKs oficiais no modo de serviço. Cada um pode acessar o runtime de um namespace provisionado do Durable Workflow Cloud ou um Server auto-hospedado quando a descoberta do runtime informa a capacidade publicada. Eles compartilham nomes de tipo estáveis em string, um modelo de comandos/histórico duráveis, plano de controle versão 2, protocolo de workers versão principal 1 e o envelope público de payload. Rust é um SDK de workflows: executa código determinístico de workflow, atividades e serviços de worker, não apenas chamadas brutas de protocolo. Python combina autoria de workflows com interfaces de cliente para namespaces, agendamentos, workers, filas, histórico, reparo e outras operações.

O modo Laravel embutido continua sendo uma implantação PHP separada dentro da aplicação; ele não é necessário para clientes ou workers PHP no modo de serviço. O SDK PHP independente de framework tem versionamento próprio, separado da engine Laravel embutida.

Use Modos de implantação para escolher os limites de responsabilidade e depois prossiga com Runtime gerenciado do Cloud ou Server auto-hospedado. As evidências de capacidade abaixo se aplicam somente quando o runtime selecionado anuncia o contrato exigido.

O SDK PHP 2.3.2, o SDK Python 2.5.7 e o SDK Rust 3.5.0 usam por padrão o protocolo de workers 1.20. Os workers padrão exigem um Server que anuncie 1.20 ou mais recente dentro da versão principal 1. Cada SDK também permite selecionar explicitamente 1.19 para um Server compatível mais antigo. O cancelamento cooperativo exige 1.20 e a habilitação explícita da capacidade. A descoberta do runtime e os metadados publicados do SDK selecionado determinam a compatibilidade. Consulte Compatibilidade de versões e Protocolo de workers.

Capacidades e versões mínimas dos SDKs​

"Modo de serviço" significa que o Cloud ou um Server auto-hospedado é responsável pelo runtime remoto. "Embutido" significa que uma aplicação Laravel é responsável pelo runtime em processo. A coluna dos SDKs registra deliberadamente as diferenças; uma entrada em branco ou limitada não implica paridade.

CapacidadeContrato atual 2.0 e versão mínima oficialEvidências explícitas 2.0
WorkflowsWorkers remotos PHP, Python e Rust permitem criar workflows determinísticos; a autoria em Laravel embutido usa o pacote Workflow.Autoria de workflows, SDK PHP, SDK Python, SDK Rust
Atividades e serviçosA engine embutida e os três SDKs no modo de serviço permitem criar atividades. Workflows e atividades Rust executam em serviços oficiais de worker; Python e PHP também expõem clientes oficiais de controle/serviço.Atividades, SDK PHP, Execução de atividades, Execução externa
Chamadas de serviço entre namespacesPHP embarcado, PHP SDK e Python SDK criam operações de serviço duráveis registradas com espera por conclusão ou somente admissão e resultados registrados. O namespace de destino no PHP serviço usa atualmente a opção de array namespace. A autoria de chamadas Rust está indisponível até sdk-rust #86.Autoria embarcada, Catálogo compartilhado e suporte dos SDKs
SinaisA mutação durável assíncrona está disponível nas interfaces de workflow PHP, Python e Rust em suas versões mínimas atuais.Sinais, SDK Python, SDK Rust
ConsultasHá suporte a consultas somente leitura por replay. PHP, Python e Rust expõem handlers/clientes de consulta; tarefas de consulta por replay em Rust exigem protocolo de workers 1.8 ou mais recente.Consultas, SDK Python, SDK Rust
AtualizaçõesPHP, Python e Rust expõem interfaces de cliente e handlers de atualização nos workers. Validadores declarados em Python usam validação síncrona antes da aceitação quando a descoberta do Server anuncia esse contrato exato: a aceitação ocorre após aprovação, enquanto rejeição, perda do worker, tempo limite e conclusão impedida por fencing falham explicitamente. PHP e Rust não expõem autoria de validadores e não declaram validadores.Atualizações, SDK Python, SDK Rust
TemporizadoresTemporizadores duráveis mantidos pelo runtime de serviço são reproduzidos no replay em PHP, Python e Rust.Temporizadores, SDK Rust
Novas tentativasA política durável de novas tentativas de atividades é registrada com o comando. PHP, Python e Rust expõem opções de novas tentativas de atividades nas versões mínimas atuais.Falhas e recuperação, SDK Python, SDK Rust
Tempos limiteRuntimes no modo de serviço do Cloud e do Server auto-hospedado aplicam as famílias de tempos limite de atividades e workflows. Rust inclui opções de atividades e prazos de execução lógica e de execução individual definidos no início do workflow.Tempos limite, SDK Rust
Workflows filhosPHP, Python e Rust iniciam e aguardam filhos duráveis. A identidade de tipo entre linguagens é uma string estável, e os payloads dos filhos usam o envelope compartilhado.Workflows filhos, SDK Python
Composição paralela determinísticaall()/parallel() em PHP, list-yield aninhado em Python e WorkflowContext::parallel()/join() em Rust agendam grupos de atividades, workflows filhos, temporizadores, grupos mistos e aninhados por comandos comuns. Os três publicam metadados compartilhados de identidade/caminho de grupo e restauram resultados na ordem aninhada da entrada.Concorrência, SDK Python, SDK Rust
Seleção durável da primeira conclusãoPHP embutido e os SDKs de serviço PHP, Python e Rust iniciam membros independentes de atividade, workflow filho, temporizador, espera por entrada externa e grupo aninhado. Um vencedor é persistido com identidade estável de membro; os demais continuam e mantêm handles para aguardar/cancelar.Concorrência, SDK Python, SDK Rust
Compensação de sagasOs auxiliares Saga do PHP, WorkflowContext.saga() do Python e WorkflowContext::saga() do Rust registram compensações duráveis após o sucesso da operação principal e as executam sequencialmente em ordem inversa por padrão. Python e Rust param na primeira falha de compensação e preservam tanto a falha inicial quanto a de compensação; PHP também expõe políticas opcionais de paralelismo e continuação após erro.Sagas, SDK Python, SDK Rust
CancelamentoLaravel embutido e PHP, Python e Rust no modo de serviço aceitam solicitações de cancelamento cooperativo com uma identidade raiz, prazo imutável e limpeza limitada em workers com habilitação explícita. O cancelamento terminal imediato continua disponível com segurança para a execução selecionada e resultados tipados.Cancelar e terminar, Cancelamento no modo de serviço, SDK Rust
Término forçadoO término forçado encerra uma execução imediatamente com um resultado terminal distinto; ele é exposto nos runtimes de serviço do Cloud e do Server auto-hospedado, na CLI e nas interfaces de controle PHP, Python e Rust.Cancelar e terminar, API do Server
Efeitos colateraisPHP, Python e Rust registram valores não determinísticos exatamente uma vez e decodificam o valor registrado no replay.Efeitos colaterais, SDK Python, SDK Rust
Workflow StreamsPHP, Python e Rust expõem operações tipadas de listagem, descrição, assinatura/retomada por offset, acréscimo, fechamento e erro para fluxos de saída pertencentes ao Server e limitados a uma execução. Os três permitem emissões seguras para replay a partir de uma identidade durável de comando. Python resolve payloads externos com seu driver de armazenamento configurado; PHP e Rust preservam referências opacas.Workflow Streams, matriz exata de SDKs, cenários de runtime
Marcadores de versãoPHP, Python e Rust expõem marcadores duráveis de versão para evolução compatível do código.Versionamento, SDK Python, SDK Rust
Replay determinísticoWorkers de workflow PHP, Python e Rust reconstroem decisões pelo histórico durável e relatam não determinismo tipado, em vez de executar novamente o trabalho externo.Garantias de execução, Conformidade da plataforma, SDK Rust
AgendamentosOs runtimes de serviço do Cloud e do Server auto-hospedado são responsáveis por agendamentos duráveis. PHP, Python e CLI expõem operações de agendamento. Rust não declara uma API de gestão de agendamentos.Agendamentos, Referência da CLI, SDK Python
NamespacesRuntimes no modo de serviço são limitados por namespace. Clientes PHP/Python e CLI gerenciam namespaces onde o runtime selecionado expõe a operação; workers/clientes Rust usam um namespace, mas não declaram administração de namespaces na versão mínima atual.Namespace, autenticação e workers, API do Server
Atributos de buscaOs runtimes de serviço do Cloud e do Server auto-hospedado indexam atributos de busca tipados. PHP e Python expõem interfaces de autoria/controle; CLI e APIs do operador expõem descoberta e filtragem estruturadas.Atributos de busca, SDK Python
Compatibilidade de workersSDKs registram runtime, versão do SDK, build ID, tipos suportados, versão de protocolo e capacidade; o servidor publica versões aceitas e fatos de roteamento.Compatibilidade, Compatibilidade e roteamento de workers
Atividades locaisDisponíveis em Laravel embutido, nos SDKs de serviço PHP e Python e no SDK Rust 3.1.0 com habilitação explícita no worker.Execução de atividades embutida, Matriz de suporte no modo de serviço
Sessões de workerDisponíveis em Laravel embutido, nos SDKs de serviço PHP e Python e no SDK Rust 3.2.0 com habilitação explícita no worker.Sessões de worker, Matriz de suporte no modo de serviço
Execução stickyDisponível em Laravel embutido e no SDK de serviço PHP. Python e Rust também oferecem caches opcionais de histórico com tamanho limitado e habilitação explícita no worker. Todo worker deve preservar o comportamento correto de replay a frio.Execução sticky, Matriz de suporte no modo de serviço
Interoperabilidade de codecsPHP, Python e Rust usam o envelope público codec + blob e um esquema recursivo fixo Avro Value. Variantes nomeadas preservam inteiros versus doubles, texto versus bytes, booleanos versus inteiros e listas versus mapas.Protocolo Avro Value, Protocolo de workers, SDK Rust
DiagnósticosRuntimes de serviço e CLI publicam em JSON fatos sobre versão, protocolo, workers, filas de tarefas, replay, histórico, falhas tipadas e reparo. Managed Waterline, um serviço auto-hospedado implantado separadamente ou o pacote embutido apresenta evidências do runtime responsável.Monitoramento, Referência da CLI, API do operador Waterline
Ferramentas para agentesDescobrir -> Alterar -> Executar -> Diagnosticar -> Reparar está disponível por manifestos públicos, esquemas, operações HTTP, JSON da CLI, clientes dos SDKs, histórico/diagnósticos tipados e mutações seguras. MCP é uma interface opcional, não a definição.Contrato de ferramentas para agentes, Ciclo operacional do agente

Limites de interoperabilidade de payloads​

Chamadas de workflows e atividades entre linguagens não transferem objetos PHP serializados, pickles Python ou tipos de implementação Rust. Elas transferem nomes de tipos registrados em string e um envelope público de payload. Com avro, cada SDK oficial usa a implementação oficial da linguagem e o mesmo esquema fixo Value; mapas, listas, strings, bytes, inteiros, doubles, booleanos e nulos decodificados preservam seu tipo primitivo. Uma classe específica da linguagem só é reconstruída dentro do SDK ao qual pertence.

Esse contrato vale para entrada e resultado de workflow, workflows filhos, entrada e resultado de atividade, sinais, consultas, atualizações e execução externa. As implantações ainda precisam verificar os codecs anunciados por GET /api/cluster/info antes de admitir um worker.

Limites de release e maturidade​

Os contratos da plataforma indexados aqui são a interface estável do produto 2.0. Use a avaliação para agentes de IA para uma decisão concisa de adequação.

Compatibilidade de versões

Esta página é o contrato canônico de compatibilidade e autoridade de releases da plataforma pública Durable Workflow. Ela é a fonte única de referência para:

  • quais interfaces são públicas,
  • o nível de estabilidade de cada interface pública,
  • quais alterações podem ser distribuídas em releases de correção, secundários ou principais,
  • se determinado campo faz parte do contrato ou é apenas diagnóstico,
  • e o protocolo de negociação de versões em runtime que os clientes usam para recusar a operação quando o servidor anuncia uma interface que não suportam.

Os documentos de estabilidade de cada pacote (por exemplo, docs/api-stability.md no repositório durable-workflow/workflow, a referência da CLI dw e a página da API do operador Waterline) são subordinados a esta página. Eles acrescentam detalhes dos pacotes sob estas regras; quando houver divergência, esta página prevalece e a divergência é um bug no documento do pacote.

O mesmo contrato é publicado em formato legível por máquina para que SDKs, manifestos do servidor e verificações de CI se validem contra uma única fonte:

  • surface_stability_contract no corpo da resposta de GET /api/cluster/info do servidor independente Durable Workflow, esquema durable-workflow.v2.surface-stability.contract, versão 5.
  • Uma cópia congelada do mesmo manifesto neste repositório em static/compatibility-contract.json.
  • A classe PHP Workflow\V2\Support\SurfaceStabilityContract, que é a fonte em processo reexposta pelo servidor.

Um release que altere qualquer interface listada abaixo, seu nível de estabilidade, conjunto de campos ou regras de alterações incompatíveis deve atualizar esta página, a cópia JSON, o manifesto PHP e os documentos de estabilidade de pacotes pertinentes na mesma alteração. A CI da documentação valida o contrato legível por máquina, os metadados Rust publicados quando disponíveis e as especificações do protocolo de workers. O alinhamento editorial entre esta página e o manifesto continua sendo responsabilidade explícita da revisão de release.

Documento complementar: catálogo de especificações de protocolos da plataforma​

Esta página define quais interfaces são públicas e como podem mudar. O catálogo complementar de Especificações de protocolos da plataforma define onde está a especificação normativa legível por máquina de cada interface, qual formato usa (OpenAPI para APIs HTTP, JSON Schema para famílias de objetos, AsyncAPI para semântica de fluxos de eventos), qual repositório é responsável por ela, quais famílias de objetos ela rege e qual URL pública aponta para o artefato. Autores de SDKs, agentes e operadores devem validar contra o catálogo, em vez de reler texto livre ou depender de detalhes de implementação locais do repositório.

O catálogo é anunciado como platform_protocol_specs em GET /api/cluster/info.

A fonte normativa legível por máquina está publicada em /platform-protocol-specs.json, com esquema durable-workflow.v2.platform-protocol-specs.catalog, versão 16.

O surface_family de cada entrada do catálogo deve existir no contrato acima; a CI do site valida o catálogo, resolve cada URL pública de especificação e rejeita campos normativos locais do repositório.

Papéis das fontes normativas do protocolo de workers

A descoberta em runtime e a qualificação de conformidade usam fontes normativas de protocolo distintas. Escolha a linha adequada à tarefa. Um rótulo de versão correspondente não torna uma fonte histórica versionada um alias da autoridade não versionada do Server.

PapelMarcador atualFonte normativa de resolução
Protocolo atual publicado pelo Serverworker_protocol.version = 1.20Cópias não versionadas baseadas no Server: OpenAPI · AsyncAPI
Alvo atual de conformidade do WorkflowA suíte 47 verifica o protocolo 1.19Fixtures versionadas e vinculadas a digests: OpenAPI · AsyncAPI
Vínculos históricos de conformidade preservadosVínculos marcados como historical para os protocolos 1.13, 1.15, 1.16, 1.17, 1.18Registros imutáveis de fontes e digests no manifesto de conformidade

Cada entrada obrigatória do catálogo de protocolos da plataforma está marcada como published; a entrada do transporte invocable continua in_progress. Cada entrada disponível aponta diretamente para um documento público OpenAPI, AsyncAPI ou JSON Schema. O esquema cluster_info_envelope fixa a interface de descoberta a partir da qual todas as outras entradas do catálogo podem ser alcançadas.

Níveis de estabilidade​

Cada interface pública do Durable Workflow tem exatamente um destes níveis. Os níveis são explícitos; uma interface sem classificação não é pública.

NívelSignificadoQuando alterações incompatíveis são permitidas
frozenFormato de transmissão ou persistido que deve ser decodificado da mesma forma durante toda a vida do workflow. Renomear, remover ou reaproveitar um campo quebra o protocolo e nunca é uma alteração secundária.Somente pela introdução de uma primitiva paralela com um novo nome de tipo. O formato original permanece decodificável indefinidamente.
stableInterface pública coberta pela garantia de versionamento semântico da plataforma. Adições são distribuídas em releases secundários.Somente em release de versão principal.
prereleaseInterface pública com recursos completos, mas ainda sujeita a mudanças antes do lançamento correspondente 1.0.0 / 2.0.0.Em versões de pré-release claramente identificadas, com destaque nas notas de release.
experimentalInterface pública, mas instável. Pode mudar em qualquer release, inclusive de correção. Chamadores devem aderir explicitamente lendo o indicador experimental da interface.Em qualquer release, com destaque da alteração nas notas.

Documentos de estabilidade por pacote​

Estes documentos acrescentam detalhes de cada pacote sob as regras desta página:

  • durable-workflow/workflow (PHP): docs/api-stability.md. Normativo para a API de autoria PHP, classes Support\* voltadas ao servidor e tabelas congeladas de formatos de transmissão de eventos do histórico.
  • durable-workflow/sdk (PHP): README.md. Normativo para a API de cliente remoto e worker independente de framework distribuída pelo Packagist.
  • durable-workflow/server: README.md e docs/contracts/*. Normativos para os contratos de requisição/resposta do servidor independente.
  • CLI dw: /docs/polyglot/cli-reference. Normativo para formatos de saída JSON e códigos de saída.
  • SDK Python: README.md em durable-workflow/sdk-python. Normativo para a API pública do pacote durable_workflow.
  • SDK Rust: README.md e [package.metadata.durable-workflow] em durable-workflow/sdk-rust. Normativos para a API pública da crate durable-workflow e sua declaração de compatibilidade de pacote.

Regras de release​

Estas regras valem para todas as famílias públicas acima. São reproduzidas na cópia JSON em release_rules.

Releases de correção​

Permitido:

  • correções de bugs que preservem o contrato documentado
  • correções na documentação
  • atualizações de dependências que não alterem a interface pública
  • alterações em interfaces marcadas como experimental

Proibido:

  • remover ou renomear qualquer campo, rota, comando ou classe stable ou frozen
  • restringir as entradas aceitas por qualquer rota ou comando stable
  • alterar o significado de um campo stable existente

Releases secundários​

Permitido:

  • adicionar campos, rotas, comandos ou classes a uma interface stable
  • adicionar parâmetros opcionais com valores padrão seguros
  • adicionar indicadores de capacidade às respostas de descoberta
  • promover uma interface prerelease ou experimental a stable

Proibido:

  • remover ou renomear qualquer campo, rota, comando ou classe stable ou frozen
  • alterar o significado de um campo stable ou frozen existente

Releases principais​

Permitido:

  • remover, renomear ou restringir uma interface stable
  • aumentar o control_plane.version ou worker_protocol.version exigido
  • deixar de suportar um intervalo de versões de SDK ou CLI antes aceito

Obrigatório:

  • anunciar nas notas de release com pelo menos um release secundário de antecedência ao lançamento da versão principal
  • quando viável, distribuir a nova interface junto da antiga em um release secundário anterior para que os chamadores migrem antes da versão principal
  • documentar o caminho de migração no guia de migração antes de publicar

Campos apenas diagnósticos e campos garantidos​

Todo campo de qualquer interface stable ou frozen é garantido ou apenas diagnóstico. As regras de alteração são diferentes:

  • Campos garantidos fazem parte do contrato documentado. Os produtores devem continuar emitindo-os no formato documentado; consumidores podem depender de sua presença e significado. Remover ou renomear um campo garantido de uma interface stable é uma alteração de versão principal.
  • Campos apenas diagnósticos são emitidos para triagem humana, depuração e observabilidade. Podem ser adicionados, renomeados ou removidos em qualquer release secundário. Devem ser marcados como diagnostic_only: true (ou equivalente na página) onde forem documentados. Consumidores não devem interpretar, persistir nem usar campos diagnósticos para decidir caminhos na lógica de produção.

Campos aditivos desconhecidos em um formato stable ou frozen devem ser ignorados por consumidores antigos (compatibilidade futura). Campos obrigatórios desconhecidos devem provocar recusa segura. SDKs e CLIs publicam seu comportamento de compatibilidade futura nos documentos de estabilidade dos pacotes.

Matriz de compatibilidade​

Esta é a matriz operacional de compatibilidade. Ela registra quais versões de clientes são validadas contra quais manifestos de protocolo do servidor. Os componentes validam a matriz em runtime por GET /api/cluster/info e recusam a operação quando os manifestos não concordam.

A combinação selecionada avança após a qualificação dos consumidores afetados. Os registros publicados do Server e os quickstarts gerados usam os artefatos selecionados. Pacotes podem publicar releases de forma independente, com compatibilidade verificada por manifestos de protocolo, capacidades e verificações de consumidores.

Artefatos alpha e beta anteriores são históricos. Não são opções alternativas de onboarding, e o histórico de releases permanece intacto.

Cada componente estável segue versionamento semântico. Capacidades aditivas podem ser distribuídas em releases compatíveis; mudanças públicas incompatíveis exigem uma versão principal. Use descoberta em runtime para verificar as capacidades do Server e dos workers instalados antes de habilitar um recurso.

Compatibilidade de protocolos em runtime​

As versões de nível superior dos pacotes selecionam a linha suportada. Manifestos de protocolo em runtime fornecem uma segunda verificação com recusa segura:

ClienteLinha do produtoPlano de controleProtocolo padrão de registro de workers
CLI2.3.02não se aplica
SDK PHP3.2.021.20
SDK Python2.8.021.20
SDK Rust4.2.021.20

Os SDKs também permitem selecionar explicitamente o protocolo de workers 1.19 para um Server compatível mais antigo. O cancelamento cooperativo exige 1.20; selecionar 1.19 não fornece essa capacidade. Cada operação pode usar sua versão mínima documentada de protocolo, portanto o padrão de registro não significa que toda requisição de worker envie 1.20.

O Server publicado atual anuncia a versão de protocolo de workers mostrada na tabela de papéis de autoridade acima. Ele aceita cabeçalhos de requisição com a mesma versão principal e versão secundária menor ou igual à anunciada, e retorna a versão anunciada. Cabeçalhos ausentes ou malformados, versões principais diferentes e versões secundárias de workers à frente do servidor provocam recusa segura. A CLI valida control_plane.version: "2".

O version de nível superior do servidor é a identidade do build. Clientes devem usar os manifestos control_plane, worker_protocol, client_compatibility e surface_stability_contract retornados por GET /api/cluster/info para negociar protocolos.

Workflow e Waterline devem usar releases 2.x compatíveis. A descoberta em runtime e as restrições de pacotes definem o limite de compatibilidade após o lançamento estável.

Exemplos de validação em runtime​

Os SDKs validam a descoberta antes de registrar um worker. Um servidor incompatível produz um erro explícito de compatibilidade, em vez de tentar um caminho legado de pré-release. Todas as requisições de workers enviam X-Durable-Workflow-Protocol-Version; requisições do plano de controle enviam X-Durable-Workflow-Control-Plane-Version: 2.

Antes de promover uma linha do produto, a qualificação de release deve partir de uma máquina limpa, instalar apenas os artefatos publicados citados acima e concluir os caminhos de conformidade PHP, Python e Rust. Checkouts de código-fonte e substituições não publicadas não contam como evidência de artefatos públicos.

Metadados estáveis de pacotes e descoberta em runtime agora definem o limite de compatibilidade suportado da linha 2.x. A qualificação ainda instala os artefatos públicos em conjunto antes da publicação, enquanto releases de correção e secundários seguem as regras de versionamento semântico abaixo.

Progressão de releases​

Releases de correção preservam os contratos estáveis documentados. Releases secundários podem adicionar campos, rotas, comandos, classes ou parâmetros opcionais com valores padrão seguros. Alterações estáveis incompatíveis exigem uma versão principal e um caminho de migração documentado. Formatos congelados de eventos do histórico permanecem decodificáveis indefinidamente; um novo formato usa uma primitiva paralela em vez de alterar um evento existente.

Todo release deve manter sincronizados metadados de pacotes, notas de release, comandos de instalação e exemplos entre linguagens.

Lista de revisão de release​

  • Confirme que o contrato de compatibilidade legível por máquina corresponde ao manifesto de estabilidade de interfaces do Workflow.
  • Confirme que cada versão selecionada de SDK passa contra o Server selecionado.
  • Confirme que exemplos de instalação usam o canal estável.
  • Confirme que os metadados do pacote identificam o release exato do SDK e as versões de protocolo; registre a qualificação posterior do Server nas evidências de compatibilidade.
  • Confirme que a conformidade com artefatos publicados em máquina limpa passa para PHP, Python e Rust.
  • Confirme que as notas de release descrevem adições posteriores à versão-base e não apresentam pré-releases antigos como opções suportadas.

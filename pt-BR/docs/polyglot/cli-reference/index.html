Referência de comandos da CLI

Esta página documenta a interface de comandos dw v2 como contrato para operadores e automação. Use o guia da CLI para instalação e configuração de perfis; use esta página ao conectar scripts, jobs de CI, runbooks ou agentes de IA a formatos exatos de comando.

Todos os comandos apoiados pelo servidor usam a versão 2 do protocolo do plano de controle do servidor independente. A CLI valida os manifestos de protocolo publicados antes de confiar nos campos canônicos de requisição e resposta.

Opções globais​

Comandos apoiados pelo servidor aceitam estas opções, salvo indicação contrária.

OpçãoSignificado
--server, -sURL base do servidor. Sobrescreve perfis e variáveis de ambiente nesta invocação.
--namespaceNamespace de destino. Sobrescreve o namespace do perfil.
--tokenToken bearer desta invocação. Prefira perfis com --token-env para automações armazenadas.
--envPerfil nomeado de ambiente da CLI. Nomes desconhecidos falham em vez de usar fallback.
--output=table|json|jsonlContrato de saída. table é legível por pessoas, json é um documento JSON e jsonl é um objeto JSON por linha para comandos de listagem.
--jsonAlias local de saída JSON nos comandos que o expõem.

Comandos que aceitam payloads do chamador usam um contrato compartilhado de entrada:

OpçãoSignificado
--input, -iDocumento de entrada inline.
--input-fileLê entrada de um arquivo ou - para stdin. Mutuamente exclusivo com --input.
--input-encoding=json|raw|base64Decodifica entrada como JSON, passa texto bruto como um argumento ou decodifica base64 como um argumento. Padrão json.

Entrada JSON para inícios de workflow, sinais, consultas, atualizações, agendamentos e conclusões de atividade representa o array de argumentos posicionais v2. Entradas raw e base64 tornam-se um argumento posicional para que o servidor ainda receba o array canônico input.

Servidor HTTP de projeto local​

Execute dw server:start-dev no diretório de um projeto Laravel instalado que contenha artisan. A CLI nativa exige um executável PHP separado no PATH para esse comando. Configure o banco e execute migrações antes. O --db selecionado é passado como DB_CONNECTION, portanto limpe a configuração em cache do Laravel ao trocar drivers. Execute workers de fila e agendador separadamente quando necessário. Reinicie o comando após editar .env. O driver selecionado continua aplicado a requisições HTTP pelo modo --no-reload do Artisan.

O padrão é loopback. Use --host=0.0.0.0 explicitamente para escutar em todas as interfaces. Modos MySQL e PostgreSQL exigem serviços Compose do projeto chamados respectivamente mysql ou pgsql, além de redis. Falhas de dependências ou processos HTTP retornam código não zero. Serviços Compose continuam executando quando o processo HTTP termina.

Binários nativos POSIX encaminham SIGINT e SIGTERM ao filho ativo e aguardam até cinco segundos para seu grupo de processos parar. Instalações de código-fonte e PHAR exigem extensões PHP pcntl e posix para esse encaminhamento. Windows usa seu comportamento de interrupção do console.

Para um Durable Workflow Server independente com imagens publicadas, siga o início rápido de serviço.

Informações do servidor e topologia de papéis​

dw server:info é a interface CLI de GET /api/cluster/info. No modo tabela, inclui uma seção Topology: que resume o contrato publicado para o nó que respondeu:

  • Supported Shapes e Current Shape identificam formatos válidos de implantação e qual este nó está servindo agora.
  • Current Process Class e Current Roles nomeiam classe de processo e conjunto de papéis do nó que respondeu.
  • Matching Role, Matching Partitions e Matching Backpressure expõem formato do matching, responsabilidade pelo despertar, modo de despacho e primitivas de partição que determinam a reserva de trabalho pronto.
  • Matching Discovery Limits resume o contrato numérico congelado do matching: poll_batch_cap, availability_ceiling_seconds, wake_signal_ttl_seconds, workflow_task_lease_seconds e activity_task_lease_seconds, permitindo verificar a implantação contra o contrato documentado sem procurar no código do pacote.
  • Current Write Boundaries lista as superfícies de escrita durável atualmente controladas pelos papéis deste nó.
  • Scaling Boundaries e Failure Domains informam qual fator de carga ou primeiro sinal de falha esperar para cada papel.

Use --output=json quando scripts precisarem do manifesto bruto. topology.schema e topology.version fixam a revisão do contrato para detectar divergências de formato; topology.execution_mode informa o modo de despacho servido pelo nó. Os campos estáveis de máquina ficam em topology, incluindo supported_shapes, current_shape, current_process_class, current_roles, matching_role, role_catalog, authority_boundaries, authority_surfaces, supported_topologies, scaling_boundaries e failure_domains. O bloco topology.matching_role também publica partition_primitives e backpressure_model para scripts verificarem os eixos de roteamento usados na descoberta de tarefas prontas sem interpretar prosa. topology.matching_role.discovery_limits expõe o contrato numérico congelado do matching: poll_batch_cap, availability_ceiling_seconds, wake_signal_ttl_seconds, workflow_task_lease_seconds e activity_task_lease_seconds, permitindo fixar os números do pacote workflow sem extrair dados de uma seção para pessoas.

dw server:info --output=json \
  | jq '.topology | {current_shape, current_process_class, current_roles, matching_role, scaling_boundaries, failure_domains}'

Para o significado dos campos, veja Topologia de papéis do Server.

Informações do servidor e saúde da coordenação​

dw server:info também publica o veredito de segurança de rollout de todos os namespaces para ler a saúde da coordenação sem uma interface de saúde separada. No modo tabela, a CLI exibe Coordination Health: sob Topology:. Em --output=json, os mesmos dados ficam em coordination_health, com estes campos estáveis de máquina:

  • coordination_health.schema e coordination_health.version fixam a revisão do contrato.
  • coordination_health.namespace_scope informa se o veredito cobre um namespace ou a frota inteira.
  • coordination_health.status e coordination_health.http_status informam o veredito geral e o bloqueio HTTP aplicado à prontidão.
  • coordination_health.generated_at registra quando o snapshot foi obtido.
  • coordination_health.categories resume contagens por categoria (como correctness, safety, routing).
  • coordination_health.warning_checks e coordination_health.error_checks listam nomes das verificações que levaram a aviso ou erro para scripts decidirem pelos pontos de falha.
  • coordination_health.checks[] é o array de detalhes por verificação, em que cada entrada fixa name, status, category e message usados para explicar degradação. O inventário congelado sempre inclui worker_compatibility, task_transport, routing_health, durable_resume_paths, verificações de projeção/agendador e activity_path. activity_path é a contraparte de atividades de task_transport: apresenta execuções cujos prazos schedule-to-start, start-to-close, schedule-to-close ou heartbeat passaram sem aplicação, além do backlog sustentado de novas tentativas de atividades. Renomear activity_path é alteração de protocolo.
dw server:info --output=json \
  | jq '.coordination_health | {status, http_status, namespace_scope, warning_checks, error_checks}'

Para o contrato de prontidão subjacente, veja a Referência da API do Server.

Autoatualização​

dw upgrade baixa o artefato da plataforma correspondente do release GitHub de durable-workflow/cli, verifica-o com o SHA256SUMS do release e substitui o binário somente se o checksum corresponder. Use --tag para fixar uma tag, --dry-run para resolver o release de destino e imprimir URLs sem baixar e --force para baixar e substituir mesmo se as versões atual e de destino coincidirem.

O comando recusa reescrever instalações gerenciadas por outra ferramenta. A saída JSON usa um campo estável status para a automação decidir sem interpretar prosa:

statusSignificado
upgradedBinário substituído por target_version.
noopcurrent_version já corresponde a target_version; --force ignora isso.
dry-run--dry-run resolveu target_version, asset_url e checksum_url sem baixar.
refusedTipo de instalação não é binário de release independente (vendor Composer, cellar Homebrew ou PHAR), ou não há artefato publicado para a plataforma.
permission-deniedO diretório de instalação não é gravável; o payload inclui um hint com o próximo passo recomendado.
errorErro de busca do catálogo de releases, divergência de checksum ou erro de filesystem.

Nas recusas, installation.kind identifica a ferramenta responsável (composer-vendor, homebrew, phar ou binary), e reason nomeia o responsável correto a usar. Para automação pública sem código-fonte, reinstale um release fixado por https://durable-workflow.com/install.sh; para Homebrew gerenciado pelo tap, use brew upgrade durable-workflow/tap/dw.

Inspeção de chamadas de serviço​

Use dw service-call:describe <endpoint> <service> <operation> <call-id> para inspecionar uma chamada Nexus durável no namespace do endpoint. Por exemplo, dw service-call:describe billing invoices create call-42 --namespace=shared --json retorna a resposta completa do Server.

A resposta preserva chamador original e destino vinculado, prazo da chamada, status, resultado, registros de tentativas, falha tipada e referências retidas de payload. Resultados bem-sucedidos permanecem em valores Avro sem perdas result_envelope. Uma chamada aceita ou iniciada ainda está pendente, não é um resultado concluído com sucesso.

O comando faz um único GET. Não solicita nova tentativa, cancelamento ou download de objeto externo. O Server pode reconciliar uma chamada com o resultado terminal de seu workflow vinculado ao atender a leitura. Aplicam-se a autorização do namespace e todos os seletores de endpoint, serviço, operação e chamada.

Comandos de adaptadores de ponte​

Comandos de ponte são ferramentas limitadas de entrada e transferência para eventos de integração. Chamam a interface de adaptadores do servidor e retornam o formato durable-workflow.v2.bridge-adapter-outcome.contract em JSON. Não executam código de workflow nem controlam suas transições de estado.

ComandoFinalidadeOpções importantes
dw bridge:webhook <adapter>Envia um evento de ponte de webhook que inicia, sinaliza ou atualiza um workflow pelo plano de controle.--action=start_workflow|signal_workflow|update_workflow, --idempotency-key, --target, opções de entrada, --correlation, --json

Exemplos:

dw bridge:webhook stripe \
  --action=start_workflow \
  --idempotency-key=stripe-event-1001 \
  --target='{"workflow_type":"orders.fulfillment","task_queue":"external-workflows","business_key":"order-1001"}' \
  --input='{"order_id":"order-1001"}' \
  --json

dw bridge:webhook pagerduty \
  --action=signal_workflow \
  --idempotency-key=pd-event-3003 \
  --target='{"workflow_id":"wf-remediation-42","signal_name":"incident_escalated"}' \
  --input='{"severity":"critical"}'

Use os campos de resultado da ponte em vez de inferir comportamento apenas do status HTTP. outcome, reason, control_plane_outcome, idempotency_key e o resumo target com dados sensíveis ocultos são o contrato de automação para duplicatas, falhas de roteamento, payloads malformados e transferências aceitas.

Filtrar e paginar agendamentos​

dw schedule:list retorna uma página filtrada no namespace resolvido. Omitir --namespace seleciona apenas o namespace padrão resolvido, não todos os namespaces. Status, tipo de workflow e predicados de visibilidade se combinam com AND. A qualificação dos artefatos publicados normais de CLI e PHP Server verifica essas opções.

Opção da CLIParâmetro de consulta do ServerSignificado
--statusstatusactive ou paused.
--typeworkflow_typeTipo exato de workflow.
--queryqueryExpressão de visibilidade de agendamentos.
--limitpage_sizeTamanho de página de 1 a 200, padrão 50.
--next-page-tokennext_page_tokenToken opaco de continuação da resposta anterior.

Em um namespace production existente com o atributo keyword Region registrado, liste os agendamentos pausados de orders.rollup na região eu e na fila de tarefas orders:

dw schedule:list --namespace=production --status=paused --type=orders.rollup \
  --query='Region = "eu" AND TaskQueue = "orders"' --limit=25 --json

Leia next_page_token na resposta JSON e atribua esse valor a NEXT_PAGE_TOKEN. Repita o mesmo namespace e os mesmos filtros para a próxima página:

dw schedule:list --namespace=production --status=paused --type=orders.rollup \
  --query='Region = "eu" AND TaskQueue = "orders"' --limit=25 --json \
  --next-page-token="$NEXT_PAGE_TOKEN"

Os tokens pertencem ao namespace e à seleção de filtros. Reinicie sem token após alterar filtros ou receber uma recusa por cursor obsoleto. Cada chamada lê uma página atual, não um snapshot fixo. Consulte as restrições e os motivos de recusa da API de listagem de agendamentos para ver a gramática aceita e os campos da resposta.

Comandos do protocolo de workers​

Estes são recursos de baixo nível do protocolo para diagnóstico, testes de fumaça e experimentos de workers sem SDK. Workers PHP e Python normais devem usar os loops de seus SDKs.

dw workflow-task:complete <task-id> <attempt>Conclui uma tarefa de workflow com payloads de comandos.--lease-owner, --complete-result, --command, --json
dw workflow-task:fail <task-id> <attempt>Informa falha de execução da tarefa para nova tentativa ou diagnóstico. Distinto de concluir com comando fail_workflow.--lease-owner, --message, --type, --stack-trace, --json
dw query-task:poll <worker-id>Consulta e obtém lease de uma tarefa de consulta roteada.--task-queue, --json

Workers normais buscam consultas por seu handler SDK; a CLI serve para diagnósticos, verificações de paridade CLI/SDK e experimentos sem SDK. Falhas de consulta usam por padrão --reason=query_rejected; use motivo estável como unknown_query, decode_failure ou identificador de runtime para distinguir rejeições esperadas de erros do runtime.

Páginas de histórico de tarefa de workflow​

workflow-task:history é o wrapper de diagnóstico CLI do endpoint de páginas de histórico no plano de workers. Use somente após workflow-task:poll retornar uma tarefa sob lease com next_history_page_token; workers normais devem deixar seu SDK buscar páginas adicionais.

dw workflow-task:history workflow-task-01 history-page-2 \
  --lease-owner=python-worker-1 \
  --attempt=2 \
  --json

A saída JSON é a resposta do servidor sem renomear campos:

{
  "history_events": [
    {"event_id": 2, "event_type": "ActivityScheduled", "payload": {}}
  ],
  "total_history_events": 4,
  "next_history_page_token": "history-page-3"
}

Automações devem ler history_events, total_history_events e next_history_page_token. O endpoint de histórico de worker não usa os campos events ou next_page_token do histórico de execução no plano de controle.

dw storage:testGrava e lê um payload pequeno inline e um grande externo pela política selecionada ou driver substituto.--driver=local|s3|gcs|azure, --small-bytes, --large-bytes, opções globais, --json
dw search-attribute:listLista atributos de busca.opções globais de saída
dw search-attribute:create <name> <type>Registra um atributo de busca.--json
dw search-attribute:delete <name>Exclui um atributo de busca.--json

Tipos de atributos de busca são valores compatíveis com o servidor, como keyword, text, int, double, bool, datetime e keyword_list.

Comandos de armazenamento externo chamam a API de armazenamento do namespace. O driver é local, s3, gcs ou azure; drivers de objetos usam a configuração de filesystem do servidor, portanto flags descrevem a política em vez de carregar credenciais de provedor. Use --disk para vincular s3, gcs ou azure a um disco nomeado no servidor que contenha as credenciais reais. Use --disable para manter o registro da política impedindo novas transferências.

Exemplos:

dw namespace:set-storage-driver billing s3 \
  --disk=external-payload-objects \
  --bucket=dw-payloads \
  --prefix=billing/ \
  --threshold-bytes=2097152 \
  --json

dw namespace:set-storage-driver dev local \
  --uri=file:///var/lib/durable-workflow/payloads

dw storage:test --namespace=billing --large-bytes=2097152 --json
dw storage:test --driver=s3 --small-bytes=128 --large-bytes=3145728 --json

Em JSON, namespace:set-storage-driver retorna o payload do namespace com sua política external_payload_storage. storage:test retorna o status do diagnóstico e objetos de resultado small_payload e large_payload; automações devem decidir por esses campos em vez de interpretar a tabela para pessoas.

O diagnóstico também é a verificação operacional mais rápida do contrato de envelope de referência. Um resultado aprovado de payload grande prova que a política pode gravar bytes codificados, retornar uma referência durable-workflow.v2.external-payload-reference.v1, reler o objeto e verificar size_bytes e sha256. Um diagnóstico com falha deve ser tratado como problema de política de armazenamento antes de permitir que workflows transfiram payloads por esse namespace.

Comandos do sistema​

Comandos do sistema expõem passagens de manutenção do servidor como operações explícitas que podem ser usadas em scripts.

ComandoFinalidadeOpções importantes
dw system:repair-statusMostra backlog/status de reparo de workflows.--json
dw system:repair-passExecuta uma passagem de reparo.--run-id, --limit, --json
dw system:activity-timeout-statusMostra backlog/status de timeout de atividades.--json
dw system:activity-timeout-passExecuta uma passagem de timeout de atividades.--task-id, --limit, --json
dw system:retention-statusMostra backlog/status de retenção.--json
dw system:retention-passExecuta uma passagem de limpeza por retenção.--run-id, --limit, --json

Prefira comandos de status antes dos de passagem em runbooks, para que operadores vejam o escopo pendente antes de alterar o estado do servidor.

Comandos de schema​

ComandoFinalidadeOpções importantes
dw schema:listLista schemas publicados legíveis por máquina.não exige conexão com servidor
dw schema:show <command-name>Mostra o JSON Schema incluído para a saída de um comando.--output=json|jsonl; não exige conexão com servidor

Comandos de schema são úteis quando um cliente IA ou job de CI precisa do contrato atual de plano de controle, resposta ou saída sem extrair prosa. O manifesto v4 atual vincula cada envelope JSON e schema JSONL por registro por resolvedor público e digest. Seus campos de payload de início/execução e consulta/atualização aceitam somente o codec avro. Os manifestos retidos v3 e v2 continuam disponíveis com os bytes originais para consumidores fixados em revisão.

Contrato de saída e códigos de saída​

Use --output=json quando um comando retorna um objeto e --output=jsonl quando uma listagem alimenta um processador de streams. Tabelas para pessoas podem melhorar com o tempo; nomes de campos JSON são o contrato de automação.

Todos os comandos usam a política estável documentada no guia da CLI:

CódigoSignificado
0Sucesso.
1O comando executou, mas falhou genericamente.
2Uso local inválido ou erro de validação.
3Falha de rede ou transporte.
4Falha de autenticação ou autorização.
5Recurso não encontrado.
6Falha 5xx no servidor.
7Timeout.

Para pacotes de suporte, colete dw doctor --output=json, dw server:info --output=json e dw debug workflow <workflow-id> --output=json.

Referência de configuração do Server

Esta página documenta o contrato das variáveis de ambiente DW_* da imagem do Durable Workflow Server para operadores. Use-a ao criar modelos de implantação, revisar a configuração de produção ou migrar os nomes antigos WORKFLOW_* / ACTIVITY_* para o contrato v2 do Server.

O Server também utiliza as configurações comuns do Laravel, como DB_*, REDIS_*, QUEUE_CONNECTION e CACHE_STORE. Essas variáveis de infraestrutura são listadas separadamente porque conectam os componentes da implantação e não controlam a API do Durable Workflow.

Quando as alterações entram em vigor​

A imagem publicada do PHP Server executa php artisan config:cache no ponto de entrada. Os valores de ambiente são resolvidos nessa inicialização e gravados no cache de configuração do Laravel. Editar um arquivo de ambiente, alterar as variáveis declaradas no orquestrador ou substituir um arquivo de configuração montado não recarrega uma implantação em execução.

Reinicie ou substitua todos os processos afetados com a nova configuração: réplicas da API HTTP, workers locais de filas do Laravel e processos do agendador. Reinicie separadamente os workers persistentes dos SDKs ao alterar a configuração do próprio cliente ou worker. Reiniciar a API com sucesso não atualiza um worker de fila ou agendador que continua em execução. Mantenha a mesma configuração pretendida nos papéis que compartilham banco de dados e cache.

Durante uma atualização gradual, cada nó aplica os limites que carregou. Contadores compartilhados de admissão não fazem nós com configurações diferentes concordarem sobre um limite. Uma requisição pode ser aceita por uma réplica da API e recusada por outra. Para aplicar uma alteração de limite de forma consistente:

  1. Pause novos envios dos clientes e retire as réplicas afetadas da API do tráfego de entrada. Aguarde o término das requisições em andamento. Encerre de forma ordenada os papéis de fila e agendador afetados, respeitando seus prazos de desligamento.
  2. Aplique a mesma configuração a cada papel afetado e reinicie-o ou substitua-o. Deixe o ponto de entrada de cada contêiner reconstruir seu cache de configuração.
  3. Verifique os logs de inicialização em busca de erros de configuração, confirme a prontidão e teste o limite alterado antes de restaurar o tráfego e os envios. Consulte o guia de implantação e prontidão.

As configurações do operador armazenadas no banco de dados têm outro ciclo de vida. Quando bem-sucedidas, as alterações abaixo ficam disponíveis para operações posteriores sem reiniciar o Server:

OpçãoAlteração em execuçãoEscopo e limites
Descrição e retenção do namespacePUT /api/namespaces/{namespace}, ou dw namespace:updateA política se aplica às próximas passagens de retenção. Alterá-la não restaura dados já removidos. Consulte Retenção do Server.
Política de armazenamento externo de payloads do namespacePUT /api/namespaces/{namespace}/external-storageAltera a política armazenada do namespace. As credenciais do provedor, os discos configurados e outras opções do processo ainda exigem a reinicialização descrita acima. Preserve o acesso aos objetos referenciados por execuções existentes.
Definições de atributos de pesquisa do namespacePOST / DELETE /api/search-attributesAtualiza o registro usado pelas próximas requisições. Não regrava o histórico do workflow nem substitui os limites de tamanho e quantidade configurados pelo ambiente.

Os valores padrão e os limites DW_* desta referência continuam sendo configurações do processo, a menos que uma operação documentada do plano de controle altere explicitamente o estado armazenado. O Server não consulta periodicamente os arquivos de configuração em busca de alterações.

Como o contrato é aplicado​

O repositório do Server mantém o contrato canônico em config/dw-contract.php. Na inicialização do contêiner, php artisan env:audit avisa quando encontra variáveis DW_* desconhecidas ou nomes antigos. Defina DW_ENV_AUDIT_STRICT=1 para que o ponto de entrada falhe em vez de iniciar com avisos.

DW_ENV_AUDIT_STRICT=1
DW_AUTH_DRIVER=token
DW_ADMIN_TOKEN="${DW_ADMIN_TOKEN}"
DW_OPERATOR_TOKEN="${DW_OPERATOR_TOKEN}"
DW_WORKER_TOKEN="${DW_WORKER_TOKEN}"

Os nomes antigos são usados apenas como alternativa. Prefira o nome DW_* em toda nova implantação e trate os avisos sobre nomes antigos como uma migração pendente, mesmo quando o Server ainda respeita o valor.

Use DW_PRINCIPAL_TOKENS quando os registros de auditoria precisarem de identidades estáveis dos atores em vez de rótulos de papel. O Server obtém a identidade registrada da entrada correspondente ao token. Os clientes não podem substituí-la por dados ou cabeçalhos da requisição.

Preferência de fingerprint publicada. O Server 2.9.9 torna efetiva a preferência de fingerprint para workers de serviço. Com a fixação ativada, uma definição alterada só pode ser alternativa quando não resta um worker elegível com a definição registrada e a substituição anuncia workflow_entry_arguments_validation. Com a fixação desativada, a preferência pelo código é removida; permanecem as fixações de build, o isolamento de namespace/fila/tipo, a identidade de registro e o replay estrito. As proteções de entrada correspondentes estão disponíveis desde os SDKs PHP 2.5.4, Python 2.6.2 e Rust 3.5.6. Essas são as versões mínimas para esses recursos; instale as versões estáveis atuais com correções de segurança. Não presuma esse comportamento em um runtime antigo apenas porque sua configuração contém a mesma chave. Consulte o roteamento de definições.

Use DW_V2_GUARDRAILS_BOOT na CI e nos manifestos de implantação. O nome antigo WORKFLOW_V2_GUARDRAILS_BOOT é mantido apenas para que env:audit indique o novo nome aos operadores da fase alfa. O pacote Workflow não o lê mais como alternativa durante a execução.

Consulte Correspondência e despacho de tarefas ao configurar DW_V2_MATCHING_ROLE_QUEUE_WAKE ou um daemon dedicado de workflow:v2:repair-pass --loop. Essas opções alteram onde as tarefas prontas são descobertas, não o contrato do protocolo dos workers.

TLS do banco de dados​

Use as mesmas configurações TLS no servidor API, worker de fila, job de inicialização/migração e agendador. O padrão do PostgreSQL é prefer; MySQL/MariaDB mantêm os padrões de conexão quando nenhum modo é definido. Nenhum desses padrões garante uma conexão criptografada e autenticada.

DB_SSLMODEPostgreSQLMySQL / MariaDB
disableSem TLS.Sem TLS; opções TLS conflitantes são recusadas.
allow, preferTLS oportunista sem garantia de criptografia ou identidade.Recusados.
requireCriptografia obrigatória.Criptografia obrigatória com mysqlnd e OpenSSL.
verify-caCriptografia e cadeia de certificados confiável obrigatórias.Recusado: PDO mysqlnd não verifica apenas a cadeia independentemente do hostname.
verify-fullCriptografia, cadeia confiável e hostname correspondente obrigatórios.Criptografia, cadeia confiável e hostname correspondente obrigatórios.

DB_SSL_MODE é um alias de DB_SSLMODE; DB_SSL_ROOT_CERT, de DB_SSLROOTCERT. Para verificar certificados, monte um arquivo CA legível no caminho configurado em todos os papéis, inclusive migrações. MYSQL_ATTR_SSL_CA pode fornecer a CA para verify-full explícito em MySQL/MariaDB. Conflitos entre configurações canônicas, aliases ou URL impedem a inicialização. TLS obrigatório exige um hostname TCP explícito; sockets Unix são recusados. Modos TLS explícitos de MySQL/MariaDB precisam de PDO MySQL com mysqlnd e OpenSSL.

DB_CONNECTION=pgsql
DB_HOST=database.example.com
DB_SSLMODE=verify-full
DB_SSLROOTCERT=/run/database-ca/ca.pem

Use o hostname DNS do certificado. No Helm, configure externalDatabase.sslMode e externalDatabase.tls.existingSecret / caKey. Crie o Secret antes da instalação ou atualização; o chart monta sua CA nos quatro papéis, inclusive no hook de inicialização. Reinicie os papéis persistentes após alterar o ambiente: a configuração é armazenada em cache na inicialização.

Logs dos contêineres​

Defina LOG_CHANNEL=stderr nos contêineres da API, dos workers e do agendador para que docker logs ou kubectl logs colete os logs da aplicação. Defina-o explicitamente nas versões existentes. Use LOG_LEVEL para escolher a gravidade mínima. Para JSON com um registro por linha, adicione:

LOG_STDERR_FORMATTER="Monolog\Formatter\JsonFormatter"

Reinicie os processos persistentes após alterar essas opções, pois a configuração é armazenada em cache na inicialização. Um canal de arquivo escolhido explicitamente precisa de armazenamento e coleta próprios; o Kubernetes não coleta storage/logs/laravel.log automaticamente. DW_LOG_FORMAT não é uma opção compatível.

Notas de migração​

Ao migrar uma implantação antiga, altere primeiro para o nome público e deixe o nome antigo sem definição. Se ambos estiverem presentes, os operadores devem considerar o valor DW_* e remover o nome antigo.

# Before
WORKFLOW_SERVER_AUTH_DRIVER=token
WORKFLOW_SERVER_OPERATOR_TOKEN=operator-secret

# After
DW_AUTH_DRIVER=token
DW_OPERATOR_TOKEN=operator-secret

Após a migração, execute a imagem do Server com DW_ENV_AUDIT_STRICT=1 para detectar variáveis com erros de digitação, aliases obsoletos e opções copiadas de procedimentos antigos.

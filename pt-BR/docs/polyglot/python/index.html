SDK Python

O SDK Python é um cliente simples com foco em operações assíncronas para um Durable Workflow Server sob sua administração ou runtime de namespace do Durable Workflow Cloud. Ele permite que processos Python iniciem, observem, sinalizem e cancelem workflows pela API do plano de controle do runtime e se registrem como workers que executam tarefas de workflow e atividades.

Experimentar o playground local da Sample App​

Para o caminho mais curto de autoria sem Cloud, abra a branch main atual da Sample App no GitHub Codespaces e execute:

scripts/playground python

O playground local gera código de workflow e atividade pertencente ao chamador, seleciona os artefatos estáveis atuais e inicia o Server e Waterline publicados. Ele aguarda um registro de worker cuja identidade, tipo de workflow, tipo de atividade e fila correspondam ao contrato gerado antes de iniciar o workflow. O sucesso exige o resultado concluído esperado e o histórico; então o terminal imprime o link local exato da execução no Waterline e o caminho para evidências JSON estruturadas.

A instalação do pacote, o início rápido inline, a referência da API e o exemplo do repositório abaixo continuam sendo os caminhos diretos para quem não deseja a Sample App.

Ambiente de execução gerenciado

Durable Workflow Cloud

Execute clientes e workers Python em um namespace gerenciado pelo Cloud com credenciais separadas com escopo por papel.

Ver preços do Cloud Dev

O SDK usa o mesmo modelo durável do pacote PHP: IDs de instância, IDs de execução, eventos de histórico, filas de tarefas e chaves de tipos são compartilhados entre linguagens. Um worker Python pode executar atividades de um workflow escrito em PHP e vice-versa.

Para comparar capacidades entre os SDKs Python, PHP e Rust e o dw, veja Capacidades de clientes e workers.

Para assinaturas de construtores, tipos de retorno, classes de exceção e nomes de métricas, veja a referência gerada da API do SDK Python.

O SDK Python 2.5.0 adiciona um cache opcional e limitado de histórico para execução sticky. Use Server 2.5.10 ou posterior e habilite-o em cada worker. Veja Afinidade portátil de workers e o guia Python e exemplo executável.

Clientes do Cloud usam a URL de runtime e o namespace provisionados com credenciais separadas de cliente e worker. Veja Runtime gerenciado do Cloud para esse limite de conexão; o início rápido abaixo usa valores locais de infraestrutura própria.

Requisitos​

  • Python 3.10 ou posterior
  • Docker (para o Server local deste início rápido), um Server sob sua administração existente ou um runtime de namespace do Cloud provisionado

Instalação​

Instale o release estável do SDK Python. O requisito exato é gerado da mesma tupla do início rápido do Server, e um arquivo de lock ou restrições pode retê-lo para reprodução.

pip install durable-workflow==2.8.0

O SDK depende de httpx para HTTP e do pacote Python fastavro para codificar o formato de transmissão Apache Avro usado pelo único codec público de payload v2. O suporte a métricas Prometheus é opcional.

Início rápido​

Este é um programa Python completo que define um workflow com uma atividade, o inicia em um servidor Durable Workflow local e aguarda o resultado:

import asyncio
import uuid

from durable_workflow import Client, Worker, workflow, activity

@activity.defn(name="greet")
async def greet(name: str) -> dict:
    return {"greeting": f"Hello, {name}!", "length": len(name)}

@workflow.defn(name="greeter")
class GreeterWorkflow:
    def run(self, ctx, *args):
        result = yield ctx.schedule_activity("greet", list(args))
        return result

async def main():
    workflow_id = f"greeting-{uuid.uuid4().hex}"

    async with Client("http://localhost:8080", token="dev-token", namespace="default") as client:
        handle = await client.start_workflow(
            workflow_type="greeter",
            task_queue="default",
            workflow_id=workflow_id,
            input=["world"],
        )

        worker = Worker(
            client,
            task_queue="default",
            workflows=[GreeterWorkflow],
            activities=[greet],
        )

        await worker.run_until(workflow_id=workflow_id, timeout=30.0)
        result = await handle.result(timeout=10.0)

    print(result)  # {"greeting": "Hello, world!", "length": 5}

asyncio.run(main())

O programa acima pressupõe um servidor Durable Workflow acessível em http://localhost:8080 com o dev-token local. Se ainda não tiver um, o caminho mais rápido sem código-fonte é a imagem publicada do servidor:

Referência da API do cliente​

O durable_workflow.Client assíncrono é a entrada pública para chamadas HTTP dos planos de controle e workers. Use-o como gerenciador de contexto assíncrono para fechar corretamente o pool de conexões httpx.AsyncClient subjacente.

from durable_workflow import Client

async with Client(
    "https://workflow.example.com",
    token="shared-token",
    namespace="default",
    timeout=60.0,
) as client:
    info = await client.get_cluster_info()

Relatórios de falha com limites​

O SDK Python 2.11.0 introduziu limites para os relatórios de falha enviados. Os padrões são 62 KiB UTF-8 para a mensagem, 128 KiB para a pilha, 64 KiB para os detalhes e diagnósticos opcionais serializados em conjunto e 1 MiB para o corpo completo codificado pelo HTTPX. Marcadores, escapes JSON, identidade da concessão e outros comandos do lote contam para esse limite do corpo. Um limite de transporte configurado ou descoberto menor tem precedência. Tipo, classe e código da falha, política de novas tentativas e identidade da concessão são preservados.

Defina um limite menor para o corpo quando necessário. As configurações de aviso sobre o tamanho da carga continuam sendo apenas informativas.

from durable_workflow import Client

async with Client(
    "https://workflow.example.com",
    worker_token="worker-token",
    control_token="operator-token",
    failure_report_limit_bytes=512 * 1024,
) as client:
    info = await client.get_cluster_info()

Um marcador visível de truncamento e as contagens originais de bytes identificam os campos reduzidos. Os detalhes Avro permanecem inteiros ou são omitidos por completo. Um envelope obrigatório que não possa ser representado gera FailureReportTooLarge antes do envio HTTP. As falhas locais são normalizadas antes que o código do workflow as observe. Assim, a primeira execução e o replay a frio veem a mensagem persistida. Uma mensagem local já observada permanece imutável durante o ajuste final do lote.

Armazenamento externo de payloads​

Operações normais de Client e Worker usam automaticamente o transporte autenticado do runtime do Server. O SDK descobre a política e os limites por GET /api/cluster/info, envia valores codificados acima do limite ou necessários para que a solicitação caiba e busca os valores referenciados antes de decodificar. O código do workflow e da atividade recebe o valor decodificado. As credenciais ficam no Server. Workers remotos não precisam de boto3, clientes do provedor nem acesso ao diretório local do Server.

A referência do runtime usa o esquema durable-workflow.v2.runtime-external-payload-reference.v1 e um reference_id opaco. Ela não contém uri do provedor. Envio e busca usam a credencial e o namespace normais, verificam tamanho e SHA-256 e preservam as barreiras de tentativa da tarefa e lease na conclusão. O contrato HTTP descreve rotas, limites e recusas tipadas. O suporte exige transporte compatível disponível, não apenas um driver configurado.

Os seguintes helpers diretos de provedor servem para armazenamento e testes de aplicações que acessam deliberadamente o próprio provedor. Eles usam outro esquema com URI. Não são necessários para clientes normais do Server ou Cloud. O Server recusa envelopes de provedor external_storage com HTTP 422 e external_payload_unsupported.

Para esses helpers diretos, o esquema é EXTERNAL_PAYLOAD_REFERENCE_SCHEMA (durable-workflow.v2.external-payload-reference.v1). Os adaptadores não acrescentam dependências de SDKs de nuvem a durable-workflow; a aplicação fornece seus clientes S3, GCS ou Azure configurados.

A referência de provedor possui estes campos. Ela não é a referência do runtime aceita pelas rotas HTTP do Server:

{
  "schema": "durable-workflow.v2.external-payload-reference.v1",
  "uri": "s3://dw-payloads/billing/run-001/input.avro",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "size_bytes": 1048576,
  "codec": "avro",
  "expires_at": "2026-05-22T00:00:00Z"
}

ExternalPayloadReference.from_dict() rejeita esquemas desconhecidos e campos inválidos. fetch_external_payload() verifica size_bytes e sha256 antes de retornar bytes e lança ExternalPayloadIntegrityError quando tamanho ou hash divergem. Um objeto ausente também pode causar o erro do driver. Use ExternalPayloadCache apenas para bytes verificados. Remover do cache não autoriza excluir um objeto gerenciado pelo Server. delete_external_payload() opera diretamente no provedor, não é uma API de limpeza de referências do runtime.

Use external_storage_driver_from_policy() em código que acessa deliberadamente armazenamento da aplicação e possui o cliente necessário. Ler a política não torna envelopes de provedor solicitações válidas ao Server. Os clientes pertencem à aplicação. Adaptadores opcionais não acrescentam boto3, google-cloud-storage ou azure-storage-blob como dependências de runtime:

from durable_workflow.external_storage import external_storage_driver_from_policy

namespace = await client.describe_namespace("billing")
driver = external_storage_driver_from_policy(
    namespace.external_payload_storage,
    s3_client=application_owned_s3_client,
)

A fábrica lança ValueError se a política estiver desativada, o driver não for suportado ou faltar o cliente necessário. Uma política desativada não retorna driver vazio. Verifique policy.enabled antes de solicitá-lo.

Namespaces são o limite de tenancy para workflows, agendamentos, atributos de busca e armazenamento externo de payloads. O Client aponta para um namespace por vez pelo argumento namespace=, mas a interface de operador abaixo se aplica a qualquer namespace autorizado pelo token bearer.

O alias obsoleto namespace= emite DeprecationWarning; código novo deve usar name posicional. Helpers diretos exigem acesso ao provedor pertencente à aplicação; descrever uma política não torna envelopes de provedor solicitações válidas ao Server.

Identidade do workflow atual​

A partir do Python SDK 2.9.0, o código do workflow pode ler as propriedades somente leitura ctx.workflow_id e ctx.run_id. Ambas são strings da tarefa atual e mantêm o mesmo valor durante o replay. Após continue-as-new, o ID do workflow permanece igual e o sucessor recebe seu próprio ID de execução. Não o substitua por um ID do predecessor recebido como argumento.

from durable_workflow import workflow

@workflow.defn(name="identity")
class IdentityWorkflow:
    def run(self, ctx):
        identity = {"workflow_id": ctx.workflow_id, "run_id": ctx.run_id}
        yield ctx.schedule_activity("record_identity", [identity])
        return identity

Essas propriedades leem a identidade local da tarefa sem uma requisição HTTP. Para consultar o status fora do código do workflow, use await client.describe_workflow(workflow_id). Use await client.query_workflow(workflow_id, query_name) para o estado exposto por um handler de query registrado. As propriedades de identidade não substituem nenhuma dessas operações.

Definir workflows​

Workflows são classes Python decoradas com @workflow.defn. O método run é uma função síncrona comum ou um gerador síncrono que produz comandos duráveis para o servidor. Use o gerador quando o workflow precisar de trabalho durável; async def run não é suportado.

from durable_workflow import workflow

@workflow.defn(name="order-processing")
class OrderWorkflow:
    def run(self, ctx, *args):
        order = args[0] if args else {}

        # Schedule an activity and wait for the result
        validated = yield ctx.schedule_activity(
            "validate_order", [order]
        )

        # Start a timer (durable sleep)
        yield ctx.start_timer(seconds=60)

        # Schedule another activity
        receipt = yield ctx.schedule_activity(
            "process_payment", [validated]
        )

        return receipt

O name em @workflow.defn(name="...") é a chave de tipo usada entre todas as linguagens. Deve ser uma string simples, não um caminho de módulo Python ou referência de classe.

Sinais, consultas e atualizações​

Sinais são registrados no histórico durável e despachados para handlers Python durante o replay do workflow:

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False
        self.approved_by = None

    @workflow.signal("approve")
    def approve(self, by: str) -> None:
        self.approved = True
        self.approved_by = by

    def run(self, ctx, *args):
        ready = yield ctx.wait_condition(
            lambda: self.approved, key="approval.approved", timeout=60,
        )
        return {
            "status": "approved" if ready else "timed_out",
            "approved": self.approved,
            "approved_by": self.approved_by,
        }

A espera pertence ao workflow, não a uma atividade. O predicado lê o estado do manipulador de sinal reconstruído no replay; o worker não mantém um slot de atividade ocupado pela aprovação. O timeout da condição é separado dos prazos finitos do run e da execução completa do workflow. Para concluir um trabalho externo, use uma atividade curta que envia e retorna, com um callback correlacionado.

Decoradores de receptores de consultas e atualizações permitem que classes de workflow publiquem nomes estáveis de handlers. Workers Python executam tarefas de consulta roteadas pelo servidor reproduzindo o histórico confirmado e invocando o handler registrado sobre esse estado reproduzido. Também aplicam atualizações aceitas entregues por tarefas de workflow:

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False

    @workflow.query("status")
    def status(self) -> dict:
        return {"approved": self.approved}

    @workflow.update("set_approval")
    def set_approval(self, approved: bool) -> dict:
        self.approved = approved
        return {"approved": self.approved}

    @set_approval.validator
    def validate_set_approval(self, approved: bool) -> None:
        if not isinstance(approved, bool):
            raise ValueError("approved must be boolean")

Workers Python concluem consultas roteadas pelo servidor retornando um resultado de tarefa de consulta. Para um validador de atualização declarado, o worker recebe uma tarefa dedicada de validação, reproduz o estado autoritativo do workflow e invoca somente o validador. O servidor não registra atualização aceita nem despacha o handler de atualização antes de essa validação ter sucesso. Workers com validadores recusam o registro a menos que a descoberta anuncie o contrato síncrono de pré-aceitação; rejeição, workers ausentes ou incompatíveis, perda de worker, timeout e conclusão duplicada ou antiga isolada por fencing continuam sendo resultados tipados explícitos. PHP e Rust atualmente não expõem APIs de autoria de validadores e anunciam essa ausência nos contratos de workflow em vez de declarar paridade de validadores.

Ciclo de vida dos handlers​

Validação publicada. O SDK Python 2.6.2 introduziu as proteções de handlers abaixo. Consultas assíncronas e validadores de atualização roteados pelo Server continuam suportados. Veja o escopo corrigido em SDK #177.

Cada replay constrói uma nova instância do workflow antes de executar run(). Sinais já registrados no início do workflow são aplicados depois que run() chega ao primeiro yield; assim, o construtor e a inicialização anterior ao yield acontecem primeiro. Handlers de sinal e atualização modificam esse estado reconstruído. Consultas o inspecionam sem alterar o estado durável; validadores de atualização inspecionam um estado reconstruído descartável antes da aceitação. Coloque comandos duráveis de atividades, timers e workflows filhos em run(), não em um handler.

HandlerForma suportada e resultado de uma falha
@workflow.signalFunção síncrona. Uma exceção ao aplicar o sinal durante o replay faz a execução do workflow falhar.
@workflow.updateFunção síncrona. Uma exceção do handler faz essa atualização falhar.
@workflow.update_validator ou @update_method.validatorFunção síncrona ou async def no Worker. Uma exceção rejeita a atualização antes da aceitação.
@workflow.queryFunção síncrona ou async def no Worker. Uma exceção do handler faz a consulta falhar, não a execução do workflow.

A validação recusa funções de corrotina para sinais e atualizações, e funções geradoras ou geradoras assíncronas para todos os tipos de handlers decorados, inclusive consultas e validadores. Ela lança InvalidWorkflowDefinition na definição, no registro ou no replay, incluindo handlers herdados e ferramentas offline. Wrappers síncronos de sinal e atualização não podem contornar as proteções retornando valores assíncronos. Retornar valores geradores ou geradores assíncronos é recusado para qualquer tipo de handler. Essas restrições não proíbem o gerador síncrono usado por run().

Para uma consulta roteada pelo Server, o Worker aguarda explicitamente o resultado assíncrono sob o prazo original da consulta e a autoridade de claim/cancelamento. A espera não concede um novo orçamento nem permite um resultado após a perda de autoridade. Na validação anterior à aceitação, o Worker também aguarda o resultado assíncrono do validador sobre um estado reconstruído descartável.

Os helpers locais síncronos não podem aguardar. workflow.query_state() recusa um resultado assíncrono com QueryFailed, e workflow.validate_update() o recusa com UpdateRejected. Eles fecham as corrotinas retornadas em vez de deixá-las escapar como resultados das operações.

Compatibilidade de entrada e recuperação​

Suporte publicado. O SDK Python 2.6.2 introduziu a proteção de entrada abaixo, com roteamento e recuperação no Server 2.9.9. Essas são as versões mínimas para esses recursos; instale as versões estáveis atuais para receber correções de segurança.

Antes de chamar run(ctx, *start_input), o worker vincula os argumentos registrados à assinatura de entrada. Um argumento obrigatório ausente ou uma quantidade incompatível de argumentos gera WorkflowEntryArgumentsMismatchError com motivo workflow_entry_arguments_mismatch antes de executar o corpo. Valores padrão preenchem somente argumentos omitidos. As anotações Python continuam sem imposição: mudar uma anotação não valida nem converte os dados registrados. Um TypeError lançado após entrar corretamente no corpo normal ou gerador continua sendo uma falha da aplicação.

O worker anuncia workflow_entry_arguments_validation automaticamente. Com um Server qualificado, a tarefa com falha fica bloqueada para replay, enquanto a execução original permanece não terminal. Runtimes antigos podem repetir essa tarefa; a recusa do SDK sozinha não estabelece o contrato completo de recuperação.

Inspecione a execução exata com await client.describe_workflow_run(workflow_id, run_id) e o endpoint de depuração da execução selecionada. Após restaurar um método de entrada compatível, use a rota HTTP de reparo da execução selecionada no procedimento de recuperação. Já await client.repair_workflow(workflow_id) e handle.repair() resolvem a execução atual da instância; nenhum aceita um argumento de run id. Preserve entrada, histórico, namespace, fila, build e prazos originais. Para alterar comandos, coloque ctx.get_version dentro desse método compatível e valide o replay a frio pelo roteamento de definições.

Tempo do workflow e esperas duráveis​

Durante o replay no worker, ctx.now() retorna o horário de início persistido do run. Ele não avança após uma atividade, temporizador, sinal ou outra etapa durável. Replays a frio do mesmo histórico retornam o mesmo valor inicial. Um sucessor continue-as-new tem seu próprio horário de início e não mantém a referência do relógio do predecessor.

A implementação Python publicada usa WorkflowStarted.payload.timestamp quando presente; caso contrário, usa o valor canônico WorkflowStarted.recorded_at. Um horário persistido ausente ou inválido gera um erro explícito de relógio, sem autorizar a leitura do relógio de parede do worker. Esse é o contrato de início fixo definido no SDK #146.

Aguarde uma operação durável em vez de repetir um laço até ctx.now() mudar:

from durable_workflow import workflow


@workflow.defn(name="wait_without_clock_loop")
class WaitWithoutClockLoop:
    def run(self, ctx):
        started_at = ctx.now()
        yield ctx.start_timer(30)
        return {
            "run_started_at": started_at.isoformat(),
            "after_wait": ctx.now().isoformat(),
        }

A conclusão durável do temporizador retoma o workflow. Os dois horários retornados são o mesmo início. Um laço como while ctx.now() < deadline não passa a falso apenas porque os temporizadores disparam.

Para um atraso relativo, use yield ctx.start_timer(seconds) ou yield ctx.sleep(seconds). Use a seleção da primeira conclusão quando um trabalho precisar disputar com um temporizador durável. Configure execution_timeout_seconds e run_timeout_seconds em client.start_workflow(...) quando o Server precisar impor um prazo ao workflow, inclusive com os workers parados. Um timeout HTTP ou da espera de get_result() limita apenas essa requisição local; ele não substitui o prazo persistido do workflow. Para manter um prazo da aplicação em continue-as-new, passe-o explicitamente como entrada sem substituir o prazo original de execução do Server.

Para medir o tempo decorrido dentro de uma invocação de atividade, leia ali um relógio monotônico e retorne a duração como resultado da atividade. Para um prazo UTC externo, faça uma atividade consultar o relógio externo que é a fonte de autoridade e retornar sua decisão; o workflow reproduz esse resultado registrado. Nunca compare horários UTC com valores monotônicos nem subtraia leituras monotônicas de processos ou hosts diferentes. Subtrair ctx.now() não mede tempo de processamento ativo nem tempo de parede decorrido em Python.

Ordene eventos emitidos com valores de sequência​

Um horário do workflow não é uma chave de ordenação de eventos. Eventos Python marcados com ctx.now() podem ter todos o mesmo horário. Use os offsets de Workflow Streams, a sequência da outbox embutida correspondente ou um contador determinístico local ao workflow. Combine um contador local ao run com run_id; passe-o explicitamente por continue-as-new se a aplicação precisar de uma sequência lógica única. Streams ou runs independentes não ganham uma ordem global a partir de seus horários.

Novas tentativas e timeouts de atividades​

Use ActivityRetryPolicy e argumentos nomeados de timeout em ctx.schedule_activity(...) quando uma chamada precisar de orçamento de novas tentativas ou prazo diferente do comportamento padrão de tentativa única:

from durable_workflow import ActivityRetryPolicy

receipt = yield ctx.schedule_activity(
    "process_payment",
    [validated],
    retry_policy=ActivityRetryPolicy(
        max_attempts=4,
        initial_interval_seconds=1,
        backoff_coefficient=2,
        maximum_interval_seconds=30,
        non_retryable_error_types=["ValidationError"],
    ),
    start_to_close_timeout=120,
    schedule_to_close_timeout=300,
    heartbeat_timeout=15,
)

start_to_close_timeout limita uma tentativa após o worker iniciá-la. schedule_to_close_timeout limita toda a execução da atividade entre todas as tentativas. heartbeat_timeout exige que atividades de longa duração chamem activity.context().heartbeat(...) antes de o intervalo expirar. A política de novas tentativas é capturada na execução durável quando ela é agendada, portanto implantações posteriores não alteram tentativas já em andamento.

ctx.schedule_activity(..., queue="payments-v2") seleciona a fila de uma nova execução de atividade. Atividades já registradas, suas novas tentativas e tarefas reparadas mantêm a fila original. Alterar Worker.task_queue não move essas tarefas nem a fila de workflow das execuções existentes. Mantenha o pool antigo compatível disponível até contabilizar todas as dependências; consulte as filas de atividade registradas.

Regras de determinismo​

O código do workflow é reproduzido do histórico. Não deve realizar diretamente operações não determinísticas:

  • Sem E/S (chamadas HTTP, leitura de arquivos, consultas ao banco)
  • Sem datetime.now() ou time.time(); use ctx.now() apenas como referência fixa do início do run e temporizadores duráveis para esperar.
  • Sem random.random(); use ctx.random()
  • Sem uuid.uuid4(); use ctx.uuid4()

Todo não determinismo deve passar pelo contexto ou ser capturado com ctx.side_effect().

Fan-out​

Produza uma lista de comandos com yield para executá-los concorrentemente:

@workflow.defn(name="fan-out-example")
class FanOutWorkflow:
    def run(self, ctx, *args):
        items = args[0]

        # Nested lists may mix activities, children, and timers.
        results = yield [
            ctx.schedule_activity("process_item", [items[0]]),
            [
                ctx.start_child_workflow("process-batch", [items[1:]]),
                ctx.start_timer(1),
            ],
        ]

        return results  # same nested shape and input order

O worker emite um comando comum por folha durável e anexa os campos estáveis compartilhados parallel_group_* e o caminho completo de fora para dentro. O histórico pode fechar membros em qualquer ordem; o replay ainda vincula resultados e falhas pela posição durável da entrada. Entrega terminal duplicada exata é ignorada. Histórico pendente após reinício e histórico totalmente concluído reconstroem o mesmo grupo sem reagendar trabalho concluído.

Seleção da primeira conclusão​

Use ctx.select() quando trabalho independente deva iniciar junto, mas o workflow possa avançar após a conclusão de um membro:

selected = yield ctx.select({
    "resolver": ctx.schedule_activity("resolve-request", [request_id]),
    "input": ctx.wait_condition(lambda: self.resolution is not None, key="resolution-ready"),
    "deadline": ctx.start_timer(2),
})

if selected.key == "deadline":
    yield selected.handles["resolver"].cancel()
    return {"status": "timed_out"}

yield selected.handles["deadline"].cancel()
return {"status": "resolved", "value": selected.result()}

O SelectionResult inclui chave estável do vencedor, índice da entrada, tipo da operação, identidade durável, resultado tipado e todas as instâncias de DurableOperationHandle. yield handle.await_result() aguarda um não vencedor mais tarde; yield handle.cancel() registra uma solicitação explícita sem valor de retorno. Somente o histórico confirmado SelectionOperationCancelled prova que o cancelamento venceu; o replay avança além de uma solicitação sem marcação, e await_result() ainda retorna uma conclusão confirmada primeiro. O replay consome o vencedor persistido mesmo se o histórico posterior contiver outra conclusão primeiro. Entrega externa duplicada e fora de ordem não pode substituir um vencedor já confirmado.

def forward(saga):

SagaCompensationFailed preserva falha inicial, falha da compensação, tipo de atividade da compensação e ordem determinística de registro como diagnósticos estruturados.

Continuar como novo​

Para workflows de longa duração, use continuar como novo para reiniciar o histórico:

from durable_workflow import ContinueAsNew

@workflow.defn(name="polling-workflow")
class PollingWorkflow:
    def run(self, ctx, *args):
        iteration = args[0] if args else 0

        result = yield ctx.schedule_activity("poll_source", [])

        if result.get("done"):
            return result

        # Continue with incremented iteration
        return ContinueAsNew(arguments=[iteration + 1])

Definir atividades​

Atividades são funções Python assíncronas decoradas com @activity.defn. Diferentemente dos workflows, atividades podem fazer E/S livremente.

from durable_workflow import activity

@activity.defn(name="send_email")
async def send_email(to: str, subject: str, body: str) -> dict:
    # Activities can do I/O: HTTP calls, database queries, etc.
    response = await some_email_client.send(to=to, subject=subject, body=body)
    return {"message_id": response.id, "sent": True}

O name é a chave de tipo compartilhada entre linguagens. Um workflow PHP pode agendar uma atividade chamada "send_email" e um worker Python a executará, e vice-versa.

Contexto da atividade​

Dentro de uma atividade, acesse metadados de execução e heartbeat por activity.context():

@activity.defn(name="long_running_task")
async def long_running_task(items: list) -> dict:
    ctx = activity.context()

    print(f"Attempt #{ctx.info.attempt_number}")
    print(f"Task queue: {ctx.info.task_queue}")

    for i, item in enumerate(items):
        # Check for cancellation
        if ctx.is_cancelled:
            return {"partial": True, "processed": i}

        await process(item)

        # Heartbeat to keep the task alive
        await ctx.heartbeat({"progress": i + 1, "total": len(items)})

    return {"processed": len(items)}

Requisições de heartbeat​

Para atividades remotas, chame await ctx.heartbeat(...) durante trabalho de atividade limitado, bem antes de heartbeat_timeout. A primeira janela começa na reivindicação pelo runtime, antes de o Python receber a tarefa. Cada heartbeat registrado usa o horário em que o runtime o registra, não quando a resposta chega ao Python. Pausas, latência das requisições e novas tentativas de transporte consomem o orçamento. Siga as orientações de cadência.

A chamada direta a Client.heartbeat_activity_task() usa a TransportRetryPolicy configurada. Após essa política, erros de transporte podem se propagar como httpx.TransportError, e recusas HTTP se tornam exceções do SDK, como ServerError. São novas tentativas HTTP, não outra tentativa de atividade nem mais tempo para o heartbeat. ActivityContext.heartbeat() pode lançar ActivityCancelled quando o worker manda a atividade parar. Quando a supervisão cooperativa de processos está ativada, falhas de heartbeat ou de verificação de posse podem parar ou abandonar o callback. Não suponha que toda falha volte a um bloco de captura ou que a limpeza sempre seja executada.

Não suprima falhas de heartbeat ou de posse para continuar trabalho externo ou informar sucesso. Progresso não é um commit externo nem uma confirmação de checkpoint retomável. Mantenha os efeitos externos idempotentes.

Recusas de heartbeat e saída do callback​

No Python SDK 2.9.0, ctx.heartbeat() e ctx.heartbeat_sync() lançam ActivityLeaseAuthorityLost quando uma resposta de heartbeat informa can_continue=false. A exceção preserva o motivo original do Server, como activity_deadline_elapsed, attempt_closed ou run_closed. Uma solicitação de cancelamento lança ActivityCancelled. Consulte a qualificação do SDK publicado.

O heartbeat que observa a recusa é um ponto de saída cooperativa. Interrompa o trabalho externo e propague a exceção; não a capture para retornar sucesso. Código que nunca envia heartbeats pode continuar executando até retornar. Um heartbeat auxiliar não pode interromper à força uma chamada de biblioteca bloqueada: use prazos finitos de E/S e o mecanismo de cancelamento da própria chamada.

O slot físico da atividade permanece ocupado até a saída do callback/thread. Perder a autoridade da tentativa não libera essa thread para outro trabalho, e o worker não publica um resultado tardio da tentativa encerrada. Aplicar o timeout do runtime e parar o código da aplicação são limites distintos. Consulte os timeouts de atividade e a orientação sobre a thread auxiliar.

Erros que não permitem nova tentativa​

Lance NonRetryableError para falhar a atividade sem novas tentativas:

from durable_workflow import NonRetryableError

@activity.defn(name="validate")
async def validate(data: dict) -> dict:
    if "required_field" not in data:
        raise NonRetryableError("Missing required_field")
    return data

Erros de negócio terminais​

non_retryable_error_types compara exatamente o nome curto (exception_type) ou o nome qualificado da classe (exception_class) da exceção externa. Por exemplo, ValidationError não corresponde a SpecificValidationError, mesmo sendo uma subclasse. Um nome qualificado como app.errors.ValidationError precisa corresponder à classe registrada. A política não percorre subclasses nem causas. raise RuntimeError(...) from NonRetryableError(...) informa o RuntimeError externo e ainda pode ser repetido.

Ao converter uma exceção de negócio conhecida, lance NonRetryableError como exceção externa e preserve a causa original do Python com cause=error. Isso marca a falha da atividade como não repetível sem depender de uma lista de nomes. Não faz o workflow inteiro falhar automaticamente: ele recebe ActivityFailed quando não há mais tentativas, por erro não repetível ou pelo esgotamento do orçamento de retries.

from durable_workflow import ActivityFailed, NonRetryableError, activity, workflow

@activity.defn(name="validate_order")
async def validate_order(order: dict) -> dict:
    try:
        if order.get("amount", 0) <= 0:
            raise ValueError("amount must be positive")
    except ValueError as error:
        raise NonRetryableError("Order validation failed", cause=error) from error
    return order

@workflow.defn(name="place_order")
class PlaceOrderWorkflow:
    def run(self, ctx, order: dict):
        try:
            yield ctx.schedule_activity("validate_order", [order])
        except ActivityFailed as failure:
            if (
                failure.activity_type != "validate_order"
                or failure.exception_type != "NonRetryableError"
                or not failure.non_retryable
            ):
                raise
            return {"order_id": order["id"], "status": "rejected"}
        return {"order_id": order["id"], "status": "accepted"}

Com a entrada {"id": "order-123", "amount": 0}, a atividade falha uma vez e o workflow conclui normalmente com status: rejected. Trate apenas a falha de negócio pretendida; o exemplo relança as demais. Continue com outros passos duráveis se o fluxo exigir. Um ActivityFailed não tratado faz o workflow falhar. Preservar uma causa Python não significa que a política examine essa cadeia nem que todos os SDKs exponham um objeto de causa idêntico.

Atividades síncronas e assíncronas​

Atividades remotas comuns com def executam em um pool de threads dedicado, limitado por max_concurrent_activity_tasks. Cada função mantém seu contexto de atividade. O polling, as tarefas de workflow e os heartbeats do worker podem avançar enquanto uma função está bloqueada. Atividades com async def executam no loop de eventos e devem usar E/S não bloqueante. Uma chamada bloqueante dentro de uma função assíncrona também bloqueia esse loop.

Em uma função síncrona, chame activity.context().heartbeat_sync(details) para enviar o progresso pelo loop de eventos responsável, com as identidades originais da tarefa, da tentativa e do worker. Funções assíncronas usam await activity.context().heartbeat(details).

Cancelar uma espera não interrompe uma thread Python que já está executando. Seu slot físico continua ocupado até a função retornar, e um retorno tardio não envia resultado após o cancelamento. Se uma função continuar executando depois de shutdown_timeout, o encerramento lança RuntimeError e mantém o registro do worker. Limite os tempos de espera de E/S dos serviços chamados e use processos de worker isolados para trabalho intensivo de CPU. Consulte a referência de execução e encerramento do SDK.

Heartbeats em uma thread auxiliar​

Para uma chamada longa e bloqueante, capture ctx = activity.context() dentro da atividade síncrona e passe esse contexto à thread auxiliar. Uma nova thread não herda automaticamente o contexto da atividade. Chame ctx.heartbeat_sync(details) na auxiliar, nunca no loop de eventos do worker. Veja o exemplo completo na referência do SDK.

Pare a auxiliar e aguarde seu término com join() quando a chamada retornar ou lançar uma exceção. Se um heartbeat lançar ActivityCancelled ou ActivityLeaseAuthorityLost, sinalize o cancelamento cooperativo à chamada e relance a exceção original antes de retornar um resultado. Uma exceção na auxiliar não interrompe à força uma chamada bloqueada. Defina um prazo finito e um mecanismo de cancelamento para a chamada e limite os tempos e as tentativas das requisições de heartbeat. Caso contrário, a auxiliar pode continuar indicando atividade enquanto o trabalho está travado.

Worker​

O Worker se registra no servidor, faz poll por tarefas e as despacha para suas implementações de workflow e atividade.

Para processos independentes de workflow e atividade, siga o guia executável de separação de processos do SDK Python. Ele cobre registros separados, filas compartilhadas ou distintas, novas tentativas, slots por papel e encerramento gracioso.

from durable_workflow import Client, Worker

async with Client("http://localhost:8080", token="secret") as client:

  • tipos desconhecidos de workflow ou atividade são reportados ao servidor como falhas de tarefa, não ocultados em logs locais
  • NonRetryableError marca falhas de atividade como não retentáveis
  • ActivityCancelled se propaga como resultado de cancelamento
  • exceções não tratadas de atividade são reportadas como falhas retentáveis, a menos que a política de novas tentativas ou prazo do servidor determine o contrário
  • exceções de handlers de consulta são reportadas como QueryFailed

Sessões de worker​

Use WorkerSessionOptions quando atividades remotas sequenciais precisarem de um recurso local do mesmo worker. Este exemplo foi verificado com Python SDK 2.9.0 e Server 2.11.0; consulte os requisitos de versão da afinidade portátil. Use um job_id único por execução do workflow para que uma nova execução não reutilize o identificador de uma sessão terminal.

O cache abaixo é descartável. Cada atividade pode reconstruí-lo a partir da entrada de negócio durável, de modo que o novo titular não dependa da memória do processo anterior:

from durable_workflow import ActivityFailed, WorkerSessionOptions, activity, workflow

# Disposable process-local state. Rebuild it from durable business input.
documents = {}

def ensure_document(job_id):
    rebuilt = job_id not in documents
    if rebuilt:
        documents[job_id] = {"text": "document:" + job_id}
    return documents[job_id], rebuilt

@activity.defn(name="prepare_document")
async def prepare_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id, "rebuilt": rebuilt}

@activity.defn(name="inspect_document")
async def inspect_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id,
            "rebuilt": rebuilt, "text": document["text"]}

@workflow.defn(name="inspect_document_workflow")
class InspectDocumentWorkflow:
    def run(self, ctx, job_id):
        session = WorkerSessionOptions(
            session_id="documents:" + job_id,
            requirements=("fs:documents",),
            lease_seconds=5,
            ttl_seconds=60,
            max_concurrent_activities=1,
            allow_reacquire_after_failure=True,
        )
        options = dict(worker_session=session,
                       start_to_close_timeout=5,
                       schedule_to_start_timeout=12,
                       schedule_to_close_timeout=20,
                       retry_policy={"max_attempts": 1})
        try:
            prepared = yield ctx.schedule_activity("prepare_document", [job_id], **options)
            inspected = yield ctx.schedule_activity("inspect_document", [job_id], **options)
        except ActivityFailed as error:
            if error.activity_type not in {"prepare_document", "inspect_document"}:
                raise
            return {"status": "resource_unavailable", "job_id": job_id}
        return {"status": "inspected", "prepared": prepared, "inspected": inspected}

Registre as duas atividades e declare a capacidade exigida no worker:

from durable_workflow import Worker

worker = Worker(
    client,
    task_queue="documents",
    workflows=[InspectDocumentWorkflow],
    activities=[prepare_document, inspect_document],
    capabilities=["fs:documents"],
)
await worker.run()

Inicie inspect_document_workflow na fila de tarefas documents com [job_id] como entrada. A primeira atividade adquire a sessão de forma tardia; a segunda usa o mesmo titular enquanto o lease estiver válido. max_concurrent_activities=1 limita as atividades simultâneas nessa sessão. O roteamento de fila e as verificações de capacidade continuam valendo. Estes leases/timeouts curtos demonstram comportamento limitado; dimensione-os para o trabalho real e envie heartbeats bem antes da expiração.

Após a perda do titular ou a expiração do lease, allow_reacquire_after_failure=True permite que outro worker apto readquira a sessão. Ele precisa reconstruir o recurso local. Resultados de atividade já confirmados são reproduzidos, mas efeitos não confirmados podem se repetir: use identificadores duráveis e operações externas idempotentes. Uma sessão não migra memória, arquivos ou handles abertos.

O fechamento explícito e a expiração do TTL absoluto são terminais para esse identificador de sessão. Uma atividade posterior não pode reabri-lo e pode continuar sem admissão até que o timeout configurado seja aplicado. Execute a função de agendamento/manutenção do Server da receita de implantação publicada; um processo somente de API não basta para aplicar timeouts. O workflow trata a falha definitiva de atividade com ActivityFailed e retorna resource_unavailable; a aplicação pode então escolher uma sessão nova e reconstruir a partir da entrada de negócio. O exemplo não promete uma exceção imediata de sessão fechada nem reabre automaticamente uma sessão terminal.

Para operações explícitas do ciclo de vida do titular, use worker.worker_session(options) e os métodos create(), renew() e close(reason). O encerramento normal do worker fecha as sessões que ele mantém. Consulte o contrato de ciclo de vida compartilhado.

Cancelamento intencionalmente não é capturado por except Exception​

WorkflowCancelled e ActivityCancelled herdam de BaseException, não de Exception. Um bloco genérico except Exception: no corpo de uma atividade, ou em código aguardando client.get_result(), não as captura. Isso é deliberado: cancelamento é um resultado do plano de controle, e engoli-lo silenciosamente em uma captura geral permitiria a uma atividade informar sucesso depois de o workflow pedir que parasse.

Se uma atividade precisar de limpeza local ao ser cancelada, capture a classe pelo nome e lance novamente. Isso não retoma o workflow fechado para compensação:

from durable_workflow import ActivityCancelled, activity

@activity.defn(name="long_task")
async def long_task(items: list) -> dict:
    ctx = activity.context()
    try:
        for i, item in enumerate(items):
            await process(item)
            await ctx.heartbeat({"progress": i + 1})
        return {"done": True}
    except ActivityCancelled:
        await cleanup_partial_state()
        raise

Isso segue o precedente da biblioteca padrão com asyncio.CancelledError e KeyboardInterrupt.

Testes​

Autores devem poder testar código de workflow sem servidor ou worker em execução. O módulo durable_workflow.testing fornece duas entradas:

  • WorkflowEnvironment conduz um workflow até a conclusão em um único processo Python com mocks de atividades registrados pelo usuário.
  • replay_history e replay_history_file reproduzem um histórico de produção capturado com o código atual e lançam erro em qualquer não determinismo.

Ambas reutilizam o mesmo mecanismo durable_workflow.workflow.replay usado pelo worker em runtime, de modo que um workflow aprovado no ambiente de testes se comporta da mesma forma em um worker real.

WorkflowEnvironment​

WorkflowEnvironment despacha comandos produzidos por yield para mocks registrados e dispara automaticamente temporizadores, efeitos colaterais e upserts de atributos de busca. Testes não precisam de relógio real, Redis ou servidor.

from durable_workflow import workflow
from durable_workflow.testing import WorkflowEnvironment

@workflow.defn(name="greeter")
class Greeter:
    def run(self, ctx, name: str):
        greeting = yield ctx.schedule_activity("greet", [name])
        return greeting


def test_greeter_returns_activity_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("greet", "hello, world")

    result = env.execute_workflow(Greeter, "world")

    assert result == "hello, world"

O ambiente falha explicitamente em fixtures ausentes:

  • agendar uma atividade sem mock registrado lança KeyError
  • iniciar um workflow filho sem mock registrado lança KeyError
  • um workflow que não chega a um estado terminal no limite de iterações (padrão 1000) lança RuntimeError

Passe iteration_limit=... a WorkflowEnvironment(...) para ajustar o teto de workflows que legitimamente iteram mais que o padrão.

Mocks de atividade com callable​

Use register_activity quando o mock precisar responder com base nos argumentos ou registrar chamadas:

def test_callable_mock_captures_arguments() -> None:
    captured: list[str] = []

    def record_greet(name: str) -> str:
        captured.append(name)
        return f"greeted:{name}"

    env = WorkflowEnvironment()
    env.register_activity("greet", record_greet)

    assert env.execute_workflow(Greeter, "alice") == "greeted:alice"
    assert captured == ["alice"]

Sinais​

Sinais enfileirados com env.signal(...) são drenados antes da próxima iteração de replay. O payload é envolvido no mesmo envelope {codec, blob} visto pelo worker em runtime e despachado ao handler @workflow.signal registrado:

@workflow.defn(name="approval")
class Approval:
    def __init__(self) -> None:
        self.approved_by: str | None = None

    @workflow.signal("approve")
    def on_approve(self, by: str) -> None:
        self.approved_by = by

    def run(self, ctx):
        yield ctx.schedule_activity("wait", [])
        return {"approved_by": self.approved_by}


def test_signal_is_delivered_before_run_returns() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("wait", None)
    env.signal("approve", ["alice"])

    result = env.execute_workflow(Approval)

    assert result == {"approved_by": "alice"}

Temporizadores, efeitos colaterais e atributos de busca​

O ambiente dispara automaticamente o evento correspondente de histórico para cada um destes comandos, para que workflows não bloqueiem no relógio real nos testes:

  • ctx.sleep(seconds) → TimerFired
  • ctx.side_effect(...) → SideEffectRecorded
  • ctx.upsert_search_attributes(...) → SearchAttributesUpserted
  • marcadores workflow.version(...) → VersionMarkerRecorded

Cadeias de continuar como novo​

Quando um workflow retorna ctx.continue_as_new(...), o ambiente acrescenta um evento WorkflowContinuedAsNew à execução que termina, reinicia o histórico e inicia uma nova execução com os argumentos do comando. O retorno de execute_workflow é o resultado terminal do último elo.

@workflow.defn(name="countdown")
class Countdown:
    def run(self, ctx, counter: int):
        yield ctx.schedule_activity("emit", [counter])
        if counter > 0:
            return ctx.continue_as_new(counter - 1)
        return {"final_counter": counter}


def test_chain_returns_final_run_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("emit", None)

    result = env.execute_workflow(Countdown, 3)

    assert result == {"final_counter": 0}
    assert env.run_count == 4
    assert [r.input for r in env.runs] == [[3], [2], [1], [0]]

Quando a cadeia troca tipos de workflow, registre primeiro a classe seguinte:

@workflow.defn(name="stage-one")
class StageOne:
    def run(self, ctx):
        yield ctx.schedule_activity("stage_one", [])
        return ctx.continue_as_new(workflow_type="stage-two")


@workflow.defn(name="stage-two")
class StageTwo:
    def run(self, ctx):
        return (yield ctx.schedule_activity("stage_two", []))


def test_chain_can_switch_workflow_type() -> None:
    env = WorkflowEnvironment()
    env.register_workflow(StageTwo)
    env.register_activity_result("stage_one", None)
    env.register_activity_result("stage_two", "done")

    assert env.execute_workflow(StageOne) == "done"
    assert [r.workflow_type for r in env.runs] == ["stage-one", "stage-two"]

Direcione um sinal a um elo específico com run=N:

env.signal("approve", ["alice"], run=2)  # delivered to the second run

O comprimento da cadeia é limitado por continue_as_new_limit (padrão 50). Excedê-lo lança RuntimeError, para que testes detectem continuações fora de controle em vez de executar indefinidamente; ajuste com WorkflowEnvironment(continue_as_new_limit=...) quando uma cadeia for legitimamente maior.

Asserções de falha​

Workflows que lançam uma exceção Python aparecem como WorkflowFailed:

import pytest
from durable_workflow.errors import WorkflowFailed

@workflow.defn(name="failing")
class Failing:
    def run(self, ctx):
        yield ctx.schedule_activity("step", [])
        raise RuntimeError("boom")


def test_workflow_failure_surfaces_as_workflow_failed() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("step", None)

    with pytest.raises(WorkflowFailed) as exc_info:
        env.execute_workflow(Failing)

    assert "boom" in str(exc_info.value)

Testes de replay com histórico de produção​

Use replay_history para testar regressões de uma mudança com histórico real capturado do servidor. O replayer executa o código atual contra a sequência registrada e lança erro se produzir comando diferente do registrado, a definição de um bug de não determinismo.

from durable_workflow import Client
from durable_workflow.testing import replay_history

async with Client("http://localhost:8080") as client:
    history = await client.get_history("order-42", run_id="...")

replay_history(OrderWorkflow, history["events"], start_input=["order-42"])

Um workflow que concluiu antes deve continuar concluindo com o mesmo histórico. Se o código divergir da sequência registrada (chamadas reordenadas de atividades, ramos removidos ou tipos alterados), replay_history lança erro para detectar a regressão na CI em vez de produção.

replay_history_file é um wrapper que lê um arquivo JSON em dois formatos: lista de eventos no topo ou dict com chave events correspondente à resposta de get_history:

from durable_workflow.testing import replay_history_file

replay_history_file(
    OrderWorkflow,
    "tests/histories/order-42.json",
    start_input=["order-42"],
)

Ambas as funções aceitam uma indicação opcional de validação payload_codec. Deixe-a sem valor para usar a tag registrada no histórico. Uma tag explícita ou registrada deve ser avro; payloads duráveis json, desconhecidos ou sem tag falham antes de decodificar.

Replayer baseado em classe​

Quando uma passagem de teste reproduzir históricos de vários tipos ou quando o evento capturado WorkflowStarted deva decidir qual workflow reproduzir, use a classe Replayer. Registre previamente todas as classes e chame replay(...) uma vez por histórico capturado:

from durable_workflow import Replayer, ReplayOutcome

replayer = Replayer(workflows=[OrderWorkflow, RefundWorkflow])

# Explicit type and input — equivalent to replay_history(OrderWorkflow, ...).
outcome: ReplayOutcome = replayer.replay(
    history["events"],
    start_input=["order-42"],
    workflow_type="order",
)

# Type and start input inferred from a WorkflowStarted event in the history.
outcome = replayer.replay(history)  # history may be an events list or a
                                    # dict with an "events" key

for command in outcome.commands:
    # Inspect commands the replayed workflow would have emitted next.
    ...

Replayer(workflows=[...]) rejeita conjunto vazio ou registro duplicado com ValueError. replay(...) lança ValueError quando o histórico pede tipo não registrado ou quando há vários workflows registrados, o chamador não fornece workflow_type e o histórico não contém WorkflowStarted.

ReplayOutcome.commands é a mesma lista retornada pelos auxiliares funcionais replay_history; a entrada baseada em classe existe para uma suíte compartilhar um registro entre muitos históricos.

Codec de payload​

Todo payload que cruza o limite do protocolo de workers tem uma tag de codec. O Durable Workflow 2.0 tem um único codec público de payload: avro. O SDK Python rejeita payloads duráveis com tag JSON, desconhecidos e sem tag em vez de selecionar outro decodificador. Veja o protocolo Avro Value.

O suporte a Avro é integrado​

O artefato fixado do SDK 2.0 inclui fastavro como dependência de runtime, portanto toda interface de saída (start_workflow, signal_workflow, query_workflow, update_workflow, codificação de resultado de atividade, ações de agendamento) emite payloads com tag Avro pelo caminho otimizado de produção. Não há extra opcional de codec a instalar.

Valores tipados fixos​

O SDK seleciona explicitamente variantes nomeadas no schema compartilhado durable_workflow.protocol.Value. Não codifica o valor em JSON dentro de Avro. Assim, inteiros e doubles, strings e bytes, booleanos e inteiros e listas e mapas permanecem distintos entre SDKs. A transmissão usa frames de objeto único Avro e o fingerprint do schema; fingerprints desconhecidos falham com unsupported_payload_schema.

Toda interface de cliente e worker funciona de ponta a ponta com o padrão Avro:

  • Inícios, sinais, consultas e atualizações do cliente: start_workflow, signal_workflow, query_workflow e update_workflow emitem payloads payload_codec = "avro" pelo schema Value fixo. Um cliente Python pode conduzir workflows que PHP e outros SDKs poliglotas reproduzirão e vice-versa.
  • Worker de atividade: argumentos com tag Avro decodificam transparentemente. O worker codifica resultados em Avro para que PHP, Python e futuros SDKs compartilhem um limite de payload.
  • Falhas de atividade: fail_activity_task(..., details=...) envia failure.details como envelope {codec, blob}. O servidor registra o blob e details_payload_codec, mantendo dados de diagnóstico Python independentes de linguagem em exportações e visualizações de observabilidade.
  • Replay de histórico do worker de workflow: entradas iniciais e eventos de resultado de atividade com tag Avro são decodificados no replay, permitindo que um workflow Python participe de uma execução codificada em Avro.
  • Tarefas de consulta de workflow: consultas roteadas pelo servidor contêm argumentos de workflow, argumentos de consulta e histórico de replay com tag Avro. O worker retorna o resultado da consulta como envelope Avro.

Executar um worker de atividade Python em uma execução v2​

Nenhuma configuração de codec é necessária. O SDK valida payload_codec antes de decodificar cada reserva, aceita somente avro, executa a atividade e retorna um resultado com tag Avro. Qualquer outra tag é rejeitada com unsupported_payload_codec; o worker nunca inspeciona o conteúdo para adivinhar o formato.

Executar em um servidor compartilhado​

O Início rápido acima mostra como iniciar um servidor local com a imagem Docker publicada. Em equipe, normalmente você aponta o worker Python para um servidor existente (staging, produção ou desenvolvimento compartilhado):

from durable_workflow import Client

client = Client(
    "https://workflow.example.internal",
    control_token="team-orders-operator-token",
    worker_token="team-orders-worker-token",
    namespace="team-orders",
)

Defina namespace para o namespace de tenant provisionado para sua equipe no servidor compartilhado e use as credenciais emitidas para ele. O operador do Server gerencia a criação de namespaces; veja o guia do Server para detalhes.

O mesmo construtor suporta um runtime gerenciado do Cloud. Use a URL de runtime e o valor de namespace fornecidos pelo Cloud, defina control_token para a credencial de runtime de cliente e worker_token para a de worker. O Cloud provisiona o namespace; não substitua por um endereço de Server sob sua administração. Veja Runtime gerenciado do Cloud.

Páginas de lista e histórico de workflows​

Estas chamadas publicadas retornam uma página, não uma leitura completa automática: await client.list_workflows(...) / await client.get_history(workflow_id, run_id, ...). Continue com o token opaco retornado preservando namespace, filtros e workflow/execução selecionados; encerre no token nulo/vazio e trate erros de página. Uma página parcial não é um bundle de replay. Use a API de exportação de histórico do SDK para replay sem servidor. O cliente publicado Python 2.9.0 define os parâmetros atuais; não se afirma um novo iterador.

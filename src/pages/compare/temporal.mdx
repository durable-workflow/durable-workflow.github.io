# Durable Workflow vs Temporal

**Durable execution inside your application, or a dedicated workflow service.**

Durable Workflow and Temporal let you express long-running processes as code,
record their progress, and recover execution after a worker fails. The important
difference for a Laravel team is where that engine lives.

Durable Workflow can run **inside your Laravel application**, using its database,
queue workers, and deployment. It also runs as a standalone Server for PHP,
Python, and Rust applications. Temporal uses a separate service with SDK workers
and a broader language ecosystem.

Durable Workflow's approach is **predictable cost, predictable behavior, and
predictable operations**: choose the infrastructure you operate, make durable
steps explicit, and inspect the history when something goes wrong.

*By the Durable Workflow maintainers. Updated September 21, 2026.*

## Architecture at a glance

| Decision | Durable Workflow | Temporal |
| --- | --- | --- |
| Where the engine lives | Embedded in Laravel, or deployed as standalone Server. | A dedicated Temporal Service, separate from application workers. |
| PHP execution | Laravel queue workers in embedded mode; a PHP SDK worker process in service mode. | PHP workers managed through RoadRunner. |
| PHP authoring | Straight-line methods with Fiber-backed durable calls. | Generator-based workflow methods with yielded durable operations. |
| Service-mode SDKs | PHP, Python, and Rust. | Go, Java, .NET, PHP, Python, Ruby, Rust, and TypeScript. |
| Recovery model | Recorded history and deterministic workflow replay. | Recorded history and deterministic workflow replay. |

## Keep workflows inside Laravel

For a Laravel application, embedded Durable Workflow adds durable execution to
the stack your team already operates. Activities can use application services
through Laravel's container. Workflow state lives in your database, and Laravel
queue workers execute workflow and activity tasks.

That means one application deployment and no separate orchestration service.
You still manage the database, queue capacity, backups, and recovery, but they
remain part of your existing Laravel operations. The
[installation guide](/docs/installation/) and
[execution model](/docs/how-it-works/) show that setup.

A dedicated service is useful when orchestration needs an independent deployment
and lifecycle. Durable Workflow supports that too:
[Server](/docs/polyglot/server/) exposes the engine to external SDK workers.
A Python- or Rust-only application can use it without adopting Laravel.

## Straight-line PHP, without RoadRunner

Durable Workflow's PHP SDK uses a managed Fiber. Calling
`$context->activity(...)` suspends workflow execution until the durable result is
available; the method then continues with that result. Your workflow remains a
straight-line PHP method with an ordinary return type. There are no `yield`
statements or Generator return types to carry through your workflow code.

The SDK worker runs directly as a PHP process: `php worker.php`. You do not need
RoadRunner to host it. In a Laravel service-mode application, the first-party
bridge also connects your handlers to the application's container and logger.

Temporal's [PHP workflow API](https://docs.temporal.io/develop/php/workflows/basics)
expresses suspension through generators and `yield`. Its
[PHP worker setup](https://docs.temporal.io/develop/php/set-up-your-local-php)
uses RoadRunner to manage workers and connect them to Temporal Service.

## Predictable behavior through replay

Both engines rebuild workflow state from recorded history. Completed activity
results are replayed into workflow code rather than repeating that completed
work. Workflow decisions therefore need to remain deterministic: put network
calls and database effects in activities, and use the engine's durable timer
and time APIs.

The mechanics are described in
[How Durable Workflow works](/docs/how-it-works/) and
[Temporal workflow replay](https://docs.temporal.io/workflow-execution#replays).
This is the common foundation that makes either engine useful for processes
that must survive worker restarts.

Activity delivery is a separate concern. A worker can perform an external action
and fail before reporting its result, so a retry may repeat that action. Use an
idempotency key for payments and other external effects. Durable Workflow
provides a stable logical activity execution identity across attempts; see
[execution guarantees](/docs/constraints/execution-guarantees/).
Temporal likewise recommends
[idempotent activities](https://docs.temporal.io/activities).

For deployment confidence, test workflow changes against recorded history as
well as testing activity business logic. Durable Workflow provides
[embedded test fakes](/docs/testing/) and
[PHP SDK replay tests](https://php.durable-workflow.com/build/testing/).
Temporal documents its
[PHP unit and integration testing tools](https://docs.temporal.io/develop/php/best-practices/testing-suite).

## Predictable operations when self-hosting

| Deployment | What you operate |
| --- | --- |
| Durable Workflow embedded | Your Laravel app, database, queue consumers, and lock-capable cache. |
| Durable Workflow Server | The Server API and background processes, persistence and queue/cache services, plus application SDK workers. |
| Temporal Service | Temporal Server, persistence and visibility stores, plus application SDK workers. |

The Durable Workflow [published Compose setup](/docs/polyglot/server/#published-image--compose)
uses MySQL and Redis. Its local quickstart also supports SQLite.
Temporal's [self-hosting guide](https://docs.temporal.io/self-hosted-guide)
covers deployment options, and its
[PHP quickstart](https://docs.temporal.io/develop/php/set-up-your-local-php)
starts a local development service through the Temporal CLI.

For production, the ownership choice matters more than a local startup command.
Embedded execution shares the application's infrastructure and failure domain.
A separate service lets you operate orchestration independently, while adding a
service boundary to deploy, secure, and monitor.

**Predictable cost starts with that ownership decision.** The
[Durable Workflow engine](https://github.com/durable-workflow/workflow/blob/main/LICENSE),
[Server](https://github.com/durable-workflow/server/blob/main/LICENSE), and
[Temporal Server](https://github.com/temporalio/temporal/blob/main/LICENSE)
are MIT-licensed. Self-hosting either engine has no per-action software fee.
Your costs are infrastructure and the work of operating it. Embedded Durable
Workflow can reuse a Laravel stack you already maintain; additional execution
and retained history still consume resources.

## Which engine fits your team?

**Choose Durable Workflow** when you want durable execution integrated into
Laravel, Fiber-based PHP workflows without RoadRunner, or a standalone engine for PHP,
Python, and Rust workers. Its embedded option is particularly useful when your
team wants workflow infrastructure to remain part of the application it already
knows how to deploy and recover.

**Choose Temporal** when you want a dedicated orchestration service and its
broader SDK coverage, especially for Go, Java, .NET, Ruby, or TypeScript
applications. Existing Temporal tooling and team expertise are also good
reasons to stay with that execution model.

**Start building:** [install embedded Durable Workflow](/docs/installation/),
[run standalone Server](/docs/polyglot/server/), or
[follow Temporal's PHP quickstart](https://docs.temporal.io/develop/php/set-up-your-local-php).

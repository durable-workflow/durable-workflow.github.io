プラットフォームプロトコル仕様

プラットフォームプロトコルカタログは、Durable Workflow の各公開インターフェースをどの機械可読仕様が規定するかを、SDK 作者、エージェント、運用者、サードパーティツールに正確に伝えます。

自動化には機械可読カタログを使用してください。利用可能な各エントリは、安定した仕様識別子と、OpenAPI、AsyncAPI、JSON Schema の成果物を直接取得できる公開 HTTPS URL の両方を提供します。

リポジトリのパス、実装シンボル、テストフィクスチャは、意図的に利用者向けの規範としていません。公開カタログから除外し、検証の診断情報としてだけ保持しています。

カタログの識別情報と検出​

機械可読の規範は /platform-protocol-specs.json に、スキーマ durable-workflow.v2.platform-protocol-specs.catalog、バージョン 16 として公開されています。

カタログは次からも利用できます。

  • https://durable-workflow.github.io/platform-protocol-specs.json の公開 JSON カタログ
  • スタンドアロン Server の GET /api/cluster/info にある platform_protocol_specs
  • 人が理解するための背景を提供する、この 2.0 ガイド

JSON URL は機械が利用するカタログの規範となる情報源です。Server は同じカタログを再公開するため、クライアントはリポジトリ構成を仮定せずに、有効なプロトコルインターフェースを検出できます。

Worker プロトコルの規範の役割

ランタイム検出と適合性検証では、別々のプロトコル規範を使います。行う作業に合った行を選んでください。バージョン表記が同じでも、過去のバージョン付きリゾルバーが、バージョンなしの Server 規範の別名になるわけではありません。

役割現在のマーカーリゾルバーの規範
現在公開されている Server プロトコルworker_protocol.version = 1.20Server を正本とするバージョンなしのミラー： OpenAPI · AsyncAPI
現在の Workflow 適合性検証の対象スイート 47 の対象はプロトコル 1.19バージョンとダイジェストで固定されたフィクスチャ： OpenAPI · AsyncAPI
保持されている過去の適合性の対応関係プロトコル 1.13, 1.15, 1.16, 1.17, 1.18 について historical と記された対応関係不変のリゾルバーとダイジェストの記録： 適合性マニフェスト

利用者向けフィールド​

各エントリは次の契約を公開します。

フィールド意味
spec_id安定した Durable Workflow プロトコル識別子。公開ドキュメントは対応する識別情報を持ちます。
spec_url機械可読仕様への直接の公開 HTTPS URL。
formatopenapi、json_schema、または asyncapi。
status参照する成果物が公開済み、作業中、計画中のいずれであるか。
surface_familyインターフェースを規定する互換性ポリシーの分類。
authority_manifestランタイムがそのインターフェースを通知する検出マニフェスト。
owner_repo仕様を担当するプロジェクト。
object_families公開オブジェクト分類名と担当プロジェクト。
evolution_rule追加変更と破壊的変更の互換性ルール。
breaking_change_releaseその進化ルールが要求するリリース境界。

利用者は spec_url を解決し、ドキュメントの識別情報が spec_id と一致することを検証してください。ソースチェックアウトへのアクセスは必要ありません。

Worker セッションランタイムの補足​

このスキーマは、Worker セッションの機能検出、ライフサイクルエンベロープ、タスクアフィニティのスナップショット、運用者向け可視性を対象にします。安定した識別子は durable-workflow.v2.worker-sessions-runtime です。

ローカルアクティビティランタイムの補足​

このスキーマは、ローカルアクティビティの機能検出、オプションのスナップショット、履歴マーカー、リトライの意味、運用者向け可視性を対象にします。安定した識別子は durable-workflow.v2.local-activity-runtime です。

Cluster-info エンベロープの補足​

このスキーマは、GET /api/cluster/info と、そのエンドポイントから利用できる入れ子の検出マニフェストを対象にします。安定した識別子は durable-workflow.v2.cluster-info-envelope です。

形式​

形式用途
OpenAPI 3.1ルート、メソッド、ステータスコード、エンベロープが契約の一部である HTTP・JSON リクエスト/レスポンスのインターフェース。
JSON Schema 2020-12永続化レコード、イベントペイロード、結果エンベロープ、ランタイムオプション、関連オブジェクト分類。
AsyncAPI 2.6 以降ポーリング、ストリーム、リース更新、順序、配信の意味。

ステータスの段階​

ステータス意味
published公開の機械可読仕様が spec_url にあり、直接利用できます。
in_progress公開仕様はありますが、対象範囲は部分的です。列挙されたフィールドとルートは規範です。
planned安定したカタログ識別情報はありますが、利用可能な仕様はまだありません。計画中のエントリは spec_url を通知しません。

進化ルール​

additive_minor_breaking_major は、マイナーリリースでの追加変更を認めます。削除、名前変更、型の制限、意味の変更にはメジャーリリースが必要であり、実用的な場合は並行するルートやフィールドを使うべきです。

parallel_primitive_only は、固定されたワイヤ形式を規定します。元の形式をデコード可能なまま保ち、破壊的な形式変更は新しいイベント型、コマンド型、スキーマ識別子の下で導入しなければなりません。

experimental_any_release は、実験的であると明示した仕様にだけ適用し、任意のリリースでの変更を認めます。

リリース検証​

ドキュメントサイトの CI は、次の機械チェックを実施します。

ゲートCI が確認する内容
catalog_aligned_with_surface_families各エントリが宣言済みの公開互換性分類を参照する。
owner_repo_knownエントリとオブジェクト分類の担当が、カタログの語彙を使う。
format_known利用可能な各成果物を宣言された形式として解析できる。
public_spec_references_resolve利用可能な各 spec_url が公開プロトコル仕様の名前空間内の HTTPS URL であり、spec_id と一致する識別情報を持つ配布済み成果物に解決する。
repository_local_authority_fields_rejected公開エントリに、リポジトリ内のパス、実装シンボル、テスト参照、古い規範フィールドが含まれない。
workflow_package_mirror_aligned当該リリース入力が利用できる場合、公開カタログがパッケージ化された Workflow カタログと一致する。
server_owned_spec_mirrors_aligned入力が利用できる場合、Server 所有の公開成果物が担当リポジトリのミラーと一致する。
diagnostic_provenance_complete検証専用の由来情報が、全カタログエントリとオブジェクト分類を網羅する。
object_family_metadata_declaredカタログエントリと公開ドキュメントで、オブジェクト分類名と担当が一致する。
rendered_retrieval_surfaces_alignedビルド済み 2.0 ページと完全な 2.0 モデル取得バンドルが、利用可能な各エントリのカタログ識別情報、公開 URL、オブジェクト分類の担当を公開する。
breaking_change_release_consistent_with_evolution_ruleすべての破壊的変更リリース値が進化ルールと一致する。
deliverable_specs_published必須の全プラットフォームインターフェースに、公開済みで解析可能な仕様がある。

機械チェックは公開 JSON カタログを読み込み、語彙と利用者に安全な参照を検証し、配布済み仕様を解析し、オブジェクト分類と埋め込みスキーマのメタデータを確認し、利用可能な場合はパッケージミラーを比較します。サイトとモデル用バンドルの生成後、意味に基づくチェックが、描画されたカタログ値を同じ JSON の規範と比較します。ドキュメントの文章や見出しは比較対象ではありません。

契約が変わる場合は、パッケージ化された Workflow カタログ、この公開 JSON ミラー、影響する公開仕様成果物をまとめて更新してください。人によるレビューでは、説明文を機械の規範とせずに、有用性が保たれていることを確認します。

続いてプラットフォーム適合性スイートで、これらのプロトコル仕様を実行検証する、現在有効なバイト列に結び付いたフィクスチャを解決してください。過去のフィクスチャの証拠はスイート内で別に識別され、現在のカタログの規範に代わるものではありません。

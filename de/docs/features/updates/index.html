Updates

Updates ermöglichen es, Informationen über den aktuellen Workflow-Zustand abzurufen und ihn gleichzeitig zu verändern. Sie verbinden im Wesentlichen eine Abfrage und ein Signal in einer Operation.

Explizite Update-Befehle​

Jedes angenommene Update:

  • ist ein Anfrage-Antwort-Aufruf an einen laufenden Workflow. attemptUpdate*() wartet auf den Handler-Abschluss. submitUpdate*() kehrt nach dauerhafter Befehlsannahme zurück und bietet mit inspectUpdate($updateId) spätere Statusabfragen;
  • verwendet den deklarierten dauerhaften Updatenamen in Befehlshistorie und Webhook-Routing. #[UpdateMethod('mark-approved')] hält den öffentlichen aufrufbaren Namen über PHP-Methodenumbenennungen hinweg stabil;
  • wird für historische oder bereits geschlossene Läufe abgelehnt, statt still den aktuellen Lauf zu verändern;
  • lehnt nicht deklarierte Methodennamen als rejected_unknown_update und vertragswidrige Argumente als rejected_invalid_arguments (mit maschinenlesbaren validation_errors) vor Ausführung des Handlers ab.

Wie Abfragen spielen Updates zuerst festgeschriebene Historie erneut ab. Anders als Abfragen dürfen sie Replay-sicheren Workflow-Zustand ändern und einen Wert zurückgeben.

Deklarieren Sie eine Update-Methode am Workflow mit UpdateMethod. Das optionale Zeichenfolgenargument legt einen dauerhaften öffentlichen Namen fest, der PHP-Methodenumbenennungen übersteht:

use Workflow\UpdateMethod;
use Workflow\V2\Workflow;

final class MyWorkflow extends Workflow
{
    private bool $ready = false;

    #[UpdateMethod('mark-ready')]
    public function updateReady(bool $ready): bool
    {
        $this->ready = $ready;

        return $this->ready;
    }
}

Rufen Sie die Update-Methode für den reinen Rückgabewert direkt auf:

use Workflow\V2\WorkflowStub;

$workflow = WorkflowStub::load('order-123');

$ready = $workflow->updateReady(true);

Dieser direkte PHP-Aufruf verwendet weiterhin den Methodennamen. Das dauerhafte Befehlsziel bleibt mark-ready.

Verwenden Sie attemptUpdate(), wenn Sie auch das dauerhafte Befehlsergebnis benötigen. Übergeben Sie dort den dauerhaften Updatenamen:

use Workflow\V2\WorkflowStub;

$workflow = WorkflowStub::load('order-123');

$result = $workflow->attemptUpdate('mark-ready', true);

$result->accepted();        // true
$result->completed();       // true when the update body ran successfully
$result->updateStatus();    // "accepted", "completed", "failed", or "rejected"
$result->updateId();        // Durable update lifecycle id
$result->result();          // Raw update return value when completed
$result->failureMessage();  // Failure message when the update body threw

attemptUpdate() zeichnet zuerst das angenommene Update auf und wartet dann, bis der Workflow-Worker es anwendet und seinen Lebenszyklus schließt. Die Wartezeit wird durch workflows.v2.update_wait.completion_timeout_seconds begrenzt. Hat der Worker das Update bei Ablauf des Budgets nicht geschlossen, gibt attemptUpdate() den angenommenen Lebenszyklus mit waitTimedOut() === true und updateStatus() === 'accepted' zurück.

Verwenden Sie withUpdateWaitTimeout(), wenn ein Aufruf ein anderes Abschlussbudget benötigt:

use Workflow\V2\WorkflowStub;

$workflow = WorkflowStub::load('order-123')
    ->withUpdateWaitTimeout(5);

$result = $workflow->attemptUpdate('mark-ready', true);

Verwenden Sie attemptUpdateWithArguments(), wenn bereits eine positionale Liste oder eine Zuordnung benannter Parameter vorliegt:

$result = $workflow->attemptUpdateWithArguments('mark-ready', [
    'ready' => true,
]);

Benannte Zuordnungen werden gegen den dauerhaft gespeicherten Update-Vertrag validiert und vor Annahme in Deklarationsreihenfolge normalisiert.

Verwenden Sie submitUpdate() oder submitUpdateWithArguments(), wenn der Aufrufer nur dauerhafte Annahme benötigt und die spätere Anwendung durch den Workflow-Worker akzeptiert:

$accepted = $workflow->submitUpdate('mark-ready', true);

$accepted->accepted();     // true
$accepted->completed();    // false
$accepted->updateStatus(); // "accepted"
$accepted->result();       // null until the worker records UpdateCompleted

Verwenden Sie inspectUpdate(), wenn bereits eine update_id vorliegt und Sie den gespeicherten Lebenszyklus später ohne erneutes Warten lesen möchten:

$latest = $workflow->inspectUpdate($accepted->updateId());

$latest->updateStatus(); // "accepted"
$latest->closedAt();     // null until the lifecycle closes

inspectUpdate() wartet nicht auf Workflow-Ausführung. Es lädt den gespeicherten dauerhaften Lebenszyklus neu und gibt das aktuelle UpdateResult zurück.

Nach einer ungewissen Antwort wiederherstellen​

Dauerhafte Annahme, Handler-Abschluss und ein externer Geschäftseffekt sind getrennte Tatsachen. Nach einem Aufrufer-Timeout kann ein angenommenes Update weiterlaufen. Eine verlorene Antwort kann ein bereits festgeschriebenes Ergebnis verbergen. Die spätere Ablehnung eines neuen Updates klärt das ursprüngliche Ergebnis nicht.

Hat Ihre Anwendung eine Update-ID gespeichert, untersuchen Sie diesen aufbewahrten Lebenszyklus, statt ein weiteres Update einzureichen. Bewahren Sie die ursprüngliche Lauf-ID auf, damit Continue-as-new die Untersuchung nicht umleitet:

use Workflow\V2\WorkflowStub;

$latest = WorkflowStub::loadRun($savedRunId, $savedNamespace)->inspectUpdate($savedUpdateId);

$latest->updateStatus();
$latest->result(); // Available when that retained update completed.

Die gespeicherten IDs stammen aus der ursprünglichen Operation. Die Untersuchung liest den aufbewahrten Datensatz und kann auch nach Abschluss oder Historischwerden dieses Laufs funktionieren. Fehlende oder bereinigte Nachweise lassen das Ergebnis ungeklärt. Sie erlauben nicht das Wiederholen eines Geschäftseffekts. Bewahren Sie einen anwendungseigenen Operationsdatensatz zum Abgleich auf, falls ursprüngliche Antwort und erzeugte Update-ID verloren gingen.

Anfrage-IDs und aufbewahrte Belege​

Speichern Sie Namespace, Instanz-ID, ursprüngliche Lauf-ID, Update-ID, Operationsnamen und beabsichtigte Wirkung in Ihrem Anwendungsdatensatz. Ein Annahmebeleg beweist dauerhafte Annahme. Ein abgeschlossener Lebenszyklus liefert das aufgezeichnete Handler-Ergebnis. Keiner beweist, dass eine separate Zahlung, E-Mail oder Datenbankschreiboperation genau einmal stattfand.

Eingebettete Laravel-Update-Webhooks lesen den Aufruferschlüssel aus X-Request-Id. Erhalten Sie diesen Header beim Weiterleiten durch Proxys. HTTP-Updates des eigenständigen Servers lesen den Schlüssel dagegen nur aus request_id im JSON-Body; ihr Header X-Request-Id dient der Korrelation. Ohne Body-Schlüssel hat das Update keinen Deduplizierungsschlüssel, auch wenn mehrere Anfragen denselben Header verwenden.

request_id ist kein portabler, laufbezogener Update-ID-Vertrag. Die geprüften PHP-Pfade können bei demselben Schlüssel mit anderen Argumenten oder Updatenamen innerhalb der Instanz das erste aufbewahrte Update zurückgeben. Das Wiederverwenden eines Schlüssels nach Continue-as-new kann das Ergebnis eines Vorgängers liefern, ohne ein Update am Nachfolger anzunehmen. Ein aufbewahrter schlüsselbezogener Beleg kann auch nach Abschluss zurückgegeben werden, während ein neues Update abgelehnt wird.

Verwenden Sie einen Schlüssel für eine logische Operation und erhalten Sie deren ursprüngliche Absicht. Ändern Sie nicht die Argumente, verwenden Sie ihn nicht für einen anderen Updatenamen und nehmen Sie nicht an, dass er im nächsten Lauf eine neue Operation startet. Die Prüfung der veröffentlichten PHP-Artefakte belegt Aufruferschlüssel unabhängig von Proxy-Headern und aufbewahrte Belege nach Abschluss. Dieses Wiederherstellungsverhalten garantiert keine portable Konflikterkennung bei gleichem Schlüssel und anderer Absicht. Dieser umfassendere Vertrag wird in Issue 216 verfolgt. Native Server- und andere SDK-Pfade benötigen eine eigene Qualifikation.

Die Wiederherstellung von Belegen hängt von aufbewahrten Befehls-, Update- und Historiendatensätzen ab. Es wird hier keine anwendungsunabhängige Deduplizierungsdauer versprochen. Prüfen Sie die Historienaufbewahrung und bewahren Sie Ihr Geschäftsbuch für die von Ihrer Anwendung benötigte Dauer auf. Fehlende Nachweise bedeuten weiterhin ein unbekanntes Ergebnis.

Den Geschäftseffekt schützen​

Für eine Operation wie das Belasten einer Rechnung:

  1. Speichern Sie vor dem Senden einen Anwendungs-Operationsschlüssel wie tenant-1:charge:invoice-123 und seine unveränderliche Absicht. Verwenden Sie diesen Schlüssel bei der Wiederherstellung erneut.
  2. Verwenden Sie in der ausführenden Aktivität eine eindeutige Datenbankbedingung für Mandant und Operationsschlüssel. Prüfen Sie die gespeicherte Absicht atomar, wenden Sie den lokalen Datenbankeffekt an und speichern Sie sein Ergebnis in einer Transaktion. Geben Sie bei einem Duplikat mit gleicher Absicht das gespeicherte Ergebnis zurück. Lehnen Sie eine andere Absicht ab.
  3. Verwenden Sie bei externen Anbietern deren unterstützten Idempotenzvertrag oder eine Outbox mit Abgleichprozess. Eine Transaktion in Ihrer Datenbank kann einen separaten Anbieteraufruf nicht atomar machen.
  4. Gleichen Sie nach einer ungewissen Antwort Operationsdatensatz, ursprünglichen Update-Lebenszyklus und Anbieternachweise ab. Dokumentieren Sie vor einer weiteren Aktion, ob der Effekt aussteht, festgeschrieben, fehlgeschlagen oder weiter unbekannt ist.

Eine Abfrage mit anschließendem Befehl lässt ein Rennen offen. Ein doppeltes Signal kann eine weitere Aktivität auslösen, auch wenn das ursprüngliche angenommen wurde. Die Anwendungssicherung muss wiederholte Zustellung vertragen. Das geprüfte Beispiel führt zwei Aktivitäten für denselben Schlüssel aus, schreibt aber nur einen lokalen Datenbankeffekt fest. Es belegt keine Genau-einmal-Ausführung für beliebige externe Systeme.

Update-Regeln:

  • load($instanceId) aktualisiert den neuesten dauerhaften Lauf dieser Instanz, auch nach Continue-as-new.
  • Neue Updates über loadRun($runId) werden mit rejected_not_current abgelehnt, sobald der ausgewählte Lauf historisch ist. Die Untersuchung aufbewahrter Belege ist davon getrennt.
  • Neue Updates gegen geschlossene Läufe werden mit rejected_not_active abgelehnt. Das Wiedergeben aufbewahrter schlüsselbezogener Belege ist davon getrennt.
  • Fehlgeschlagene Update-Rümpfe schließen den Workflow-Lauf nicht. Sie werden als Update-bezogene Fehler aufgezeichnet und lassen den Lauf für die nächste Replay-Aufgabe offen.
  • Abfragen spielen abgeschlossene Updates erneut ab. Abgelehnte oder fehlgeschlagene Updates bleiben ausschließlich nicht erneut abspielbare Befehls- und Historienfakten.

Fähigkeitsübersicht für Durable Workflow 2.0

Dies ist die Fähigkeitsübersicht für die stabile Durable-Workflow-2.0-Versionslinie.

Unterstützter installierbarer Kanal​

Genaue Artefaktidentitäten gehören in Paketregistries und Veröffentlichungsmetadaten, nicht in diese Fähigkeitszusammenfassung.

SchnittstelleUnterstützter KanalRolle in dieser Übersicht
CLI2.0 stabilMaschinenlesbarer Operator- und Diagnoseclient.
PHP-SDK2.0 stabilOffizieller Dienstmodus-Client durable-workflow/sdk und entfernter Workflow-/Aktivitäts-Worker für eine Cloud-Namespace-Laufzeit oder einen selbst gehosteten Server.
Eingebettete Laravel-Engine2.0 stabilSeparater Bereitstellungsmodus innerhalb der Anwendung mit durable-workflow/workflow, eigener Programmierlaufzeit, Persistenzengine, Warteschlangen und Replay.
Python-SDK2.0 stabilOffizielles deterministisches Workflow-/Aktivitäts-SDK für den Dienstmodus sowie Betriebs- und Control-Plane-Client für eine Cloud-Namespace-Laufzeit oder einen selbst gehosteten Server. Erfordert Python 3.10 oder neuer.
Rust-SDK2.0 stabilOffizielles deterministisches Workflow-/Aktivitäts-SDK für den Dienstmodus, Worker-Dienst und Control-Plane-Client für eine Cloud-Namespace-Laufzeit oder einen selbst gehosteten Server. Erfordert Rust 1.86 oder neuer.
Server2.0 stabilSelbst gehostete, in PHP implementierte sprachneutrale Laufzeit für die v2-Control-Plane- und Worker-Protokolle.
Waterline2.0 stabilCloud enthält Managed Waterline. Selbsthosting-Operatoren stellen das Dienstimage separat gegen einen Server-Namespace bereit. Eingebettetes Laravel installiert das Composer-Paket und liest anwendungseigenen Zustand im Prozess.

PHP, Python und Rust sind die drei offiziellen SDK-Sprachen für den Dienstmodus. Jede kann eine bereitgestellte Durable-Workflow-Cloud-Namespace-Laufzeit oder einen selbst gehosteten Server ansprechen, dessen Laufzeitermittlung die veröffentlichte Fähigkeit ausweist. Sie teilen stabile Typnamen als Zeichenketten, ein dauerhaftes Befehls-/Historienmodell, Control-Plane-Version 2, Worker-Protokollhauptversion 1 und die öffentliche Nutzdatenhülle. Rust ist ein Workflow-SDK: Es führt deterministischen Workflow-Code, Aktivitäten und Worker-Dienste aus und beschränkt sich nicht auf rohe Protokollaufrufe. Python verbindet Workflow-Programmierung mit Clientschnittstellen für Namespace, Zeitplan, Worker, Warteschlange, Historie, Reparatur und weitere Betriebsaufgaben.

Eingebettetes Laravel bleibt ein separater PHP-Bereitstellungsmodus innerhalb der Anwendung. PHP-Dienstmodus-Clients und -Worker benötigen es nicht. Das frameworkneutrale PHP-SDK wird unabhängig von der eingebetteten Laravel-Engine versioniert.

Wählen Sie unter Bereitstellungsmodi die Verantwortungsgrenze und fahren Sie dann mit Verwaltete Cloud-Laufzeit oder dem selbst gehosteten Server fort. Die folgenden Fähigkeitsnachweise gelten nur, wenn die gewählte Laufzeit den erforderlichen Vertrag ausweist.

PHP-SDK 2.3.2, Python-SDK 2.5.7 und Rust-SDK 3.5.0 verwenden standardmäßig Worker-Protokoll 1.20. Standard-Worker benötigen einen Server, der 1.20 oder neuer innerhalb der Hauptversion 1 ausweist. Jedes SDK unterstützt außerdem die explizite Wahl von 1.19 für einen älteren kompatiblen Server. Kooperativer Abbruch erfordert 1.20 und die ausdrückliche Aktivierung dieser Fähigkeit. Laufzeitermittlung und veröffentlichte Metadaten des gewählten SDKs bestimmen die Kompatibilität. Siehe Versionskompatibilität und Worker-Protokoll.

Fähigkeiten und SDK-Mindeststände​

„Dienstmodus“ bedeutet, dass Cloud oder ein selbst gehosteter Server die entfernte Laufzeit verantwortet. „Eingebettet“ bedeutet, dass eine Laravel-Anwendung die Laufzeit im Prozess verantwortet. Die SDK-Spalte hält Unterschiede bewusst fest. Ein leeres oder eingeschränktes SDK gilt nicht stillschweigend als gleichwertig.

Aktivitäten und DiensteDie eingebettete Engine und alle drei Dienstmodus-SDKs ermöglichen Aktivitäten. Rust-Workflows und -Aktivitäten laufen in offiziellen Worker-Diensten. Python und PHP bieten außerdem offizielle Steuerungs-/Dienstclients.Aktivitäten, PHP-SDK, Aktivitätsausführung, Externe Ausführung
Namespace-übergreifende Service-AufrufeEingebettetes PHP, PHP SDK und Python SDK verfassen dauerhafte registrierte Service-Operationen mit Warten auf Abschluss oder nur Annahme und aufgezeichneten Ergebnissen. Der Ziel-Namespace im PHP-Service-Modus verwendet derzeit die Array-Option namespace. Verfasste Rust-Aufrufe sind bis sdk-rust #86 nicht verfügbar.Eingebettete Schnittstelle, Gemeinsamer Katalog und SDK-Unterstützung

AbfragenSchreibgeschützte Replay-Abfragen werden unterstützt. PHP, Python und Rust stellen Abfragehandler/-clients bereit. Rust-Abfrageaufgaben mit Replay erfordern Worker-Protokoll 1.8 oder neuer.Abfragen, Python-SDK, Rust-SDK
UpdatesPHP, Python und Rust stellen Update-Schnittstellen für Clients und Worker-Handler bereit. Deklarierte Python-Validatoren verwenden synchrone Validierung vor der Annahme, wenn die Serverermittlung genau diesen Vertrag ausweist: Die Annahme erfolgt nach der Freigabe. Ablehnung, Worker-Verlust, Timeout und durch Fencing zurückgewiesener Abschluss schlagen explizit fehl. PHP und Rust ermöglichen keine Validatorprogrammierung und deklarieren keine Validatoren.Updates, Python-SDK, Rust-SDK
TimerVon der Dienstlaufzeit gestützte dauerhafte Timer werden in PHP, Python und Rust per Replay rekonstruiert.Timer, Rust-SDK
WiederholungenDie dauerhafte Wiederholungsrichtlinie einer Aktivität wird mit dem Befehl aufgezeichnet. PHP, Python und Rust bieten auf den aktuellen Mindestständen Optionen für Aktivitätswiederholungen.Fehler und Wiederherstellung, Python-SDK, Rust-SDK
TimeoutsDienstmodus-Laufzeiten in Cloud und selbst gehostetem Server setzen Aktivitäts- und Workflow-Timeoutfamilien durch. Rust enthält Aktivitätsoptionen und Startfristen für Workflow-Ausführung/Lauf.Timeouts, Rust-SDK
Untergeordnete WorkflowsPHP, Python und Rust starten dauerhafte untergeordnete Workflows und warten auf sie. Die sprachübergreifende Typidentität ist eine stabile Zeichenkette. Nutzdaten untergeordneter Workflows verwenden die gemeinsame Hülle.Untergeordnete Workflows, Python-SDK
Deterministische parallele KompositionPHP all()/parallel(), verschachteltes List-Yield in Python und Rust WorkflowContext::parallel()/join() planen Aktivitäts-, untergeordnete Workflow-, Timer-, gemischte und verschachtelte Gruppen über gewöhnliche Befehle. Alle drei veröffentlichen gemeinsame Gruppenidentitäts-/Pfadmetadaten und stellen Ergebnisse in verschachtelter Eingabereihenfolge wieder her.Nebenläufigkeit, Python-SDK, Rust-SDK
Dauerhafte Auswahl des ersten AbschlussesEingebettetes PHP sowie die PHP-, Python- und Rust-Dienst-SDKs starten unabhängige Mitglieder für Aktivitäten, untergeordnete Workflows, Timer, Wartezustände auf externe Eingaben und verschachtelte Gruppen. Ein Gewinner wird mit stabiler Mitgliedsidentität gespeichert. Nichtgewinner laufen weiter und behalten Handles zum Warten/Abbrechen.Nebenläufigkeit, Python-SDK, Rust-SDK
Saga-KompensationPHP-Saga-Helfer, Python WorkflowContext.saga() und Rust WorkflowContext::saga() registrieren dauerhafte Kompensationen nach erfolgreichem Vorwärtsschritt und führen sie standardmäßig nacheinander in umgekehrter Reihenfolge aus. Python und Rust stoppen beim ersten Kompensationsfehler und erhalten auslösenden Fehler sowie Kompensationsfehler. PHP bietet zusätzlich explizit aktivierbare Richtlinien für parallele Ausführung und Fortsetzung bei Fehlern.Sagas, Python-SDK, Rust-SDK
AbbruchEingebettetes Laravel und PHP, Python und Rust im Dienstmodus unterstützen kooperative Abbruchanforderungen mit einer gemeinsamen Wurzelidentität, unveränderlicher Frist und begrenzter Bereinigung auf ausdrücklich aktivierten Workern. Sofortiger terminaler Abbruch bleibt mit Absicherung des ausgewählten Laufes und typisierten Ergebnissen verfügbar.Abbrechen und terminieren, Abbruch im Dienstmodus, Rust-SDK
TerminierungTerminierung schließt einen Lauf sofort mit einem eigenen terminalen Ergebnis. Sie ist über Dienstlaufzeiten von Cloud und selbst gehostetem Server, CLI sowie PHP-, Python- und Rust-Steuerungsschnittstellen verfügbar.Abbrechen und terminieren, Server-API
SeiteneffektePHP, Python und Rust zeichnen nichtdeterministische Werte genau einmal auf und dekodieren den aufgezeichneten Wert beim Replay.Seiteneffekte, Python-SDK, Rust-SDK
Workflow StreamsPHP, Python und Rust bieten typisierte Operationen für Auflisten, Beschreiben, offsetbasiertes Abonnieren/Wiederaufnehmen, Anhängen, Schließen und Fehler für serververwaltete laufbezogene Ausgabeströme. Alle drei ermöglichen Replay-sichere Ausgaben aus einer dauerhaften Befehlsidentität. Python löst externe Nutzdaten mit seinem konfigurierten Speichertreiber auf. PHP und Rust erhalten undurchsichtige Referenzen.Workflow Streams, genaue SDK-Matrix, Laufzeitszenarien
VersionsmarkerPHP, Python und Rust bieten dauerhafte Versionsmarker für kompatible Codeweiterentwicklung.Versionierung, Python-SDK, Rust-SDK
Deterministisches ReplayPHP-, Python- und Rust-Workflow-Worker rekonstruieren Entscheidungen aus dauerhafter Historie und melden typisierten Nichtdeterminismus, statt externe Arbeit erneut auszuführen.Ausführungsgarantien, Plattformkonformität, Rust-SDK
ZeitpläneDienstlaufzeiten von Cloud und selbst gehostetem Server verwalten dauerhafte Zeitpläne. PHP, Python und CLI bieten Zeitplanoperationen. Rust beansprucht keine Zeitplanverwaltungs-API.Zeitpläne, CLI-Referenz, Python-SDK
NamespacesDienstmodus-Laufzeiten sind auf Namespaces begrenzt. PHP-/Python-Clients und CLI verwalten Namespaces, soweit die ausgewählte Laufzeit diese Operation bereitstellt. Rust-Worker/-Clients sprechen einen Namespace an, beanspruchen auf dem aktuellen Mindeststand aber keine Namespace-Verwaltung.Namespace, Authentifizierung und Worker, Server-API
SuchattributeDienstlaufzeiten von Cloud und selbst gehostetem Server indexieren typisierte Suchattribute. PHP und Python bieten Programmier-/Steuerungsschnittstellen. CLI und Operator-APIs bieten strukturierte Ermittlung und Filterung.Suchattribute, Python-SDK
Worker-KompatibilitätSDKs registrieren Laufzeit, SDK-Version, Build-ID, unterstützte Typen, Protokollversion und Kapazität. Der Server veröffentlicht akzeptierte Versionen und Routinginformationen.Kompatibilität, Worker-Kompatibilität und -Routing
Lokale AktivitätenIn eingebettetem Laravel, PHP- und Python-Dienst-SDKs sowie Rust-SDK 3.1.0 mit ausdrücklicher Worker-Aktivierung verfügbar.Eingebettete Aktivitätsausführung, Unterstützungsmatrix für den Dienstmodus
Worker-SitzungenIn eingebettetem Laravel, PHP- und Python-Dienst-SDKs sowie Rust-SDK 3.2.0 mit ausdrücklicher Worker-Aktivierung verfügbar.Worker-Sitzungen, Unterstützungsmatrix für den Dienstmodus
Sticky-AusführungIn eingebettetem Laravel und im PHP-Dienst-SDK verfügbar. Python und Rust bieten ebenfalls optionale begrenzte Historiencaches mit ausdrücklicher Worker-Aktivierung. Jeder Worker muss korrektes kaltes Replay weiterhin unterstützen.Sticky-Ausführung, Unterstützungsmatrix für den Dienstmodus
Codec-InteroperabilitätPHP, Python und Rust verwenden die öffentliche Hülle codec + blob und ein festes rekursives Avro-Value-Schema. Benannte Zweige erhalten die Unterschiede zwischen Ganzzahlen und Doubles, Text und Bytes, booleschen Werten und Ganzzahlen sowie Listen und Maps.Avro-Value-Protokoll, Worker-Protokoll, Rust-SDK
DiagnoseDienstlaufzeiten und CLI veröffentlichen Fakten zu Version, Protokoll, Workern, Aufgabenwarteschlangen, Replay, Historie, typisierten Fehlern und Reparatur als JSON. Managed Waterline, ein separat bereitgestellter selbst gehosteter Dienst oder das eingebettete Paket zeigt Nachweise seiner verantwortlichen Laufzeit.Überwachung, CLI-Referenz, Waterline-Operator-API
AgentenwerkzeugeErmitteln -> Ändern -> Ausführen -> Diagnostizieren -> Reparieren ist über öffentliche Manifeste, Schemas, HTTP-Operationen, CLI-JSON, SDK-Clients, typisierte Historie/Diagnose und sichere Mutationen verfügbar. Grenze der Nutzdateninteroperabilität​

Sprachübergreifende Workflow- und Aktivitätsaufrufe übertragen keine serialisierten PHP-Objekte, Python-Pickles oder Rust-Implementierungstypen. Sie übertragen registrierte Typnamen als Zeichenketten und eine öffentliche Nutzdatenhülle. Mit avro verwendet jedes offizielle SDK die offizielle Sprachimplementierung und dasselbe feste Value-Schema. Dekodierte Maps, Listen, Zeichenketten, Bytes, Ganzzahlen, Doubles, boolesche Werte und Nullwerte erhalten ihren primitiven Typ. Eine sprachspezifische Klasse wird nur innerhalb ihres eigenen SDKs rekonstruiert.

Dieser Vertrag gilt für Workflow-Eingabe und -Ergebnis, untergeordnete Workflows, Aktivitätseingabe und -ergebnis, Signale, Abfragen, Updates und externe Ausführung. Bereitstellungen müssen vor der Zulassung eines Workers weiterhin die von GET /api/cluster/info ausgewiesenen Codecs prüfen.

Die hier aufgeführten Plattformverträge bilden die stabile 2.0-Produktoberfläche. Verwenden Sie die Bewertung für KI-Agenten für eine kurze Eignungsentscheidung.

CLI-Befehlsreferenz

Diese Seite dokumentiert die v2-dw-Befehlsoberfläche als Vertrag für Betrieb und Automatisierung. Installation und Profileinrichtung beschreibt der CLI-Leitfaden. Nutzen Sie diese Seite, um Skripte, CI-Jobs, Betriebsanleitungen oder KI-Agenten an genaue Befehlsformen anzubinden.

Alle servergestützten Befehle verwenden die Control-Plane-Protokollversion 2 des eigenständigen Servers. Die CLI prüft die vom Server veröffentlichten Protokollmanifeste, bevor sie kanonischen Anfrage- und Antwortfeldern vertraut.

Globale Optionen​

Servergestützte Befehle akzeptieren diese Optionen, sofern nicht anders angegeben.

OptionBedeutung
--server, -sServer-Basis-URL. Überschreibt Profile und Umgebungsvariablen für diesen Aufruf.
--namespaceZiel-Namespace. Überschreibt den Profil-Namespace.
--tokenBearer-Token für diesen Aufruf. Für gespeicherte Automatisierung Profile mit --token-env bevorzugen.
--envBenanntes CLI-Umgebungsprofil. Unbekannte Profilnamen führen zum Fehler statt zum Rückfall.
--output=table|json|jsonlAusgabevertrag. table ist menschenlesbar, json ein JSON-Dokument und jsonl ein JSON-Objekt je Zeile für Listenbefehle.
--jsonLokaler Alias für JSON-Ausgabe bei Befehlen, die ihn anbieten.

Befehle mit Aufrufernutzlasten verwenden einen gemeinsamen Eingabevertrag:

OptionBedeutung
--input, -iInline-Eingabedokument.
--input-fileEingabe aus einer Datei oder - für stdin lesen. Schließt --input aus.
--input-encoding=json|raw|base64Eingabe als JSON decodieren, Rohtext als ein Argument übergeben oder Base64 als ein Argument decodieren. Standard json.

JSON-Eingaben für Workflow-Starts, Signale, Abfragen, Updates, Zeitpläne und Aktivitätsabschlüsse repräsentieren das v2-Array der Positionsargumente. Raw- und Base64-Eingaben werden zu einem Positionsargument, sodass der Server weiterhin das kanonische Array input erhält.

HTTP-Server für ein lokales Projekt​

Führen Sie dw server:start-dev im Verzeichnis eines installierten Laravel-Projekts mit artisan aus. Die native CLI benötigt dafür ein separates PHP-Programm auf PATH. Konfigurieren Sie zuerst die Datenbank und führen Sie Migrationen aus. Der gewählte --db-Wert wird als DB_CONNECTION übergeben. Leeren Sie beim Treiberwechsel Laravels Konfigurationscache. Führen Sie bei Bedarf Warteschlangen-Worker und Scheduler separat aus. Starten Sie den Befehl nach Änderungen an .env neu. Der gewählte Treiber bleibt durch Artisans --no-reload-Modus für HTTP-Anfragen angewendet.

Der Befehl bindet standardmäßig an Loopback. Verwenden Sie explizit --host=0.0.0.0 für alle Schnittstellen. MySQL- und PostgreSQL-Modi benötigen Compose-Dienste des Projekts namens mysql beziehungsweise pgsql sowie redis. Fehler von Abhängigkeits- oder HTTP-Prozessen liefern einen Exit-Code ungleich null. Compose-Dienste laufen nach Ende des HTTP-Prozesses weiter.

Native POSIX-Binärdateien leiten SIGINT und SIGTERM an das aktive Kind weiter und warten bis zu fünf Sekunden auf das Ende seiner Prozessgruppe. Quellcode- und PHAR-Installationen benötigen dafür PHPs Erweiterungen pcntl und posix. Windows verwendet sein Konsolen-Unterbrechungsverhalten.

Für einen eigenständigen Durable Workflow Server mit veröffentlichten Images folgen Sie dem Service-Schnellstart.

Server-Info und Rollentopologie​

dw server:info ist die CLI-Oberfläche für GET /api/cluster/info. Im Tabellenmodus enthält es einen Abschnitt Topology:, der den vom antwortenden Knoten veröffentlichten Rollentopologievertrag zusammenfasst:

  • Supported Shapes und Current Shape zeigen zulässige Bereitstellungsformen und die aktuell von diesem Knoten bediente Form.
  • Current Process Class und Current Roles benennen Prozessklasse und Rollenbündel des antwortenden Knotens.
  • Matching Role, Matching Partitions und Matching Backpressure zeigen Matching-Form, Aufweckzuständigkeit, Task-Zuweisungsmodus und Aufteilungsmerkmale für die Übernahme bereiter Arbeit.
  • Matching Discovery Limits fasst den festgelegten numerischen Matching-Vertrag zusammen: poll_batch_cap, availability_ceiling_seconds, wake_signal_ttl_seconds, workflow_task_lease_seconds und activity_task_lease_seconds. Der Betrieb kann damit den dokumentierten Vertrag prüfen, ohne den Paketquellcode zu durchsuchen.
  • Current Write Boundaries nennt dauerhafte Schreiboberflächen, die aktuell den Rollen dieses Knotens gehören.
  • Scaling Boundaries und Failure Domains zeigen je Rolle erwartete Lasttreiber oder erste Ausfallsignale.

Verwenden Sie --output=json, wenn Skripte das rohe Manifest benötigen. topology.schema und topology.version binden die Vertragsrevision, damit Skripte Strukturabweichungen erkennen. topology.execution_mode meldet den Zuweisungsmodus des antwortenden Knotens. Stabile Maschinenfelder liegen unter topology, darunter supported_shapes, current_shape, current_process_class, current_roles, matching_role, role_catalog, authority_boundaries, authority_surfaces, supported_topologies, scaling_boundaries und failure_domains. topology.matching_role veröffentlicht außerdem partition_primitives und backpressure_model, damit Skripte Routing-Achsen der Suche nach bereiten Tasks ohne Prosaauswertung prüfen können. topology.matching_role.discovery_limits zeigt den festgelegten numerischen Vertrag mit poll_batch_cap, availability_ceiling_seconds, wake_signal_ttl_seconds, workflow_task_lease_seconds und activity_task_lease_seconds. Skripte können damit die Matching-Werte des Workflow-Pakets binden, ohne menschenlesbare Abschnitte auszuwerten.

dw server:info --output=json \
  | jq '.topology | {current_shape, current_process_class, current_roles, matching_role, scaling_boundaries, failure_domains}'

Die Bedeutung dieser Felder erklärt Server-Rollentopologie.

Server-Info und Koordinationszustand​

dw server:info veröffentlicht auch das Namespace-übergreifende Urteil zur Rollout-Sicherheit des Servers. Der Betrieb kann den Koordinationszustand ohne separate Zustandsoberfläche lesen. Im Tabellenmodus zeigt die CLI unter Topology: einen Abschnitt Coordination Health:. Mit --output=json liegen dieselben Daten unter coordination_health mit stabilen Maschinenfeldern:

  • coordination_health.schema und coordination_health.version binden die Vertragsrevision.
  • coordination_health.namespace_scope meldet, ob das Urteil einen Namespace oder die gesamte Flotte abdeckt.
  • coordination_health.status und coordination_health.http_status melden das Gesamturteil und die HTTP-Bereitschaftsschranke des Servers.
  • coordination_health.generated_at hält den Snapshot-Zeitpunkt fest.
  • coordination_health.categories fasst Anzahlen je Kategorie zusammen, etwa correctness, safety, routing.
  • coordination_health.warning_checks und coordination_health.error_checks nennen die Prüfungen, die Warnung oder Fehler ausgelöst haben, damit Skripte nach den fehlerhaften Oberflächen verzweigen können.
  • coordination_health.checks[] enthält Details je Prüfung mit name, status, category und message, anhand derer Automatisierung ein beeinträchtigtes Urteil erklären kann. Das feste Inventar enthält stets worker_compatibility, task_transport, routing_health, durable_resume_paths, die Projektions-/Scheduler-Prüfungen und activity_path. activity_path ist das Aktivitätsgegenstück zu task_transport: Es zeigt Aktivitätsausführungen mit überschrittener, aber nicht durchgesetzter Schedule-to-start-, Start-to-close-, Schedule-to-close- oder Heartbeat-Frist sowie anhaltenden Aktivitätswiederholungsrückstau. Das Umbenennen von activity_path ist eine Protokolländerung.
dw server:info --output=json \
  | jq '.coordination_health | {status, http_status, namespace_scope, warning_checks, error_checks}'

Den zugrunde liegenden Bereitschaftsvertrag beschreibt die Server-API-Referenz.

Selbstaktualisierung​

dw upgrade lädt das passende Plattformartefakt aus dem GitHub-Release von durable-workflow/cli, prüft es gegen dessen SHA256SUMS und ersetzt die laufende Binärdatei nur bei passender Prüfsumme. --tag bindet ein bestimmtes Release-Tag, --dry-run löst das Zielrelease auf und zeigt Artefakt-URLs ohne Download, --force lädt und ersetzt erneut, auch bei gleicher aktueller und Zielversion.

Der Befehl verweigert das Überschreiben fremdverwalteter Installationen. JSON-Ausgabe verwendet ein stabiles status-Feld für Verzweigungen ohne Prosaauswertung:

statusBedeutung
upgradedBinärdatei durch target_version ersetzt.
noopcurrent_version entspricht bereits target_version; --force umgeht dies.
dry-run--dry-run hat target_version, asset_url und checksum_url ohne Download aufgelöst.
refusedInstallation ist keine eigenständige Release-Binärdatei (Composer vendor, Homebrew cellar oder PHAR), oder für die Plattform ist kein Artefakt veröffentlicht.
permission-deniedInstallationsverzeichnis nicht beschreibbar; die Nutzlast enthält einen hint mit empfohlenem nächsten Schritt.
errorFehler beim Abruf des Release-Katalogs, abweichende Prüfsumme oder Dateisystemfehler.

Bei Ablehnungen benennt installation.kind das verwaltende Werkzeug (composer-vendor, homebrew, phar oder binary) und reason den richtigen zuständigen Weg. Für öffentliche Automatisierung ohne Quellcode installieren Sie ein festgelegtes Release über https://durable-workflow.com/install.sh erneut. Für Tap-verwaltete Homebrew-Installationen verwenden Sie brew upgrade durable-workflow/tap/dw.

Dienstaufrufe untersuchen​

Mit dw service-call:describe <endpoint> <service> <operation> <call-id> untersuchen Sie einen dauerhaften Nexus-Aufruf im Namespace des Endpunkts. Beispielsweise liefert dw service-call:describe billing invoices create call-42 --namespace=shared --json die vollständige Server-Antwort.

Die Antwort erhält ursprünglichen Aufrufer und verknüpftes Ziel, Aufruffrist, Status, Ergebnis, Versuchseinträge, typisierten Fehler und aufbewahrte Nutzlastreferenzen. Erfolgreiche Ergebnisse bleiben verlustfreie Avro-Werte in result_envelope. Ein angenommener oder gestarteter Aufruf ist noch ausstehend, kein erfolgreich abgeschlossenes Ergebnis.

Der Befehl führt ein einzelnes GET aus. Er fordert weder Wiederholung noch Abbruch oder Download externer Objekte an. Der Server kann einen Aufruf beim Lesen mit dem terminalen Ergebnis seines verknüpften Workflows abgleichen. Namespace-Autorisierung und die Auswahl von Endpunkt, Dienst, Operation und Aufruf gelten vollständig.

Brückenadapter-Befehle​

Brückenbefehle sind begrenzte Eingangs- und Übergabewerkzeuge für Integrationsereignisse. Sie rufen die Brückenadapter-Oberfläche des Servers auf und liefern im JSON-Modus die Struktur durable-workflow.v2.bridge-adapter-outcome.contract. Sie führen keinen Workflow-Code aus und verantworten keine Workflow-Zustandsübergänge.

BefehlZweckWichtige Optionen
dw bridge:webhook <adapter>Ein Webhook-Brückenereignis senden, das über die Control Plane einen Workflow startet, signalisiert oder aktualisiert.--action=start_workflow|signal_workflow|update_workflow, --idempotency-key, --target, Eingabeoptionen, --correlation, --json

Beispiele:

dw bridge:webhook stripe \
  --action=start_workflow \
  --idempotency-key=stripe-event-1001 \
  --target='{"workflow_type":"orders.fulfillment","task_queue":"external-workflows","business_key":"order-1001"}' \
  --input='{"order_id":"order-1001"}' \
  --json

dw bridge:webhook pagerduty \
  --action=signal_workflow \
  --idempotency-key=pd-event-3003 \
  --target='{"workflow_id":"wf-remediation-42","signal_name":"incident_escalated"}' \
  --input='{"severity":"critical"}'

Verwenden Sie Brückenergebnisfelder, statt Verhalten allein aus dem HTTP-Status abzuleiten. outcome, reason, control_plane_outcome, idempotency_key und die geschwärzte target-Zusammenfassung bilden den Automatisierungsvertrag für Duplikate, fehlende Routing-Ziele, ungültige Nutzlasten und angenommene Übergaben.

Zeitpläne filtern und seitenweise abrufen​

dw schedule:list liefert eine gefilterte Seite im aufgelösten Namespace. Ohne --namespace wird nur der aufgelöste Standard-Namespace ausgewählt, nicht jeder Namespace. Status, Workflow-Typ und Sichtbarkeitsprädikate werden mit AND verknüpft. Die Prüfung der regulär veröffentlichten CLI- und PHP-Server-Artefakte bestätigt diese Optionen.

CLI-OptionServer-AbfrageparameterBedeutung
--statusstatusactive oder paused.
--typeworkflow_typeExakter Workflow-Typ.
--queryqueryAusdruck für die Sichtbarkeit von Zeitplänen.
--limitpage_sizeSeitengröße von 1 bis 200, Standard 50.
--next-page-tokennext_page_tokenOpakes Fortsetzungstoken aus der vorherigen Antwort.

Listen Sie im vorhandenen Namespace production mit dem registrierten Keyword-Attribut Region die pausierten Zeitpläne von orders.rollup für Region eu und Task Queue orders auf:

dw schedule:list --namespace=production --status=paused --type=orders.rollup \
  --query='Region = "eu" AND TaskQueue = "orders"' --limit=25 --json

Lesen Sie next_page_token aus der JSON-Antwort und setzen Sie NEXT_PAGE_TOKEN auf diesen Wert. Verwenden Sie für die nächste Seite denselben Namespace und dieselben Filter:

dw schedule:list --namespace=production --status=paused --type=orders.rollup \
  --query='Region = "eu" AND TaskQueue = "orders"' --limit=25 --json \
  --next-page-token="$NEXT_PAGE_TOKEN"

Tokens gehören zum Namespace und zur Filterauswahl. Beginnen Sie nach einer Filteränderung oder einer Ablehnung wegen eines veralteten Cursors erneut ohne Token. Jeder Aufruf liest eine aktuelle Seite, keinen unveränderlichen Snapshot. Die unterstützte Abfragesyntax und die Antwortfelder stehen unter API-Grenzen und Ablehnungsgründen für Zeitplanlisten.

Die Task-Warteschlangenbefehle sind die bevorzugte Betriebsansicht für Drosselung, Kapazität und Diagnose fehlender Worker. Task-Warteschlangenzulassung erklärt die serverseitige Richtlinie dieser Felder und Worker-Build-ID-Rollout den vollständigen Lebenszyklus von Umstellung auf Versionierung, Canary, Leeren und Rollback.

Beides zusammen scheitert sofort mit einem Fehler für ungültige Optionen. Beide Befehle sind idempotent: Wiederholtes Leeren verschiebt drained_at nicht. Das Fortsetzen einer bereits aktiven Kohorte ändert nichts.

dw query-task:fail <query-task-id> <attempt>Fehler eines geleasten Abfrage-Tasks mit maschinenlesbarem Grund melden.--lease-owner, --message, --reason, --type, --stack-trace, --json
dw activity:complete <task-id> <attempt-id>Einen geleasten Aktivitätsversuch abschließen.--lease-owner, Eingabeoptionen, --json
dw activity:fail <task-id> <attempt-id>Einen geleasten Aktivitätsversuch als fehlgeschlagen melden.--lease-owner, --message, --type, --non-retryable, --json

Verwenden Sie workflow-task:fail für workerseitige Ausführungsfehler wie Replay-Abweichungen oder Deserialisierungsfehler. Es zielt auf POST /worker/workflow-tasks/{taskId}/fail. Den Workflow durch einen Workflow-Befehl scheitern zu lassen, ist eine getrennte Aufgabe und erfolgt über workflow-task:complete mit passender Befehlsnutzlast.

query-task:poll, query-task:complete und query-task:fail bedienen die geroutete Abfrage-Worker-Oberfläche unter /worker/query-tasks/…. Normale Worker beziehen Abfrage-Tasks über ihren SDK-Abfrage-Handler. Die CLI dient Diagnose, CLI-/SDK-Paritätsprüfungen und Worker-Experimenten ohne SDK. Abfrage-Task-Fehler verwenden standardmäßig --reason=query_rejected. Verwenden Sie einen stabilen Grund wie unknown_query, decode_failure oder eine laufzeitspezifische Kennung, damit Aufrufer erwartete Ablehnungen von Laufzeitfehlern unterscheiden können.

Historienseiten von Workflow-Tasks​

workflow-task:history ist der CLI-Diagnosewrapper für den Worker-Plane-Historienseitenendpunkt. Verwenden Sie ihn erst, nachdem workflow-task:poll einen geleasten Workflow-Task mit next_history_page_token liefert. Normale Worker sollten zusätzliche Historienseiten durch ihr SDK abrufen lassen.

dw workflow-task:history workflow-task-01 history-page-2 \
  --lease-owner=python-worker-1 \
  --attempt=2 \
  --json

Die JSON-Ausgabe ist die Server-Antwort ohne Feldumbenennung:

{
  "history_events": [
    {"event_id": 2, "event_type": "ActivityScheduled", "payload": {}}
  ],
  "total_history_events": 4,
  "next_history_page_token": "history-page-3"
}

Automatisierung sollte history_events, total_history_events und next_history_page_token lesen. Der Worker-Historienendpunkt verwendet nicht die Control-Plane-Laufhistorienfelder events oder next_page_token.

Suchattributtypen sind serverkompatible Werte wie keyword, text, int, double, bool, datetime und keyword_list.

Befehle für externen Nutzlastspeicher rufen die Namespace-Speicher-API des Servers auf. Das Treiberargument ist local, s3, gcs oder azure. Objektspeichertreiber verwenden serverseitige Dateisystemkonfiguration. Die CLI-Optionen beschreiben daher die Namespace-Richtlinie statt Anbieterzugangsdaten zu transportieren. Binden Sie mit --disk den Treiber s3, gcs oder azure an einen benannten serverseitigen Dateisystem-Datenträger mit den tatsächlichen Anbieterzugangsdaten. --disable erhält den Richtliniendatensatz und verhindert neue Auslagerungen.

Beispiele:

dw namespace:set-storage-driver billing s3 \
  --disk=external-payload-objects \
  --bucket=dw-payloads \
  --prefix=billing/ \
  --threshold-bytes=2097152 \
  --json

dw namespace:set-storage-driver dev local \
  --uri=file:///var/lib/durable-workflow/payloads

dw storage:test --namespace=billing --large-bytes=2097152 --json
dw storage:test --driver=s3 --small-bytes=128 --large-bytes=3145728 --json

Im JSON-Modus liefert namespace:set-storage-driver die Namespace-Nutzlast mit ihrer external_payload_storage-Richtlinie. storage:test liefert den Diagnosestatus und die Ergebnisobjekte small_payload und large_payload. Automatisierung sollte nach diesen Feldern verzweigen, statt die Tabelle auszuwerten.

Die Diagnose ist auch die schnellste Betriebsprüfung des Referenz-Envelope-Vertrags. Ein bestandener Test der großen Nutzlast belegt, dass die Richtlinie codierte Bytes schreiben, eine Referenz durable-workflow.v2.external-payload-reference.v1 zurückgeben, das Objekt zurücklesen und size_bytes plus sha256 prüfen kann. Behandeln Sie eine fehlgeschlagene Diagnose als Speicherrichtlinienproblem, bevor Workflows über diesen Namespace Nutzlasten auslagern dürfen.

BefehlZweckWichtige Optionen

Schemabefehle helfen, wenn ein KI-Client oder CI-Job den aktuellen Control-Plane-, Antwort- oder Ausgabevertrag ohne Auswertung von Prosadokumentation benötigt. Das aktuelle v4-Manifest bindet jede JSON-Envelope und jedes JSONL-Schema auf Datensatzebene über öffentlichen Resolver und Hash. Seine Workflow-Start-/Lauf- und Abfrage-/Update-Nutzlastfelder akzeptieren nur avro. Das aufbewahrte v3-Manifest und v2-Manifest bleiben für an Revisionen gebundene Verbraucher mit ursprünglichen Bytes verfügbar.

Ausgabe- und Exit-Vertrag​

Verwenden Sie --output=json für ein Objekt und --output=jsonl, wenn ein Listenbefehl einen Stream-Prozessor speist. Menschliche Tabellen dürfen sich verbessern. JSON-Feldnamen bilden den Automatisierungsvertrag.

Alle Befehle verwenden die im CLI-Leitfaden dokumentierten stabilen Exit-Codes:

CodeBedeutung
0Erfolg.
1Befehl lief, scheiterte aber allgemein.
2Ungültige lokale Verwendung oder Validierungsfehler.
3Netzwerk- oder Transportfehler.
4Authentifizierungs- oder Autorisierungsfehler.
5Ressource nicht gefunden.
6Serverseitiger 5xx-Fehler.
7Timeout.

Sammeln Sie für Support-Pakete dw doctor --output=json, dw server:info --output=json und dw debug workflow <workflow-id> --output=json.

Verwandte Leitfäden​

  • CLI erklärt Installation, Profileinrichtung und Exit-Codes.
  • Server dokumentiert die von servergestützten Befehlen aufgerufene HTTP-Control-Plane.
  • Client- und Worker-Fähigkeiten vergleicht die Client- und Worker-Oberflächen von CLI, PHP, Python und Rust.

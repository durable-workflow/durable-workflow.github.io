Server-API-Referenz

Der eigenständige Server bietet eine versionierte HTTP+JSON-API. Nutzen Sie diese Seite beim Erstellen von SDKs, Skripten, Brückenadaptern oder Betriebsanleitungen mit direktem Server-Zugriff. Bereitstellung und Konfiguration beschreibt der Server-Leitfaden. Für Aufrufe von dw verwenden Sie die CLI-Befehlsreferenz.

Header und Versionierung​

Alle authentifizierten Anfragen verwenden Bearer-Tokens, sofern kein anderer Authentifizierungstreiber konfiguriert ist:

Authorization: Bearer <token>
X-Namespace: default
Content-Type: application/json
Accept: application/json

Control-Plane-Routen benötigen:

X-Durable-Workflow-Control-Plane-Version: 2

Worker-Plane-Routen benötigen:

X-Durable-Workflow-Protocol-Version: 1.0

Der Server veröffentlicht unterstützte Versionen und maschinenlesbare Verträge über GET /api/cluster/info. Clients sollten dort vor dem Start langlebiger Automatisierung Versionen ermitteln. Fehlende oder nicht unterstützte Control-Plane-Versionen werden strikt mit einem benannten Grund wie missing_control_plane_version oder unsupported_control_plane_version abgelehnt.

Verwenden Sie für Validierung, Codeerzeugung und Abweichungsprüfungen den normativen Katalog Plattform-Protokollspezifikationen statt dieser Prosareferenz. Er verlinkt das Control-Plane-OpenAPI-Dokument, Worker-Protokoll-OpenAPI- und -AsyncAPI-Dokumente, das JSON Schema cluster_info und die zugehörigen MCP-, Historien-, Waterline- und Reparatur-/Handlungsschemas.

Erkennung und Zustand​

Diese Routen dienen Load Balancern, SDK-Bootstraps und Kompatibilitätsprüfungen.

MethodePfadAuthentifizierungZweck
GET/api/healthneinLebendigkeitsprüfung mit maschinenlesbarer Topologiezusammenfassung des antwortenden Knotens.
GET/api/readyneinBereitschaftsprüfung mit derselben Topologiezusammenfassung und Bootstrap-Prüfungen der Rollout-Sicherheit.
GET/api/cluster/infojaServer-Identität, unterstützte SDK-Bereiche, Rollentopologie, Koordinationszustand, Control-Plane-Vertrag, Worker-Protokollvertrag, Nutzlast-Codecs und Fähigkeiten.

Beispiel:

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/cluster/info" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: default" | jq '.control_plane.version, .worker_protocol.version'

/api/cluster/info benötigt bewusst keinen Control-Plane-Versions-Header, da es die unterstützten Versionen erst meldet. Die Antwort enthält auch coordination_health, die Namespace-übergreifende Rollout- und Bereitschaftszusammenfassung derselben Prüfungen, die den Server-Bereitschaftszustand bestimmen.

Öffentliche Topologiezusammenfassung​

GET /api/health und GET /api/ready liefern beide ein oberstes Objekt topology aus dem implementierten Zustandszusammenfassungsvertrag. Ermitteln Sie damit den antwortenden Knoten, bevor Control-Plane-Authentifizierung, Namespace-Auflösung oder umfassendere Erkennung über /api/cluster/info gelingen.

Die öffentliche Zusammenfassung enthält stets:

  • topology.schema
  • topology.version
  • topology.current_shape
  • topology.current_process_class
  • topology.current_roles
  • topology.execution_mode
  • topology.matching_role.queue_wake_enabled
  • topology.matching_role.shape
  • topology.matching_role.wake_owner
  • topology.matching_role.task_dispatch_mode
  • topology.matching_role.partition_primitives
  • topology.matching_role.backpressure_model
  • topology.matching_role.discovery_limits.poll_batch_cap
  • topology.matching_role.discovery_limits.availability_ceiling_seconds
  • topology.matching_role.discovery_limits.wake_signal_ttl_seconds
  • topology.matching_role.discovery_limits.workflow_task_lease_seconds
  • topology.matching_role.discovery_limits.activity_task_lease_seconds

topology.matching_role.discovery_limits ist der festgelegte numerische Matching-Vertrag: poll_batch_cap ist die maximale Menge bereiter Task-Zeilen je Abfrage, availability_ceiling_seconds die backendübergreifende Toleranz für available_at, damit gerade verfügbare Tasks Zeitstempelabweichungen unter einer Sekunde überstehen, wake_signal_ttl_seconds die Standard-Signal-TTL von CacheLongPollWakeStore und workflow_task_lease_seconds / activity_task_lease_seconds die Standard-Lease-Dauern für Workflow- und Aktivitäts-Tasks. Jede Verschärfung dieser Werte ist eine Protokolländerung, da Worker und nachgelagerte Werkzeuge sie als maßgeblichen Matching-Vertrag lesen. Auch das Umbenennen eines Feldes bricht das Protokoll.

/api/ready liefert denselben Block topology, auch wenn der oberste Bereitschafts-status not_ready ist. Prüfungen können so trotz aktiver Bootstrap-Blocker Antworten von server_http_node, scheduler_node, matching_node und execution_node unterscheiden.

Beispiel:

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/health" | jq '{
  status,
  topology: {
    schema: .topology.schema,
    version: .topology.version,
    current_shape: .topology.current_shape,
    current_process_class: .topology.current_process_class,
    current_roles: .topology.current_roles,
    execution_mode: .topology.execution_mode,
    matching_role: .topology.matching_role
  }
}'

Bereitschaftsblocker​

GET /api/ready liefert einen obersten status und maschinenlesbare checks. Zwei Prüfungen bestimmen, ob der Server Rollout-Sicherheit sicher bewerten kann:

  • checks.migrations ist die Bootstrap- und Migrationsschranke. Sie veröffentlicht repository_exists, pending_migrations, adoptable_migrations, blocking_migrations, missing_tables, operator_surface und readiness_contract.
  • adoptable_migrations bedeutet, dass bestehende Workflow-Tabellen nur eine Übernahme der Migrationshistorie benötigen. Server bleibt bereit und meldet status: "warning", damit der Betrieb die Übernahme vor dem nächsten Migrationsdurchlauf planen kann.
  • blocking_migrations bedeutet, dass noch Migrationsdatensätze für Rollout-Sicherheit erforderlich sind. Server lehnt strikt mit status: "pending" und einer remediation ab, statt eine aktuelle Flotte vorzutäuschen.
  • operator_surface.available und operator_surface.required_tables zeigen, ob die v2-Betriebsoberfläche die zum Erklären der Rollout-Sicherheit nötigen dauerhaften Tabellen besitzt.
  • readiness_contract.version bindet die Revision des Installations- und Übernahmevertrags, die Skripte beim Auswerten dieser Felder erwarten sollen.
  • checks.workflow_v2 spiegelt das Namespace-übergreifende Rollout-Sicherheitsurteil. Fehlen Bereitschaftsvoraussetzungen, meldet es status: "blocked" mit blocked_by, message und remediation, statt eine gesunde Flotte vorzutäuschen.

Beispiel:

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/ready" | jq '{
  status,
  migrations: {
    status: .checks.migrations.status,
    adoptable_migrations: .checks.migrations.adoptable_migrations,
    blocking_migrations: (.checks.migrations.blocking_migrations | map(.migration)),
    missing_tables: .checks.migrations.missing_tables,
    operator_surface: .checks.migrations.operator_surface,
    readiness_contract: .checks.migrations.readiness_contract
  },
  workflow_v2: {
    status: .checks.workflow_v2.status,
    blocked_by: .checks.workflow_v2.blocked_by,
    remediation: .checks.workflow_v2.remediation
  }
}'

Cluster-Topologiemanifest​

/api/cluster/info liefert auch das topology-Manifest des Knotens mit dem Schema durable-workflow.v2.role-topology. Es ist der unterstützte Weg, um standalone_server, embedded oder split_control_execution, zugehörige Rollen und die Server-Erwartungen an matching_role, shape_assignments, authority_boundaries, failure_domains, scaling_boundaries und migration_path zu erkennen. Dieselbe Antwort veröffentlicht den aktuellen Rollout-Sicherheitszustand dieses Knotens.

Lesen Sie das Manifest so:

  • topology.current_shape, topology.current_process_class, topology.current_roles und topology.execution_mode nennen die tatsächlich bediente Rollenform des antwortenden Knotens, nicht der gesamten Flotte.
  • topology.role_vocabulary ist die feste Liste zulässiger v2-Rollennamen.
  • topology.matching_role.queue_wake_enabled, topology.matching_role.shape, topology.matching_role.wake_owner, topology.matching_role.task_dispatch_mode, topology.matching_role.partition_primitives und topology.matching_role.backpressure_model zeigen, ob die breite Suche nach bereiten Tasks im Worker oder durch einen dedizierten Matching-Suchlauf erfolgt, welcher Prozess ihn verantwortet, welche Routing-Achsen stabil bleiben und welche dauerhafte Zulassungsgrenze v2 heute erzwingt.
  • topology.matching_role.discovery_limits veröffentlicht die festen numerischen Vertragswerte poll_batch_cap, availability_ceiling_seconds, wake_signal_ttl_seconds, workflow_task_lease_seconds und activity_task_lease_seconds. Prüfen Sie damit den dokumentierten Vertrag der Bereitstellung. Das Paket gibt dieselben Kennungen in dw server:info, dem Betriebsmetrik-Snapshot und der Namespace-bezogenen Zustandsoberfläche aus.
  • topology.role_catalog und topology.authority_surfaces ordnen Rollennamen den Schnittstellen, dauerhaften Schreiboberflächen und Lesepfaden zu, die Automatisierung auf dem antwortenden Knoten erwarten sollte.
  • topology.shape_assignments ist das maschinenlesbare Prozessklasseninventar je unterstützter Form. Vergleichen Sie das aktuelle Rollenbündel damit, um den antwortenden Knoten einer dokumentierten Prozessklasse zuzuordnen.
  • topology.supported_topologies fasst unterstützte Bereitstellungsfamilien und deren erwartete Knotenklassen zusammen.
  • coordination_health fasst flottenweites Rollout- und Kompatibilitätsrisiko maschinenlesbar zusammen. Neben status und http_status kann es blocked_by, message und remediation melden, wenn vorgelagerte Bereitschaftsprobleme wie fehlende Migrationen oder Datenbankerreichbarkeit die Rollout-Sicherheitsbewertung blockieren.
  • coordination_health.checks[] enthält stets die feste Prüfung activity_path neben worker_compatibility, task_transport, routing_health, durable_resume_paths und den Projektions-/Scheduler-Prüfungen. activity_path ist das Aktivitätsgegenstück zu task_transport: Es zeigt Aktivitätsausführungen mit überschrittener, aber nicht durchgesetzter Schedule-to-start-, Start-to-close-, Schedule-to-close- oder Heartbeat-Frist (timeout_overdue, oldest_timeout_overdue_at, max_timeout_overdue_age_ms) sowie anhaltenden Aktivitätswiederholungsrückstau (retrying, oldest_retrying_started_at, max_retrying_age_ms). Eine Umbenennung ist eine Protokolländerung.
  • coordination_health.routing_drains fasst auslaufende Build-ID-Kohorten über Namespaces und Warteschlangen zusammen. queues_with_drains und die warteschlangenbezogenen build_ids zeigen, wo Verkehr bewusst von auslaufenden Workern ferngehalten wird.
  • execution_mode unterscheidet eingebettete local_queue_worker-Ausführung von remote_worker_protocol-Ausführung.
  • split_control_execution ist eine unterstützte Produkttopologie, kein zweites Server-Produkt und keine andere API.

Beispiel:

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/cluster/info" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: default" \
  | jq '{
    current_shape: .topology.current_shape,
    current_roles: .topology.current_roles,
    execution_mode: .topology.execution_mode,
    matching_role: .topology.matching_role,
    coordination_health: {
      status: .coordination_health.status,
      http_status: .coordination_health.http_status,
      blocked_by: .coordination_health.blocked_by,
      queues_with_drains: .coordination_health.routing_drains.queues_with_drains
    }
  }'

Den konzeptionellen Vertrag hinter diesen Feldern, einschließlich Rollenvokabular und Migrationspfad, erklärt Server-Rollentopologie.

Topologieablehnung bei falschem Knoten​

Authentifizierte gehostete Routen lehnen strikt ab, wenn der antwortende Knoten nicht die für den Endpunkt erforderliche HTTP-Steuerungsoberfläche hostet. Die Schranke läuft nach Rollen- und Protokollversionsprüfung, aber vor Namespace-Auflösung. Anfragen an falsche Knoten verraten daher keine Namespace-Existenz.

Blockiert die Schranke, liefert Server 503 mit reason: "topology_role_unavailable" sowie:

  • current_shape: gemeldete Topologieform des antwortenden Knotens.
  • current_process_class: deklarierte Prozessklasse, etwa scheduler_node oder execution_node.
  • current_roles: tatsächlich auf diesem Knoten gehostete Rollen.
  • required_roles: benötigte Rollen der gehosteten Route.
  • missing_roles: die auf dem antwortenden Knoten fehlende Teilmenge von required_roles.

Control-Plane-Routen liefern diese Nutzlast in ihrer Envelope. Worker-Protokollrouten liefern dieselben Felder in ihrer Envelope und behalten den normalen Worker-Protokollversions-Header.

Beispiel einer falschen Knotenantwort auf GET /api/workflows, wenn die Anfrage auf einem reinen Scheduler-Knoten landet:

{
  "reason": "topology_role_unavailable",
  "message": "This node does not host the topology roles required for this endpoint.",
  "current_shape": "standalone_server",
  "current_process_class": "scheduler_node",
  "current_roles": ["scheduler"],
  "required_roles": ["api_ingress", "control_plane"],
  "missing_roles": ["api_ingress", "control_plane"]
}

GET /api/health, GET /api/ready und authentifiziertes GET /api/cluster/info bleiben auch ohne aktuelle HTTP-Steuerungsoberfläche für Lebendigkeit und Erkennung verfügbar.

Workflow-Bootstrap-Schranke​

Authentifizierte Routen, die Workflow-v2-Verkehr ändern oder bedienen, lehnen ebenfalls strikt ab, wenn checks.workflow_v2.status des antwortenden Knotens blocked ist. Die Schranke läuft nach Rollen- und Protokollversionsprüfung, aber vor Namespace-Auflösung. Eine Anfrage während eines blockierten Rollouts erfährt niemals die Namespace-Existenz.

Die Schranke liefert 503 mit reason: "workflow_v2_blocked" sowie:

  • blocked_by: geordnete Liste vorgelagerter Bereitschaftsblocker (etwa migrations), die sicheren Workflow-v2-Betrieb verhindern.
  • remediation: kurze Betriebsanweisung zur Behebung, gespiegelt aus /api/ready checks.workflow_v2.remediation.

Die Bootstrap-geschützten Routenfamilien sind:

  • Workflow-Start und -Änderung: jede /api/workflows-Route der Start-, Beschreibungs-, Befehls- und laufbezogenen Befehlsgruppen (etwa POST /api/workflows, POST /api/workflows/{workflowId}/signal/{signalName}, POST /api/workflows/{workflowId}/runs/{runId}/cancel).
  • Zeitplanänderung: POST /api/schedules, PUT /api/schedules/{scheduleId}, DELETE /api/schedules/{scheduleId}, POST /api/schedules/{scheduleId}/pause, POST /api/schedules/{scheduleId}/resume, POST /api/schedules/{scheduleId}/trigger und POST /api/schedules/{scheduleId}/backfill.
  • Brückenadapter: POST /api/bridge-adapters/webhook/{adapter}.
  • Worker-Protokoll: jede Route /api/worker und /api/worker/*, einschließlich Registrierung, Heartbeat und Abfrage-/Abschluss-/Fehler-/Heartbeat-Operationen für Workflow-, Abfrage- und Aktivitäts-Tasks.

Zeitplan-Lesezugriffe sind bewusst ausgenommen, damit der Betrieb während Wiederherstellung Zeitplanzustand prüfen kann: GET /api/schedules, GET /api/schedules/{scheduleId} und GET /api/schedules/{scheduleId}/history bleiben verfügbar, während die Bootstrap-Schranke andere Routen blockiert.

Control-Plane-Routen liefern die Schranken-Nutzlast in der Control-Plane-Envelope mit X-Durable-Workflow-Control-Plane-Version. Worker-Protokollrouten liefern dieselben Felder reason, blocked_by und remediation in ihrer Envelope und behalten X-Durable-Workflow-Protocol-Version. Worker können so anhand des maschinenlesbaren Grunds verzweigen, statt aus einem bloßen 503 auf Warteschlangenzustand zu schließen.

Beispiel einer Bootstrap-Schranken-Antwort auf POST /api/workflows bei fehlender Rollout-Sicherheitsmigration:

{
  "reason": "workflow_v2_blocked",
  "message": "This node is not ready to serve workflow v2 traffic until bootstrap blockers are cleared.",
  "blocked_by": ["migrations"],
  "remediation": "Restore database connectivity and migrate the workflow tables before relying on workflow v2 rollout-safety health."
}

Dieselbe Nutzlast wird für /api/worker/* in der Worker-Protokoll-Envelope geliefert. Worker-SDKs können weiter nach reason verzweigen und nach Behebung des vorgelagerten Blockers erneut versuchen.

Namespace-bezogener Systemzustand​

GET /api/system/health ist die authentifizierte Rollout-Sicherheits- und Koordinationszustandsoberfläche eines Namespace. Sie benötigt Admin-Authentifizierung und X-Durable-Workflow-Control-Plane-Version: 2, löst den Namespace nach den normalen Control-Plane-Regeln auf und liefert den tatsächlich bewerteten Namespace mit aktuellem health-Snapshot:

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/system/health" \
  -H "Authorization: Bearer $DW_ADMIN_TOKEN" \
  -H "X-Namespace: orders-prod" \
  -H "X-Durable-Workflow-Control-Plane-Version: 2" \
  | jq '{namespace, status: .health.status, healthy: .health.healthy}'

Interpretieren Sie die Nutzlast so:

  • namespace: Namespace, dessen Rollout-/Koordinationszustand bewertet wurde.
  • health.status und health.healthy: oberstes maschinenlesbares Zustandsurteil dieses Namespace.
  • health.checks und health.categories: Bereitschafts-, Kompatibilitäts-, Projektions- und Koordinationsangaben je Oberfläche.
  • health.operator_metrics: aktueller Namespace-bezogener Warteschlangen-, Worker- und Reparaturmetrik-Snapshot.
  • health.structural_limits: wirksame strukturelle Grenzen und zugehörige Diagnosen, die Server für diesen Namespace erzwingt.

Workflow-Control-Plane​

Workflow-Routen sind Betriebs-/Control-Plane-Routen. Sie benötigen die Rolle Operator oder Admin und X-Durable-Workflow-Control-Plane-Version: 2.

MethodePfadZweck
GET/api/workflowsWorkflow-Instanzen auflisten. Unterstützt Filter wie Status, Typ, Abfragetext und Grenze.
POST/api/workflowsWorkflow-Instanz starten.
GET/api/workflows/{workflowId}Aktuellen Lauf einer Workflow-ID beschreiben.
GET/api/workflows/{workflowId}/debugBegrenzte Diagnoseangaben für festhängende Läufe liefern.
GET/api/workflows/{workflowId}/runsLäufe einer Workflow-ID auflisten.
GET/api/workflows/{workflowId}/runs/{runId}Bestimmten Lauf beschreiben.
GET/api/workflows/{workflowId}/runs/{runId}/debugBegrenzte Diagnoseangaben für ausgewählten Lauf liefern.
GET/api/workflows/{workflowId}/runs/{runId}/historyLaufhistorienereignisse seitenweise lesen.
GET/api/workflows/{workflowId}/runs/{runId}/history/exportReplay-Archivpaket eines Laufs exportieren.

Startanfragen verwenden die sprachneutrale Control-Plane-Struktur:

curl -sS -X POST "$DURABLE_WORKFLOW_SERVER_URL/api/workflows" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: default" \
  -H "X-Durable-Workflow-Control-Plane-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "workflow_type": "orders.fulfillment",
    "workflow_id": "order-1001",
    "task_queue": "orders",
    "input": ["order-1001"],
    "memo": {"source": "api-reference"},
    "search_attributes": {"CustomerId": "cust-42"},
    "duplicate_policy": "fail"
  }'

duplicate_policy akzeptiert nur fail und use-existing. Wird das Feld weggelassen oder als null gesendet, gilt fail. Beide Richtlinien erstellen einen Lauf, wenn die Workflow-ID noch nicht verwendet wurde.

RichtlinieEin aktiver Lauf existiert bereitsDer vorhandene Lauf ist geschlossen
fail (Standard)Den doppelten Start ablehnen.Den doppelten Start ablehnen.
use-existingDen vorhandenen ausstehenden, laufenden oder wartenden Lauf zurückgeben, ohne einen weiteren zu starten.Den doppelten Start ablehnen.

Keine der Richtlinien öffnet einen geschlossenen Lauf erneut. Verwenden Sie für eine neue Ausführung eine neue Workflow-ID. reject ist kein zulässiger Wert und führt zu HTTP 422.

Workflow-Befehle​

Server bietet auch kooperative request-cancellation-Routen. Kooperativer Abbruch beschreibt den Vertrag begrenzter Bereinigung und die Worker-Anforderungen.

Instanzbezogene Befehlsrouten arbeiten auf dem aktuellen Lauf einer Workflow-ID:

MethodePfadZweck
POST/api/workflows/{workflowId}/signal/{signalName}Signal senden.
POST/api/workflows/{workflowId}/query/{queryName}Schreibgeschützte Abfrage ausführen.
POST/api/workflows/{workflowId}/update/{updateName}Update übermitteln oder ausführen.
POST/api/workflows/{workflowId}/cancelLauf sofort als abgebrochen schließen; setzt Workflow-Bereinigung nicht fort.
POST/api/workflows/{workflowId}/terminateTerminierung erzwingen.
POST/api/workflows/{workflowId}/repairServer um Reparatur wiederholbaren festhängenden Zustands bitten.
POST/api/workflows/{workflowId}/archiveGeschlossenen Workflow-Lauf archivieren.

Laufbezogene Befehlsrouten lehnen historische oder falsche Laufziele explizit ab:

MethodePfadZweck
POST/api/workflows/{workflowId}/runs/{runId}/signal/{signalName}Signal nur senden, wenn der gewählte Lauf aktuell ist.
POST/api/workflows/{workflowId}/runs/{runId}/query/{queryName}Abfrage für den gewählten Lauf ausführen.
POST/api/workflows/{workflowId}/runs/{runId}/update/{updateName}Update nur übermitteln oder ausführen, wenn der gewählte Lauf aktuell ist.
POST/api/workflows/{workflowId}/runs/{runId}/cancelNur abbrechen, wenn der gewählte Lauf aktuell ist.
POST/api/workflows/{workflowId}/runs/{runId}/terminateNur terminieren, wenn der gewählte Lauf aktuell ist.
POST/api/workflows/{workflowId}/runs/{runId}/repairNur reparieren, wenn der gewählte Lauf aktuell ist.
POST/api/workflows/{workflowId}/runs/{runId}/archiveNur archivieren, wenn der gewählte Lauf aktuell und geschlossen ist.

Befehle übertragen Geschäftswerte in Avro-Envelopes. Die offiziellen SDKs codieren sie automatisch. Direkte HTTP-Clients müssen den {codec, blob}-Envelope des offiziellen Avro-Encoders oder die unten beschriebene Runtime-Referenz verwenden. Das äußere HTTP-Dokument ist JSON; uncodiertes Geschäfts-JSON ist kein alternativer Nutzlast-Codec.

Namespace und Speicher​

Namespace-Routen benötigen Operator- oder Admin-Rollen. Ändernde Namespace- und externe Speicherrouten benötigen die Admin-Rolle.

MethodePfadZweck
GET/api/namespacesNamespaces auflisten.
POST/api/namespacesNamespace erstellen.
GET/api/namespaces/{namespace}Aufbewahrung, Metadaten und Speicherrichtlinie eines Namespace beschreiben.
PUT/api/namespaces/{namespace}Namespace-Metadaten oder Aufbewahrung aktualisieren.
PUT/api/namespaces/{namespace}/external-storageExterne Nutzlastspeicherrichtlinie des Namespace konfigurieren.
POST/api/storage/testKleine und große Nutzlast über konfigurierten externen Speichertreiber schreiben und zurücklesen.

Externe Nutzlastspeicherrichtlinien ersetzen rohe Bytes großer Envelopes durch stabile Referenzen. Lokale Richtlinien lösen über den konfigurierten Dateisystempfad auf. Objektspeicherrichtlinien wie s3, gcs und azure verwenden einen explizit konfigurierten Dateisystem-Datenträger sowie Bucket-/Präfixeinstellungen auf dem Server.

Externe Nutzlastreferenz-Envelope​

Server akzeptiert Runtime-Referenzen, nicht die Anbieter-URI-Referenzen eingebetteter Speicherhelfer. Eine Anfrage mit external_storage wird mit HTTP 422 und external_payload_unsupported abgelehnt. Übernehmen Sie keine Anbieterreferenz mit file://, s3://, gs:// oder azure:// in Server-Anfragen.

Der Runtime-Envelope enthält genau codec und external_payload:

{
  "codec": "avro",
  "external_payload": {
    "schema": "durable-workflow.v2.runtime-external-payload-reference.v1",
    "reference_id": "ep_01ARZ3NDEKTSV4RRFFQ69G5FAV",
    "codec": "avro",
    "size_bytes": 1048576,
    "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  }
}

ID und Hash sind illustrative Beispiele. Verwenden Sie unverändert die Referenz eines tatsächlichen Uploads. Die verschachtelte Referenz enthält genau fünf Felder:

FeldErforderlichBedeutung
schemajadurable-workflow.v2.runtime-external-payload-reference.v1.
reference_idjaOpake Server-ID: ep_ gefolgt von 26 großgeschriebenen ULID-Zeichen. Keine Anbieter-URI.
codecjaavro, passend zum äußeren Envelope.
size_bytesjaNichtnegative ganzzahlige Größe der hochgeladenen codierten Bytes.
sha256jaSHA-256 genau dieser Bytes, als kleingeschriebene Hexadezimalzahl zurückgegeben.

Externer Runtime-Nutzlasttransport​

Ermitteln Sie namespace.external_payload_storage.transport über GET /api/cluster/info. Das Schema lautet durable-workflow.v2.runtime-external-payload-transport.v1, Version 1. Verwenden Sie seine Routen und Limits nur bei Namespace-Speicherstatus available. Der Server hält Anbieter-Zugangsdaten und liefert keine Anbieter-Speicherorte aus.

MethodePfadErgebnis
POST/api/external-payloads/v1Lädt begrenzte codierte Bytes hoch. 201 liefert Schema durable-workflow.v2.runtime-external-payload-upload.v1, transport_version: 1 und reference.
GET/api/external-payloads/v1/{referenceId}Lädt und prüft die referenzierten codierten Bytes. 200 liefert application/octet-stream.

Beide Routen verwenden normale Runtime-Zugangsdaten mit Rolle worker, operator oder admin und X-Namespace. Beide benötigen X-Durable-Workflow-Payload-Codec, X-Durable-Workflow-Payload-Size und X-Durable-Workflow-Payload-SHA256. Uploads benötigen zusätzlich Content-Type: application/octet-stream. Namespace-übergreifende Suche meldet nicht gefunden, ohne fremde Objekte offenzulegen. Der Besitz einer ID gewährt weder Zugriff noch die Befugnis, einen Workflow abzuschließen.

Hochgeladen werden die UTF-8-Bytes der base64-Zeichenfolge blob aus dem offiziellen Avro-Envelope, ohne angehängten Zeilenumbruch. Es handelt sich weder um decodiertes binäres Avro noch um Geschäfts-JSON. Berechnen Sie Länge und SHA-256 exakt über diese Bytes. Beispiel nach Installation des Python-SDK:

python - <<'PY'
from pathlib import Path
from durable_workflow.serializer import encode

Path("payload.avro.txt").write_bytes(
    encode([{"message": "large value", "optional": None}]).encode("utf-8")
)
PY

PAYLOAD_SIZE=$(wc -c < payload.avro.txt | tr -d ' ')
PAYLOAD_SHA256=$(sha256sum payload.avro.txt | cut -d ' ' -f 1)

curl --fail-with-body -sS -X POST "$DURABLE_WORKFLOW_SERVER_URL/api/external-payloads/v1" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: billing" \
  -H "Content-Type: application/octet-stream" \
  -H "X-Durable-Workflow-Payload-Codec: avro" \
  -H "X-Durable-Workflow-Payload-Size: $PAYLOAD_SIZE" \
  -H "X-Durable-Workflow-Payload-SHA256: $PAYLOAD_SHA256" \
  --data-binary @payload.avro.txt > upload.json

REFERENCE_ID=$(jq -r '.reference.reference_id' upload.json)
curl --fail-with-body -sS "$DURABLE_WORKFLOW_SERVER_URL/api/external-payloads/v1/$REFERENCE_ID" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: billing" \
  -H "X-Durable-Workflow-Payload-Codec: avro" \
  -H "X-Durable-Workflow-Payload-Size: $PAYLOAD_SIZE" \
  -H "X-Durable-Workflow-Payload-SHA256: $PAYLOAD_SHA256" \
  -o fetched.avro.txt
cmp payload.avro.txt fetched.avro.txt

Der Upload prüft die Byteintegrität vor dem Speichern einer Referenz. Er führt keinen Workflow aus und beweist nicht, dass die Bytes eine gültige Geschäftsnutzlast sind. Die erste geprüfte zustandsbehaftete Anfrage beansprucht die Referenz. Nutzlastvalidierung und normale Anfrage-, Namespace-, Aufgabenversuchs- und Lease-Prüfungen gelten weiter. Verwenden Sie für Worker-Abschlussuploads das offizielle SDK und dessen ermittelten Abschlusskontext, statt in einem direkten Client eine Lease-Freigabe zu erfinden.

Lesen Sie limits.max_payload_bytes, request_timeout_seconds und abandoned_upload_expiry_seconds aus dem Transportmanifest. Namespace-Byte- und Objektkontingente, normale Anfragelimits sowie Abschlussupload-Limits gelten ebenfalls. Nach dem Schwellenwertkriterium bleibt ein gleich großer Wert inline. SDKs lagern größere Werte aus und können weitere Werte auslagern, damit die gesamte Anfrage passt.

ErgebnisHTTP-StatusHandlung
Fehlende oder abgelaufene Referenz404 / 410Stellen Sie das benötigte Objekt wieder her oder korrigieren Sie die Referenz. Decodieren Sie einen fehlenden Wert nicht als null.
Nicht autorisiert401 / 403Korrigieren Sie Zugangsdaten, Rolle oder Namespace-Berechtigung.
Nicht unterstützter Envelope oder Integritätsfehler415 / 422Korrigieren Sie Codec, Felder, Größe, Hash oder codierte Bytes.
Zu große Nutzlast413Verkleinern Sie den codierten Wert oder verwenden Sie eine zulässige größere Richtlinie.
Namespace-Kontingent oder Upload-Freigabe erschöpft429Prüfen Sie Kapazität und wiederholen Sie nur innerhalb des ursprünglichen Operationsbudgets.
Speicher nicht verfügbar503Stellen Sie Verfügbarkeit her, bevor Sie innerhalb desselben Budgets wiederholen.
Veralteter oder widersprüchlicher Abschluss409Wiederholen Sie nicht mit erfundener Aufgabenidentität oder neuer Lease.

Der Server steuert die Aufbewahrung. Es gibt keine Client-Löschroute. Cache-Verdrängung darf das Objekt nicht löschen. Unbeanspruchte Uploads können ablaufen; aufbewahrte Eigentümer, gemeinsame Objekte, Speicherfehler und Backup-Sperren beeinflussen die Bereinigung. Ein Verlaufsexport mit Referenzen ist kein eigenständiges Backup ihrer Bytes.

404Namespace, Workflow, Lauf, Zeitplan, Worker oder Suchattribut nicht gefunden.
409Duplikat oder Konflikt, etwa bereits gestarteter Workflow oder ungültiges Laufziel.
422Validierung fehlgeschlagen; Antwort enthält Details je Feld.
429Zulassungs- oder Task-Warteschlangenkapazität ist voll.
503Anfrage erreichte einen Knoten ohne die erforderlichen Topologierollen. Gehostete Routen liefern reason: "topology_role_unavailable" mit current_shape, current_process_class, current_roles, required_roles und missing_roles. Derselbe Status mit reason: "workflow_v2_blocked", blocked_by und remediation gilt für Workflow-Start/-Änderung, Zeitplanänderung, Brückenadapter und Worker-Protokoll, während Workflow-v2-Bootstrap blockiert ist. Zeitplan-Leserouten (GET /api/schedules, GET /api/schedules/{scheduleId}, GET /api/schedules/{scheduleId}/history) bleiben zur Inspektion während Wiederherstellung verfügbar.
500Serverfehler. Nur als wiederholbar behandeln, wenn die Operation idempotent ist oder einen Idempotenzschlüssel hat.

Validierungsantworten enthalten reason: "validation_failed" plus errors oder validation_errors. Workflow-Befehlsantworten projizieren Validierungs- und Operationsdetails zusätzlich in das verschachtelte Objekt control_plane.

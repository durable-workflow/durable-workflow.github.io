Workflow-Streams

Workflow-Streams sind benannte, laufgebundene Ausgabeprotokolle unter der Verantwortung von Durable Workflow Server. PHP, Python und Rust bieten typisierte Operationen zum Auflisten, Beschreiben, Abonnieren, Anhängen, Schließen und Melden von Fehlern, sodass Anwendungen keine HTTP-Anfragen zusammenstellen müssen. Die Runtime meldet durable-workflow.v2.workflow-streams.contract@1. Die maschinenlesbare SDK-Matrix hält die genaue Unterstützung jedes SDKs fest.

Jeder Stream vergibt monoton steigende Offsets ab 0. next_offset einer Seite ist der nächste inklusiv anzufordernde Offset. Verbraucher erhalten Elemente mindestens einmal: Schließen Sie die idempotenten Effekte der Seite ab und speichern Sie anschließend next_offset dauerhaft als Checkpoint. Ein Absturz vor diesem Checkpoint kann zur erneuten Zustellung von Elementen führen.

Aus Workflow-Code ausgeben​

Die drei SDKs erzeugen Ausgaben an derselben deterministischen Befehlsgrenze: record_side_effect.workflow_stream. Jedes SDK leitet den Idempotenzschlüssel eines Elements aus der dauerhaften Workflow-Befehlsidentität des Tasks, der Ordnungsnummer des Stream-Befehls und dem Batch-Index ab. Server schreibt die Stream-Änderung und den aufgezeichneten Seiteneffekt gemeinsam fest. Replay verbraucht diesen Seiteneffekt und kann für dasselbe logische Anhängen kein weiteres dauerhaftes Element erzeugen.

PHP:

use DurableWorkflow\Model\WorkflowStreamAppendItem;

$context->appendWorkflowStream('progress', [
    new WorkflowStreamAppendItem(['percent' => 50]),
]);
$context->closeWorkflowStream('progress');

Python:

from durable_workflow import WorkflowStreamAppendItem

yield ctx.append_workflow_stream("progress", [
    WorkflowStreamAppendItem(payload={"percent": 50}),
])
yield ctx.close_workflow_stream("progress")

Rust:

let item = WorkflowStreamAppendItem::new(serde_json::json!({"percent": 50}))?;
ctx.append_workflow_stream("progress", &[item], None)?;
ctx.close_workflow_stream("progress", None)?;

Die Workflow-Hilfsmethoden dienen der deterministischen Implementierung. Code außerhalb eines Workflows kann die typisierte append-Operation des jeweiligen Clients verwenden und einen eigenen stabilen Idempotenzschlüssel angeben.

Abonnieren und fortsetzen​

Ein Abonnement liest eine begrenzte Seite und wartet optional bis zu 60 Sekunden auf neue Elemente. PHP akzeptiert einen Abbruch-Callback zwischen begrenzten Abfragen. Python akzeptiert den normalen Task-Abbruch oder ein asyncio.Event, das die laufende Abfrage abbricht. Das Verwerfen des Rust-Abonnement-Futures bricht dessen Anfrage ab.

SDKSeitenoperationWert zum FortsetzenTypisierte Iteration
PHPsubscribeWorkflowStream(...)WorkflowStreamPage::$nextOffsetiterateWorkflowStream(...)
Pythonawait subscribe_workflow_stream(...)WorkflowStreamPage.next_offsetiter_workflow_stream(...)
Rustsubscribe_workflow_stream(...).awaitWorkflowStreamPage::next_offsetDas begrenzte Seiten-Future wiederholen, bis terminal erreicht ist.

open, closed und errored sind die Lebenszykluszustände. Die typisierte Beschreibung enthält außerdem last_offset, total_items, pending_items und error_reason. Das Anhängen an einen terminalen Stream wird abgelehnt. Wenn die konfigurierte Grenze ausstehender Elemente erreicht ist, liefert Anhängen stream_full. Erzeuger müssen langsamer werden oder warten, bis Verbraucher den Stream abgearbeitet haben.

Externe Nutzlastreferenzen​

Inline-Werte verwenden die gemeinsame Avro-Value-Envelope. Externe Referenzen folgen dem bestehenden Speichervertrag des jeweiligen SDKs, statt einen weiteren Transport einzuführen:

SDKVerhalten externer Referenzen
PHPHängt eine opake payload_reference an und gibt sie zurück; Hochladen und Abrufen des Speichers bleiben Aufgabe der Anwendung.
PythonVerwendet den konfigurierten Treiber für externen Speicher zum Hochladen, Prüfen der Integrität, Zwischenspeichern, Abrufen und Decodieren einer externen Avro-Envelope. Ohne Treiber können Aufrufer eine opake payload_reference anhängen oder untersuchen.
RustHängt eine opake Referenz samt Metadaten an und gibt sie zurück. Das aktuelle Rust SDK beansprucht keinen Treiber für externen Speicher.

Workflow-Streams und eingebetteter MessageStream​

Die Namen stimmen dort überein, wo das Verhalten übereinstimmt. Die Modelle sind jedoch nicht austauschbar.

KonzeptWorkflow-Stream im Service-ModusEingebetteter Laravel MessageStream
AdresseWorkflow-Lauf + Stream-NameWorkflow-Instanz/-Lauf + Stream-Schlüssel
RichtungNur Workflow-AusgabeWorkflow-Posteingang und -ausgang
Erster Offset01
ZustellungMindestens einmal; Checkpoint durch den Verbraucher verwaltetMindestens einmal; Nachrichten-Cursor durch die Engine verwaltet
Continue-as-newKeine Übertragung des Stream-CursorsPosteingangs-Cursor wird auf den fortgesetzten Lauf übertragen
Eingehende Workflow-NachrichtenNicht angeboten; Signale oder Updates verwendenÜber inbox()->receive() angeboten

Waterline verwendet eine normalisierte Tabelle für beide Modi und zeigt Modus, Lebenszyklus, Kopf-/Cursor-Offsets, Anzahl ausstehender Elemente, Richtung und Fehler. Es stellt Service-Ausgabestreams nicht als eingehenden Workflow-Posteingang dar.

Qualifizierung​

Das öffentliche Workflow-Stream-Szenariomanifest verlangt Läufe mit veröffentlichten Artefakten für einen PHP-Erzeuger mit Python- und Rust-Verbrauchern, Neustart des erzeugenden Workers, Wiederverbindung des Verbrauchers, Lebenszyklus/Rückstaukontrolle/Abbruch und externe Nutzlastreferenzen. Ein Release-Ergebnis muss jedes erforderliche Szenario aufzeichnen. Reine Quellcode-Unit-Tests sind kein Konformitätsnachweis.

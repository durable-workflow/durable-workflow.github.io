Konfigurationsreferenz für Server

Diese Seite beschreibt den Vertrag der Umgebungsvariablen DW_* für Betreiber des Durable Workflow Server-Images. Nutzen Sie sie für Bereitstellungsvorlagen, die Prüfung der Produktionskonfiguration und die Umstellung älterer Namen WORKFLOW_* / ACTIVITY_* auf den Server-v2-Vertrag.

Server verwendet außerdem gewöhnliche Laravel-Einstellungen wie DB_*, REDIS_*, QUEUE_CONNECTION und CACHE_STORE. Diese Infrastrukturvariablen sind gesondert aufgeführt, weil sie die Bereitstellung konfigurieren und keine Durable Workflow API-Einstellungen darstellen.

Wann Änderungen wirksam werden​

Das veröffentlichte PHP Server-Image führt in seinem Einstiegsskript php artisan config:cache aus. Die Umgebungswerte werden beim Start aufgelöst und in den Laravel-Konfigurationscache geschrieben. Änderungen an einer Umgebungsdatei, an der Umgebungsdeklaration des Orchestrators oder an einer eingebundenen Konfigurationsdatei laden eine laufende Bereitstellung nicht neu.

Starten oder ersetzen Sie jeden betroffenen Prozess mit der neuen Konfiguration: HTTP-API-Replikate, lokale Laravel-Queue-Worker und Scheduler-Prozesse. Starten Sie langlebige SDK-Worker gesondert neu, wenn sich deren eigene Client- oder Worker-Konfiguration ändert. Ein erfolgreicher API-Neustart aktualisiert keinen weiterlaufenden Queue-Worker oder Scheduler. Rollen mit gemeinsamer Datenbank und gemeinsamem Cache benötigen eine einheitliche Konfiguration.

Bei einer schrittweisen Änderung setzt jeder Knoten seine eigenen geladenen Grenzen durch. Gemeinsame Zulassungszähler gleichen unterschiedlich konfigurierte Grenzen nicht an. Daher kann ein API-Replikat eine Anfrage annehmen, die ein anderes ablehnt. Wenn eine neue Grenze einheitlich gelten muss:

  1. Pausieren Sie neue Anfragen der Aufrufer und nehmen Sie betroffene API-Replikate aus dem Ingress. Lassen Sie laufende Anfragen abschließen. Beenden Sie betroffene Queue- und Scheduler-Rollen innerhalb ihrer Abschaltbudgets geordnet.
  2. Wenden Sie dieselbe Konfiguration auf alle betroffenen Rollen an und starten oder ersetzen Sie sie. Das Einstiegsskript jedes Containers baut dessen Konfigurationscache neu auf.
  3. Prüfen Sie Startprotokolle auf Konfigurationsfehler, prüfen Sie die Bereitschaft und testen Sie die geänderte Grenze, bevor Sie Ingress und neue Aufruferanfragen wieder freigeben. Siehe den Leitfaden zu Bereitstellung und Bereitschaft.

In der Datenbank gespeicherte Betriebseinstellungen haben einen anderen Lebenszyklus. Erfolgreiche Änderungen in der folgenden Tabelle stehen nachfolgenden Vorgängen ohne Server-Neustart zur Verfügung:

EinstellungÄnderung ohne NeustartGeltung und Grenzen
Namespace-Beschreibung und AufbewahrungPUT /api/namespaces/{namespace} oder dw namespace:updateDie Regel steuert spätere Aufbewahrungsdurchläufe. Ihre Änderung stellt bereits entfernte Daten nicht wieder her. Siehe Server-Aufbewahrung.

Die DW_*-Standardwerte und Obergrenzen dieser Referenz bleiben Prozesskonfiguration, sofern ein dokumentierter Steuerungsvorgang nicht ausdrücklich gespeicherten Zustand ändert. Server fragt Konfigurationsdateien nicht regelmäßig auf Änderungen ab.

Prüfung des Vertrags​

Im Server-Repository liegt der maßgebliche Vertrag in config/dw-contract.php. Beim Containerstart warnt php artisan env:audit vor unbekannten DW_*-Variablen und alten Namen. Mit DW_ENV_AUDIT_STRICT=1 schlägt das Einstiegsskript fehl, anstatt mit Warnungen zu starten.

DW_ENV_AUDIT_STRICT=1
DW_AUTH_DRIVER=token
DW_ADMIN_TOKEN="${DW_ADMIN_TOKEN}"
DW_OPERATOR_TOKEN="${DW_OPERATOR_TOKEN}"
DW_WORKER_TOKEN="${DW_WORKER_TOKEN}"

Alte Namen dienen nur als Rückfalloption. Verwenden Sie bei neuen Bereitstellungen den Namen DW_*. Eine Warnung über einen alten Namen bedeutet eine noch nicht abgeschlossene Migration, auch wenn Server den Wert weiterhin berücksichtigt.

  }

Veröffentlichte Fingerabdruckpräferenz. Server 2.9.9 macht die Bevorzugung des Fingerabdrucks für Service-Worker wirksam. Bei aktivierter Bindung darf nur dann auf eine geänderte Definition ausgewichen werden, wenn kein geeigneter Worker mit der aufgezeichneten Definition mehr vorhanden ist und der Ersatz workflow_entry_arguments_validation ankündigt. Bei deaktivierter Bindung entfällt die Quellcodepräferenz; Build-Bindungen, Namespace-/Warteschlangen-/Typisolation, Registrierungsidentität und striktes Replay bleiben bestehen. Der zugehörige Einstiegsschutz ist ab PHP SDK 2.5.4, Python SDK 2.6.2 und Rust SDK 3.5.6 verfügbar. Dies sind Mindestversionen für diese Funktionen; installieren Sie aktuelle stabile Versionen mit Sicherheitskorrekturen. Nehmen Sie dieses Verhalten auf älteren Laufzeiten nicht allein deshalb an, weil deren Konfiguration denselben Schlüssel enthält. Siehe Routing nach Definition.

Verwenden Sie DW_V2_GUARDRAILS_BOOT in CI und Bereitstellungsmanifesten. Der alte Name WORKFLOW_V2_GUARDRAILS_BOOT bleibt nur erhalten, damit env:audit Betreiber von Alpha-Versionen auf die Umbenennung hinweisen kann. Das Workflow-Paket liest ihn nicht mehr als Rückfallwert zur Laufzeit.

Lesen Sie Aufgabenzuordnung und Zustellung, wenn Sie DW_V2_MATCHING_ROLE_QUEUE_WAKE oder einen eigenen workflow:v2:repair-pass --loop-Daemon konfigurieren. Diese Einstellungen ändern den Ort der Erkennung bereiter Aufgaben, nicht den Worker-Protokollvertrag.

Datenbank-TLS​

Setzen Sie dieselben TLS-Einstellungen für API-Server, Queue-Worker, Bootstrap-/Migrationsjob und Scheduler. PostgreSQL verwendet standardmäßig prefer; MySQL/MariaDB behalten ohne Modus ihre Verbindungsstandards. Keiner dieser Standards garantiert eine authentifizierte, verschlüsselte Verbindung.

DB_SSLMODEPostgreSQLMySQL / MariaDB
disableKein TLS.Kein TLS; widersprüchliche TLS-Optionen werden abgelehnt.
allow, preferOpportunistisches TLS ohne Verschlüsselungs- oder Identitätsgarantie.Abgelehnt.
requireVerschlüsselung erforderlich.Verschlüsselung mit mysqlnd und OpenSSL erforderlich.
verify-caVerschlüsselung und vertrauenswürdige Zertifikatskette erforderlich.Abgelehnt: PDO mysqlnd kann die Kette nicht unabhängig vom Hostnamen prüfen.
verify-fullVerschlüsselung, vertrauenswürdige Kette und passender Hostname erforderlich.Verschlüsselung, vertrauenswürdige Kette und passender Hostname erforderlich.

DB_SSL_MODE ist ein Alias für DB_SSLMODE, DB_SSL_ROOT_CERT für DB_SSLROOTCERT. Mounten Sie zur Zertifikatsprüfung ein lesbares CA-Bundle am konfigurierten Pfad in jeder Rolle, auch für Migrationen. MYSQL_ATTR_SSL_CA kann die CA für explizites MySQL-/MariaDB-verify-full liefern. Widersprüche zwischen kanonischen Einstellungen, Aliasen oder URL verhindern den Start. Erforderliches TLS braucht einen expliziten TCP-Hostnamen; Unix-Sockets werden abgelehnt. Explizite MySQL-/MariaDB-TLS-Modi benötigen PDO MySQL mit mysqlnd und OpenSSL.

DB_CONNECTION=pgsql
DB_HOST=database.example.com
DB_SSLMODE=verify-full
DB_SSLROOTCERT=/run/database-ca/ca.pem

Verwenden Sie den DNS-Hostnamen des Zertifikats. Konfigurieren Sie in Helm externalDatabase.sslMode und externalDatabase.tls.existingSecret / caKey. Erstellen Sie das Secret vor Installation oder Upgrade; das Chart mountet die CA in allen vier Rollen einschließlich Bootstrap-Hook. Starten Sie dauerhafte Rollen nach Umgebungsänderungen neu, da die Konfiguration beim Start gecacht wird.

Container-Protokolle​

Setzen Sie LOG_CHANNEL=stderr für API-, Worker- und Scheduler-Container, damit docker logs oder kubectl logs die Anwendungsprotokolle erfassen kann. Setzen Sie die Variable bei bestehenden Versionen ausdrücklich. Mit LOG_LEVEL wählen Sie den Mindestschweregrad. Für JSON mit einem Datensatz pro Zeile setzen Sie zusätzlich:

LOG_STDERR_FORMATTER="Monolog\Formatter\JsonFormatter"

Starten Sie dauerhafte Prozesse nach Änderungen neu, da die Konfiguration beim Start zwischengespeichert wird. Ein ausdrücklich gewählter Dateikanal benötigt eigene Speicherung und Erfassung; Kubernetes erfasst storage/logs/laravel.log nicht automatisch. DW_LOG_FORMAT wird nicht unterstützt.

Hinweise zur Migration​

Stellen Sie bei der Migration einer älteren Bereitstellung auf den öffentlichen Namen um und lassen Sie den alten Namen ungesetzt. Falls beide vorhanden sind, ist der DW_*-Wert für die Betriebsplanung maßgeblich; entfernen Sie den alten Namen.

# Before
WORKFLOW_SERVER_AUTH_DRIVER=token
WORKFLOW_SERVER_OPERATOR_TOKEN=operator-secret

Python SDK

Das Python SDK ist ein schlanker, vorrangig asynchroner Client für einen selbst gehosteten Durable Workflow Server oder eine Cloud-Namespace-Laufzeitumgebung. Python-Prozesse können über deren Control-Plane-API Workflows starten, beobachten, signalisieren und abbrechen sowie sich als Worker zur Ausführung von Workflow-Tasks und Aktivitäten registrieren.

Die lokale Testumgebung der Sample App ausprobieren​

Für den kürzesten Implementierungsweg ohne Cloud öffnen Sie den aktuellen main-Branch der Sample App in GitHub Codespaces und führen Sie aus:

scripts/playground python

Die lokale Testumgebung erzeugt Workflow- und Aktivitätsquellcode unter der Verantwortung des Aufrufers, wählt aktuelle stabile Artefakte und startet die veröffentlichten Server- und Waterline-Versionen. Vor dem Workflow-Start wartet sie auf eine Worker-Registrierung, deren Identität, Workflow-Typ, Aktivitätstyp und Task-Warteschlange zum erzeugten Vertrag passen. Erfolg erfordert das erwartete abgeschlossene Ergebnis und die Historie. Danach gibt das Terminal den genauen lokalen Waterline-Lauflink und den Pfad zum strukturierten JSON-Nachweis aus.

Paketinstallation, Inline-Schnellstart, API-Referenz und Repository-Beispiel unten bleiben die direkten Wege ohne Sample App.

Verwaltete Laufzeitumgebung

Durable Workflow Cloud

Führen Sie Python-Clients und -Worker mit getrennten rollenspezifischen Zugangsdaten gegen einen Cloud-verwalteten Namespace aus.

Cloud-Dev-Preise ansehen

Das SDK verwendet dasselbe dauerhafte Modell wie das PHP-Paket: Instanz-IDs, Lauf-IDs, Historienereignisse, Task-Warteschlangen und Typschlüssel sind sprachübergreifend gemeinsam. Ein Python-Worker kann Aktivitäten eines in PHP implementierten Workflows bedienen und umgekehrt.

Den Fähigkeitsvergleich von Python SDK, PHP SDK, Rust SDK und dw bietet Client- und Worker-Fähigkeiten.

Konstruktorsignaturen, Rückgabetypen, Ausnahmeklassen und Metriknamen stehen in der generierten Python-SDK-API-Referenz.

Python SDK 2.5.0 ergänzt einen optionalen begrenzten Historiencache für Sticky-Ausführung. Verwenden Sie Server 2.5.10 oder neuer und aktivieren Sie ihn auf jedem Worker. Siehe Portable Worker-Affinität und den Python-Leitfaden mit ausführbarem Beispiel.

Cloud-Kunden verwenden Laufzeit-URL und Namespace des bereitgestellten Namespace mit getrennten Client- und Worker-Zugangsdaten. Die Verbindungsgrenze beschreibt Verwaltete Cloud-Laufzeitumgebung. Der Schnellstart unten verwendet lokale selbst gehostete Werte.

Voraussetzungen​

  • Python 3.10 oder neuer
  • Docker für den lokalen Server dieses Schnellstarts, ein bestehender selbst gehosteter Server oder eine bereitgestellte Cloud-Namespace-Laufzeitumgebung

Installation​

Installieren Sie das stabile Python-SDK-Release. Die genaue Anforderung wird aus demselben Tupel wie der Server-Schnellstart erzeugt. Eine Lock- oder Constraints-Datei kann sie für Reproduzierbarkeit festhalten.

pip install durable-workflow==2.8.0

Das SDK verwendet httpx für HTTP und das Python-Paket fastavro zum Codieren des Apache-Avro-Übertragungsformats des einzigen öffentlichen v2-Nutzlast-Codecs. Prometheus-Metriken sind optional.

Schnellstart​

Dieses vollständige Python-Programm definiert einen Workflow mit einer Aktivität, startet ihn gegen einen lokalen Durable Workflow Server und wartet auf das Ergebnis:

import asyncio
import uuid

from durable_workflow import Client, Worker, workflow, activity

@activity.defn(name="greet")
async def greet(name: str) -> dict:
    return {"greeting": f"Hello, {name}!", "length": len(name)}

@workflow.defn(name="greeter")
class GreeterWorkflow:
    def run(self, ctx, *args):
        result = yield ctx.schedule_activity("greet", list(args))
        return result

async def main():
    workflow_id = f"greeting-{uuid.uuid4().hex}"

    async with Client("http://localhost:8080", token="dev-token", namespace="default") as client:
        handle = await client.start_workflow(
            workflow_type="greeter",
            task_queue="default",
            workflow_id=workflow_id,
            input=["world"],
        )

        worker = Worker(
            client,
            task_queue="default",
            workflows=[GreeterWorkflow],
            activities=[greet],
        )

        await worker.run_until(workflow_id=workflow_id, timeout=30.0)
        result = await handle.result(timeout=10.0)

    print(result)  # {"greeting": "Hello, world!", "length": 5}

asyncio.run(main())

Das Programm oben setzt einen unter http://localhost:8080 erreichbaren Durable Workflow Server mit lokalem dev-token voraus. Falls noch keiner läuft, ist das veröffentlichte Server-Image der schnellste Weg ohne Quellcode:

Client-API-Referenz​

Der asynchrone durable_workflow.Client ist der öffentliche Einstiegspunkt für Control-Plane- und Worker-Plane-HTTP-Aufrufe. Verwenden Sie ihn als asynchronen Kontextmanager, damit der zugrunde liegende Verbindungspool von httpx.AsyncClient sauber geschlossen wird.

from durable_workflow import Client

async with Client(
    "https://workflow.example.com",
    token="shared-token",
    namespace="default",
    timeout=60.0,
) as client:
    info = await client.get_cluster_info()

Begrenzte Fehlerberichte​

Das Python SDK 2.11.0 führte begrenzte ausgehende Fehlerberichte ein. Standardmäßig gelten 62 KiB UTF-8 für die Meldung, 128 KiB für den Stack, 64 KiB für gemeinsam serialisierte optionale Details und Diagnosen und 1 MiB für den vollständigen HTTPX-codierten Body. Markierungen, JSON-Escaping, die Claim-Identität und weitere Befehle im Batch zählen zum Body-Limit. Ein niedrigeres konfiguriertes oder erkanntes Transportlimit hat Vorrang. Fehlertyp, Klasse, Code, Retry-Regeln und Claim-Identität bleiben erhalten.

Bei Bedarf lässt sich das Body-Budget verkleinern. Einstellungen für Warnungen zur Payload-Größe bleiben reine Hinweise.

from durable_workflow import Client

async with Client(
    "https://workflow.example.com",
    worker_token="worker-token",
    control_token="operator-token",
    failure_report_limit_bytes=512 * 1024,
) as client:
    info = await client.get_cluster_info()

Eine sichtbare Kürzungsmarkierung und die ursprünglichen Byte-Anzahlen kennzeichnen gekürzte Felder. Avro-Details bleiben vollständig erhalten oder werden als Ganzes weggelassen. Ein nicht darstellbarer erforderlicher Umschlag löst vor der HTTP-Übertragung FailureReportTooLarge aus. Lokale Fehler werden normalisiert, bevor der Workflow-Code sie beobachtet. Dadurch sehen die erste Ausführung und ein kalter Replay dieselbe gespeicherte Meldung. Eine bereits beobachtete lokale Meldung bleibt bei der abschließenden Größenanpassung des Batches unveränderlich.

Externer Nutzlastspeicher​

Normale Client- und Worker-Operationen verwenden automatisch den authentifizierten Runtime-Transport von Server. Das SDK ermittelt Richtlinie und Limits über GET /api/cluster/info, lädt codierte Werte über dem Schwellenwert oder bei Bedarf zum Einhalten des Anfragelimits hoch und lädt Referenzwerte vor dem Decodieren. Workflow- und Aktivitätscode erhalten den decodierten Wert. Anbieter-Zugangsdaten bleiben auf dem Server. Entfernte Worker benötigen weder boto3 noch Anbieter-Clients oder Zugriff auf das lokale Server-Verzeichnis.

Die Runtime-Referenz verwendet Schema durable-workflow.v2.runtime-external-payload-reference.v1 und eine opake reference_id. Sie enthält keine Anbieter-uri. Upload und Abruf verwenden normale Rollen-Zugangsdaten und den Namespace, prüfen Größe und SHA-256 und erhalten die Aufgabenversuchs- und Lease-Abgrenzung beim Worker-Abschluss. Der HTTP-Vertrag beschreibt Routen, Limits und typisierte Ablehnungen. Unterstützung erfordert einen verfügbaren kompatiblen Transport, nicht nur einen konfigurierten Treiber.

Die folgenden direkten Anbieterhelfer dienen anwendungseigenem Speicher und Tests, die bewusst auf ihren eigenen Anbieter zugreifen. Sie verwenden ein anderes URI-Schema. Normale Server- oder Cloud-Clients benötigen sie nicht. Server lehnt Anbieter-Envelopes external_storage mit HTTP 422 und external_payload_unsupported ab.

Für diese direkten Helfer lautet das Referenzschema EXTERNAL_PAYLOAD_REFERENCE_SCHEMA (durable-workflow.v2.external-payload-reference.v1). Anbieteradapter fügen durable-workflow keine Cloud-SDK-Abhängigkeiten hinzu; Anwendungen stellen ihre konfigurierten S3-, GCS- oder Azure-Clients bereit.

Ihre Anbieterreferenz enthält diese Felder. Sie ist nicht die Runtime-Referenz der Server-HTTP-Routen:

{
  "schema": "durable-workflow.v2.external-payload-reference.v1",
  "uri": "s3://dw-payloads/billing/run-001/input.avro",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "size_bytes": 1048576,
  "codec": "avro",
  "expires_at": "2026-05-22T00:00:00Z"
}

ExternalPayloadReference.from_dict() lehnt unbekannte Schemas und fehlerhafte Felder ab. fetch_external_payload() prüft size_bytes und sha256 vor der Rückgabe und wirft bei Größen- oder Hashabweichung ExternalPayloadIntegrityError. Fehlende Objekte können außerdem einen Fehler des Anbietertreibers auslösen. Verwenden Sie ExternalPayloadCache nur für geprüfte Bytes. Cache-Verdrängung berechtigt nicht zum Löschen Server-verwalteter Objekte. delete_external_payload() ist eine direkte Anbieteroperation, keine Bereinigungs-API für Runtime-Referenzen.

Verwenden Sie external_storage_driver_from_policy() in Code, der bewusst auf anwendungseigenen Anbieterspeicher zugreift und den erforderlichen Client besitzt. Das Lesen der Richtlinie macht Anbieter-Envelopes nicht zu gültigen Server-Anfragen. Die Clients bleiben anwendungseigen. Optionale Adapter ergänzen keine Runtime-Abhängigkeiten auf boto3, google-cloud-storage oder azure-storage-blob:

from durable_workflow.external_storage import external_storage_driver_from_policy

namespace = await client.describe_namespace("billing")
driver = external_storage_driver_from_policy(
    namespace.external_payload_storage,
    s3_client=application_owned_s3_client,
)

Die Factory wirft ValueError, wenn die Richtlinie deaktiviert, der Treiber nicht unterstützt oder der passende Client nicht vorhanden ist. Deaktivierte Richtlinien liefern keinen leeren Treiber. Prüfen Sie vorher policy.enabled.

Identität des aktuellen Workflows​

Ab Python SDK 2.9.0 kann Workflow-Code die schreibgeschützten Eigenschaften ctx.workflow_id und ctx.run_id lesen. Beide sind Zeichenfolgen aus der aktuellen Aufgabe und bleiben bei der Wiederholung identisch. Bei continue-as-new bleibt die Workflow-ID erhalten, der Nachfolgelauf bekommt eine eigene Run-ID. Ersetzen Sie diese nicht durch eine als Argument übergebene ID des Vorgängers.

from durable_workflow import workflow

Workflows definieren​

Workflows sind mit @workflow.defn dekorierte Python-Klassen. Die Methode run ist eine gewöhnliche synchrone Funktion oder ein synchroner Generator, der dauerhafte Befehle an den Server ausgibt. Verwenden Sie die Generatorform, wenn der Workflow dauerhafte Arbeit ausführen muss; async def run wird nicht unterstützt.

from durable_workflow import workflow

@workflow.defn(name="order-processing")
class OrderWorkflow:
    def run(self, ctx, *args):
        order = args[0] if args else {}

        # Schedule an activity and wait for the result
        validated = yield ctx.schedule_activity(
            "validate_order", [order]
        )

        # Start a timer (durable sleep)
        yield ctx.start_timer(seconds=60)

        # Schedule another activity
        receipt = yield ctx.schedule_activity(
            "process_payment", [validated]
        )

        return receipt

Der name in @workflow.defn(name="...") ist der sprachübergreifende Typschlüssel. Er muss eine einfache Zeichenfolge sein, kein Python-Modulpfad oder Klassenverweis.

Signale, Abfragen und Updates​

Signale werden in dauerhafter Historie aufgezeichnet und beim Workflow-Replay an Python-Handler zugestellt:

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False
        self.approved_by = None

    @workflow.signal("approve")
    def approve(self, by: str) -> None:
        self.approved = True
        self.approved_by = by

    def run(self, ctx, *args):
        ready = yield ctx.wait_condition(
            lambda: self.approved, key="approval.approved", timeout=60,
        )
        return {
            "status": "approved" if ready else "timed_out",
            "approved": self.approved,
            "approved_by": self.approved_by,
        }

Der Workflow wartet, nicht eine Aktivität. Das Prädikat liest den bei der Wiedergabe rekonstruierten Zustand des Signalhandlers; für die Freigabe bleibt kein Aktivitätsslot belegt. Das Zeitlimit der Bedingung ist von den endlichen Lauf- und Ausführungsfristen des Workflows getrennt. Zur Fertigstellung externer Aufträge verwenden Sie eine kurze Aktivität, die den Auftrag übermittelt und zurückkehrt, sowie einen zugeordneten Rückruf.

Empfängerdekoratoren für Abfragen und Updates erlauben Workflow-Klassen, stabile Handler-Namen zu veröffentlichen. Python-Worker führen servergeroutete Abfrage-Tasks aus, indem sie die festgeschriebene Workflow-Historie wiedergeben und den registrierten Abfrage-Handler auf dem rekonstruierten Zustand aufrufen. Sie wenden auch angenommene, über Workflow-Tasks zugestellte Updates an:

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False

    @workflow.query("status")
    def status(self) -> dict:
        return {"approved": self.approved}

    @workflow.update("set_approval")
    def set_approval(self, approved: bool) -> dict:
        self.approved = approved
        return {"approved": self.approved}

    @set_approval.validator
    def validate_set_approval(self, approved: bool) -> None:
        if not isinstance(approved, bool):
            raise ValueError("approved must be boolean")

Python-Worker schließen servergeroutete Abfragen durch Rückgabe eines Abfrage-Task-Ergebnisses an den Server ab. Für einen deklarierten Update-Validator erhält der Worker stattdessen einen eigenen Validierungs-Task, gibt maßgeblichen Workflow-Zustand wieder und ruft nur den Validator auf. Vor erfolgreicher Validierung zeichnet der Server kein angenommenes Update auf und startet keinen Update-Handler. Worker mit Validatoren verweigern die Registrierung, sofern die Erkennung nicht den synchronen Vertrag vor Annahme meldet. Ablehnung, fehlende oder inkompatible Worker, Worker-Verlust, Timeout und gesperrte doppelte oder veraltete Abschlüsse bleiben explizite typisierte Ergebnisse. PHP und Rust bieten derzeit keine APIs zur Update-Validator-Implementierung und melden diese Abwesenheit in ihren Workflow-Verträgen, statt Validator-Parität zu beanspruchen.

Lebenszyklus der Handler​

Veröffentlichte Validierung. Python SDK 2.6.2 hat die folgenden Handler-Schutzprüfungen eingeführt. Asynchrone, vom Server geroutete Abfragen und Update-Validatoren werden weiterhin unterstützt. Den korrigierten Umfang beschreibt SDK #177.

Jedes Replay erstellt vor der Ausführung von run() eine neue Workflow-Instanz. Bereits beim Workflow-Start aufgezeichnete Signale werden angewendet, nachdem run() sein erstes yield erreicht hat. Konstruktor und Initialisierung vor diesem yield laufen daher zuerst. Signal- und Update-Handler verändern diesen durch Replay hergestellten Zustand. Abfragen untersuchen ihn, ohne dauerhaften Zustand zu ändern; Update-Validatoren prüfen vor der Annahme einen anschließend verworfenen Replay-Zustand. Dauerhafte Aktivitäten, Timer und Kind-Workflow-Befehle gehören in run(), nicht in einen Handler.

HandlerUnterstützte Form und Fehlerfolge
@workflow.signalSynchrone Funktion. Eine Ausnahme beim Anwenden des Signals während des Replays lässt den Workflow-Lauf fehlschlagen.
@workflow.updateSynchrone Funktion. Eine Handler-Ausnahme lässt dieses Update fehlschlagen.
@workflow.update_validator oder @update_method.validatorSynchrone Funktion oder async def unter dem Worker. Eine Ausnahme lehnt das Update vor seiner Annahme ab.
@workflow.querySynchrone Funktion oder async def unter dem Worker. Eine Handler-Ausnahme lässt die Abfrage fehlschlagen, nicht den Workflow-Lauf.

Die Validierung lehnt Coroutine-Funktionen für Signale und Updates ab. Generator- und asynchrone Generatorfunktionen werden für alle Arten dekorierter Handler abgelehnt, einschließlich Abfragen und Validatoren. Sie löst bei Definition, Registrierung oder Replay InvalidWorkflowDefinition aus, auch bei geerbten Handlern und in Offline-Werkzeugen. Synchrone Wrapper für Signale und Updates können die Prüfungen nicht durch die Rückgabe asynchroner Werte umgehen. Generatorwerte und asynchrone Generatorwerte werden bei jeder Handler-Art abgelehnt. Diese Einschränkungen verbieten nicht den synchronen Generator von run().

Bei einer vom Server gerouteten Abfrage wartet der Worker ausdrücklich auf ein asynchrones Ergebnis, unter der ursprünglichen Abfragefrist sowie der ursprünglichen Claim- und Abbruchautorität. Dieses Warten gibt weder ein neues Budget noch erlaubt es ein Ergebnis nach Verlust der Autorität. Bei der Prüfung vor Annahme wartet der Worker ebenfalls auf ein asynchrones Validatorergebnis, das anhand eines anschließend verworfenen Replay-Zustands ermittelt wird.

Die lokalen synchronen Hilfsmethoden können nicht asynchron warten. Dabei lehnt workflow.query_state() ein asynchrones Ergebnis mit QueryFailed ab, und workflow.validate_update() lehnt es mit UpdateRejected ab. Beide schließen zurückgegebene Coroutinen, statt sie als Operationsergebnisse nach außen gelangen zu lassen.

Kompatibilität am Einstieg und Wiederherstellung​

Veröffentlichte Unterstützung. Python SDK 2.6.2 hat den nachfolgenden Einstiegsschutz eingeführt, ergänzt durch Routing und Wiederherstellung in Server 2.9.9. Dies sind die Mindestversionen für diese Funktionen. Installieren Sie aktuelle stabile Versionen, um Sicherheitskorrekturen zu erhalten.

Vor dem Aufruf von run(ctx, *start_input) bindet der Worker die aufgezeichneten Argumente an die Einstiegssignatur. Ein fehlendes erforderliches Argument oder eine unpassende Argumentanzahl löst vor der Ausführung des Rumpfs WorkflowEntryArgumentsMismatchError mit dem Grund workflow_entry_arguments_mismatch aus. Standardwerte ergänzen nur ausgelassene Argumente. Python-Annotationen werden weiterhin nicht erzwungen: Eine geänderte Annotation prüft oder konvertiert keine aufgezeichneten Daten. Ein TypeError im erfolgreich betretenen normalen Rumpf oder Generatorrumpf bleibt ein Anwendungsfehler.

Der Worker kündigt workflow_entry_arguments_validation automatisch an. Mit einem qualifizierten Server wird die fehlgeschlagene Aufgabe für Replay blockiert, während der ursprüngliche Lauf nichtterminal bleibt. Ältere Laufzeiten können die Aufgabe stattdessen wiederholen; die SDK-seitige Ablehnung allein belegt nicht den vollständigen Wiederherstellungsvertrag.

Prüfen Sie den genauen Lauf mit await client.describe_workflow_run(workflow_id, run_id) und dem Debug-Endpunkt für den ausgewählten Lauf. Bewahren Sie ursprüngliche Eingabe, Historie, Namespace, Warteschlange, Build und Fristen. Platzieren Sie bei Befehlsänderungen ctx.get_version innerhalb dieser kompatiblen Methode und qualifizieren Sie kaltes Replay anhand des Routings nach Definition.

Workflow-Zeit und dauerhafte Warteoperationen​

Beim Replay im Worker gibt ctx.now() die gespeicherte Startzeit des Runs zurück. Sie schreitet nach einer Aktivität, einem Timer, Signal oder anderen dauerhaften Schritt nicht fort. Wiederholte Cold-Replays derselben Historie liefern denselben Startwert. Ein Continue-as-new-Nachfolger hat seine eigene Startzeit und übernimmt nicht den Uhranker des Vorgängers.

Die veröffentlichte Python-Implementierung verwendet WorkflowStarted.payload.timestamp, falls vorhanden, andernfalls das kanonische WorkflowStarted.recorded_at. Fehlende oder ungültige gespeicherte Replay-Zeit führt zu einem ausdrücklichen Uhrfehler, nicht zum Lesen der Wanduhr des Workers. Das ist der in SDK #146 vereinbarte Vertrag mit fester Startzeit.

Warten Sie auf eine dauerhafte Operation, statt auf eine Änderung von ctx.now() zu warten:

from durable_workflow import workflow


@workflow.defn(name="wait_without_clock_loop")
class WaitWithoutClockLoop:
    def run(self, ctx):
        started_at = ctx.now()
        yield ctx.start_timer(30)
        return {
            "run_started_at": started_at.isoformat(),
            "after_wait": ctx.now().isoformat(),
        }

Der dauerhafte Abschluss des Timers setzt den Workflow fort. Beide zurückgegebenen Zeitstempel enthalten dieselbe Startzeit. Eine Schleife wie while ctx.now() < deadline wird nicht allein durch ausgelöste Timer falsch.

Für eine relative Verzögerung verwenden Sie yield ctx.start_timer(seconds) oder yield ctx.sleep(seconds). Verwenden Sie die Auswahl des ersten Abschlusses, wenn Arbeit mit einem dauerhaften Timer konkurrieren soll. Setzen Sie execution_timeout_seconds und run_timeout_seconds bei client.start_workflow(...), wenn der Server eine Workflow-Frist auch bei gestoppten Workern durchsetzen muss. Ein HTTP- oder get_result()-Wartezeitlimit begrenzt nur die lokale Anfrage und ersetzt keine gespeicherte Workflow-Frist. Geben Sie eine Anwendungsfrist ausdrücklich als Eingabe an Continue-as-new weiter, ohne die ursprüngliche Ausführungsfrist des Servers zu ersetzen.

Um die tatsächliche Dauer innerhalb eines Aktivitätsaufrufs zu messen, lesen Sie dort eine monotone Uhr und geben die Dauer als Aktivitätsergebnis zurück. Für eine externe UTC-Frist lassen Sie eine Aktivität die maßgebliche externe Uhr prüfen und ihre Entscheidung zurückgeben; der Workflow spielt dieses gespeicherte Ergebnis ab. Vergleichen Sie UTC-Zeitstempel nie mit monotonen Werten und subtrahieren Sie keine monotonen Messwerte verschiedener Prozesse oder Hosts. Die Differenz von ctx.now()-Werten misst in Python weder aktive Verarbeitungszeit noch verstrichene Wanduhrzeit.

Unterschiede zwischen den SDK-Uhren​

Diese APIs sind, soweit vorhanden, deterministisch, teilen aber keine gemeinsame Uhr:

Das Embedded-PHP-Verhalten ist im veröffentlichten Core vorhanden. Der separate PHP-SDK-Kontext und Rust-SDK-Kontext haben eigene APIs. Übertragen Sie die dauerhafte Operation und Fristenregel, statt für jeden SDK-Uhrhelfer dieselbe Semantik anzunehmen.

Ausgegebene Ereignisse mit Sequenzwerten ordnen​

Ein Workflow-Zeitstempel ist kein Sortierschlüssel für Ereignisse. Python-Ereignisse mit ctx.now() können alle denselben Zeitstempel haben. Verwenden Sie Workflow-Stream-Offsets, die passende Embedded-Outbox-Sequenz oder einen deterministischen Workflow-lokalen Zähler. Kombinieren Sie einen Run-lokalen Zähler mit run_id; übergeben Sie ihn bei Continue-as-new ausdrücklich, wenn die Anwendung eine logische Sequenz benötigt. Zeitstempel geben unabhängigen Streams oder Runs keine globale Reihenfolge.

Aktivitätswiederholungen und -Timeouts​

Verwenden Sie ActivityRetryPolicy und Timeout-Schlüsselwortargumente an ctx.schedule_activity(...), wenn ein Aufruf ein anderes Wiederholungsbudget oder eine andere Frist als das standardmäßige Ein-Versuch-Verhalten benötigt:

from durable_workflow import ActivityRetryPolicy

receipt = yield ctx.schedule_activity(
    "process_payment",
    [validated],
    retry_policy=ActivityRetryPolicy(
        max_attempts=4,
        initial_interval_seconds=1,
        backoff_coefficient=2,
        maximum_interval_seconds=30,
        non_retryable_error_types=["ValidationError"],
    ),
    start_to_close_timeout=120,
    schedule_to_close_timeout=300,
    heartbeat_timeout=15,
)

start_to_close_timeout begrenzt einen Versuch ab Worker-Start. schedule_to_close_timeout begrenzt die gesamte Aktivitätsausführung über alle Versuche. heartbeat_timeout verlangt bei lang laufenden Aktivitäten activity.context().heartbeat(...) vor Ablauf des Intervalls. Die Wiederholungsrichtlinie wird beim Planen als Snapshot an die dauerhafte Aktivitätsausführung gebunden. Spätere Bereitstellungen ändern daher laufende Versuche nicht.

ctx.schedule_activity(..., queue="payments-v2") wählt die Queue einer neu geplanten Aktivitätsausführung. Bereits gespeicherte Aktivitäten, ihre Wiederholungen und reparierte Aufgaben behalten die ursprüngliche Queue. Eine Änderung von Worker.task_queue verschiebt weder diese Aufgaben noch die Workflow-Queue bestehender Läufe. Halte den kompatiblen alten Pool verfügbar, bis alle Abhängigkeiten berücksichtigt sind; siehe gespeicherte Aktivitätsqueues.

Regeln für Determinismus​

Workflow-Code wird aus der Historie wiedergegeben. Er darf keine nicht deterministischen Operationen direkt ausführen:

  • Keine E/A (HTTP-Aufrufe, Dateilesen, Datenbankabfragen).
  • Kein datetime.now() oder time.time(): ctx.now() nur als festen Run-Startanker verwenden; für Warteoperationen dauerhafte Timer verwenden.
  • Kein random.random(): ctx.random() verwenden.
  • Kein uuid.uuid4(): ctx.uuid4() verwenden.

Jeder Nichtdeterminismus muss über den Kontext laufen oder mit ctx.side_effect() erfasst werden.

Heartbeat-Anfragen​

Rufen Sie bei entfernten Aktivitäten await ctx.heartbeat(...) während begrenzter Aktivitätsarbeit deutlich vor heartbeat_timeout auf. Das erste Zeitfenster beginnt mit der Beanspruchung durch die Laufzeit, bevor Python die Aufgabe empfängt. Jeder aufgezeichnete Heartbeat verwendet den Aufzeichnungszeitpunkt der Laufzeit, nicht den Empfangszeitpunkt der Antwort in Python. Pausen, Anfragelatenz und Transportwiederholungen verbrauchen das Budget. Beachten Sie die Taktempfehlungen.

Der direkte Aufruf von Client.heartbeat_activity_task() verwendet die konfigurierte TransportRetryPolicy. Nach dieser Richtlinie können Transportfehler als httpx.TransportError weitergegeben werden. HTTP-Ablehnungen werden zu zugeordneten SDK-Ausnahmen wie ServerError. Das ist HTTP-Wiederholungsverhalten, kein neuer Aktivitätsversuch und keine zusätzliche Heartbeat-Zeit. ActivityContext.heartbeat() kann ActivityCancelled auslösen, wenn der Worker die Aktivität zum Stoppen auffordert. Wenn die kooperative Prozessüberwachung aktiviert ist, können fehlgeschlagene Heartbeat- oder Besitzprüfungen den Callback stoppen oder aufgeben. Nicht jeder Fehler erreicht einen Ausnahmehandler, und Bereinigungscode läuft nicht immer.

Unterdrücken Sie Heartbeat- oder Besitzfehler nicht, um externe Arbeit fortzusetzen oder Erfolg zu melden. Fortschritt ist weder ein externer Commit noch eine Bestätigung eines fortsetzbaren Prüfpunkts. Halten Sie externe Effekte idempotent.

Heartbeat-Ablehnung und Ende des Callbacks​

Im Python SDK 2.9.0 lösen ctx.heartbeat() und ctx.heartbeat_sync() einen ActivityLeaseAuthorityLost aus, wenn eine Heartbeat-Antwort can_continue=false enthält. Die Ausnahme bewahrt den ursprünglichen Server-Grund, etwa activity_deadline_elapsed, attempt_closed oder run_closed. Eine Abbruchanforderung löst dagegen ActivityCancelled aus. Siehe die Qualifikation des veröffentlichten SDK.

Der Heartbeat, der die Ablehnung empfängt, ist ein kooperativer Ausstiegspunkt. Beenden Sie externe Arbeit und reichen Sie die Ausnahme weiter; fangen Sie sie nicht ab, um Erfolg zurückzugeben. Code ohne Heartbeats kann bis zur Rückkehr weiterlaufen. Ein Hilfs-Heartbeat kann einen blockierten Bibliotheksaufruf nicht zwangsweise unterbrechen: Verwenden Sie endliche E/A-Fristen und den eigenen Abbruchmechanismus des Aufrufs.

Der physische Activity-Slot bleibt bis zum Ende des Callbacks/Threads belegt. Der Verlust der Ausführungsberechtigung gibt diesen Thread nicht für andere Arbeit frei, und der Worker veröffentlicht kein verspätetes Ergebnis für den geschlossenen Versuch. Die Durchsetzung eines Runtime-Timeouts und das Anhalten von Anwendungscode sind getrennte Grenzen. Siehe Activity-Timeouts und die Hinweise zum Hilfsthread.

Terminale fachliche Fehler​

non_retryable_error_types vergleicht den kurzen Namen (exception_type) oder vollständig qualifizierten Klassennamen (exception_class) der äußersten Ausnahme exakt. ValidationError passt beispielsweise nicht zu SpecificValidationError, auch wenn diese Klasse davon erbt. Ein qualifizierter Eintrag wie app.errors.ValidationError muss dem aufgezeichneten Klassennamen entsprechen. Die Richtlinie durchsucht weder Unterklassen noch Ursachen. raise RuntimeError(...) from NonRetryableError(...) meldet den äußeren RuntimeError und kann weiterhin wiederholt werden.

Wenn Sie eine bekannte fachliche Ausnahme umwandeln, lösen Sie NonRetryableError als äußere Ausnahme aus und erhalten Sie die ursprüngliche Python-Ursache mit cause=error. Dadurch wird der Aktivitätsfehler ohne Namensliste als nicht wiederholbar markiert. Das lässt nicht automatisch den ganzen Workflow scheitern: Er erhält ActivityFailed, wenn keine Aktivitätsversuche verbleiben, entweder wegen eines nicht wiederholbaren Fehlers oder wegen ausgeschöpften Budgets.

from durable_workflow import ActivityFailed, NonRetryableError, activity, workflow

@activity.defn(name="validate_order")
async def validate_order(order: dict) -> dict:
    try:
        if order.get("amount", 0) <= 0:
            raise ValueError("amount must be positive")
    except ValueError as error:
        raise NonRetryableError("Order validation failed", cause=error) from error
    return order

@workflow.defn(name="place_order")
class PlaceOrderWorkflow:
    def run(self, ctx, order: dict):
        try:
            yield ctx.schedule_activity("validate_order", [order])
        except ActivityFailed as failure:
            if (
                failure.activity_type != "validate_order"
                or failure.exception_type != "NonRetryableError"
                or not failure.non_retryable
            ):
                raise
            return {"order_id": order["id"], "status": "rejected"}
        return {"order_id": order["id"], "status": "accepted"}

Bei der Eingabe {"id": "order-123", "amount": 0} schlägt die Aktivität einmal fehl und der Workflow schließt normal mit status: rejected ab. Behandeln Sie nur den vorgesehenen fachlichen Fehler; das Beispiel löst andere Fehler erneut aus. Fahren Sie mit weiteren dauerhaften Schritten fort, wenn der Geschäftsablauf es erfordert. Ein unbehandelter ActivityFailed lässt den Workflow scheitern. Eine erhaltene Python-Ursache bedeutet weder, dass die Wiederholungsrichtlinie die Kette prüft, noch dass jedes SDK dasselbe Ursachenobjekt bereitstellt.

Synchrone und asynchrone Aktivitäten​

Gewöhnliche entfernte def-Aktivitäten laufen in einem eigenen Threadpool, dessen Größe durch max_concurrent_activity_tasks begrenzt ist. Jeder Callback behält seinen Aktivitätskontext. Polling, Workflow-Tasks und Worker-Heartbeats können weiterlaufen, während ein Callback blockiert. Aktivitäten mit async def laufen in der Ereignisschleife und müssen nichtblockierende Ein-/Ausgabe verwenden. Ein blockierender Aufruf in einer asynchronen Funktion blockiert weiterhin diese Schleife.

Verwenden Sie in einem synchronen Callback activity.context().heartbeat_sync(details), um Fortschritt über die zuständige Ereignisschleife mit den ursprünglichen Kennungen von Task, Versuch und Worker zu melden. Asynchrone Callbacks verwenden await activity.context().heartbeat(details).

Das Abbrechen eines Await-Vorgangs stoppt keinen laufenden Python-Thread. Sein tatsächlicher Slot bleibt bis zur Rückkehr des Callbacks belegt. Eine verspätete Rückkehr übermittelt nach dem Abbruch kein Ergebnis. Läuft ein Callback nach shutdown_timeout noch, löst das Herunterfahren RuntimeError aus und behält die Worker-Registrierung bei. Legen Sie Zeitlimits für nachgelagerte Ein-/Ausgabe fest und verwenden Sie für rechenintensive Arbeit getrennte, isolierte Worker-Prozesse. Siehe die SDK-Referenz zu Ausführung und Herunterfahren.

Heartbeats aus einem Hilfsthread​

Erfassen Sie bei einem langen blockierenden Aufruf ctx = activity.context() innerhalb der synchronen Aktivität und übergeben Sie den Kontext an den Hilfsthread. Ein neuer Thread erbt den Aktivitätskontext nicht automatisch. Verwenden Sie dort ctx.heartbeat_sync(details), niemals in der Ereignisschleife des Workers. Die vollständige Anleitung steht in der SDK-Referenz.

Beenden Sie den Hilfsthread bei Rückkehr oder Fehler des Aufrufs und warten Sie mit join() auf sein Ende. Löst ein Heartbeat ActivityCancelled oder ActivityLeaseAuthorityLost aus, signalisieren Sie dem Aufruf den kooperativen Abbruch und lösen Sie vor der Ergebnisrückgabe die ursprüngliche Ausnahme erneut aus. Eine Ausnahme im Hilfsthread kann einen blockierten Bibliotheksaufruf nicht gewaltsam unterbrechen. Geben Sie diesem eine eigene endliche Frist und einen Abbruchmechanismus. Begrenzen Sie auch Heartbeat-Anfragen und Wiederholungen. Andernfalls meldet der Hilfsthread weiter Lebenszeichen, obwohl die Arbeit hängt.

Worker-Sessions​

Verwenden Sie WorkerSessionOptions, wenn aufeinanderfolgende Remote-Activities eine lokale Ressource desselben Workers brauchen. Dieses Beispiel wurde mit Python SDK 2.9.0 und Server 2.11.0 geprüft; siehe die Versionsanforderungen für portable Affinität. Verwenden Sie pro Workflow-Ausführung eine eindeutige job_id, damit ein neuer Lauf keine Session-ID im Endzustand wiederverwendet.

Der folgende Cache ist verwerfbar. Jede Activity kann ihn aus dauerhaft gespeicherten Geschäftseingaben neu aufbauen. Ein neuer Inhaber hängt daher nicht vom Speicher des vorherigen Prozesses ab:

from durable_workflow import ActivityFailed, WorkerSessionOptions, activity, workflow

documents = {}

    rebuilt = job_id not in documents
    if rebuilt:
        documents[job_id] = {"text": "document:" + job_id}
    return documents[job_id], rebuilt

@activity.defn(name="prepare_document")
async def prepare_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id, "rebuilt": rebuilt}

@activity.defn(name="inspect_document")
async def inspect_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id,
            "rebuilt": rebuilt, "text": document["text"]}

@workflow.defn(name="inspect_document_workflow")
class InspectDocumentWorkflow:
    def run(self, ctx, job_id):
        session = WorkerSessionOptions(
            session_id="documents:" + job_id,
            requirements=("fs:documents",),
            lease_seconds=5,
            ttl_seconds=60,
            max_concurrent_activities=1,
            allow_reacquire_after_failure=True,
        )
        options = dict(worker_session=session,
                       start_to_close_timeout=5,
                       schedule_to_start_timeout=12,
                       schedule_to_close_timeout=20,
                       retry_policy={"max_attempts": 1})
        try:
            prepared = yield ctx.schedule_activity("prepare_document", [job_id], **options)
            inspected = yield ctx.schedule_activity("inspect_document", [job_id], **options)
        except ActivityFailed as error:
            if error.activity_type not in {"prepare_document", "inspect_document"}:
                raise
            return {"status": "resource_unavailable", "job_id": job_id}
        return {"status": "inspected", "prepared": prepared, "inspected": inspected}

Diese kurzen Leases und Timeouts zeigen begrenztes Verhalten; passen Sie sie an die tatsächliche Arbeit an und senden Sie Heartbeats deutlich vor Ablauf.

Nach dem Verlust des Inhabers oder Ablauf der Lease erlaubt allow_reacquire_after_failure=True einem anderen geeigneten Worker, die Session erneut zu erwerben. Er muss die lokale Ressource neu aufbauen. Bereits bestätigte Activity-Ergebnisse werden wiedergegeben, während unbestätigte Effekte sich wiederholen können: Verwenden Sie dauerhafte Ressourcenkennungen und idempotente externe Operationen. Eine Session migriert weder Speicher noch Dateien oder offene Handles.

Explizites Schließen und der Ablauf der absoluten TTL sind für diese Session-ID endgültig. Eine spätere Activity kann sie nicht erneut öffnen und bleibt möglicherweise bis zur Durchsetzung ihres konfigurierten Timeouts unzugelassen. Führen Sie die Scheduler-/Wartungsrolle des Servers aus dem veröffentlichten Deployment-Rezept aus; ein reiner API-Prozess reicht zur Timeout-Durchsetzung nicht aus. Der Workflow behandelt den endgültigen Activity-Fehler mit ActivityFailed und gibt resource_unavailable zurück. Die Anwendung kann dann eine neue Session wählen und die Ressource aus den Geschäftseingaben neu aufbauen. Das Beispiel verspricht weder eine sofortige Ausnahme wegen einer geschlossenen Session noch ein automatisches Wiederöffnen einer endgültig beendeten Session.

Für explizite Operationen am Lebenszyklus des Inhabers verwenden Sie worker.worker_session(options) und dessen Methoden create(), renew() und close(reason). Beim geordneten Herunterfahren schließt der Worker seine gehaltenen Sessions. Siehe den gemeinsamen Lebenszyklusvertrag.

Abbruch ist bewusst nicht mit except Exception abfangbar​

WorkflowCancelled und ActivityCancelled erben von BaseException, nicht Exception. Ein allgemeiner Block except Exception: im Aktivitätskörper oder in Code, der auf client.get_result() wartet, fängt sie nicht ab. Das ist beabsichtigt: Abbruch ist ein Control-Plane-Ergebnis. Ihn still in einem Sammel-Catch zu verschlucken würde einer Aktivität erlauben, nach Aufforderung ihres Workflows zum Stoppen Erfolg zu melden.

Benötigt eine Aktivität lokale Bereinigung bei Task-Abbruch, fangen Sie die Klasse namentlich ab und lösen Sie sie erneut aus. Dies setzt den geschlossenen Workflow nicht für Kompensation fort:

from durable_workflow import ActivityCancelled, activity

@activity.defn(name="long_task")
async def long_task(items: list) -> dict:
    ctx = activity.context()
    try:
        for i, item in enumerate(items):
            await process(item)
            await ctx.heartbeat({"progress": i + 1})
        return {"done": True}
    except ActivityCancelled:
        await cleanup_partial_state()
        raise

Dies folgt dem Vorbild von asyncio.CancelledError und KeyboardInterrupt aus der Standardbibliothek.

Tests​

Workflow-Entwickler sollen Workflow-Code ohne laufenden Server oder Worker testen können. durable_workflow.testing liefert zwei Einstiegspunkte:

  • WorkflowEnvironment führt einen Workflow in einem Python-Prozess gegen vom Nutzer registrierte Aktivitäts-Mocks bis zum Abschluss.
  • replay_history und replay_history_file geben erfasste Produktionshistorie gegen aktuellen Workflow-Code wieder und lösen bei Nichtdeterminismus Fehler aus.

Beide verwenden dieselbe durable_workflow.workflow.replay-Mechanik wie der Worker zur Laufzeit. Ein Workflow, der seine Testumgebung besteht, verhält sich daher unter einem echten Worker genauso.

WorkflowEnvironment​

WorkflowEnvironment führt ausgegebene Workflow-Befehle gegen registrierte Mocks aus und löst Timer, Seiteneffekte sowie Suchattribut-Upserts automatisch aus. Tests benötigen weder echte Uhr noch Redis oder Server.

from durable_workflow import workflow
from durable_workflow.testing import WorkflowEnvironment

@workflow.defn(name="greeter")
class Greeter:
    def run(self, ctx, name: str):
        greeting = yield ctx.schedule_activity("greet", [name])
        return greeting


def test_greeter_returns_activity_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("greet", "hello, world")

    result = env.execute_workflow(Greeter, "world")

    assert result == "hello, world"

  • Planen einer Aktivität ohne registrierten Mock löst KeyError aus.
  • Starten eines Kind-Workflows ohne registrierten Mock löst KeyError aus.
  • Ein Workflow ohne terminalen Zustand innerhalb der Iterationsgrenze (Standard 1000) löst RuntimeError aus.

Signale​

Mit env.signal(...) eingereihte Signale werden vor der nächsten Replay-Iteration zugestellt. Die Signalnutzlast wird in dieselbe {codec, blob}-Envelope verpackt, die der Worker zur Laufzeit sieht, und an den registrierten Handler @workflow.signal des Workflows übergeben:

@workflow.defn(name="approval")
class Approval:
    def __init__(self) -> None:
        self.approved_by: str | None = None

    @workflow.signal("approve")
    def on_approve(self, by: str) -> None:
        self.approved_by = by

    def run(self, ctx):

    env.register_activity_result("wait", None)

Timer, Seiteneffekte und Suchattribute​

Die Testumgebung löst für jeden dieser Befehle das entsprechende Historienereignis automatisch aus. Workflows warten in Tests daher nicht auf die reale Uhrzeit:

  • ctx.sleep(seconds) → TimerFired
  • ctx.side_effect(...) → SideEffectRecorded
  • ctx.upsert_search_attributes(...) → SearchAttributesUpserted
  • workflow.version(...)-Marker → VersionMarkerRecorded

Continue-as-new-Ketten​

Liefert ein Workflow ctx.continue_as_new(...), hängt die Testumgebung ein Ereignis WorkflowContinuedAsNew an den abschließenden Lauf an, setzt die Historie zurück und startet einen neuen Lauf mit den Befehlsargumenten. execute_workflow liefert das terminale Ergebnis des letzten Glieds.

@workflow.defn(name="countdown")
class Countdown:
    def run(self, ctx, counter: int):
        yield ctx.schedule_activity("emit", [counter])
        if counter > 0:
            return ctx.continue_as_new(counter - 1)
        return {"final_counter": counter}


def test_chain_returns_final_run_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("emit", None)

    result = env.execute_workflow(Countdown, 3)

    assert result == {"final_counter": 0}
    assert env.run_count == 4
    assert [r.input for r in env.runs] == [[3], [2], [1], [0]]

Wechselt die Kette Workflow-Typen, registrieren Sie zuerst die Folgeklasse:

@workflow.defn(name="stage-one")
class StageOne:
    def run(self, ctx):
        yield ctx.schedule_activity("stage_one", [])
        return ctx.continue_as_new(workflow_type="stage-two")


@workflow.defn(name="stage-two")
class StageTwo:
    def run(self, ctx):
        return (yield ctx.schedule_activity("stage_two", []))


def test_chain_can_switch_workflow_type() -> None:
    env = WorkflowEnvironment()
    env.register_workflow(StageTwo)
    env.register_activity_result("stage_one", None)
    env.register_activity_result("stage_two", "done")

    assert env.execute_workflow(StageOne) == "done"
    assert [r.workflow_type for r in env.runs] == ["stage-one", "stage-two"]

Zielen Sie mit run=N auf ein bestimmtes Glied der Kette:

env.signal("approve", ["alice"], run=2)  # delivered to the second run

Die Kettenlänge ist durch continue_as_new_limit begrenzt (Standard 50). Überschreiten löst RuntimeError aus, damit Tests entgleiste Fortsetzungen erkennen, statt endlos zu laufen. Passen Sie die Grenze mit WorkflowEnvironment(continue_as_new_limit=...) an, wenn eine Kette berechtigt länger läuft.

Replay-Tests gegen Produktionshistorie​

Verwenden Sie replay_history, um Workflow-Änderungen gegen echte, vom Server erfasste Historie auf Regressionen zu prüfen. Der Replayer führt aktuellen Workflow-Code gegen die aufgezeichnete Ereignisfolge aus und scheitert, wenn er einen anderen als den aufgezeichneten Befehl ausgibt. Das ist die Definition eines Nichtdeterminismusfehlers.

from durable_workflow import Client
from durable_workflow.testing import replay_history

async with Client("http://localhost:8080") as client:
    history = await client.get_history("order-42", run_id="...")

replay_history(OrderWorkflow, history["events"], start_input=["order-42"])

Ein zuvor abgeschlossener Workflow muss beim Replay derselben Historie erneut abschließen. Weicht geänderter Workflow-Code von der aufgezeichneten Folge ab (umgeordnete Aktivitätsaufrufe, entfernte Zweige, geänderte Aktivitätstypen), scheitert replay_history, damit CI die Regression vor der Produktion erkennt.

replay_history_file ist ein Komfortwrapper zum Lesen einer JSON-Datei mit einer von zwei Formen: einer obersten Ereignisliste oder einem Dictionary mit events-Schlüssel entsprechend der Antwortstruktur von get_history:

from durable_workflow.testing import replay_history_file

replay_history_file(
    OrderWorkflow,
    "tests/histories/order-42.json",
    start_input=["order-42"],
)

Beide Funktionen akzeptieren einen optionalen Validierungshinweis payload_codec. Ohne Angabe gilt das aufgezeichnete Tag der Historie. Ein explizites oder aufgezeichnetes Tag muss avro sein. json, unbekannte oder nicht getaggte dauerhafte Nutzlasten scheitern vor der Decodierung.

Klassenbasierter Replayer​

Verwenden Sie Replayer, wenn ein Testdurchlauf Historien mehrerer Workflow-Typen wiedergibt oder das erfasste Ereignis WorkflowStarted den Typ bestimmen soll. Registrieren Sie alle Workflow-Klassen vorab und rufen Sie je erfasster Historie replay(...) auf:

from durable_workflow import Replayer, ReplayOutcome

replayer = Replayer(workflows=[OrderWorkflow, RefundWorkflow])

# Explicit type and input — equivalent to replay_history(OrderWorkflow, ...).
outcome: ReplayOutcome = replayer.replay(
    history["events"],
    start_input=["order-42"],
    workflow_type="order",
)

# Type and start input inferred from a WorkflowStarted event in the history.
outcome = replayer.replay(history)  # history may be an events list or a
                                    # dict with an "events" key

for command in outcome.commands:
    # Inspect commands the replayed workflow would have emitted next.
    ...

ReplayOutcome.commands ist dieselbe Befehlsliste wie bei den funktionalen replay_history-Hilfen. Die Klasse erlaubt einer Testsuite, eine Registrierung über viele Historien gemeinsam zu nutzen.

Nutzlast-Codec​

Jede Nutzlast über die Worker-Protokollgrenze trägt ein Codec-Tag. Durable Workflow 2.0 hat einen öffentlichen Nutzlast-Codec: avro. Das Python SDK lehnt JSON-getaggte, unbekannte und nicht getaggte dauerhafte Nutzlasten ab, statt einen anderen Decoder zu wählen. Siehe das Avro-Value-Protokoll.

Avro-Unterstützung ist eingebaut​

Das festgelegte 2.0-SDK-Artefakt bindet fastavro als Laufzeitabhängigkeit ein. Jede ausgehende Oberfläche (start_workflow, signal_workflow, query_workflow, update_workflow, Aktivitätsergebniscodierung, Zeitplanaktionen) erzeugt daher Avro-getaggte Nutzlasten über den optimierten Produktionspfad. Es gibt kein optionales Codec-Extra zu installieren.

Feste typisierte Werte​

Das SDK wählt benannte Zweige im gemeinsamen Schema durable_workflow.protocol.Value explizit aus. Es codiert Werte nicht als JSON innerhalb von Avro. Ganzzahlen und Double-Werte, Zeichenfolgen und Bytes, boolesche Werte und Ganzzahlen sowie Listen und Maps bleiben daher SDK-übergreifend verschieden. Die Übertragung verwendet Avro-Einzelobjektrahmen und Schema-Fingerabdruck. Unbekannte Fingerabdrücke scheitern mit unsupported_payload_schema.

Jede Client- und Worker-Oberfläche funktioniert durchgehend mit Avro als Standard:

  • Client-Starts, Signale, Abfragen, Updates: start_workflow, signal_workflow, query_workflow und update_workflow erzeugen payload_codec = "avro"-Nutzlasten über das feste Value-Schema. Ein Python-Client kann deshalb Workflows steuern, die PHP und andere polyglotte SDKs wiedergeben, und umgekehrt.
  • Aktivitäts-Worker: Avro-getaggte Aktivitätsargumente werden transparent decodiert. Der Worker codiert Ergebnisse als Avro, damit PHP, Python und künftige SDK-Worker eine Nutzlastgrenze teilen.
  • Aktivitätsfehler: fail_activity_task(..., details=...) sendet failure.details als {codec, blob}-Envelope. Server zeichnet Blob und details_payload_codec auf, damit Diagnosedaten von Python-Workern in Historienexporten und Beobachtungsansichten sprachneutral bleiben.
  • Historien-Replay im Workflow-Worker: Avro-getaggte Starteingaben und Aktivitätsergebnisereignisse werden beim Replay decodiert, sodass ein Python-Workflow an einem Avro-codierten Lauf teilnehmen kann.
  • Workflow-Abfrage-Tasks: Servergeroutete Abfrage-Tasks enthalten Avro-getaggte Workflow-Argumente, Abfrageargumente und Replay-Historie. Der Worker liefert das Abfrageergebnis als Avro-Envelope.

Einen Python-Aktivitäts-Worker gegen einen v2-Lauf ausführen​

Keine Codec-Konfiguration ist nötig. Das SDK prüft payload_codec vor jeder Claim-Decodierung, akzeptiert nur avro, führt die Aktivität aus und liefert ein Avro-getaggtes Ergebnis. Jedes andere Tag wird strikt mit unsupported_payload_codec abgelehnt. Der Worker versucht niemals, das Format zu erkennen oder zu erraten.

Mit einem gemeinsam genutzten Server ausführen​

Der Schnellstart oben startet einen lokalen Server mit dem veröffentlichten Docker-Image. In einer Teamumgebung richten Sie den Python-Worker gewöhnlich auf einen bestehenden Server (Staging, Produktion oder gemeinsame Entwicklungsinstanz):

from durable_workflow import Client

client = Client(
    "https://workflow.example.internal",
    control_token="team-orders-operator-token",
    worker_token="team-orders-worker-token",
    namespace="team-orders",
)

Setzen Sie namespace auf den für Ihr Team bereitgestellten Mandanten-Namespace und verwenden Sie dessen ausgestellte Zugangsdaten. Der Server-Betrieb verwaltet die Namespace-Erstellung. Details stehen im Server-Leitfaden.

Derselbe Konstruktor unterstützt eine Cloud-verwaltete Laufzeitumgebung. Verwenden Sie die von Cloud gelieferte Laufzeit-URL und den Namespace-Wert, setzen Sie control_token auf die Client-Laufzeit-Zugangsdaten und worker_token auf die Worker-Laufzeit-Zugangsdaten. Cloud stellt den Namespace bereit. Setzen Sie keine selbst gehostete Server-Adresse ein. Siehe Verwaltete Cloud-Laufzeitumgebung.

Seiten für Workflow-Listen und Verlauf​

Diese veröffentlichten Aufrufe liefern eine Seite, keinen automatischen vollständigen Abruf: await client.list_workflows(...) / await client.get_history(workflow_id, run_id, ...). Setzen Sie mit dem zurückgegebenen undurchsichtigen Token fort und behalten Sie Namespace, Filter und Workflow/Lauf bei. Enden Sie beim letzten null/leeren Token und behandeln Sie Seitenfehler ausdrücklich. Eine Teilseite ist kein Replay-Bundle. Nutzen Sie für Offline-Replay die Verlaufsexport-API des SDK. Der veröffentlichte Client Python 2.9.0 definiert aktuelle Parameter; neue automatische Iteratoren werden damit nicht zugesagt.

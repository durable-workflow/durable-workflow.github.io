Verwaltete Cloud-Laufzeitumgebung

Durable Workflow Cloud ist ein verwalteter Orchestrierungsdienst. Cloud betreibt sowohl die gehostete Control Plane als auch die Orchestrierungslaufzeit, einschließlich Workflow-Zustand, Historie, Zeitplänen, Task-Warteschlangen, Leases und dauerhafter Einsicht. Kunden betreiben SDK-Clients und -Worker gegen einen bereitgestellten Cloud-Namespace.

Dies ist vom Selbsthosting getrennt. Ein selbst gehosteter Durable Workflow Server läuft unabhängig und wird niemals an Cloud angeschlossen.

Pläne und Preise​

Sie zahlen für bereitgestellte Kapazität, nicht für Workflow-Semantik. Jeder Namespace erhält eine isolierte verwaltete Laufzeitumgebung. Ihre PHP-, Python- und Rust-Worker laufen in Ihrer eigenen Umgebung. Aktuelle Bereitstellungsverfügbarkeit zeigen Cloud-Preise und das Dashboard.

Cloud Dev ist jetzt verfügbar. Die vier HA-Pläne werden qualifiziert und können noch nicht gekauft oder bereitgestellt werden. Ihre unten genannten Preise, Kapazitäten, Verfügbarkeit und SLA-Bedingungen sind geplant, keine aktuellen Kaufangebote.

Kapazität umfasst verwaltete Laufzeitkomponenten, nicht die Rechenleistung Ihrer Worker. Bei geplanten HA-Plänen sind Replikation und Standby-Kapazität im Preis enthalten. Die Tabelle addiert Replikate nicht als zusätzliche Workflow-Ausführungskapazität. Jeder Plan enthält Managed Waterline, grundlegende verschlüsselte Sicherungen, Upgrades und eine stabile Laufzeit-URL.

Bereitgestellte Laufzeitumgebungen werden nach Laufzeitdauer abgerechnet, von Aktivierung bis Stilllegung minutengenau gemessen. Mindestbeträge und Obergrenzen gelten je Laufzeitkauf in einem UTC-Kalendermonat. Ungenutzte bereitgestellte Zeit ist kostenpflichtig. Ein Monat ohne bereitgestellte Zeit hat keine Laufzeitkosten. Ein neuer Kauf hat eigene Mindest- und Höchstbeträge. Dienstseitige Reparatur oder Wiederherstellung setzt sie nicht zurück. Stripe stellt aufgelaufene Nutzung monatlich in Rechnung. Preise verstehen sich zuzüglich gegebenenfalls anfallender Steuern.

Speicher ist auf die enthaltene Zuteilung begrenzt. Es gibt keine separat käuflichen Speichererweiterungen, automatische Speichervergrößerung oder Speicher-Mehrverbrauchsgebühren. Fordern Sie einen größeren Laufzeitplan an, bevor Sie die Grenze erreichen. Der alleinige Wechsel von einer zu mehreren Regionen erhöht den Speicher nicht. Ein Kapazitätsupgrade erfordert eine tatsächliche Laufzeitänderung, nicht nur eine Abrechnungsänderung, und wird derzeit mit Support vereinbart. Netzwerknutzung wird gemessen, derzeit nicht berechnet und ist nicht unbegrenzt.

Wählen Sie einen Plan über Cloud-Preise. Für größere Kapazität, andere Vernetzung, SSO, Unternehmenssupport oder eigene Verfügbarkeitsanforderungen kontaktieren Sie uns.

Grenze des verwalteten Dienstes​

Die kundensichtbare Grenze ist ein Cloud-Namespace:

Cloud organization
  project
    environment
      namespace
        stable runtime URL
        client runtime credential  ---> workflow starts and commands
        worker runtime credential  ---> registration, polling, and completion

Cloud-operated runtime
  workflow state and history
  schedules and task queues
  leases, matching, and visibility
  Managed Waterline

Cloud verantwortet Namespace-Bereitstellung, Laufzeitbetrieb, Persistenz, Platzierung, Laufzeitzustand, Wiederherstellung und Managed Waterline für den Namespace. Kunden verantworten Anwendungscode, Workflow- und Aktivitätsimplementierungen sowie ihre Worker-Prozesse. Cloud-Kunden stellen keinen separaten Waterline-Dienst bereit.

Der HTTPS-Endpunkt des Namespace verbindet direkt mit seiner verwalteten Laufzeitumgebung. SDK-Verkehr wird nicht durch die Cloud-Website-/Control-Plane-Anwendung geleitet. Verwenden Sie die zurückgegebene Laufzeit-URL unverändert ohne angehängtes /api. SDK und CLI bauen ihre API-Pfade selbst. Verwaltungs-API-Aufrufe verwenden weiterhin https://cloud.durable-workflow.com/api/v1.

Cloud-Verwaltung und Laufzeitverkehr verwenden unterschiedliche Zugangsdaten:

  • Ein Cloud-API-Schlüssel (dwc_...) verwaltet Projekte, Umgebungen, Namespaces, Abrechnung und den Lebenszyklus von Laufzeit-Zugangsdaten.
  • Client-Laufzeit-Zugangsdaten (dwr_...) starten und steuern Workflows in einem verwalteten Namespace.
  • Worker-Laufzeit-Zugangsdaten (dwr_...) registrieren Worker, fragen Tasks per Long Polling ab, senden Heartbeats und schließen Arbeit in diesem Namespace ab.

Ein Cloud-API-Schlüssel wird an der Namespace-Laufzeit-URL nicht angenommen. Laufzeit-Zugangsdaten gelten für einen Namespace und eine Rolle, werden nur bei Erstellung zurückgegeben und fehlen in späteren Listen- und Audit-Antworten.

Verwendet der Cloud-Einstieg die CLI, installieren Sie sie nach dem CLI-Leitfaden und aktualisieren Sie eine bestehende eigenständige Installation explizit mit dw upgrade. Die CLI aktualisiert sich niemals im Hintergrund. Führen Sie nach Installation oder Upgrade command -v dw und dw --version aus. Beheben Sie Hinweise zum Installer-PATH, bevor Sie Cloud-Zugangsdaten verwenden, damit das gewählte Release die aktive Binärdatei ist.

Einen Namespace bereitstellen und verbinden​

1. Namespace erstellen und bereitstellen​

Erstellen Sie im Cloud-Dashboard eine Organisation, ein Projekt, eine Umgebung und einen Namespace. Wählen Sie dann seinen Kapazitätsplan. Das Erstellen eines Kontos oder einer Namespace-Definition stellt keine kostenpflichtige Kapazität bereit. Schließen Sie die Zahlungseinrichtung über Stripe ab und wählen Sie auf der Namespace-Seite Bereitstellen (Provision). Das bloße Hinzufügen einer Karte startet die Bereitstellung nicht.

Bereitstellung ist asynchron. Die Namespace-Seite aktualisiert den Fortschritt, während Cloud die Laufzeitumgebung vorbereitet. Warten Sie vor SDK-Arbeit auf den aktiven Zustand. Die Seite bietet außerdem die Erstellung von Laufzeit-Zugangsdaten und Managed-Waterline-Zugriff zur Inspektion von Workflows und ihrer Historie.

Schließen Sie bei API-gesteuerter Einrichtung zuerst die Zahlungseinrichtung ab. Das folgende Beispiel verwendet den Standardplan der Organisation. capacity_plan_version kann einen anderen verfügbaren Plan wählen. Geben Sie keine eigene Server-URL, Bereitstellungskennung oder Platzierungsangabe an:

curl -X POST \
  https://cloud.durable-workflow.com/api/v1/projects/PROJECT/environments/ENVIRONMENT/namespaces \
  -H "Authorization: Bearer dwc_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"orders","retention_days":30}'

curl -X POST \
  https://cloud.durable-workflow.com/api/v1/projects/PROJECT/environments/ENVIRONMENT/namespaces/orders/provision \
  -H "Authorization: Bearer dwc_..."

Nach abgeschlossener Bereitstellung liefert die Namespace-Antwort die stabile runtime_url, runtime_namespace, den verwalteten Status und kundensichtbare Regionsinformationen. Behandeln Sie URL und Namespace als von Cloud verwaltete Konfiguration. Leiten Sie keinen Endpunkt ab und ersetzen Sie ihn nicht durch eine selbst gehostete Server-Adresse.

2. Getrennte Client- und Worker-Zugangsdaten ausstellen​

Stellen Sie die beiden Laufzeitrollen unabhängig aus:

curl -X POST \
  https://cloud.durable-workflow.com/api/v1/projects/PROJECT/environments/ENVIRONMENT/namespaces/orders/runtime-credentials \
  -H "Authorization: Bearer dwc_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"orders-client","role":"client"}'

curl -X POST \
  https://cloud.durable-workflow.com/api/v1/projects/PROJECT/environments/ENVIRONMENT/namespaces/orders/runtime-credentials \
  -H "Authorization: Bearer dwc_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"orders-worker","role":"worker"}'

Jedes Token wird einmal in seiner Erstellungsantwort angezeigt. Speichern Sie es im Geheimnisspeicher, den nur die zugehörige Rolle verwendet. Ein bewusst kombinierter Client-/Worker-Prozess erhält beide Werte als zwei getrennte Geheimnisse. Rotieren und widerrufen Sie die Rollen unabhängig. Ersetzen Sie Laufzeit-Zugangsdaten niemals durch einen Cloud-API-Schlüssel.

3. Einen ersten Cloud-Workflow abschließen​

Die gemeinsame Testumgebung der Sample App für externe Laufzeitumgebungen führt denselben implementierten Workflow-/Aktivitätsablauf mit PHP, Python oder Rust aus. Öffnen Sie einen Sample-App-Codespace, exportieren Sie die bereitgestellten Namespace-Werte und zwei Laufzeit-Zugangsdaten und wählen Sie eine Anwendungs-Task-Warteschlange:

export DURABLE_WORKFLOW_RUNTIME_URL='<provisioned-runtime-url>'
export DURABLE_WORKFLOW_NAMESPACE='<provisioned-runtime-namespace>'
export DURABLE_WORKFLOW_CLIENT_TOKEN='<client-runtime-credential>'
export DURABLE_WORKFLOW_WORKER_TOKEN='<worker-runtime-credential>'
export DURABLE_WORKFLOW_TASK_QUEUE='<language-task-queue>'

Wählen Sie dann ein offizielles SDK und führen Sie denselben verwalteten Laufzeitvertrag aus:

language=php # Choose php, python, or rust.
scripts/playground "$language" --runtime managed \
  --runtime-url "$DURABLE_WORKFLOW_RUNTIME_URL" \
  --namespace "$DURABLE_WORKFLOW_NAMESPACE" \
  --task-queue "$DURABLE_WORKFLOW_TASK_QUEUE"

Der Runner ermittelt aktuelle stabile Artefaktversionen, gibt jede Zugangsdatenrolle nur an ihren Kindprozess, wartet bis zu 60 Sekunden auf eine Worker-Registrierung mit genau der Warteschlange und den erzeugten Workflow- und Aktivitätstypen und startet dann eine Client-Anfrage. Erfolg erfordert das erwartete SDK-Ergebnis, completed von dw und die erforderliche Workflow- und Aktivitätshistorie. Im verwalteten Modus startet der Befehl keinen lokalen Server und kein lokales Waterline.

Führen Sie für jede Sprache den vollständigen verwalteten Befehl oben erneut aus und ändern Sie nur language. Die Implementierung im jeweiligen SDK beschreibt dessen Leitfaden:

  • PHP SDK: language=php setzen.
  • Python SDK: language=python setzen.
  • Rust-Schnellstart für verwaltete Laufzeitumgebungen: language=rust setzen und die Diagnosen für Worker-Bereitschaft, abgeschlossenes Ergebnis und Abweichungen verwenden.

Ein kombinierter Client-/Worker-Ablauf hält beide Laufzeit-Zugangsdaten als getrennte Geheimnisse. Ein Cloud-Verwaltungsschlüssel ist keine Laufzeit-Zugangsberechtigung und darf unter keiner Laufzeit-Token-Variable exportiert werden.

4. Im verwalteten Betrieb fortfahren​

Der SDK-Client startet Workflows und sendet Folgebefehle über die Namespace-Laufzeit-URL. Kundenseitig betriebene Worker registrieren sich und fragen mit der Worker-Rolle über dieselbe URL per Long Polling ab. Cloud authentifiziert und begrenzt jede Anfrage, führt das Orchestrierungsprotokoll in der verwalteten Laufzeitumgebung aus und speichert Workflow-Zustand und Historie.

Die Kundenanwendung wählt für eine Operation keine Laufzeitbereitstellung. Workflow-IDs, Lauf-IDs, Task-Warteschlangen, Kompatibilitätsmarker und Avro-Nutzlastcodierung bleiben dauerhafte Anwendungsverträge im Cloud-Namespace.

Vernetzung kundenseitig betriebener Worker​

Worker können in Ihrem Netzwerk, Ihrer VM-Flotte, Containerplattform oder Anwendungsumgebung laufen. Sie benötigen ausgehendes HTTPS zur Namespace-Laufzeit-URL und müssen langlebige Worker-Protokoll-Abfragen zulassen.

  • Eingehende Verbindungen von Cloud zu Workern sind nicht erforderlich.
  • Proxys und Ausgangsgateways dürfen Long Polling nicht in eine hektische Wiederholungsschleife verkürzen.
  • Worker sollten vorübergehende Verbindungsfehler und Nichtverfügbarkeitsantworten mit begrenzten Wartezeiten wiederholen.
  • Das Verschieben eines Worker-Prozesses verschiebt keinen Workflow-Zustand. Cloud hält dauerhaften Namespace-Zustand und Historie.
  • Zugangsdatenrotation erfordert keine Änderung von Laufzeit-URL, Namespace oder Task-Warteschlange.

Regionsplatzierung und Wiederherstellungsgrenze​

Cloud Dev ist mit der unten beschriebenen Wiederherstellungsgrenze verfügbar. Die HA-Grenzen beschreiben geplante, bis zur Qualifizierung nicht verfügbare Pläne:

  • Cloud Dev: ein isolierter Host mit dauerhaftem Zustand und Sicherungen. Wartung und Wiederherstellung können den Dienst unterbrechen. Es gibt kein Verfügbarkeits-SLA und kein automatisches regionales Failover.
  • Geplante HA in einer Region: drei replizierte Hosts in einer Region mit automatischem Primary-Failover. Ein Host darf ausfallen, ohne das verbleibende Quorum zu verlieren. Ein Ausfall der gesamten Region ist vom SLA nicht abgedeckt.
  • Geplante HA über mehrere Regionen: drei replizierte Hosts in drei Regionen mit automatischem Primary-Failover. Das SLA umfasst Verlust oder Isolation einer konfigurierten Region, sofern die verbleibenden Mitglieder ein Quorum bilden können.

Bei den geplanten HA-Profilen soll die stabile Laufzeit-URL dem gewählten Primary folgen. Bei unterstütztem Failover ändern Sie die SDK-Konfiguration nicht. Ein isolierter ehemaliger Primary darf keine maßgebliche Arbeit weiter bedienen. Kann kein sicherer Primary bestimmt werden, stoppt die Laufzeitumgebung, statt widersprüchliche Schreibzugriffe anzunehmen. HA verspricht keine unterbrechungsfreien Anfragen: Clients und Worker benötigen weiterhin begrenzte Wiederholungen für vorübergehende Fehler.

Die Namespace-Seite zeigt Topologie, Regionsinformationen und Dienststatus. Sicherungen unterstützen Wiederherstellung, ersetzen aber keine laufende Replikation. Kurze Failover-Tests belegen die geprüften Ausfälle, keine allgemeine Wiederherstellungszeitgarantie oder erreichte Monatsverfügbarkeit.

SLA-Messung und Gutschriften​

Die vier geplanten SLA-Pläne sehen 99.99% Verfügbarkeit je UTC-Kalendermonat vor, am Kunden-Laufzeitendpunkt in Ein-Minuten-Fenstern gemessen. Fehlende Messungen zählen als nicht verfügbar; geplante Wartung wird nicht ausgenommen. Die Verfügbarkeit kundenseitiger Worker ist von der verwalteten Laufzeitverfügbarkeit getrennt.

SLA-Pläne erhalten automatisch Servicegutschriften auf das Konto. Die Summe ist auf die Gebühren der betroffenen Laufzeitumgebung im jeweiligen Monat begrenzt; für Ausfälle gibt es keine Barauszahlungen. Cloud Dev hat keine SLA-Gutschriften. Verfügbarkeit und Abrechnungsbedingungen stehen in den Cloud-Nutzungsbedingungen und unter Cloud-Preise.

Private Vernetzung und Support-Grenze​

Der Cloud-Selbstbedienungsvertrag für 2.0 setzt ausgehenden Zugriff von Clients und Workern auf die öffentliche Namespace-Laufzeit-URL voraus. Rein private Eingänge, individuelle VPN-/Peering-Vereinbarungen und anbieterspezifisches privates Routing sind supportbegleitete Vernetzungsentwürfe, keine versteckten Standards. Kunden erhalten niemals interne Laufzeitadressen und werden nicht aufgefordert, die Namespace-URL zu umgehen.

Cloud oder selbst gehosteter Server​

Wählen Sie Cloud, wenn Durable Workflow Orchestrierungslaufzeit, Persistenz, Verfügbarkeit des gewählten Plans, Wiederherstellung und Managed Waterline betreiben soll, während Ihr Team SDK-Clients und -Worker betreibt.

Wählen Sie selbst gehosteten Server, wenn Ihr Team Server-Image, Datenbank, Cache, Vernetzung, Authentifizierung, Sicherungen und Failover unabhängig betreiben muss. Ein selbst gehosteter Server kann nicht für einen Cloud-Namespace registriert, daran angeschlossen oder als dessen Laufzeitgrundlage verwendet werden. Eingebettetes Laravel, selbst gehosteter Server und Cloud sind getrennte Bereitstellungsentscheidungen.

Die Latenz enthält Client-Netzwerk und Ergebnisabfragen alle 100 ms. Sie ist keine interne Task-Planungslatenz und sollte nicht mit einer internen Planungsmetrik einer Engine verglichen werden.

Die Host-CPU war in Fünf-Sekunden-Stichproben durchschnittlich 63.5% und maximal 89% ausgelastet. Es gab keine Container-OOM-Kills oder Neustarts. Größere Nutzlasten, zusätzliche Aktivitäten, Timer, Signale, Abfragen, Replay-lastige Historien und Kunden-Worker-Latenz ändern die Kapazität. Cloud-Abrechnung basiert auf bereitgestellter Laufzeitdauer mit fest enthaltenem Speicher, nicht auf Workflow-Operationen.

Die Zuteilung umfasst den von Cloud betriebenen Server, MySQL, Redis, Planung, Waterline-Zugriff, Sicherungen, Upgrades und Infrastruktur. Ihre PHP-, Python- und Rust-Worker laufen außerhalb davon. Workflow-Starts, Aktivitätsversuche, Wiederholungen, Timer, Signale, Abfragen, Updates und Kind-Workflows sind Betriebstelemetrie, keine separaten Abrechnungseinheiten. Preise verstehen sich zuzüglich gegebenenfalls anfallender Steuern. Enthaltener Speicher erzeugt keine separate Gebühr.

Cloud bietet organisationsbezogene Nutzungsdaten für Finanzen, Betrieb und automatisierte Kostenverrechnung. Der Endpunkt authentifiziert per Cloud-API-Schlüssel und akzeptiert keine Kunden- oder Organisations-ID in der Anfrage. Die Organisation wird aus dem dwc_-Bearer-Token aufgelöst, damit Kunden keine fremde Nutzung abfragen können.

GET /api/v1/billing/usage?period_start=2026-05-01&period_end=2026-05-31
Authorization: Bearer dwc_...
Accept: application/json

period_start und period_end sind optionale ISO-8601-Daten. Ohne Angabe liefert Cloud den aktuellen Kalendermonat. Lesen und Export der Nutzungsdaten bleiben auch verfügbar, wenn Abrechnungsbeschränkungen Namespace-Bereitstellung oder Workflow-Operationen pausieren. Finanzteams können so weiterhin den Kontostatus bereinigen.

Das Antwortschema ist durable_workflow.cloud.namespace_capacity_usage.v1. Es trennt zugeteilte Kapazitätszeit von semantischen Ereigniszählern. Speicherbezogene Felder bleiben für historische Abrechnung im Schema. Sie autorisieren keinen Erweiterungskauf. Die verkürzte Cloud-Dev-Antwort unten zeigt die aktuellen Planbedingungen.

Cloud Devs Zeitmessung beginnt mit Aktivierung der isolierten Laufzeitumgebung und endet mit deren Stilllegung. Monatsobergrenze und Mindestbetrag gelten je Laufzeitkauf in UTC-Kalendermonaten. Speicher wächst nicht automatisch und beginnt nicht automatisch Gebühren zu erzeugen. Cloud hält auf dem Laufzeitdatenträger eine Betriebs- und Wiederherstellungsreserve vor. Fordern Sie vor Erreichen der enthaltenen Zuteilung einen größeren Laufzeitplan an.

Ungenutzte Laufzeitumgebungen verursachen weiter Kapazitätskosten. Stilllegung stoppt die Kapazitätsabrechnung und entfernt aktive Laufzeitdaten und Zugangsdaten. Sie ist kein Pausieren/Fortsetzen. Geplante SLA-Bedingungen nutzen dasselbe Modell bereitgestellter Zeit mit eigenen Sätzen, Mindest- und Höchstbeträgen. Verwenden Sie beim Interpretieren der Nutzung die vom Plan zurückgegebenen billing_terms. Historische Rechnungen behalten ihre akzeptierten Bedingungen.

Exportieren Sie dieselben Nachweise als CSV oder JSON-Bericht, wenn ein nachgelagertes Finanzsystem eine Datei benötigt:

curl -OJ "https://cloud.durable-workflow.com/api/v1/billing/usage/export?period_start=2026-05-01&period_end=2026-05-31" \
  -H "Authorization: Bearer dwc_..."

curl -OJ "https://cloud.durable-workflow.com/api/v1/billing/usage/report?period_start=2026-05-01&period_end=2026-05-31" \
  -H "Authorization: Bearer dwc_..."

Für ein JSON-gestütztes Dashboard-Panel fordern Sie dieselbe API mit dessen Zeitraum an:

GET https://cloud.durable-workflow.com/api/v1/billing/usage?period_start=${__from:date:YYYY-MM-DD}&period_end=${__to:date:YYYY-MM-DD}
Authorization: Bearer dwc_...

Führen Sie dann die Namespace-Kapazitätszeilen in eine flache Struktur über:

.by_namespace[]
| {
    project,
    environment,
    namespace,
    plan: .plan.name,
    cpu_vcpu: .allocation.managed_cpu_vcpu,
    memory_gb: .allocation.managed_memory_gb,
    included_storage_gb: .allocation.included_durable_storage_gb,
    capacity_status
  }

Verwenden Sie invoice_units für Kapazitäts- und Speicherabgleich. operational_telemetry hilft, Lastform und Benchmark-Verhalten zu verstehen. Wandeln Sie diese Ereigniszähler nicht in Gebühren um.

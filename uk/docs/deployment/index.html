Самостійне розгортання

Durable Workflow v2 підтримує кілька варіантів самостійного розгортання. Оберіть найпростіший, що відповідає вашому середовищу, і явно визначте образ, базу даних, кеш, автентифікацію, готовність до роботи та контракт оновлення.

Цей посібник описує окремий дистрибутив Server. Якщо пакет Laravel вбудовано у ваш застосунок, використовуйте сторінки встановлення та налаштування пакета. Durable Workflow Cloud — окремий керований сервіс: Cloud обслуговує середовище виконання, зберігання, розміщення та відновлення. Власний Server ніколи не підключається до Cloud. Дивіться кероване середовище Cloud. Поточний контракт Cloud охоплює кероване виконання та відновлення в одному регіоні. Він не обіцяє міжрегіональної реплікації, автоматичного перемикання регіонів після відмови або повернення до початкового регіону.

Дистрибутив Server для самостійного розгортання не містить і не обслуговує Waterline. Розгортайте Waterline окремо, коли потрібен його операторський інтерфейс, і підключайте його до простору імен Server за посібником розгортання та моніторингу Waterline. Cloud натомість містить Managed Waterline для свого керованого простору імен.

Публічний дистрибутив навмисно оптимізовано для локальної розробки, одновузлового виробничого середовища та невеликих кластерів. Маніфести Kubernetes надано командам, які вже обслуговують Kubernetes. Матеріали щодо кількох регіонів з активним і резервним регіонами є оцінювальним посібником за участю підтримки, а не доведеним самостійним контрактом 2.0. Дивіться активний і резервний регіони нижче.

Висока доступність в одному регіоні — перемикання керованої бази чи Redis, втрата вузла API чи worker, перезапуск процесу планувальника — наразі потребує участі підтримки, доки перевірка точного випуску не пройдена. Дивіться високу доступність і перемикання в одному регіоні. Для власного Server кілька активних регіонів, автоматичне регіональне перемикання, дублікати планувальника як стала топологія та перевірка керованого Kubernetes конкретного провайдера залишаються шляхами за участю підтримки: вони залежать від ваших бази, кешу, мережі, безпеки, процесів і оновлень. Опублікований чарт Helm є самостійним шляхом пакування в тих самих межах відповідальності оператора. Cloud наразі надає керовану роботу й відновлення в одному регіоні, без міжрегіональної реплікації чи регіонального перемикання. Дивіться кероване середовище Cloud та межу підтримки щодо комерційної моделі.

Безпека, дані та аудит​

Власні розгортання Durable Workflow успадковують більшість механізмів безпеки від вашого середовища. Публікуйте ці факти в тому самому комплекті випуску чи операційному посібнику, що й тег образу, план міграції та підтвердження відновлення:

ОбластьЧесне твердження про випуск
Обробка данихАргументи workflow, результати, історія, memo, пошукові атрибути, мітки видимості, контекст команд, записи аудиту, повідомлення винятків та примітки оператора можуть містити дані застосунку клієнта. Ідентифікатори workflow, пошукові атрибути й мітки — видимі оператору метадані, а не сховище секретів. Ідентифікатори workflow залишаються відкритим текстом і не охоплюються кодеками payload.
ШифруванняВикористовуйте TLS для кожного виробничого HTTP-інтерфейсу й налаштуйте TLS бази даних у кожній ролі Server, включно з міграціями. Шифрування під час зберігання забезпечують ваша база, об’єктне сховище, файлова система, черга, кеш і засіб керування секретами. Пакет workflow і Server не шифрують автоматично кожне поле payload.
Відповідність вимогамПакет із відкритим кодом і власний Server надають механізми й підтвердження аудиту, а не сертифікацію відповідності самі по собі. Твердження про SOC 2, HIPAA, PCI, ISO або FedRAMP належать вашій програмі, якщо керована пропозиція не документує інше.
Журнали аудитуКоманди workflow, події аудиту розкладів, метадані експорту історії та записи викликів служб надають стійкі операційні підтвердження. Вони не є повноцінною SIEM, DLP, незмінним зовнішнім реєстром або системою юридичного збереження даних, якщо ви не додасте ці компоненти.
ПідтримкаТут документовано облікові дані з обмеженням за ролями, завершення TLS, резервні копії, репетиції відновлення та вузькі самостійні топології. Розширене керування ідентичністю, розгортання mTLS, приватна мережа, власні рушії політик, відповідність провайдера й індивідуальна перевірка топології потребують участі підтримки, якщо публічні документи не визначають інше.

Мережева модель має бути явною:

  • Вхідні webhook: документуйте публічну кінцеву точку, метод автентифікації, захист від повторних запитів або стратегію ідемпотентності, тайм-аут, межу payload, довірені заголовки проксі та план ротації секретів.
  • Трафік worker до сервера: використовуйте перевірку TLS, облікові дані worker з обмеженням за ролями, заголовки простору імен, приватну мережу чи mTLS за перетину недовіреної мережі та ротацію, що не надає токенам worker повноважень оператора.
  • Операторські інтерфейси: захищайте Waterline, операторські API Server, кінцеві точки автоматизації CLI та власні адміністративні панелі автентифікованими сеансами чи службовими обліковими даними з обмеженням за ролями, захистом CSRF для браузерних сеансів і задокументованими межами проксі/TLS.

Опубліковані образи​

Для власних розгортань Server використовуйте опубліковані образи:

  • Docker Hub: durableworkflow/server:2.10.1
  • GitHub Container Registry: ghcr.io/durable-workflow/server:2.10.1
  • Закріплення за дайджестом: durableworkflow/server@sha256:... або ghcr.io/durable-workflow/server@sha256:...

Використовуйте змінювані теги лише для локальних експериментів. Виробничі файли змінних середовища мають закріплювати конкретну версію чи дайджест, щоб кроки оновлення й відкату можна було перевірити.

Локальна розробка та внутрішнє невиробниче середовище​

Використовуйте рецепт Compose опублікованого образу для середовища без вихідного коду з MySQL і Redis:

curl -fsSLO https://raw.githubusercontent.com/durable-workflow/server/main/docker-compose.published.yml

export DW_SERVER_TAG=2.10.1
export DW_AUTH_TOKEN=dev-token

docker compose -f docker-compose.published.yml up -d --wait

Перевірте API, готовність до роботи, виявлення кластера й реєстрацію worker:

curl http://localhost:8080/api/health
curl http://localhost:8080/api/ready
curl -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  http://localhost:8080/api/cluster/info

curl -X POST http://localhost:8080/api/worker/register \
  -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Namespace: default" \
  -H "X-Durable-Workflow-Protocol-Version: 1.0" \
  -d '{"worker_id":"compose-worker","task_queue":"compose","runtime":"python"}'

Цей шлях придатний для розробки та внутрішнього тестового середовища. Він не є межею виробничої безпеки: приклад використовує один токен сумісності, типові паролі служб, локальні іменовані томи й не має TLS.

Одновузлове виробниче середовище​

Використовуйте той самий артефакт Compose із виробничою конфігурацією поза системою керування версіями:

DW_SERVER_IMAGE=durableworkflow/server:2.10.1
SERVER_PORT=8080
APP_ENV=production
APP_DEBUG=false

DB_DATABASE=durable_workflow
DB_USERNAME=workflow
DB_PASSWORD=replace-with-random-password
DB_ROOT_PASSWORD=replace-with-random-root-password

DW_AUTH_DRIVER=token
DW_AUTH_BACKWARD_COMPATIBLE=false
DW_WORKER_TOKEN=replace-with-worker-token
DW_OPERATOR_TOKEN=replace-with-operator-token
DW_ADMIN_TOKEN=replace-with-admin-token

Запустіть із цим файлом змінних середовища:

docker compose --env-file durable-workflow.prod.env \
  -f docker-compose.published.yml up -d --wait

Обслуговуйте хост як виробничий сервіс:

  • Розмістіть TLS, публічну маршрутизацію, журналювання запитів і списки дозволених IP у зворотному проксі перед контейнером API.
  • Не відкривайте MySQL чи Redis публічно.
  • Використовуйте DW_WORKER_TOKEN для worker, DW_OPERATOR_TOKEN для трафіку застосунку й оператора та DW_ADMIN_TOKEN для просторів імен і адміністрування.
  • Резервуйте том MySQL перед кожним оновленням образу й за регулярним розкладом. Redis варто зберігати для коректних перезапусків, але MySQL залишається стійким джерелом істини історії workflow.
  • Для відновлення зберігайте разом точний файл змінних середовища, тег чи дайджест образу та резервну копію бази.

Порядок оновлення:

  1. Створіть резервну копію MySQL і запишіть поточне посилання на образ.
  2. Змініть лише DW_SERVER_IMAGE або DW_SERVER_TAG.
  3. Завантажте новий образ.
  4. Виконайте docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml up -d --wait.
  5. Перевірте /api/ready, /api/cluster/info та реєстрацію worker перед переведенням зовнішнього трафіку.

Невеликі кластерні розгортання​

Невеликий кластер помірно розширює одновузлову модель. Перевірений самостійний контракт навмисно вузький:

  • Запускайте 2–3 контейнери API без локального стану за балансувальником. Перевірки працездатності й готовності, виявлення кластера, реєстрація worker, опитування та завершення завдань workflow мають працювати без закріплених сеансів.
  • Використовуйте одну спільну зовнішню MySQL або PostgreSQL для стійкої історії. SQLite підтримує лише один вузол і не є кластерним сховищем.
  • Використовуйте спільний Redis для кешу, сигналів пробудження довгого опитування, блокувань черг query, блокувань приймання черг завдань та стану черг. Багатовузловий режим без Redis не входить до підтримуваного контракту.
  • Під час розгортання перевіряйте GET /api/cluster/info кожного вузла API. topology.current_shape має залишатися standalone_server, topology.current_roles — містити api_ingress, control_plane, matching і history_projection, а topology.execution_mode має залишатися remote_worker_protocol для окремих вузлів Server. Перевіряйте фактично розгорнутий підбір завдань через topology.matching_role: типові вузли повідомляють queue_wake_enabled: true, shape: "in_worker" та wake_owner: "worker_loop", а розгортання окремого підбору перемикають вузли з DW_V2_MATCHING_ROLE_QUEUE_WAKE=0 на queue_wake_enabled: false, shape: "dedicated" та wake_owner: "dedicated_repair_pass". Цей самий блок має далі оголошувати потрібний task_dispatch_mode, закріплені осі маршрутизації partition_primitives і поточний backpressure_model. Значення кожного поля описано в топології ролей Server.
  • Масштабуйте зовнішні worker SDK незалежно від вузлів API. Worker можуть працювати на окремих хостах чи в окремих процесах, але мають звертатися до збалансованої кінцевої точки API, а не до одного закріпленого вузла.
  • Налаштуйте приймання черги завдань для черг, які захищають орендаря, зовнішній API, пул з’єднань бази або іншу спільну залежність-отримувача.
  • Запускайте рівно один процес планувальника чи обслуговування для оцінювання розкладів, застосування тайм-аутів activity та очищення історії.
  • Виконуйте початкове налаштування й міграції один раз на розгортання до приймання трафіку новими контейнерами API та worker.
  • Оберіть режим оновлення цього випуску: повна зупинка (завершення прийнятої роботи worker, зупинка планувальника й обслуговування, заміна вузлів API, початкове налаштування й міграції, перезапуск worker і планувальника) або поступове оновлення, коли виконано всі гарантії контракту.
  • Розглядайте базу й Redis як основні області відмов. Контейнери Server можна замінити; шари зберігання та координації — ні.

Опубліковані самостійні рецепти починаються з форми standalone_server, хоча виявлення кластера також називає split_control_execution підтримуваною топологією продукту. Це один контракт із різними призначеннями ролей, а не другий серверний продукт. Якщо пізніше випробовуватимете явніший поділ ролей, продовжуйте читати topology.current_shape, topology.current_roles та topology.matching_role з /api/cluster/info, а не виводити обов’язки з назв хостів чи контейнерів. Топологія ролей Server пояснює призначення ролей і шлях міграції.

Кожен вузол API має використовувати однакові токени автентифікації чи ключі підпису, версію застосунку, версію пакета workflow, конфігурацію кодеків payload, підключення бази й Redis. Задайте кожному вузлу API унікальний DW_SERVER_ID, щоб виявлення кластера та журнали розрізняли вузли.

Непідтримувані межі явні: кластер SQLite, багатовузловий режим без Redis, дублікати планувальника як стала топологія, бази з кількома активними вузлами запису, автономне регіональне перемикання власного середовища та широкі SLA «п’ять дев’яток» чи «без простою» потребують окремої перевірки або проєктування за участю підтримки до використання. Матеріали щодо активного й резервного регіонів також є оцінювальними; дивіться відповідний розділ. Висока доступність в одному регіоні — перемикання керованої бази й Redis, втрата вузла API чи worker та перезапуск планувальника — залишається оцінювальним контрактом за участю підтримки до проходження перевірки випуску. Цілі відновлення рушія, правила готовності під час перемикання та потрібні підтвердження наведено в контракті одного регіону.

Цей шлях самостійний, коли команда вже має чітку модель VM, мережі, бази, кешу, резервування та балансувальника. Підтримка потрібна, коли необхідна допомога з визначенням цих меж, місткості, порядку розгортання чи процедур відновлення.

Бюджети таймаутів довгих опитувань worker​

Справне опитування worker може не передавати даних до завершення очікування на сервері. Ураховуйте цю тишу в HTTP-клієнті worker, вихідному проксі, service mesh, публічному балансувальнику, ingress і кожному зворотному проксі перед API. Опитування worker проходять через спільний API ingress. Окрема роль matching не оминає ці вузли.

БюджетЩо він обмежує
Тривалість опитування на серверіЧас очікування роботи до порожньої відповіді. timeout_seconds у запиті перевизначає DW_WORKER_POLL_TIMEOUT. Змінна є типовим значенням для запиту без цього поля, а не межею для SDK. Протокол дозволяє до 60 секунд.
Таймаут з’єднання / пулу клієнтаУстановлення з’єднання або отримання його з пулу. Ці етапи не повинні тривати весь час тихого опитування.
Таймаут читання / загальний таймаут клієнтаОчікування байтів відповіді або всієї операції, якщо транспорт має загальну межу. Додайте до очікування сервера запас на з’єднання, планування та відповідь. Таймаут читання може вимірювати паузу між частинами даних, а не весь запит.
Idle / upstream read / request timeout посередникаКожна межа активного запиту на кожному вузлі має дозволяти нормальне тихе опитування та відповідь. Keepalive для з’єднання між запитами є іншою межею.
Завершення worker / кінцевий строк викликуБюджет завершення worker та початковий кінцевий строк виклику чи query залишаються жорсткими межами. Скасовуйте або завершуйте роботу в цих межах. Не подовжуйте query через проксі чи повторну спробу.

Перевіряйте розрахунки встановленого SDK. У перевіреній нижче версії Python позитивне очікування на сервері обмежується 60 секундами, а таймаути фаз HTTP мають щонайменше п’ять додаткових секунд. Типове опитування Worker триває 35 секунд, що зазвичай дає 40 секунд для фаз HTTP. Межа читання посередника у 30 секунд може обірвати справне типове опитування. PHP і Rust мають власні типові значення та політики повторів. Запас Python або налаштування gRPC keepalive не є універсальним правилом. Дивіться посібники SDK для PHP, Python, Rust та довідник matching.

Звичайні виклики control plane через Client у PHP SDK 3.2.0 не задають типового загального кінцевого строку HTTP. Дивіться перевірений дефект PHP #203. Налаштуйте обмежений HTTP-клієнт для цих викликів і зберігайте початковий кінцевий строк. Таймаут опитування Worker не обмежує всі запити SDK.

PHP SDK 3.4.0 або новіший додає типовий загальний строк 60 секунд для звичайних control HTTP-запитів через власний транспорт SDK; задайте скінченне requestTimeoutSeconds щонайменше 0.001 секунди. Ці таймаути власного транспорту SDK мають reason=request_timeout і status=0. SDK робить одну спробу: mutation із таймаутом уже могла бути прийнята, тому перед повтором перевірте початкову ідентичність/результат. Вставлені клієнти/транспорти зберігають власну timeout policy й не поєднуються з цим параметром. Межа одного запиту не замінює строки worker long-poll, передавання payload чи workflow/виклику. Перевіряйте composer.lock: мінімум функції не змінює вибрану комбінацію встановлення. Див. налаштування HTTP-клієнта і перевірку звичайного встановлення 3.4.0.

Перевірений приклад короткого опитування​

Ізольована перевірка використовувала опубліковані Python SDK 2.9.0, PHP Server 2.11.0 і Nginx 1.30.5 з порожньою чергою. В обох випадках опитування SDK тривало 3 секунди, таймаути connect/read/write/pool HTTPX становили 8 секунд, а зовнішня межа виклику — 10 секунд. Змінювався лише таймаут читання upstream у Nginx:

Налаштування посередникаСпостережена відповідь
proxy_read_timeout 1sПриблизно за секунду Nginx повернув HTTP 504, очікуючи заголовок upstream. SDK передав ServerError.
proxy_read_timeout 8sПриблизно за три секунди нормальне тихе опитування повернуло HTTP 200, task: null і poll_status: empty.

Типове очікування сервера навмисно становило одну секунду в обох випадках. Явні три секунди в запиті все одно діяли. HTTP-повтори обмежувалися однією спробою, щоб показати першу помилку. Це функціональний приклад, а не вимірювання місткості чи рекомендація для production. Перевірка в #267 містить точні образи, запити та журнали.

Для Nginx задайте належний бюджет читання upstream у наявному location опитувань worker. Вісім секунд нижче стосуються саме прикладу з трисекундним опитуванням:

proxy_connect_timeout 2s;
proxy_read_timeout 8s;

Nginx вимірює proxy_read_timeout між читаннями upstream. HTTPX розрізняє таймаути connect, read, write і pool. Вісім секунд на фазу не є загальним восьмисекундним кінцевим строком. За потреби задавайте явну зовнішню межу. Інші проксі й провайдери мають інші назви та семантику. Перевіряйте весь шлях фактичним SDK: збільшення одного таймауту ingress не виправляє коротшу межу в іншому місці.

З’ясуйте причину відповіді перед перезапуском worker​

  • Нормальне порожнє опитування: успішна відповідь без завдання. У перевіреній версії необроблена відповідь має poll_status: empty. Продовжуйте опитування.
  • Розрив посередником: транспортний виняток, скидання з’єднання або 502/504 проксі можуть передувати кінцю очікування сервера. Зіставляйте помилку та тривалість із журналами проксі/upstream. Справний readiness і подальша успішна робота не виключають помилковий таймаут.
  • Недоступний runtime: перевіряйте структуровану причину та readiness бази даних, кешу й admission. HTML-помилка шлюзу не є типізованою відмовою runtime.
  • Відмова admission для namespace чи опитування: перевірте причину, namespace/чергу та затримку повтору, зокрема для HTTP 429. Збільшення idle timeout не додає місткості та не виправляє авторизацію.

Повторне з’єднання worker не доводить правильність попереднього налаштування проксі. Перевіряйте, чи реально тривають опитування та завершення завдань. За сталих помилок зберігайте клас, чергу, час і частоту. Поодинокий розрив не вимагає перезапуску процесу. Клієнт Python також може створити poll_status: timeout після повторів HTTP-таймауту. Саме це значення не доводить, що порожня відповідь runtime пройшла через проксі. Не змішуйте транспортні повтори з повторами activity, кінцевими строками запуску та повноваженнями query.

Бюджети SQL-з’єднань​

Сплануйте сесії бази даних, перш ніж додавати репліки API або одночасно запускати старі й нові процеси під час поступового оновлення. База може вичерпати ліміт з’єднань, коли CPU ще доступний. Це окрема межа від затримки запису/commit, місткості HTTP та зростання обсягу збережених даних.

Врахуйте кожен процес із доступом до SQL​

Опубліковане PHP-розгортання Compose має такі можливі SQL-клієнти:

РольЩо враховувати
APIКожен процес PHP, який одночасно обслуговує запит і може використовувати SQL, включно з перевірками готовності, операторськими запитами та poll у режимі очікування. Опублікована конфігурація Apache prefork дозволяє 24 процеси запитів на контейнер API. Це верхня межа HTTP-процесів, а не SQL-пул чи вимірювання 24 відкритих сесій.
Worker черги LaravelКожен процес php artisan queue:work. Опублікований рецепт Compose запускає один; додаткові контейнери worker додають процеси. Вони відрізняються від зовнішніх SDK worker.
Планувальник/обслуговуванняОдночасні команди PHP, а не лише контейнер планувальника. Планувальник Compose послідовно виконує оцінювання розкладів, відновлення, контроль тайм-аутів activity та очищення. У звичайному циклі одночасно активна одна команда. Зберігайте правило єдиного планувальника.
Ініціалізація та операційні інструментиКоманди міграції/ініціалізації, перебудова проєкцій, завдання зберігання, резервування, моніторинг та інтерактивні SQL-клієнти, які можуть працювати під час розгортання. Навмисно паралельні команди враховуйте окремо.
SDK-клієнти та workerЗазвичай жодних прямих сесій до бази Server: PHP, Python і Rust SDK у сервісному режимі використовують HTTP. Додавайте з’єднання лише тоді, коли код activity чи іншої частини застосунку справді звертається до цієї бази.

Рахуйте окремі SQL-з’єднання, які використовує кожен процес, а не лише контейнери чи імена хостів. Типове з’єднання Laravel і workflows.storage.connection можуть мати спільне налаштоване ім’я. Інше ім’я сховища, SQL-з’єднання черги/кешу/сесій або окремий дескриптор читання/запису/прямого доступу може відкрити додаткову сесію навіть до тієї самої кінцевої точки. Redis-з’єднання не є SQL-сесіями. Перевіряйте фактичну кешовану конфігурацію та імена з’єднань, які справді використовує кожна роль.

У власному FPM-розгортанні рахуйте виконавчі процеси PHP-FPM, а не потоки nginx чи Apache event. В Octane врахуйте worker запитів, worker завдань і фактичні клієнти бази. Не використовуйте число 24 з Apache як розмір пулу цих фронтендів. Синхронний long poll займає виконавчий процес PHP під час очікування й може утримувати SQL-сесію. Не вважайте автоматично, що HTTP-poll без роботи не використовує SQL.

Консервативний приклад поступового оновлення​

Це приклад планування, не виміряна місткість. Припустімо, база дозволяє 120 клієнтських сесій: десять для інших застосунків, п’ятнадцять зарезервовано для відновлення й адміністрування. Для цього розгортання залишається 95. Черга й кеш використовують Redis; кожен PHP-процес має не більше одного SQL-з’єднання.

Перераховуйте бюджет при зміні з’єднань сховища, кількості worker або перекриття версій. Зменшуйте межі процесів/реплік або замінюйте їх поетапно, не припускаючи, що база витримає накладання. Підвищення max_connections також потребує оцінки пам’яті бази та навантаження.

Спостерігайте й дотримуйтеся бюджету​

  1. Запишіть фактичний ліміт з’єднань, сторонні клієнти та доступ, зарезервований для відновлення. Визначте максимум реплік/процесів API та додаткових реплік під час оновлення. Врахуйте одночасні покоління worker черги й інструменти.
  2. В ізольованій копії з вашим точним опублікованим образом і конфігурацією спостерігайте сесії у спокої, під час очікування poll, виконання справжньої роботи та обмеженого перекриття старої й нової версій. Рахуйте неактивні сесії й сам монітор. PostgreSQL надає pg_stat_activity, MySQL — information_schema.PROCESSLIST. Використовуйте роль моніторингу з відповідно обмеженими правами, не експортуйте SQL-тексти чи корисні дані.
  3. Порівняйте сесії за користувачем застосунку/базою з бюджетом на процес. Коротка вибірка перевіряє припущення конкретного стенда, а не межу насичення чи гарантію для кожного навантаження.
  4. Стежте за запасом сесій разом із відмовами з’єднання, затримкою транзакцій/commit, очікуванням блокувань, утримуваними HTTP-запитами й зростанням сховища. Готовність сама по собі не доводить запас для оновлення.
  5. Поблизу ліміту зменшіть перекриття або спорожніть і зупиніть стару групу API/worker до запуску заміни. Зберігайте доступ для відновлення й запускайте ініціалізацію лише в заплановане вікно міграції. Якщо безпечне перекриття не вміщується в бюджет, використовуйте задокументоване оновлення з повною зупинкою.

Допуск до черги завдань обмежує окремі операції відправлення та lease. DW_WORKER_LONG_POLL_MAX_CONCURRENT і DW_QUERY_TASK_POLL_MAX_CONCURRENT обмежують очікування poll на вузлі. Жоден із них не встановлює глобальної межі SQL-сесій, байтів бази чи затримки commit. Залишайте місце також для завершень, heartbeat, операторських запитів і перевірок стану.

Базовий варіант — пряме підключення до доступної для запису бази. Проксі потребує перевірки з точною версією Server, режимом пулу й налаштуваннями підготовлених запитів, меж транзакцій, стану сесії та блокувань. Пул транзакцій PgBouncer потребує виправленого Server версії 2.9.8 або новішої. Приймальна перевірка опублікованої версії 2.9.8 підтверджує PostgreSQL 16.15 з PgBouncer 1.26.1: пряме підключення PostgreSQL, пул сесій і пул транзакцій з max_prepared_statements=0 або max_prepared_statements=200. Це мінімальна сумісна версія й точно перевірена конфігурація, а не фіксація найновішої версії чи гарантія місткості; інші комбінації перевіряйте окремо. Перед прийняттям трафіку виконайте звичайну ініціалізацію server-bootstrap через вибрану кінцеву точку.

GET /api/ready виконує читання бази з прив’язаними параметрами (bound_read_query) та налаштовані перевірки готовності; можливість обслуговувати записи явно залишається неперевіреною. Успішне TCP-з’єднання, міграція чи відповідь готовності не доводить виконання всіх SQL-операцій workflow або достатньої пропускної здатності commit. Репліки читання не можуть замінити авторитетний вузол запису для claims і стійких переходів.

Чарт Helm для Kubernetes​

Репозиторій Server містить код чарта й інструкції випуску. Установіть опублікований чарт із реєстру OCI:

helm install durable-workflow \
  oci://ghcr.io/durable-workflow/charts/durable-workflow \
  --version 0.2.3 \
  --namespace durable-workflow --create-namespace \
  -f my-values.yaml

Файл values має вказувати на зовнішні MySQL/PostgreSQL і Redis, отримувати production-облікові дані з наявних Kubernetes Secrets та налаштовувати ingress/TLS для вашого середовища. Чарт не створює сховище чи керовану провайдером інфраструктуру. Для відтворюваного розгортання закріпіть образ Server за digest.

Вибір випуску чарту​

Кожен випуск чарту записує образ Server, з яким його перевіряли, у appVersion файлу Chart.yaml; номери версій чарту й Server незалежні. Вибрана сумісна комбінація поєднує чарт 0.2.3 із Server 2.10.1, використовуючи ті самі метадані випусків, що й таблиця та команда встановлення. Підтвердження опублікованих OCI/package перевіряє цю пару, а не нове встановлення Kubernetes.

Для іншої версії Server перевірте Chart.yaml потрібного опублікованого чарту (джерело вибраного чарту є прикладом) й виберіть точну версію, чий appVersion відповідає потрібному Server. Прочитайте нотатки UPGRADING вибраного випуску для кожної версії чарту, через яку переходите. Не виводьте версію чарту з версії Server і не вибирайте неопублікований чарт із поточного джерела.

Перевизначення image.tag змінює образ, але не записаний appVersion чарту. Це власна комбінація чарту й образу, доки вона не пройде перевірку згенерованих маніфестів, bootstrap, rollout і runtime. Включайте звичайні резервні копії бази та межі відкату до плану оновлення; саме успішне генерування маніфестів не доводить працездатність розгортання.

В опублікованій історії є виняток: чарт 0.2.2 перейшов на нову мінорну версію Server під patch-номером чарту. Пізніше опубліковане виправлення пояснення визнає цей виняток і повертає заявлену політику мінорних версій. Історичні версії незмінні; ця примітка не вибирає новішу комбінацію Server/чарту.

Маніфести Kubernetes​

Репозиторій Server містить маніфести без обгортки в k8s/ для команд, які вже обслуговують Kubernetes:

  • Namespace і спільні мітки
  • Поділ ConfigMap і Secret
  • Job початкового налаштування й міграцій
  • Deployment і Service API
  • Deployment worker
  • CronJob планувальника
  • PodDisruptionBudget
  • Перевірки працездатності /api/health і готовності /api/ready
  • Обережні запити й обмеження ресурсів

Перед застосуванням маніфестів замініть тег образу на конкретну опубліковану версію чи дайджест, надайте справжні облікові дані бази й Redis та підключіть значення ConfigMap до служб вашого кластера. Маніфести навмисно відкриті для перевірки: вони не є чартом Helm і не обіцяють універсальної поведінки керованого Kubernetes.

Для виробничого розгортання Kubernetes перевірте щонайменше:

kubectl -n durable-workflow wait --for=condition=complete job/durable-workflow-migrate --timeout=180s
kubectl -n durable-workflow rollout status deploy/durable-workflow-server
kubectl -n durable-workflow rollout status deploy/durable-workflow-worker
kubectl -n durable-workflow port-forward svc/durable-workflow-server 8080:8080
curl http://localhost:8080/api/ready
curl -H "Authorization: Bearer $DW_ADMIN_TOKEN" http://localhost:8080/api/cluster/info

Висока доступність в одному регіоні — перемикання керованої бази й Redis, втрата вузла API чи worker та перезапуск планувальника — на шляху маніфестів потребує підтримки так само, як і в невеликому кластері, доки перевірка випуску не пройдена. Передбачений контракт вимагає правил готовності, єдиного планувальника та спільної основи з контракту одного регіону. Балансувальники провайдера, класи сховищ, мережеві політики, кілька активних регіонів та автономне регіональне перемикання власного середовища потребують підтримки або відстежуються окремо від контракту маніфестів. Для встановлення й оновлень під керуванням Helm використовуйте окремо версійований шлях вище.

Запуск SDK workers у Kubernetes​

Розгортайте workers вашого застосунку окремо від Laravel queue worker сервера. Зберіть образ із зареєстрованими обробниками PHP, Python або Rust і зафіксованими залежностями SDK. Використовуйте entrypoint у формі exec, щоб процес worker отримував SIGTERM. Замініть наведений образ незмінним digest цієї збірки.

Для workers у тому самому кластері використовуйте фактичні назву, namespace і порт Service сервера. Сирі маніфести надають http://durable-workflow-server.durable-workflow.svc.cluster.local:8080. Випуск Helm може мати іншу назву Service. Workers поза кластером потребують доступної HTTPS-адреси ingress або балансувальника з нормальною перевіркою сертифіката. Узгодьте бюджети long poll і транспорту з рекомендаціями щодо таймаутів.

Створіть Secret у Kubernetes namespace Pod worker, використовуючи наявні облікові дані worker. Не додавайте токен до маніфесту чи образу. Namespace сервера — окрема межа продукту, відмінна від namespace Kubernetes.

kubectl -n durable-workflow create secret generic orders-worker-auth --from-literal=token="$DW_WORKER_TOKEN"

Збережіть це як orders-worker.yaml. Ці назви змінних середовища є конфігурацією застосунку: entrypoint має передати їх клієнту SDK і Worker. Надайте кожному одночасно активному процесу власний worker ID і зареєструйте обробники для налаштованої черги.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-worker
  namespace: durable-workflow
spec:
  replicas: 2
  selector:
    matchLabels:
      app: orders-worker
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: orders-worker
    spec:
      automountServiceAccountToken: false
      terminationGracePeriodSeconds: 75
      containers:
        - name: worker
          image: registry.example.com/acme/orders-worker:release-id
          env:
            - name: DW_SERVER_URL
              value: http://durable-workflow-server.durable-workflow.svc.cluster.local:8080
            - name: DW_NAMESPACE
              value: default
            - name: DW_TASK_QUEUE
              value: orders
            - name: DW_WORKER_ID
              valueFrom:
                fieldRef:
                  fieldPath: metadata.uid
            - name: DW_WORKER_TOKEN
              valueFrom:
                secretKeyRef:
                  name: orders-worker-auth
                  key: token
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: "1"
              memory: 512Mi

Застосуйте Deployment і перевірте його розгортання:

kubectl apply -f orders-worker.yaml
kubectl -n durable-workflow rollout status deployment/orders-worker

Кількість реплік і ресурси — початкові приклади, а не гарантії місткості. Налаштуйте їх за фактичною тривалістю завдань, використанням пам’яті, лімітами залежних сервісів і бюджетами допуску worker. Доступність Deployment не доводить реєстрацію SDK чи корисну роботу. Перевірте свіжі реєстрації workers та очікувані збірку й чергу, потім запустіть і завершіть показовий workflow. Запуск у Kubernetes сам собою не створює HTTP endpoint здоров’я для SDK worker. Використовуйте probe застосунку, якщо він існує, і не використовуйте здоров’я сервера як liveness-перевірку worker.

Передавання SIGTERM і очікування очищення​

SDKЗавершення процесу worker
PHPВикористовуйте керований цикл Worker::run() зі встановленим pcntl. Його signal handler запитує завершення, після чого активне синхронне завдання доходить до межі перед керованим очищенням і зняттям реєстрації. Власний цикл навколо tick() не надає цього lifecycle. Див. коректне завершення PHP.
PythonПід’єднайте SIGTERM до шляху завершення того самого Worker та дочекайтеся і Worker.stop(), і його run task. Явно задайте shutdown_timeout. Прийняті завдання поділяють цей deadline спорожнення. Скасування await не може примусово зупинити активний синхронний потік, а непідтверджена зупинка залишається помилкою. Використовуйте приклад окремих процесів і signal wiring та контракт lifecycle.
RustПередайте до Worker::run_until(...) future, який завершується за Unix SIGTERM, і дочекайтеся результату. Future лише для Ctrl-C не обробляє signal завершення Pod. Асинхронні обробники мають віддавати керування, а блокувальну роботу потрібно обмежувати окремо. Див. Worker::run_until.

Виділіть у terminationGracePeriodSeconds достатньо часу для poll, завершення прийнятих завдань і очищення HTTP/session/реєстрації у встановленому SDK. Приклад із 75 секундами потрібно звірити з фактичними межами вашого застосунку. Kubernetes зараховує будь-який hook preStop у той самий пільговий період і примусово зупиняє процеси, що залишилися після його спливу. Hook лише зі sleep не просить SDK спорожнити роботу й не подовжує його deadline. Див. процес завершення Pod у Kubernetes.

Відрепетируйте завершення під час простою й обмеженої за часом роботи. Вважайте помилки очищення, збережену реєстрацію або примусове завершення неповним вимкненням. Worker на заміну продовжує durable-роботу за її записаними leases, retries і deadlines. Зупинка Pod не скасовує workflow і не відкочує зовнішній побічний ефект. Перед зміною збірок дотримуйтеся розгортання за build ID worker і зберігайте його перевірки сумісності, replay та rollback.

Висока доступність і перемикання в одному регіоні​

Висока доступність і перемикання в одному регіоні наразі є неперевіреним кандидатом контракту за участю підтримки поверх невеликого кластера та маніфестів Kubernetes. Він охоплює режими відмов, які рушій розрахований витримати всередині одного регіону: перемикання керованої бази (RDS Multi-AZ, перемикання кластера Aurora, Cloud SQL HA, підвищення Patroni тощо), керованого Redis (Sentinel, перемикання групи реплікації Elasticache, Memorystore HA тощо), втрату вузла API чи worker та перезапуск процесу планувальника й обслуговування. Міжрегіональне відновлення з активним і резервним регіонами є окремим оцінюванням за участю підтримки; дивіться наступний розділ.

Передбачений контракт — поведінка рушія, правила готовності, цілі відновлення за подіями, запобігання роздвоєнню керування та приймальна репетиція — зберігається в бібліотеці workflow у docs/deployment/ha-failover.md та в окремому Server у docs/ha-failover-validation.md. Цей розділ є публічним викладом цих документів.

Стан підтвердження випуску​

Для документованого публічного випуску Server немає посилання на успішний результат точного випуску. Записана спроба опублікованого образу зупинилася під час topology_start, очікуючи готовності API, перш ніж можна було підтвердити матрицю відмов або межі відновлення. Наявність програми перевірки, її маніфесту сценаріїв або репетиція конкретного розгортання не доводять проходження повної матриці опублікованим образом. Тому висока доступність в одному регіоні залишається шляхом за участю підтримки.

Самостійні формулювання дозволені лише після запуску без вихідного коду, який використовує точний документований випуск Server для образу, програми перевірки й топології Compose та публікує single-region-failover-result.json з outcome: "pass", runner_blocked: false, status: "pass" кожного запису phase_outcomes, успішними вердиктами всіх меж відновлення та підтвердженням кожного обов’язкового сценарію з публічного маніфесту перемикання в одному регіоні. Посилання на цей публічний успішний результат має бути в цьому розділі й називати той самий образ Server, що й durableworkflow/server:2.10.1. До виконання всіх умов наведені нижче межі відновлення є цілями оцінювання, а не твердженнями про перевірений опублікований образ.

Кандидат топології​

Передбачений контракт високої доступності діє, коли розгортання відповідає невеликому кластеру чи маніфестам без обгортки та оператор зберігає три правила:

  • Завжди одна кінцева точка запису бази workflow. Кероване перемикання (RDS Multi-AZ, перемикання кластера Aurora, Cloud SQL HA, Patroni тощо) дозволене, якщо попередній основний вузол ізольовано до повторного підключення: відкликано користувача запису, увімкнено read_only=on, розірвано реплікацію або відновлено відомий справний знімок. Проксі має зберігати потрібну Server семантику бази та пройти перевірку точної версії, режиму й налаштувань. Вимоги до версій і перевірені режими пулу транзакцій PgBouncer наведено в бюджетах SQL-з’єднань.
  • Одна кінцева точка Redis одночасно із задокументованим підвищенням резервного вузла. Кероване перемикання Redis (Sentinel, перемикання групи реплікації Elasticache, Memorystore HA тощо) дозволене. Redis — шар прискорення, а не основа коректності, тому його перемикання є подією затримки, а не зміною коректності.
  • Завжди один процес планувальника й обслуговування. Оркестратор (служба Compose з deploy.replicas: 1, модуль systemd з орендою на рівні хоста або Kubernetes Deployment з replicas: 1 та RollingUpdate.maxSurge: 0) відповідає за збереження єдиного екземпляра під час перезапуску. Дублікати планувальника як стала топологія не входять до цього контракту.

Правила балансувальника, готовності й переведення трафіку​

Балансувальник перед вузлами API є єдиною точкою рішення про приймання трафіку під час перемикання:

  • Підключіть балансувальник до GET /api/ready, а не лише /api/health. /api/health лише доводить, що процес обслуговує HTTP; /api/ready повідомляє про з’єднання з базою й налаштовані перевірки готовності, зокрема чи прискорення пробудження Redis справне або погіршене. Він не перевіряє всі SQL-операції workflow чи доступну потужність запису. Під час відмови бази /api/ready правильно не проходить на всіх вузлах. Балансувальник МАЄ приймати стан повної недоступності, а не повертатися до застарілого «останнього справного» списку.
  • Задайте інтервал перевірки 5–10 секунд і поріг видалення у 2–3 послідовні невдалі перевірки.
  • Не вимагайте закріплених сеансів: базова перевірка невеликого кластера доводить, що зовнішній worker може опитати server-a і завершити на server-b.
  • За перемикання лише Redis готовність залишається успішною на кожному вузлі, поки доступні стійкі шляхи на основі бази. Погіршення шару прискорення відображається як checks.cache.status=warning із checks.cache.degraded_capability=long_poll_wake_acceleration; не налаштовуйте балансувальник на видалення вузлів через це попередження.

Після відновлення основи рекомендовано дочекатися HTTP 200 від /api/ready хоча б одного вузла, запитати /api/cluster/info через балансувальник з адміністративним токеном для перевірки маніфесту топології, виконати POST /api/worker/register для перевірочного worker через збалансовану кінцеву точку, переконатися в наявності рівно одного процесу планувальника в оркестраторі та відновити зовнішній трафік.

Репетиція точного артефакту​

Випуск Server містить багаторазову базову репетицію повної матриці відмов без збирання продукту з робочої копії. Програма перевірки й топологія Compose мають походити з того самого тегу випуску, що й образ Server; не поєднуйте мінливу стандартну гілку з довільним образом. На чистому хості з Docker Engine, Docker Compose v2, Python 3.11 або новішим і доступом до публічних реєстрів виконайте:

export DW_SERVER_RELEASE=2.10.1
git clone --depth 1 --single-branch --branch "$DW_SERVER_RELEASE" \
  https://github.com/durable-workflow/server.git "server-$DW_SERVER_RELEASE"
cd "server-$DW_SERVER_RELEASE"
export DW_SERVER_IMAGE="durableworkflow/server:$DW_SERVER_RELEASE"
scripts/conformance/single-region-failover-published-artifacts.sh \
  --result-dir ./failover-result

Цей шлях навмисно визначає робочу копію та DW_SERVER_IMAGE за однією змінною випуску. Не перевизначайте образ незалежно; оберіть інший випуск, змінивши DW_SERVER_RELEASE до клонування. Програма вимагає конкретного публічного тегу чи дайджесту Server, завантажує всі допоміжні образи, визначає дайджести репозиторіїв усіх образів виконання й відхиляє секції збирання Compose, монтування вихідного коду продукту та локальні або рухомі посилання на Server. Вона запускає рівно два вузли API за однією кінцевою точкою nginx, одну базу MySQL, один Redis і один процес планувальника й обслуговування.

Отриманий single-region-failover-result.json використовує схему durable-workflow.v2.single-region-failover.result. Він записує точні версії артефактів та інструментів, нормалізовану топологію, переходи готовності, виміряні часи відновлення й вердикти меж, ідентичності workflow, запусків, завдань і розкладів, а також перевірки дублікатів і втрат для завершення між вузлами, втрати API, переривань бази й Redis, втрати оренди worker та перезапуску єдиного планувальника. Зовнішні програми знаходять виклик і публічний маніфест сценаріїв через single_region_failover_contract у відповіді GET /api/cluster/info.

Результат підтверджує видимі рушію переривання й відновлення опублікованого образу лише після проходження вимог випуску вище. Невдалий, частковий або заблокований програмою результат є діагностикою, а не перевіркою. Навіть успішна базова перевірка не перетворює перезапуск локального контейнера MySQL чи Redis на підтвердження механізму підвищення резервного вузла хмарного провайдера. Зберігайте підтвердження підвищення засобами провайдера, ізоляції старого вузла, RPO та фактичного часу поруч із базовим результатом, перш ніж заявляти про високу доступність керованого сервісу.

Доповнення комплекту відновлення​

Невеликий кластер чи розгортання маніфестів, яке заявляє цей контракт, МАЄ доповнити комплект відновлення за операторськими межами експлуатації підтвердженнями репетицій кожного класу подій:

  • перемикання керованої бази без втрати підтверджених записів та в межах зазначеного вище часу відновлення;
  • перемикання керованого Redis без коливань списку вузлів балансувальника, без втрати підтвердженої роботи та з checks.cache.status=warning і long_poll_wake_acceleration як погіршеною можливістю;
  • втрата вузла API, яку балансувальник поглинає в налаштованому інтервалі перевірки готовності без втрати підтверджених записів;
  • втрата worker зі збереженням стійкого запуску до завершення оренди, повторним отриманням у налаштованій межі відновлення та рівно одним завершенням;
  • перезапуск планувальника на іншому хості без дублікатів розкладів і без розкладу, який залишився неоціненим після next_fire_at плюс один такт.

Доки перевірка випуску не пройдена, кожне розгортання потребує участі підтримки, навіть якщо його власна репетиція успішна. Після публічного успішного результату всіх фаз розгортання стає самостійним за цим контрактом лише після запису репетиції конкретного середовища в комплект відновлення оператора та її оновлення з періодичністю, яку визначають операторські межі експлуатації.

Межа непідтримуваних тверджень про високу доступність​

Контракт високої доступності в одному регіоні навмисно вузький. Наведене нижче залишається поза ним і потребує проєктування за участю підтримки, оскільки сама топологія є частиною ризику продукту:

  • топології бази з кількома активними вузлами запису;
  • кілька регіонів з активним і резервним регіонами та автоматичне чи автономне регіональне перемикання власних топологій (наступний розділ містить оцінювальні настанови);
  • синхронна міжрегіональна реплікація бази (RPO=0);
  • дублікати процесів планувальника й обслуговування як стала топологія;
  • прив’язані до регіону черги завдань як вісь маршрутизації, яку забезпечує рушій;
  • перевірка керованого Kubernetes провайдера поза контрактом пакування чарта;
  • широкі SLA «п’ять дев’яток» чи «без простою» поза наведеними межами відновлення.

Контракт визначає обмежене відновлення під час названих подій, а не обіцянку доступності, що залежить від вибору оператором бази, мережі й оркестратора. Маркетингові чи SLA-твердження для власних розгортань НЕ МОЖУТЬ переходити цю межу без окремої перевірки.

Активний і резервний регіони​

Кілька регіонів з активним і резервним регіонами — оцінювальний посібник за участю підтримки, а не доведений самостійний контракт підтримуваних меж експлуатації 2.0. Використовуйте цей розділ для перевірки кандидата архітектури й репетиції конкретного середовища з підтримкою до виробничого використання. Кожен регіон починається з документованого одновузлового, невеликого кластерного шляху чи маніфестів Kubernetes, але ці однорегіональні контракти не встановлюють міжрегіональної реплікації, перемикання, повернення, RPO, RTO чи поведінки за роздвоєння керування. Глибші матеріали — повноваження даних, припущення реплікації, поведінка просторів імен, черг і worker, інструкції перемикання й повернення, ізоляція старого вузла та компроміси узгодженості й затримки — зберігаються в бібліотеці workflow у docs/deployment/multi-region.md та в окремому Server у docs/multi-region-validation.md.

Кандидат архітектури для оцінювання:

  • Один активний регіон із перевіреним одновузловим чи невеликим кластерним контрактом: контейнери API за балансувальником, спільна зовнішня MySQL або PostgreSQL як стійка база для запису, спільний Redis, рівно один процес планувальника й обслуговування та зовнішні worker.
  • Один резервний регіон з асинхронно реплікованою резервною базою workflow, необов’язковим резервним Redis, без процесу планувальника й обслуговування та з нулем або більшою кількістю підготовлених контейнерів API/worker, які простоюють до підвищення.
  • Регіональне перемикання — явна робота оператора: зупинити трафік запису до несправного регіону, звірити реплікацію з опублікованим RPO, підвищити резервну базу, виконати потрібні випуску міграції нового основного вузла, запустити єдиний процес планувальника й обслуговування в новому активному регіоні, змінити кінцеві точки worker, перевести зовнішній трафік та відновити похідні проєкції. Автоматичного міжрегіонального переходу немає.
  • Повернення виконує ту саму послідовність у зворотному порядку після відновлення початкового регіону. Відновлений основний вузол потрібно ізолювати до підключення як резервного: відкликати користувача запису, увімкнути read_only=on, розірвати реплікацію або відновити відомий справний знімок.

Повноваження даних і припущення реплікації:

  • База workflow — єдине стійке джерело істини, прив’язане до регіону: у будь-який момент записує рівно один регіон. База резервного регіону є реплікою лише для читання до підвищення. Цільова точка відновлення (RPO) дорівнює затримці асинхронної реплікації, а цільовий час відновлення (RTO) — часу виконання операційного посібника оператором.
  • Redis — локальне прискорення регіону. Сигнали пробудження, блокування черг query та приймання не передаються між регіонами; не очікуйте цього. Кожен регіон запускає власний Redis; кеш резервного може бути холодним або прогрітим за рішенням оператора, і коректність не залежить від його збереження під час перемикання.
  • Видимість обслуговує база активного регіону. Спочатку підвищення, потім читання.

Поведінка просторів імен, черг завдань та реєстрації worker:

  • Простори імен і черги завдань зберігаються в базі workflow та переживають підвищення точно в стані останньої реплікованої транзакції. Рушій не поділяє їх за регіонами.
  • Worker нового активного регіону реєструються на локальній кінцевій точці API після підвищення. Попередні реєстрації несправного регіону залишаються в базі та втрачають чинність через звичайний механізм завершення реєстрації worker.
  • Розгортання за ідентифікатором збірки та стан життєвого циклу розгортання переживають перемикання, оскільки зберігаються в базі workflow.

Компроміси узгодженості й затримки у сталому стані:

  • Запуски workflow, signal та update фіксуються в базі активного регіону. Їхня затримка дорівнює затримці фіксації цього регіону. Вони відхиляються, поки повноваження відкликаються під час перемикання.
  • Доставка завдань workflow та activity дотримується контракту прискорення активного регіону: менше секунди за справного Redis, інакше — стійкий інтервал опитування.
  • Розклади запускає єдиний планувальник активного регіону. Вони призупиняються, поки він не працює, і відновлюються зі стійких записів розкладів після підвищення.
  • Читання після запису узгоджене лише всередині активного регіону; рушій не надає міжрегіонального читання власних записів або RPO=0.

Межа аварійного відновлення явна: кандидат архітектури не замінює резервні копії чи підтвердження. Комплект відновлення за операторськими межами експлуатації залишається обов’язковим. Доповніть його SLO відставання реплікації, часом виконання інструкцій підвищення, датою останньої успішної репетиції перемикання та процедурою ізоляції відновленого основного вузла.

Для власних розгортань активний і резервний або кілька активних регіонів, автоматичне регіональне перемикання, синхронна міжрегіональна реплікація (RPO=0), активна міжрегіональна видимість і прив’язані до регіону черги як вісь маршрутизації рушія залишаються шляхами за участю підтримки, оскільки топологія є частиною ризику продукту. Поточний контракт керованого середовища Cloud однорегіональний і не надає цих міжрегіональних гарантій.

Контракт готовності​

Використовуйте перевірки і працездатності, і готовності:

  • GET /api/health доводить, що процес обслуговує HTTP.
  • GET /api/ready повідомляє результати налаштованих перевірок залежностей, зокрема з’єднання з базою, міграцій і готовності типового простору імен. Він не доводить працездатності всіх SQL-операцій workflow чи запасу для запису.
  • GET /api/cluster/info доводить, що автентифікований клієнт може виявити ідентичність збірки, протокол площини керування, протокол worker, кодеки payload та можливості Server.
  • POST /api/worker/register доводить, що worker можуть автентифікуватися в очікуваних просторі імен і черзі завдань.

Не переводьте трафік лише на основі /api/health.

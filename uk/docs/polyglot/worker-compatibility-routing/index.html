Сумісність і маршрутизація воркерів

Сумісність — це контракт маршрутизації. Зберігайте воркерів, здатних відтворювати наявні історії, змінюючи збірку для нових запусків. Дренування не переносить їхні виконання на іншу збірку.

Дві пов'язані ідентичності​

  • Ідентифікатор збірки — зареєстрована build_id когорти окремого Server у певних просторі імен і черзі. Просування, дренування та відновлення застосовуються до цієї когорти.
  • Маркер сумісності записується в надійній роботі. Вбудований PHP використовує DW_V2_CURRENT_COMPATIBILITY і DW_V2_SUPPORTED_COMPATIBILITIES; збірки окремих воркерів надають відповідну ідентичність маршрутизації.

Вважайте ці значення непрозорими рядками. Новіша на вигляд назва не доводить replay-сумісності й не дозволяє змінити наявне закріплення.

Що закріплюється​

Окремий Server обирає закріплення нових запусків за явним просуванням, потім резервними правилами єдиної активної когорти. За неоднозначності запуск може залишитися без закріплення. Дивіться порядок вибору.

Задачі workflow й активності успадковують сумісність виконання. Повтори задач, спливання оренди й повторне доставлення її зберігають. Повторні виконання, діти та continue-as-new також успадковують початкове закріплення. Просування впливає на наступні нові екземпляри, а не переносить продовжений ланцюг.

Як працює маршрутизація​

Звуження під час poll​

Воркери запитують простір імен, чергу й сумісну когорту. Вибір під час poll уникає несумісних пропозицій, але не є остаточною межею повноважень.

Перевірка під час захоплення​

Захоплення перевіряє початкову сумісність задачі та ідентичність воркера. Несумісний воркер не отримує оренду через відсутність іншої збірки. Спливання оренди теж не розширює сумісності.

Еволюція fingerprint визначення​

Підтримка в опублікованих випусках. Server 2.9.9 та SDK PHP 2.5.4, Python 2.6.2 і Rust 3.5.6 запровадили захист входу й описану нижче поведінку маршрутизації та відновлення. Це мінімальні версії для цих можливостей. Установлюйте поточні стабільні випуски, щоб отримувати виправлення безпеки.

Початкова прив’язка build і fingerprint визначення відповідають на різні запитання. Сумісна з replay повторна збірка може зберегти сімейство build, змінивши fingerprint вихідного коду. За замовчуванням Server віддає перевагу придатному worker із fingerprint, записаним у WorkflowStarted. Якщо таких більше немає, змінене визначення може отримати початковий task лише тоді, коли його worker оголошує workflow_entry_arguments_validation. Ця можливість обіцяє відмову до входу без завершення бізнесового run помилкою. Вона не виводиться з мови runtime або версії протоколу, а ручне додавання рядка не робить небезпечну реалізацію worker безпечною.

Резервний маршрут усе ще вимагає початкових namespace, task queue, типу workflow, build і можливостей replay. Run зберігає записаний fingerprint та знімки допуску. SDK має перевірити початковий вхід і відтворити зафіксовані команди; зміна вихідного коду, маркер версії чи успішна реєстрація не доводять, що replay буде успішним. Перезапускайте змінений код із новим worker id, бо активна реєстрація не може змінити оголошений fingerprint.

Деталі run, debug вибраного run, відповіді repair та деталі task queue містять definition_routing:

СтатусЗначення та дія
matching_definition_available / matching_definition_preferredЄ придатна потужність із записаним визначенням або їй віддається перевага перед зміненим worker.
replay_requiredПридатне змінене визначення може отримати task. Перевірка входу й суворий replay усе ще мають пройти. Це не висновок про блокування.
entry_validation_unavailableЗаміна не має можливості перевірки входу. Оновіть SDK або відновіть записане визначення.
no_eligible_worker / worker_definition_missing / recorded_definition_missingДослідіть відсутню потужність або дані fingerprint, зберігаючи початкові захисні перевірки маршрутизації.
pinning_disabledПеревагу збігу вихідного коду вимкнено; інші перевірки claim та replay залишаються.

blocked = true описує готовий task workflow, час якого настав і для якого немає придатного маршруту визначення. Деталі queue містять вибірку щонайбільше десяти run і вказують, чи є інші готові run; це не повна кількість усіх пасивних або заблокованих run. Repair не може створити відповідний worker або переписати історію. Після справжньої відмови входу виконайте процедуру відновлення того самого оригіналу.

DW_V2_PIN_TO_RECORDED_FINGERPRINT=false прибирає перевагу збігу вихідного коду. Це не скасовує прив’язки build, меж namespace/queue/type, ідентичності реєстрації, fencing оренди чи суворого replay. Параметр не замінює безпечний SDK та оновлення стандартним шляхом. Старіші runtime можуть непомітно зупиняти змінене визначення або повторювати некласифіковану відмову входу; використовуйте точну перевірену комбінацію runtime/SDK.

Що налаштовувати оператору​

Для вбудованого PHP задайте поточну й явно підтримувані родини:

DW_V2_CURRENT_COMPATIBILITY=orders-2026-04-28
DW_V2_SUPPORTED_COMPATIBILITIES=orders-2026-04-28,orders-2026-04-21

Перше значення закріплює нові вбудовані виконання; друге дозволяє брати задачі цих родин. Використовуйте * лише зі свідомо перевіреною політикою сумісності. Для окремих воркерів реєструйте сталу build_id і використовуйте просування та керування життєвим циклом Server. Зберігайте родину між replay-сумісними перезбірками; інша мітка не робить несумісний код безпечним для відтворення.

Безпечна схема розгортання​

  1. Розгорніть і перевірте простір імен, чергу, типи та свіжі реєстрації нової когорти. Збережіть стару доступною.
  2. Явно просуньте потрібну збірку для нових запусків. Кількість воркерів не задає відсотків трафіку.
  3. Зберігайте сумісну потужність для закріплених виконань, включно з пасивним очікуванням таймера, сигналу, активності чи дитини.
  4. Дренуйте лише задля свідомої зупинки нових захоплень когорти. Якщо раннє дренування зупинило роботу, відновіть когорту та початкову сумісну збірку.
  5. Для відкату нових запусків відновіть і просуньте відому справну когорту, потім відкотіть невдале розгортання. Наявні закріплення не змінюються.

Нуль незавершених задач не доводить безпечного виведення збірки. Зберігайте артефакт і відновлення, поки закріплене виконання чи успадкований ланцюг можуть їх потребувати. Server #519 відстежує окрему захищену функцію; цей список її не реалізує.

Явний стан відсутнього воркера​

Спільно перевіряйте задачі за когортами, свіжі/дреновані/застарілі реєстрації й початкове закріплення. no_compatible_worker означає незавершену workflow-роботу ненульової збірки без активного сумісного воркера. Це не підрахунок черг активностей або всіх пасивних закріплених виконань. Відсутнє поле, невдала відповідь чи старий heartbeat не означає порожній парк або нуль задач. Відновіть відповідну збірку або перевірте чергу, простір імен і типи перед додаванням сторонніх воркерів.

Зв'язок із розгортанням збірок​

Стан розгортання описує зареєстровану потужність і наміри нових запусків та життєвого циклу; сумісність визначає захоплення конкретної початкової задачі. Використовуйте обидва. Ні дренування, ні відкат не переписує надійну сумісність і не доводить можливості видалити збірку.

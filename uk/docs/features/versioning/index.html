Керування версіями

Replay перед зміною build​

Перед promotion кандидата виконайте replay репрезентативних відкритих і нещодавно закритих історій на його точному коді застосунку. Перед відкатом перевірте історії новішого build на старішому артефакті. Дотримуйтесь перевірки replay; сумісна когорта маршрутизації чи успішна перевірка цілісності самі по собі не доводять replay-сумісність.

Workflow можуть працювати довго, іноді місяцями або роками, тому часто потрібно змінювати визначення workflow, поки виконання ще тривають. Без керування версіями зміна коду workflow, яка впливає на шлях виконання, спричиняла б помилки недетермінізму під час replay.

Функція getVersion() дає змогу безпечно змінювати активні workflow, створюючи точки розгалуження з версіями.

Еволюція записаних вхідних аргументів​

Запуск зберігає аргументи, записані під час його старту. Розгортання нового визначення не переписує ці вхідні дані. Під час replay runtime зіставляє записані значення з поточним вхідним методом workflow до виконання будь-якого коду в тілі цього методу. Гілка getVersion() або patched() у тілі не може врятувати несумісну сигнатуру: спочатку потрібно увійти в метод.

Зберігайте порядок наявних позиційних аргументів і приймайте їхні записані типи. Значення за замовчуванням у PHP заповнює пропущений аргумент, але не замінює несумісне значення, уже записане в цій позиції. Наприклад, запуск, розпочатий із [7], після розгортання все одно передає ціле число 7:

Зміна вхідного методуВплив на записані вхідні дані [7]
handle(int $amount) → handle(int $amount, string $currency = 'USD')Старий аргумент залишається сумісним; новий кінцевий аргумент може отримати значення за замовчуванням. Також зберігайте сумісність відтворюваних команд.
Додавання обов’язкового кінцевого аргументу без значення за замовчуваннямСтарий запуск не має для нього значення.
Вставлення, видалення або переставлення початкових аргументівНаявні значення можуть потрапити не в той параметр. Однакові назви параметрів не виправляють позиційні вхідні дані.
Заміна int $amount на string $amountЗаписане ціле число не стало рядком.
Заміна int $amount на PaymentRequest $requestІн’єкція залежностей не є міграцією вхідних даних. Щойно створений DTO не повинен замінювати записану суму значеннями конструктора за замовчуванням.
Видалення лише кінцевого параметраPHP може прийняти виклик, але перевірте, що втрата його значення не змінює відтворювані команди чи бізнес-поведінку.

Надавайте перевагу додаванню необов’язкового кінцевого параметра або новому типу workflow для іншого контракту вхідних даних. Якщо всередині потрібен новий DTO, явно створюйте його із сумісних записаних аргументів у тілі workflow та керуйте версіями будь-яких змін стійких команд саме там. Зберігайте код, здатний відтворити кожну підтримувану форму вхідних даних, доки відповідні запуски його потребують. Перевіряйте фактично збережені дані з новим визначенням, зокрема холодний replay після стійкого очікування: тести лише нових запусків не охоплюють цю межу розгортання.

Поведінка Workflow 2.7.2​

У Workflow 2.7.2 помилка кількості або типу вхідних аргументів може перетворитися на термінальну подію WorkflowFailed. Натомість деякі помилки вирішення залежностей залишають запуск відкритим із завданням, яке постійно зазнає невдачі. Заміна скалярного значення на ін’єктований DTO зі значеннями конструктора за замовчуванням може навіть призвести до виконання з неправильними даними. Це дефекти продукту, зафіксовані у Workflow #866, а не безпечна стратегія керування версіями.

Відновлення сумісного коду може відновити відкритий запуск, який допускає повторну доставку, але не відкриває вже термінальний запуск. Ані repair(), ані нова гілка версії не обіцяють оживити такий невдалий початковий запуск. Спочатку перевірте його фактичний стан і помилку; зберігайте вхідні дані та історію, обираючи спосіб відновлення.

Опублікований захист у вбудованому режимі​

Workflow 2.7.3 перевіряє записані вхідні аргументи до входу в код застосунку. Несумісне зіставлення спричиняє типізований WorkflowEntryArgumentsMismatchException і блокує replay workflow task з replay_blocked_reason = workflow_entry_arguments_mismatch; run залишається нетермінальним. Поля діагностики вказують workflow, метод входу, параметр та очікуваний і фактичний типи, не копіюючи значень аргументів. Новий ін’єктований DTO, який відкинув би записані дані, теж відхиляється. Перевірте фактично встановлений пакет Workflow у вбудованому застосунку. Цей захист не відкриває заново термінальні run, створені старішим релізом.

Із цим опублікованим захистом відновлюйте той самий ще відкритий run так:

  1. Перевірте діагностику завдання вибраного запуску й підтвердьте workflow_entry_arguments_mismatch, не вважаючи, що кожна помилка завдання має цю причину.
  2. Відновіть визначення, яке приймає початкові записані аргументи, або розгорніть сумісний адаптер у тілі workflow. Зберігайте початкову ідентичність workflow, вхідні дані, історію та строки; не редагуйте сховище, щоб підлаштувати його під нову сигнатуру.
  3. Після появи сумісного коду застосуйте підтримувану дію відновлення до того самого відкритого запуску, а потім перевірте, що початкова робота продовжилася, а термінальний результат записано рівно один раз. Відновлення не подовжує початковий строк: якщо він уже минув, він усе одно діє.

Захист не переосмислює винятки з тіла workflow як невідповідності розгортання. Справжній TypeError застосунку або інша необроблена помилка в тілі й надалі підпорядковується звичайній поведінці відмови workflow. Захист також не надає перевірки всіх запусків для безпечного вилучення старих гілок, що відстежується у shared #220.

SDK у сервісному режимі мають окремі межі​

Виправлення вбудованого Core не змінює процес SDK, який виконує workflow у сервісному режимі. Наведені нижче старіші опубліковані SDK ще не мають захисту входу, роботу над яким відстежує спільна задача #221:

Опублікований SDKПоведінка зіставлення вхідних даних
PHP 2.5.3Викликає зареєстрований обробник із контекстом, після якого йдуть записані позиційні дані. Вхідний ArgumentCountError або TypeError може потрапити у звичайний шлях відмови workflow.
Python 2.6.1Викликає run(ctx, *start_input). Зміна кількості аргументів може завершити workflow помилкою; самі анотації типів не забезпечують перевірки типів і не перетворюють записані значення. Помилки тіла генератора також є помилками застосунку.
Rust 3.5.5Типізований адаптер десеріалізує вхідні дані до виклику обробника з фіксованою сигнатурою. Зміна типу запиту може зірвати це декодування. Це відрізняється від позиційного зіставлення PHP/Python; побічна відмова через неспожиту історію не є обіцяним відновлюваним захистом сигнатур.

Відокремлюйте сумісність сервісних вхідних даних і фактичну кваліфікацію SDK від вбудованого релізу. Не перехоплюйте кожен TypeError або кожну помилку Rust-обробника, називаючи їх безпечними для replay: це приховає справжні помилки застосунку.

Захист входу в сервісних SDK​

Підтримка в опублікованих випусках. Server 2.9.9 та SDK PHP 2.5.4, Python 2.6.2 і Rust 3.5.6 запровадили захист входу й описану нижче поведінку маршрутизації та відновлення. Це мінімальні версії для цих можливостей. Установлюйте поточні стабільні випуски, щоб отримувати виправлення безпеки.

Підготовлені SDK перевіряють записані вхідні аргументи до виконання коду workflow застосунку. Несумісний вхід спричиняє workflow_entry_arguments_mismatch: помилку заблокованого для replay task workflow, без команди fail_workflow і без закриття бізнесового run. Вхід, ідентичність workflow/run, зафіксована історія, прив’язка build та початкові дедлайни не змінюються. PHP перевіряє обов’язкові позиційні аргументи та оголошені PHP-типи. Python зіставляє сигнатуру з кількістю аргументів і значеннями за замовчуванням; анотації не стають перевірками типів під час виконання. Типізовані адаптери Rust перевіряють декодування входу до виклику handler або його фабрики стану. Низькорівневі Rust handler самі відповідають за обробку входу застосунку.

Специфічне поле task на Server failure_reason має значення workflow_entry_arguments_mismatch; replay_blocked_reason залишається загальним worker_reported_replay_failure. Перевіряйте latest_workflow_task_failure.reason у debug-відповіді вибраного run. Не плутайте ці поля з наведеною вище діагностикою вбудованого Core. Якщо після успішного входу код застосунку кидає TypeError, Rust handler повертає помилку або виникає інший збій, діють звичайні правила бізнесових помилок.

Відновіть код, який приймає початковий записаний вхід, а потім виконайте підтримувану процедуру відновлення того самого оригінального run. Не підміняйте вхід значеннями DTO за замовчуванням, не змінюйте історію та не починайте дедлайн заново. Захист не відкриває повторно оригінал, який старіший worker уже зробив термінальним.

Безпечна маршрутизація до заміни також потребує можливості worker перевіряти вхід. Змінений fingerprint не доводить сумісність replay й не є підставою переписувати початковий fingerprint run. Версіонуйте зміни durable-команд усередині сумісного методу входу та перевіряйте холодний replay перед promotion.

Зміна записаних аргументів і результатів activity​

Activity має два збережені контракти: аргументи, записані під час її планування, і результат, записаний після завершення. Розгортання не переносить ці дані до нової схеми. Це стосується вбудованого PHP та сервісних worker з PHP, Python і Rust SDK.

Відкладена або повторна спроба отримує початкові записані аргументи. Вона виконує реалізацію activity, обрану за реєстрацією worker і політикою маршрутизації збірок. Це може бути старіша збірка. Розгортання нової реалізації не гарантує, що кожна спроба використає її, і не змінює аргументи в черзі.

Під час replay завершеної activity поточний код workflow отримує записаний результат без повторного виконання activity. Зіставлення кроку та типу activity не перевіряє схему аргументів чи результату. Зміна структури даних може спричинити помилку в коді застосунку без невідповідності історії.

Додавайте необов’язковий аргумент, зберігаючи значення старих даних​

Зберігайте наявні позиційні аргументи та їхнє значення. У вбудованому PHP необов’язковий останній параметр дозволяє прийняти старі заплановані аргументи, наприклад [7]:

use Workflow\V2\Activity;

final class PriceActivity extends Activity
{
    public function handle(int $amount, string $currency = 'USD'): array
    {
        return ['amount' => $amount, 'currency' => $currency];
    }
}

Типове значення заповнює відсутній аргумент. Воно не перетворює несумісне записане значення і не виправляє змінений порядок аргументів. Зовнішні ефекти activity також мають залишатися сумісними: повторна спроба може відбутися після розгортання і повинна зберігати ідемпотентність.

Обробники PHP у сервісному режимі отримують контекст activity, а потім записані позиційні аргументи. Обробники Python отримують позиційні аргументи безпосередньо. В обох випадках для пропущених аргументів потрібні типові значення. Самі лише анотації Python не перевіряють і не перетворюють значення. Типізовані activity Rust десеріалізують одне значення запиту. Додавайте необов’язкове поле або поле з явним типовим значенням Serde, зберігаючи наявне представлення. Нове обов’язкове поле може спричинити помилку декодування ще до виклику обробника Rust. API activity описано в посібниках SDK для PHP, Python і Rust.

Читайте старі результати з резервним значенням​

Коли новий результат activity додає currency, workflow має й надалі приймати старі завершені результати, які містять лише amount:

$result = activity(PriceActivity::class, 7);
$currency = $result['currency'] ?? 'USD';

Оберіть резервне значення, що зберігає попередній бізнесовий зміст. Підтримуйте його для всіх історій, які можуть відтворюватися, зокрема для query і відновлення. Розгорніть сумісних читачів перед кодом, що записує нове представлення. Перед відкотом перевірте, чи старі читачі приймають нові записані результати. Типове значення аргументу activity не додає поле до вже записаного результату.

Для іншого контракту використовуйте новий тип​

Якщо ви перейменовуєте поле, змінюєте представлення або бізнесовий зміст, залиште старий тип activity доступним і додайте новий. Використовуйте гілку getVersion() у місці планування, коли старі історії повинні зберегти свій крок activity, а нові запуски мають планувати новий тип. Гілка всередині activity не виправить аргументи, що спричиняють помилку до входу в її тіло. Маркер версії не переписує результати в історії.

Перевіряйте дві межі розгортання в нових процесах на фактично встановлених пакетах: планування старим кодом із виконанням новим кодом activity, а потім завершення старим кодом activity з replay новим кодом workflow. Додайте несумісні аргументи та результати як контрольні помилкові випадки. Не припускайте, що описаний вище захист аргументів входу workflow також захищає сигнатури activity або читання результату застосунком. Підтверджений дефект із DTO у вбудованих activity відстежується в Workflow #910.

Перегляньте разом із цими контрактами activity правила записаних початкових аргументів workflow та рецепт зміни даних signal.

Перевірені межі помилок​

Перевірки опублікованих пакетів у #363 використовували нові процеси на кожній межі розгортання. Це перевірені базові версії, а не мінімальні підтримувані версії:

Опублікований пакетНесумісні аргументи activityНесумісне читання результату
Вбудований Workflow 2.11.2Відсутній обов’язковий аргумент спричиняє ArgumentCountError і помилку activity.Читання відсутнього поля масиву з обробкою помилок Laravel спричиняє ErrorException і помилку workflow.
PHP SDK 3.2.0 із Server 2.11.0Відсутній обов’язковий позиційний аргумент передається як ArgumentCountError у помилці activity.Передавання відсутнього поля читачу з обов’язковим рядковим аргументом спричиняє TypeError і помилку workflow.

Rust SDK 4.2.2 із Server 2.11.0Нове обов’язкове поле запиту спричиняє помилку типізованого декодування до виклику обробника activity.Нове обов’язкове поле результату спричиняє помилку типізованого декодування результату у workflow.

Сервісні перевірки записували max_attempts = 1, після чого необроблена помилка activity завершувала workflow з помилкою. Загалом помилки activity підпорядковуються записаній політиці повторних спроб і таймаутів. Workflow може обробити помилку activity після вичерпання повторних спроб. Помилка читання результату є помилкою коду workflow, а не запитом повторити завершену activity. Усі сумісні контрольні випадки завершилися з початковим значенням 7 і типовою валютою USD, з однією спробою activity та без repair. У перевірках результатів завершена activity залишалася завершеною.

Вбудований Workflow 2.11.2 також приймає зміну сигнатури activity, що замінює записаний скаляр 7 ін’єктованим DTO з типовою сумою 0, і може помилково завершитися зі значенням 0. Цей дефект продукту відстежує Workflow #910. Не використовуйте ін’єкцію залежностей для перенесення аргументів activity і не вважайте, що захист входу workflow охоплює цей випадок. Повернення сумісного коду не відкриває термінальний запуск знову. Перевірте фактичний стан і дотримуйтеся посібника з відновлення, не змінюючи записаних аргументів, історії чи кінцевих строків.

Опублікований захист входу в embedded activity​

Workflow 2.11.3 — мінімальна виправлена версія embedded PHP-захисту від прив’язування activity, що витісняє записані аргументи. Для чергових і локальних activity заміна записаного скаляра 7 інжектованим DTO зі значенням 0 за замовчуванням відхиляється до виконання тіла через ActivityEntryArgumentsMismatchException. Перевірка встановленого опублікованого пакета в нових процесах підтверджує відмову й відновлення з початковим входом. Описана вище версія 2.11.2 залишається вразливою до цього дефекту. Захист не додає поля до старих результатів activity; сумісним читачам усе ще потрібне резервне значення.

Відмова дотримується записаної політики спроб, backoff і таймаутів activity. За однієї дозволеної спроби activity вичерпується, а необроблена помилка завершує workflow невдало. Якщо визначені автором спроби ще залишилися, а сумісний код повернувся до дозволеної повторної спроби й дедлайнів, той самий початковий запуск/activity може завершитися із записаним входом. Перевірка підтверджує дві визначені автором спроби з нульовим backoff і результатом 7; вона не обіцяє необмеженого очікування майбутнього розгортання й не надає додаткових спроб.

Повернення коду або встановлення пакета не відкриває завершені оригінали, не скидає дедлайни й не відновлює витрачені спроби. Перевіряйте фактичну помилку та зберігайте записаний вхід/історію. Перевіряйте пакет Workflow, установлений в embedded-застосунку: цей випуск бібліотеки не оновлює наявні образи Server і не підтверджує приймання для service-worker/native.

Використання getVersion​

getVersion() — це безпечна щодо replay функція для послідовного коду. Під час першого виконання кожна точка зміни записує стійкий маркер версії запуску. Кожен подальший replay використовує це зафіксоване значення замість повторного визначення гілки за поточним кодом. Старі запуски, що передують новій точці розгалуження, консервативно отримують DEFAULT_VERSION.

use Workflow\V2\Workflow;
use Workflow\V2\WorkflowStub;
use function Workflow\V2\{activity, getVersion};

final class MyWorkflow extends Workflow
{
    public function handle(): void
    {
        $version = getVersion(
            'my-change-id',
            WorkflowStub::DEFAULT_VERSION,
            1
        );

        if ($version === WorkflowStub::DEFAULT_VERSION) {
            activity(OldActivity::class);
        } else {
            activity(NewActivity::class);
        }
    }
}

Як це працює​

Метод getVersion() приймає три параметри:

  • changeId — унікальний ідентифікатор точки зміни
  • minSupported — найменша версія, яку цей код ще підтримує
  • maxSupported — найбільша, поточна версія для нових виконань

Коли workflow доходить до getVersion():

  • Нові виконання додають типізовану подію історії VersionMarkerRecorded із change_id, вибраною version і підтримуваним діапазоном, а потім повертають maxSupported
  • Виконання під час replay повертають раніше записану версію з цього маркера історії
  • Запуски без маркера переходять до WorkflowStub::DEFAULT_VERSION, коли runtime визначає, що гілка передує поточному визначенню workflow. Спочатку він перевіряє маркер сумісності запуску відносно поточного worker, а потім порівнює стійко зафіксований workflow_definition_fingerprint запуску з поточним доступним для завантаження класом workflow. Якщо відбитки збігаються, запуск використовує те саме визначення й записує новий маркер. Якщо ні, запуск передує зміні й застосовується запасний варіант. Запуски, чия історія WorkflowStarted передує фіксації відбитка та не містить його, консервативно отримують DEFAULT_VERSION, оскільки runtime не може довести незмінність визначення. Це зафіксована політика 2.0 для запусків без відбитка: runtime не блокує отримання завдання лише через відсутність записаного відбитка в старого запуску. Запасний варіант не додає штучного маркера й не споживає нового кроку workflow
  • Методи query відтворюють той самий зафіксований маркер версії перед викликом анотованого методу, тому query бачать ту саму гілку, що й завдання workflow
  • Waterline показує записані маркери в хронології вибраного запуску з version_change_id, version, version_min_supported та version_max_supported. Деталі вибраного запуску також містять workflow_definition_fingerprint, workflow_definition_current_fingerprint і workflow_definition_matches_current, щоб оператори бачили, коли тривалий запуск почався зі старішим визначенням, навіть до фіксації маркера версії

Це дає новим workflow змогу використовувати найновіший шлях коду, поки наявні workflow продовжують використовувати початковий.

Додавання нової версії​

Припустімо, наявний workflow викликає prePatchActivity:

use Workflow\V2\Workflow;
use function Workflow\V2\activity;

final class MyWorkflow extends Workflow
{
    public function handle()
    {
        $result = activity(PrePatchActivity::class);

        return $result;
    }
}

Щоб замінити його на postPatchActivity без порушення активних workflow:

use Workflow\V2\Workflow;
use Workflow\V2\WorkflowStub;
use function Workflow\V2\{activity, getVersion};

final class MyWorkflow extends Workflow
{
    public function handle()
    {
        $version = getVersion(
            'activity-change',
            WorkflowStub::DEFAULT_VERSION,
            1
        );

        $result = $version === WorkflowStub::DEFAULT_VERSION
            ? activity(PrePatchActivity::class)
            : activity(PostPatchActivity::class);

        return $result;
    }
}

Під час розгортання нової точки розгалуження getVersion() продовжуйте змінювати DW_V2_CURRENT_COMPATIBILITY для цієї хвилі збірок. Runtime насамперед використовує workflow_definition_fingerprint, зафіксований на початку запуску, щоб визначити, чи відсутній маркер версії належить новому виконанню або старішому запуску, який має залишитися на DEFAULT_VERSION. Маркер сумісності залишається важливим для маршрутизації до сумісних worker і перевіряється перед відбитком. Запуски без записаного відбитка консервативно залишаються на DEFAULT_VERSION, оскільки runtime не може перевірити незмінність визначення.

Додавання наступних версій​

Для подальших змін збільшуйте maxSupported:

$version = getVersion(
    'activity-change',
    WorkflowStub::DEFAULT_VERSION,
    2
);

$result = match($version) {
    WorkflowStub::DEFAULT_VERSION => activity(PrePatchActivity::class),
    1 => activity(PostPatchActivity::class),
    2 => activity(AnotherPatchActivity::class),
};

Припинення підтримки старих версій​

Після завершення всіх workflow, які використовують стару версію, можна припинити її підтримку, збільшивши minSupported. Тоді більше не потрібно підтримувати старі шляхи коду.

// After all DEFAULT_VERSION workflows have completed:
$version = getVersion(
    'activity-change',
    1,  // No longer supporting DEFAULT_VERSION
    2
);

$result = match($version) {
    1 => activity(PostPatchActivity::class),
    2 => activity(AnotherPatchActivity::class),
};

Якщо workflow із версією, старішою за minSupported, намагається виконати replay, виникає VersionNotSupportedException. Це також стосується запусків зі старішою сумісністю, чий безпечний запасний варіант досі є WorkflowStub::DEFAULT_VERSION.

Якщо випадково повторно використати той самий changeId для іншої точки розгалуження, runtime вважатиме це помилкою детермінізму, а не непомітно прийме невідповідність. Зберігайте один стабільний changeId для кожної логічної зміни коду.

Кілька точок зміни​

Для незалежних змін можна використовувати кілька викликів getVersion() в одному workflow:

use Workflow\V2\Workflow;
use Workflow\V2\WorkflowStub;
use function Workflow\V2\getVersion;

final class MyWorkflow extends Workflow
{
    public function handle(): void
    {
        $version1 = getVersion('change-1', WorkflowStub::DEFAULT_VERSION, 1);
        $version2 = getVersion('change-2', WorkflowStub::DEFAULT_VERSION, 1);

        // Each change point is tracked independently
    }
}

Важливо: кожен changeId має бути унікальним у межах workflow. Вибрана версія записується в типізовану історію workflow й детерміновано відтворюється в подальших завданнях workflow, query та деталях Waterline. Якщо Waterline не показує VersionMarkerRecorded для точки зміни в старішому запуску, replay залишився на старому шляху DEFAULT_VERSION без додавання нового маркера до наявної історії. Поля деталей вибраного запуску workflow_definition_fingerprint, workflow_definition_current_fingerprint та workflow_definition_matches_current показують, чи почався запуск з іншим визначенням workflow, ніж те, яке може завантажити поточна збірка.

Скорочений виклик patched()​

patched($changeId) — це скорочений виклик із двома станами для звичного питання: чи перейшов запуск через одноразову зміну коду? Він записує ту саму стійку подію історії VersionMarkerRecorded, що й getVersion(), але повертає булеве значення замість цілого числа.

use Workflow\V2\Workflow;
use function Workflow\V2\{activity, patched};

final class MyWorkflow extends Workflow
{
    public function handle(): string
    {
        if (patched('use-new-payment-activity')) {
            return activity(NewPaymentActivity::class);
        }

        return activity(LegacyPaymentActivity::class);
    }
}

Поведінка:

  • Нові запуски фіксують маркер, обирають нову гілку, а patched() повертає true.
  • Запуски, які почалися до додавання цього changeId, залишаються на DEFAULT_VERSION за тією самою перевіркою відбитка, що й у getVersion(), а patched() повертає false.
  • Replay обох типів читає раніше зафіксований маркер і повертає те саме значення, тому рішення про гілку є стійким.

patched() точно еквівалентний getVersion($changeId, DEFAULT_VERSION, 1) === 1. Використовуйте його, коли є лише дві гілки й не потрібно зберігати стару гілку назавжди. Булевий виклик читається простіше, ніж match за DEFAULT_VERSION та 1.

Якщо потрібні понад дві гілки або згодом планується ще одна версія тієї самої логічної зміни, використовуйте getVersion() із явним maxSupported. Перехід від patched() до getVersion() для того самого changeId є помилкою детермінізму, оскільки наявний маркер записано з maxSupported = 1.

Видалення старої гілки через deprecatePatch()​

Коли всі старі запуски для точки зміни patched() завершилися, стару гілку можна видалити з коду workflow. Сумісний спосіб — замінити виклик patched() на deprecatePatch(), а не видаляти його повністю.

use Workflow\V2\Workflow;
use function Workflow\V2\{activity, deprecatePatch};

final class MyWorkflow extends Workflow
{
    public function handle(): string
    {
        deprecatePatch('use-new-payment-activity');

        return activity(NewPaymentActivity::class);
    }
}

deprecatePatch() зберігає точку зміни на хронології workflow, щоб уже зафіксовані події історії VersionMarkerRecorded і далі відповідали відомому виклику. Він повертає null і безумовно обирає новий шлях. Після випуску цієї версії:

  • Нові запуски фіксують маркер deprecate_patch, обирають нову гілку, а виклик deprecatePatch() повертає null.
  • Наявні запуски, які вже зафіксували маркер patched для цього changeId, продовжують відтворювати його й проходять через гілку після припинення підтримки старого коду, яка тепер є єдиною, без помилки.
  • Передбачається, що наявні запуски, які зафіксували false для patched() і використовували старий шлях, уже не активні. Якщо такий запуск досі працює й виконує replay, workflow прочитає старий маркер, але виконає нову гілку. Тому безпечний порядок — дочекатися завершення старих запусків перед розгортанням deprecatePatch().

Двоетапний життєвий цикл patch і правила розміщення:

  1. Додайте patched() у точці зміни. Обидві гілки залишаються в коді workflow. Нові запуски обирають нову гілку, а старі продовжують використовувати стару.
  2. Дочекайтеся завершення всіх старих запусків. За допомогою пошуку запусків Waterline або dw workflow:list підтвердьте відсутність відкритих запусків, які можуть відтворювати стару гілку.
  3. Замініть patched() на deprecatePatch() у тому самому місці з тим самим changeId і видаліть стару гілку з тіла функції. Залиште виклик, щоб стійка історія й далі відповідала відомій точці зміни.
  4. Необов’язково: повністю видаліть deprecatePatch(), коли впевнені, що жоден історичний replay для query, експорту або аудиту більше не читатиме історію з цим маркером. Це незворотний крок. Більшість workflow можуть залишати deprecatePatch() необмежено довго без витрат під час виконання.

Правила розміщення:

  • patched() та deprecatePatch() слід викликати з тіла функції workflow, а не з activity, обробників signal або методів query. Це кроки workflow, які мають відтворюватися детерміновано.
  • Кожен changeId є однією логічною точкою зміни. Повторне використання того самого changeId для іншої гілки є помилкою детермінізму.
  • Протягом життєвого циклу changeId може використовуватися у формі patched() або deprecatePatch(), але ніколи в обох одночасно. Розгортання, яке змінює виклик, має замінити його, а не залишати обидва.
  • getVersion() та patched() не можуть співіснувати для того самого changeId. Оберіть одну модель під час додавання точки зміни.

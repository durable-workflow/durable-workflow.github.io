Python SDK

The Python SDK is a thin, async-first client for a self-hosted Durable Workflow Server or Durable Workflow Cloud namespace runtime. It lets Python processes start, observe, signal, and cancel workflows through the runtime's control-plane API, and register as workers that execute workflow tasks and activities.

Try the local Sample App playground​

For the shortest no-Cloud authoring journey, open the current Sample App main branch in GitHub Codespaces and run:

scripts/playground python

The local playground generates caller-owned workflow and activity source, selects the current stable artifacts, and starts the published Server and Waterline. It waits for a worker registration whose identity, workflow type, activity type, and task queue match the generated contract before starting the workflow. Success requires the expected completed result and history; the terminal then prints the exact local Waterline run link and the path to structured JSON evidence.

The package installation, inline quickstart, API reference, and repository example below remain the direct paths for users who do not want Sample App.

The SDK targets the same durable model as the PHP package — instance IDs, run IDs, history events, task queues, and type keys are shared across languages. A Python worker can serve activities for a PHP-authored workflow, and vice versa.

For a capability comparison across the Python SDK, PHP SDK, Rust SDK, and dw, see Client and Worker Capabilities.

For constructor signatures, return types, exception classes, and metric names, see the generated Python SDK API reference.

Python SDK 2.5.0 adds an optional bounded history cache for sticky execution. Use Server 2.5.10 or newer and enable it on each worker. See Portable Worker Affinity and the Python guide and runnable example.

Cloud customers use the provisioned namespace's runtime URL and namespace with separate client and worker credentials. See Cloud Managed Runtime for that connection boundary; the quickstart below uses local self-hosted values.

Requirements​

  • Python 3.10 or later
  • Docker (for the local Server used in this quickstart), an existing self-hosted Server, or a provisioned Cloud namespace runtime

Installation​

Install the stable Python SDK release. The exact requirement is generated from the same tuple as the Server quickstart, and a lock or constraints file can retain it for reproducibility.

pip install durable-workflow==2.8.0

The SDK depends on httpx for HTTP and on the fastavro Python package to encode the Apache Avro wire format used by the only public v2 payload codec. Prometheus metrics support is optional.

Quickstart​

Here is a complete Python program that defines a workflow with one activity, starts it against a local Durable Workflow server, and waits for the result:

import asyncio
import uuid

from durable_workflow import Client, Worker, workflow, activity

@activity.defn(name="greet")
async def greet(name: str) -> dict:
    return {"greeting": f"Hello, {name}!", "length": len(name)}

@workflow.defn(name="greeter")
class GreeterWorkflow:
    def run(self, ctx, *args):
        result = yield ctx.schedule_activity("greet", list(args))
        return result

async def main():
    workflow_id = f"greeting-{uuid.uuid4().hex}"

    async with Client("http://localhost:8080", token="dev-token", namespace="default") as client:
        handle = await client.start_workflow(
            workflow_type="greeter",
            task_queue="default",
            workflow_id=workflow_id,
            input=["world"],
        )

        worker = Worker(
            client,
            task_queue="default",
            workflows=[GreeterWorkflow],
            activities=[greet],
        )

        await worker.run_until(workflow_id=workflow_id, timeout=30.0)
        result = await handle.result(timeout=10.0)

    print(result)  # {"greeting": "Hello, world!", "length": 5}

asyncio.run(main())

Bounded failure reports​

Python SDK 2.11.0 introduced bounded outgoing failure reports. Defaults are 62 KiB UTF-8 for the message, 128 KiB for the stack, 64 KiB for combined serialized optional details and diagnostics, and 1 MiB for the complete HTTPX-encoded body. Markers, JSON escaping, claim identity and other commands in the batch count toward that body limit. A lower configured or discovered transport limit takes precedence. Failure type, class, code, retry policy and claim identity are preserved.

Set a smaller body budget when needed. Payload-size warning settings remain advisory.

from durable_workflow import Client

async with Client(
    "https://workflow.example.com",
    worker_token="worker-token",
    control_token="operator-token",
    failure_report_limit_bytes=512 * 1024,
) as client:
    info = await client.get_cluster_info()

A visible truncation marker and original byte counts identify shortened fields. Avro details remain intact or are omitted whole. An unrepresentable required envelope raises FailureReportTooLarge before HTTP submission. Local failures are normalized before workflow code observes them, so first execution and cold replay see the persisted message. An already observed local message remains immutable during final batch fitting.

External Payload Storage​

Normal Client and Worker operations use Server's authenticated runtime transport automatically. The SDK discovers namespace policy and transport limits through GET /api/cluster/info, uploads encoded values above the threshold or needed to fit the request, and fetches referenced values before decode. Application workflow and activity code receives the decoded value. Provider credentials stay on Server. Remote workers do not need boto3, provider clients or access to Server's local storage directory.

The runtime reference has schema durable-workflow.v2.runtime-external-payload-reference.v1 and an opaque reference_id. It has no provider uri. Upload/fetch uses the normal role credential and namespace, verifies encoded-byte size and SHA-256, and preserves task-attempt and lease fencing for worker completion. See the runtime HTTP contract for routes, limits and typed refusals. SDK support depends on an available compatible transport, not merely on a configured storage driver.

The following direct provider helpers serve application-managed storage and test fixtures that deliberately access their own provider. They use a different provider-URI schema. They are not required for normal Server or Cloud clients, and a provider external_storage envelope is rejected by Server with HTTP 422 and external_payload_unsupported.

For these direct helpers, the reference schema is EXTERNAL_PAYLOAD_REFERENCE_SCHEMA (durable-workflow.v2.external-payload-reference.v1). Object-store adapters do not add cloud SDK dependencies to durable-workflow; applications pass their already configured S3, GCS, or Azure clients.

Their provider reference has the following fields. This is not the runtime reference accepted by Server HTTP routes:

{
  "schema": "durable-workflow.v2.external-payload-reference.v1",
  "uri": "s3://dw-payloads/billing/run-001/input.avro",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "size_bytes": 1048576,
  "codec": "avro",
  "expires_at": "2026-05-22T00:00:00Z"
}

ExternalPayloadReference.from_dict() rejects unknown schemas and malformed fields. fetch_external_payload() verifies size_bytes and sha256 before returning bytes, and raises ExternalPayloadIntegrityError on size or hash mismatch. Missing objects can also raise the provider driver's error. Use ExternalPayloadCache for verified bytes only. Cache eviction does not grant permission to delete a Server-managed object. delete_external_payload() is a direct provider operation, not a runtime-reference cleanup API.

Use external_storage_driver_from_policy() in code that deliberately accesses application-owned provider storage and owns the required client. Reading a namespace policy does not make provider envelopes valid Server requests. Provider clients remain application-owned; these optional adapters do not add boto3, google-cloud-storage or azure-storage-blob as runtime dependencies:

from durable_workflow.external_storage import external_storage_driver_from_policy

namespace = await client.describe_namespace("billing")
driver = external_storage_driver_from_policy(
    namespace.external_payload_storage,
    s3_client=application_owned_s3_client,
)

The factory raises ValueError when the policy is disabled, when the named driver is unsupported, or when the matching provider client is missing. Disabled policies do not return a no-op driver; callers should branch on policy.enabled before asking for a driver.

Current workflow identity​

Python SDK 2.9.0 and later exposes read-only ctx.workflow_id and ctx.run_id inside workflow code. Both are strings from the current task and stay identical during replay. After continue-as-new, the workflow ID stays unchanged and the successor gets its own run ID. Do not replace that ID with a predecessor ID passed as an argument.

from durable_workflow import workflow

@workflow.defn(name="identity")
class IdentityWorkflow:
    def run(self, ctx):
        identity = {"workflow_id": ctx.workflow_id, "run_id": ctx.run_id}
        yield ctx.schedule_activity("record_identity", [identity])
        return identity

These properties read local task identity without an HTTP request. For status polling outside workflow code, use await client.describe_workflow(workflow_id). Use await client.query_workflow(workflow_id, query_name) for state exposed by a registered query handler. Identity properties do not replace either operation.

System Maintenance​

Operator scripts and on-call automation drive the same maintenance loops as the dw system:* commands through the Client. Each method requires the bearer token to carry admin scope; without it the server returns Unauthorized.

repair_pass runs one task-repair sweep. With no filters the server runs a full-scope pass over the namespace; pass run_ids to narrow the sweep to a specific list of workflow runs, or instance_id to bound it to a single running instance.

With no run_ids, retention_pass asks the PHP Server to prune expired terminal runs under the current namespace policy, up to its scan limit. Review the retention procedure before shortening a policy or submitting explicit targets.

activity_timeout_pass enforces start-to-close and schedule-to-close deadlines on activity executions that have already passed their deadline. With no filters the server processes any expired activity executions up to its scan limit; pass execution_ids to target a specific list, or limit to bound a single pass.

These methods do not raise on empty work — repeated calls during a quiet period return the same passes / repaired / pruned counters with zero deltas, so they are safe to call from cron-driven operator scripts.

Defining Workflows​

Workflows are Python classes decorated with @workflow.defn. The run method is an ordinary synchronous function or a synchronous generator that yields durable commands to the server. Use the generator form when the workflow needs durable work; async def run is not supported.

from durable_workflow import workflow

@workflow.defn(name="order-processing")
class OrderWorkflow:
    def run(self, ctx, *args):
        order = args[0] if args else {}

        # Schedule an activity and wait for the result
        validated = yield ctx.schedule_activity(
            "validate_order", [order]
        )

        # Start a timer (durable sleep)
        yield ctx.start_timer(seconds=60)

        # Schedule another activity
        receipt = yield ctx.schedule_activity(
            "process_payment", [validated]
        )

        return receipt

The name in @workflow.defn(name="...") is the type key used across all languages. It must be a plain string — not a Python module path or class reference.

Signals, Queries, and Updates​

Signals are recorded in durable history and dispatched to Python handlers during workflow replay:

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False
        self.approved_by = None

    @workflow.signal("approve")
    def approve(self, by: str) -> None:
        self.approved = True
        self.approved_by = by

    def run(self, ctx, *args):
        ready = yield ctx.wait_condition(
            lambda: self.approved, key="approval.approved", timeout=60,
        )
        return {
            "status": "approved" if ready else "timed_out",
            "approved": self.approved,
            "approved_by": self.approved_by,
        }

The wait belongs to the workflow, not an activity. Its predicate reads replayed signal-handler state; the worker does not hold an activity slot for the approval. The condition's timeout is separate from the workflow's finite run and execution deadlines. For external-job completion, use a short submit-and-return activity and a correlated callback.

Query and update receiver decorators are available so workflow classes can publish stable handler names. Python workers execute server-routed query tasks by replaying the committed workflow history and invoking the registered query handler against that replayed state. They also apply accepted updates delivered through workflow tasks:

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False

    @workflow.query("status")
    def status(self) -> dict:
        return {"approved": self.approved}

    @workflow.update("set_approval")
    def set_approval(self, approved: bool) -> dict:
        self.approved = approved
        return {"approved": self.approved}

    @set_approval.validator
    def validate_set_approval(self, approved: bool) -> None:
        if not isinstance(approved, bool):
            raise ValueError("approved must be boolean")

Python workers complete server-routed queries by returning a query-task result to the server. For a declared update validator, the worker instead receives a dedicated validation task, replays authoritative workflow state, and invokes only the validator. The server records no accepted update and dispatches no update handler until that validation succeeds. Validator-bearing workers refuse to register unless discovery advertises the synchronous pre-accept contract; rejection, missing or incompatible workers, worker loss, timeout, and fenced duplicate or stale completion remain explicit typed outcomes. PHP and Rust do not currently expose update-validator authoring APIs and advertise that absence in their workflow contracts rather than claiming validator parity.

Handler lifecycle​

Released validation. Python SDK 2.6.2 introduced the handler guards below. Server-routed asynchronous queries and update validators remain supported. See SDK #177 for the corrected scope.

Every replay constructs a fresh workflow instance before executing run(). Signals already recorded at workflow start are applied after run() reaches its first yield, so constructor and pre-yield initialization happen first. Signal and update handlers mutate that replayed state. Queries inspect it without changing durable state; update validators inspect a disposable replayed state before acceptance. Put durable activities, timers and child workflow commands in run(), not in a handler.

The validation rejects coroutine functions for signals and updates, and rejects generator or async-generator functions for all decorated handler kinds, including queries and validators. Synchronous signal and update wrappers cannot bypass the guards by returning asynchronous values. Returning generator or async-generator values is refused for every handler kind. For a server-routed query, the Worker explicitly awaits an asynchronous result under the original query deadline and claim/cancellation authority. Awaiting does not grant a fresh budget or permit a result after authority is lost. For pre-accept validation, the Worker also awaits an asynchronous validator result against disposable replayed state.

The local synchronous helpers cannot await. workflow.query_state() refuses an asynchronous result with QueryFailed, and workflow.validate_update() refuses it with UpdateRejected. They close returned coroutines instead of leaking them as operation results.

Workflow time and durable waits​

During worker replay, ctx.now() returns the run's persisted start time. It does not advance after an activity, timer, signal, or other durable step. Repeated cold replays of the same history return that same start value. A continue-as-new successor has its own start time; it does not keep the predecessor's clock anchor.

The published Python implementation uses WorkflowStarted.payload.timestamp when present, otherwise the canonical WorkflowStarted.recorded_at. Missing or invalid persisted replay time is an explicit clock error, not permission to read the worker's wall clock. This is the fixed-start contract settled in SDK #146.

Wait for a durable operation instead of looping until ctx.now() changes:

from durable_workflow import workflow


@workflow.defn(name="wait_without_clock_loop")
class WaitWithoutClockLoop:
    def run(self, ctx):
        started_at = ctx.now()
        yield ctx.start_timer(30)
        return {
            "run_started_at": started_at.isoformat(),
            "after_wait": ctx.now().isoformat(),
        }

The timer's durable completion resumes the workflow. Both returned timestamps are the same start time. A loop such as while ctx.now() < deadline will not become false merely because timers fire.

For a relative delay, yield ctx.start_timer(seconds) or ctx.sleep(seconds). Use first-completion selection when work should race a durable timer. Set execution_timeout_seconds and run_timeout_seconds on client.start_workflow(...) when Server must enforce a workflow deadline, including while workers are stopped. An HTTP or get_result() waiting timeout only limits that local request; it does not replace the workflow's persisted deadline. Keep an application deadline across continue-as-new by explicitly passing it as input, without replacing the Server's original execution deadline.

For measured elapsed time within one activity invocation, read a monotonic clock there and return the duration as the activity result. For an external UTC deadline, let an activity check the authoritative external clock and return its decision; workflow code replays that recorded result. Never compare UTC timestamps with monotonic values, or subtract monotonic readings from different processes or hosts. ctx.now() subtraction measures neither active processing time nor elapsed wall time in Python.

Activity Retries and Timeouts​

Use ActivityRetryPolicy and timeout keyword arguments on ctx.schedule_activity(...) when one activity call needs a different retry budget or deadline than the default single-attempt behavior:

from durable_workflow import ActivityRetryPolicy

receipt = yield ctx.schedule_activity(
    "process_payment",
    [validated],
    retry_policy=ActivityRetryPolicy(
        max_attempts=4,
        initial_interval_seconds=1,
        backoff_coefficient=2,
        maximum_interval_seconds=30,
        non_retryable_error_types=["ValidationError"],
    ),
    start_to_close_timeout=120,
    schedule_to_close_timeout=300,
    heartbeat_timeout=15,
)

start_to_close_timeout caps one attempt after a worker starts it. schedule_to_close_timeout caps the whole activity execution across all attempts. heartbeat_timeout requires long-running activities to call activity.context().heartbeat(...) before the interval expires. The retry policy is snapped onto the durable activity execution when it is scheduled, so later deploys do not change already-running attempts.

ctx.schedule_activity(..., queue="payments-v2") selects the queue for a newly scheduled activity. An already scheduled execution, its retries and repaired tasks keep their recorded queue. Changing the worker's task_queue does not reroute them or change an existing run's workflow queue. Keep compatible old-queue workers until the remaining dependencies are accounted for. Follow recorded activity queues and recovery.

Determinism Rules​

Workflow code is replayed from history. It must not perform any non-deterministic operations directly:

  • No I/O (HTTP calls, file reads, database queries)
  • No datetime.now() or time.time() — use ctx.now() only for the fixed run-start anchor; use durable timers for waits
  • No random.random() — use ctx.random()
  • No uuid.uuid4() — use ctx.uuid4()

All non-determinism must flow through the context or be captured with ctx.side_effect().

Finally blocks and context managers​

SDK 2.12.2 and later. A suspension is not a workflow exit. Python may execute finally blocks and with exits while disposing of a suspended replay. The SDK discards durable commands and ctx.logger messages produced only by disposal; queries see the state at the pending command. Actual completion, failure or cooperative cancellation runs cleanup through the normal history, and cold replay uses its recorded results.

Keep direct I/O out of these hooks. Schedule external cleanup as an Activity with yield ctx.schedule_activity(...), and wrap that Activity in with ctx.cancellation_shield(): if it must finish after cooperative cancellation.

Fan-Out​

Yield a list of commands to run them concurrently:

@workflow.defn(name="fan-out-example")
class FanOutWorkflow:
    def run(self, ctx, *args):
        items = args[0]

        # Nested lists may mix activities, children, and timers.
        results = yield [
            ctx.schedule_activity("process_item", [items[0]]),
            [
                ctx.start_child_workflow("process-batch", [items[1:]]),
                ctx.start_timer(1),
            ],
        ]

        return results  # same nested shape and input order

The worker emits one ordinary command per durable leaf and attaches the shared stable parallel_group_* fields plus the full outer-to-inner path. History can close members in any order; replay still binds results and failures by durable input position. Exact duplicate terminal delivery is ignored. Pending history after a worker restart and fully completed history reconstruct the same group without rescheduling completed work.

First-completion selection​

Use ctx.select() when independent work should start together but the workflow can make progress after one member completes:

selected = yield ctx.select({
    "resolver": ctx.schedule_activity("resolve-request", [request_id]),
    "input": ctx.wait_condition(lambda: self.resolution is not None, key="resolution-ready"),
    "deadline": ctx.start_timer(2),
})

if selected.key == "deadline":
    yield selected.handles["resolver"].cancel()
    return {"status": "timed_out"}

yield selected.handles["deadline"].cancel()
return {"status": "resolved", "value": selected.result()}

The SelectionResult includes the winner's stable key, input index, operation kind and durable identity, typed outcome, and all DurableOperationHandle instances. yield handle.await_result() waits for a non-winner later; yield handle.cancel() records an explicit void request. Only committed SelectionOperationCancelled history proves cancellation won; replay advances past an unmarked request, and await_result() still returns a completion that committed first. Replay consumes the persisted winner even if later history contains another completion first. Duplicate and out-of-order external delivery cannot replace an already committed winner.

Saga Compensation​

def forward(saga):
    flight = yield ctx.schedule_activity("trip.reserve-flight", [])
    saga.add_compensation("trip.cancel-flight", [flight])

    hotel = yield ctx.schedule_activity("trip.reserve-hotel", [])
    saga.add_compensation("trip.cancel-hotel", [hotel])

    yield ctx.schedule_activity("trip.charge", [])
    return {"status": "booked"}

The saga executes ordinary activity commands sequentially in reverse registration order after a failure. Terminal cancel_workflow does not resume the workflow to run compensations. The helper stops on the first compensation failure. Continue-as-New​

For long-running workflows, use continue-as-new to reset the history:

from durable_workflow import ContinueAsNew

Defining Activities​

Activities are async Python functions decorated with @activity.defn. Unlike workflows, activities can perform I/O freely.

from durable_workflow import activity

@activity.defn(name="send_email")
async def send_email(to: str, subject: str, body: str) -> dict:
    # Activities can do I/O: HTTP calls, database queries, etc.
    response = await some_email_client.send(to=to, subject=subject, body=body)
    return {"message_id": response.id, "sent": True}

The name is the type key shared across languages. A PHP workflow can schedule an activity named "send_email" and a Python worker will pick it up, and vice versa.

Activity Context​

Inside an activity, access execution metadata and heartbeat via activity.context():

@activity.defn(name="long_running_task")
async def long_running_task(items: list) -> dict:
    ctx = activity.context()

    print(f"Attempt #{ctx.info.attempt_number}")
    print(f"Task queue: {ctx.info.task_queue}")

    for i, item in enumerate(items):
        # Check for cancellation
        if ctx.is_cancelled:
            return {"partial": True, "processed": i}

        await process(item)

        # Heartbeat to keep the task alive
        await ctx.heartbeat({"progress": i + 1, "total": len(items)})

    return {"processed": len(items)}

Received retry policy and original attempt​

Requires Python SDK 2.12.0 or later. info = activity.context().info exposes the original attempt_number and an immutable retry_info snapshot. info.retry_info.policy() returns a fresh copy, including unknown fields.

A missing policy and root retry_policy: null both have an unknown retry limit. policy_provided distinguishes them (False and True). A received policy object with max_attempts: null explicitly means unlimited: is_unlimited() is True, while max_attempts() remains None. For a positive integer limit, max_attempts() returns that limit and is_last_configured_attempt() compares it with the original attempt. An unknown limit returns None for that last-attempt check.

This check describes the received budget. Cancellation, deadlines, workflow closure and non-retryable failures can end execution earlier. Ordinary and supervised remote callbacks receive the original snapshot. Inline and prepared local callbacks do not inherit the parent's remote retry policy.

Signal the originating run​

info.workflow_id and info.run_id preserve the original received identities and can be None. Local callbacks inherit only known parent identities. The SDK never substitutes a task ID. Pass an authorized application client to this helper; the handle pins the original run:

from durable_workflow import Client, activity


async def signal_originating_run(client: Client, business_event_id: str) -> dict:
    info = activity.context().info
    if info.workflow_id is None or info.run_id is None:
        raise RuntimeError("This activity has no known originating workflow run")
    handle = client.get_workflow_handle(info.workflow_id, run_id=info.run_id)

        "payment_recorded",

Keep business_event_id stable across retries and within the Server's command-key length limit. The currently published Server does not retain these keys for every signal path. Make business-event processing idempotent and reconcile uncertain delivery. See the canonical activity reference and signal receipt-retention requirement.

Heartbeat requests​

For remote activities, call await ctx.heartbeat(...) during bounded work, well before heartbeat_timeout. Its first window starts at runtime claim, before Python receives the task. Each recorded heartbeat uses the runtime's recording time, not the time its response reaches Python. Pauses, request latency and transport retries consume the budget. Follow the cadence guidance.

The direct Client.heartbeat_activity_task() call uses the configured TransportRetryPolicy. After that policy, transport errors can propagate as httpx.TransportError, and HTTP refusals become mapped SDK exceptions such as ServerError. This is HTTP retry behavior, not another activity attempt or more heartbeat time. ActivityContext.heartbeat() can raise ActivityCancelled when the worker tells the activity to stop. When cooperative process supervision is enabled, failed heartbeat or ownership checks can stop or abandon the callback. Do not assume every failure returns to a catch block or that cleanup code always runs.

Do not suppress heartbeat/ownership failures and continue external work or report success. Progress is not an external commit or a resumable-checkpoint receipt. Keep external effects idempotent.

Heartbeat refusals and callback exit​

In Python SDK 2.9.0, ctx.heartbeat() and ctx.heartbeat_sync() raise ActivityLeaseAuthorityLost when a heartbeat response says can_continue=false. The exception retains the original Server reason, such as activity_deadline_elapsed, attempt_closed or run_closed. A cancellation request instead raises ActivityCancelled. See the published SDK qualification.

The heartbeat that observes the refusal is a cooperative exit point. Stop external work and propagate the exception; do not catch it and return success. Code that never heartbeats can keep running until it returns. A helper heartbeat cannot forcibly interrupt a blocked library call: use finite I/O deadlines and the call's own cancellation mechanism.

The physical activity slot stays occupied until the callback/thread exits. Losing attempt authority does not make that thread available for replacement work, and the worker does not publish a late result for the closed attempt. Runtime timeout enforcement and stopping application code are separate boundaries. See activity timeouts and the helper-thread guidance.

Non-Retryable Errors​

Raise NonRetryableError to fail the activity without retries:

from durable_workflow import NonRetryableError

@activity.defn(name="validate")
async def validate(data: dict) -> dict:
    if "required_field" not in data:
        raise NonRetryableError("Missing required_field")
    return data

Terminal business errors​

non_retryable_error_types matches the outermost exception's short name (exception_type) or fully qualified class name (exception_class) exactly. For example, ValidationError does not match SpecificValidationError, even if it is a subclass. A qualified entry such as app.errors.ValidationError must match that recorded class name. The policy does not walk subclasses or exception causes. raise RuntimeError(...) from NonRetryableError(...) reports the outer RuntimeError and can still be retried.

When converting a known business exception, make NonRetryableError the outer exception and keep the original Python cause with cause=error. This marks the activity failure non-retryable without relying on a name list. It does not make the entire workflow fail automatically: workflow code receives ActivityFailed when the activity has no retries left, either because it is non-retryable or because its retry budget is exhausted.

from durable_workflow import ActivityFailed, NonRetryableError, activity, workflow

@activity.defn(name="validate_order")
async def validate_order(order: dict) -> dict:
    try:
        if order.get("amount", 0) <= 0:
            raise ValueError("amount must be positive")
    except ValueError as error:
        raise NonRetryableError("Order validation failed", cause=error) from error
    return order

@workflow.defn(name="place_order")
class PlaceOrderWorkflow:
    def run(self, ctx, order: dict):
        try:
            yield ctx.schedule_activity("validate_order", [order])
        except ActivityFailed as failure:
            if (
                failure.activity_type != "validate_order"
                or failure.exception_type != "NonRetryableError"
                or not failure.non_retryable
            ):
                raise
            return {"order_id": order["id"], "status": "rejected"}
        return {"order_id": order["id"], "status": "accepted"}

For input {"id": "order-123", "amount": 0}, the activity fails once and the workflow completes normally with status: rejected. Handle only the business failure you intend to handle; the example rethrows other failures. Continue with further durable steps if your business flow requires them. An uncaught ActivityFailed fails the workflow. Preserving a Python cause does not mean retry policy examines that chain or that every SDK exposes an identical cause object.

Synchronous and asynchronous activities​

Ordinary def remote activities run in a dedicated thread pool bounded by max_concurrent_activity_tasks. Each callback keeps its activity context. Polling, workflow tasks and worker heartbeats can progress while a callback blocks. async def activities run on the event loop and must use nonblocking I/O; a blocking call inside an async function still stalls that loop.

From a synchronous callback, call activity.context().heartbeat_sync(details) to send progress through the owner event loop with the original task, attempt and worker identity. Async callbacks use await activity.context().heartbeat(details).

Cancelling an await does not stop a running Python thread. Its physical slot stays occupied until the callback returns, and a late return does not submit a result after cancellation. If a callback is still running after shutdown_timeout, shutdown raises RuntimeError and retains the worker registration. Set timeouts on downstream I/O and use separately isolated worker processes for CPU-heavy work. See the SDK's execution and shutdown reference.

Heartbeating from a helper thread​

For one long blocking call, capture ctx = activity.context() inside the synchronous activity and pass it to the helper. A new thread does not automatically inherit the activity context. Use ctx.heartbeat_sync(details) from the helper, never from the worker event loop. See the SDK's complete helper-thread recipe.

Stop and join the helper when the call returns or raises. If a heartbeat raises ActivityCancelled or ActivityLeaseAuthorityLost, signal cooperative cancellation to the call and re-raise the original exception before returning a result. A helper exception cannot forcibly interrupt a blocked library call. Give that call its own finite deadline and cancellation mechanism, and bound heartbeat request timeouts and retries. Helper heartbeats can otherwise keep reporting liveness while the work is hung.

A missing or incompatible manifest raises RuntimeError during registration, so supervisors fail fast instead of running a worker that cannot safely complete tasks.

run_until() uses the same registration and dispatch path as run(), but polls sequentially and returns the final WorkflowExecution for the named workflow. It raises TimeoutError when the workflow is still non-terminal after the timeout.

During task execution:

  • unknown workflow or activity types are reported back to the server as task failures, not hidden in local logs
  • NonRetryableError marks activity failures as non-retryable
  • ActivityCancelled propagates as a cancellation outcome
  • unhandled activity exceptions are reported as retryable failures unless the activity retry policy or server deadline says otherwise
  • query handler exceptions are reported as QueryFailed

Worker sessions​

Use WorkerSessionOptions when sequential remote activities need one worker's local resource. This example is checked with Python SDK 2.9.0 and Server 2.11.0; see the portable affinity version requirements. Use a unique job_id for each workflow run so a new run does not reuse a terminal session id.

The cache below is disposable. Each activity can rebuild it from the durable business input, so a replacement holder does not depend on a previous process's memory:

from durable_workflow import ActivityFailed, WorkerSessionOptions, activity, workflow

# Disposable process-local state. Rebuild it from durable business input.
documents = {}

def ensure_document(job_id):
    rebuilt = job_id not in documents
    if rebuilt:
        documents[job_id] = {"text": "document:" + job_id}
    return documents[job_id], rebuilt

@activity.defn(name="prepare_document")
async def prepare_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id, "rebuilt": rebuilt}

@activity.defn(name="inspect_document")
async def inspect_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id,
            "rebuilt": rebuilt, "text": document["text"]}

@workflow.defn(name="inspect_document_workflow")
class InspectDocumentWorkflow:
    def run(self, ctx, job_id):
        session = WorkerSessionOptions(
            session_id="documents:" + job_id,
            requirements=("fs:documents",),
            lease_seconds=5,
            ttl_seconds=60,
            max_concurrent_activities=1,
            allow_reacquire_after_failure=True,
        )
        options = dict(worker_session=session,
                       start_to_close_timeout=5,
                       schedule_to_start_timeout=12,
                       schedule_to_close_timeout=20,
                       retry_policy={"max_attempts": 1})
        try:
            prepared = yield ctx.schedule_activity("prepare_document", [job_id], **options)
            inspected = yield ctx.schedule_activity("inspect_document", [job_id], **options)
        except ActivityFailed as error:
            if error.activity_type not in {"prepare_document", "inspect_document"}:
                raise
            return {"status": "resource_unavailable", "job_id": job_id}
        return {"status": "inspected", "prepared": prepared, "inspected": inspected}

Register both activities and declare the required capability on the worker:

from durable_workflow import Worker

worker = Worker(
    client,
    task_queue="documents",
    workflows=[InspectDocumentWorkflow],
    activities=[prepare_document, inspect_document],
    capabilities=["fs:documents"],
)
await worker.run()

Start inspect_document_workflow on the documents task queue with [job_id] as input. The first activity lazily acquires the session; the second uses the same holder while its lease remains valid. max_concurrent_activities=1 bounds simultaneous activities in that session. Queue routing and capability checks still apply. These short leases/timeouts demonstrate bounded behavior; size them for your real work and heartbeat well before expiry.

After holder loss or lease expiry, allow_reacquire_after_failure=True permits another eligible worker to reacquire the session. Its local resource must be rebuilt. Already committed activity results replay, while uncommitted effects can repeat: use durable resource identifiers and idempotent external operations. A session does not migrate memory, files or open handles.

Explicit close and absolute TTL expiry are terminal for that session id. A later activity cannot reopen it and can remain unadmitted until its configured timeout is enforced. Run the Server's scheduler/maintenance role from the published deployment recipe; an API-only process is insufficient for timeout enforcement. The workflow handles exhausted activity failure with ActivityFailed and returns resource_unavailable; the application can then choose a fresh session and rebuild from the business input. This example does not promise an immediate session-closed exception or automatically reopen a terminal session.

For explicit holder lifecycle operations, use worker.worker_session(options) and its create(), renew() and close(reason) methods. Graceful worker shutdown closes its held sessions. See the shared lifecycle contract.

Cancellation is intentionally uncatchable by except Exception​

WorkflowCancelled and ActivityCancelled inherit from BaseException, not Exception. A generic except Exception: block in an activity body — or in code that awaits client.get_result() — will not catch them. This is deliberate: cancellation is a control-plane outcome, and silently swallowing it in a catch-all would let an activity report success after its workflow asked it to stop.

If an activity needs local cleanup when its task is cancelled, catch the class by name and re-raise. This does not resume the closed workflow for compensation:

from durable_workflow import ActivityCancelled, activity

@activity.defn(name="long_task")
async def long_task(items: list) -> dict:
    ctx = activity.context()
    try:
        for i, item in enumerate(items):
            await process(item)
            await ctx.heartbeat({"progress": i + 1})
        return {"done": True}
    except ActivityCancelled:
        await cleanup_partial_state()
        raise

This mirrors the standard-library precedent set by asyncio.CancelledError and KeyboardInterrupt.

Testing​

Workflow authors should be able to test workflow code without a running server or worker. The durable_workflow.testing module ships two entry points:

  • WorkflowEnvironment drives a workflow to completion in a single Python process against user-registered activity mocks.
  • replay_history and replay_history_file replay a captured production history against current workflow code and raise on any non-determinism.

Both entry points reuse the same durable_workflow.workflow.replay machinery the worker uses at runtime, so a workflow that passes its test harness behaves the same way under a real worker.

WorkflowEnvironment​

WorkflowEnvironment dispatches yielded workflow commands against registered mocks and auto-fires timers, side effects, and search-attribute upserts. Tests do not need a real clock, Redis, or server.

    def run(self, ctx, name: str):

        return greeting


def test_greeter_returns_activity_result() -> None:
    env = WorkflowEnvironment()

    result = env.execute_workflow(Greeter, "world")

The harness auto-fires the corresponding history event for each of these commands, so workflows do not block on wall-clock time inside tests:

Continue-as-new chains​

When a workflow returns ctx.continue_as_new(...), the harness appends a WorkflowContinuedAsNew event to the completing run, resets history, and starts a new run with the command's arguments. The return value of execute_workflow is the terminal result of the final link.

@workflow.defn(name="countdown")
class Countdown:
    def run(self, ctx, counter: int):
        yield ctx.schedule_activity("emit", [counter])
        if counter > 0:
            return ctx.continue_as_new(counter - 1)
        return {"final_counter": counter}


def test_chain_returns_final_run_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("emit", None)

    result = env.execute_workflow(Countdown, 3)

    assert result == {"final_counter": 0}
    assert env.run_count == 4
    assert [r.input for r in env.runs] == [[3], [2], [1], [0]]

When the chain switches workflow types, register the follow-on class first:

@workflow.defn(name="stage-one")
class StageOne:
    def run(self, ctx):
        yield ctx.schedule_activity("stage_one", [])
        return ctx.continue_as_new(workflow_type="stage-two")


@workflow.defn(name="stage-two")
class StageTwo:
    def run(self, ctx):
        return (yield ctx.schedule_activity("stage_two", []))


def test_chain_can_switch_workflow_type() -> None:
    env = WorkflowEnvironment()
    env.register_workflow(StageTwo)
    env.register_activity_result("stage_one", None)

    assert [r.workflow_type for r in env.runs] == ["stage-one", "stage-two"]

Replay testing against production history​

Use replay_history to regression-test a workflow change against a real history captured from the server. The replayer runs the current workflow code against the recorded event sequence and raises if it yields a different command than the one history recorded — the definition of a non-determinism bug.

async with Client("http://localhost:8080") as client:

A workflow that previously completed must still complete when replayed against the same history. If the workflow code changed in a way that diverges from the recorded sequence (reordered activity calls, removed branches, changed activity types), replay_history raises so the regression is caught in CI rather than in production.

replay_history_file is a convenience wrapper that reads a JSON file in either of two shapes: a top-level list of events, or a dict with an events key matching the get_history response shape:

Class-based replayer​

When one test pass replays histories for several different workflow types, or when the test should let the captured WorkflowStarted event decide which workflow to replay, use the Replayer class. Register every workflow class up front and call replay(...) once per captured history:

from durable_workflow import Replayer, ReplayOutcome

replayer = Replayer(workflows=[OrderWorkflow, RefundWorkflow])

outcome: ReplayOutcome = replayer.replay(
    history["events"],
    start_input=["order-42"],
    workflow_type="order",
)

# Type and start input inferred from a WorkflowStarted event in the history.
outcome = replayer.replay(history)  # history may be an events list or a
                                    # dict with an "events" key

for command in outcome.commands:
    # Inspect commands the replayed workflow would have emitted next.
    ...

Replayer(workflows=[...]) rejects an empty workflow set or a duplicate registration with ValueError. replay(...) raises ValueError when a history asks for a workflow type that was not registered, or when multiple workflows are registered and the caller does not provide workflow_type and the history does not include a WorkflowStarted event.

ReplayOutcome.commands is the same command list the functional replay_history helpers return; the class-based entry point exists so a test suite can share one registration across many histories.

Payload Codec​

Every payload that crosses the worker-protocol boundary is codec-tagged. Durable Workflow 2.0 has one public payload codec: avro. The Python SDK rejects JSON-tagged, unknown, and untagged durable payloads instead of selecting another decoder. See the Avro Value protocol.

Avro support is built in​

The pinned 2.0 SDK artifact pulls in fastavro as a runtime dependency, so every outgoing surface (start_workflow, signal_workflow, query_workflow, update_workflow, activity result encoding, schedule actions) emits Avro-tagged payloads through the optimized production path. There is no optional codec extra to install.

Fixed typed values​

The SDK explicitly selects named branches in the shared durable_workflow.protocol.Value schema. It does not JSON-encode the value inside Avro. Integers and doubles, strings and bytes, booleans and integers, and lists and maps therefore remain distinct across SDKs. The wire uses Avro single-object framing and the schema fingerprint; unknown fingerprints fail with unsupported_payload_schema.

Every client and worker surface works end-to-end on the Avro default:

  • Client starts, signals, queries, updates — start_workflow, signal_workflow, query_workflow, and update_workflow emit payload_codec = "avro" payloads through the fixed Value schema. A Python client can therefore drive workflows that PHP and other polyglot SDKs will replay, and vice-versa.
  • Activity worker — Avro-tagged activity arguments decode transparently. The worker encodes activity results as Avro so PHP, Python, and future SDK workers share one payload boundary.
  • Activity failures — fail_activity_task(..., details=...) sends failure.details as a {codec, blob} envelope. The server records the blob plus details_payload_codec, so diagnostic failure data from Python workers remains language-neutral in history exports and observability views.
  • Workflow worker history replay — Avro-tagged start input and activity result events are decoded during replay, so a Python workflow can participate in an Avro-coded run.
  • Workflow query tasks — Server-routed query tasks carry Avro-tagged workflow arguments, query arguments, and replay history. The worker returns the query result as an Avro envelope.

Running a Python activity worker against a v2 run​

No codec configuration is needed. The SDK validates payload_codec before decoding every claim, accepts only avro, runs the activity, and returns an Avro-tagged result. Any other tag fails closed with unsupported_payload_codec; the worker never sniffs or guesses the format.

    namespace="team-orders",
)

Set the namespace argument to whichever tenant namespace the shared server has provisioned for your team, and use the credentials issued for that namespace. The Server operator manages namespace creation; see the Server guide for details.

The same constructor supports a Cloud managed runtime. Use the namespace's Cloud-provided runtime URL and namespace value, set control_token to the client runtime credential, and set worker_token to the worker runtime credential. Cloud provisions the namespace; do not substitute a self-hosted Server address. See Cloud Managed Runtime.

Workflow list and history pages​

These published calls return one page, not an automatic complete read: await client.list_workflows(...) / await client.get_history(workflow_id, run_id, ...). Continue with the returned opaque token while keeping namespace, filters and selected workflow/run fixed; stop at the final null/empty token and handle page errors explicitly. A partial page is not a replay bundle. Use the SDK history-export API for offline replay. The published Python 2.9.0 client source defines the current parameters; no new iterator capability is implied.

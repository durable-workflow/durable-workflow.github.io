自托管部署

Durable Workflow v2 支持多种自托管形态。选择与你运维环境相符的最小路径，然后明确镜像、数据库、缓存、身份验证、就绪和升级契约。

本指南涵盖独立 Server 发行版。如果将 Laravel 软件包嵌入自己的应用中运行，请改用软件包安装和配置页面。Durable Workflow Cloud 是独立的托管服务选择，由 Cloud 运维运行时、持久化、放置和恢复；自托管 Server 绝不会接入 Cloud。参见 Cloud 托管运行时。当前 Cloud 契约是单区域托管运行时和恢复边界，不承诺多区域复制、自动区域故障转移或故障回切。

自托管 Server 发行版不捆绑或运维 Waterline。仅在需要其操作 UI 时单独部署 Waterline，并按照 Waterline 部署与监控指南连接到 Server 管理的命名空间。Cloud 则为托管命名空间提供 Managed Waterline。

生产恢复交付物​

称某个拓扑“生产就绪”，意味着发布该拓扑的恢复资料包，而不只是启动容器。将最新证据与部署命令保存在同一本运维手册中：

路径最低限度的已发布恢复资料包
单节点生产备份计划、固定镜像或摘要、env/配置快照位置、最大可接受恢复滞后，以及最近成功恢复演练时间戳和验证证据。
小型集群部署单节点资料包，加丢失一个 API 节点、一个 Worker 节点、调度器/维护运行器、Redis 或共享数据库的预期影响；恢复后的 Worker 重新注册步骤；当前发布记录的滚动升级或整体停机策略。
Kubernetes Helm chart集群资料包，加 chart 版本、values 修订、镜像摘要、集群特定 ingress 和密钥负责方，以及最近 chart 升级/回滚演练。
原始 Kubernetes 清单集群资料包，加宣布流量重新健康前必须恢复或重新应用的集群特定存储、密钥、ingress 和发布负责方。
单区域高可用评估（发布证据门槛关闭时由支持团队指导）集群或原始清单资料包，加托管数据库故障转移、托管 Redis 故障转移、API 节点丢失、Worker 丢失和调度器运行器重启的演练证据；每项都在单区域高可用契约发布的恢复目标内完成，且无已确认写入丢失。
主备多区域评估（支持团队指导）每区域资料包，加数据库复制和隔离设计、测得复制滞后、操作人员负责的 RPO/RTO、提升和回切手册，以及环境特定演练证据。

如果无法随时提供该资料包，在恢复契约成文并完成演练前应将环境视为预发布。操作运行边界定义这些资料包必须遵循的恢复顺序、验证过程和演练频率。

安全、数据与审计状况​

自托管 Durable Workflow 部署的大多数安全控制继承自你运维的环境。将以下事实与镜像标签、迁移计划和恢复证据放在同一发布或运维资料包中：

方面如实的发布说明
数据处理工作流参数、结果、历史、memo、搜索属性、可见性标签、命令上下文、审计行、异常消息和操作人员备注都可能包含客户应用数据。工作流 ID、搜索属性和标签是操作人员可见的元数据，不是密钥存储。工作流 ID 保持明文，不受负载编解码器保护。
加密每个生产 HTTP 接口均使用 TLS，并为 Server 的每个角色（包括迁移任务）配置数据库 TLS。静态加密来自数据库、对象存储、文件系统、队列、缓存和密钥管理器。工作流软件包与 Server 不自动加密每个负载字段。
合规开源软件包和自托管 Server 提供控制措施及审计证据，本身不构成合规认证。除非托管产品另有说明，SOC 2、HIPAA、PCI、ISO 或 FedRAMP 等声明属于你自己的合规计划。
审计日志工作流命令、计划审计事件、历史导出元数据和服务调用记录提供持久操作证据。除非自行添加相应组件，否则它们不是完整 SIEM、DLP 系统、不可变外部账本或法律保全系统。
支持本页记录按角色限定权限的凭据、TLS 终止、备份、恢复演练和范围明确的自助拓扑。除非公开文档另有说明，高级身份、mTLS 发布、私有网络、自定义策略引擎、提供商合规和定制拓扑审查均需支持团队指导。

必须明确网络状况：

  • Webhook 入口： 记录公开端点、身份验证方式、重放或幂等策略、超时、负载限制、受信代理头配置和密钥轮换计划。
  • Worker 到后端流量： 使用 TLS 验证、按角色限定权限的 Worker 凭据和命名空间头；Worker 跨越不可信网络时使用私有网络或 mTLS；轮换不得将操作权限授予 Worker 令牌。
  • 操作接口： 将 Waterline、独立 Server 操作 API、CLI 自动化端点和自定义管理面板置于已验证会话或按角色限定权限的服务凭据之后，为浏览器会话提供 CSRF 保护，并记录代理/TLS 边界。

已发布镜像​

自托管 Server 部署使用已发布镜像：

  • Docker Hub：durableworkflow/server:2.10.1
  • GitHub Container Registry：ghcr.io/durable-workflow/server:2.10.1
  • 摘要固定：durableworkflow/server@sha256:... 或 ghcr.io/durable-workflow/server@sha256:...

可变标签仅用于本地实验。生产 env 文件应固定具体版本标签或摘要，让升级和回滚步骤可审计。

本地开发和内部非生产环境​

需要无需源码、由 MySQL 和 Redis 支撑的栈时，使用已发布镜像 Compose 配方：

curl -fsSLO https://raw.githubusercontent.com/durable-workflow/server/main/docker-compose.published.yml

export DW_SERVER_TAG=2.10.1
export DW_AUTH_TOKEN=dev-token

docker compose -f docker-compose.published.yml up -d --wait

验证 API、就绪状态、集群发现和 Worker 注册：

curl http://localhost:8080/api/health
curl http://localhost:8080/api/ready
curl -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  http://localhost:8080/api/cluster/info

curl -X POST http://localhost:8080/api/worker/register \
  -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Namespace: default" \
  -H "X-Durable-Workflow-Protocol-Version: 1.0" \
  -d '{"worker_id":"compose-worker","task_queue":"compose","runtime":"python"}'

此路径适用于开发和内部预发布，但不是生产安全边界：示例使用一个兼容令牌、默认服务密码、本地命名卷，且没有 TLS。

单节点生产​

使用同一个 Compose 产物，将生产配置保存在版本控制之外：

DW_SERVER_IMAGE=durableworkflow/server:2.10.1
SERVER_PORT=8080
APP_ENV=production
APP_DEBUG=false

DB_DATABASE=durable_workflow
DB_USERNAME=workflow
DB_PASSWORD=replace-with-random-password
DB_ROOT_PASSWORD=replace-with-random-root-password

DW_AUTH_DRIVER=token
DW_AUTH_BACKWARD_COMPATIBLE=false
DW_WORKER_TOKEN=replace-with-worker-token
DW_OPERATOR_TOKEN=replace-with-operator-token
DW_ADMIN_TOKEN=replace-with-admin-token

使用该 env 文件启动：

docker compose --env-file durable-workflow.prod.env \
  -f docker-compose.published.yml up -d --wait

按生产服务运维主机：

  • 在 API 容器前的反向代理中配置 TLS、公开路由、请求日志和 IP 允许列表。
  • 不要公开暴露 MySQL 或 Redis。
  • Worker 使用 DW_WORKER_TOKEN，应用和操作流量使用 DW_OPERATOR_TOKEN，命名空间与管理工作使用 DW_ADMIN_TOKEN。
  • 每次镜像升级前备份 MySQL 卷，并定期备份。正常重启时应保留 Redis，但 MySQL 始终是持久工作流历史的事实来源。
  • 将确切 env 文件、镜像标签或摘要和数据库备份保存在一起，用于恢复。

升级顺序：

  1. 备份 MySQL，记录当前镜像引用。
  2. 仅修改 DW_SERVER_IMAGE 或 DW_SERVER_TAG。
  3. 拉取新镜像。
  4. 运行 docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml up -d --wait。
  5. 切换外部流量前，确认 /api/ready、/api/cluster/info 和 Worker 注册。

Server README 的官方镜像 + Compose部分维护最新命令级 Compose 示例。

小型集群部署​

小型集群是单节点模型的适度扩展。已验证自助契约刻意保持狭窄：

  • 在负载均衡器后运行 2 至 3 个无状态 API 容器。健康、就绪、集群发现、Worker 注册、工作流任务轮询和完成均必须无需粘性会话即可工作。
  • 使用一个共享外部 MySQL 或 PostgreSQL 数据库存储持久历史。SQLite 仅限单节点，不是集群持久化后端。
  • 使用共享 Redis 承载缓存、长轮询唤醒信号、查询任务队列锁、任务队列准入锁和队列状态。无 Redis 多节点模式不是受支持集群契约。
  • 发布期间检查每个 API 节点的 GET /api/cluster/info。topology.current_shape 应保持 standalone_server，topology.current_roles 应包含 api_ingress、control_plane、matching 和 history_projection，独立 Server 节点的 topology.execution_mode 应保持 remote_worker_protocol。用 topology.matching_role 确认实际部署的匹配路径：默认节点报告 queue_wake_enabled: true、shape: "in_worker" 和 wake_owner: "worker_loop"；专用匹配发布将设置 DW_V2_MATCHING_ROLE_QUEUE_WAKE=0 的节点改为 queue_wake_enabled: false、shape: "dedicated" 和 wake_owner: "dedicated_repair_pass"。同一块还应继续声明预期的 task_dispatch_mode、partition_primitives 中冻结的路由轴和当前 backpressure_model。拓扑清单的逐字段含义参见 Server 角色拓扑。
  • 独立于 API 节点扩缩外部 SDK Worker。Worker 可运行在单独主机或进程上，但应连接负载均衡 API 端点，而非固定到一个节点。
  • 对保护租户、外部 API、数据库池或其他共享下游依赖的队列，配置任务队列准入。
  • 恰好运行一个调度器或维护进程，负责计划评估、活动超时执行和历史清理。
  • 每次发布运行一次 bootstrap/迁移，然后才让新 API 和 Worker 容器接收流量。
  • 为当前发布选择方式：整体停机（排空 Worker、停止调度器/维护、替换 API 节点、运行 bootstrap/迁移，再重启 Worker 和调度器），或在全部保证成立时使用滚动升级。
  • 将数据库和 Redis 视为主要故障域。Server 容器可替换，持久化和协调层不可随意替换。

已发布自助配方从 standalone_server 形态开始，虽然集群发现也将 split_control_execution 列为受支持产品拓扑。应将它视为角色分配不同的同一契约，而非第二个 Server 产品。以后试点更明确的角色拆分时，仍读取 /api/cluster/info 的 topology.current_shape、topology.current_roles 和 topology.matching_role，不要从主机名或容器名推断职责。Server 角色拓扑集中解释角色分配和迁移路径。

每个 API 节点应使用相同身份验证令牌或签名密钥、应用版本、工作流软件包版本、负载编解码器配置、数据库连接和 Redis 连接。为每个 API 节点分配唯一 DW_SERVER_ID，让集群发现和日志可以区分节点。

不受支持的边界必须明确：SQLite 集群、无 Redis 多节点模式、以重复调度器作为稳态拓扑、双活多写数据库、自托管无人值守区域故障转移，以及宽泛的“五个九”或“零停机”SLA 承诺，需要另行验证或支持团队指导设计后才能依赖。主备多区域指南也属于支持团队指导的评估材料，参见下方主备多区域。单区域高可用故障转移，即区域内的托管数据库故障转移、托管 Redis 故障转移、API 节点丢失、Worker 丢失和调度器运行器重启，在发布证据门槛通过前属于支持团队指导的评估契约；下方单区域高可用与故障转移说明引擎恢复目标、故障转移时的就绪规则和开放门槛所需证据。

团队已明确 VM、网络、数据库、缓存、备份和负载均衡模型时，此路径可自助执行。需要协助确定这些边界、容量、发布顺序或恢复流程时，则由支持团队指导。

Worker 长轮询的超时预算​

健康的 Worker 轮询可能一直保持静默，直到服务端等待结束。Worker HTTP 客户端、出口代理、服务网格、公网负载均衡器、ingress 以及 API 前的每一级反向代理，都必须容许这段静默。Worker 轮询经过共享 API ingress；单独部署 matching 角色不会绕过这些节点。

预算限制的范围
服务端轮询时长等待任务到返回空响应的时间。请求中的 timeout_seconds 覆盖 DW_WORKER_POLL_TIMEOUT。该变量是省略请求字段时的默认值，不是 SDK 轮询的上限。协议允许最多 60 秒。
客户端连接 / 连接池超时建立连接或从连接池获取连接。这些阶段不必持续整个静默轮询时段。
客户端读取 / 总超时等待响应字节，或在传输层支持总时限时约束整个操作。应在服务端等待时长之外留出连接、调度和响应余量。读取超时可能只计算数据块之间的静默，而非整个请求。
中间节点 idle / upstream read / 请求超时每一跳的所有活动请求限制，都必须容许正常静默轮询及其响应。请求之间的空闲连接 keepalive 是另一种限制。
关闭 / 调用方截止时间Worker 关闭预算和调用方或查询的原始权限期限仍是硬性边界。在边界内取消或排空，不要因代理或重试延长查询期限。

请核对已安装 SDK 的计算方式。下述已验证 Python 版本对正数等待最多请求服务端等待 60 秒，并为 HTTP 各阶段至少增加五秒余量。Worker 默认轮询为 35 秒，通常对应 40 秒的 HTTP 阶段超时。30 秒的中间节点读取限制因此可能中断正常默认轮询。PHP 和 Rust 有各自的默认值和重试策略；Python 的余量或 gRPC keepalive 配置都不是通用规则。参见 PHP、Python、Rust SDK 指南及任务 matching 参考。

PHP SDK 3.2.0 的普通控制平面 Client 调用不提供默认 HTTP 总期限，见已验证的 PHP #203 超时缺口。请为这些调用配置有界 HTTP 客户端，并保留调用方原始截止时间。Worker 轮询超时并不限制所有 SDK 请求。

PHP SDK 3.4.0 或更新版本为 SDK 自有传输的普通控制 HTTP 请求增加默认 60 秒总期限；可用至少 0.001 秒的有限数值 requestTimeoutSeconds 配置。这些 SDK 自有请求的超时携带 reason=request_timeout 和 status=0。SDK 只尝试一次：超时的变更可能已经被接受，重发前应检查原始身份及结果。注入的客户端/传输保留自身超时策略，不能与此选项同时使用。每请求的期限不替代 worker 长轮询、payload 传输或工作流/调用方期限。请检查 composer.lock：此最低版本不改变所选安装组合。参见 HTTP 客户端配置 和普通安装 3.4.0 验收。

已验证的短轮询示例​

隔离验证使用已发布的 Python SDK 2.9.0、PHP Server 2.11.0 和 Nginx 1.30.5，任务队列为空。两个验证单元均保持 3 秒 SDK 轮询、8 秒 HTTPX connect/read/write/pool 超时，以及 10 秒调用方外层期限。仅改变 Nginx 的 upstream 读取超时：

中间节点配置实际响应
proxy_read_timeout 1sNginx 等待 upstream 响应头约一秒后返回 HTTP 504，SDK 抛出 ServerError。
proxy_read_timeout 8s正常静默轮询约三秒后返回 HTTP 200、task: null 和 poll_status: empty。

两个单元都故意将服务端默认等待设为一秒，请求显式指定的三秒仍然生效。HTTP 重试限制为一次尝试，以暴露首次失败。这是功能性超时示例，不是容量或生产规模测量。#267 验证记录包含精确镜像、请求和代理日志。

使用 Nginx 时，在现有 Worker 轮询 location 中设置合适的 upstream 读取预算。下面的八秒仅属于这个三秒轮询示例：

proxy_connect_timeout 2s;
proxy_read_timeout 8s;

Nginx 在两次 upstream 读取之间计算 proxy_read_timeout。HTTPX 区分连接、读取、写入和连接池超时，各阶段八秒并非整个请求八秒。需要总期限时，另设明确的外层期限。其他代理和提供商使用不同名称与语义；请用实际 SDK 验证完整路径。调大一处 ingress 限制，不能修复另一跳更短的限制。

重启 Worker 前先诊断响应​

  • 正常空轮询： runtime 成功响应但没有任务。已验证版本的原始响应为 poll_status: empty。正常继续轮询。
  • 中间节点断连： 传输异常、连接重置或代理 502/504，可能在服务端正常等待结束前发生。结合 SDK 错误、耗时与代理/upstream 日志判断。readiness 健康、后续轮询成功，都不排除中间节点配置错误。
  • runtime 不可用： 检查结构化原因及数据库、缓存、准入的 readiness 检查。网关 HTML 错误页不是 runtime 的类型化拒绝。
  • 命名空间或轮询准入拒绝： 检查结构化原因、命名空间/队列及重试延迟，包括 HTTP 429。调大 idle 超时不会增加准入容量，也不会修复授权。

Worker 重连不证明原代理配置健康。确认轮询和任务完成是否实际持续；失败持续时保留错误类别、队列、时间和频率。偶发断连本身不要求重启进程。Python 客户端还可能在 HTTP 超时重试后合成 poll_status: timeout；单凭这个值，不能证明 runtime 的空响应穿过了代理。请区分传输重试、活动重试、运行截止时间与查询权限期限。

SQL 连接预算​

增加 API 副本或在滚动升级中让新旧进程重叠运行前，先规划数据库会话预算。 即使 CPU 仍有余量，数据库也可能达到连接上限。这与写入/commit 延迟、HTTP 请求容量和保留数据增长是不同的限制。

统计所有使用 SQL 的进程​

已发布的 PHP Compose 部署包含以下潜在 SQL 客户端：

角色统计对象
API每个可能使用 SQL 的并发 PHP 请求进程，包括就绪检查、运维请求和等待中的轮询。已发布的 Apache prefork 配置允许每个 API 容器有 24 个请求进程。这是 HTTP 进程上限，不是 SQL 连接池，也不是已测得的 24 个开放会话。
Laravel 队列 Worker每个 php artisan queue:work 进程。已发布的 Compose 示例运行一个；增加 Worker 容器就会增加进程。它们与外部 SDK Worker 不同。
调度器/维护并发 PHP 命令，而不只是调度器容器数量。Compose 调度器依次执行计划评估、修复、活动超时和清理命令，所以普通循环同一时间只有一个命令活动。保持调度器单实例规则。
初始化和运维工具可能与部署重叠的迁移/初始化命令、投影重建、保留任务、备份、监控和交互式 SQL 客户端。主动并发的命令要分别计数。
SDK 客户端和 Worker通常不直接占用 Server 数据库会话，因为 PHP、Python 和 Rust 服务模式 SDK 使用 HTTP。只有活动代码或其他应用代码确实连接该数据库时才增加连接数。

统计每个进程使用的不同 SQL 连接句柄，而不只是容器或主机名。Laravel 默认连接和 workflows.storage.connection 可能共享一个已配置的连接名。不同的存储连接名、数据库队列/缓存/会话连接， 或独立的读/写/直连句柄，都可能打开额外会话，即使连接的是同一个数据库端点。Redis 连接不属于 SQL 会话。 检查实际生效的缓存配置及各角色真正使用的连接名。

自定义 FPM 部署应统计执行请求的 PHP-FPM 子进程，而不是 nginx 或 Apache event 线程。 自定义 Octane 部署应清点请求 Worker、任务 Worker 和真实数据库客户端。 不能把 Apache 的 24 个进程直接当作这些前端的连接池大小。同步长轮询等待时仍占用 PHP 执行进程， 也可能保留数据库会话。不能自动将空闲 HTTP 轮询按零 SQL 用量计算。

保守的滚动升级预算示例​

这是规划示例，不是实测容量。假设数据库允许 120 个客户端会话，其中其他应用使用十个， 为恢复/管理预留十五个，则本部署可用 95 个。假设队列和缓存使用 Redis，每个 PHP 进程最多使用一个 SQL 句柄。

峰值重叠计算计划会话数
API 副本，包含滚动发布时增加的一个副本(2 + 1) × 24 × 172
Laravel 队列 Worker2 × 12
单实例调度器/维护命令1 × 11
初始化/迁移1 × 11
备份、监控和其他获准工具明确分配4
部署小计80
部署内尚未分配的余量95 − 8015

按这些假设，第四个 API 副本会使小计增加到 104，超过分配的 95 个会话。 如果每个 API 进程使用两个 SQL 句柄，仅三个 API 副本就需要 144 个会话。 变更存储连接、Worker 数量或滚动发布的额外副本数时，都要重新计算。 应降低进程/副本上限或分批替换，不要假定数据库能承担重叠运行。提高 max_connections 也需要评估数据库内存和工作负载。

观察并执行预算​

  1. 记录实际连接上限、其他客户端和预留恢复访问。明确设置 API 副本数、进程数以及滚动发布额外副本数的上限。 包含新旧队列 Worker 和运维工具同时运行的情况。
  2. 在使用准确已发布镜像和配置的隔离副本中，采样空闲、轮询等待、真实任务执行和有界新旧重叠时的会话。 包含空闲会话和监控连接自身。PostgreSQL 提供 pg_stat_activity，MySQL 提供 information_schema.PROCESSLIST。使用权限范围适当的监控角色，不要导出 SQL 文本或负载。
  3. 按应用用户/数据库比较实际会话数与每进程预算。短时采样只能验证该测试环境的假设，不能证明饱和上限或保证所有负载。
  4. 除会话余量外，同时观察连接拒绝、事务/commit 延迟、锁等待、占用中的 HTTP 请求和存储增长。 仅就绪正常不能证明滚动发布有可用余量。
  5. 接近上限时，减少重叠数量，或先排空并退役一组旧 API/Worker，再启动替代组。 保留恢复访问，只在计划的迁移窗口执行初始化。安全重叠无法容纳时，使用文档中的全停机升级方式。

任务队列准入限制特定的分发和租约活动。 DW_WORKER_LONG_POLL_MAX_CONCURRENT 和 DW_QUERY_TASK_POLL_MAX_CONCURRENT 限制每个节点等待中的轮询。 它们都不是全局 SQL 会话、数据库字节数或 commit 延迟上限。也要为完成提交、心跳、运维请求和健康检查保留容量。

以直接连接可写数据库端点为基线。连接代理必须按准确的 Server 版本、连接池模式，以及预处理语句、事务边界、会话状态和锁设置进行验证。PgBouncer 事务池需要已修复的 Server 2.9.8 或更高版本。 已发布 2.9.8 的验收记录验证了 PostgreSQL 16.15 与 PgBouncer 1.26.1：直接连接 PostgreSQL、会话池，以及 max_prepared_statements=0 或 max_prepared_statements=200 的事务池。这表示最低兼容版本和准确的已测配置，并非要求固定到最新版本，也不保证容量；其他组合需单独验证。接纳流量之前，请针对所选端点执行正常的 server-bootstrap 初始化。

GET /api/ready 会执行绑定参数的数据库读取（bound_read_query）及已配置的就绪检查，并明确保留“写入容量未验证”的边界。TCP 连接、迁移或就绪响应成功，不能证明所有工作流 SQL 操作均可用或提交容量充足。只读副本不能替代负责认领和持久状态转换的权威写入节点。

适用于 Kubernetes 的 Helm chart​

Server 仓库负责 chart 源码和发布指南。从 OCI 镜像仓库安装已发布 chart：

helm install durable-workflow \
  oci://ghcr.io/durable-workflow/charts/durable-workflow \
  --version 0.2.3 \
  --namespace durable-workflow --create-namespace \
  -f my-values.yaml

values 文件必须指向外部 MySQL/PostgreSQL 和 Redis，通过已有 Kubernetes Secret 提供生产凭据，并为环境配置 ingress/TLS。Chart 不会创建持久化存储或提供商托管基础设施。为了可复现部署，请按摘要固定 Server 镜像。

选择 Chart 版本​

每个 Chart 发布版都会在 Chart.yaml 的 appVersion 中记录其测试过的 Server 镜像；Chart 与 Server 的版本号彼此独立。所选兼容组合使用 Chart 0.2.3 和 Server 2.10.1，与表格和安装命令共享同一份发布元数据。已发布 OCI/软件包的验证记录核实的是这个组合，并非一次新的 Kubernetes 安装。

对于其他 Server 版本，请检查候选已发布 Chart 的 Chart.yaml（当前所选 Chart 源码可作为示例），选择 appVersion 与目标 Server 一致的确切 Chart 版本。阅读所选版本的 UPGRADING 说明，包括升级跨越的每个 Chart 版本。不要根据 Server 版本推算 Chart 版本，也不要从当前源码选择尚未发布的 Chart。

覆盖 image.tag 会更换镜像，却不会改变 Chart 记录的 appVersion。这会形成一个自定义 Chart/镜像组合，直到该组合单独完成渲染清单、初始化、滚动部署和运行时验证。升级计划应包含常规数据库备份和回滚边界；成功渲染清单并不能证明部署可用。

已发布历史中存在一个例外：Chart 0.2.2 在 Chart 补丁版本号下跨越了 Server 的次版本。后续已发布的更正说明承认了该例外，并恢复所述的次版本策略。历史版本保持不变；这条说明不会选择后续 Server/Chart 组合。

在 Kubernetes 上运行 SDK Worker​

将应用的 Worker 与 Server 的 Laravel 队列 Worker 分开部署。构建包含已注册 PHP、Python 或 Rust 处理函数及锁定 SDK 依赖的镜像。使用 exec 形式的 entrypoint，让 Worker 进程能够接收 SIGTERM。将下方镜像替换为该构建不可变的 digest。

对于同一集群内的 Worker，使用 Server Service 的实际名称、命名空间和端口。原始清单公开 http://durable-workflow-server.durable-workflow.svc.cluster.local:8080。Helm 发布可能使用不同的 Service 名称。集群外的 Worker 需要可访问的 ingress 或负载均衡器 HTTPS URL，并正常验证证书。按超时指南协调长轮询和传输时间预算。

使用现有 Worker 凭据，在 Worker Pod 所属的 Kubernetes 命名空间中创建 Secret。不要把令牌写入清单或镜像。Server 命名空间是产品中的独立边界，与 Kubernetes 命名空间不同。

kubectl -n durable-workflow create secret generic orders-worker-auth --from-literal=token="$DW_WORKER_TOKEN"

将其保存为 orders-worker.yaml。这些环境变量名属于应用配置：entrypoint 必须将值传给 SDK 客户端和 Worker。为每个同时运行的进程分配独立 worker ID，并注册所配置队列的处理函数。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-worker
  namespace: durable-workflow
spec:
  replicas: 2
  selector:
    matchLabels:
      app: orders-worker
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: orders-worker
    spec:
      automountServiceAccountToken: false
      terminationGracePeriodSeconds: 75
      containers:
        - name: worker
          image: registry.example.com/acme/orders-worker:release-id
          env:
            - name: DW_SERVER_URL
              value: http://durable-workflow-server.durable-workflow.svc.cluster.local:8080
            - name: DW_NAMESPACE
              value: default
            - name: DW_TASK_QUEUE
              value: orders
            - name: DW_WORKER_ID
              valueFrom:
                fieldRef:
                  fieldPath: metadata.uid
            - name: DW_WORKER_TOKEN
              valueFrom:
                secretKeyRef:
                  name: orders-worker-auth
                  key: token
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: "1"
              memory: 512Mi

应用 Deployment 并等待发布完成：

kubectl apply -f orders-worker.yaml
kubectl -n durable-workflow rollout status deployment/orders-worker

副本数和资源值只是起始示例，不保证容量。根据实际任务时长、内存使用、下游限制和 Worker 准入预算调整。Deployment 可用并不能证明 SDK 已注册或已完成有效工作。先验证新鲜的 Worker 注册、预期构建和队列，再启动并完成一个有代表性的工作流。仅在 Kubernetes 中运行不会自动为 SDK Worker 提供 HTTP 健康端点。如果应用有自己的探针，应使用该探针，不要把 Server 健康状态用作 Worker 存活检查。

传递 SIGTERM 并等待清理​

SDKWorker 进程关闭
PHP安装 pcntl 并使用受管理的 Worker::run() 循环。信号处理函数请求关闭，活动同步任务到达边界后才执行受管理的清理和注销。围绕 tick() 的自定义循环不提供该生命周期。参见 PHP 优雅关闭。
Python将 SIGTERM 接到同一 Worker 的关闭路径，同时 await Worker.stop() 及其运行任务。显式设置 shutdown_timeout。已接受工作共享该排空期限。取消 await 无法强制停止正在运行的同步线程，未确认停止仍是错误。使用独立进程与信号连接示例和生命周期契约。
Rust向 Worker::run_until(...) 传入一个在收到 Unix SIGTERM 时完成的 future，并 await 其结果。只等待 Ctrl-C 的 future 无法处理 Pod 终止信号。异步处理函数必须让出执行权，并单独限制阻塞工作。参见 Worker::run_until。

在 terminationGracePeriodSeconds 中，为已安装 SDK 的轮询、已接受任务的关闭，以及 HTTP、会话和注销清理留出足够时间。必须根据应用的实际上限核对示例中的 75 秒。Kubernetes 将任何 preStop hook 计入同一宽限期，并在期限结束后强制停止剩余进程。仅执行 sleep 的 hook 不会要求 SDK 排空工作，也不会延长其期限。参见 Kubernetes Pod 终止流程。

在空闲时和执行有时间上限的工作时演练终止。将清理错误、保留的注册或强制结束视为未完成关闭。替代 Worker 根据已记录的租约、重试和期限继续持久工作。停止 Pod 不会取消工作流，也不会撤销外部副作用。更换构建前，请遵循 Worker build ID 发布流程，保留其中的兼容性、重放和回滚检查。

单区域高可用与故障转移​

单区域高可用故障转移当前是在小型集群和原始 Kubernetes 形态之上叠加的尚未验证、由支持团队指导的候选契约。它面向引擎设计上能在单一区域内承受的故障模式：托管数据库故障转移（RDS Multi-AZ、Aurora 集群故障转移、Cloud SQL HA、Patroni 提升等）、托管 Redis 故障转移（Sentinel、Elasticache 复制组故障转移、Memorystore HA 等）、API 节点丢失、Worker 丢失，以及调度器/维护运行器重启。跨区域主备恢复是另一种由支持团队指导的评估，参见下方主备多区域。

预期契约包含引擎行为、就绪规则、各事件恢复目标、防脑裂规则和演练验收测试，位于 Workflow 库的 docs/deployment/ha-failover.md 和独立 Server 的 docs/ha-failover-validation.md。本节是这些文档的公开说明。

发布证据状态​

当前文档所述公开 Server 发布尚无链接的通过确切发布验证结果。记录的已发布镜像尝试在 topology_start 阶段等待 API 就绪时停止，尚不能建立任何故障矩阵或恢复边界声明。不要把运行器存在、场景清单或某个部署的演练，当作已发布镜像通过完整矩阵的证据。因此单区域高可用仍由支持团队指导。

只有无需源码的运行对镜像、运行器和 Compose 拓扑使用文档中的同一确切 Server 发布，并发布满足以下条件的 single-region-failover-result.json 后，才允许使用自助表述：outcome: "pass"、runner_blocked: false、phase_outcomes 每项均为 status: "pass"、每个恢复边界判定通过，以及公开单区域故障转移场景清单中每个必需场景均有证据。该公开通过结果必须从本状态节链接，并指定与 durableworkflow/server:2.10.1 相同的 Server 镜像。在所有条件满足前，下述恢复边界是评估目标，而非已发布镜像验证声明。

候选拓扑​

部署符合小型集群或原始清单形态，且操作人员保持三条规则时，预期高可用契约适用：

  • 始终只有一个可写工作流数据库端点。 允许托管故障转移（RDS Multi-AZ、Aurora 集群故障转移、Cloud SQL HA、Patroni 等），前提是原主节点重新接入前先隔离它：撤销写入用户、用 read_only=on 降级、断开复制，或从已知正常快照恢复。连接代理必须保留 Server 使用的数据库语义，并通过准确版本、模式和设置的验证。PgBouncer 事务池的版本要求与已测模式见 SQL 连接预算。
  • 每次只有一个 Redis 端点，并记录提升路径。 允许托管 Redis 故障转移（Sentinel、Elasticache 复制组故障转移、Memorystore HA 等）。Redis 是加速层，不是正确性基础，因此 Redis 故障转移是延迟事件，绝非正确性事件。
  • 始终只有一个调度器/维护运行器。 编排器（deploy.replicas: 1 的 Compose 服务、受主机级租约保护的 systemd unit，或 replicas: 1 且 RollingUpdate.maxSurge: 0 的 Kubernetes Deployment）负责在重启时保持单实例不变量。重复调度器运行器作为稳态拓扑不在此契约内。

各事件行为与恢复目标​

预期引擎契约为每类事件定义有界恢复目标。发布证据门槛关闭时，它们不是已发布镜像保证。操作人员观察到的实际恢复时间，是引擎目标加托管服务自身的提升延迟。

事件候选引擎行为恢复目标（基础层/运行器恢复后）
托管数据库故障转移写入返回错误，不会悄悄缓冲。读取返回错误。全部 API 节点和调度器的 /api/ready 失败。不丢失已确认工作。一次连接池重连，加一个 task_repair 周期（默认 3 秒），再加进行中轮询者的一次长轮询超时（默认 30 秒，最大 60 秒）。
托管 Redis 故障转移唤醒信号丢失 → 发现回退到长轮询超时。加速层健康检查进入 warning，不是 error。/api/ready 通常保持正常。Redis 客户端重连间隔。
API 节点丢失（N 个中的 1 个）负载均衡器在其就绪检查间隔内移除故障节点。发往该节点的进行中请求在 LB 失败，由客户端重试。负载均衡器就绪检查间隔（操作人员控制，通常 5–10 秒）。
Worker 丢失故障 Worker 持有的任务暂停到租约过期。其他 Worker 继续领取自己的任务。租约过期（活动任务为 5 分钟），加一个 task_repair 周期。
调度器/维护重启计划触发、活动超时执行和历史清理暂停。重启后下一个 tick 全部恢复。由于运行器是单实例，不会重复触发。编排器重启延迟，加一个调度器 tick。

负载均衡器、就绪和流量切换规则​

API 节点前的负载均衡器是故障转移期间流量准入的唯一决策点：

  • 将负载均衡器连接到 GET /api/ready，不要仅用 /api/health。/api/health 仅证明进程能提供 HTTP 服务；/api/ready 报告数据库连接和已配置的就绪检查，包括 Redis 唤醒加速是健康还是降级。它不会验证每种工作流 SQL 操作或写入容量。数据库中断时，每个节点的 /api/ready 都会正确失败；负载均衡器必须容忍全部不可用状态，不能回退到过期的“上次已知正常”节点列表。
  • 使用 5–10 秒检查间隔，以及连续失败 2–3 次的移除阈值。
  • 不要求粘性会话；小型集群冒烟测试证明外部 Worker 能在 server-a 轮询并在 server-b 完成。
  • 仅 Redis 故障转移期间，只要基于数据库的持久路径可用，每个节点仍保持就绪。加速层降级表现为 checks.cache.status=warning 和 checks.cache.degraded_capability=long_poll_wake_acceleration；不要配置负载均衡器因该警告移除节点。

基础层恢复后，建议按以下顺序验证：等待至少一个节点的 /api/ready 返回 200，通过负载均衡器使用 admin 令牌 curl /api/cluster/info 确认拓扑清单，通过负载均衡端点为探测 Worker 发出 POST /api/worker/register，在编排器中确认恰好一个调度器运行器存活，然后恢复外部流量。

运行确切产物演练​

Server 发布包含可复用的基线演练，目标是不从检出源码构建产品代码也能执行完整故障矩阵。运行器和 Compose 拓扑必须来自与 Server 镜像相同的发布标签；不要混用持续变化的默认分支检出和任意镜像。在具有 Docker Engine、Docker Compose v2、Python 3.11 或更新版本，以及公开镜像仓库访问权限的干净主机上运行：

export DW_SERVER_RELEASE=2.10.1
git clone --depth 1 --single-branch --branch "$DW_SERVER_RELEASE" \
  https://github.com/durable-workflow/server.git "server-$DW_SERVER_RELEASE"
cd "server-$DW_SERVER_RELEASE"
export DW_SERVER_IMAGE="durableworkflow/server:$DW_SERVER_RELEASE"
scripts/conformance/single-region-failover-published-artifacts.sh \
  --result-dir ./failover-result

此路径刻意从同一发布变量派生检出和 DW_SERVER_IMAGE。不要单独覆盖镜像；若要选择不同发布，克隆前修改 DW_SERVER_RELEASE。运行器要求具体的公开 Server 标签或摘要，拉取每个支撑镜像，将全部运行时镜像解析为仓库摘要，并拒绝 Compose build 节、产品源码绑定挂载、本地或滚动 Server 引用。它在一个 nginx 端点后启动恰好两个 API 节点、一个 MySQL 数据库、一个 Redis 服务和一个调度器/维护运行器。

生成的 single-region-failover-result.json 使用 schema durable-workflow.v2.single-region-failover.result。它记录确切产物和工具版本、规范化拓扑、就绪转换、测得恢复时间及边界判定、工作流/运行/任务/计划身份，以及跨节点完成、API 节点丢失、数据库中断、Redis 中断、Worker 租约丢失和单实例调度器重启的重复/丢失断言。外部运行器通过 GET /api/cluster/info 的 single_region_failover_contract 发现调用方法和公开场景清单。

只有通过上方发布证据门槛的结果，才验证已发布镜像对引擎可见中断与恢复的行为。失败、部分完成或 runner-blocked 结果都是诊断证据，不是验证。即使基线通过，也不能把本地 MySQL 或 Redis 容器重启当作云提供商提升机制的证据。宣称托管服务高可用前，应在基线结果旁保留提供商原生提升、隔离、RPO 和耗时证据。

恢复资料包补充项​

宣称符合此契约的小型集群或原始清单部署，必须依据操作运行边界扩充恢复资料包，为每类事件提供演练证据：

  • 托管数据库故障转移在上述有界恢复时间内完成，无已确认写入丢失；
  • 托管 Redis 故障转移不导致负载均衡轮转抖动，不丢失任何已确认工作，并报告 checks.cache.status=warning，降级能力为 long_poll_wake_acceleration；
  • API 节点丢失由负载均衡器在配置的就绪检查间隔内吸收，无已确认写入丢失；
  • Worker 丢失时，持久运行实例跨越租约过期被保留，在配置修复边界之后重新领取，并恰好完成一次；
  • 调度器运行器在另一主机重启，不触发重复计划，也不让任何计划超过 next_fire_at 加一个 tick 仍未评估。

发布证据门槛关闭时，即使部署自身演练通过，每个部署仍需支持团队指导。公开的全阶段通过结果开放发布门槛后，部署也只有将环境特定演练证据记录进操作人员恢复资料包，并按操作运行边界公布的频率刷新，才成为本契约下的自助部署。

不受支持高可用声明的边界​

单区域高可用契约刻意保持狭窄。以下内容仍不在其内，继续需要支持团队指导设计；拓扑本身属于产品风险：

  • 双活多写数据库拓扑；
  • 自托管拓扑的主备多区域及自动或无人值守区域故障转移（下一节保留评估指南）；
  • 同步跨区域数据库复制（RPO=0）；
  • 以重复调度器/维护运行器作为稳态拓扑；
  • 将引擎强制的区域固定任务队列作为路由轴；
  • 超出已发布 chart 打包契约的提供商特定托管 Kubernetes 验证；
  • 超出上述有界恢复时间的宽泛“五个九”或“零停机”SLA 承诺。

契约是在指定事件期间的有界恢复，不是依赖操作人员数据库、网络和编排器选择的可用性承诺。没有专门验证，自托管部署的营销或 SLA 表述不得越过此边界。

主备多区域​

主备多区域是支持团队指导的评估指南，不是受支持 2.0 运行边界内已验证的自助契约。用本节审查候选架构，并在支持团队协助下构建环境特定演练，再在生产中依赖它。每个区域仍从文档中的单节点、小型集群或原始 Kubernetes 路径开始，但这些单区域契约并不证明跨区域复制、故障转移、回切、RPO、RTO 或脑裂行为。更深入的设计材料，包括数据权威、复制假设、命名空间/任务队列/Worker 行为、故障转移和回切手册、隔离及一致性/延迟权衡，位于 Workflow 库的 docs/deployment/multi-region.md 和独立 Server 的 docs/multi-region-validation.md。

待评估的候选形态：

  • 一个主区域运行已验证单节点或小型集群契约：负载均衡器后的 API 容器、用作可写持久数据库的共享外部 MySQL 或 PostgreSQL、共享 Redis、恰好一个调度器/维护运行器和外部 Worker。
  • 一个备用区域保存异步复制的工作流数据库备库、可选备用 Redis，不运行调度器/维护进程，并可预先配置零个或多个 API/Worker 容器，在提升前保持空闲。
  • 区域故障转移是明确的操作人员工作：停止发往故障区域的写流量，根据公布 RPO 确认复制状态，提升备用数据库，在新主库执行发布要求的迁移，在新主区域启动单实例调度器/维护运行器，切换 Worker 端点，切换外部流量，重建派生投影。没有自动跨区域切换。
  • 原区域恢复服务后，故障回切按相反方向执行同样序列；恢复的原主库在重新作为备库接入前必须隔离（撤销写入用户、以 read_only=on 降级、断开复制，或从已知正常快照恢复）。

数据权威和复制假设：

  • 工作流数据库是唯一持久事实来源，且受区域约束：任何时刻恰好一个区域写入。备用区域数据库在提升前是只读副本。恢复点目标（RPO）是异步复制滞后；恢复时间目标（RTO）是操作人员执行手册所需时间。
  • Redis 是区域本地加速。唤醒信号、查询任务队列锁和准入锁不会跨区域传播，也不应预期其传播。每个区域运行自己的 Redis；备用区域缓存可由操作人员选择冷或热状态，正确性不依赖其跨故障转移保留。
  • 可见性由主区域数据库提供。先提升，再读取。

命名空间、任务队列和 Worker 注册行为：

  • 命名空间和任务队列存储在工作流数据库中，提升后保持最近复制提交时的状态。引擎不按区域对其分区。
  • 新主区域 Worker 在提升后向本地 API 端点注册。故障区域已有注册仍留在数据库中，通过正常 Worker 过期路径失效。
  • Build-id 发布和部署生命周期状态存于工作流数据库，因此故障转移后仍保留。

稳态下的一致性与延迟权衡：

  • 工作流启动、信号和更新向主区域数据库提交；延迟等于主区域提交延迟，故障转移撤销权威期间会被拒绝。
  • 工作流任务和活动任务投递遵循主区域内单区域加速契约：Redis 健康时为亚秒级，否则按持久轮询周期进行。
  • 计划由主区域单实例调度器触发，无调度器运行时暂停；提升后从持久计划行恢复触发。
  • 可见性读取仅在主区域内保证写后读；引擎不提供跨区域读己之写或 RPO=0。

灾难恢复边界必须明确：候选设计不能替代备份或证据。操作运行边界所述恢复资料包仍然必需，并应额外补充复制滞后 SLO、提升手册耗时、最近成功故障转移演练日期，以及恢复原主库的隔离流程。

对自托管部署，主备和双活多区域、自动区域故障转移、同步跨区域复制（RPO=0）、跨区域活动可见性，以及引擎强制的区域固定任务队列路由轴仍由支持团队指导，因为拓扑本身属于产品风险。当前 Cloud 托管运行时契约是单区域契约，不提供这些多区域保证。

就绪契约​

同时使用健康和就绪检查：

  • GET /api/health 证明进程正在提供 HTTP 服务。
  • GET /api/ready 报告已配置的依赖检查，包括数据库连接、迁移和默认命名空间就绪状态；它不证明每种工作流 SQL 操作正常或具备可用写入容量。
  • GET /api/cluster/info 证明已验证客户端能发现构建身份、控制平面协议、Worker 协议、负载编解码器和 Server 能力。
  • POST /api/worker/register 证明 Worker 能通过身份验证进入预期命名空间和任务队列。

不要仅根据 /api/health 切换流量。

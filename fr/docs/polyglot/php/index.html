SDK PHP

Utilisez durable-workflow/sdk lorsqu’une application PHP ou un worker distant se connecte au Server autonome Durable Workflow ou à l’URL de runtime d’un espace de noms Durable Workflow Cloud. Ce SDK officiel est indépendant du framework. Il fournit le client du plan de contrôle, l’authentification, le transport, le codec public de données utiles, le gestionnaire de relecture et le cycle de vie du worker distant géré, sans nécessiter Laravel ni le paquet du moteur embarqué.

Essayer l’environnement local de l’application d’exemple​

Pour le parcours de création le plus court sans Cloud, ouvrez la branche main de l’application d’exemple dans GitHub Codespaces et exécutez :

scripts/playground php

L’environnement local génère le code de workflow et d’activité appartenant à l’appelant, sélectionne les artefacts stables actuels et démarre Server et Waterline publiés. Il attend un enregistrement de worker dont l’identité, le type de workflow, le type d’activité et la file de tâches correspondent au contrat généré avant de démarrer le workflow. La réussite exige le résultat terminé attendu et l’historique requis. Le terminal affiche ensuite le lien exact vers l’exécution Waterline locale et le chemin des preuves JSON structurées.

Le démarrage rapide et la référence d’API gérés par le paquet, ci-dessous, restent le parcours direct pour ajouter le SDK à un projet existant sans application d’exemple.

Runtime géré

Durable Workflow Cloud

Exécutez des clients et workers PHP sur un espace de noms Cloud géré avec des identifiants distincts limités par rôle.

Voir les tarifs Cloud Dev

Pour l’intégration pas à pas, les parcours des frameworks, les tests, le déploiement et le dépannage, consultez le portail de développement PHP. Pour les signatures exactes de constructeurs, types de retour et classes d’exception, utilisez sa référence d’API générée distincte. Le contrat lisible par machine du portail identifie le paquet, les formes de runtime, les rôles des identifiants, les fichiers source livrés, le résultat attendu et le test sur artefacts publiés comme un seul parcours testé.

Les clients Cloud utilisent l’URL de runtime et l’espace de noms retournés au provisionnement, avec des identifiants client et worker distincts. Le runtime Cloud géré décrit cette frontière de connexion. Les exemples ci-dessous utilisent le même SDK avec des valeurs locales auto-hébergées.

Utilisez durable-workflow/workflow pour le parcours Laravel embarqué distinct, dans lequel l’application possède l’état des workflows dans sa base existante et exécute le travail via ses files Laravel. Les modes de déploiement comparent toutes les responsabilités.

Prérequis​

  • PHP 8.1 ou ultérieur
  • Un Server auto-hébergé accessible ou un runtime d’espace de noms Cloud provisionné

Installation​

Installez le SDK PHP actuellement publié. La dépendance exacte ci-dessous est générée à partir de la référence des artefacts publiés actualisée depuis le registre. Composer enregistre le paquet résolu dans composer.lock :

composer require durable-workflow/sdk:3.2.0

Le SDK utilise le paquet Composer officiel apache/avro pour l’enveloppe publique de données utiles. Ses dépendances de production excluent Laravel, Illuminate, durable-workflow/workflow et durable-workflow/server.

Démarrer et inspecter un workflow​

Le démarrage rapide du SDK crée un projet Composer vierge, définit un workflow et une activité avec des attributs, démarre le worker, lance un workflow unique et attend son résultat. Les mêmes fichiers bootstrap.php, worker.php et client.php livrés sont installés depuis le paquet et exécutés par le test protégé sur artefacts publiés. Cette page n’entretient donc pas un deuxième exemplaire du code.

Choisissez uniquement la valeur de connexion au runtime :

RuntimeValeur transmise à ClientComportement du chemin des requêtes SDK
Server auto-hébergéOrigine seule, comme http://localhost:8080Ajoute un segment /api. L’appelant ne doit pas ajouter /api.
Durable Workflow CloudURI provisionnée complète, comme https://cloud.example/api/runtime/v1/namespaces/<runtime-id>Conserve le chemin du runtime d’espace de noms et y ajoute le segment de point de terminaison /api.

Ouvrez le parcours PHP testé pour les commandes exactes et le code visible. Les opérations client lisent DURABLE_WORKFLOW_CLIENT_TOKEN. L’interrogation du worker lit DURABLE_WORKFLOW_WORKER_TOKEN. Le guide garde ces identifiants dans des processus séparés sans afficher ni committer leur valeur.

Worker::register() découvre les gestionnaires #[Workflow] et #[Activity] dans le même fichier source. Le guide décrit aussi l’alternative registerWorkflow()/registerActivity() pour le code fondé directement sur des callables. L’amorçage évite à l’utilisateur de sélectionner le chemin de l’autoloader lorsque les fichiers livrés s’exécutent dans un projet autonome, un checkout SDK, un paquet installé ou un environnement de test/conteneur qui les place à côté de son répertoire Composer vendor/.

WorkflowHandle suit l’exécution courante après une continuation avec une nouvelle exécution. Utilisez ses méthodes ciblant une exécution sélectionnée si une opération doit rester protégée par l’identité d’une seule exécution.

Cycle de vie, mises à jour, planifications et visibilité​

Le client public actuel dépasse la seule gestion du résultat d’une exécution :

  • WorkflowHandle expose describe, result, signal, query, cancel et terminate, avec des variantes ciblant une exécution sélectionnée pour les opérations qui doivent être limitées à celle-ci.
  • Client expose listWorkflows avec filtrage et pagination Server, workflowHistory, updateWorkflow, cancelWorkflow et terminateWorkflow.
  • requestCancellation() demande un nettoyage borné aux workers coopératifs. Les méthodes existantes cancel() et cancelWorkflow() ferment immédiatement l’exécution. L’annulation coopérative définit le contrat d’écriture et de reprise.
  • Les méthodes de planification couvrent la création, description, liste, modification, pause, reprise, déclenchement, rattrapage et suppression.
  • La visibilité d’exploitation inclut listNamespaces, listWorkers et listTaskQueues, avec les méthodes de description correspondantes.

Les workers distants enregistrent les gestionnaires de workflows, activités, requêtes de lecture et mises à jour via registerWorkflow, registerActivity, registerQuery et registerUpdate. La référence d’API générée du SDK PHP donne tous les paramètres et types de retour.

Contexte de reprise et exécution propriétaire d’une activité​

Le SDK PHP 3.6.1 ou ultérieur expose $context->retryInfo, $context->workflowId et $context->runId dans les activités en mode service. Vérifiez $context->retryInfo->isLastConfiguredAttempt() === true pour reconnaître la dernière tentative configurée d’une politique limitée. attemptNumber conserve le numéro de tentative reçu à l’origine.

L’instantané distingue trois états : policyProvided === false indique que la politique est absente de la tâche attribuée ; une valeur racine null fournie représente une ancienne politique inconnue ; un objet contenant explicitement max_attempts: null signifie des tentatives illimitées. Un retour null de maxAttempts() ne suffit pas à établir ce caractère illimité. Le SDK n’invente aucun budget par défaut. L’annulation, un échec non réessayable, la fermeture du workflow et l’expiration des délais peuvent arrêter l’exécution avant épuisement du budget.

Les identifiants du workflow et de l’exécution désignent l’exécution propriétaire d’origine. Une identité absente des anciennes tâches reste null. Les activités locales conservent les identifiants connus du parent sans hériter d’une politique de reprise distante. Pour signaler le workflow propriétaire, exigez les deux identifiants, ciblez runId et réutilisez un identifiant de requête stable lié à l’événement métier entre les tentatives.

Traitez les signaux de manière idempotente pour l’événement métier. Un identifiant de requête stable ne garantit pas à lui seul une admission unique du signal.

Consultez les exemples complets de dernière tentative et de signal à sa propre exécution dans le guide du SDK PHP.

Heartbeats d’activité​

Pour les activités distantes, appelez ActivityContext::heartbeat($details) pendant un travail d’activité borné, bien avant le délai de heartbeat configuré. La première fenêtre commence lorsque le moteur réclame l’activité, pas lorsque PHP reçoit la tâche. La latence des requêtes, les pauses et les nouvelles tentatives de transport consomment cette fenêtre. Suivez les conseils de fréquence.

La méthode renvoie void. Dans le chemin direct du gestionnaire, une réponse demandant l’arrêt lève ActivityCancelled. Les erreurs HTTP et de transport de Client::heartbeatActivityTask() apparaissent comme ServerException. Un worker à supervision coopérative peut arrêter ou abandonner son callback lorsqu’un heartbeat ou une vérification de possession échoue, au lieu de livrer une réponse normale au code de l’activité. Ne supposez pas que le nettoyage s’exécute toujours, ne masquez pas une perte d’autorité et ne soumettez pas de réussite après cette perte.

Le retour de l’appel ne valide pas le travail externe et ne fournit pas de point de reprise. Gardez les effets externes idempotents et ne considérez pas une nouvelle tentative de transport comme une nouvelle fenêtre de heartbeat.

Exécuter un worker PHP distant​

Les gestionnaires de workflow sont des callables ordinaires exécutant du code linéaire dans une Fiber gérée. Appelez directement les opérations comme WorkflowContext::activity(). Le SDK suspend la Fiber aux décisions durables et retourne les résultats enregistrés pendant la relecture sans répéter l’activité externe. Ne déclarez pas le workflow comme Generator et n’utilisez pas yield pour les commandes WorkflowContext : les résultats Generator sont refusés. Le worker géré enregistre ses noms de types de workflow et d’activité, interroge le protocole worker public, émet des battements de cœur, termine ou fait échouer les tâches et gère l’arrêt propre si pcntl est disponible.

Sélection de la première fin​

Utilisez WorkflowContext::select() pour démarrer des activités différées, workflows enfants, temporisateurs, attentes conditionnelles ou barrières ordinaires imbriquées indépendantes, puis reprendre au premier gagnant validé durablement. Le SelectionResult retourné contient des clés et identités stables ainsi qu’un handle par membre :

$selected = $ctx->select([
    'resolver' => fn () => $ctx->activity('resolve-request', [$requestId]),
    'input' => fn () => $ctx->waitCondition(
        fn (): bool => $this->resolution !== null,
        key: 'resolution-ready',
    ),
    'deadline' => fn () => $ctx->sleep(2),
]);

if ($selected->key === 'deadline') {
    $selected->handles['resolver']->cancel();
}

La sélection n’annule pas les autres membres. Appelez await() sur un handle pour consommer son résultat ultérieur, ou cancel() pour enregistrer une annulation explicite. Un worker à froid ou une relecture d’historique terminé consomme le gagnant enregistré même si des entrées en double ou ultérieures et des événements terminaux arrivent dans un autre ordre. cancel() ne retourne aucune valeur et ne rapporte pas son résultat terminal. Seul l’historique SelectionOperationCancelled prouve que l’annulation a gagné. La relecture dépasse une demande d’annulation sans marqueur et, si l’opération s’est terminée avant, await() retourne toujours ce résultat.

Compatibilité à l’entrée et récupération​

Prise en charge publiée. Le SDK PHP 2.5.4 a introduit la protection d’entrée ci-dessous, avec le routage et la récupération dans Server 2.9.9. Ce sont les versions minimales pour ces fonctions. Installez les versions stables actuelles pour bénéficier des correctifs de sécurité.

Le worker géré vérifie l’entrée positionnelle enregistrée du handler avant d’entrer dans sa Fiber. Un argument obligatoire absent ou un type PHP déclaré incompatible lève DurableWorkflow\Exception\WorkflowEntryArgumentsMismatch et signale le motif de tâche workflow_entry_arguments_mismatch. Les valeurs par défaut des arguments facultatifs ne s’appliquent qu’aux entrées omises ; elles ne remplacent jamais une valeur enregistrée incompatible. Un TypeError levé après une entrée réussie reste un échec applicatif.

Le worker annonce automatiquement workflow_entry_arguments_validation. Avec la prise en charge Server correspondante, une tâche refusée est bloquée pour la relecture et l’exécution d’origine reste non terminale. Un ancien runtime peut au contraire relancer la tâche en échec ; une mise à niveau du SDK seule n’établit donc pas le contrat complet de récupération.

Inspectez l’original avec Client::describeWorkflow($workflowId, $runId) et l’endpoint de débogage ciblant l’exécution. Restaurez du code compatible avant d’appeler Client::repairWorkflow($workflowId, $runId), puis vérifiez que cette même exécution reprend sans modifier son entrée, son historique, son identité de routage ou ses échéances. Ne capturez pas cet échec dans le corps du workflow et ne réparez pas en boucle un code incompatible. Consultez la procédure de récupération en mode service et le routage des définitions.

Mode service avec framework et Laravel embarqué​

Le même paquet fournit les ponts officiels Laravel en mode service et Symfony en mode service. Ils conservent l’injection de dépendances, la configuration, la journalisation, les workers en console et les fakes de test du framework en se connectant à Cloud ou Server.

Ces ponts sont distincts des workflows Laravel embarqués, où durable-workflow/workflow fait de l’application Laravel la propriétaire de l’état durable et exécute via les files Laravel. Le guide d’adoption Laravel et de transition du runtime montre le même cas d’usage Laravel en v1, en v2 embarquée et avec ce pont mode service livré, y compris le drainage et le retour arrière. Les modes de déploiement comparent plus largement les frontières du runtime.

Frontière de protocole et de version​

Le SDK déclare dans ses métadonnées Composer la plage Server prise en charge, la version du protocole worker, celle du plan de contrôle et les codecs de données utiles. Server publie aussi les protocoles et codecs acceptés depuis GET /api/cluster/info. Vérifiez la découverte du runtime pendant le déploiement plutôt que de déduire la compatibilité d’une version corrective de Server.

Le SDK PHP est versionné indépendamment du paquet Laravel. Conservez la version publiée exacte dans les exemples exécutables et consultez les notes de version lors d’une mise à niveau du SDK. La compatibilité suit son contrat déclaré, sans dépendre de l’égalité des numéros de version des paquets.

Pages de liste et d’historique des workflows​

Ces appels publiés renvoient une page, pas une lecture complète automatique : Client::listWorkflows(...) / Client::workflowHistory(...). Continuez avec le token opaque retourné en conservant namespace, filtres et workflow/exécution sélectionnés ; terminez au token nul/vide et traitez explicitement les erreurs de page. Une page partielle n’est pas un bundle de replay. Utilisez l’API d’export d’historique du SDK pour le replay hors ligne. Le client publié PHP 3.2.0 définit les paramètres actuels ; aucun nouvel itérateur n’est annoncé.

Rapports d’échec bornés​

Le SDK PHP 3.5.0 a introduit des rapports d’échec sortants bornés. Les limites par défaut sont de 62 KiB UTF-8 pour le message, 128 KiB pour la pile, 64 KiB pour l’ensemble des détails et diagnostics facultatifs sérialisés et 1 MiB pour le corps complet encodé en JSON. Les marqueurs, l’échappement JSON, l’identité du bail et les autres commandes du lot comptent dans cette limite du corps. Une limite de transport configurée ou déclarée par le transport plus basse est prioritaire. Le type, la classe et le code de l’échec, la politique de nouvelle tentative et l’identité du bail sont conservés.

withFailureReportLimit() renvoie un nouveau client avec un budget plus faible pour la requête entière, de 1 à 1 048 576 octets. Utilisez cette instance. Une limite plus basse déclarée par le transport s’applique aussi.

<?php

use DurableWorkflow\Client;

$client = (new Client(
    baseUri: 'https://workflow.example.com',
    controlToken: 'operator-token',
    workerToken: 'worker-token',
))->withFailureReportLimit(512 * 1024);

Un marqueur de troncature visible et les tailles originales en octets identifient les champs raccourcis. Les détails Avro sont conservés intégralement ou omis en entier. Une enveloppe obligatoire impossible à représenter déclenche DurableWorkflow\Exception\FailureReportRefused avant l’envoi HTTP. Les échecs locaux sont normalisés avant que le code du workflow les observe. La première exécution et la relecture à froid voient donc le même message persistant. Un message local déjà observé reste immuable lors de l’ajustement final du lot.

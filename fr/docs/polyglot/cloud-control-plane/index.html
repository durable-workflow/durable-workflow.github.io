Runtime géré Cloud

Durable Workflow Cloud est un service d'orchestration géré. Cloud exploite le plan de contrôle hébergé et le runtime d'orchestration, dont l'état des workflows, l'historique, les planifications, files de tâches, baux et la visibilité durable. Les clients exécutent leurs clients SDK et workers sur un espace de noms Cloud provisionné.

C'est une option distincte de l'auto-hébergement. Un Durable Workflow Server auto-hébergé fonctionne indépendamment et n'est jamais rattaché à Cloud.

Offres et tarifs​

Vous payez la capacité provisionnée, pas la sémantique des workflows. Chaque espace de noms reçoit un runtime géré isolé ; vos workers PHP, Python et Rust s'exécutent dans votre environnement. Consultez les tarifs Cloud et le tableau de bord pour la disponibilité actuelle du provisionnement.

Cloud Dev est disponible maintenant. Les quatre offres HA sont en qualification et ne peuvent pas encore être achetées ni provisionnées. Les tarifs, capacités, disponibilités et SLA ci-dessous sont prévus et ne constituent pas des offres d'achat actuelles.

La capacité couvre les composants du runtime géré, pas le calcul des workers clients. Pour les offres HA prévues, réplication et capacité de secours sont incluses dans le prix ; la table n'additionne pas les répliques en capacité supplémentaire d'exécution des workflows. Chaque offre inclut Managed Waterline, des sauvegardes chiffrées de base, les mises à niveau et une URL de runtime stable.

Les runtimes provisionnés sont facturés selon leur durée, mesurée à la minute de l'activation au déprovisionnement. Minimums et plafonds s'appliquent par achat de runtime et mois civil UTC. Le temps provisionné inactif est facturable ; un mois sans temps provisionné ne produit aucun frais de runtime. Un nouvel achat a son propre minimum et plafond ; une réparation ou reprise gérée par le service ne les réinitialise pas. Stripe facture mensuellement l'usage accumulé. Les prix excluent les taxes applicables.

Le stockage est fixé à l'allocation incluse. Il n'y a ni extension de stockage achetée séparément, ni augmentation automatique, ni frais de dépassement. Pour plus d'espace, demandez une offre de runtime supérieure avant d'atteindre la limite. Passer seulement de monorégion à multirégion n'augmente pas le stockage. Une augmentation de capacité nécessite un véritable changement de runtime, pas seulement de facturation ; elle s'organise actuellement avec le support. L'usage réseau est mesuré, pas facturé actuellement, et n'est pas illimité.

Consultez les tarifs Cloud pour choisir une offre. Pour plus de capacité, une autre connectivité, le SSO, le support entreprise ou une disponibilité personnalisée, contactez-nous.

Frontière du service géré​

La frontière visible du client est un espace de noms Cloud :

Cloud organization
  project
    environment
      namespace
        stable runtime URL
        client runtime credential  ---> workflow starts and commands
        worker runtime credential  ---> registration, polling, and completion

Cloud-operated runtime
  workflow state and history
  schedules and task queues
  leases, matching, and visibility
  Managed Waterline

Cloud gère le provisionnement des espaces de noms, l'exploitation du runtime, la persistance, le placement, la santé, la reprise et l'interface Managed Waterline de l'espace. Les clients gèrent leur code applicatif, les implémentations de workflows et d'activités et les processus de leurs workers. Ils ne déploient pas de service Waterline distinct.

Le point de terminaison HTTPS de l'espace se connecte directement au runtime géré. Le trafic SDK ne passe pas par l'application du site/plan de contrôle Cloud. Utilisez l'URL retournée sans modification ni ajout de /api ; le SDK et la CLI construisent leurs chemins d'API. Les appels administratifs utilisent toujours https://cloud.durable-workflow.com/api/v1.

L'administration Cloud et le trafic runtime utilisent des identifiants différents :

  • Une clé API Cloud (dwc_...) gère projets, environnements, espaces de noms, facturation et cycle de vie des identifiants runtime.
  • Un identifiant runtime client (dwr_...) démarre et contrôle les workflows d'un espace de noms géré.
  • Un identifiant runtime worker (dwr_...) inscrit les workers, interroge longuement les tâches, envoie les heartbeats et règle le travail dans cet espace.

Une clé API Cloud n'est pas acceptée par l'URL de runtime de l'espace. Les identifiants runtime sont limités à un espace et un rôle, retournés seulement à leur création et omis des réponses ultérieures de listage et d'audit.

Si l'intégration Cloud utilise la CLI, installez-la depuis le guide CLI et mettez explicitement à jour une installation autonome existante avec dw upgrade. La CLI ne se met jamais à jour en arrière-plan. Après installation ou mise à niveau, exécutez command -v dw et dw --version. Corrigez les problèmes de PATH indiqués par l'installateur avant d'utiliser les identifiants Cloud, pour que le binaire actif soit celui de la version sélectionnée.

Provisionner et connecter un espace de noms​

1. Créer et provisionner l'espace de noms​

Dans le tableau de bord Cloud, créez une organisation, un projet, un environnement et un espace de noms, puis sélectionnez son offre de capacité. Créer un compte ou une définition d'espace de noms ne provisionne aucune capacité payante. Configurez le paiement avec Stripe, puis sélectionnez Provision sur la page de l'espace de noms. Ajouter une carte ne démarre pas seul le provisionnement.

Le provisionnement est asynchrone. La page de l'espace met à jour la progression pendant la préparation du runtime par Cloud. Attendez son activation avant de lancer le travail SDK. La page permet aussi de créer les identifiants runtime et d'accéder à Managed Waterline pour inspecter les workflows et leur historique.

Pour une configuration par API, terminez d'abord la configuration du paiement. L'exemple utilise l'offre par défaut de l'organisation ; capacity_plan_version permet d'en sélectionner une autre disponible. Ne fournissez pas votre propre URL Server, identifiant de déploiement ni enregistrement de placement :

curl -X POST \
  https://cloud.durable-workflow.com/api/v1/projects/PROJECT/environments/ENVIRONMENT/namespaces \
  -H "Authorization: Bearer dwc_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"orders","retention_days":30}'

curl -X POST \
  https://cloud.durable-workflow.com/api/v1/projects/PROJECT/environments/ENVIRONMENT/namespaces/orders/provision \
  -H "Authorization: Bearer dwc_..."

Après provisionnement, la réponse de l'espace fournit sa runtime_url stable, son runtime_namespace, son état géré et les informations régionales visibles par le client. L'URL et l'espace retournés sont une configuration appartenant à Cloud ; ne déduisez pas de point de terminaison et ne les remplacez pas par une adresse Server auto-hébergée.

2. Émettre des identifiants client et worker séparés​

Émettez les deux rôles runtime indépendamment :

curl -X POST \
  https://cloud.durable-workflow.com/api/v1/projects/PROJECT/environments/ENVIRONMENT/namespaces/orders/runtime-credentials \
  -H "Authorization: Bearer dwc_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"orders-client","role":"client"}'

curl -X POST \
  https://cloud.durable-workflow.com/api/v1/projects/PROJECT/environments/ENVIRONMENT/namespaces/orders/runtime-credentials \
  -H "Authorization: Bearer dwc_..." \
  -H "Content-Type: application/json" \
  -d '{"name":"orders-worker","role":"worker"}'

Chaque jeton n'est affiché qu'une fois, dans sa réponse de création. Conservez-le dans le gestionnaire de secrets utilisé uniquement par le rôle correspondant. Un processus réunissant volontairement client et worker reçoit les deux valeurs comme secrets distincts. Faites tourner et révoquez les rôles indépendamment ; ne substituez jamais de clé API Cloud à un identifiant runtime.

3. Terminer un premier workflow Cloud​

Le terrain d'essai partagé de runtime externe de Sample App exécute le même parcours de workflow et d'activité en PHP, Python ou Rust. Ouvrez un Codespace Sample App, exportez les valeurs de l'espace provisionné et les deux identifiants runtime, puis choisissez une file de tâches applicative :

export DURABLE_WORKFLOW_RUNTIME_URL='<provisioned-runtime-url>'
export DURABLE_WORKFLOW_NAMESPACE='<provisioned-runtime-namespace>'
export DURABLE_WORKFLOW_CLIENT_TOKEN='<client-runtime-credential>'
export DURABLE_WORKFLOW_WORKER_TOKEN='<worker-runtime-credential>'
export DURABLE_WORKFLOW_TASK_QUEUE='<language-task-queue>'

Choisissez ensuite un SDK officiel et exécutez le même contrat de runtime géré :

language=php # Choose php, python, or rust.
scripts/playground "$language" --runtime managed \
  --runtime-url "$DURABLE_WORKFLOW_RUNTIME_URL" \
  --namespace "$DURABLE_WORKFLOW_NAMESPACE" \
  --task-queue "$DURABLE_WORKFLOW_TASK_QUEUE"

Le runner résout les versions stables actuelles des artefacts, ne transmet chaque identifiant qu'au processus enfant correspondant, attend jusqu'à 60 secondes une inscription worker annonçant la file exacte et les types générés de workflow et d'activité, puis lance une requête client. Il ne réussit qu'après retour du résultat attendu par le SDK, annonce de completed par dw et présence de l'historique requis du workflow et de l'activité. La commande n'exécute ni Server ni Waterline local en mode géré.

Pour chaque langage, réexécutez la commande gérée complète ci-dessus en ne changeant que language. Poursuivez avec son guide pour l'écriture propre au SDK :

  • SDK PHP : définissez language=php.
  • SDK Python : définissez language=python.
  • Démarrage rapide Rust avec runtime géré : définissez language=rust et utilisez ses diagnostics de disponibilité du worker, de résultat terminé et de discordance.

Un parcours réunissant client et worker détient les deux identifiants runtime comme secrets distincts. Une clé d'administration Cloud n'est pas un identifiant runtime et ne doit être exportée dans aucune des deux variables de jeton runtime.

4. Poursuivre l'exploitation gérée​

Le client SDK démarre les workflows et envoie les commandes ultérieures via l'URL runtime de l'espace. Les workers clients s'inscrivent et interrogent longuement la même URL avec le rôle worker. Cloud authentifie et limite chaque requête, exécute le protocole d'orchestration dans le runtime géré et persiste l'état et l'historique du workflow.

L'application cliente ne sélectionne pas de déploiement de runtime pour une opération. Identifiants de workflows et d'exécutions, files de tâches, marqueurs de compatibilité et encodage Avro restent des contrats applicatifs durables dans l'espace Cloud.

Connectivité des workers exécutés par le client​

Les workers peuvent s'exécuter dans votre réseau, flotte de VM, plateforme de conteneurs ou environnement applicatif. Ils nécessitent un accès HTTPS sortant à l'URL runtime de l'espace et doivent autoriser les longues requêtes d'interrogation du protocole worker.

  • Aucune connexion entrante de Cloud vers un worker n'est nécessaire.
  • Les proxys et passerelles de sortie ne doivent pas raccourcir les interrogations longues en une boucle de nouvelles tentatives intensive.
  • Les workers devraient réessayer les échecs transitoires de connexion et les réponses d'indisponibilité avec une attente bornée.
  • Déplacer un processus worker ne déplace pas l'état des workflows ; Cloud conserve l'état durable et l'historique de l'espace.
  • La rotation d'identifiants ne nécessite de changer ni URL runtime, ni espace de noms, ni file de tâches.

Placement régional et frontière de reprise​

Cloud Dev est disponible avec la frontière de reprise ci-dessous. Les frontières HA décrivent les offres prévues, encore indisponibles en attente de qualification :

  • Cloud Dev : un hôte isolé avec état persistant et sauvegardes. Maintenance et reprise peuvent interrompre le service. Aucun SLA de disponibilité ni basculement régional automatique.
  • HA monorégion prévue : trois hôtes répliqués dans une région, avec basculement automatique du primaire. Un hôte peut tomber sans perte du quorum restant. Une panne régionale entière sort du SLA de cette offre.
  • HA multirégion prévue : trois hôtes répliqués dans trois régions, avec basculement automatique du primaire. Le SLA inclut la perte ou l'isolement d'une région configurée, si les membres restants peuvent former un quorum.

Pour les profils HA prévus, l'URL runtime stable est destinée à suivre le primaire élu ; la configuration SDK ne change pas pendant un basculement pris en charge. Un ancien primaire isolé ne peut plus servir de travail faisant autorité. Si aucun primaire sûr ne peut être établi, le runtime cesse de servir plutôt que d'accepter des écritures conflictuelles. HA ne promet pas des requêtes ininterrompues : clients et workers nécessitent toujours des nouvelles tentatives bornées pour les échecs transitoires.

La page de l'espace expose topologie, régions et état du service. Les sauvegardes aident à la reprise mais ne remplacent pas la réplication active. Les courts tests de basculement démontrent les cas de panne exercés, pas une garantie universelle de délai de reprise ni la disponibilité atteinte sur un mois.

Les quatre offres SLA prévues spécifient une disponibilité de 99,99 % sur un mois civil UTC, mesurée au point de terminaison runtime client par fenêtres d'une minute. Les mesures absentes comptent comme indisponibles et la maintenance planifiée n'est pas exclue. La disponibilité des workers hébergés par le client est distincte de celle du runtime géré.

Ces crédits ne dépassent jamais les frais du mois pour le runtime concerné ; les interruptions ne donnent lieu à aucun remboursement en numéraire. Cloud Dev n’a pas de crédits SLA. Connectivité privée et frontière du support​

Le contrat Cloud 2.0 en libre-service suppose un accès sortant des clients et workers à l'URL runtime publique de l'espace. L'entrée exclusivement privée, les VPN ou interconnexions sur mesure et les routages privés propres aux fournisseurs sont conçus avec le support, pas des valeurs par défaut cachées. Les clients ne reçoivent jamais d'adresses internes du runtime et ne sont pas invités à contourner l'URL de l'espace.

Cloud ou Server auto-hébergé​

Choisissez Cloud si Durable Workflow doit gérer le runtime d'orchestration, la persistance, la disponibilité de l'offre choisie, la reprise et Managed Waterline, tandis que votre équipe gère les clients SDK et workers.

Choisissez Server auto-hébergé si votre équipe doit gérer indépendamment l'image Server, la base, le cache, le réseau, l'authentification, les sauvegardes et le basculement. Un Server auto-hébergé ne peut pas être enregistré dans Cloud, rattaché à Cloud ni servir de runtime à un espace Cloud. Laravel embarqué, Server auto-hébergé et Cloud sont des choix de déploiement distincts.

Les workers clients PHP, Python et Rust s'exécutent hors de cette allocation. Démarrages de workflows, tentatives d'activités, nouvelles tentatives, temporisateurs, signaux, requêtes, mises à jour et workflows enfants sont une télémétrie opérationnelle, pas des unités de facturation distinctes. Cloud expose l'usage de facturation par organisation pour la finance, l'exploitation et la refacturation automatisée. Le point est authentifié par une clé API Cloud et n'accepte aucun identifiant de client ou d'organisation dans la requête ; l'organisation de l'appelant est déterminée à partir du jeton Bearer dwc_ afin qu'un client ne puisse interroger l'usage d'un autre.

GET /api/v1/billing/usage?period_start=2026-05-01&period_end=2026-05-31
Authorization: Bearer dwc_...
Accept: application/json

period_start et period_end sont des dates ISO-8601 facultatives. Sans elles, Cloud renvoie le mois civil courant. Les lectures et exports d'usage restent disponibles même si des restrictions de facturation suspendent le provisionnement ou les opérations workflow, pour permettre aux équipes financières de régulariser le compte.

Le schéma de réponse est durable_workflow.cloud.namespace_capacity_usage.v1. Il sépare le temps de capacité allouée des compteurs d'événements sémantiques. Les champs de stockage restent dans le schéma pour la facturation historique ; ils n'autorisent pas l'achat d'une extension. Le compteur de temps Cloud Dev démarre à l'activation du runtime isolé et s'arrête à son déprovisionnement. Le plafond et le minimum mensuels s'appliquent par achat de runtime et mois civil UTC. Le stockage ne croît pas et ne devient pas facturable automatiquement. Cloud préserve une réserve d'exploitation et de reprise sur le disque du runtime ; demandez une offre supérieure avant d'atteindre l'allocation incluse.

Les runtimes inactifs engendrent toujours des frais de capacité. Le déprovisionnement arrête la facturation et supprime les données actives et identifiants du runtime ; ce n'est pas une pause réversible. Les SLA prévus suivent le même modèle de temps provisionné avec leurs propres tarifs, minimums et plafonds. Interprétez l'usage avec les billing_terms retournés par l'offre ; les factures historiques conservent leurs conditions acceptées.

Exportez ces mêmes éléments en CSV ou rapport JSON si un système financier aval nécessite un fichier :

curl -OJ "https://cloud.durable-workflow.com/api/v1/billing/usage/export?period_start=2026-05-01&period_end=2026-05-31" \
  -H "Authorization: Bearer dwc_..."

curl -OJ "https://cloud.durable-workflow.com/api/v1/billing/usage/report?period_start=2026-05-01&period_end=2026-05-31" \
  -H "Authorization: Bearer dwc_..."

Pour un panneau de tableau de bord fondé sur JSON, interrogez la même API avec sa plage temporelle :

GET https://cloud.durable-workflow.com/api/v1/billing/usage?period_start=${__from:date:YYYY-MM-DD}&period_end=${__to:date:YYYY-MM-DD}
Authorization: Bearer dwc_...

Puis aplatissez les lignes de capacité des espaces de noms avec :

.by_namespace[]

Utilisez invoice_units pour rapprocher la capacité et le stockage. Utilisez operational_telemetry pour comprendre la forme de la charge et le comportement des benchmarks ; ne convertissez pas ces compteurs d'événements en frais.

Référence de l'API Server

Le serveur autonome expose une API HTTP+JSON versionnée. Utilisez cette page pour construire des SDK, scripts, adaptateurs de passerelle ou procédures d'exploitation appelant directement le serveur. Consultez le guide Server pour le déploiement et la configuration, et la référence des commandes CLI pour appeler dw.

En-têtes et versionnement​

Toutes les requêtes authentifiées utilisent des jetons Bearer sauf si le serveur est configuré avec un autre pilote d'authentification :

Authorization: Bearer <token>
X-Namespace: default
Content-Type: application/json
Accept: application/json

Les routes du plan de contrôle exigent :

X-Durable-Workflow-Control-Plane-Version: 2

Les routes du plan worker exigent :

X-Durable-Workflow-Protocol-Version: 1.0

Le serveur publie les versions prises en charge et contrats lisibles par machine via GET /api/cluster/info. Les clients devraient y découvrir les versions avant de démarrer une automatisation de longue durée. Les versions de plan de contrôle absentes ou incompatibles sont rejetées avec un motif nommé comme missing_control_plane_version ou unsupported_control_plane_version.

Pour la validation, la génération de code et les contrôles de dérive, utilisez le catalogue normatif des spécifications des protocoles de la plateforme plutôt que cette référence en prose. Il lie le document OpenAPI du plan de contrôle, les documents OpenAPI et AsyncAPI du protocole worker, le JSON Schema cluster_info et les schémas associés MCP, d'historique, Waterline et de réparation/actions possibles.

Découverte et santé​

Ces routes servent aux répartiteurs de charge, à l'initialisation des SDK et aux contrôles de compatibilité.

MéthodeCheminAuthentificationRôle
GET/api/healthnonSonde de présence et résumé de topologie lisible par machine du nœud répondant.
GET/api/readynonSonde de disponibilité, même résumé de topologie et contrôles préalables de sûreté du déploiement.
GET/api/cluster/infoouiIdentité du serveur, plages de SDK prises en charge, topologie des rôles, résumé de santé de coordination, contrats du plan de contrôle et du protocole worker, codecs des charges utiles et capacités fonctionnelles.

Exemple :

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/cluster/info" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: default" | jq '.control_plane.version, .worker_protocol.version'

/api/cluster/info n'exige volontairement pas l'en-tête de version du plan de contrôle, car c'est lui qui annonce les versions prises en charge. La même réponse inclut coordination_health, résumé de déploiement et de disponibilité sur tous les espaces de noms reflétant les contrôles qui alimentent déjà la disponibilité du serveur.

Résumé public de topologie​

GET /api/health et GET /api/ready renvoient tous deux un objet topology de premier niveau issu du contrat livré de résumé de santé. Utilisez-le pour identifier le nœud ayant répondu avant la réussite de l'authentification du plan de contrôle, de la résolution de l'espace de noms ou de la découverte plus large /api/cluster/info.

Le résumé public inclut toujours :

  • topology.schema
  • topology.version
  • topology.current_shape
  • topology.current_process_class
  • topology.current_roles
  • topology.execution_mode
  • topology.matching_role.queue_wake_enabled
  • topology.matching_role.shape
  • topology.matching_role.wake_owner
  • topology.matching_role.task_dispatch_mode
  • topology.matching_role.partition_primitives
  • topology.matching_role.backpressure_model
  • topology.matching_role.discovery_limits.poll_batch_cap
  • topology.matching_role.discovery_limits.availability_ceiling_seconds
  • topology.matching_role.discovery_limits.wake_signal_ttl_seconds
  • topology.matching_role.discovery_limits.workflow_task_lease_seconds
  • topology.matching_role.discovery_limits.activity_task_lease_seconds

topology.matching_role.discovery_limits est le contrat numérique figé du rôle d'appariement : poll_batch_cap est le lot maximal de lignes de tâches prêtes renvoyé par interrogation ; availability_ceiling_seconds est la tolérance entre moteurs de stockage appliquée à available_at, pour que les tâches nouvellement disponibles résistent aux écarts d'horodatage inférieurs à une seconde ; wake_signal_ttl_seconds est le TTL par défaut des signaux CacheLongPollWakeStore ; workflow_task_lease_seconds et activity_task_lease_seconds sont les durées de bail par défaut des tâches de workflow et d'activité. Resserrer ces valeurs change le protocole, car workers et outils aval les utilisent comme contrat de référence de l'appariement. Renommer un champ est aussi une rupture de protocole.

/api/ready renvoie le même bloc topology même lorsque le status de disponibilité global vaut not_ready. Les sondes peuvent donc distinguer les réponses de server_http_node, scheduler_node, matching_node et execution_node pendant les blocages d'initialisation.

Exemple :

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/health" | jq '{
  status,
  topology: {
    schema: .topology.schema,
    version: .topology.version,
    current_shape: .topology.current_shape,
    current_process_class: .topology.current_process_class,
    current_roles: .topology.current_roles,
    execution_mode: .topology.execution_mode,
    matching_role: .topology.matching_role
  }
}'

Blocages de disponibilité​

GET /api/ready renvoie un status global et des checks lisibles par machine. Deux contrôles déterminent si le serveur peut évaluer sans risque la santé de sûreté du déploiement :

  • checks.migrations est le contrôle d'initialisation et de migration. Il publie repository_exists, pending_migrations, adoptable_migrations, blocking_migrations, missing_tables, operator_surface et readiness_contract.
  • adoptable_migrations indique que les tables de workflow existantes ne nécessitent que l'adoption de l'historique des migrations. Le serveur reste disponible avec status: "warning" pour planifier l'adoption avant la prochaine passe de migration.
  • blocking_migrations indique que des enregistrements de migration de sûreté du déploiement sont encore requis. Le serveur refuse avec status: "pending" et une chaîne remediation au lieu de servir comme si la flotte était à jour.
  • operator_surface.available et operator_surface.required_tables indiquent si l'interface opérateur v2 dispose des tables durables nécessaires pour expliquer la sûreté du déploiement après démarrage.
  • readiness_contract.version fixe la révision du contrat d'installation et d'adoption attendue par les scripts analysant ces champs.
  • checks.workflow_v2 reflète le verdict de sûreté sur tous les espaces de noms. Si les prérequis de disponibilité manquent, il annonce status: "blocked" avec blocked_by, message et remediation au lieu de prétendre la flotte saine.

Exemple :

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/ready" | jq '{
  status,
  migrations: {
    status: .checks.migrations.status,
    adoptable_migrations: .checks.migrations.adoptable_migrations,
    blocking_migrations: (.checks.migrations.blocking_migrations | map(.migration)),
    missing_tables: .checks.migrations.missing_tables,
    operator_surface: .checks.migrations.operator_surface,
    readiness_contract: .checks.migrations.readiness_contract
  },
  workflow_v2: {
    status: .checks.workflow_v2.status,
    blocked_by: .checks.workflow_v2.blocked_by,
    remediation: .checks.workflow_v2.remediation
  }
}'

Manifeste de topologie du cluster​

/api/cluster/info renvoie aussi le manifeste topology du nœud sous le schéma durable-workflow.v2.role-topology. C'est le moyen pris en charge de découvrir si le nœud agit actuellement comme standalone_server, embedded ou split_control_execution, les rôles qu'il détient et les attentes du serveur pour matching_role, shape_assignments, authority_boundaries, failure_domains, scaling_boundaries et migration_path. La même réponse publie l'état actuel de sûreté du déploiement de ce nœud.

Lisez le manifeste ainsi :

  • topology.current_shape, topology.current_process_class, topology.current_roles et topology.execution_mode indiquent la forme de rôles effectivement servie par le nœud. Ces champs décrivent le répondant, pas toute la flotte.
  • topology.role_vocabulary est la liste fixe des noms de rôles v2 valides.
  • topology.matching_role.queue_wake_enabled, topology.matching_role.shape, topology.matching_role.wake_owner, topology.matching_role.task_dispatch_mode, topology.matching_role.partition_primitives et topology.matching_role.backpressure_model indiquent si la découverte générale des tâches prêtes s'effectue dans le worker ou par un balayage dédié, le processus responsable, les axes de routage stables et la frontière d'admission durable appliquée actuellement par v2.
  • topology.matching_role.discovery_limits publie les valeurs numériques figées du contrat d'appariement : poll_batch_cap, availability_ceiling_seconds, wake_signal_ttl_seconds, workflow_task_lease_seconds et activity_task_lease_seconds. Vérifiez ainsi le déploiement avec le contrat documenté. Le paquet émet les mêmes identifiants dans dw server:info, l'instantané operator-metrics et la santé limitée à un espace de noms.
  • topology.role_catalog et topology.authority_surfaces associent ces rôles aux interfaces, surfaces d'écriture durable et chemins de lecture attendus par l'automatisation sur le nœud répondant.
  • topology.shape_assignments est l'inventaire lisible par machine des classes de processus pour chaque forme prise en charge. Comparez-y les rôles actuels pour rattacher le nœud à une classe de processus documentée.
  • topology.supported_topologies résume les familles de déploiement prises en charge et les classes de nœuds attendues par chacune.
  • coordination_health résume les risques de déploiement et de compatibilité de la flotte dans un bloc lisible par machine. Outre status et http_status, il peut publier blocked_by, message et remediation quand l'évaluation est bloquée par des problèmes de disponibilité préalables, comme des migrations manquantes ou une base de données inaccessible.
  • coordination_health.checks[] inclut toujours le contrôle figé activity_path à côté de worker_compatibility, task_transport, routing_health, durable_resume_paths et des contrôles de projection/planificateur. Équivalent côté activité de task_transport, activity_path expose les exécutions dont le délai schedule-to-start, start-to-close, schedule-to-close ou de heartbeat a été dépassé sans application de la limite (timeout_overdue, oldest_timeout_overdue_at, max_timeout_overdue_age_ms) et le retard persistant de nouvelles tentatives (retrying, oldest_retrying_started_at, max_retrying_age_ms). Renommer ce contrôle change le protocole.
  • coordination_health.routing_drains résume les cohortes build-id en drainage entre espaces de noms et files. queues_with_drains et les entrées build_ids par file indiquent où le trafic est volontairement éloigné des workers en drainage.
  • execution_mode distingue l'exécution embarquée local_queue_worker de l'exécution par protocole worker remote_worker_protocol.
  • split_control_execution est une topologie du produit prise en charge, pas un second produit serveur ni une autre API.

Exemple :

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/cluster/info" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: default" \
  | jq '{
    current_shape: .topology.current_shape,
    current_roles: .topology.current_roles,
    execution_mode: .topology.execution_mode,
    matching_role: .topology.matching_role,
    coordination_health: {
      status: .coordination_health.status,
      http_status: .coordination_health.http_status,
      blocked_by: .coordination_health.blocked_by,
      queues_with_drains: .coordination_health.routing_drains.queues_with_drains
    }
  }'

Pour le contrat conceptuel de ces champs, dont le vocabulaire des rôles et le chemin de migration, consultez la topologie des rôles de Server.

Rejets de topologie sur un mauvais nœud​

Les routes hébergées authentifiées rejettent les requêtes si le nœud répondant n'héberge pas l'interface de contrôle HTTP requise. Le contrôle intervient après validation du rôle et de la version du protocole, avant résolution de l'espace de noms, pour ne pas révéler son existence sur un mauvais nœud.

Lors d'un blocage, le serveur renvoie 503 avec reason: "topology_role_unavailable" et :

  • current_shape : forme de topologie annoncée du nœud répondant.
  • current_process_class : classe de processus déclarée, comme scheduler_node ou execution_node.
  • current_roles : rôles effectivement hébergés par ce nœud.
  • required_roles : rôles des routes hébergées requis par le point de terminaison.
  • missing_roles : sous-ensemble de required_roles absent du nœud répondant.

Les routes du plan de contrôle renvoient cette charge dans son enveloppe. Les routes du protocole worker renvoient les mêmes champs dans l'enveloppe worker et conservent l'en-tête normal de version du protocole worker.

Exemple de réponse à GET /api/workflows reçu par un nœud limité au planificateur :

{
  "reason": "topology_role_unavailable",
  "message": "This node does not host the topology roles required for this endpoint.",
  "current_shape": "standalone_server",
  "current_process_class": "scheduler_node",
  "current_roles": ["scheduler"],
  "required_roles": ["api_ingress", "control_plane"],
  "missing_roles": ["api_ingress", "control_plane"]
}

GET /api/health, GET /api/ready et GET /api/cluster/info authentifié restent disponibles pour la présence et la découverte même sur les nœuds n'hébergeant pas l'interface actuelle de contrôle HTTP.

Contrôle d'initialisation des workflows​

Les routes authentifiées qui modifient ou servent le trafic workflow v2 rejettent aussi les requêtes si checks.workflow_v2.status du nœud répondant vaut blocked. Le contrôle intervient après validation du rôle et de la version du protocole, avant résolution de l'espace de noms. Une requête pendant un déploiement bloqué n'observe donc jamais son existence.

Lors d'un blocage, le serveur renvoie 503 avec reason: "workflow_v2_blocked" et :

  • blocked_by : liste ordonnée des blocages préalables de disponibilité (par exemple migrations) empêchant le service sûr de workflow v2.
  • remediation : instruction courte destinée à l'opérateur pour lever les blocages, reprise du champ checks.workflow_v2.remediation de /api/ready.

Les familles de routes soumises à ce contrôle sont :

  • Démarrage et modification de workflows : toutes les routes /api/workflows des groupes démarrage, description, commande et commande ciblant une exécution (par exemple POST /api/workflows, POST /api/workflows/{workflowId}/signal/{signalName}, POST /api/workflows/{workflowId}/runs/{runId}/cancel).
  • Modification des planifications : POST /api/schedules, PUT /api/schedules/{scheduleId}, DELETE /api/schedules/{scheduleId}, POST /api/schedules/{scheduleId}/pause, POST /api/schedules/{scheduleId}/resume, POST /api/schedules/{scheduleId}/trigger et POST /api/schedules/{scheduleId}/backfill.
  • Adaptateurs de passerelle : POST /api/bridge-adapters/webhook/{adapter}.
  • Protocole worker : toutes les routes /api/worker et /api/worker/*, dont l'inscription, le heartbeat et les opérations d'interrogation, finalisation, échec et heartbeat des tâches de workflow, de requête et d'activité.

Les lectures des planifications sont volontairement exemptées pour inspecter leur état pendant une reprise : GET /api/schedules, GET /api/schedules/{scheduleId} et GET /api/schedules/{scheduleId}/history restent accessibles tandis que le contrôle bloque les autres routes.

Les routes du plan de contrôle renvoient la charge de blocage dans leur enveloppe, avec l'en-tête X-Durable-Workflow-Control-Plane-Version. Les routes worker renvoient les mêmes champs reason, blocked_by et remediation dans leur enveloppe et conservent X-Durable-Workflow-Protocol-Version, pour réagir au motif machine au lieu de déduire l'état de la file d'un simple 503.

Exemple de réponse de blocage de POST /api/workflows lorsqu'une migration de sûreté du déploiement manque :

{
  "reason": "workflow_v2_blocked",
  "message": "This node is not ready to serve workflow v2 traffic until bootstrap blockers are cleared.",
  "blocked_by": ["migrations"],
  "remediation": "Restore database connectivity and migrate the workflow tables before relying on workflow v2 rollout-safety health."
}

La même charge est renvoyée dans l'enveloppe worker pour /api/worker/*. Les SDK peuvent continuer à se baser sur reason et réessayer après levée du blocage préalable.

Santé système par espace de noms​

GET /api/system/health est l'interface authentifiée de santé de sûreté du déploiement et de coordination d'un espace de noms. Elle exige l'authentification admin et X-Durable-Workflow-Control-Plane-Version: 2, résout l'espace de noms selon les règles normales du plan de contrôle et renvoie l'espace exact évalué avec l'instantané health actuel :

curl -sS "$DURABLE_WORKFLOW_SERVER_URL/api/system/health" \
  -H "Authorization: Bearer $DW_ADMIN_TOKEN" \
  -H "X-Namespace: orders-prod" \
  -H "X-Durable-Workflow-Control-Plane-Version: 2" \
  | jq '{namespace, status: .health.status, healthy: .health.healthy}'

Interprétez la charge ainsi :

  • namespace : espace dont l'état de déploiement/coordination a été évalué.
  • health.status et health.healthy : verdict global de santé lisible par machine pour cet espace de noms.
  • health.checks et health.categories : faits par interface de disponibilité, compatibilité, projection et coordination.
  • health.operator_metrics : métriques actuelles des files, workers et réparations de cet espace incluses dans le même instantané.
  • health.structural_limits : limites structurelles effectives et diagnostics associés appliqués par le serveur à cet espace de noms.

Plan de contrôle des workflows​

Les routes de workflow relèvent de l'opérateur/du plan de contrôle. Elles exigent un rôle operator ou admin et X-Durable-Workflow-Control-Plane-Version: 2.

MéthodeCheminRôle
GET/api/workflowsLister les instances de workflow. Accepte les filtres d'état, de type, de texte de requête et de limite.
POST/api/workflowsDémarrer une instance de workflow.
GET/api/workflows/{workflowId}Décrire l'exécution actuelle d'un identifiant de workflow.
GET/api/workflows/{workflowId}/debugRenvoyer des diagnostics bornés pour examiner une exécution bloquée.
GET/api/workflows/{workflowId}/runsLister les exécutions d'un identifiant de workflow.
GET/api/workflows/{workflowId}/runs/{runId}Décrire une exécution précise.
GET/api/workflows/{workflowId}/runs/{runId}/debugRenvoyer des diagnostics bornés pour une exécution sélectionnée.
GET/api/workflows/{workflowId}/runs/{runId}/historyParcourir par pages les événements d'historique d'une exécution.
GET/api/workflows/{workflowId}/runs/{runId}/history/exportExporter l'ensemble de relecture archivable d'une exécution.

Les requêtes de démarrage suivent la forme du plan de contrôle indépendante du langage :

curl -sS -X POST "$DURABLE_WORKFLOW_SERVER_URL/api/workflows" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: default" \
  -H "X-Durable-Workflow-Control-Plane-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "workflow_type": "orders.fulfillment",
    "workflow_id": "order-1001",
    "task_queue": "orders",
    "input": ["order-1001"],
    "memo": {"source": "api-reference"},
    "search_attributes": {"CustomerId": "cust-42"},
    "duplicate_policy": "fail"
  }'

duplicate_policy accepte uniquement fail et use-existing. Si le champ est omis ou vaut null, la politique est fail. Les deux politiques créent une exécution si l'identifiant du workflow n'a pas encore été utilisé.

PolitiqueUne exécution active existe déjàL'exécution existante est clôturée
fail (par défaut)Refuser le démarrage en double.Refuser le démarrage en double.
use-existingRenvoyer l'exécution existante en attente, en cours ou en sommeil, sans en démarrer une autre.Refuser le démarrage en double.

Aucune politique ne rouvre une exécution clôturée. Utilisez un nouvel identifiant de workflow pour une nouvelle exécution. reject n'est pas une valeur acceptée et entraîne une réponse HTTP 422.

Commandes de workflow​

Le serveur fournit aussi les routes coopératives request-cancellation. Consultez l'annulation coopérative pour le contrat de nettoyage borné et les exigences des workers.

Les commandes ciblant une instance opèrent sur l'exécution actuelle de l'identifiant de workflow :

MéthodeCheminRôle
POST/api/workflows/{workflowId}/signal/{signalName}Envoyer un signal.
POST/api/workflows/{workflowId}/query/{queryName}Exécuter une requête de lecture.
POST/api/workflows/{workflowId}/update/{updateName}Soumettre ou exécuter une mise à jour.
POST/api/workflows/{workflowId}/cancelFermer immédiatement l'exécution comme annulée ; ne reprend pas le nettoyage du workflow.
POST/api/workflows/{workflowId}/terminateForcer la terminaison.
POST/api/workflows/{workflowId}/repairDemander au serveur de réparer un état bloqué réessayable.
POST/api/workflows/{workflowId}/archiveArchiver une exécution de workflow fermée.

Les commandes ciblant une exécution rejettent explicitement les cibles historiques ou les mauvaises exécutions :

MéthodeCheminRôle
POST/api/workflows/{workflowId}/runs/{runId}/signal/{signalName}Envoyer un signal uniquement si l'exécution sélectionnée est actuelle.
POST/api/workflows/{workflowId}/runs/{runId}/query/{queryName}Exécuter une requête sur l'exécution sélectionnée.
POST/api/workflows/{workflowId}/runs/{runId}/update/{updateName}Soumettre ou exécuter une mise à jour uniquement sur l'exécution actuelle.
POST/api/workflows/{workflowId}/runs/{runId}/cancelAnnuler uniquement l'exécution actuelle sélectionnée.
POST/api/workflows/{workflowId}/runs/{runId}/terminateTerminer uniquement l'exécution actuelle sélectionnée.
POST/api/workflows/{workflowId}/runs/{runId}/repairRéparer uniquement l'exécution actuelle sélectionnée.
POST/api/workflows/{workflowId}/runs/{runId}/archiveArchiver uniquement l'exécution sélectionnée actuelle et fermée.

Les commandes transportent les valeurs métier dans des enveloppes Avro. Les SDK officiels les encodent automatiquement. Un client HTTP direct doit utiliser l’enveloppe {codec, blob} de l’encodeur Avro officiel ou la référence du runtime ci-dessous. Le document HTTP extérieur reste JSON ; le JSON métier brut n’est pas un autre codec de charge utile.

Espaces de noms et stockage​

Les routes des espaces de noms exigent les rôles operator ou admin. Leurs routes de modification et celles de stockage externe exigent le rôle admin.

MéthodeCheminRôle
GET/api/namespacesLister les espaces de noms.
POST/api/namespacesCréer un espace de noms.
GET/api/namespaces/{namespace}Décrire la rétention, les métadonnées et la politique de stockage d'un espace de noms.
PUT/api/namespaces/{namespace}Mettre à jour ses métadonnées ou sa rétention.
PUT/api/namespaces/{namespace}/external-storageConfigurer sa politique de stockage externe des charges utiles.
POST/api/storage/testEffectuer un aller-retour de petite et grande charge utile via le pilote de stockage externe configuré.

Les politiques de stockage externe permettent aux grandes enveloppes de porter des références stables plutôt que des octets bruts. Les politiques locales utilisent le chemin de système de fichiers configuré. Celles de stockage objet telles que s3, gcs et azure utilisent un disque explicitement configuré et les paramètres de bucket/préfixe sur le serveur.

Enveloppe de référence de charge utile externe​

Server accepte les références du runtime, pas les références avec URI fournisseur des utilitaires embarqués. Une requête contenant external_storage est refusée avec HTTP 422 et external_payload_unsupported. Ne copiez pas de référence file://, s3://, gs:// ou azure:// dans une requête Server.

L’enveloppe du runtime contient exactement codec et external_payload :

{
  "codec": "avro",
  "external_payload": {
    "schema": "durable-workflow.v2.runtime-external-payload-reference.v1",
    "reference_id": "ep_01ARZ3NDEKTSV4RRFFQ69G5FAV",

Transport des charges externes du runtime​

Découvrez namespace.external_payload_storage.transport via GET /api/cluster/info. Son schéma est durable-workflow.v2.runtime-external-payload-transport.v1, version 1. Utilisez ses routes et limites uniquement lorsque le stockage de l’espace de noms est available. Server conserve les identifiants fournisseur et ne renvoie aucun emplacement fournisseur.

MéthodeCheminRésultat
POST/api/external-payloads/v1Téléverse des octets encodés bornés. 201 renvoie le schéma durable-workflow.v2.runtime-external-payload-upload.v1, transport_version: 1 et reference.
GET/api/external-payloads/v1/{referenceId}Récupère et vérifie les octets encodés référencés. 200 renvoie application/octet-stream.

Les deux routes utilisent un identifiant ordinaire du runtime avec le rôle worker, operator ou admin et X-Namespace. Toutes deux exigent X-Durable-Workflow-Payload-Codec, X-Durable-Workflow-Payload-Size et X-Durable-Workflow-Payload-SHA256. Le téléversement exige aussi Content-Type: application/octet-stream. Une recherche entre espaces de noms répond introuvable sans révéler les objets d’autrui. Posséder un identifiant ne donne ni accès ni autorité pour terminer un workflow.

Les octets téléversés sont les octets UTF-8 de la chaîne base64 blob de l’enveloppe Avro officielle, sans saut de ligne ajouté. Ce n’est ni l’Avro binaire décodé ni du JSON métier. Calculez longueur et SHA-256 sur ces octets précis. Par exemple, après installation du SDK Python :

python - <<'PY'
from pathlib import Path
from durable_workflow.serializer import encode

Path("payload.avro.txt").write_bytes(
    encode([{"message": "large value", "optional": None}]).encode("utf-8")
)
PY

PAYLOAD_SIZE=$(wc -c < payload.avro.txt | tr -d ' ')
PAYLOAD_SHA256=$(sha256sum payload.avro.txt | cut -d ' ' -f 1)

curl --fail-with-body -sS -X POST "$DURABLE_WORKFLOW_SERVER_URL/api/external-payloads/v1" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: billing" \
  -H "Content-Type: application/octet-stream" \
  -H "X-Durable-Workflow-Payload-Codec: avro" \
  -H "X-Durable-Workflow-Payload-Size: $PAYLOAD_SIZE" \
  -H "X-Durable-Workflow-Payload-SHA256: $PAYLOAD_SHA256" \
  --data-binary @payload.avro.txt > upload.json

REFERENCE_ID=$(jq -r '.reference.reference_id' upload.json)
curl --fail-with-body -sS "$DURABLE_WORKFLOW_SERVER_URL/api/external-payloads/v1/$REFERENCE_ID" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: billing" \
  -H "X-Durable-Workflow-Payload-Codec: avro" \
  -H "X-Durable-Workflow-Payload-Size: $PAYLOAD_SIZE" \
  -H "X-Durable-Workflow-Payload-SHA256: $PAYLOAD_SHA256" \
  -o fetched.avro.txt
cmp payload.avro.txt fetched.avro.txt

Le téléversement vérifie l’intégrité des octets avant d’enregistrer une référence. Il n’exécute aucun workflow et ne prouve pas que les octets sont une charge métier valide. La première requête vérifiée incorporant un état revendique la référence ; la validation et les contrôles ordinaires de requête, d’espace de noms, de tentative de tâche et de bail restent applicables. Pour les téléversements de terminaison des workers, utilisez le SDK officiel et son contexte découvert plutôt que d’inventer une autorisation de bail dans un client direct.

Lisez limits.max_payload_bytes, request_timeout_seconds et abandoned_upload_expiry_seconds dans le manifeste. Les quotas d’octets et d’objets, limites ordinaires de requête et limites de téléversement de terminaison s’appliquent aussi. Selon le seuil, une valeur exactement égale reste intégrée. Les SDK externalisent les valeurs supérieures et peuvent en externaliser d’autres pour respecter la limite de la requête agrégée.

RésultatStatut HTTPAction
Référence absente ou expirée404 / 410Restaurez l’objet requis ou corrigez la référence. Ne décodez pas une absence comme null.
Non autorisé401 / 403Corrigez identifiant, rôle ou autorisation de l’espace de noms.
Enveloppe non prise en charge ou intégrité incorrecte415 / 422Corrigez codec, champs, taille, empreinte ou octets encodés.
Charge trop grande413Réduisez la valeur encodée ou utilisez une politique supérieure autorisée.
Quota ou autorisation de téléversement épuisés429Inspectez la capacité et réessayez uniquement dans le budget d’origine.
Stockage indisponible503Rétablissez la disponibilité avant de réessayer dans ce même budget.
Terminaison périmée ou conflictuelle409Ne réessayez pas avec une identité de tâche inventée ou un nouveau bail.

Server gère la rétention. Aucune route de suppression cliente n’existe. L’éviction du cache ne doit pas supprimer l’objet. Les téléversements non revendiqués peuvent expirer ; propriétaires conservés, objets partagés, défaillances du stockage et blocages de sauvegarde affectent le nettoyage. Un export d’historique contenant une référence n’est pas une sauvegarde autonome de ses octets.

API d'administration du catalogue de services​

Les routes du catalogue de services sont des routes authentifiées admin du plan de contrôle. Elles utilisent les mêmes résolution d'espace de noms, contrôle des rôles de topologie et exigence X-Durable-Workflow-Control-Plane-Version: 2 que le reste du plan hébergé.

Cette famille de routes inscrit les métadonnées de points de terminaison, services et opérations propres à un espace de noms pour le catalogue inter-espaces de noms. Les noms sont insensibles à la casse en entrée et normalisés en minuscules dans les réponses et recherches.

MéthodeCheminRôle
GET/api/service-endpointsLister les points de terminaison de services de l'espace de noms actuel.
POST/api/service-endpointsCréer un point de terminaison de service.
GET/api/service-endpoints/{endpointName}Décrire un point de terminaison.
PUT/api/service-endpoints/{endpointName}Mettre à jour sa description ou ses métadonnées.
DELETE/api/service-endpoints/{endpointName}Supprimer un point de terminaison inutilisé.
GET/api/service-endpoints/{endpointName}/servicesLister les services inscrits sous un point de terminaison.
POST/api/service-endpoints/{endpointName}/servicesCréer un service sous un point de terminaison.
GET/api/service-endpoints/{endpointName}/services/{serviceName}Décrire un service.
PUT/api/service-endpoints/{endpointName}/services/{serviceName}Mettre à jour sa description ou ses métadonnées.
DELETE/api/service-endpoints/{endpointName}/services/{serviceName}Supprimer un service inutilisé.
GET/api/service-endpoints/{endpointName}/services/{serviceName}/operationsLister les opérations inscrites sous un service.
POST/api/service-endpoints/{endpointName}/services/{serviceName}/operationsCréer une liaison d'opération.
GET/api/service-endpoints/{endpointName}/services/{serviceName}/operations/{operationName}Décrire une opération.

PUT/api/service-endpoints/{endpointName}/services/{serviceName}/operations/{operationName}Mettre à jour une liaison d'opération.
DELETE/api/service-endpoints/{endpointName}/services/{serviceName}/operations/{operationName}Supprimer une opération inutilisée.

Les collections de réponse utilisent les tableaux service_endpoints, services ou operations. Chaque ressource inclut un nom stable en minuscules, des métadonnées et des horodatages :

  • Les points de terminaison renvoient id, namespace, endpoint_name, description, metadata, created_at et updated_at.
  • Les services ajoutent endpoint_id et service_name.
  • Les opérations ajoutent service_id, operation_name, operation_mode, handler_binding_kind, handler_target_reference, handler_binding, deadline_policy, idempotency_policy, cancellation_policy, retry_policy, boundary_policy et metadata.
  • Les instantanés d'appels ajoutent caller_namespace, les identifiants de workflow appelant et lié, status, resolved_binding_kind, resolved_target_reference, les références de charges utiles, instantanés de politiques et horodatages du cycle de vie comme accepted_at, started_at, completed_at, failed_at et cancelled_at.

Les requêtes de création/mise à jour d'opération utilisent les mêmes noms de champs JSON que la réponse. operation_mode vaut sync ou async. handler_binding_kind vaut start_workflow, signal_workflow, update_workflow, query_workflow, activity_execution ou invocable_http. Une nouvelle opération doit fournir handler_target_reference ou une charge handler_binding non vide.

Le détail imbriqué de l'appel expose aussi service_call_attempts, retry_attempt_count, le call_deadline_at d'origine, les métadonnées typées d'échec et le result_envelope Avro conservé. Les appels acceptés ou démarrés ne sont pas terminaux. L'appelant workflow attendant la fin reçoit le résultat réel ou l'échec/annulation terminal du workflow lié, en conservant l'identité et l'échéance de l'appel d'origine.

Utilisez l'inspection CLI des appels de service ou le catalogue Waterline pour inspecter cet appel d'origine. L'inspection ne demande pas une autre exécution du service.

Les suppressions sont refusées avec HTTP 409 et un motif nommé tant que des dépendants existent, comme endpoint_has_services, service_has_operations ou operation_has_service_calls.

Adaptateurs de passerelle​

Les adaptateurs de passerelle sont des points d'entrée bornés. Ils n'exécutent pas de code workflow ; ils transmettent les événements au plan de contrôle et renvoient un résultat nommé.

MéthodeCheminRôle
POST/api/bridge-adapters/webhook/{adapter}Démarrer, signaler ou mettre à jour un workflow depuis un événement de type webhook.

Exemple :

curl -sS -X POST "$DURABLE_WORKFLOW_SERVER_URL/api/bridge-adapters/webhook/stripe" \
  -H "Authorization: Bearer $DURABLE_WORKFLOW_AUTH_TOKEN" \
  -H "X-Namespace: default" \
  -H "X-Durable-Workflow-Control-Plane-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "start_workflow",
    "idempotency_key": "evt_1001",
    "target": {
      "workflow_type": "orders.fulfillment",
      "task_queue": "orders",
      "business_key": "order-1001"
    },
    "input": {"order_id": "order-1001"}
  }'

Utilisez les champs de réponse comme outcome, reason, idempotency_key et control_plane_outcome au lieu de déduire le comportement du seul état HTTP.

Quand worker_protocol.server_capabilities.poll_status vaut true, chaque réponse d'interrogation de tâche de workflow, d'activité et de requête porte un champ poll_status lisible par machine. Examinez-le avant les champs de charge utile propres à la route :

poll_statusÉtat HTTP habituelSignification

empty200Aucune tâche correspondante n'était prête avant le retour.
throttled200La file est visible, mais les limites d'admission des baux ou de distribution ont retenu une nouvelle tâche.
unavailable503 ou 200Le serveur n'a pas pu coordonner sans risque un chemin d'interrogation et a renvoyé une indisponibilité typée plutôt qu'un résultat vide silencieux.
draining409La cohorte inscrite du worker est en drainage ; le serveur refuse un nouveau bail et renvoie reason: "worker_draining".

Ces routes exposent les diagnostics opérationnels des flottes de workers et de l'admission des files. Elles appartiennent au plan de contrôle.

Filtres et continuation des listes de planifications​

GET /api/schedules lit l’espace de noms de la requête. La qualification de PHP Server publié avec une installation normale vérifie les filtres combinés et la continuation. Envoyez les paramètres suivants avec l’encodage URL habituel :

ParamètreValeur acceptée
statusactive ou paused.
workflow_typeType de workflow non vide, de 255 caractères au maximum. Les espaces seuls sont invalides.
queryExpression de visibilité non vide, de 2048 caractères au maximum.
page_sizeEntier de 1 à 200, 50 par défaut.
next_page_tokenJeton opaque non vide, de 8192 caractères au maximum.

Le statut, le type de workflow et les prédicats de requête se combinent avec AND. Une requête de visibilité des planifications accepte des prédicats d’égalité reliés par AND, par exemple Region = "eu" AND TaskQueue = "orders". Les champs intégrés sont ScheduleId, Status, WorkflowType, TaskQueue et Note. Les autres champs doivent être des attributs de recherche enregistrés dans l’espace de noms de la requête, avec des littéraux correspondant à leurs types. L’égalité sur un attribut keyword_list teste l’appartenance. Les opérateurs tels que OR, NOT, IN, LIKE et les comparaisons d’intervalle ne sont pas acceptés et renvoient 422.

La réponse contient namespace, schedules, schedule_count pour cette page et next_page_token. Continuez uniquement si un jeton est renvoyé. Transmettez-le sans modification avec les mêmes espace de noms, statut, type de workflow et requête. Le jeton est lié à la sélection de filtres analysée. La pagination lit des données évolutives plutôt qu’un instantané. Un curseur supprimé ou ne correspondant plus aux filtres impose un nouveau parcours sans jeton.

422 / validation_failedCorrigez les erreurs de validation des champs.
422 / unsupported_schedule_visibility_fieldUtilisez un champ intégré ou un attribut enregistré dans cet espace de noms.
422 / unsupported_schedule_visibility_predicateUtilisez des prédicats d’égalité reliés par AND.

Les exemples CLI de filtrage et de pagination des planifications suivent le même contrat. Un refus de liste indique le champ field concerné et les détails de validation. Examinez le motif avant de réessayer.

Pour la rétention de PHP Server, la route d'état lit la politique actuelle de l'espace de noms et renvoie une liste bornée d'exécutions admissibles. Modifier la politique affecte aussi l'historique fermé existant. Une passe sans filtre sélectionne les exécutions expirées ; des run_ids explicites ciblent directement les exécutions fermées sans filtre d'âge borné. La rétention illimitée et les protections des archives restent applicables. Revoyez la procédure de rétention et les étapes de sauvegarde avant de modifier la politique ou de nettoyer.

/api/system/health répond rapidement à la question de la santé suffisante d'un espace pour continuer à recevoir du trafic. Il renvoie {namespace, health}, où health contient les contrôles de sûreté du déploiement catégorisés, l'instantané imbriqué health.operator_metrics et le résumé des limites structurelles utilisé par l'interface de santé.

/api/system/operator-metrics complète /api/cluster/info à l'échelle d'un espace de noms pour obtenir les nombres bruts de tâches en retard, l'âge du blocage par compatibilité, le détail de la flotte et les autres métriques derrière le résumé de santé.

/api/system/metrics est une interface JSON opérateur, pas un point de collecte Prometheus. Les noms et dimensions des métriques sont bornés par la politique de croissance bornée du serveur.

Contrat d'erreur​

Les réponses d'erreur utilisent des codes d'état HTTP et des motifs nommés lisibles par machine. Les clients devraient examiner reason ou les motifs imbriqués du plan de contrôle/protocole worker, pas les messages rédigés.

États courants :

ÉtatSignification
400En-tête de protocole/version absent ou incompatible, requête mal formée ou méthode de route non prise en charge.
401Authentification absente ou invalide.
403Le jeton authentifié n'a pas le rôle requis.
404Espace de noms, workflow, exécution, planification, worker ou attribut de recherche introuvable.
409Doublon ou conflit, comme un workflow déjà démarré ou une cible d'exécution invalide.
422Échec de validation ; la réponse contient les détails par champ.
429Capacité d'admission ou de file de tâches pleine.
503La requête a atteint un nœud sans les rôles de topologie requis. Les routes hébergées renvoient reason: "topology_role_unavailable" avec current_shape, current_process_class, current_roles, required_roles et missing_roles. Le même état avec reason: "workflow_v2_blocked", blocked_by et remediation couvre les routes de démarrage/modification de workflow, modification de planification, adaptateur de passerelle et protocole worker pendant un blocage d'initialisation v2. Les lectures de planification (GET /api/schedules, GET /api/schedules/{scheduleId}, GET /api/schedules/{scheduleId}/history) restent disponibles pour inspecter l'état pendant la reprise.

Les réponses de validation incluent reason: "validation_failed" avec errors ou validation_errors. Les réponses des commandes workflow projettent aussi les détails de validation et d'opération dans l'objet control_plane imbriqué.

SDK Rust

Ce guide présente le SDK accessible à tous. Consultez ensuite la référence d’API générée pour les types et méthodes individuels. Aucun compte Cloud n’est nécessaire : le parcours principal utilise la crate Rust publiée avec un Server auto-hébergé. Les développeurs déjà inscrits à l’accès anticipé contrôlé Durable Workflow Cloud peuvent choisir le démarrage rapide avec runtime géré, clairement séparé.

Le SDK Rust officiel permet d’écrire des workflows, au-delà du rôle de client compatible avec le protocole. Rust permet de créer des workflows déterministes, des activités et des services worker de longue durée selon le même modèle d’exécution durable que PHP et Python. Le client asynchrone du plan de contrôle démarre les exécutions, envoie des signaux, effectue des requêtes de lecture et mises à jour, annule, arrête de force et attend les résultats. Le runtime worker relit l’historique, exécute les gestionnaires de workflow, d’activité et de mise à jour, émet les battements de cœur worker et activité et échange des données indépendantes du langage avec un Server auto-hébergé ou un runtime d’espace de noms Durable Workflow Cloud.

L’accueil de la documentation Rust fournit l’index du SDK et les points d’entrée généraux. Pour les modules, structures, traits et méthodes de la crate, consultez la référence d’API générée du SDK Rust.

Le SDK Rust stable prend en charge les temporisateurs durables, workflows enfants, nouvelles tentatives et délais d’activité, activités locales, sessions de worker, exécution sticky, signaux, gestionnaires de requête de lecture par relecture, annulation et arrêt forcé, échéances de workflow appliquées par le serveur, effets de bord typés, marqueurs de version, mises à jour et échecs terminaux ou de relecture typés. Il ne revendique pas encore la gestion des planifications. Consultez l’index des capacités 2.0 pour connaître l’étendue exacte de chaque SDK.

Essayer l’environnement local de l’application d’exemple​

Pour le parcours de création le plus court sans Cloud, ouvrez la branche main de l’application d’exemple dans GitHub Codespaces et exécutez :

scripts/playground rust

L’environnement local génère le code de workflow et d’activité appartenant à l’appelant, sélectionne les artefacts stables actuels et démarre Server et Waterline publiés. Il attend un enregistrement de worker dont l’identité, le type de workflow, le type d’activité et la file correspondent au contrat généré avant de démarrer le workflow. La réussite exige le résultat terminé attendu et l’historique requis. Le terminal affiche ensuite le lien exact de l’exécution Waterline locale et le chemin des preuves JSON structurées.

Ce modèle volontairement réduit privilégie le transport et utilise serde_json::Value. Ce n’est pas le seul contrat recommandé pour une application Rust. Poursuivez avec l’exemple d’entrées/sorties typées, l’exemple de politique d’activité couvrant tentatives, délais, battements de cœur et échecs terminaux et l’exemple d’activité locale. Le paquet, l’exemple du dépôt et la référence d’API générée restent les parcours directs pour les utilisateurs ne souhaitant pas l’application d’exemple.

Paquet et code source​

  • Crate sur crates.io
  • Dépôt source

Installez le SDK Rust de la dernière combinaison d’artefacts qualifiée avec succès. La dépendance exacte est générée depuis la même référence lisible par machine que le démarrage rapide Server :

cargo add durable-workflow@=4.2.0

Ou déclarez directement la même dépendance qualifiée dans Cargo.toml :

[dependencies]
durable-workflow = "=4.2.0"

La crate nécessite Rust 1.86 ou ultérieur. Ses métadonnées enregistrent la version Server utilisée pour qualifier le SDK, les versions par défaut et minimale du protocole worker, et le plan de contrôle 2. La compatibilité avec un Server plus récent est vérifiée séparément. Pendant le déploiement, utilisez les manifestes de protocole et capacités annoncés par GET /api/cluster/info.

Server négocie les en-têtes du protocole worker dans la version majeure 1 : un serveur annonçant 1.N accepte un en-tête 1.M uniquement si M <= N. Le SDK Rust 3.5.0 utilise par défaut X-Durable-Workflow-Protocol-Version: 1.20 et exige un serveur annonçant 1.20 ou ultérieur. Pour un ancien Server compatible, sélectionnez WorkerProtocolVersion::V119 via le réglage worker_protocol_version du constructeur de client. Le SDK 3.4.x utilise 1.19 par défaut. Le profil facultatif d’annulation coopérative exige 1.20 et refuse une sélection explicite de 1.19.

La négociation refuse tout cas non reconnu. Un en-tête absent ou mal formé, une autre version majeure ou une version mineure worker plus récente que celle annoncée par Server est refusée. Les versions de publication SDK et Server sont suivies indépendamment. Leurs manifestes de protocole runtime déterminent la compatibilité.

Listes de workflows et historique complet d’une exécution​

Ces API nécessitent Rust SDK 4.6.0 ou ultérieur ; vérifiez Cargo.lock, car la combinaison d’installation précédente peut choisir un crate plus ancien. L’acceptation du paquet installé normalement vérifie trois pages de liste, six d’historique, un payload de 128 KiB, export/replay et l’exemple en lecture seule avec Server 2.11.0 publié. Les outils de test hors ligne nécessitent 4.5.0 ; ces méthodes et itérateurs de liste/historique nécessitent 4.6.0. La combinaison Server/SDK sélectionnée reste inchangée.

Client::list_workflows(WorkflowListOptions) et Client::get_workflow_history(workflow_id, run_id, WorkflowHistoryOptions) renvoient chacun une page. Continuez manuellement avec son next_page_token opaque, ou utilisez les itérateurs paresseux pour une lecture complète. Ils préservent validation, filtres et namespace du Server ; ils n’ajoutent ni champ ni grammaire de requête. Par exemple, trouvez une exécution ouverte par un attribut keyword enregistré :

use durable_workflow::WorkflowListOptions;
async fn find(client: durable_workflow::Client) -> durable_workflow::Result<()> {
let mut matches = client.iter_workflows(
    WorkflowListOptions::new()
        .workflow_type("payments")
        .status("running")
        .query("OrderRef = 'order-42'")
        .page_size(2),
);
match (matches.next().await?, matches.next().await?) {
    (Some(run), None) => println!("open run: {} / {}", run.workflow_id, run.run_id),
    (None, _) => println!("no open run"),
    _ => println!("multiple open runs; refine the query"),
}
Ok(())
}

Le filtre Server status=running sélectionne le groupe d’états actif, y compris les états bruts pending et waiting. WorkflowSummary conserve status, status_bucket, is_terminal, les attributs de recherche et les métadonnées inconnues dans raw. Ces attributs ne sont pas uniques : le filtre peut trouver un parent et les enfants ayant hérité de sa valeur. Traitez zéro, un et plusieurs résultats comme ci-dessus. Créez le client dans le namespace voulu avant l’itérateur ; namespace et filtres restent fixes entre les tokens.

Lisez toute l’exécution sélectionnée sans charger toutes les pages à la fois :

use durable_workflow::WorkflowHistoryOptions;
async fn audit(client: durable_workflow::Client) -> durable_workflow::Result<()> {
let mut events = client.iter_workflow_history(
    "payment-42", "selected-run-id", WorkflowHistoryOptions::new().page_size(100),
);
while let Some(event) = events.next().await? {
    println!("{}", event.event_type);
}
Ok(())
}

iter_workflows(options) fournit chaque WorkflowSummary via next().await. Les deux itérateurs proposent into_stream() pour futures_util::TryStreamExt ; épinglez le stream avant de le sonder. Leur construction n’effectue aucun I/O ; la page suivante est chargée après épuisement de l’actuelle. Un token nul/vide termine ; une page vide avec token est suivie. Les tokens répétés ou cycliques renvoient Error::Pagination avec un état borné. Une page en échec conserve l’erreur typée initiale, puis l’itérateur termine. Traitez l’erreur : une lecture partielle n’est pas complète. Collecter un stream stocke tous les éléments collectés.

L’historique conserve l’identité workflow/exécution d’origine et énumère les événements disponibles ; il ne suit pas continue-as-new et ne s’abonne pas indéfiniment. Métadonnées et enveloppes wire des payloads sont conservées. Pour le replay hors ligne, utilisez Client::export_workflow_history avec testing::WorkflowHistory::from_export plutôt qu’une page partielle. Voir le replay hors ligne.

Server 2.11 publié utilise par défaut 50 lignes de liste (maximum 200) et 100 événements d’historique (maximum 1 000) par page. Les tailles sont transmises telles quelles pour validation du Server. Arrêtez-vous dès que les résultats suffisent, choisissez une taille adaptée et un timeout applicatif. La pagination n’ajoute aucune isolation par instantané lorsque les exécutions changent simultanément. Voir l’exemple publié en lecture seule, l’API Client et les types de pagination.

Métriques et export Prometheus​

Ces API nécessitent Rust SDK 4.7.0 ou ultérieur. Vérifiez Cargo.lock : la combinaison précédente peut choisir un ancien crate. L’acceptation installée normalement vérifie quatre contrôles HTTP, les six métriques d’un vrai worker avec Server 2.11.0 publié et l’exemple d’export. Ce minimum ne change pas la combinaison sélectionnée.

Le recorder par défaut est no-op. Fournissez un Arc<dyn metrics::MetricsRecorder> implémentant increment(name, count, tags) et record(name, seconds, tags). Le client, ses clones et les nouveaux workers en héritent. Worker::metrics_recorder remplace les observations poll/task du worker ; les requêtes gardent le recorder du client. Les callbacks doivent être rapides et gérer localement les échecs d’exporter. Les paniques avec unwinding sont isolées des résultats SDK ; ce hook ne corrige ni exporter bloquant ni arrêt brutal du processus.

Chaque requête, poll ou traitement d’une tâche acquise incrémente un compteur de un et enregistre une durée monotone non négative en secondes. Les six noms stables sont :

CompteurHistogramme de durée
durable_workflow_client_requestsdurable_workflow_client_request_duration_seconds
durable_workflow_worker_pollsdurable_workflow_worker_poll_duration_seconds
durable_workflow_worker_tasksdurable_workflow_worker_task_duration_seconds

Les clés client sont exactement method, route, plane, status_code, outcome ; celles du worker sont task_kind, task_queue, outcome. Les modèles de route revus excluent ID, chaînes de requête, payloads et secrets ; les chemins inconnus utilisent unknown. Les noms de file dépendent de l’application : gardez un ensemble borné, pas une file par exécution.

Les résultats client incluent ok, http_error, bridge_rejected, TransportError, TimeoutError, SdkError et pending pour un future annulé. status_code conserve le statut HTTP décimal observé, sinon none. Les noms d’exceptions Rust peuvent différer de ceux d’autres SDK.

Une observation client inclut les réessais internes de transport/storage admission et le traitement réponse/payload ; les appels distincts gérés par l’application/worker sont séparés. L’itérateur paresseux observe chaque page chargée. Les polls incluent retry/backoff gérés et distinguent task, empty, backpressure, error. Les résultats task completed, failed, expired décrivent le traitement, pas l’état terminal du workflow. Ce sont des observations de processus, pas des comptes durables, unités facturables ou latences schedule-to-start ; une perte brutale peut omettre l’échantillon final.

Pour l’adaptateur officiel Prometheus, activez le feature Cargo facultatif metrics-prometheus. Cet exemple utilise les dépendances publiées :

[dependencies]
durable-workflow = { version = "=4.7.0", features = ["metrics-prometheus"] }
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }

Enregistrez l’exemple publié dans examples/metrics_prometheus.rs. Ces octets exacts ont été compilés et exécutés lors de l’acceptation installée ; l’exemple affiche les métriques d’une requête de santé :

//! Preview application-owned Prometheus export; serve `encode()` from your HTTP metrics route.
use durable_workflow::{metrics::PrometheusMetrics, Client};
use std::sync::Arc;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let recorder = Arc::new(PrometheusMetrics::new()?);
    let client = Client::builder(std::env::var("DURABLE_WORKFLOW_SERVER_URL")?)
        .token(std::env::var("DURABLE_WORKFLOW_AUTH_TOKEN").ok())
        .metrics_recorder(recorder.clone())
        .build()?;
    client.health().await?;
    // Workers inherit this client recorder; Worker::metrics_recorder overrides
    // only worker poll/task observations. Applications own the scrape endpoint.
    print!("{}", String::from_utf8(recorder.encode()?)?);
    Ok(())
}

Exécutez-le avec votre Server auto-hébergé :

DURABLE_WORKFLOW_SERVER_URL=http://localhost:8080 \
DURABLE_WORKFLOW_AUTH_TOKEN=your-token \
cargo run --features metrics-prometheus --example metrics_prometheus

PrometheusMetrics::new() possède un registre dédié basé sur le client officiel Prometheus Rust 0.14. Servez les octets encode() depuis la route métriques de l’application avec Content-Type: text/plain; version=0.0.4. L’adaptateur ne crée ni listener ni registre global. L’application gère accès/authentification de scrape, exposition réseau, ressources et arrêt. Les compteurs ajoutent _total ; les histogrammes utilisent bucket/sum/count. registry() permet collecte et métriques supplémentaires de l’application.

Pour les métriques OpenTelemetry, implémentez le recorder avec votre meter existant : compteurs d’unité 1, histogrammes en secondes s, noms/tags exacts ci-dessus. Provider, agrégation, labels de ressources et cycle de l’exporter restent applicatifs. Cela est distinct du tracing d’exécution. Voir l’API recorder, l’API Prometheus et le contrat publié.

Concurrence des tâches du worker​

Les voies bornées ci-dessous nécessitent Rust SDK 4.3.1 ou ultérieur. Vérifiez la version dans Cargo.lock : l’installation fixée plus haut appartient à une autre combinaison qualifiée et peut sélectionner un ancien SDK. La vérification du paquet publié confirme trois emplacements configurés, un quatrième callback admis après libération d’un emplacement et sept workflows terminés, dont un échec d’activité traité. Les exigences de protocole Server précédentes restent applicables.

Worker::max_concurrent_workflow_tasks(...) et Worker::max_concurrent_activity_tasks(...) valent chacun 10 par défaut. run() et run_until() utilisent des voies bornées indépendantes pour workflow et activité distante. Choisissez 1 pour une exécution séquentielle au sein de cette famille de tâches. Par exemple, configurez un client existant avant d’enregistrer les handlers applicatifs :

use durable_workflow::Worker;

let mut worker = Worker::new(client.clone(), "payments")
    .max_concurrent_workflow_tasks(1)
    .max_concurrent_activity_tasks(1);

Enregistrez les handlers, puis lancez run() ou run_until() normalement. Deux limites à un permettent encore une tâche de workflow et une tâche d’activité distante simultanées. Les requêtes de lecture gardent leur propre voie de polling. Les clones partagent la capacité configurée, y compris entre appels simultanés à run_once() ; cloner ne crée pas de quota indépendant supplémentaire.

La disponibilité des heartbeats suit les tâches réellement réclamées : chargement d’entrée/historique, exécution et confirmation. Un long poll vide laisse la capacité disponible. Succès, échec, refus et annulation libèrent l’emplacement local. Les activités locales inline occupent leur emplacement de tâche de workflow et contournent le pool distant ; la limite d’activité ne borne donc pas séparément l’exécution inline entre workflows.

Les handlers sont des futures async Tokio et doivent céder la main. Utilisez tokio::task::spawn_blocking ou un processus séparé pour le travail bloquant, avec une limite explicite d’annulation et d’arrêt. Augmenter la concurrence n’isole pas le CPU et ne rend pas un thread détaché annulable. Voir l’API Worker du SDK installé.

Budgets de tentatives reçus par une activité​

Rust SDK 4.8.0 ou ultérieur expose ActivityContext::retry_info() dans les gestionnaires d’activités en mode service. Vérifiez le crate installé dans Cargo.lock : la version d’installation sélectionnée séparément ci-dessus peut être plus ancienne. Le ActivityRetryInfo renvoyé conserve le attempt_number() original et le JSON policy() reçu, y compris les champs inconnus. Cet instantané immuable de l’invocation est indépendant des champs de compatibilité modifiables du contexte.

Utilisez attempt_limit() et is_last_configured_attempt() pour interpréter le budget reçu :

Politique de tentatives reçueActivityAttemptLimitDernière tentative configurée
Objet avec un entier positif max_attempts: nBounded(n), première tentative compriseSome(true) lorsque la tentative originale atteint ou dépasse n, sinon Some(false)
Objet avec max_attempts: nullUnlimitedSome(false)
Politique omise, null à la racine, champ absent ou limite invalideUnknownNone

Le helper renvoie aussi None pour un numéro de tentative nul invalide. Le comportement de planification par défaut du runtime ne prouve pas les métadonnées reçues : le contrôle publié sur Server 2.11.0 sans politique définie par l’auteur omet l’instantané et indique donc Unknown, sans déduire Bounded(1). policy() distingue une politique omise d’un JSON null reçu sans considérer l’un ou l’autre comme illimité. L’acceptation avec installation normale comprend ce contrôle et l’exemple ci-dessous.

Pour choisir une solution de repli ou enregistrer une alerte applicative lors de la dernière tentative configurée, enregistrez un gestionnaire sur votre Worker existant :

use durable_workflow::{json, Worker};

pub fn register_charge(worker: &mut Worker) {
    worker.register_activity("charge", |ctx, _| async move {
        let retry = ctx.retry_info();
        if retry.is_last_configured_attempt() == Some(true) {
            // Select a final-attempt fallback or record an application alert.
        }
        Ok(json!({"attempt": retry.attempt_number()}))
    });
}

Some(false) ne promet pas une nouvelle exécution. Un échec non réessayable, l’annulation, la fermeture du workflow ou des échéances dépassées peuvent terminer le travail avant épuisement du budget configuré. Le helper ne change pas l’admission des tentatives et n’accorde pas de temps supplémentaire.

Les activités locales et les appels directs à testing::WorkflowEnvironment::run_activity n’ont pas d’instantané reçu du Server et indiquent une politique inconnue. Les nouveaux tests run_workflow exposent l’instantané modélisé enregistré dans leur historique généré. Cette sémantique de test ne prouve pas qu’un Server déployé transmet une politique. Voir ActivityRetryInfo et ActivityAttemptLimit.

Identité stable des activités et idempotence des effets externes​

Le SDK Rust 4.9.0 ou ultérieur expose l’identité reçue à l’origine via ActivityContext. Vérifiez le crate installé dans Cargo.lock : la version d’installation choisie séparément ci-dessus peut être plus ancienne. Ces méthodes renvoient des valeurs Option<&str> immuables capturées dans le claim initial, y compris pour les activités des sessions de worker.

MéthodeIdentité et usage
activity_execution_id()Une exécution logique d’activité à travers ses tentatives ; servez-vous-en pour dédupliquer une opération externe.
workflow_id()ID de l’instance de workflow propriétaire ; utilisez-le pour la corrélation métier.
run_id()ID du run de workflow propriétaire ; utilisez-le pour corréler cette exécution précise.

Dérivez une clé pour une opération précise et transmettez-la à une API externe idempotente ou à un registre durable des effets. Ce handler construit seulement la clé : il ne débite aucun paiement et ne réalise pas la déduplication externe. Il refuse une identité absente avant tout effet ; l’application peut aussi fournir sa propre clé métier explicitement stable.

use durable_workflow::{json, ActivityError, Worker};

pub fn register_charge(worker: &mut Worker) {
    worker.register_activity("charge", |ctx, _| async move {
        let execution_id = ctx.activity_execution_id().ok_or_else(|| {
            ActivityError::new("MissingActivityIdentity", "Server activity identity is required")
                .non_retryable(true)
        })?;
        // Pass this key to an idempotent downstream API or durable effect ledger.
        let key = format!("payments:charge:{execution_id}");
        Ok(json!({
            "idempotency_key": key,
            "workflow_id": ctx.workflow_id(),
            "run_id": ctx.run_id(),
        }))
    });
}

Lorsqu’un ancien Server omet ces champs, ils restent None. Ne remplacez jamais un ID logique absent par un ID de tâche, un ID de tentative ou un numéro de tentative : la clé changerait lors du retry. Les activités locales inline peuvent recevoir les vrais ID du workflow/run parent, mais ne possèdent pas d’ID d’exécution d’activité du Server avant l’enregistrement de leur commande. Les tests d’activité sans Server ne reçoivent aucune identité de claim.

Une clé stable ne permet d’éviter les effets en double que si le système externe respecte cette clé. La livraison reste au moins une fois ; cette API ne rend pas les effets externes exactement une fois, ne restaure pas la progression des heartbeats et ne fournit pas de checkpoints d’activité permettant une reprise.

Consultez les méthodes d’identité d’ActivityContext et la vérification d’installation normale 4.9.0 avec les contrôles ordinary/cooperative, locaux et de sessions de worker. Le contrat commun figure dans les garanties d’exécution.

Rapports d’échec bornés​

Ces limites nécessitent Rust SDK 4.10.1 ou ultérieur réellement installé. Vérifiez le Cargo.lock du worker : un nouveau client ou checkout ne met pas à jour un ancien worker. Elles concernent les rapports sortants, pas l’historique reçu ni les autres payloads métier.

Champ ou enveloppeMaximum
Message UTF-8, marqueur compris62 KiB
Stack lorsque pris en charge128 KiB
Total sérialisé des details, diagnostics et métadonnées facultatifs64 KiB
Corps complet encodé de la requête d’échec1 MiB

La limite effective réserve 2 KiB sous le budget initial 64 KiB pour les préfixes de timeline du Server publié. Échappement JSON, marqueurs, identité du claim et tous les autres champs comptent dans le corps encodé. Une limite de transport connue plus basse peut encore réduire ces maxima. Les petits rapports conservent leur contenu initial.

Le texte excessif porte un marqueur visible. Le champ existant diagnostics.sdk_failure_truncation, lorsque le schéma le permet, indique tailles initiales et champs omis. Les schémas workflow/query-task sans diagnostics et les messages de commande simples portent ces statistiques dans le marqueur. Les details Avro restent une enveloppe/référence runtime complète valide ou sont entièrement omis et marqués ; le base 64 n’est jamais coupé en une valeur corrompue.

Le type initial d’exception, la décision de retry et l’identité obligatoire du claim sont préservés. Les consommateurs bas niveau peuvent utiliser Client::fail_activity_task_with_failure et Client::fail_workflow_task_with_failure avec le schéma publié. Error::FailureReporting refuse explicitement un rapport dont les données obligatoires ne tiennent pas ; il ne décide pas du retry métier et n’invente pas une identité plus courte.

Les échecs locaux sont bornés avant leur observation par le workflow, normalisation des espaces/NUL du Server publié comprise. Le contrôle final ne réécrit ni message local déjà observé ni autre payload métier ; il refuse si ces données fixes ne tiennent pas.

Ces limites SDK ne prouvent pas une correction du stockage des résumés Core, la livraison d’un autre SDK, le mode embedded ou l’adoption dans une image Server. Les anciens workers peuvent encore ne pas transmettre un échec excessif. Voir la politique du source publié et le guide commun.

Activités locales​

Le SDK Rust 3.1.0 ajoute l’exécution locale en ligne sur les workers configurés avec Worker::local_activities(true). Enregistrez les callbacks via les méthodes ordinaires d’enregistrement d’activités, puis utilisez les méthodes d’activité locale du contexte de workflow. L’exemple exécutable et la référence LocalActivityOptions décrivent les tentatives et délais.

Server enregistre le résultat terminal pour la relecture à froid. Des effets locaux non validés peuvent se reproduire après la perte d’un worker et doivent être idempotents. Les callbacks asynchrones doivent rendre la main à Tokio. Le travail bloquant exige une supervision de processus séparée. L’exécution locale en ligne et la supervision locale coopérative préparée utilisent des profils de worker distincts.

Sessions de worker​

Activez Worker::worker_sessions(true) et déclarez les exigences satisfaites par votre worker avec capabilities(...). Routez les activités distantes avec in_worker_session(WorkerSessionOptions::new(session_id)). Le contexte d’activité donne accès au handle partagé via worker_session(). Les handles explicites prennent en charge create(), renew() et close(reason) après enregistrement du worker.

Bornez le nombre de sessions avec max_concurrent_worker_sessions(...) et la concurrence d’activité avec max_concurrent_activities(...). Renouvelez explicitement les handles inactifs. Les battements d’activité renouvellent aussi le bail du détenteur, en conservant le TTL absolu d’origine. Un callback asynchrone qui rend la main à Tokio est abandonné lorsque son bail ou TTL observé localement expire, sans exiger de battements applicatifs.

Les ressources de session vivent dans le processus détenteur. Un remplaçant doit les reconstruire. Les effets externes interrompus nécessitent idempotence et protection contre les tentatives obsolètes. Les résultats validés sont relus sans réexécuter le callback. L’arrêt propre ferme les sessions détenues avant désenregistrement. Les activités locales ne peuvent pas utiliser ce routage.

La prise en charge commence avec le SDK Rust 3.2.0. Utilisez Server 2.5.1 ou ultérieur. L’exemple exécutable réutilise un cache local au processus entre deux activités typées et affiche sa génération. Consultez WorkerSessionOptions et WorkerSession pour la configuration et les méthodes de cycle de vie.

Exécution sticky bornée​

Activez Worker::sticky_cache(StickyCacheOptions::new(capacity)) pour conserver un historique encodé immuable destiné aux relectures suivantes. Le cache est désactivé par défaut. Définissez max_history_bytes(...) et ttl(...) pour borner l’historique conservé et sa durée de vie. Prévoyez de la mémoire supplémentaire pour le décodage et la relecture.

Le cache utilise les identités de workflow, d’exécution et de build. Le remplacement du worker, l’expiration, l’éviction ou un curseur d’historique invalide provoque un repli vers l’historique durable complet. Les workflows terminaux et workers arrêtés suppriment leurs entrées. Le code doit être relu correctement avec un cache vide.

La prise en charge commence avec le SDK Rust 3.4.0 et la référence Server qualifiée. Consultez la référence de configuration, l’exemple exécutable et le guide d’affinité portable des workers.

Démarrer avec des délais de workflow appliqués par Server​

Le SDK Rust fournit WorkflowStartOptions et Client::start_workflow_with_options pour les échéances de workflow appliquées par Server même après la fin du processus de démarrage. Le délai d’exécution global couvre toute l’instance, y compris les continuations avec une nouvelle exécution. Le délai d’une exécution couvre une seule exécution et est recalculé au début de la suivante.

use durable_workflow::{json, Client, Result, WorkflowStartOptions};

async fn start(client: &Client) -> Result<()> {
    let handle = client.start_workflow_with_options(
        "orders.await-payment",
        "orders",
        "order-42",
        WorkflowStartOptions::new()
            .execution_timeout_seconds(300)
            .run_timeout_seconds(30),
        json!([{"order_id": "order-42"}]),
    ).await?;

    println!("workflow={} run={:?}", handle.workflow_id, handle.run_id);
    Ok(())
}

Les deux valeurs sont en secondes et doivent être positives. Le délai d’une exécution ne peut pas dépasser le délai global de l’instance. La méthode Client::start_workflow utilise WorkflowStartOptions::default() : 3 600 secondes pour l’instance et 600 secondes par exécution. Les délais d’expiration décrivent les échéances Server et la continuation avec une nouvelle exécution.

Ce sont des politiques de workflow. WorkflowResultOptions::timeout interrompt uniquement l’attente locale de result(). Il ne ferme, n’annule ni ne modifie l’exécution. L’appelant peut inspecter l’identité retournée et attendre de nouveau. Une échéance configurée par WorkflowStartOptions est un état durable Server. À son expiration, Server ferme l’exécution avec le résultat terminal timed_out.

Groupes parallèles déterministes​

WorkflowContext::parallel et son alias join composent activités, workflows enfants, temporisateurs, groupes mixtes et imbriqués sans nouvelle commande Server. Les constructeurs de ParallelOperation diffèrent chaque feuille jusqu’à ce que l’arbre complet soit connu :

use durable_workflow::{json, ChildWorkflowOptions, ParallelOperation};
use std::time::Duration;

let results = ctx.parallel(vec![
    ParallelOperation::activity("load-profile", json!(["customer-42"])),
    ParallelOperation::group(vec![
        ParallelOperation::child_workflow(
            "quote-shipping",
            ChildWorkflowOptions::new("shipping-workers"),
            json!(["customer-42"]),
        ),
        ParallelOperation::timer(Duration::from_secs(1)),
    ]),
]).await?;

Chaque feuille porte l’identité stable du groupe partagé et son chemin complet de l’extérieur vers l’intérieur. Les résultats réussis conservent la structure imbriquée et l’ordre d’entrée. Error::ParallelFailed préserve la cause typée de la feuille, son chemin déterministe, le chemin du groupe et les membres voisins terminés. Les historiques en attente et terminés sont relus sans nouvelle planification. Les doublons exacts et fins tardives ne changent pas le résultat positionnel retenu.

Sélection durable de la première fin​

WorkflowContext::select et select_keyed démarrent ensemble activités, workflows enfants, temporisateurs, signaux, attentes conditionnelles et groupes ordinaires imbriqués, puis reprennent avec le gagnant enregistré par le runtime :

use durable_workflow::{json, ParallelOperation, SelectionKey};
use std::time::Duration;

let selected = ctx.select_keyed(vec![
    ("resolver", ParallelOperation::activity("resolve-request", json!([request_id]))),
    ("input", ParallelOperation::signal("resolution.received")),
    ("deadline", ParallelOperation::timer(Duration::from_secs(2))),
]).await?;

if selected.key == SelectionKey::Name("deadline".to_string()) {
    if let Some(resolver) = selected.handle(&SelectionKey::Name("resolver".to_string())) {
        resolver.cancel().await?;
    }
}

SelectionResult préserve la clé ou l’index stable, le type et l’identité de l’opération, la valeur ou l’échec typé et un DurableOperationHandle par membre. Un perdant continue sauf si le workflow attend ensuite handle.await_result() ou handle.cancel(). La future d’annulation se résout en unité. Seul un événement validé SelectionOperationCancelled prouve que l’annulation a gagné. La relecture dépasse une demande sans marqueur, et await_result() retourne toujours une fin validée en premier. Le redémarrage et la relecture utilisent le gagnant persistant. Les événements terminaux tardifs ou en double ne peuvent pas le modifier.

Compensation des sagas​

N’enregistrez une compensation qu’après la fin de l’activité correspondante, puis transmettez le résultat des opérations principales à Saga::finish :

let mut saga = ctx.saga();
let outcome = async {
    let flight = ctx.activity("trip.reserve-flight", json!([])).await?;
    saga.add_compensation("trip.cancel-flight", json!([flight]))?;

    let hotel = ctx.activity("trip.reserve-hotel", json!([])).await?;
    saga.add_compensation("trip.cancel-hotel", json!([hotel]))?;

    ctx.activity("trip.charge", json!([])).await?;
    Ok(json!({"status": "booked"}))
}.await;

saga.finish(outcome).await

Un échec géré exécute la commande d’activité existante dans l’ordre inverse d’enregistrement, une compensation à la fois. La compensation s’arrête au premier échec. Error::SagaCompensationFailed préserve les deux erreurs typées, le type d’activité de compensation et son ordre d’enregistrement à travers les redémarrages et relectures. Un cancel_workflow terminal ne reprend pas le code pour exécuter les compensations.

Effets de bord déterministes et marqueurs de version​

Le SDK Rust enregistre les petites valeurs non déterministes avec WorkflowContext::side_effect et produit des UUIDv4 déterministes avec WorkflowContext::uuid_v4. Une relecture à froid décode la valeur enregistrée sans rappeler le callback. Des marqueurs réordonnés, manquants, en double ou au codec incompatible retournent Error::NonDeterministicReplay.

Utilisez WorkflowContext::get_version(change_id, min_supported, max_supported) pour garder les anciennes et nouvelles branches compatibles avec la relecture pendant un déploiement. Les nouvelles exécutions enregistrent max_supported. Les anciennes réutilisent le marqueur durable. patched(change_id) fournit la forme booléenne de déploiement et deprecate_patch(change_id) préserve le marqueur après la fin des anciennes branches. Les effets de bord et la gestion des versions décrivent ces règles communes.

Règles de déterminisme Rust​

Une relecture doit produire les mêmes commandes durables dans le même ordre pour l’entrée et l’historique enregistrés. Les collections, horloges et primitives de concurrence ordinaires de Rust ne préservent pas automatiquement ce contrat :

Motif dans le code du workflowRemplacement durable
Planifier en parcourant un HashMapTrier les clés d’abord ou utiliser un BTreeMap.
Lire l’horloge, thread_rng ou un nouvel UUIDEnregistrer un instantané avec ctx.side_effect(...) ou utiliser une activité.
tokio::time::sleep ou std::thread::sleepctx.sleep(...) ou ctx.start_timer(...).
tokio::select! ou mise en concurrence de futures ordinairesctx.select(...) ou ctx.select_keyed(...).
Appels durables concurrents non suivisctx.parallel(...) avec un ordre d’entrée stable.

Les effets externes des activités doivent rester idempotents ; le déterminisme ne rend pas sûr un paiement ou une écriture répétés. Consultez idempotence et déterminisme.

Tests unitaires d’activités et de workflows​

testing::WorkflowEnvironment exécute les workflows et activités enregistrés dans le processus courant. Utilisez from_worker(worker) pour reprendre les enregistrements de l’application, ou enregistrez directement les callbacks ; worker_mut() expose les API typées habituelles. Les mocks sont explicites : les callbacks réels exécutent leur propre code, donc remplacez délibérément les effets externes.

Utilisez durable-workflow = "=4.5.0" pour la recette vérifiée, Tokio avec macros, rt-multi-thread et time, et serde_json = "1" pour le helper d’export ci-dessous. Enregistrez l’exemple publié dans examples/workflow_testing.rs et lancez cargo run --example workflow_testing :

//! Run with `cargo run --example workflow_testing`; no Server is required.
use durable_workflow::{
    json,
    testing::{WorkflowEnvironment, WorkflowHistory},
    Result,
};

#[tokio::main]
async fn main() -> Result<()> {
    let mut env = WorkflowEnvironment::new()?;
    env.register_activity("greet", |_, args| async move {
        Ok(json!(format!(
            "Hello, {}!",
            args[0].as_str().unwrap_or("friend")
        )))
    });
    env.register_workflow("hello", |ctx, args| async move {
        ctx.activity("greet", args).await
    });

    // An activity unit test executes the real callback and argument adapters.
    assert_eq!(
        env.run_activity("greet", "Ada").await?,
        json!("Hello, Ada!")
    );
    // A workflow unit test may replace activity callbacks explicitly.
    env.mock_activity("greet", |_, args| async move {
        Ok(json!({"greeting_for":args[0]}))
    });
    assert_eq!(
        env.run_workflow("hello", "Ada").await?,
        json!({"greeting_for":"Ada"})
    );

    // Replay executes the same registered workflow without running activities.
    // In a deployment test, read the JSON produced by dw workflow:history-export
    // or Client::export_workflow_history instead of this captured test history.
    let history = WorkflowHistory::from_export(env.last_history().unwrap().export())?;
    assert!(env.replay(&history)?.completed);
    println!("activity, workflow and offline replay passed");
    Ok(())
}

run_activity direct exécute une tentative. Dans run_workflow, la politique de tentatives enregistrée s’applique avant de transmettre l’échec terminal au workflow. Les échecs réels ou simulés d’activités distantes/locales utilisent Error::ActivityFailed typé, avec type d’exception, numéro de tentative et marqueur non réessayable ; une erreur de workflow non interceptée conserve sa variante Rust initiale. Les heartbeats sont capturés localement. Utilisez les variantes *_avro_value si JSON ne préserve pas la valeur Avro initiale.

Relire une exécution exportée​

Enregistrez le workflow candidat, puis chargez un bundle JSON autonome de dw workflow:history-export ou Client::export_workflow_history(workflow_id, run_id).await?. Ajoutez ce helper à l’exemple précédent ; il utilise les mêmes imports et attend une exécution de test terminée :

fn replay(env: WorkflowEnvironment) -> std::result::Result<(), Box<dyn std::error::Error>> {
let export = serde_json::from_slice(&std::fs::read("workflow-history.json")?)?;
let history = WorkflowHistory::from_export(export)?;
let report = env.replay(&history)?;
assert!(report.completed); // A running snapshot can remain durably pending.
Ok(())
}

Pour l’historique brut, combinez toutes les pages et utilisez WorkflowHistory::from_history("hello", original_input, response), en fournissant la file d’origine si elle manque. Gardez l’entrée initiale et les résultats enregistrés ; les payloads élagués/masqués, références externes non résolues et jetons de page restants sont refusés. Le helper d’export résout les références pendant le téléchargement. La relecture elle-même ne contacte aucun Server et n’exécute aucun callback d’activité.

La relecture utilise les chemins du worker pour le décodage, les effets de bord, marqueurs de version et résolutions select enregistrées. Des commandes modifiées ou réordonnées renvoient Error::NonDeterministicReplay(ReplayFailure) avec sequence, expected et actual ; le contrôle installé sur un export réel détecte l’activité changée à la séquence 3. Les nouvelles commandes au-delà de l’instantané échouent aussi. Un instantané ouvert peut montrer un préfixe durablement en attente plutôt qu’une fin : affirmez le résultat attendu et testez les nouvelles branches avec une nouvelle exécution dans le processus et des tests d’intégration. Consultez les contrôles de relecture publiés.

Limites d’exécution​

Les délais de timers et de tentatives sont sautés. Les callbacks parallèles s’exécutent dans l’ordre des commandes : cet environnement ne teste ni courses d’ordonnancement ni performances. Il ne simule pas les files, baux ou déploiements. Les callbacks doivent céder le contrôle ; max_steps(n) borne tours durables, commandes et tentatives (10 000 par défaut), et tokio::time::timeout peut borner le temps d’un callback asynchrone.

La simulation de timeouts d’activité, les nouvelles courses select, signaux, enfants, services, sessions, continue-as-new et annulation nécessitent l’intégration ; les commandes non prises en charge renvoient Error::Testing. Un gagnant select enregistré peut être relu même si une nouvelle course n’est pas simulée. Gardez des tests avec un runtime réel pour ces limites. Consultez l’API de test et le contrat d’exécution publié.

Compatibilité à l’entrée et récupération​

Prise en charge publiée. Le SDK Rust 3.5.6 a introduit la protection d’entrée ci-dessous, avec le routage et la récupération dans Server 2.9.9. Ce sont les versions minimales pour ces fonctions. Installez les versions stables actuelles pour bénéficier des correctifs de sécurité.

Worker::register_typed_workflow et les adaptateurs typés avec état désérialisent l’entrée enregistrée avant d’appeler le handler applicatif ou sa fabrique d’état. Une structure d’entrée incompatible signale le type d’échec de tâche WorkflowEntryArgumentsMismatch et le motif workflow_entry_arguments_mismatch, sans envoyer fail_workflow. L’erreur locale du SDK pour l’entrée d’un workflow est Error::HandlerType ; elle indique le workflow et le type Rust attendu plutôt que la valeur enregistrée. Les handlers de workflow bruts ne reçoivent pas de nouveaux contrôles de signature Rust. Une erreur renvoyée par un handler applicatif entré avec succès reste un échec ordinaire de workflow, même si son texte ressemble au diagnostic d’entrée.

Le worker géré annonce automatiquement workflow_entry_arguments_validation. Un Server qualifié conserve la tâche en échec comme bloquée pour la relecture et laisse l’exécution d’origine non terminale. Les anciens runtimes peuvent relancer cette tâche ; le SDK seul n’établit donc pas le contrat complet de récupération.

Utilisez Client::describe_workflow_run(workflow_id, run_id) pour inspecter l’original et l’endpoint de débogage ciblant l’exécution pour lire le motif de tâche. Restaurez un décodage d’entrée et du code compatibles avant d’utiliser la route HTTP de réparation ciblant l’exécution dans la procédure de récupération. Cette crate n’a pas de méthode de commodité repair_workflow. Préservez l’entrée, l’historique, le namespace, la file, le build et les échéances d’origine ; versionnez les changements de commandes durables dans un handler compatible et qualifiez la relecture à froid. Consultez le routage des définitions.

Annuler, arrêter de force et traiter les résultats terminaux​

En mode service, cancel_workflow et terminate_workflow ferment tous deux l’exécution immédiatement. Ils enregistrent des résultats terminaux distincts, sans demander de nettoyage au code du workflow. Utilisez request_cancellation() avec des workers coopératifs pour un nettoyage borné. Le guide d’annulation coopérative décrit les politiques d’opération, la supervision et la reprise.

use durable_workflow::{Client, WorkflowCommandOptions};

# async fn cancel(client: &Client) -> durable_workflow::Result<()> {
client.cancel_workflow(
    "order-42",
    WorkflowCommandOptions::new()
        .reason("customer withdrew the order")
        .request_id("cancel-order-42"),
).await?;
# Ok(())
# }

Les commandes cancel_workflow et terminate_workflow visant une instance résolvent son exécution courante sur Server. Pour protéger une exécution sélectionnée, appelez cancel_workflow_run ou terminate_workflow_run, ou les méthodes cancel_selected_run et terminate_selected_run d’un handle. Si l’exécution sélectionnée est ancienne, Error::WorkflowCommandRejected expose le motif stable historical_run_command_rejected, les identifiants de workflow et d’exécution, le périmètre cible, l’état HTTP et le corps de réponse.

Les appels réussis à WorkflowHandle::result retournent la valeur JSON décodée. Traitez les variantes terminales typées pour tous les autres résultats. Branchez-vous sur les champs stables de motif et de catégorie :

use durable_workflow::{Error, WorkflowHandle, WorkflowResultOptions};

# async fn wait(handle: WorkflowHandle) -> durable_workflow::Result<()> {
match handle.result(WorkflowResultOptions::default()).await {
    Ok(value) => println!("completed: {value}"),
    Err(Error::WorkflowCancelled(outcome)) => {
        println!("cancelled {:?}: {}", outcome.run_id, outcome.reason);
    }
    Err(Error::WorkflowTerminated(outcome)) => {
        println!("terminated: {}", outcome.reason);
    }
    Err(Error::WorkflowFailed(outcome)) => {
        println!("failure {:?}: {:?}", outcome.failure_id, outcome.exception_class);
    }
    Err(Error::WorkflowTimedOut(outcome)) => match (
        outcome.reason.as_str(),
        outcome.failure_category.as_deref(),
    ) {
        ("result_wait_timeout", Some("client_timeout")) => {
            println!(
                "caller deadline for {} / {:?}; the run may still be open",
                outcome.workflow_id, outcome.run_id,
            );
        }
        ("execution_timeout" | "run_timeout", category) => {
            println!(
                "server timeout for {} / {:?}: reason={} category={:?}",
                outcome.workflow_id, outcome.run_id, outcome.reason, category,
            );
        }
        (reason, category) => {
            println!("other typed timeout: reason={reason} category={category:?}");
        }
    }
    Err(error) => return Err(error),
}
# Ok(())
# }

Chaque résultat terminal porte les identités de workflow et d’exécution. Il conserve aussi le motif public, la catégorie et l’identité de l’échec, le type et la classe d’exception, le caractère non réessayable, le message et les données d’exception fournis par Server. Une échéance locale d’attente a pour motif result_wait_timeout et catégorie client_timeout. Une expiration Server est une exécution terminale timed_out dont le motif stable est execution_timeout ou run_timeout.

Les handles retournés par les deux méthodes de démarrage conservent le run_id sélectionné. WorkflowHandle::result décrit cette route propre à l’exécution. Réutiliser l’identifiant du workflow pour une nouvelle exécution ne peut donc pas faire retourner silencieusement son résultat par une ancienne attente. Conservez outcome.workflow_id et outcome.run_id dans les journaux, métriques et enregistrements de nouvelles tentatives. N’utilisez les recherches par instance que pour suivre volontairement l’exécution courante.

Mises à jour des workflows​

Rust prend en charge les mises à jour durables dans les rôles client applicatif, handle sélectionné et écriture worker. Utilisez Client::update_workflow ou WorkflowHandle::update pour les valeurs compatibles JSON, et update_workflow_avro_value ou update_avro_value pour les valeurs Avro explicitement typées.

Les workers enregistrent les gestionnaires nommés avec Worker::register_update. Utilisez register_update_avro_value si le gestionnaire consomme et retourne directement des valeurs Avro. Une mise à jour est une mutation durable de workflow qui produit un résultat. Elle se distingue des signaux sans attente de réponse et des requêtes de lecture relues sans mutation.

Enveloppe de données utiles​

Les entrées de workflow, signaux, activités, requêtes de lecture et résultats utilisent le contrat publié PayloadEnvelope : un codec et un blob encodé. Le parcours avro par défaut utilise la dépendance déclarée apache-avro et le schéma Value fixe versionné de la plateforme. Ne fabriquez pas le blob manuellement et ne remplacez pas l’enveloppe par un enregistrement propre à une implémentation.

use durable_workflow::{decode_payload, json, PayloadEnvelope, Result, Value};

fn round_trip() -> Result<()> {
    let envelope = PayloadEnvelope::avro(&json!({"order_id": "order-42"}))?;
    assert_eq!(envelope.codec, "avro");

    let decoded: Value = decode_payload(&envelope)?;
    assert_eq!(decoded["order_id"], "order-42");
    Ok(())
}

start_workflow et start_workflow_with_options appliquent automatiquement l’enveloppe à leur entrée sérialisable. Utilisez les fonctions publiques uniquement lorsqu’un programme doit échanger directement une enveloppe.

Heartbeats d’activité​

Pour les activités distantes, ActivityContext::heartbeat(...).await renvoie Result<ActivityHeartbeatResponse>. Propagez les erreurs et vérifiez should_stop() sur une réponse réussie. Les erreurs des requêtes directes comprennent Error::Transport et les refus HTTP typés Error::ActivityTaskRejected. Une tâche à supervision coopérative peut renvoyer Error::ActivityExecutionAbandoned lorsque les heartbeats ou les vérifications de possession échouent. Arrêtez le travail externe après la perte d’autorité. Ne supposez pas qu’un callback atteint toujours le nettoyage applicatif.

La première fenêtre de heartbeat commence lorsque le moteur réclame l’activité, avant la livraison de la tâche. Un heartbeat enregistré utilise son horodatage du moteur, pas la réception par l’appelant. Choisissez une fréquence bien à l’intérieur du délai configuré, bornez chaque étape de travail ou d’E/S et gardez une marge pour les pauses, la latence et les éventuelles nouvelles tentatives de transport. Suivez les conseils de fréquence. Aucune programmation automatique de progression ou de regroupement n’est promise.

À l’annulation, libérez les ressources locales au processus lorsque l’exécution le permet encore et retournez rapidement. L’état durable refuse une fin tardive et ne peut pas transformer une exécution annulée ou terminée en réussite. Les workers gérés continuent de sonder après ce refus définitif et après redémarrage. Un heartbeat réussi n’est ni une validation des effets externes ni un point de reprise pour une tentative de remplacement.

SDK Python

Le SDK Python est un client léger privilégiant l'asynchrone pour un Server Durable Workflow auto-hébergé ou un runtime d'espace de noms Durable Workflow Cloud. Il permet aux processus Python de démarrer, observer, signaler et annuler des workflows via l'API du plan de contrôle, et de s'enregistrer comme workers qui exécutent des tâches de workflow et des activités.

Essayer l'environnement local Sample App​

Pour le parcours d'écriture le plus court sans Cloud, ouvrez la branche main actuelle de Sample App dans GitHub Codespaces et lancez :

scripts/playground python

L'environnement local génère les sources de workflow et d'activité appartenant à l'appelant, choisit les artefacts stables actuels et démarre les images publiées Server et Waterline. Il attend un enregistrement worker dont identité, type de workflow, type d'activité et file correspondent au contrat généré avant de démarrer le workflow. La réussite exige le résultat terminé et l'historique attendus. Le terminal affiche alors le lien exact de l'exécution Waterline locale et le chemin des preuves JSON structurées.

Installation du paquet, démarrage rapide présenté ci-dessous, référence API et exemple de dépôt ci-dessous restent les parcours directs sans Sample App.

Runtime géré

Durable Workflow Cloud

Exécutez clients et workers Python sur un espace de noms Cloud géré avec des identifiants distincts limités par rôle.

Voir les tarifs Cloud Dev

Le SDK cible le même modèle durable que le paquet PHP : identifiants d'instance et d'exécution, événements d'historique, files et clés de type sont partagés entre langages. Un worker Python peut servir les activités d'un workflow PHP, et inversement.

Pour comparer les SDK Python, PHP, Rust et dw, consultez les capacités des clients et workers.

Pour les signatures de constructeur, types de retour, classes d'exception et noms de métriques, consultez la référence API SDK Python générée.

Le SDK Python 2.5.0 ajoute un cache d'historique borné facultatif pour l'exécution avec affinité. Utilisez Server 2.5.10 ou ultérieur et activez-le sur chaque worker. Consultez l'affinité portable des workers et le guide Python avec exemple exécutable.

Les clients Cloud utilisent l'URL et l'espace de noms provisionnés avec des identifiants client et worker distincts. Le runtime Cloud géré définit cette frontière de connexion. Le démarrage rapide ci-dessous utilise des valeurs auto-hébergées locales.

Prérequis​

  • Python 3.10 ou ultérieur
  • Docker pour le Server local de ce démarrage rapide, un Server auto-hébergé existant ou un runtime Cloud provisionné

Installation​

Installez la version stable du SDK Python. La dépendance exacte est générée depuis le même tuple que le démarrage rapide Server. Un fichier de verrouillage ou de contraintes peut la conserver pour la reproductibilité.

pip install durable-workflow==2.8.0

Le SDK dépend de httpx pour HTTP et du paquet Python fastavro pour encoder le format Apache Avro du seul codec public v2. Les métriques Prometheus sont facultatives.

Démarrage rapide​

Ce programme Python complet définit un workflow avec une activité, le démarre sur un serveur Durable Workflow local et attend son résultat :

import asyncio
import uuid

from durable_workflow import Client, Worker, workflow, activity

@activity.defn(name="greet")
async def greet(name: str) -> dict:
    return {"greeting": f"Hello, {name}!", "length": len(name)}

@workflow.defn(name="greeter")
class GreeterWorkflow:
    def run(self, ctx, *args):
        result = yield ctx.schedule_activity("greet", list(args))
        return result

async def main():
    workflow_id = f"greeting-{uuid.uuid4().hex}"

    async with Client("http://localhost:8080", token="dev-token", namespace="default") as client:
        handle = await client.start_workflow(
            workflow_type="greeter",
            task_queue="default",
            workflow_id=workflow_id,
            input=["world"],
        )

        worker = Worker(
            client,
            task_queue="default",
            workflows=[GreeterWorkflow],
            activities=[greet],
        )

        await worker.run_until(workflow_id=workflow_id, timeout=30.0)
        result = await handle.result(timeout=10.0)

    print(result)  # {"greeting": "Hello, world!", "length": 5}

asyncio.run(main())

Rapports d’échec bornés​

Le SDK Python 2.11.0 a introduit des rapports d’échec sortants bornés. Les limites par défaut sont de 62 KiB UTF-8 pour le message, 128 KiB pour la pile, 64 KiB pour l’ensemble des détails et diagnostics facultatifs sérialisés et 1 MiB pour le corps complet encodé par HTTPX. Les marqueurs, l’échappement JSON, l’identité du bail et les autres commandes du lot comptent dans cette limite du corps. Une limite de transport configurée ou découverte plus basse est prioritaire. Le type, la classe et le code de l’échec, la politique de nouvelle tentative et l’identité du bail sont conservés.

Configurez un budget plus faible pour le corps si nécessaire. Les paramètres d’avertissement sur la taille des données restent indicatifs.

from durable_workflow import Client

async with Client(
    "https://workflow.example.com",
    worker_token="worker-token",
    control_token="operator-token",
    failure_report_limit_bytes=512 * 1024,
) as client:
    info = await client.get_cluster_info()

Un marqueur de troncature visible et les tailles originales en octets identifient les champs raccourcis. Les détails Avro sont conservés intégralement ou omis en entier. Une enveloppe obligatoire impossible à représenter déclenche FailureReportTooLarge avant l’envoi HTTP. Les échecs locaux sont normalisés avant que le code du workflow les observe. La première exécution et la relecture à froid voient donc le même message persistant. Un message local déjà observé reste immuable lors de l’ajustement final du lot.

Stockage externe des charges utiles​

Les opérations ordinaires de Client et Worker utilisent automatiquement le transport authentifié du runtime Server. Le SDK découvre politique et limites via GET /api/cluster/info, téléverse les valeurs encodées supérieures au seuil ou nécessaires pour respecter la limite de requête, puis récupère les références avant décodage. Le code du workflow et de l’activité reçoit la valeur décodée. Les identifiants fournisseur restent sur Server. Les workers distants n’ont besoin ni de boto3, ni de clients fournisseur, ni d’accès au répertoire local de Server.

La référence du runtime utilise le schéma durable-workflow.v2.runtime-external-payload-reference.v1 et un reference_id opaque. Elle ne contient aucun uri fournisseur. Téléversement et récupération utilisent les identifiants ordinaires du rôle et l’espace de noms, vérifient taille et SHA-256 et préservent les barrières de tentative de tâche et de bail lors de la terminaison. Le contrat HTTP décrit routes, limites et refus typés. La prise en charge exige un transport compatible disponible, pas seulement un pilote configuré.

Les utilitaires fournisseur directs suivants servent au stockage et aux tests d’applications accédant délibérément à leur propre fournisseur. Ils utilisent un autre schéma avec URI. Ils ne sont pas nécessaires aux clients ordinaires de Server ou Cloud. Server refuse les enveloppes fournisseur external_storage avec HTTP 422 et external_payload_unsupported.

Pour ces utilitaires directs, le schéma est EXTERNAL_PAYLOAD_REFERENCE_SCHEMA (durable-workflow.v2.external-payload-reference.v1). Les adaptateurs n’ajoutent aucune dépendance aux SDK cloud dans durable-workflow ; l’application fournit ses clients S3, GCS ou Azure configurés.

Leur référence fournisseur contient les champs suivants. Ce n’est pas la référence du runtime acceptée par les routes HTTP Server :

{
  "schema": "durable-workflow.v2.external-payload-reference.v1",
  "uri": "s3://dw-payloads/billing/run-001/input.avro",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "size_bytes": 1048576,
  "codec": "avro",
  "expires_at": "2026-05-22T00:00:00Z"
}

ExternalPayloadReference.from_dict() refuse les schémas inconnus et champs incorrects. fetch_external_payload() vérifie size_bytes et sha256 avant de renvoyer les octets et lève ExternalPayloadIntegrityError si taille ou empreinte diffèrent. Un objet absent peut aussi provoquer l’erreur du pilote fournisseur. Utilisez ExternalPayloadCache uniquement pour les octets vérifiés. L’éviction du cache n’autorise pas à supprimer un objet géré par Server. delete_external_payload() est une opération directe du fournisseur, pas une API de nettoyage des références du runtime.

Utilisez external_storage_driver_from_policy() dans du code accédant délibérément au stockage fournisseur de l’application et possédant le client requis. Lire une politique ne rend pas les enveloppes fournisseur valides dans les requêtes Server. Les clients restent à la charge de l’application. Les adaptateurs facultatifs n’ajoutent pas boto3, google-cloud-storage ou azure-storage-blob comme dépendances du runtime :

from durable_workflow.external_storage import external_storage_driver_from_policy

namespace = await client.describe_namespace("billing")
driver = external_storage_driver_from_policy(
    namespace.external_payload_storage,
    s3_client=application_owned_s3_client,
)

La fabrique lève ValueError si la politique est désactivée, le pilote non pris en charge ou le client requis absent. Une politique désactivée ne renvoie pas de pilote vide. Vérifiez policy.enabled avant l’appel.

Identité du workflow courant​

Depuis Python SDK 2.9.0, le code du workflow peut lire les propriétés en lecture seule ctx.workflow_id et ctx.run_id. Ce sont des chaînes issues de la tâche courante, identiques lors du rejeu. Après continue-as-new, l'identifiant du workflow reste le même et le successeur reçoit son propre identifiant de run. Ne le remplacez pas par un identifiant du prédécesseur passé en argument.

from durable_workflow import workflow

@workflow.defn(name="identity")
class IdentityWorkflow:
    def run(self, ctx):
        identity = {"workflow_id": ctx.workflow_id, "run_id": ctx.run_id}
        yield ctx.schedule_activity("record_identity", [identity])
        return identity

Ces propriétés lisent l'identité locale de la tâche sans requête HTTP. Pour consulter l'état hors du code du workflow, utilisez await client.describe_workflow(workflow_id). Utilisez await client.query_workflow(workflow_id, query_name) pour l'état exposé par un gestionnaire de requêtes enregistré. Les propriétés d'identité ne remplacent aucune de ces opérations.

Définir des workflows​

Les workflows sont des classes Python décorées avec @workflow.defn. La méthode run est une fonction synchrone ordinaire ou un générateur synchrone qui émet des commandes durables vers le serveur avec yield. Utilisez la forme générateur lorsque le workflow a besoin de travail durable ; async def run n’est pas pris en charge.

from durable_workflow import workflow

@workflow.defn(name="order-processing")
class OrderWorkflow:
    def run(self, ctx, *args):
        order = args[0] if args else {}

        # Schedule an activity and wait for the result
        validated = yield ctx.schedule_activity(
            "validate_order", [order]
        )

        # Start a timer (durable sleep)
        yield ctx.start_timer(seconds=60)

        # Schedule another activity
        receipt = yield ctx.schedule_activity(
            "process_payment", [validated]
        )

        return receipt

Le name de @workflow.defn(name="...") est la clé de type commune aux langages. Il doit être une chaîne simple, pas un chemin de module ou une référence de classe Python.

Signaux, requêtes de lecture et mises à jour​

Les signaux sont enregistrés dans l'historique durable et transmis aux gestionnaires Python pendant la relecture :

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False
        self.approved_by = None

    @workflow.signal("approve")
    def approve(self, by: str) -> None:
        self.approved = True
        self.approved_by = by

    def run(self, ctx, *args):
        ready = yield ctx.wait_condition(
            lambda: self.approved, key="approval.approved", timeout=60,
        )
        return {
            "status": "approved" if ready else "timed_out",
            "approved": self.approved,
            "approved_by": self.approved_by,
        }

L’attente appartient au workflow, pas à une activité. Son prédicat lit l’état du gestionnaire de signal reconstruit par rejeu ; le worker ne réserve aucun slot d’activité pour cette approbation. Le délai de la condition est distinct des échéances finies de l’exécution individuelle et de l’exécution logique du workflow. Pour terminer un travail externe, utilisez une activité courte qui soumet puis revient, ainsi qu’un rappel corrélé.

Les décorateurs de réception de requête et de mise à jour permettent de publier des noms de gestionnaire stables. Les workers Python exécutent les requêtes routées par le serveur en relisant l'historique validé puis en appelant le gestionnaire sur cet état. Ils appliquent aussi les mises à jour acceptées livrées par les tâches de workflow :

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False

    @workflow.query("status")
    def status(self) -> dict:
        return {"approved": self.approved}

    @workflow.update("set_approval")
    def set_approval(self, approved: bool) -> dict:
        self.approved = approved
        return {"approved": self.approved}

    @set_approval.validator
    def validate_set_approval(self, approved: bool) -> None:
        if not isinstance(approved, bool):
            raise ValueError("approved must be boolean")

Le worker termine une requête routée en renvoyant son résultat au serveur. Pour un validateur de mise à jour déclaré, il reçoit plutôt une tâche de validation dédiée, relit l'état de référence et appelle uniquement le validateur. Le serveur n'enregistre aucune acceptation et ne distribue aucun gestionnaire avant réussite de la validation. Les workers avec validateurs refusent l'enregistrement si la découverte n'annonce pas le contrat synchrone de préacceptation. Rejet, worker absent ou incompatible, perte worker, délai dépassé et achèvement dupliqué ou périmé rejeté par la protection de bail restent des résultats typés explicites. PHP et Rust n'exposent actuellement pas d'API d'écriture de validateurs et annoncent cette absence dans leurs contrats au lieu de revendiquer la parité.

Cycle de vie des handlers​

Validation publiée. Le SDK Python 2.6.2 a introduit les contrôles de handlers ci-dessous. Les requêtes asynchrones et les validateurs d’updates routés par le serveur restent pris en charge. Consultez SDK #177 pour le périmètre corrigé.

Chaque relecture construit une nouvelle instance de workflow avant d’exécuter run(). Les signaux déjà enregistrés au démarrage du workflow sont appliqués après que run() atteint son premier yield ; le constructeur et l’initialisation précédant ce yield passent donc en premier. Les handlers de signaux et d’updates modifient cet état reconstitué. Les requêtes l’inspectent sans changer l’état durable ; les validateurs d’updates inspectent avant l’acceptation un état reconstitué qui ne sera pas conservé. Placez les commandes durables d’activités, de timers et de workflows enfants dans run(), pas dans un handler.

HandlerForme prise en charge et résultat d’un échec
@workflow.signalFonction synchrone. Une exception lors de l’application du signal pendant la relecture fait échouer l’exécution du workflow.
@workflow.updateFonction synchrone. Une exception du handler fait échouer cet update.
@workflow.update_validator ou @update_method.validatorFonction synchrone ou async def sous le Worker. Une exception rejette l’update avant son acceptation.
@workflow.queryFonction synchrone ou async def sous le Worker. Une exception du handler fait échouer la requête, pas l’exécution du workflow.

La validation refuse les fonctions coroutine pour les signaux et les updates, ainsi que les fonctions génératrices ou génératrices asynchrones pour tous les types de handlers décorés, y compris les requêtes et les validateurs. Elle lève InvalidWorkflowDefinition à la définition, à l’enregistrement ou à la relecture, y compris pour les handlers hérités et les outils hors ligne. Les wrappers synchrones de signaux et d’updates ne peuvent pas contourner ces contrôles en renvoyant des valeurs asynchrones. Le renvoi de générateurs ou de générateurs asynchrones est refusé pour chaque type de handler. Ces restrictions n’interdisent pas le générateur synchrone utilisé par run().

Pour une requête routée par le serveur, le Worker attend explicitement le résultat asynchrone sous l’échéance d’origine de la requête et l’autorité de prise de tâche et d’annulation. Cette attente n’accorde pas de nouveau budget et n’autorise pas de résultat après la perte de l’autorité. Pour la validation précédant l’acceptation, le Worker attend aussi le résultat asynchrone d’un validateur travaillant sur un état reconstitué qui ne sera pas conservé.

Les utilitaires locaux synchrones ne peuvent pas attendre de résultat asynchrone. workflow.query_state() refuse un résultat asynchrone avec QueryFailed et workflow.validate_update() le refuse avec UpdateRejected. Ils ferment les coroutines renvoyées au lieu de les laisser devenir des résultats d’opération.

Compatibilité à l’entrée et récupération​

Prise en charge publiée. Le SDK Python 2.6.2 a introduit la protection d’entrée ci-dessous, avec le routage et la récupération dans Server 2.9.9. Ce sont les versions minimales pour ces fonctions. Installez les versions stables actuelles pour bénéficier des correctifs de sécurité.

Avant d’appeler run(ctx, *start_input), le worker lie les arguments enregistrés à la signature d’entrée. Un argument obligatoire absent ou une arité incompatible lève WorkflowEntryArgumentsMismatchError avec le motif workflow_entry_arguments_mismatch, avant l’exécution du corps. Les valeurs par défaut ne complètent que les arguments omis. Les annotations Python ne sont toujours pas imposées : changer une annotation ne valide ni ne convertit les données enregistrées. Un TypeError levé dans un corps ordinaire ou générateur après une entrée réussie reste un échec applicatif.

Le worker annonce automatiquement workflow_entry_arguments_validation. Avec un Server qualifié, la tâche en échec est bloquée pour la relecture et l’exécution d’origine reste non terminale. Les anciens runtimes peuvent relancer cette tâche ; le refus côté SDK seul n’établit pas le contrat complet de récupération.

Inspectez l’exécution exacte avec await client.describe_workflow_run(workflow_id, run_id) et l’endpoint de débogage ciblant l’exécution. Après avoir restauré une méthode d’entrée compatible, utilisez la route HTTP de réparation ciblant l’exécution décrite dans la procédure de récupération. await client.repair_workflow(workflow_id) et handle.repair() résolvent au contraire l’exécution actuelle de l’instance ; aucun n’accepte d’argument d’identifiant d’exécution. Préservez l’entrée, l’historique, le namespace, la file, le build et les échéances d’origine. Pour les changements de commandes, placez ctx.get_version dans cette méthode compatible et qualifiez la relecture à froid avec le routage des définitions.

Temps du workflow et attentes durables​

Pendant la relecture par le worker, ctx.now() renvoie l'heure de début persistée du run. Elle n'avance pas après une activité, un temporisateur, un signal ou une autre étape durable. Les relectures à froid du même historique renvoient cette même valeur initiale. Un successeur continue-as-new possède sa propre heure de début, sans conserver l'ancrage de l'horloge du prédécesseur.

L'implémentation Python publiée utilise WorkflowStarted.payload.timestamp s'il est présent, sinon la valeur canonique WorkflowStarted.recorded_at. Une heure persistée absente ou invalide produit une erreur d'horloge explicite, sans autoriser la lecture de l'horloge murale du worker. C'est le contrat à début fixe établi dans SDK #146.

Attendez une opération durable plutôt que de boucler jusqu'à ce que ctx.now() change :

from durable_workflow import workflow


@workflow.defn(name="wait_without_clock_loop")
class WaitWithoutClockLoop:
    def run(self, ctx):
        started_at = ctx.now()
        yield ctx.start_timer(30)
        return {
            "run_started_at": started_at.isoformat(),
            "after_wait": ctx.now().isoformat(),
        }

La fin durable du temporisateur reprend le workflow. Les deux horodatages renvoyés sont la même heure de début. Une boucle comme while ctx.now() < deadline ne devient pas fausse simplement parce que des temporisateurs se déclenchent.

Pour un délai relatif, utilisez yield ctx.start_timer(seconds) ou yield ctx.sleep(seconds). Utilisez la sélection de la première fin pour mettre un travail en concurrence avec un temporisateur durable. Définissez execution_timeout_seconds et run_timeout_seconds dans client.start_workflow(...) lorsque Server doit imposer une échéance au workflow, y compris lorsque les workers sont arrêtés. Le délai d'attente HTTP ou de get_result() limite seulement cette requête locale ; il ne remplace pas l'échéance persistée du workflow. Transmettez explicitement une échéance applicative en entrée de continue-as-new pour la conserver, sans remplacer l'échéance d'exécution initiale de Server.

Pour mesurer le temps écoulé au sein d'un appel d'activité, lisez une horloge monotone dans cette activité et renvoyez la durée dans son résultat. Pour une échéance UTC externe, faites vérifier l'horloge externe faisant autorité par une activité et renvoyez sa décision ; le workflow relit ce résultat enregistré. Ne comparez jamais des horodatages UTC à des valeurs monotones et ne soustrayez pas des mesures monotones de processus ou d'hôtes différents. La soustraction de ctx.now() ne mesure en Python ni le temps de traitement actif ni le temps mural écoulé.

Ordonner les événements émis avec des séquences​

Un horodatage de workflow n'est pas une clé d'ordre des événements. Tous les événements Python horodatés avec ctx.now() peuvent avoir la même heure. Utilisez les offsets des Workflow Streams, la séquence de l'outbox intégrée appropriée ou un compteur déterministe local au workflow. Associez un compteur local au run à run_id ; transmettez-le explicitement via continue-as-new si l'application a besoin d'une séquence logique unique. Les horodatages ne donnent pas d'ordre global aux streams ou runs indépendants.

Tentatives et délais d'activité​

Utilisez ActivityRetryPolicy et les arguments nommés de délai de ctx.schedule_activity(...) si un appel nécessite un budget ou une échéance différents du comportement par défaut à tentative unique :

from durable_workflow import ActivityRetryPolicy

receipt = yield ctx.schedule_activity(
    "process_payment",
    [validated],
    retry_policy=ActivityRetryPolicy(
        max_attempts=4,
        initial_interval_seconds=1,
        backoff_coefficient=2,
        maximum_interval_seconds=30,
        non_retryable_error_types=["ValidationError"],
    ),
    start_to_close_timeout=120,
    schedule_to_close_timeout=300,
    heartbeat_timeout=15,
)

start_to_close_timeout borne une tentative après démarrage par le worker. schedule_to_close_timeout borne toute l'exécution d'activité à travers les tentatives. heartbeat_timeout exige que les activités longues appellent activity.context().heartbeat(...) avant expiration de l'intervalle. La politique est figée dans l'exécution durable à sa planification. Les déploiements ultérieurs ne changent donc pas les tentatives en cours.

ctx.schedule_activity(..., queue="payments-v2") choisit la file d’une nouvelle exécution d’activité. Les activités déjà enregistrées, leurs nouvelles tentatives et tâches réparées conservent la file d’origine. Modifier Worker.task_queue ne déplace ni ces tâches ni la file de workflow des exécutions existantes. Gardez l’ancien pool compatible disponible jusqu’à avoir pris en compte toutes les dépendances ; voir les files d’activité enregistrées.

Règles de déterminisme​

Le code du workflow est relu depuis l'historique. Il ne doit effectuer aucune opération non déterministe directement :

  • Aucune entrée/sortie : appels HTTP, fichiers, requêtes de base
  • Aucun datetime.now() ou time.time() : utilisez ctx.now() uniquement comme ancrage fixe du début du run et des temporisateurs durables pour les attentes.
  • Aucun random.random() : utilisez ctx.random()
  • Aucun uuid.uuid4() : utilisez ctx.uuid4()

Tout non-déterminisme doit passer par le contexte ou être capturé avec ctx.side_effect().

Distribution parallèle​

Émettez une liste de commandes avec yield pour les exécuter simultanément :

@workflow.defn(name="fan-out-example")
class FanOutWorkflow:
    def run(self, ctx, *args):
        items = args[0]

        # Nested lists may mix activities, children, and timers.
        results = yield [
            ctx.schedule_activity("process_item", [items[0]]),
            [
                ctx.start_child_workflow("process-batch", [items[1:]]),
                ctx.start_timer(1),
            ],
        ]

        return results  # same nested shape and input order

Le worker émet une commande ordinaire par feuille durable et ajoute les champs stables partagés parallel_group_* et le chemin complet de l'extérieur vers l'intérieur. L'historique peut fermer les membres dans tout ordre. La relecture associe toujours résultats et échecs à leur position d'entrée durable. Un doublon terminal exact est ignoré. L'historique en attente après redémarrage et l'historique entièrement terminé reconstruisent le même groupe sans replanifier le travail terminé.

return {"status": "resolved", "value": selected.result()}

SelectionResult inclut clé stable, index d'entrée, nature d'opération et identité durable du gagnant, son résultat typé et toutes les instances DurableOperationHandle. yield handle.await_result() attend plus tard un autre membre. yield handle.cancel() enregistre une demande explicite sans résultat. Seul l'historique validé SelectionOperationCancelled prouve que l'annulation a gagné. La relecture dépasse une demande non marquée et await_result() renvoie encore un achèvement validé avant elle. Elle consomme le gagnant persisté même si un historique ultérieur contient d'abord un autre achèvement. Livraisons externes dupliquées ou désordonnées ne remplacent pas un gagnant déjà validé.

Compensation saga​

def forward(saga):

La fonction utilitaire s'arrête au premier échec de compensation. SagaCompensationFailed conserve échec initial, échec de compensation, type d'activité et ordre d'enregistrement déterministe comme diagnostics structurés.

Définir des activités​

Les activités sont des fonctions Python asynchrones décorées par @activity.defn. Contrairement aux workflows, elles peuvent effectuer des entrées/sorties librement.

from durable_workflow import activity

@activity.defn(name="send_email")
async def send_email(to: str, subject: str, body: str) -> dict:
    # Activities can do I/O: HTTP calls, database queries, etc.
    response = await some_email_client.send(to=to, subject=subject, body=body)
    return {"message_id": response.id, "sent": True}

Le name est la clé commune aux langages. Un workflow PHP peut planifier une activité "send_email" exécutée par un worker Python, et inversement.

Contexte d'activité​

Dans une activité, accédez aux métadonnées et au battement de cœur avec activity.context() :

@activity.defn(name="long_running_task")
async def long_running_task(items: list) -> dict:
    ctx = activity.context()

    print(f"Attempt #{ctx.info.attempt_number}")
    print(f"Task queue: {ctx.info.task_queue}")

    for i, item in enumerate(items):
        # Check for cancellation
        if ctx.is_cancelled:
            return {"partial": True, "processed": i}

        await process(item)

        # Heartbeat to keep the task alive
        await ctx.heartbeat({"progress": i + 1, "total": len(items)})

    return {"processed": len(items)}

Requêtes de heartbeat​

Pour les activités distantes, appelez await ctx.heartbeat(...) pendant un travail d’activité borné, bien avant heartbeat_timeout. La première fenêtre commence lorsque le moteur réclame l’activité, avant que Python reçoive la tâche. Chaque heartbeat enregistré utilise le moment de son enregistrement par le moteur, pas celui où sa réponse atteint Python. Les pauses, la latence et les nouvelles tentatives de transport consomment le budget. Suivez les conseils de fréquence.

L’appel direct à Client.heartbeat_activity_task() utilise la TransportRetryPolicy configurée. Après cette politique, les erreurs de transport peuvent se propager comme httpx.TransportError, et les refus HTTP deviennent des exceptions du SDK telles que ServerError. Il s’agit de nouvelles tentatives HTTP, pas d’une autre tentative d’activité ni de temps supplémentaire pour le heartbeat. ActivityContext.heartbeat() peut lever ActivityCancelled lorsque le worker demande à l’activité de s’arrêter. Lorsque la supervision coopérative des processus est activée, un échec de heartbeat ou de vérification de possession peut arrêter ou abandonner le callback. Ne supposez pas que chaque échec revient dans un gestionnaire d’exception ou que le nettoyage s’exécute toujours.

Ne masquez pas les échecs de heartbeat ou de possession pour poursuivre le travail externe ou annoncer une réussite. La progression n’est ni une validation externe ni une confirmation de point de reprise. Gardez les effets externes idempotents.

Refus du heartbeat et sortie du callback​

Avec le SDK Python 2.9.0, ctx.heartbeat() et ctx.heartbeat_sync() lèvent ActivityLeaseAuthorityLost lorsqu’une réponse de heartbeat indique can_continue=false. L’exception conserve le motif initial du Server, par exemple activity_deadline_elapsed, attempt_closed ou run_closed. Une demande d’annulation lève plutôt ActivityCancelled. Consultez la qualification du SDK publié.

Le heartbeat qui constate le refus constitue un point de sortie coopérative. Arrêtez le travail externe et propagez l’exception ; ne l’interceptez pas pour renvoyer un succès. Le code qui n’envoie jamais de heartbeat peut continuer jusqu’à son retour. Un heartbeat auxiliaire ne peut pas interrompre de force un appel de bibliothèque bloqué : utilisez des échéances d’E/S finies et le mécanisme d’annulation propre à l’appel.

Le créneau physique de l’activité reste occupé jusqu’à la sortie du callback/thread. La perte d’autorité de la tentative ne libère pas ce thread pour un autre travail, et le worker ne publie pas de résultat tardif pour la tentative fermée. L’application du timeout par le runtime et l’arrêt du code applicatif sont des limites distinctes. Consultez les timeouts d’activité et les conseils pour le thread auxiliaire.

Erreurs non réessayables​

Levez NonRetryableError pour faire échouer l'activité sans nouvelle tentative :

from durable_workflow import NonRetryableError

@activity.defn(name="validate")
async def validate(data: dict) -> dict:
    if "required_field" not in data:
        raise NonRetryableError("Missing required_field")
    return data

Erreurs métier terminales​

non_retryable_error_types correspond exactement au nom court (exception_type) ou au nom de classe qualifié (exception_class) de l’exception extérieure. Par exemple, ValidationError ne correspond pas à SpecificValidationError, même si c’est une sous-classe. Un nom qualifié comme app.errors.ValidationError doit correspondre à la classe enregistrée. La politique ne parcourt ni les sous-classes ni les causes. raise RuntimeError(...) from NonRetryableError(...) signale le RuntimeError extérieur et peut encore être retenté.

Pour convertir une exception métier connue, levez NonRetryableError comme exception extérieure et conservez la cause Python d’origine avec cause=error. L’échec de l’activité devient non réessayable sans liste de noms. Cela ne fait pas automatiquement échouer tout le workflow : son code reçoit ActivityFailed quand l’activité n’a plus de tentatives, soit parce que l’erreur est non réessayable, soit parce que le budget est épuisé.

from durable_workflow import ActivityFailed, NonRetryableError, activity, workflow

@activity.defn(name="validate_order")
async def validate_order(order: dict) -> dict:
    try:
        if order.get("amount", 0) <= 0:
            raise ValueError("amount must be positive")
    except ValueError as error:
        raise NonRetryableError("Order validation failed", cause=error) from error
    return order

@workflow.defn(name="place_order")
class PlaceOrderWorkflow:
    def run(self, ctx, order: dict):
        try:
            yield ctx.schedule_activity("validate_order", [order])
        except ActivityFailed as failure:
            if (
                failure.activity_type != "validate_order"
                or failure.exception_type != "NonRetryableError"
                or not failure.non_retryable
            ):
                raise
            return {"order_id": order["id"], "status": "rejected"}
        return {"order_id": order["id"], "status": "accepted"}

Pour l’entrée {"id": "order-123", "amount": 0}, l’activité échoue une fois et le workflow termine normalement avec status: rejected. Traitez seulement l’échec métier prévu ; l’exemple relance les autres. Poursuivez avec d’autres étapes durables si le parcours métier l’exige. Un ActivityFailed non intercepté fait échouer le workflow. Conserver une cause Python ne signifie ni que la politique inspecte cette chaîne ni que tous les SDK exposent le même objet de cause.

Activités synchrones et asynchrones​

Les activités distantes ordinaires définies avec def s’exécutent dans un pool de threads dédié, limité par max_concurrent_activity_tasks. Chaque fonction conserve son contexte d’activité. Le polling, les tâches de workflow et les heartbeats du worker peuvent progresser pendant qu’une fonction est bloquée. Les activités async def s’exécutent dans la boucle événementielle et doivent utiliser des E/S non bloquantes. Un appel bloquant dans une fonction asynchrone bloque toujours cette boucle.

Dans une fonction synchrone, appelez activity.context().heartbeat_sync(details) pour transmettre la progression par la boucle événementielle responsable, avec les identités d’origine de la tâche, de la tentative et du worker. Les fonctions asynchrones utilisent await activity.context().heartbeat(details).

Annuler une attente n’arrête pas un thread Python déjà en cours d’exécution. Son slot physique reste occupé jusqu’au retour de la fonction. Un retour tardif ne transmet aucun résultat après l’annulation. Si une fonction tourne encore après shutdown_timeout, l’arrêt lève RuntimeError et conserve l’enregistrement du worker. Fixez des délais pour les E/S vers les services appelés et utilisez des processus de worker isolés pour les calculs intensifs. Consultez la référence du SDK sur l’exécution et l’arrêt.

Heartbeats depuis un thread auxiliaire​

Pour un long appel bloquant, capturez ctx = activity.context() dans l’activité synchrone, puis transmettez ce contexte au thread auxiliaire. Un nouveau thread n’hérite pas automatiquement du contexte d’activité. Appelez ctx.heartbeat_sync(details) depuis ce thread, jamais depuis la boucle événementielle du worker. Consultez l’exemple complet dans la référence du SDK.

Arrêtez le thread et attendez sa fin avec join() quand l’appel retourne ou lève une exception. Si un heartbeat lève ActivityCancelled ou ActivityLeaseAuthorityLost, signalez l’annulation coopérative à l’appel et relancez l’exception d’origine avant de retourner un résultat. Une exception dans le thread auxiliaire ne peut pas interrompre de force un appel bloqué. Prévoyez un délai fini et un mécanisme d’annulation pour cet appel, et bornez les délais et tentatives des requêtes de heartbeat. Sinon, le thread peut continuer à signaler que le processus vit alors que le travail est bloqué.

Worker​

Worker s'enregistre auprès du serveur, interroge les tâches et les transmet à vos implémentations de workflow et d'activité.

Pour des processus indépendants, suivez le guide exécutable de séparation des processus du SDK Python. Il couvre enregistrements distincts, files communes ou séparées, tentatives, emplacements par rôle et arrêt propre.

Sessions de worker​

Utilisez WorkerSessionOptions lorsque des activités distantes séquentielles doivent utiliser une ressource locale du même worker. Cet exemple est vérifié avec le SDK Python 2.9.0 et Server 2.11.0 ; consultez les versions requises pour l’affinité portable. Utilisez un job_id unique par exécution de workflow afin qu’une nouvelle exécution ne réutilise pas l’identifiant d’une session terminale.

Le cache ci-dessous est jetable. Chaque activité peut le reconstruire à partir de l’entrée métier durable ; le nouveau détenteur ne dépend donc pas de la mémoire du processus précédent :

from durable_workflow import ActivityFailed, WorkerSessionOptions, activity, workflow

# Disposable process-local state. Rebuild it from durable business input.
documents = {}

def ensure_document(job_id):
    rebuilt = job_id not in documents
    if rebuilt:
        documents[job_id] = {"text": "document:" + job_id}
    return documents[job_id], rebuilt

@activity.defn(name="prepare_document")
async def prepare_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id, "rebuilt": rebuilt}

@activity.defn(name="inspect_document")
async def inspect_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id,
            "rebuilt": rebuilt, "text": document["text"]}

@workflow.defn(name="inspect_document_workflow")
class InspectDocumentWorkflow:
    def run(self, ctx, job_id):
        session = WorkerSessionOptions(
            session_id="documents:" + job_id,
            requirements=("fs:documents",),
            lease_seconds=5,
            ttl_seconds=60,
            max_concurrent_activities=1,
            allow_reacquire_after_failure=True,
        )
        options = dict(worker_session=session,
                       start_to_close_timeout=5,
                       schedule_to_start_timeout=12,
                       schedule_to_close_timeout=20,
                       retry_policy={"max_attempts": 1})
        try:
            prepared = yield ctx.schedule_activity("prepare_document", [job_id], **options)
            inspected = yield ctx.schedule_activity("inspect_document", [job_id], **options)
        except ActivityFailed as error:
            if error.activity_type not in {"prepare_document", "inspect_document"}:
                raise
            return {"status": "resource_unavailable", "job_id": job_id}
        return {"status": "inspected", "prepared": prepared, "inspected": inspected}

Enregistrez les deux activités et déclarez la capacité requise sur le worker :

from durable_workflow import Worker

worker = Worker(
    client,
    task_queue="documents",
    workflows=[InspectDocumentWorkflow],
    activities=[prepare_document, inspect_document],
    capabilities=["fs:documents"],
)
await worker.run()

Démarrez inspect_document_workflow dans la file de tâches documents avec [job_id] en entrée. La première activité acquiert la session à la demande ; la seconde utilise le même détenteur tant que son bail reste valide. max_concurrent_activities=1 limite les activités simultanées dans cette session. Le routage de file et les contrôles de capacité s’appliquent toujours. Ces baux et timeouts courts illustrent un comportement borné ; dimensionnez-les pour le travail réel et envoyez les heartbeats bien avant l’expiration.

Après la perte du détenteur ou l’expiration du bail, allow_reacquire_after_failure=True permet à un autre worker admissible de réacquérir la session. Il doit reconstruire la ressource locale. Les résultats d’activité déjà validés sont relus, mais les effets non validés peuvent se répéter : utilisez des identifiants durables et des opérations externes idempotentes. Une session ne migre ni mémoire, ni fichiers, ni descripteurs ouverts.

La fermeture explicite et l’expiration du TTL absolu sont terminales pour cet identifiant de session. Une activité ultérieure ne peut pas le rouvrir et peut rester sans admission jusqu’à l’application du timeout configuré. Exécutez le rôle d’ordonnancement/maintenance du Server de la recette de déploiement publiée ; un processus API seul ne suffit pas à appliquer les timeouts. Le workflow traite l’échec définitif d’activité avec ActivityFailed et renvoie resource_unavailable ; l’application peut ensuite choisir une nouvelle session et reconstruire depuis l’entrée métier. Cet exemple ne promet ni exception immédiate de session fermée, ni réouverture automatique d’une session terminale.

Pour gérer explicitement le cycle de vie du détenteur, utilisez worker.worker_session(options) et ses méthodes create(), renew() et close(reason). L’arrêt normal du worker ferme les sessions qu’il détient. Consultez le contrat de cycle de vie commun.

    note="Changed to every 30 minutes",
)

# Read the audit history stream (paused/resumed/triggered/updated events)
page = await handle.history(limit=100)
for event in page.events:
    print(event.sequence, event.event_type, event.recorded_at)
while page.has_more and page.next_cursor is not None:
    page = await handle.history(limit=100, after_sequence=page.next_cursor)
    for event in page.events:
        print(event.sequence, event.event_type, event.recorded_at)

# Or iterate every event without managing cursors
async for event in handle.iter_history():
    print(event.sequence, event.event_type)

# Delete the schedule (history survives the delete for audit)
await handle.delete()

L'annulation échappe volontairement à except Exception​

WorkflowCancelled et ActivityCancelled héritent de BaseException, pas Exception. Un bloc générique except Exception: dans une activité ou du code attendant client.get_result() ne les intercepte pas. C'est délibéré : l'annulation est un résultat du plan de contrôle. L'absorber silencieusement permettrait à une activité d'annoncer un succès alors que le workflow lui a demandé de s'arrêter.

Si une activité doit nettoyer localement à l'annulation, interceptez la classe par son nom puis relevez l'exception. Cela ne reprend pas le workflow fermé pour compenser :

from durable_workflow import ActivityCancelled, activity

@activity.defn(name="long_task")
async def long_task(items: list) -> dict:
    ctx = activity.context()
    try:
        for i, item in enumerate(items):
            await process(item)
            await ctx.heartbeat({"progress": i + 1})
        return {"done": True}
    except ActivityCancelled:
        await cleanup_partial_state()
        raise

Ce choix suit le précédent de asyncio.CancelledError et KeyboardInterrupt dans la bibliothèque standard.

Tests​

Les auteurs doivent pouvoir tester un workflow sans serveur ni worker actif. Le module durable_workflow.testing fournit deux entrées :

  • WorkflowEnvironment conduit un workflow à son terme dans un processus Python unique avec des activités simulées enregistrées par l'utilisateur.
  • replay_history et replay_history_file relisent un historique de production capturé contre le code actuel et lèvent une erreur en cas de non-déterminisme.

Les deux réutilisent le mécanisme durable_workflow.workflow.replay du worker. Un workflow validé par son banc de test se comporte donc de la même manière avec un vrai worker.

WorkflowEnvironment​

WorkflowEnvironment distribue les commandes émises avec yield aux simulations enregistrées et déclenche automatiquement temporisateurs, effets de bord et insertions/mises à jour d'attributs de recherche. Les tests n'ont besoin ni d'horloge réelle, ni Redis, ni serveur.

from durable_workflow import workflow
from durable_workflow.testing import WorkflowEnvironment

@workflow.defn(name="greeter")
class Greeter:
    def run(self, ctx, name: str):
        greeting = yield ctx.schedule_activity("greet", [name])
        return greeting


def test_greeter_returns_activity_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("greet", "hello, world")

    result = env.execute_workflow(Greeter, "world")

    assert result == "hello, world"

Le banc échoue explicitement si une fixture manque :

  • planifier une activité sans simulation enregistrée lève KeyError
  • démarrer un enfant sans simulation enregistrée lève KeyError
  • ne pas atteindre d'état terminal dans la limite d'itérations (1000 par défaut) lève RuntimeError

Passez iteration_limit=... à WorkflowEnvironment(...) pour les workflows qui nécessitent légitimement davantage d'itérations.

Simulations d'activité par fonction​

Utilisez register_activity pour répondre selon les arguments ou enregistrer les appels :

def test_callable_mock_captures_arguments() -> None:
    captured: list[str] = []

    def record_greet(name: str) -> str:
        captured.append(name)
        return f"greeted:{name}"

    env = WorkflowEnvironment()
    env.register_activity("greet", record_greet)

    assert env.execute_workflow(Greeter, "alice") == "greeted:alice"
    assert captured == ["alice"]

Signaux​

Les signaux de env.signal(...) sont distribués avant la prochaine relecture. Leur charge utile est enveloppée dans le même {codec, blob} que voit le worker, puis transmise au gestionnaire @workflow.signal enregistré :

@workflow.defn(name="approval")
class Approval:
    def __init__(self) -> None:
        self.approved_by: str | None = None

    @workflow.signal("approve")
    def on_approve(self, by: str) -> None:
        self.approved_by = by

    def run(self, ctx):
        yield ctx.schedule_activity("wait", [])
        return {"approved_by": self.approved_by}


def test_signal_is_delivered_before_run_returns() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("wait", None)
    env.signal("approve", ["alice"])

    result = env.execute_workflow(Approval)

    assert result == {"approved_by": "alice"}

Temporisateurs, effets de bord et attributs de recherche​

Le banc déclenche automatiquement l'événement correspondant à chaque commande. Les workflows ne bloquent donc pas sur le temps réel en test :

  • ctx.sleep(seconds) → TimerFired
  • ctx.side_effect(...) → SideEffectRecorded
  • ctx.upsert_search_attributes(...) → SearchAttributesUpserted
  • marqueurs workflow.version(...) → VersionMarkerRecorded

Chaînes continue-as-new​

Quand un workflow renvoie ctx.continue_as_new(...), le banc ajoute WorkflowContinuedAsNew à l'exécution qui se termine, remet l'historique à zéro et démarre une exécution avec les arguments de la commande. execute_workflow renvoie le résultat terminal du dernier maillon.

@workflow.defn(name="countdown")
class Countdown:
    def run(self, ctx, counter: int):
        yield ctx.schedule_activity("emit", [counter])
        if counter > 0:
            return ctx.continue_as_new(counter - 1)
        return {"final_counter": counter}


def test_chain_returns_final_run_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("emit", None)

    result = env.execute_workflow(Countdown, 3)

    assert result == {"final_counter": 0}
    assert env.run_count == 4
    assert [r.input for r in env.runs] == [[3], [2], [1], [0]]

Si la chaîne change de type, enregistrez d'abord la classe suivante :

@workflow.defn(name="stage-one")
class StageOne:
    def run(self, ctx):
        yield ctx.schedule_activity("stage_one", [])
        return ctx.continue_as_new(workflow_type="stage-two")


@workflow.defn(name="stage-two")
class StageTwo:
    def run(self, ctx):
        return (yield ctx.schedule_activity("stage_two", []))


def test_chain_can_switch_workflow_type() -> None:
    env = WorkflowEnvironment()
    env.register_workflow(StageTwo)
    env.register_activity_result("stage_one", None)
    env.register_activity_result("stage_two", "done")

    assert env.execute_workflow(StageOne) == "done"
    assert [r.workflow_type for r in env.runs] == ["stage-one", "stage-two"]

Ciblez un maillon précis avec run=N :

env.signal("approve", ["alice"], run=2)  # delivered to the second run

La longueur est bornée par continue_as_new_limit, 50 par défaut. Dépasser la limite lève RuntimeError pour détecter les continuations incontrôlées plutôt que boucler indéfiniment. Ajustez-la avec WorkflowEnvironment(continue_as_new_limit=...) si une chaîne plus longue est légitime.

Assertions d'échec​

Un workflow levant une exception Python produit WorkflowFailed :

import pytest
from durable_workflow.errors import WorkflowFailed

@workflow.defn(name="failing")
class Failing:
    def run(self, ctx):
        yield ctx.schedule_activity("step", [])
        raise RuntimeError("boom")


def test_workflow_failure_surfaces_as_workflow_failed() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("step", None)

    with pytest.raises(WorkflowFailed) as exc_info:
        env.execute_workflow(Failing)

    assert "boom" in str(exc_info.value)

Tester la relecture d'un historique de production​

Utilisez replay_history pour tester une modification contre un historique réel capturé du serveur. Le moteur exécute le code actuel sur les événements enregistrés et lève une erreur s'il émet une autre commande que celle enregistrée, ce qui définit un bogue de non-déterminisme.

from durable_workflow import Client
from durable_workflow.testing import replay_history

async with Client("http://localhost:8080") as client:
    history = await client.get_history("order-42", run_id="...")

replay_history(OrderWorkflow, history["events"], start_input=["order-42"])

Un workflow précédemment terminé doit toujours terminer avec le même historique. Si le code diverge, par réordre d'appels, retrait de branches ou changement de types d'activité, replay_history lève une erreur pour détecter la régression en CI plutôt qu'en production.

replay_history_file lit un fichier JSON sous deux formes : liste d'événements racine, ou dictionnaire avec clé events conforme à la réponse get_history :

from durable_workflow.testing import replay_history_file

replay_history_file(
    OrderWorkflow,
    "tests/histories/order-42.json",
    start_input=["order-42"],
)

Les deux fonctions acceptent l'indication de validation facultative payload_codec. Laissez-la absente pour utiliser l'étiquette enregistrée. Toute étiquette explicite ou enregistrée doit être avro. Les charges durables json, inconnues ou non étiquetées échouent avant décodage.

Moteur de relecture par classe​

Pour relire plusieurs types de workflow dans un même test, ou laisser l'événement WorkflowStarted capturé choisir le type, utilisez Replayer. Enregistrez les classes en amont et appelez replay(...) pour chaque historique :

from durable_workflow import Replayer, ReplayOutcome

replayer = Replayer(workflows=[OrderWorkflow, RefundWorkflow])

# Explicit type and input — equivalent to replay_history(OrderWorkflow, ...).
outcome: ReplayOutcome = replayer.replay(
    history["events"],
    start_input=["order-42"],
    workflow_type="order",
)

# Type and start input inferred from a WorkflowStarted event in the history.
outcome = replayer.replay(history)  # history may be an events list or a
                                    # dict with an "events" key

for command in outcome.commands:
    # Inspect commands the replayed workflow would have emitted next.
    ...

Replayer(workflows=[...]) rejette un ensemble vide ou un enregistrement dupliqué avec ValueError. replay(...) lève ValueError si le type demandé n'est pas enregistré, ou si plusieurs workflows sont enregistrés sans workflow_type fourni ni événement WorkflowStarted dans l'historique.

ReplayOutcome.commands est la même liste de commandes que renvoient les fonctions replay_history. La classe permet de partager un enregistrement entre de nombreux historiques d'une suite de tests.

Codec des charges utiles​

Chaque charge utile traversant la frontière du protocole worker porte une étiquette de codec. Durable Workflow 2.0 a un seul codec public : avro. Le SDK Python rejette les charges durables JSON, inconnues et non étiquetées au lieu de choisir un autre décodeur. Consultez le protocole Avro Value.

Avro est inclus​

L'artefact SDK 2.0 fixé installe fastavro comme dépendance runtime. Chaque sortie (start_workflow, signal_workflow, query_workflow, update_workflow, encodage de résultats d'activité, actions de planification) émet donc des charges Avro par le parcours optimisé de production. Aucune option de codec supplémentaire n'est à installer.

Valeurs typées fixes​

Le SDK sélectionne explicitement des branches nommées du schéma partagé durable_workflow.protocol.Value. Il n'encode pas la valeur en JSON dans Avro. Entiers/doubles, chaînes/octets, booléens/entiers et listes/tables de correspondance restent donc distincts entre SDK. Le format utilise l'encadrement Avro à objet unique et l'empreinte du schéma. Une empreinte inconnue échoue avec unsupported_payload_schema.

Chaque interface client et worker fonctionne de bout en bout avec Avro par défaut :

  • Démarrages, signaux, requêtes de lecture et mises à jour client : start_workflow, signal_workflow, query_workflow et update_workflow émettent payload_codec = "avro" via le schéma Value fixe. Un client Python peut piloter les workflows relus par PHP et les autres SDK, et inversement.
  • Worker d'activité : les arguments Avro se décodent automatiquement. Le worker encode les résultats en Avro pour une frontière commune à PHP, Python et aux futurs SDK.
  • Échecs d'activité : fail_activity_task(..., details=...) envoie failure.details dans une enveloppe {codec, blob}. Le serveur enregistre le blob et details_payload_codec pour garder les diagnostics Python indépendants du langage dans les exports et vues d'observabilité.
  • Relecture d'historique worker : entrée de démarrage et résultats d'activité Avro sont décodés pendant la relecture. Un workflow Python participe ainsi à une exécution encodée en Avro.
  • Tâches de requête de lecture : les tâches routées portent arguments de workflow, arguments de requête et historique en Avro. Le worker renvoie le résultat dans une enveloppe Avro.

Exécuter un worker d'activité Python sur une exécution v2​

Aucune configuration de codec n'est nécessaire. Le SDK valide payload_codec avant chaque décodage, n'accepte que avro, exécute l'activité et renvoie un résultat Avro. Toute autre étiquette est refusée avec unsupported_payload_codec. Le worker ne tente jamais de détecter ou deviner le format.

Utiliser un serveur partagé​

Le démarrage rapide montre comment lancer un serveur local avec l'image Docker publiée. En équipe, le worker vise généralement un serveur existant, en préproduction, production ou développement partagé :

from durable_workflow import Client

client = Client(
    "https://workflow.example.internal",
    control_token="team-orders-operator-token",
    worker_token="team-orders-worker-token",
    namespace="team-orders",
)

Définissez namespace sur l'espace provisionné pour votre équipe et utilisez ses identifiants. L'opérateur Server gère sa création. Consultez le guide Server.

Le même constructeur prend en charge Cloud. Utilisez l'URL et la valeur d'espace de noms fournies par Cloud. Définissez control_token sur l'identifiant runtime client et worker_token sur celui du worker. Cloud provisionne l'espace. Ne remplacez pas son adresse par un Server auto-hébergé. Consultez le runtime Cloud géré.

Pages de liste et d’historique des workflows​

Ces appels publiés renvoient une page, pas une lecture complète automatique : await client.list_workflows(...) / await client.get_history(workflow_id, run_id, ...). Continuez avec le token opaque retourné en conservant namespace, filtres et workflow/exécution sélectionnés ; terminez au token nul/vide et traitez explicitement les erreurs de page. Une page partielle n’est pas un bundle de replay. Utilisez l’API d’export d’historique du SDK pour le replay hors ligne. Le client publié Python 2.9.0 définit les paramètres actuels ; aucun nouvel itérateur n’est annoncé.

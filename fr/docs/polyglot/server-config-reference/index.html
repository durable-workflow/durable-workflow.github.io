Référence de configuration de Server

Cette page décrit le contrat des variables d’environnement DW_* destiné aux opérateurs de l’image Durable Workflow Server. Utilisez-la pour préparer vos modèles de déploiement, vérifier la configuration de production ou remplacer les anciens noms WORKFLOW_* / ACTIVITY_* par le contrat Server v2.

Server utilise aussi les paramètres habituels de Laravel, comme DB_*, REDIS_*, QUEUE_CONNECTION et CACHE_STORE. Ces variables d’infrastructure sont présentées séparément : elles configurent le déploiement et ne constituent pas des commandes de l’API Durable Workflow.

Prise en compte des modifications​

L’image PHP Server publiée exécute php artisan config:cache dans son point d’entrée. Les valeurs de l’environnement sont lues au démarrage et écrites dans le cache de configuration Laravel. Modifier un fichier d’environnement, la déclaration d’environnement de l’orchestrateur ou un fichier de configuration monté ne recharge pas un déploiement en cours d’exécution.

Redémarrez ou remplacez chaque processus concerné avec la nouvelle configuration : réplicas HTTP API, workers locaux de la file Laravel et processus du planificateur. Redémarrez séparément les workers SDK persistants si leur propre configuration de client ou de worker change. Le redémarrage réussi de l’API ne met pas à jour un worker de file ou un planificateur encore actif. Les rôles qui partagent une base et un cache doivent recevoir une configuration cohérente.

Pendant une mise à jour progressive, chaque nœud applique les limites qu’il a chargées. Les compteurs d’admission partagés n’uniformisent pas des configurations différentes. Un réplica API peut donc accepter une requête qu’un autre refuse. Pour appliquer une nouvelle limite de façon cohérente :

  1. Suspendez les nouvelles requêtes des appelants et retirez les réplicas API concernés de l’ingress. Laissez les requêtes en cours se terminer. Arrêtez proprement les rôles de file et de planificateur concernés dans leurs budgets d’arrêt.
  2. Appliquez la même configuration à chaque rôle concerné, puis redémarrez-les ou remplacez-les. Laissez le point d’entrée de chaque conteneur reconstruire son cache de configuration.
  3. Recherchez les erreurs de configuration dans les journaux de démarrage, vérifiez la disponibilité et testez la limite modifiée avant de rétablir l’ingress et les requêtes des appelants. Consultez le guide de déploiement et de disponibilité.

Les paramètres opérateur stockés dans la base ont un autre cycle de vie. Les mutations réussies ci-dessous sont disponibles pour les opérations suivantes sans redémarrer Server :

ParamètreModification sans redémarragePortée et limites
Description et conservation du namespacePUT /api/namespaces/{namespace}, ou dw namespace:updateLa politique régit les passages de conservation suivants. Sa modification ne restaure pas les données déjà supprimées. Voir Conservation Server.
Politique de stockage externe des payloads du namespacePUT /api/namespaces/{namespace}/external-storageModifie la politique stockée du namespace. Les identifiants du fournisseur, les disques de système de fichiers configurés et les autres paramètres de processus nécessitent toujours le redémarrage décrit ci-dessus. Préservez l’accès aux objets référencés par les runs existants.

Les valeurs par défaut et plafonds DW_* de cette référence restent des paramètres de processus, sauf lorsqu’une opération documentée du plan de contrôle modifie explicitement l’état stocké. Server ne surveille pas les fichiers de configuration pour détecter leurs modifications.

Vérification du contrat​

Le dépôt Server conserve le contrat canonique dans config/dw-contract.php. Au démarrage du conteneur, php artisan env:audit signale les variables DW_* inconnues et les anciens noms. Définissez DW_ENV_AUDIT_STRICT=1 pour que le point d’entrée échoue au lieu de démarrer avec des avertissements.

DW_ENV_AUDIT_STRICT=1
DW_AUTH_DRIVER=token
DW_ADMIN_TOKEN="${DW_ADMIN_TOKEN}"
DW_OPERATOR_TOKEN="${DW_OPERATOR_TOKEN}"
DW_WORKER_TOKEN="${DW_WORKER_TOKEN}"

Les anciens noms servent uniquement de repli. Préférez le nom DW_* dans chaque nouveau déploiement. Un avertissement concernant un ancien nom indique une migration inachevée, même si Server utilise encore sa valeur.

Préférence d’empreinte publiée. Server 2.9.9 rend effective la préférence d’empreinte pour les workers en mode service. Quand la fixation est activée, le repli vers une définition modifiée n’est possible que s’il ne reste aucun worker éligible avec la définition enregistrée et si le remplacement annonce workflow_entry_arguments_validation. Quand elle est désactivée, la préférence de code source disparaît ; les builds fixés, l’isolation namespace/file/type, l’identité d’enregistrement et la relecture stricte demeurent. Les protections d’entrée correspondantes sont disponibles depuis les SDK PHP 2.5.4, Python 2.6.2 et Rust 3.5.6. Ce sont les versions minimales pour ces fonctions. Installez les versions stables actuelles avec les correctifs de sécurité. Ne supposez pas qu’un ancien runtime offre ce comportement simplement parce que sa configuration contient la même clé. Consultez le routage des définitions.

Utilisez DW_V2_GUARDRAILS_BOOT dans la CI et les manifestes de déploiement. L’ancien nom WORKFLOW_V2_GUARDRAILS_BOOT n’est conservé que pour permettre à env:audit de signaler le renommage aux opérateurs des versions alpha. Le package Workflow ne le lit plus comme valeur de repli à l’exécution.

Consultez Attribution et distribution des tâches pour configurer DW_V2_MATCHING_ROLE_QUEUE_WAKE ou un démon dédié workflow:v2:repair-pass --loop. Ces paramètres changent l’emplacement de la détection des tâches prêtes, pas le contrat du protocole worker.

TLS de la base de données​

Appliquez les mêmes réglages TLS au serveur API, au worker de file, au job d'initialisation/migration et à l'ordonnanceur. PostgreSQL utilise prefer par défaut ; MySQL/MariaDB conservent leurs réglages de connexion sans mode explicite. Aucun de ces défauts ne garantit une connexion chiffrée et authentifiée.

DB_SSLMODEPostgreSQLMySQL / MariaDB
disableSans TLS.Sans TLS ; les options TLS contradictoires sont refusées.
allow, preferTLS opportuniste sans garantie de chiffrement ni d'identité.Refusés.
requireChiffrement obligatoire.Chiffrement obligatoire avec mysqlnd et OpenSSL.
verify-caChiffrement et chaîne de certificats de confiance obligatoires.Refusé : PDO mysqlnd ne peut pas vérifier la chaîne indépendamment du nom d'hôte.
verify-fullChiffrement, chaîne de confiance et nom d'hôte correspondant obligatoires.Chiffrement, chaîne de confiance et nom d'hôte correspondant obligatoires.

DB_SSL_MODE est un alias de DB_SSLMODE ; DB_SSL_ROOT_CERT, de DB_SSLROOTCERT. Pour vérifier les certificats, montez un fichier CA lisible au chemin configuré dans chaque rôle, migrations comprises. MYSQL_ATTR_SSL_CA peut fournir la CA pour un verify-full explicite sur MySQL/MariaDB. Les contradictions entre réglages canoniques, alias ou URL empêchent le démarrage. TLS obligatoire exige un nom d'hôte TCP explicite ; les sockets Unix sont refusés. Les modes TLS explicites de MySQL/MariaDB nécessitent PDO MySQL avec mysqlnd et OpenSSL.

DB_CONNECTION=pgsql
DB_HOST=database.example.com
DB_SSLMODE=verify-full
DB_SSLROOTCERT=/run/database-ca/ca.pem

Utilisez le nom DNS du certificat. Avec Helm, configurez externalDatabase.sslMode et externalDatabase.tls.existingSecret / caKey. Créez le Secret avant l'installation ou la mise à niveau ; le chart monte sa CA dans les quatre rôles, hook d'initialisation compris. Redémarrez les rôles persistants après modification de l'environnement : la configuration est mise en cache au démarrage.

Journaux des conteneurs​

Définissez LOG_CHANNEL=stderr sur les conteneurs API, workers et ordonnanceur pour que docker logs ou kubectl logs collecte les journaux applicatifs. Définissez-le explicitement sur les versions existantes. LOG_LEVEL sélectionne la gravité minimale. Pour du JSON avec un enregistrement par ligne, ajoutez :

LOG_STDERR_FORMATTER="Monolog\Formatter\JsonFormatter"

Redémarrez les processus persistants après toute modification, car la configuration est mise en cache au démarrage. Un canal de fichier choisi explicitement nécessite son propre stockage et sa propre collecte ; Kubernetes ne collecte pas automatiquement storage/logs/laravel.log. DW_LOG_FORMAT n'est pas un paramètre pris en charge.

Notes de migration​

Lors de la migration d’un ancien déploiement, passez au nom public et laissez l’ancien nom non défini. Si les deux sont présents, les opérateurs doivent se baser sur la valeur DW_* et supprimer l’ancien nom.

# Before
WORKFLOW_SERVER_AUTH_DRIVER=token
WORKFLOW_SERVER_OPERATOR_TOKEN=operator-secret

# After
DW_AUTH_DRIVER=token
DW_OPERATOR_TOKEN=operator-secret

Après la migration, exécutez l’image Server avec DW_ENV_AUDIT_STRICT=1 pour détecter les fautes de frappe, les anciens alias et les paramètres copiés d’anciens guides d’exploitation.

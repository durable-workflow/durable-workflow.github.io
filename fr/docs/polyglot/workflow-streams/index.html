Flux de workflow

Les Workflow Streams sont des journaux de sortie nommés, propres à une exécution, gérés par Durable Workflow Server. PHP, Python et Rust exposent des opérations typées pour lister, décrire, s'abonner, ajouter, fermer et signaler une erreur, sans que les applications aient à composer des requêtes HTTP. Le runtime annonce durable-workflow.v2.workflow-streams.contract@1. La matrice des SDK lisible par machine consigne la prise en charge exacte de chaque SDK.

Chaque flux attribue des offsets strictement croissants à partir de 0. Le next_offset d'une page est le prochain offset inclusif à demander. La livraison aux consommateurs a lieu au moins une fois : terminez les effets idempotents de la page, puis enregistrez durablement next_offset comme point de reprise. Un arrêt brutal avant cet enregistrement peut entraîner une nouvelle livraison des éléments.

Émettre depuis le code du workflow​

Les trois SDK émettent à travers la même frontière de commande déterministe : record_side_effect.workflow_stream. Chaque SDK déduit la clé d'idempotence de l'élément de l'identité durable de commande de workflow de la tâche, du numéro ordinal de la commande de flux et de l'index dans le lot. Server valide ensemble la mutation du flux et l'effet enregistré. La relecture consomme cet effet et ne peut pas créer un autre élément durable pour le même ajout logique.

PHP :

use DurableWorkflow\Model\WorkflowStreamAppendItem;

$context->appendWorkflowStream('progress', [
    new WorkflowStreamAppendItem(['percent' => 50]),
]);
$context->closeWorkflowStream('progress');

Python :

from durable_workflow import WorkflowStreamAppendItem

yield ctx.append_workflow_stream("progress", [
    WorkflowStreamAppendItem(payload={"percent": 50}),
])
yield ctx.close_workflow_stream("progress")

Rust :

let item = WorkflowStreamAppendItem::new(serde_json::json!({"percent": 50}))?;
ctx.append_workflow_stream("progress", &[item], None)?;
ctx.close_workflow_stream("progress", None)?;

Les fonctions de workflow servent à l'écriture déterministe. Le code extérieur à un workflow peut utiliser l'opération typée append de chaque client et fournir sa propre clé d'idempotence stable.

S'abonner et reprendre​

L'abonnement lit une page bornée et peut attendre de nouveaux éléments pendant 60 secondes au maximum. PHP accepte un callback d'annulation entre les interrogations bornées. Python accepte l'annulation normale d'une tâche ou un asyncio.Event qui annule l'interrogation en cours. Abandonner la future d'abonnement Rust annule sa requête.

SDKOpération de pageValeur de repriseItération typée
PHPsubscribeWorkflowStream(...)WorkflowStreamPage::$nextOffsetiterateWorkflowStream(...)
Pythonawait subscribe_workflow_stream(...)WorkflowStreamPage.next_offsetiter_workflow_stream(...)
Rustsubscribe_workflow_stream(...).awaitWorkflowStreamPage::next_offsetRépéter la future de page bornée jusqu'à terminal.

Les états du cycle de vie sont open, closed et errored. La description typée expose également last_offset, total_items, pending_items et error_reason. Tout ajout à un flux terminal est rejeté. Quand la limite configurée d'éléments en attente est atteinte, l'ajout renvoie stream_full. Les producteurs doivent ralentir ou attendre que les consommateurs vident le flux.

Références aux charges utiles externes​

Les valeurs en ligne utilisent l'enveloppe Avro Value commune. Les références externes suivent le contrat de stockage existant de chaque SDK au lieu d'introduire un nouveau transport :

SDKComportement des références externes
PHPAjoute et renvoie un payload_reference opaque ; le téléversement et la récupération depuis le stockage restent à la charge de l'application.
PythonUtilise le pilote de stockage externe configuré pour téléverser, vérifier l'intégrité, mettre en cache, récupérer et décoder une enveloppe Avro externe. Sans pilote, les appelants peuvent ajouter ou inspecter un payload_reference opaque.
RustAjoute et renvoie une référence opaque et ses métadonnées. Le SDK Rust actuel ne revendique aucun pilote de stockage externe.

Workflow Streams et MessageStream embarqué​

Les noms concordent lorsque le comportement concorde, mais les modèles ne sont pas interchangeables.

ConceptWorkflow Stream en mode serviceMessageStream Laravel embarqué
AdresseExécution de workflow + nom du fluxInstance/exécution de workflow + clé du flux
DirectionSortie de workflow uniquementBoîtes de réception et d'envoi du workflow
Premier offset01
LivraisonAu moins une fois ; point de reprise géré par le consommateurAu moins une fois ; curseur de message géré par le moteur
Poursuite par une nouvelle exécutionAucun transfert de curseur du fluxLe curseur de réception est transféré à la nouvelle exécution
Messages entrants du workflowNon fournis ; utiliser les signaux ou mises à jourFournis par inbox()->receive()

Waterline utilise une table normalisée commune aux deux modes et affiche le mode, le cycle de vie, les offsets de tête/curseur, le nombre en attente, la direction et l'erreur. Il ne présente pas les flux de sortie du mode service comme une boîte de réception de workflow.

Qualification​

Le manifeste public des scénarios Workflow Stream exige des exécutions sur artefacts publiés couvrant un producteur PHP avec des consommateurs Python et Rust, le redémarrage du worker producteur, la reconnexion du consommateur, le cycle de vie/la contre-pression/l'annulation et les références aux charges utiles externes. Un résultat de publication doit consigner chaque scénario requis. Les seuls tests unitaires des sources ne constituent pas une preuve de conformité.

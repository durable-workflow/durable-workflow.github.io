Référence API opérateur Waterline

Waterline est l'interface opérateur de l'état durable pour Laravel embarqué et les déploiements de serveur autonome. Son interface utilise la même API HTTP+JSON documentée ici. Scripts, tableaux de bord et agents peuvent donc lire les faits durables sans analyser de HTML.

Utilisez cette référence pour des preuves opérateur typées : détail d'exécution, export d'historique, actions possibles, commandes disponibles, vues enregistrées, préférences et visibilité des planifications. La supervision explique la distinction entre état durable Waterline et télémétrie worker/runtime.

Installation​

Installez Waterline dans l'application Laravel embarquée qui installe le paquet Workflow :

composer require \
  durable-workflow/waterline:2.12.1 \
  durable-workflow/workflow:2.11.0
php artisan waterline:install

Les versions générées sélectionnent des versions stables 2.x de Waterline et Workflow. Le mode embarqué lit directement l'état de l'application sans SDK de service. Après mise à niveau de Waterline, publiez les ressources actuelles :

composer update durable-workflow/waterline
php artisan waterline:publish

Pour l'observation en mode service dans un hôte Laravel, installez aussi le SDK PHP :

composer require durable-workflow/sdk:3.2.0

L'image de service Waterline autonome inclut déjà ce SDK. Les paramètres de connexion, d'authentification et de persistance sont décrits dans la supervision.

Langue de l'interface​

Waterline prend en charge l'anglais, le portugais brésilien, le chinois simplifié, le français, l'allemand, le japonais, l'espagnol et l'ukrainien, en mode embarqué et service. Définissez la langue dans l'environnement de l'application Laravel ou du conteneur de service :

WATERLINE_LOCALE=es

Anglaisen
Portugais brésilienpt-BR
Chinois simplifiézh-Hans
Françaisfr
Allemandde
Japonaisja
Espagnoles

Les alias régionaux espagnols comme es-ES, es-MX et es-419 sélectionnent l'interface espagnole commune. pt, pt_br et les variantes de casse sélectionnent le portugais brésilien (pt-BR). Les autres régions portugaises reviennent à l'anglais. Les nombres, libellés des graphiques et durées relatives suivent la langue d'interface choisie. Utilisez zh-Hans pour le chinois simplifié. zh, zh-CN, zh-SG et les balises explicitement simplifiées comme zh-Hans-CN sélectionnent la même interface. Les traits de soulignement et variantes de casse sont acceptés. Les balises traditionnelles zh-Hant, zh-TW et zh-HK reviennent à l'anglais. Utilisez ja pour le japonais. Les alias régionaux comme ja-JP, traits de soulignement et variantes de casse sélectionnent la même interface japonaise. Utilisez fr pour le français. fr-FR, fr-CA, traits de soulignement et variantes de casse sélectionnent l'interface française commune. Utilisez de pour l'allemand. de-DE, de-AT, de-CH, traits de soulignement et variantes de casse sélectionnent l'interface allemande commune.

L'anglais est la langue par défaut et de repli. Les applications embarquées peuvent aussi définir waterline.locale dans leur configuration résolue. Reconstruisez le cache de configuration Laravel après modification. Waterline conserve la langue de l'application hôte, les noms de workflows, identifiants, charges utiles et textes d'exception originaux. Les noms de champs JSON et états machine gardent leurs valeurs existantes.

Frontière de déploiement​

Waterline dispose de deux adaptateurs backend :

  • Le mode embarqué s'exécute dans Laravel et lit l'état durable du paquet Workflow dans le même processus.
  • Le mode service exécute l'image publiée et lit un espace de noms du serveur autonome via durable-workflow/sdk et son API publique.

Les deux exposent les routes documentées ici. Le mode service les traduit vers les contrats serveur correspondants :

Famille de routes WaterlineContrat du serveur autonome utilisé en mode service
GET /waterline/api/v2/healthSanté serveur, enregistrement des workers et visibilité des files.
GET /waterline/api/statsTableau de bord opérateur et instantané de métriques limités à l'espace de noms.
Listes de workflows, détail d'exécution et export d'historiqueListe, détail, exécutions, historique et diagnostics de la référence API Server.
Signaux, mises à jour, requêtes de lecture, annulation, terminaison, réparation et archivageContrats correspondants de commandes et réparation des workflows serveur.
Routes sous /waterline/api/v2/schedulesContrats serveur de liste, détail, historique et mutation des planifications.

API serveur, CLI et SDK restent directement accessibles avec Waterline. Ne supposez aucune visibilité entre modes ou espaces de noms : lecture et actions restent dans le runtime et l'espace de noms propriétaires. Les modes de déploiement définissent cette frontière commune du produit.

Chemin de base et périmètre​

Waterline est monté sous le chemin configuré dans l'application Laravel. Les exemples utilisent /waterline. Si votre préfixe diffère, conservez les suffixes /api/....

Quand WATERLINE_NAMESPACE est configuré, chaque route de liste, détail, planification et action opérateur est limitée à cet espace. Les lectures et commandes vers un autre espace renvoient une sémantique « introuvable » sans divulguer l'état des workflows de cet espace.

curl -sS "$APP_URL/waterline/api/instances/order-1001" \
  -H "Accept: application/json" | jq '.status, .run_id, .actionability'

Authentification​

Chaque contrôleur d'interface et d'API JSON passe par le contrôle d'accès Waterline. En mode embarqué, l'hôte Laravel le définit : gardes, middlewares, gates, politiques, sessions SSO/OIDC/SAML, groupes d'annuaire, jetons de service et limites de débit applicables.

Le groupe actuel de l'API JSON opérateur exclut le middleware CSRF Laravel afin que l'hôte applique une frontière cohérente de session ou jeton aux lectures et commandes. L'hôte reste responsable de l'authentification et de la documentation des protections CSRF ajoutées autour de l'API pour les sessions navigateur.

L'image autonome n'a pas d'utilisateurs d'application hôte. Placez-la derrière un proxy inverse authentifiant ou sur une interface privée avant de définir WATERLINE_ALLOW_UNAUTHENTICATED=true. Ce paramètre délègue le contrôle d'entrée au déploiement environnant. Séparément, WATERLINE_SERVER_TOKEN authentifie les appels SDK PHP au serveur autonome. N'exposez jamais cet identifiant au navigateur.

WATERLINE_ACCESS_MODE=read_only bloque localement les routes de mutation. operator les active, mais le serveur connecté applique toujours le rôle de son jeton et les autorisations d'espace de noms. La supervision donne un exemple de déploiement et détaille les deux frontières d'authentification.

Tableau de bord et santé​

MéthodeCheminRôle
GET/waterline/api/statsTotaux du tableau de bord, compteurs de retard, politique de réparation, métriques opérateur et tendances des workers.
GET/waterline/api/v2/healthSanté du paquet/runtime Waterline et disponibilité de la source v2.

/waterline/api/stats est le résumé du tableau de bord. Traitez operator_metrics comme des diagnostics JSON propres à Waterline, pas une source de collecte Prometheus. Utilisez les métriques SDK worker pour la latence du runtime et la télémétrie applicative personnalisée.

Le périmètre d'exploitation opérateur définit leur interprétation lors des déploiements et incidents. En particulier :

Famille de champsSignification
operator_metrics.backlog.*Comptages durables du travail exécutable, différé, loué, défaillant, à réparer, à prise en charge échouée ou bloqué par compatibilité, et faits globaux de débit tasks_added_last_minute et tasks_dispatched_last_minute.
operator_metrics.matching_role.*Contrat local de mise en correspondance/distribution du processus répondant : queue_wake_enabled, topologie shape, task_dispatch_mode, partition_primitives figées et backpressure_model courant.
operator_metrics.repair.*Empreinte des passages de réparation : candidats choisis, ancienneté et pression de balayage.
operator_metrics.projections.*Comptages des dérives de projection des résumés, attentes, chronologies, temporisateurs et filiations.
operator_metrics.command_contracts.*Instantanés des anciens contrats WorkflowStarted qui nécessitent encore un rattrapage.
operator_metrics.history.*Pression de taille et de nombre d'événements et recommandations continue-as-new.
queue_visibility.available, queue_visibility.reasonDisponibilité de la visibilité des files par espace de noms sur cet hôte et raison d'indisponibilité.
queue_visibility.task_queues[].stats.*Retard et ancienneté par file, nombre de pollers, tâches de workflow/activité prêtes ou louées et débits tasks_added_last_minute / tasks_dispatched_last_minute de la file.
queue_visibility.task_queues[].repair.*Pression de réparation locale : candidats, échecs de distribution, baux expirés, distributions en retard et ancienneté maximale de chaque condition.
coordination_alerts[]Synthèse d'avertissements et erreurs des contrôles de santé et des risques des files : retard sans pollers, pollers périmés ou anciens candidats à la réparation.
checks[], categories.*Contrôles de santé v2 bloquants ou indicatifs, avec category = correctness | acceleration par contrôle et synthèses de catégorie utilisées dans la vue workers.
engine_source, readiness_contractUtilisation active du pont opérateur v2 et contrat de disponibilité régissant cet état.

Les champs de débit répondent à une question précise : les entrées durables arrivent-elles plus vite que leur distribution ? tasks_added_last_minute compte les lignes de tâche distinctes créées dans les 60 dernières secondes. tasks_dispatched_last_minute compte celles dont la dernière distribution réussie est dans ce même intervalle.

Utilisez ces totaux avec les routes serveur de visibilité des files. Waterline indique si les entrées dépassent la distribution. /api/task-queues et /api/task-queues/{taskQueue} indiquent si la file chargée est saturated, volontairement throttled, no_active_workers ou manque autrement de pollers sains ou d'emplacements.

GET /waterline/api/v2/health expose les mêmes preuves locales aux files sans quitter Waterline. Scripts et tableaux de bord qui ont besoin de la situation d'un espace de noms doivent lire queue_visibility.task_queues[] pour les statistiques par file et coordination_alerts[] pour savoir quelle file ou condition de santé nécessite l'attention de l'opérateur.

Les champs matching_role répondent à une autre question : quelle topologie de mise en correspondance sert ce nœud ? shape distingue in_worker et dedicated. partition_primitives fige les axes de routage connection/queue/compatibility/namespace. backpressure_model annonce actuellement lease_ownership. Ce bloc est local au processus. Lors d'un déploiement à topologies mixtes, comparez-le entre nœuds avant d'attribuer les différences de retard ou d'interrogation à un problème worker.

GET /waterline/api/v2/health utilise la même distinction : error bloque, warning est indicatif et ok signifie que le pont opérateur v2 courant est prêt.

Vues de liste​

Les listes sont regroupées par état durable :

MéthodeCheminCatégorie
GET/waterline/api/flows/runningExécutions ouvertes ou activement bloquées.
GET/waterline/api/flows/completedExécutions fermées avec succès, y compris celles poursuivies avec closed_reason = continued.
GET/waterline/api/flows/failedExécutions échouées.
GET/waterline/api/flows/cancelledExécutions annulées.
GET/waterline/api/flows/terminatedExécutions terminées de force.

Les lignes sont des résumés opérateur compacts. Les champs stables incluent l'identité (id, instance_id, run_id, workflow_type), l'état (status, closed_reason, archived_at), les temps, history_event_count, history_size_bytes, continue_as_new_recommended et les indicateurs de réparation ou d'action possible comme repair_blocked.

Détail d'exécution sélectionnée​

Waterline a deux modes d'adressage :

MéthodeCheminRôle
GET/waterline/api/instances/{instanceId}Exécution courante sélectionnée d'une instance.
GET/waterline/api/instances/{instanceId}/runs/{runId}Exécution explicitement sélectionnée.
GET/waterline/api/flows/{id}Ancienne recherche de détail par ligne Waterline ou identifiant d'exécution.

Le détail d'exécution est le contrat JSON de référence des écrans opérateur. Il contient l'état durable et les diagnostics dérivés :

Famille de champsSignification
activities, timers, waits, childrenAttentes courantes et historiques reconstruites d'abord à partir de l'historique typé.
signals, updates, declared_signals, declared_updates, declared_queriesCycle de vie des commandes et cibles chargeables du contrat de workflow.
timelineÉvénements durables ordonnés et entrées de diagnostic.
exceptions, logsFaits d'échec et contexte de relecture ou diagnostic.
can_signal, can_update, can_query, can_cancel, can_terminate, can_archiveActions disponibles pour l'interface et l'automatisation sur l'exécution choisie.
actionabilityContrat versionné de réparation et de preuves décrit ci-dessous.

L'automatisation doit préférer le détail aux captures d'écran. Une capture montre ce qu'a vu l'opérateur. Le détail explique pourquoi un workflow peut ou non être réparé, interrogé, annulé, archivé ou relu.

Export d'historique​

Les exports sont des ensembles de relecture et diagnostic. Ils incluent volontairement les charges utiles stockées des workflows, commandes, activités, mises à jour, tâches, échecs et historique pour reproduire ou archiver l'exécution.

MéthodeCheminRôle
GET/waterline/api/instances/{instanceId}/history-exportExporter l'exécution courante sélectionnée d'une instance.
GET/waterline/api/instances/{instanceId}/runs/{runId}/history-exportExporter une exécution explicite.
GET/waterline/api/flows/{id}/history-exportAncien export de détail par ligne Waterline ou identifiant d'exécution.

Si l'export peut quitter un environnement protégé, configurez d'abord la suppression des données sensibles de l'export. Les outils en aval doivent préserver ses métadonnées redaction pour rendre la politique appliquée visible.

Contrat des actions possibles​

Waterline annote listes, détails, chronologies et exports avec le contrat versionné :

{
  "actionability_contract": {
    "schema": "waterline.actionability",
    "version": 1
  }
}

Il est identifié par actionability_contract.schema = waterline.actionability avec actionability_contract.version = 1.

Le bloc actionability d'exécution indique si l'exécution choisie est réparable :

ChampSignification
repair_staterepairable, blocked, not_needed ou unknown.
repairableRaccourci booléen pour repair_state = repairable.
blocked_reasonCode de raison stable si repair_state = blocked.
status_bucketCatégorie Waterline ayant déterminé la décision pour l'exécution.
closed_reasonRaison durable de fermeture si l'exécution est fermée.
task_problemPrésence d'un problème de tâche vu par Waterline sur l'exécution.
diagnostic_only_evidenceVrai si au moins une ligne informe sans constituer une source de reprise.

Les preuves sous activities, waits, timers, exceptions, logs et les entrées de chronologie ou d'export peuvent contenir leur bloc actionability :

ChampSignification
stateactionable si la ligne est une source de réparation valide, sinon diagnostic_only.
repair_sourceVrai uniquement pour les lignes appuyées par une source de référence réparable.
diagnostic_onlyVrai si la ligne ne doit pas servir de source de reprise.
history_authorityRéférence source telle que typed_history, mutable_open_fallback, failure_row_fallback ou unsupported_terminal_without_history.
history_unsupported_reasonCode de raison stable d'un historique de repli non pris en charge.

Agents et scripts doivent conditionner réparation et reprise à actionability.repair_state, actionability.repairable et actionability.repair_source de chaque ligne. diagnostic_only = true constitue une preuve, pas une autorisation de relecture ou de reprise.

Actions opérateur​

Les actions Waterline sont des commandes durables émises via le contrat d'exécution sélectionnée. Les routes d'instance ciblent l'exécution courante. Les routes d'exécution rejettent explicitement les cibles périmées ou incorrectes.

MéthodeCheminRôle
POST/waterline/api/instances/{instanceId}/queries/{query}Exécuter une requête de lecture déclarée sur l'exécution courante.
POST/waterline/api/instances/{instanceId}/signals/{signal}Envoyer un signal à l'exécution courante.
POST/waterline/api/instances/{instanceId}/updates/{update}Soumettre une mise à jour à l'exécution courante.
POST/waterline/api/instances/{instanceId}/repairDistribuer un passage de réparation de l'exécution courante si le contrat l'autorise.
POST/waterline/api/instances/{instanceId}/cancelDemander l'annulation de l'exécution courante.
POST/waterline/api/instances/{instanceId}/terminateTerminer de force l'exécution courante.
POST/waterline/api/instances/{instanceId}/archiveArchiver l'exécution fermée sélectionnée.
POST/waterline/api/instances/{instanceId}/runs/{runId}/queries/{query}Exécuter une requête de lecture sur une exécution explicite.
POST/waterline/api/instances/{instanceId}/runs/{runId}/signals/{signal}Envoyer un signal uniquement si l'exécution choisie est courante.
POST/waterline/api/instances/{instanceId}/runs/{runId}/updates/{update}Soumettre une mise à jour uniquement si l'exécution choisie est courante.
POST/waterline/api/instances/{instanceId}/runs/{runId}/repairRéparer une exécution explicitement choisie.
POST/waterline/api/instances/{instanceId}/runs/{runId}/cancelAnnuler uniquement si l'exécution choisie est courante.
POST/waterline/api/instances/{instanceId}/runs/{runId}/terminateTerminer de force uniquement si l'exécution choisie est courante.
POST/waterline/api/instances/{instanceId}/runs/{runId}/archiveArchiver l'exécution fermée sélectionnée.

Signaux, mises à jour et requêtes acceptent arguments en JSON. Les arguments invalides renvoient des erreurs de validation par champ. Les blocages de relecture renvoient 409 Conflict avec une raison stable comme workflow_definition_unavailable au lieu de tenter une exécution approximative.

Inspection des mises à jour​

MéthodeCheminRôle
GET/waterline/api/instances/{instanceId}/updates/{updateId}Inspecter le cycle de vie d'une mise à jour de l'exécution courante.
GET/waterline/api/instances/{instanceId}/runs/{runId}/updates/{updateId}Inspecter le cycle de vie d'une mise à jour d'une exécution explicite.

Cette inspection permet à une interface ou un agent d'expliquer si une mise à jour est acceptée, appliquée, terminée, rejetée, expirée en attente ou bloquée par la compatibilité de relecture.

Planifications​

Les routes de planification Waterline offrent visibilité et actions opérateur v2 :

MéthodeCheminRôle
GET/waterline/api/v2/schedulesLister les planifications visibles dans le périmètre courant.
GET/waterline/api/v2/schedules/{scheduleId}Décrire une planification.
GET/waterline/api/v2/schedules/{scheduleId}/historyLire les événements d'audit du cycle de vie de la planification.
POST/waterline/api/v2/schedules/{scheduleId}/pauseSuspendre les futurs déclenchements.
POST/waterline/api/v2/schedules/{scheduleId}/resumeReprendre une planification suspendue.
POST/waterline/api/v2/schedules/{scheduleId}/triggerDéclencher immédiatement.
POST/waterline/api/v2/schedules/{scheduleId}/backfillRattraper une période.
DELETE/waterline/api/v2/schedules/{scheduleId}Supprimer une planification.

Une planification est identifiée par son espace de noms et son schedule_id. Le même schedule_id peut exister dans plusieurs espaces de noms. Chaque route propre à une planification accepte un paramètre namespace facultatif, en paramètre d'URL ou dans le corps de la requête :

  • Un Waterline limité à un espace de noms n'agit que sur son propre espace de noms. C'est le cas du Waterline embarqué avec WATERLINE_NAMESPACE défini et de tout déploiement en mode service. Une requête pour un autre espace de noms renvoie 404.
  • Un Waterline embarqué couvrant tout le cluster agit sur l'espace de noms demandé. Sans namespace, un schedule_id présent dans plusieurs espaces de noms renvoie 409 avec la raison schedule_namespace_required. Rien n'est modifié.
curl -sS -X POST \
  "$APP_URL/waterline/api/v2/schedules/nightly-invoice-sync/pause?namespace=billing" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"note": "Supplier maintenance"}' | jq '.status, .note'

Lignes de planification​

La réponse de liste est paginée avec data, current_page, last_page, per_page, total et operator_scope. Chaque ligne de data a les mêmes champs en mode embarqué et service :

ChampSignification
schedule_idIdentifiant de la planification. Envoyez-le avec namespace à chaque route propre à une planification.
idMême valeur que schedule_id, conservée pour les anciens clients.
namespaceEspace de noms de la planification.
workflow_type, workflow_classWorkflow démarré par la planification. Chacun peut valoir null.
status, pausedactive, paused ou deleted, et si la planification est suspendue ou non.
noteNote de l'opérateur, ou null.
specCadence : cron_expressions (chaînes cron), intervals (objets avec des durées ISO 8601 every et offset facultatif) et timezone.
overlap_policyskip, buffer_one, buffer_all, cancel_other, terminate_other ou allow_all.
next_fire_at, last_fired_atHorodatages ISO 8601, ou null.
last_outcomeRésultat du dernier déclenchement enregistré, ou null si aucun n'a été enregistré. Il contient outcome (par exemple scheduled, drained, backfilled, skipped ou failed), at, reason, workflow_id et run_id.
fires_count, failures_count, skipped_trigger_count, remaining_actionsCompteurs, ou null quand le backend ne fournit pas ce compteur.
search_attributesAttributs de recherche de la planification, ou null.
created_at, updated_atHorodatages ISO 8601.

Une ligne avec last_fired_at mais sans last_outcome signifie que le backend a fourni l'heure du déclenchement sans son résultat.

Les lignes de liste et les réponses de détail, pause et resume incluent aussi action, max_runs, jitter_seconds, paused_at, last_skip_reason, last_skipped_at, latest_workflow_instance_id, buffered_actions, memo et recent_actions. Chaque action récente contient outcome, fired_at, reason, workflow_id, run_id et occurrence_time. latest_instance_id reprend latest_workflow_instance_id pour les anciens clients. Un spec conserve, après ses champs de cadence, toutes les autres clés stockées par le backend.

Résultats du déclenchement et du rattrapage​

trigger accepte un champ overlap_policy facultatif. La route renvoie schedule_id, namespace, outcome (triggered, buffered, buffer_full ou skipped), triggered, workflow_id, run_id et reason. triggered vaut true uniquement si un workflow a démarré. instance_id reprend workflow_id pour les anciens clients.

backfill exige les horodatages ISO 8601 from et to et accepte un champ overlap_policy facultatif. La route renvoie schedule_id, namespace, fires_attempted, started_count, skipped_count, failed_count et results. Chaque résultat contient fire_time, workflow_id, outcome (started, skipped ou failed) et reason. Pour les anciens clients, chaque résultat reprend aussi schedule_id, et cron_time, instance_id et error reprennent fire_time, workflow_id et le reason d'un résultat en échec. backfill refuse avec 422 et la raison invalid_time_range une fenêtre dont la fin n'est pas postérieure au début.

Les deux routes refusent une valeur overlap_policy inconnue avec 422 et la raison invalid_overlap_policy.

Vues enregistrées et préférences​

Vues et préférences sont des configurations opérateur de l'interface, pas de l'historique de workflow. Elles restent utiles aux procédures stables, car les équipes peuvent partager les filtres et la disposition exacts utilisés en incident.

MéthodeCheminRôle
GET/waterline/api/saved-viewsLister les vues opérateur enregistrées.
POST/waterline/api/saved-viewsCréer une vue enregistrée.
GET/waterline/api/saved-views/{view}Lire une vue enregistrée.
PUT/waterline/api/saved-views/{view}Modifier une vue enregistrée.
DELETE/waterline/api/saved-views/{view}Supprimer une vue enregistrée.
GET/waterline/api/preferences/{surface}Lire les préférences d'une interface.
PUT/waterline/api/preferences/{surface}Modifier les préférences d'une interface.

Ne traitez pas les noms de vue ou charges utiles de préférences comme des faits durables. Pour les preuves, citez le détail d'exécution ou l'export d'historique.

Contrat des erreurs​

Waterline utilise les codes HTTP ordinaires et des détails d'erreur JSON :

ÉtatSignification
400Requête mal formée ou charge utile d'action non prise en charge.
404Instance, exécution, mise à jour, planification, vue enregistrée ou interface de préférences introuvable dans l'espace de noms courant.
409L'exécution choisie ne peut effectuer l'action, souvent car elle est historique, fermée, bloquée à la relecture ou sans définition disponible. Une requête de planification couvrant tout le cluster renvoie aussi 409 quand son schedule_id exige un namespace.
422Échec de validation, avec erreurs par champ dans la réponse.
500Échec applicatif inattendu.

L'automatisation doit décider selon le code et les champs stables comme blocked_reason, query_blocked_reason, outcome, reason et actionability. N'analysez pas les messages de notification ou libellés de boutons comme contrat.

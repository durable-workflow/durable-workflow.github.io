Compatibilité des versions

Cette page est le contrat de référence de compatibilité et d'autorité de publication de la plateforme publique Durable Workflow. Elle définit de manière unique :

  • les interfaces publiques,
  • le niveau de stabilité de chacune,
  • les modifications autorisées dans une version corrective, mineure ou majeure,
  • les champs contractuels et ceux réservés au diagnostic,
  • le protocole de négociation de version utilisé par les clients pour refuser toute opération si le serveur annonce une interface qu'ils ne savent pas utiliser.

Les documents de stabilité de chaque paquet (par exemple docs/api-stability.md dans durable-workflow/workflow, la référence CLI dw et la page API opérateur Waterline) dépendent de cette page. Ils précisent ces règles pour leur paquet. En cas de divergence, cette page fait foi et le document du paquet comporte un bogue.

Le même contrat est publié dans un format lisible par machine pour que SDK, manifestes serveur et contrôles CI se valident contre une référence unique :

  • surface_stability_contract dans la réponse de GET /api/cluster/info du serveur autonome Durable Workflow, schéma durable-workflow.v2.surface-stability.contract, version 5.
  • Un miroir figé de ce manifeste dans ce dépôt à static/compatibility-contract.json.
  • La classe PHP Workflow\V2\Support\SurfaceStabilityContract, source dans le processus que le serveur réexporte.

Une publication qui modifie une interface ci-dessous, son niveau de stabilité, ses champs ou ses règles d'incompatibilité doit mettre à jour cette page, le miroir JSON, le manifeste PHP et les documents de stabilité des paquets concernés dans la même modification. La CI documentaire valide le contrat lisible par machine, les métadonnées Rust publiées quand elles sont disponibles et les spécifications du protocole worker. L'alignement éditorial de cette page avec le manifeste reste une responsabilité explicite de la revue de publication.

Complément : catalogue des spécifications de protocoles​

Cette page indique quelles interfaces sont publiques et comment elles peuvent évoluer. Le catalogue Spécifications des protocoles de la plateforme indique où se trouve la spécification normative lisible par machine de chacune, son format (OpenAPI pour les API HTTP, JSON Schema pour les familles d'objets, AsyncAPI pour les flux d'événements), le dépôt responsable, les familles d'objets couvertes et l'URL publique de l'artefact. Auteurs de SDK, agents et opérateurs doivent valider leurs usages contre ce catalogue, sans relire toute la prose ni dépendre de détails d'implémentation propres à un dépôt.

Le catalogue est annoncé sous platform_protocol_specs dans GET /api/cluster/info.

La référence lisible par machine est publiée à /platform-protocol-specs.json avec le schéma durable-workflow.v2.platform-protocol-specs.catalog, version 16.

Le champ surface_family de chaque entrée doit exister dans le contrat ci-dessus. La CI du site valide le catalogue, résout les URL publiques des spécifications et rejette les champs de référence propres à un dépôt.

La découverte du runtime et la qualification de conformité utilisent des références de protocole distinctes. Choisissez la ligne correspondant à votre tâche. Une même étiquette de version ne fait pas d'un résolveur historique versionné un alias de la référence Server non versionnée.

Chaque entrée obligatoire du catalogue des protocoles porte l'état published. L'entrée du transport invocable reste in_progress. Le schéma cluster_info_envelope fixe l'interface de découverte depuis laquelle toutes les autres entrées sont accessibles.

Niveaux de stabilité​

Chaque interface publique Durable Workflow porte exactement un de ces niveaux. Les niveaux sont explicites. Une interface non classée n'est pas publique.

NiveauSignificationModifications incompatibles autorisées
frozenFormat d'échange ou forme persistée qui doit se décoder de la même manière pendant toute la vie du workflow. Renommer, supprimer ou réaffecter un champ casse le protocole et n'est jamais une modification mineure.Uniquement en introduisant une primitive parallèle avec un nouveau nom de type. La forme d'origine reste décodable indéfiniment.
stableInterface publique couverte par la garantie semver de la plateforme. Les ajouts sont publiés dans des versions mineures.Version majeure uniquement.
prereleaseInterface publique fonctionnellement complète, mais encore modifiable avant la publication correspondante 1.0.0 / 2.0.0.Dans des préversions clairement identifiées et signalées dans les notes de publication.
experimentalInterface publique instable. Peut changer à chaque publication, y compris corrective. Les appelants doivent l'activer en lisant son indicateur expérimental.Toute publication, avec mention dans les notes.

Documents de stabilité par paquet​

Ces documents précisent les règles de cette page pour chaque paquet :

  • durable-workflow/workflow (PHP) : docs/api-stability.md. Référence pour l'API PHP d'écriture, les classes Support\* destinées au serveur et les tables de formats figés d'événements d'historique.
  • durable-workflow/sdk (PHP) : README.md. Référence pour l'API distante de client et worker indépendante du framework, distribuée sur Packagist.
  • durable-workflow/server : README.md et docs/contracts/*. Référence pour les contrats de requêtes et réponses du serveur autonome.
  • CLI dw : /docs/polyglot/cli-reference. Référence pour les formes JSON de sortie et codes de sortie.
  • SDK Python : README.md dans durable-workflow/sdk-python. Référence pour l'API publique du paquet durable_workflow.
  • SDK Rust : README.md et [package.metadata.durable-workflow] dans durable-workflow/sdk-rust. Référence pour l'API publique de la crate durable-workflow et sa déclaration de compatibilité.

Règles de publication​

Ces règles s'appliquent à toutes les familles publiques ci-dessus. Elles sont reproduites sous release_rules dans le miroir JSON.

Versions correctives​

Autorisé :

  • corriger des bogues en préservant le contrat documenté
  • corriger la documentation
  • mettre à jour les dépendances sans modifier l'interface publique
  • modifier des interfaces marquées experimental

Interdit :

  • supprimer ou renommer un champ, une route, une commande ou une classe stable ou frozen
  • restreindre les entrées acceptées par une route ou commande stable
  • changer le sens d'un champ stable existant

Versions mineures​

Autorisé :

  • ajouter des champs, routes, commandes ou classes à une interface stable
  • ajouter des paramètres facultatifs avec des valeurs par défaut sûres
  • ajouter des indicateurs de capacité aux réponses de découverte
  • promouvoir une interface prerelease ou experimental à stable

Interdit :

  • supprimer ou renommer un champ, une route, une commande ou une classe stable ou frozen
  • changer le sens d'un champ stable ou frozen existant

Versions majeures​

Autorisé :

  • supprimer, renommer ou restreindre une interface stable
  • augmenter le control_plane.version ou worker_protocol.version requis
  • retirer une plage de versions SDK ou CLI précédemment prise en charge

Obligatoire :

  • annoncer la modification dans les notes au moins une version mineure avant la publication majeure
  • si possible, fournir l'ancienne et la nouvelle interface ensemble dans une version mineure antérieure pour permettre la migration avant la majeure
  • documenter la migration dans le guide de migration avant la publication

Champs de diagnostic et champs garantis​

Chaque champ d'une interface stable ou frozen est garanti ou uniquement diagnostique. Leurs règles d'évolution diffèrent :

  • Les champs garantis font partie du contrat documenté. Les producteurs doivent continuer à les émettre sous la forme documentée. Les consommateurs peuvent compter sur leur présence et leur sens. Supprimer ou renommer un champ garanti d'une interface stable est une modification majeure.
  • Les champs uniquement diagnostiques servent au triage humain, au débogage et à l'observabilité. Ils peuvent être ajoutés, renommés ou supprimés dans toute version mineure. Ils doivent porter diagnostic_only: true (ou son équivalent documentaire) là où ils sont documentés. Les consommateurs ne doivent ni analyser, ni persister, ni utiliser ces champs pour leurs décisions de production.

Les anciens consommateurs doivent ignorer les champs supplémentaires inconnus d'une forme stable ou frozen pour assurer la compatibilité ascendante. Les champs obligatoires inconnus doivent provoquer un refus. SDK et CLI publient leur propre comportement de compatibilité dans leurs documents de stabilité.

Matrice de compatibilité​

Cette matrice d'exploitation indique les versions de clients validées contre les manifestes de protocole serveur. Les composants la valident à l'exécution via GET /api/cluster/info et refusent de fonctionner si les manifestes divergent.

L’appVersion enregistré du chart Helm est 2.10.1, correspondant au Server sélectionné. La vérification de la paire publiée contrôle les digests OCI/du paquet et l’identité source ; ce n’est pas le résultat d’une nouvelle installation de cluster. PyPI affiche la version de distribution Python sous 2.8.0. La forme d'installation PEP 440 documentée 2.8.0 désigne cette même publication. Cette normalisation ne crée pas une seconde version prise en charge.

La combinaison choisie évolue après qualification des consommateurs concernés. Les registres Server publiés et les démarrages rapides générés utilisent ces artefacts. Les paquets peuvent être publiés indépendamment, avec compatibilité vérifiée via leurs manifestes de protocole, capacités et contrôles consommateurs.

Les anciens artefacts alpha et bêta sont historiques. Ils ne sont pas des choix alternatifs pour démarrer. L'historique des publications reste intact.

Chaque composant stable suit le versionnage sémantique. Les capacités ajoutées peuvent être publiées dans des versions compatibles. Les changements publics incompatibles exigent une version majeure. Vérifiez par découverte les capacités du Server et des workers installés avant d'activer une fonctionnalité.

Compatibilité des protocoles à l'exécution​

Les versions de paquets sélectionnent la ligne de produit prise en charge. Les manifestes de protocole ajoutent un second contrôle avec refus par défaut :

ClientLigne de produitPlan de contrôleProtocole d’enregistrement worker par défaut
CLI2.3.02sans objet
SDK PHP3.2.021.20
SDK Python2.8.021.20
SDK Rust4.2.021.20

Les SDK permettent aussi de sélectionner explicitement le protocole worker 1.19 pour un ancien Server compatible. L’annulation coopérative exige 1.20. Sélectionner 1.19 ne fournit pas cette capacité. Chaque opération peut utiliser sa version minimale documentée. La valeur par défaut de l’enregistrement ne signifie donc pas que toutes les requêtes worker envoient 1.20.

Le Server publié actuel annonce la version worker indiquée dans le tableau des rôles de référence ci-dessus. Il accepte des en-têtes de la même majeure avec une mineure inférieure ou égale à celle annoncée, puis renvoie sa version annoncée. Les en-têtes absents ou mal formés, les majeures différentes et les mineures worker en avance sur le serveur sont refusés. La CLI valide control_plane.version: "2".

Le version racine du serveur identifie son build. Les clients doivent utiliser les manifestes control_plane, worker_protocol, client_compatibility et surface_stability_contract renvoyés par GET /api/cluster/info pour négocier le protocole.

Workflow et Waterline doivent utiliser des versions 2.x compatibles. La découverte du runtime et les contraintes des paquets définissent la frontière de compatibilité après la publication stable.

Exemples de validation à l'exécution​

Les SDK valident la découverte avant d'enregistrer un worker. Un serveur incompatible produit une erreur de compatibilité explicite au lieu de tenter un ancien parcours de préversion. Toutes les requêtes worker envoient X-Durable-Workflow-Protocol-Version. Les requêtes du plan de contrôle envoient X-Durable-Workflow-Control-Plane-Version: 2.

Avant promotion d'une ligne de produit, la qualification doit partir d'une machine propre, n'installer que les artefacts publiés ci-dessus et réussir les parcours de conformité PHP, Python et Rust. Les sources locales et substitutions non publiées ne constituent pas des preuves sur les artefacts publics.

Les métadonnées stables des paquets et la découverte du runtime définissent désormais la compatibilité 2.x prise en charge. La qualification installe toujours les artefacts publics ensemble avant publication. Les versions correctives et mineures suivent les règles sémantiques ci-dessous.

Progression des publications​

Les versions correctives préservent les contrats stables documentés. Les mineures peuvent ajouter des champs, routes, commandes, classes ou paramètres facultatifs avec des valeurs par défaut sûres. Les modifications stables incompatibles exigent une majeure et une migration documentée. Les formes figées des événements d'historique restent décodables indéfiniment. Une nouvelle forme utilise une primitive parallèle sans modifier un événement existant.

Chaque publication doit synchroniser les métadonnées des paquets, les notes, les commandes d'installation et les exemples interlangages.

Liste de contrôle de publication​

  • Confirmer que le contrat de compatibilité lisible par machine correspond au manifeste de stabilité de Workflow.
  • Confirmer que chaque version SDK choisie fonctionne avec le Server choisi.
  • Confirmer que les exemples d'installation utilisent le canal stable.
  • Confirmer que les métadonnées identifient la version SDK exacte et les versions de protocole. Consigner les qualifications Server ultérieures dans les preuves de compatibilité.
  • Confirmer la réussite de la conformité sur machine propre avec les artefacts publiés PHP, Python et Rust.
  • Confirmer que les notes décrivent les ajouts postérieurs à la référence et ne présentent pas d'anciennes préversions comme choix pris en charge.

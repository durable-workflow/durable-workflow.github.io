Version: 2.x

Supervision

Waterline est l'interface et l'API opérateur pour l'état des workflows. Sa distribution suit la frontière du runtime choisi : Cloud inclut Managed Waterline, tandis qu'en auto-hébergement, l'opérateur déploie Waterline séparément s'il souhaite cette interface.

Waterline est un même produit opérateur avec trois modes d'utilisation :

  • Le mode embarqué installe le paquet Composer dans l'application Laravel propriétaire des workflows et lit son état durable dans le même processus.
  • Le mode service auto-hébergé utilise l'image publiée durableworkflow/waterline et lit l'état du serveur autonome via le SDK PHP et l'API publique serveur. La distribution Server n'inclut ni n'exploite Waterline.
  • Cloud Managed Waterline est l'expérience opérateur limitée à un espace de noms incluse dans Durable Workflow Cloud. Cloud exploite Managed Waterline et le runtime de l'espace de noms associé.

Les interfaces embarquée et de service auto-hébergé exposent la même interface principale Waterline et les mêmes familles de routes opérateur /waterline/api/.... Cloud fournit ces capacités par son interface gérée, sans hôte Waterline à déployer par le client. Aucune de ces interfaces ne fusionne les états des runtimes : chaque vue se limite aux exécutions de son runtime et de son espace de noms. Pour Server auto-hébergé, les interfaces opérateur natives API, CLI et SDK restent disponibles avec ou sans Waterline. Consultez la référence API Server pour ces routes et la référence API opérateur Waterline pour les routes et contrats de réponse Waterline.

Durable Workflow a deux plans d'observabilité :

PlanSource de véritéQuestions habituelles
État durableBase de données et API du runtime propriétaire, projections Waterline et export d'historiqueLe workflow a-t-il démarré ? Quelle exécution est courante ? Quel signal, mise à jour, temporisateur, activité, nouvelle tentative ou échec a été validé ? Quelle action opérateur est sûre maintenant ?
Télémétrie worker/runtimeJournaux des workers de file, enregistreurs de métriques SDK, points de terminaison Prometheus/OpenMetrics et traces applicativesLes workers interrogent-ils les files ? Combien de temps prennent les tâches ? Un exportateur est-il configuré ? Les métriques personnalisées ont-elles quitté le processus worker ?

Waterline ne remplace pas les métriques des workers. Si une métrique personnalisée est enregistrée dans le code d'une activité ou d'un worker, collectez-la sur le point de télémétrie du worker. Waterline permet de la corréler à l'historique durable et à l'état courant de l'exécution.

La configuration des workers et clients reste distincte de l'interface opérateur. Utilisez la référence API du SDK PHP, la référence API du SDK Python ou la référence API du SDK Rust générées en complément des guides de langage pour connecter clients et workers au runtime propriétaire de l'espace de noms.

Si la télémétrie montre des prises en charge répétées, des courses d'achèvement tardif ou des baux bloqués, lisez aussi les garanties d'exécution et l'idempotence. Ce contrat distingue l'incertitude du transport au moins une fois des résultats durables dupliqués, pour éviter les mauvaises conclusions face à des preuves qui ressemblent à des doublons.

Rust SDK 4.7.0 ou ultérieur fournit des recorders interchangeables et un adaptateur facultatif metrics-prometheus. Le défaut est no-op ; l’application gère endpoint scrape et cycle d’exporter. Voir la configuration Rust et l’exemple publié pour noms exacts, tags bornés et limites d’observation. Cela ne configure pas les métriques Server ou Cloud.

Traçage OpenTelemetry​

Reliez les requêtes de l’application, les tâches de workflow et les tentatives d’activité entre processus avec le traçage OpenTelemetry facultatif. Choisissez la configuration du runtime qui gère vos exécutions.

Laravel embarqué​

Pour relier les logs de l'application à une exécution de workflow et à une tentative d'activité, configurez l'intégration facultative de traçage en mode embarqué (en anglais). Elle conserve le contexte W3C entre les workers de file, les nouvelles tentatives et la reprise, et utilise le fournisseur OpenTelemetry ainsi que les canaux de logs Laravel de votre application. Le guide explique comment activer le traçage, ajouter le tap de logs, exécuter les migrations du schéma et borner les exports. Consultez le diagramme des spans et la matrice des capacités des runtimes et SDK avant le déploiement.

Dans le fichier config/workflows.php de l’application, associez une variable d’environnement propre à l’application à la configuration de traçage existante :

'tracing' => [
    'enabled' => (bool) env('DW_TRACING_ENABLED', false),
    'baggage_allowlist' => [],
],

Cet exemple ne propage aucun baggage au départ. Installez l’API facultative et configurez le fournisseur, le tap de logs, les migrations et l’exporteur borné selon le guide lié, puis redémarrez les workers.

Traçage en mode service​

Configurez le fournisseur, l'échantillonnage, les propagateurs et un export borné avant d'activer la télémétrie du SDK. Consultez le guide PHP, le guide Python ou l'API Rust (en anglais).

RuntimeLimite de propagation
Laravel embarquéL'intégration Core facultative conserve le contexte entre les workers de l'application.
Serveur PHPLe guide du serveur exige une image applicative avec l'API facultative, l'option activée et le schéma nullable réel.
SDK PHP, Python et RustSpans de tâches/tentatives et corrélation des logs sur activation. La propagation durable exige la capacité exacte annoncée par le serveur. Une capacité absente ou mal formée produit des traces de tâches indépendantes.
Serveur Rust natifCette version PHP ne qualifie ni les carriers natifs ni la conversion du catalogue.
CloudCette version ne déploie rien dans Cloud. Vérifiez le support du runtime géré.

Les identifiants de trace, de run, d'activité, de tentative et de requête restent distincts. Le baggage utilise une liste autorisée, vide par défaut; les liens n'en contiennent pas. L'application possède les fournisseurs et exporteurs. Un arrêt brutal peut perdre la télémétrie; le replay ne garantit pas un export exactement une fois. L'historique durable fait foi pour les résultats métier.

Vues Waterline​

Vue du tableau de bord​

Le tableau de bord présente les totaux en cours, les compteurs d'exécutions récentes et les métriques de l'ensemble des workers pour voir rapidement si le travail progresse, stagne ou échoue.

Consultez le périmètre d'exploitation opérateur pour le contrat de déploiement et les procédures associés : diagnostics qui bloquent le trafic ou restent indicatifs, répartition des faits de santé des files entre Waterline et télémétrie worker, vérification de la reconstruction, de l'export et de l'archivage.

Vue du workflow​

Le détail présente la chronologie durable d'une exécution : activités, signaux, temporisateurs et workflows enfants dans l'ordre, avec leurs entrées, sorties et temps d'exécution.

Déploiement et accès à Waterline​

Laravel embarqué​

Installez Waterline dans votre application Laravel avec le paquet Workflow et exécutez ses migrations. Le guide complet d'installation et de configuration se trouve dans durable-workflow/waterline.

Le mode embarqué utilise la connexion à la base, les middlewares de route, le contrôle d'authentification et le paquet Workflow de l'application hôte. Exploitez l'application Laravel, ses workers de file, l'ordonnanceur, les migrations et les ressources Waterline comme une même unité de déploiement. La référence API opérateur Waterline contient la commande Composer actuelle et la publication des ressources.

Permissions des opérateurs en mode embarqué​

Ces contrôles facultatifs nécessitent Waterline 2.13.0. Conservez le gate de consultation viewWaterline : les gates d’action n’accordent aucun accès en lecture. Par défaut, les utilisateurs pouvant consulter Waterline embarqué peuvent effectuer les actions opérateur ; les nouveaux réglages sont explicites et préservent ce comportement lorsqu’ils sont absents. Vérifiez composer.lock : ce minimum fonctionnel ne met pas à jour la combinaison d’installation sélectionnée séparément, dont les commandes peuvent encore fixer un ancien paquet sans ces contrôles.

Pour bloquer les écritures opérateur pour tous, définissez 'read_only' => true dans config/waterline.php, ou reliez WATERLINE_READ_ONLY=true à la configuration hôte avant de reconstruire son cache. Consultation, exports d’historique, requêtes et vues/préférences personnelles gardent leur autorisation existante. Cela n’arrête pas les workers de l’hôte et ne modifie pas les permissions d’accès direct au SDK/Server.

Pour distinguer les permissions par utilisateur, définissez des gates Laravel dans un service provider et associez chaque groupe d’actions à restreindre. Les noms de permissions suivants relèvent de la politique de votre application :

use Illuminate\Support\Facades\Gate;

Gate::define('waterline-messages', fn ($user) => $user->can('support-workflows'));
Gate::define('waterline-operations', fn ($user) => $user->can('operate-workflows'));

Intégrez cette configuration à config/waterline.php :

'authorization' => [
    'gates' => [
        'messages' => 'waterline-messages',
        'repair' => 'waterline-operations',
        'cancel' => 'waterline-operations',
        'terminate' => 'waterline-operations',
        'archive' => 'waterline-operations',
        'schedules' => 'waterline-operations',
    ],
],

messages couvre signaux et mises à jour ; schedules couvre pause, reprise, déclenchement, backfill et suppression. Chaque gate reçoit l’utilisateur hôte courant et, facultativement, la requête HTTP comme deuxième argument. Une association nulle ou absente conserve l’accès par défaut. Un gate configuré doit exister et autoriser l’utilisateur ; un réglage invalide refuse l’action. Les règles Laravel habituelles pour les invités et Gate::before s’appliquent, mais la lecture seule globale prime même sur les exceptions administrateur. Aucun gate ne contourne les restrictions du namespace ou du runtime.

Déployez la configuration résolue de l’hôte et reconstruisez son cache avec php artisan config:cache ; changer seulement l’environnement ne met pas à jour les réglages en cache ou littéraux. Installez le paquet qualifié et publiez ses assets correspondants selon les étapes d’installation. Les écritures refusées renvoient HTTP 403 avec reason=waterline_action_forbidden ou reason=waterline_read_only et une capability. L’interface masque les commandes d’exécution indisponibles et explique les actions/commandes de planification désactivées ; le backend protège aussi les anciennes URL de mutation et celles ciblant une exécution précise.

Il s’agit de contrôles des utilisateurs de l’hôte embarqué. Le mode service conserve WATERLINE_ACCESS_MODE=read_only et les permissions du token upstream plutôt que les gates Laravel de l’hôte. Cette fonction ne change aucun minimum de dépendance SDK/Core et ne configure pas Cloud Managed Waterline.

Service Waterline​

L'image publiée contient son propre runtime PHP et Laravel. Elle ne nécessite ni PHP, ni Composer, ni paquet Workflow sur l'hôte du conteneur et ne se connecte jamais à la base de données du serveur autonome.

Cet exemple lie Waterline à l'interface de boucle locale sur le port hôte 8080, persiste son état d'interface dans un volume nommé et le connecte à un espace de noms serveur :

export WATERLINE_SERVER_ENDPOINT=https://workflow.example.com
export WATERLINE_SERVER_TOKEN=replace-with-a-server-token

docker run --detach \
  --name waterline \
  --restart unless-stopped \
  --publish 127.0.0.1:8080:8080 \
  --volume waterline-data:/data \
  --env WATERLINE_SERVER_ENDPOINT \
  --env WATERLINE_SERVER_TOKEN \
  --env WATERLINE_NAMESPACE=orders \
  --env WATERLINE_ACCESS_MODE=read_only \
  --env WATERLINE_ALLOW_UNAUTHENTICATED=true \
  --env APP_URL=https://waterline.example.com \
  durableworkflow/waterline:2.12.1

Ouvrez /waterline via l'URL représentée par APP_URL. L'image écoute sur le port conteneur 8080. Définissez PORT seulement pour changer délibérément ce port interne. WATERLINE_PATH modifie le préfixe d'URL waterline par défaut. Le dépôt publie aussi une définition de service Docker Compose avec la même frontière de connexion.

Le mode service a deux couches d'authentification indépendantes :

  1. WATERLINE_SERVER_TOKEN est le jeton porteur utilisé quand le SDK PHP appelle WATERLINE_SERVER_ENDPOINT. L'observation des workflows, workers, files et planifications nécessite un rôle opérateur serveur. La santé serveur et les métriques opérateur peuvent nécessiter un rôle administrateur.
  2. L'accès navigateur et API Waterline constitue la frontière d'entrée du déploiement. L'image autonome n'a pas d'annuaire d'utilisateurs Laravel hôte. WATERLINE_ALLOW_UNAUTHENTICATED=true ne convient donc que derrière un proxy inverse authentifiant ou sur une interface privée, comme la boucle locale ci-dessus. Gardez false tant que cette frontière d'authentification externe n'est pas en place.

Définissez WATERLINE_NAMESPACE sur l'espace de noms à inspecter. Waterline l'envoie à chaque requête SDK. La valeur par défaut WATERLINE_ACCESS_MODE=read_only bloque les mutations dans Waterline. Utilisez operator uniquement avec un jeton serveur autorisé pour les commandes requises.

Le volume /data contient les vues enregistrées, préférences d'affichage et l'état Laravel appartenant à Waterline. Par défaut, il contient une base SQLite sur fichier à /data/waterline.sqlite. Il ne contient jamais l'historique de workflows du serveur. Utilisez DATABASE_URL ou les paramètres DB_* habituels si l'état propre de Waterline doit être dans MySQL ou PostgreSQL.

Santé et métriques​

Ces sondes répondent à des questions différentes :

InterfaceCe qu'elle prouve
GET /upLe processus HTTP Waterline a démarré et peut répondre. Le contrôle de santé Docker de l'image utilise cette route.
GET /waterline/api/v2/healthWaterline peut assembler via le SDK PHP les preuves de santé serveur, d'enregistrement des workers et des files, dans l'espace de noms.
GET /waterline/api/statsLes totaux du tableau de bord et le résumé opérateur issus du serveur utilisés par Waterline.
GET /api/system/health et GET /api/system/operator-metrics sur le serveurLes contrats natifs de santé et d'exploitation du serveur, indépendants de Waterline.

Traitez /waterline/api/stats comme du JSON opérateur, pas comme un point de collecte Prometheus. Métriques SDK, journaux, traces et télémétrie applicative personnalisée viennent toujours des workers. Un /up sain avec une réponse Waterline de santé ou statistiques indisponible indique un problème de connexion serveur, d'autorisation, d'espace de noms ou de capacité SDK plutôt qu'un processus Waterline défaillant.

Visibilité des workflows et actions opérateur​

En mode service, listes, détail d'exécution, export d'historique, planifications, état des workers, preuves des files, signaux, mises à jour, requêtes de lecture, réparation, annulation, terminaison et archivage sont projetés depuis le serveur autonome configuré via le SDK PHP. Les formes des routes restent celles de la référence API opérateur Waterline. Les contrats serveur sous-jacents restent dans la référence API Server.

Waterline n'affiche que l'espace de noms configuré et les exécutions du serveur connecté. Les exécutions embarquées restent visibles dans leur Waterline embarqué, et celles gérées par Server dans le service ou ses interfaces natives. Changer le backend Waterline ne migre ni ne combine les exécutions.

Frontières de diagnostic​

SymptômeFrontière à vérifier
Le conteneur quitte avant de servir /upVérifiez WATERLINE_SERVER_ENDPOINT obligatoire, les droits d'écriture sur /data, la validité de PORT, les paramètres de base et les journaux bornés de migration au démarrage.
Une vue issue du serveur renvoie 401 ou 403Vérifiez WATERLINE_SERVER_TOKEN et son rôle serveur. Un refus à l'entrée Waterline relève séparément du proxy ou de WATERLINE_ALLOW_UNAUTHENTICATED.
Une route de mutation renvoie waterline_read_onlyGardez la lecture seule ou définissez explicitement WATERLINE_ACCESS_MODE=operator. Le jeton serveur doit toujours autoriser la commande.
Des workflows attendus sont absentsConfirmez WATERLINE_NAMESPACE, l'adresse serveur et le runtime qui a accepté le démarrage. Waterline ne recherche pas dans d'autres espaces de noms ou runtimes embarqués.
/up réussit mais la santé, les statistiques ou une vue signale une capacité indisponibleVérifiez directement le serveur avec son API ou sa CLI, puis les rôles du jeton et la méthode requise dans le tuple publié Waterline/SDK PHP.
Une route de catalogue de services signale backend_capability_unavailableLe mode service ne reproduit pas le catalogue de services interespaces de noms embarqué de Waterline. Utilisez les routes et l'API natives du serveur connecté pour cette capacité.
Une métrique personnalisée manque dans WaterlineInspectez l'exportateur du worker. Waterline expose les faits durables d'exploitation, pas les métriques arbitraires des processus.

Bandeau d’environnement​

Distinguez les onglets de production et hors production avec le bandeau Waterline. Ces variables fonctionnent en Laravel embarqué et en mode service autonome :

WATERLINE_ENV_NAME=production
WATERLINE_ENV_COLOR="#dc3545"

WATERLINE_ENV_COLOR sélectionne une palette fixe compatible avec la CSP :

Valeur acceptéeCouleur du bandeau
#0d6efd ou #2563ebBleu
#198754 ou #28a745Vert
#6f42c1 ou #7746ecViolet
#dc3545Rouge
#fd7e14Orange
#ffc107Jaune

Les autres valeurs donnent un gris neutre, y compris des couleurs hexadécimales valides comme #ff0000. Utilisez une valeur du tableau pour la couleur souhaitée.

En Laravel embarqué, les clés résolues env_name et env_color de config/waterline.php font autorité. La configuration publiée peut remplacer les valeurs issues de l’environnement. Après modification, reconstruisez le cache de configuration de l’application dans son déploiement habituel :

php artisan config:cache

Si le bandeau diffère de .env, inspectez la configuration résolue de Waterline : le cache reste effectif jusqu’à sa reconstruction. En mode service autonome, mettez à jour l’environnement du déploiement Waterline puis recréez ou redéployez son conteneur pour charger les valeurs. Ce sont des réglages d’affichage Waterline ; appliquez-les au service Waterline décrit plus haut.

Cloud Managed Waterline​

Les clients Cloud ouvrent Cloud Managed Waterline depuis l'interface opérateur gérée de leur espace de noms. Ils ne déploient ni ne configurent Waterline, Server, PHP ou des adresses internes et ne gèrent pas un second compte Waterline. Les instructions précédentes sur l'image auto-hébergée, les paramètres WATERLINE_*, le jeton Server, la base et l'authentification d'entrée ne s'appliquent pas à ce parcours.

L'authentification Cloud du client établit l'identité opérateur. Les autorisations de l'organisation, du projet, de l'environnement et de l'espace de noms Cloud déterminent le périmètre Managed Waterline accessible. Dans ce périmètre, les opérateurs disposent des listes et recherches, du détail et de l'historique durable, de la santé et des actions permises à leur rôle. L'interface reste limitée à l'espace de noms choisi, sans fusion de données d'autres environnements ou espaces de noms.

Les mutations sont contrôlées par rôle. Cloud attribue chaque mutation opérateur prise en charge à l'acteur Cloud authentifié dans ses données d'audit. La transition durable qui en résulte reste visible dans l'historique du workflow. Par exemple, un archivage réussi est attribué dans l'audit Cloud et enregistre l'événement durable WorkflowArchived. Les opérateurs n'ont jamais besoin d'un identifiant privé du runtime ni de connaître son déploiement interne pour utiliser cette interface.

API de liste et de détail​

Les listes Waterline (/waterline/api/flows/{bucket}) et le détail d'exécution (/waterline/api/flows/{id}) renvoient des contrats JSON typés, consommables directement par vos tableaux de bord ou scripts. La référence API opérateur Waterline documente les routes, les familles de champs de détail, l'export d'historique, les actions possibles, les planifications, les vues enregistrées, les préférences et le contrat des actions opérateur.

Contrat des actions possibles​

Waterline annote les lignes de liste, les réponses de détail et les exports d'historique avec un contrat versionné des actions possibles. Les consommateurs doivent utiliser actionability_contract.schema = waterline.actionability et actionability_contract.version = 1 pour identifier le contrat des champs suivants.

Le bloc actionability d'exécution indique si l'exécution choisie peut être réparée :

ChampSignification
repair_staterepairable, blocked, not_needed ou unknown.
repairableRaccourci booléen pour repair_state = repairable.
blocked_reasonCode de raison stable si repair_state = blocked.
status_bucketCatégorie Waterline qui a déterminé la décision pour l'exécution.
closed_reasonRaison durable de fermeture si l'exécution est fermée.
task_problemIndique si Waterline a vu un problème de tâche sur l'exécution.
diagnostic_only_evidenceVrai si au moins une ligne de preuve enfant est informative sans être une source de reprise.

Les preuves sous activities, waits, timers, exceptions, logs et les entrées de chronologie ou d'export peuvent aussi inclure leur bloc actionability :

ChampSignification
stateactionable si la ligne est une source de réparation valide, sinon diagnostic_only.
repair_sourceVrai uniquement pour les lignes appuyées par une source de référence réparable.
diagnostic_onlyVrai si la ligne ne doit pas servir de source de reprise.
history_authorityRéférence source telle que typed_history, mutable_open_fallback, failure_row_fallback ou unsupported_terminal_without_history.
history_unsupported_reasonCode de raison stable pour un historique de repli non pris en charge.

L'automatisation doit conditionner réparation, reprise et relecture à actionability.repair_state, actionability.repairable et actionability.repair_source sur chaque ligne. Une ligne avec diagnostic_only = true n'est jamais une source de reprise durable, même si elle contient des métadonnées d'échec ou de repli utiles. Les lignes avec history_authority = unsupported_terminal_without_history ne servent qu'au diagnostic : elles expliquent le blocage sans prouver un historique typé suffisant pour reconstruire la progression sans risque.

Actions du plan de contrôle depuis Waterline​

Les opérateurs peuvent annuler, terminer, réparer et archiver depuis le détail. Chaque action correspond à un POST sur le même identifiant d'exécution et renvoie 200 avec le nouvel état, ou 409 si l'état courant ne permet pas l'action.

En mode service, Waterline transmet les commandes prises en charge via le SDK PHP. Les mutations nécessitent à la fois WATERLINE_ACCESS_MODE=operator et un identifiant serveur autorisé pour la commande. L'API serveur et la CLI restent utilisables directement sans Waterline.

Dans Cloud Managed Waterline, chaque mutation prise en charge est contrôlée par le rôle Cloud et l'autorisation d'espace de noms. L'identité Cloud authentifiée fournit son attribution d'audit. Les clients ne configurent pas d'identifiant Waterline-vers-Server pour cette interface gérée.

Guides associés​

  • Les garanties d'exécution et l'idempotence expliquent le contrat de relecture, de nouvelles tentatives, d'expiration des baux et de résultats durables qui détermine les preuves opérateur.
  • Le périmètre d'exploitation opérateur relie santé, état des files, reconstruction, export, archivage et topologie dans un même contrat opérateur.
  • Les échecs et la reprise expliquent l'épuisement des tentatives, les échecs permanents, les délais et la réparation derrière les faits du tableau de bord.
  • Le développement assisté par IA identifie les contrats Waterline, CLI, MCP et lisibles par les LLM à utiliser pour diagnostiquer l'état d'un workflow.

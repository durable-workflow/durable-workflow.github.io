Index des capacités de Durable Workflow 2.0

Cet index couvre les capacités de la branche stable Durable Workflow 2.0.

Canal installable pris en charge​

Les identités exactes des artefacts relèvent des registres de paquets et des métadonnées de publication, pas de ce résumé des capacités.

InterfaceCanal pris en chargeRôle dans cet index
CLI2.0 stableClient opérateur et de diagnostic lisible par machine.
SDK PHP2.0 stableClient officiel durable-workflow/sdk en mode service et worker distant de workflows et d'activités pour le runtime d'un espace de noms Cloud ou un Server auto-hébergé.
Moteur Laravel embarqué2.0 stableMode de déploiement distinct durable-workflow/workflow dans l'application, avec son propre runtime d'écriture, moteur de persistance, files et relecture.
SDK Python2.0 stableSDK officiel de workflows et d'activités déterministes en mode service, avec client d'exploitation et du plan de contrôle pour un runtime Cloud ou un Server auto-hébergé. Nécessite Python 3.10 ou ultérieur.
SDK Rust2.0 stableSDK officiel de workflows et d'activités déterministes en mode service, service worker et client du plan de contrôle pour un runtime Cloud ou un Server auto-hébergé. Nécessite Rust 1.86 ou ultérieur.
Server2.0 stableRuntime auto-hébergé indépendant des langages, implémenté en PHP, pour les protocoles v2 du plan de contrôle et des workers.
Waterline2.0 stableCloud inclut Managed Waterline. Les opérateurs auto-hébergés déploient séparément l'image de service pour un espace de noms Server. Laravel embarqué installe le paquet Composer et lit l'état de l'application dans son processus.

PHP, Python et Rust sont les trois langages des SDK officiels en mode service. Chacun peut cibler le runtime d'un espace de noms Durable Workflow Cloud provisionné ou un Server auto-hébergé dont la découverte annonce la capacité publiée. Ils partagent des noms de type stables sous forme de chaînes, un même modèle durable de commandes et d'historique, la version 2 du plan de contrôle, la version majeure 1 du protocole worker et l'enveloppe publique des charges utiles. Rust est un SDK de workflows : il exécute du code de workflow déterministe, des activités et des services workers, au-delà des appels bruts au protocole. Python associe l'écriture de workflows à des clients d'exploitation des espaces de noms, planifications, workers, files, historiques, réparations et autres opérations.

Laravel embarqué reste un mode PHP distinct dans l'application. Il n'est pas requis pour les clients ou workers PHP en mode service. Le SDK PHP indépendant du framework est versionné séparément du moteur Laravel embarqué.

Utilisez les modes de déploiement pour choisir la frontière de responsabilité, puis consultez le runtime Cloud géré ou le Server auto-hébergé. Les preuves de capacités ci-dessous ne s'appliquent que si le runtime choisi annonce le contrat requis.

Les SDK PHP 2.3.2, Python 2.5.7 et Rust 3.5.0 utilisent par défaut le protocole worker 1.20. Les workers par défaut nécessitent un Server annonçant 1.20 ou une version mineure ultérieure de la majeure 1. Chaque SDK permet aussi de choisir explicitement 1.19 pour un Server compatible plus ancien. L'annulation coopérative exige 1.20 et son activation explicite. La découverte du runtime et les métadonnées publiées du SDK sélectionné déterminent la compatibilité. Consultez Compatibilité des versions et le protocole worker.

Capacités et versions minimales des SDK​

Le « mode service » signifie que Cloud ou un Server auto-hébergé possède le runtime distant. Le mode « embarqué » signifie qu'une application Laravel possède le runtime dans son processus. La colonne SDK consigne volontairement les différences. Un SDK absent ou limité n'est pas présumé offrir la parité.

CapacitéContrat 2.0 actuel et version minimale officiellePreuves 2.0 explicites
WorkflowsLes workers distants PHP, Python et Rust exécutent des workflows déterministes. L'écriture Laravel embarquée utilise le paquet Workflow.Écrire des workflows, SDK PHP, SDK Python, SDK Rust
Activités et servicesLe moteur embarqué et les trois SDK en mode service permettent d'écrire des activités. Les workflows et activités Rust s'exécutent dans des services workers officiels. Python et PHP exposent aussi des clients officiels de contrôle et de service.Activités, SDK PHP, Exécution des activités, Exécution externe
Appels de service entre espaces de nomsPHP embarqué, PHP SDK et Python SDK créent des opérations de service durables enregistrées avec attente de fin ou seulement d’admission et résultats enregistrés. L’espace cible en PHP service utilise actuellement l’option de tableau namespace. La création d’appels Rust reste indisponible jusqu’à sdk-rust #86.Création embarquée, Catalogue partagé et prise en charge des SDK
SignauxLes interfaces de workflow PHP, Python et Rust offrent une mutation durable asynchrone à leurs versions minimales actuelles.Signaux, SDK Python, SDK Rust
Requêtes de lectureLes requêtes de relecture en lecture seule sont prises en charge. PHP, Python et Rust exposent des gestionnaires et clients de requête. Les tâches de requête relues en Rust exigent le protocole worker 1.8 ou ultérieur.Requêtes de lecture, SDK Python, SDK Rust
Mises à jourPHP, Python et Rust exposent des clients et gestionnaires workers de mise à jour. Les validateurs déclarés en Python valident synchroniquement avant acceptation quand la découverte Server annonce ce contrat exact : l'acceptation suit l'approbation, tandis que rejet, perte de worker, dépassement de délai et achèvement bloqué par clôture de bail échouent explicitement. PHP et Rust ne permettent pas d'écrire des validateurs et n'en déclarent aucun.Mises à jour, SDK Python, SDK Rust
TemporisateursLes temporisateurs durables du runtime de service sont relus en PHP, Python et Rust.Temporisateurs, SDK Rust
Nouvelles tentativesLa politique durable de nouvelles tentatives d'activité est enregistrée avec la commande. PHP, Python et Rust exposent ces options à leurs versions minimales actuelles.Échecs et reprise, SDK Python, SDK Rust
DélaisLes runtimes Cloud et Server auto-hébergés appliquent les familles de délais des activités et workflows. Rust inclut les options d'activité et les échéances d'exécution et de lancement d'une exécution de workflow.Délais, SDK Rust
Workflows enfantsPHP, Python et Rust lancent et attendent des enfants durables. Leur identité de type interlangage est une chaîne stable et leurs charges utiles utilisent l'enveloppe partagée.Workflows enfants, SDK Python
Composition parallèle déterministePHP all()/parallel(), les listes imbriquées avec yield de Python et Rust WorkflowContext::parallel()/join() planifient des groupes d'activités, d'enfants, de temporisateurs, mixtes et imbriqués via des commandes ordinaires. Les trois publient les métadonnées partagées d'identité et de chemin de groupe et restaurent les résultats dans l'ordre des entrées imbriquées.Concurrence, SDK Python, SDK Rust
Sélection durable du premier achèvementPHP embarqué et les SDK de service PHP, Python et Rust lancent des membres indépendants : activité, workflow enfant, temporisateur, attente d'entrée externe et groupe imbriqué. Un gagnant est persisté avec une identité de membre stable. Les autres continuent et conservent leurs moyens d'attente et d'annulation.Concurrence, SDK Python, SDK Rust
Compensation sagaLes assistants Saga de PHP, Python WorkflowContext.saga() et Rust WorkflowContext::saga() enregistrent des compensations durables après la réussite de l'action et les exécutent par défaut séquentiellement dans l'ordre inverse. Python et Rust s'arrêtent au premier échec de compensation et conservent les échecs initial et de compensation. PHP expose aussi des politiques facultatives parallèles et de poursuite malgré les erreurs.Sagas, SDK Python, SDK Rust
AnnulationLaravel embarqué et les SDK de service PHP, Python et Rust prennent en charge les demandes d'annulation coopérative avec une identité racine unique, une échéance immuable et un nettoyage borné sur les workers explicitement activés. L'annulation terminale immédiate reste disponible avec protection de l'exécution sélectionnée et résultats typés.Annuler et terminer, Annulation en mode service, SDK Rust
TerminaisonLa terminaison ferme immédiatement une exécution avec un résultat terminal distinct. Elle est exposée par les runtimes Cloud et Server auto-hébergés, la CLI et les interfaces de contrôle PHP, Python et Rust.Annuler et terminer, API Server
Effets de bordPHP, Python et Rust enregistrent une valeur non déterministe exactement une fois, puis décodent la valeur enregistrée à la relecture.Effets de bord, SDK Python, SDK Rust
Workflow StreamsPHP, Python et Rust exposent des opérations typées de liste, description, abonnement/reprise par décalage, ajout, fermeture et erreur sur les flux de sortie appartenant au Server et limités à l'exécution. Les trois produisent des émissions sûres à la relecture à partir d'une identité de commande durable. Python résout les charges utiles externes via son pilote de stockage configuré. PHP et Rust conservent les références opaques.Workflow Streams, matrice SDK exacte, scénarios du runtime
Marqueurs de versionPHP, Python et Rust exposent des marqueurs durables pour faire évoluer le code de manière compatible.Versionnage, SDK Python, SDK Rust
Relecture déterministeLes workers PHP, Python et Rust reconstruisent les décisions à partir de l'historique durable et signalent le non-déterminisme avec un type précis au lieu de réexécuter le travail externe.Garanties d'exécution, Conformité de la plateforme, SDK Rust
PlanificationsLes runtimes Cloud et Server auto-hébergés possèdent les planifications durables. PHP, Python et la CLI exposent leurs opérations. Rust ne revendique pas d'API de gestion des planifications.Planifications, Référence CLI, SDK Python
Espaces de nomsLes runtimes en mode service sont limités par espace de noms. Les clients PHP/Python et la CLI les gèrent si le runtime choisi expose cette opération. Les workers et clients Rust ciblent un espace de noms, sans revendiquer son administration à la version minimale actuelle.Espace de noms, authentification et workers, API Server
Attributs de rechercheLes runtimes Cloud et Server auto-hébergés indexent des attributs typés. PHP et Python exposent des interfaces d'écriture et de contrôle. La CLI et les API opérateur exposent la découverte et le filtrage structurés.Attributs de recherche, SDK Python
Compatibilité des workersLes SDK enregistrent runtime, version SDK, identifiant de build, types pris en charge, version de protocole et capacité. Le serveur publie les versions acceptées et les faits de routage.Compatibilité, Compatibilité et routage des workers
Activités localesDisponibles dans Laravel embarqué, les SDK de service PHP et Python et le SDK Rust 3.1.0 avec activation explicite du worker.Exécution des activités embarquées, Matrice en mode service
Sessions workersDisponibles dans Laravel embarqué, les SDK de service PHP et Python et le SDK Rust 3.2.0 avec activation explicite du worker.Sessions workers, Matrice en mode service
Exécution avec affinitéDisponible dans Laravel embarqué et le SDK de service PHP. Python et Rust fournissent aussi des caches d’historique bornés facultatifs, activés explicitement sur le worker. Chaque worker doit conserver un comportement correct de relecture à froid.Exécution avec affinité, Matrice en mode service
Interopérabilité des codecsPHP, Python et Rust utilisent l'enveloppe publique codec + blob et un même schéma Avro Value récursif fixe. Les branches nommées préservent les distinctions entier/double, texte/octets, booléen/entier et liste/table de correspondance.Protocole Avro Value, Protocole worker, SDK Rust
DiagnosticsLes runtimes de service et la CLI publient en JSON les faits de version, protocole, workers, files, relecture, historique, échecs typés et réparation. Managed Waterline, le service auto-hébergé distinct ou le paquet embarqué présentent les preuves de leur runtime propriétaire.Supervision, Référence CLI, API opérateur Waterline
Outils pour agentsDécouvrir -> Modifier -> Exécuter -> Diagnostiquer -> Réparer est accessible via les manifestes publics, schémas, opérations HTTP, JSON CLI, clients SDK, historiques et diagnostics typés et mutations sûres. MCP est une interface facultative, pas la définition.Contrat des outils pour agents, Boucle opératoire des agents

Frontière d'interopérabilité des charges utiles​

Les appels interlangages de workflow et d'activité ne transmettent ni objets PHP sérialisés, ni pickles Python, ni types d'implémentation Rust. Ils transmettent des noms de type enregistrés sous forme de chaînes et une enveloppe publique. Avec avro, chaque SDK officiel utilise l'implémentation officielle du langage et le même schéma Value fixe. Tables de correspondance, listes, chaînes, octets, entiers, doubles, booléens et valeurs nulles décodés gardent leur type primitif. Une classe propre à un langage n'est reconstruite que dans son SDK.

Ce contrat couvre les entrées et résultats de workflow, enfants, entrées et résultats d'activité, signaux, requêtes de lecture, mises à jour et exécution externe. Les déploiements doivent toujours vérifier les codecs annoncés par GET /api/cluster/info avant d'admettre un worker.

Frontière de publication et de maturité​

Les contrats de plateforme indexés ici constituent l'interface stable du produit 2.0. Utilisez l'évaluateur pour agents IA pour décider rapidement si le produit convient.

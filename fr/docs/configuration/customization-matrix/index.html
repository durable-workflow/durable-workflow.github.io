Matrice de personnalisation

Cette page fixe le contrat de personnalisation pris en charge par Durable Workflow v2. Consultez-la pour déplacer les modèles durables v2 vers une autre connexion, remplacer des sous-classes de modèles ou le dépôt PHP d’observabilité destiné aux opérateurs, ou déterminer si un ancien réglage de sérialisation reste valide pendant la migration.

Matrice des personnalisations prises en charge​

Les relations héritées conservent le contrat de clé étrangère workflow_instance_id du package.

Clés exactes des modèles v2​

La configuration workflows.php publiée expose les clés de modèles durables suivantes sous workflows.v2 :

  • instance_model
  • run_model
  • history_event_model
  • task_model
  • command_model
  • link_model
  • activity_execution_model
  • activity_attempt_model
  • timer_model
  • failure_model
  • run_summary_model
  • run_wait_model
  • run_timeline_entry_model
  • run_timer_entry_model
  • run_lineage_entry_model
  • schedule_model
  • schedule_history_event_model

Utilisez des sous-classes des modèles du package pour ces clés. Conservez ses noms de colonnes et clés étrangères, sauf indication contraire dans cette documentation.

Règle de personnalisation du modèle d’instance​

La seule personnalisation v2 actuelle nécessitant un travail supplémentaire sur les relations est workflows.v2.instance_model lorsque votre sous-classe conduit à inférer une clé étrangère différente de workflow_instance_id.

Exemple courant sûr :

namespace App\Models\V2;

use Workflow\V2\Models\WorkflowInstance as BaseWorkflowInstance;

final class WorkflowInstance extends BaseWorkflowInstance
{
    protected $connection = 'workflow';
}

Le nom de base de la sous-classe étant toujours WorkflowInstance, Eloquent conserve la même clé étrangère inférée et les relations héritées restent cohérentes.

Si vous utilisez un autre nom de base ou un modèle de stockage qui change de table, redéfinissez explicitement les relations concernées :

namespace App\Workflow\Storage;

use Illuminate\Database\Eloquent\Relations\HasMany;
use Workflow\V2\Models\WorkflowCommand;
use Workflow\V2\Models\WorkflowInstance as BaseWorkflowInstance;
use Workflow\V2\Models\WorkflowRun;
use Workflow\V2\Models\WorkflowUpdate;
use Workflow\V2\Support\ConfiguredV2Models;

final class TenantWorkflowInstance extends BaseWorkflowInstance
{
    protected $table = 'tenant_workflow_instances';

    public function runs(): HasMany
    {
        return $this->hasMany(
            ConfiguredV2Models::resolve('run_model', WorkflowRun::class),
            'workflow_instance_id',
        );
    }

    public function commands(): HasMany
    {
        return $this->hasMany(
            ConfiguredV2Models::resolve('command_model', WorkflowCommand::class),
            'workflow_instance_id',
        )->oldest('created_at');
    }

    public function updates(): HasMany
    {
        return $this->hasMany(
            ConfiguredV2Models::resolve('update_model', WorkflowUpdate::class),
            'workflow_instance_id',
        )
            ->orderBy('command_sequence')
            ->oldest('accepted_at')
            ->oldest('created_at')
            ->oldest('id');
    }
}

Si ces redéfinitions manquent, le package échoue désormais immédiatement au démarrage au lieu de laisser l’application utiliser des clés inférées comme tenant_workflow_instance_id ou custom_workflow_instance_id.

Règles de sérialisation, d’import et de santé​

  • Conservez serializer = 'avro' pour les nouveaux traitements v2.
  • Utilisez les anciens codecs uniquement pour terminer ou importer un historique v1 qui nécessite encore un décodage des données natif PHP.
  • Ne configurez pas v2 avec des classes de sérialisation personnalisées v1 supprimées.
  • Exécutez php artisan workflow:v2:doctor après une mise à niveau ou un changement de configuration. Ce diagnostic signale les anciens réglages de sérialisation et les autres problèmes de préparation au démarrage.
  • Considérez la santé et les statistiques Waterline v2 comme la vue opérateur de cette même configuration de modèles durables.

Règles de migration et d’écriture​

  • Le fonctionnement normal utilise les migrations du package chargées automatiquement sur la connexion par défaut.
  • Si vos modèles durables utilisent une autre connexion, publiez les migrations et définissez leur $connection pour que php artisan migrate cible la même base de données que les sous-classes de modèles configurées.
  • Conservez les noms de tables, clés primaires et clés étrangères du package sur chaque modèle participant au chemin d’écriture du runtime.
  • Cette personnalisation ne se limite pas aux lectures : les démarrages, chargements, résolutions de l’exécution courante et exécutions de tâches utilisent tous les modèles durables configurés.

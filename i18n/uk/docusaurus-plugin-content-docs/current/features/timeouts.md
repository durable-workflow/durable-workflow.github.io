# Тайм-аути {#timeouts}

Тайм-аути рівня workflow обмежують допустиму тривалість його виконання. Є два рівні обмеження:

- **Тайм-аут виконання** — обмежує загальний календарний час усіх запусків екземпляра workflow, включно з переходами continue-as-new. Кінцевий термін обчислюється один раз під час старту й переноситься без змін.
- **Тайм-аут запуску** — обмежує окремий запуск. Кінцевий термін перераховується на початку кожного нового запуску, зокрема після continue-as-new.

Обидва тайм-аути необов’язкові й можуть застосовуватися разом.

## Налаштування {#configuration}

Тайм-аути налаштовуються через `StartOptions` під час запуску workflow:

```php
use Workflow\V2\StartOptions;
use Workflow\V2\WorkflowStub;

$workflow = WorkflowStub::make(MyWorkflow::class, 'order-123');

$workflow->start(
    $orderId,
    StartOptions::rejectDuplicate()
        ->withExecutionTimeout(7200)   // 2 hours across all runs
        ->withRunTimeout(3600),        // 1 hour per run
);
```

### Тайм-аут виконання {#execution-timeout}

Тайм-аут виконання охоплює весь екземпляр workflow. Якщо workflow використовує continue-as-new, кінцевий термін залишається однаковим для всіх запусків у ланцюжку.

```php
StartOptions::rejectDuplicate()->withExecutionTimeout(86400); // 24 hours
```

Значення тайм-ауту зберігається в моделі `WorkflowInstance`, а обчислений кінцевий термін фіксується в кожному `WorkflowRun`.

### Тайм-аут запуску {#run-timeout}

Тайм-аут запуску діє на один запуск. Після continue-as-new новий запуск отримує новий кінцевий термін: поточний час плюс налаштований тайм-аут запуску.

```php
StartOptions::rejectDuplicate()->withRunTimeout(1800); // 30 minutes per run
```

### Перевірка значень {#validation}

Значення тайм-ауту має становити щонайменше 1 секунду. Нульове або від’ємне значення спричиняє `LogicException`:

```php
// Throws LogicException: "Workflow v2 execution timeout must be at least 1 second."
StartOptions::rejectDuplicate()->withExecutionTimeout(0);
```

### Площина керування {#control-plane}

Тайм-аути також можна задати під час запуску workflow через площину керування:

```php
$controlPlane->start('my-app.order-workflow', 'order-123', [
    'execution_timeout_seconds' => 7200,
    'run_timeout_seconds' => 3600,
]);
```

Відповідь `describe` містить поля тайм-аутів і кінцевих термінів:

```php
$description = $controlPlane->describe('order-123');

$description['execution_timeout_seconds']; // 7200
$description['run']['run_timeout_seconds']; // 3600
$description['run']['execution_deadline_at']; // ISO 8601 timestamp
$description['run']['run_deadline_at'];       // ISO 8601 timestamp
```

### Waterline {#waterline}

Якщо тайм-аути налаштовано, детальний перегляд запуску у Waterline показує їхню тривалість та обчислені кінцеві терміни.

### Історія {#history}

Дані події історії `WorkflowStarted` містять поля тайм-аутів і кінцевих термінів, якщо їх налаштовано:

```json
{
    "execution_timeout_seconds": 7200,
    "run_timeout_seconds": 3600,
    "execution_deadline_at": "2026-04-12T14:00:00+00:00",
    "run_deadline_at": "2026-04-12T13:00:00+00:00"
}
```

### Continue-as-new {#continue-as-new}

Під час continue-as-new:

- **Кінцевий термін виконання** переноситься з попереднього запуску без змін.
- Значення **тайм-ауту запуску** переноситься, але **кінцевий термін запуску** перераховується від поточного часу.

Отже, тайм-аут виконання завжди відлічується від початкового старту, а кожен новий запуск отримує власне нове часове вікно.

## Застосування тайм-аутів {#enforcement}

Тайм-аути рівня workflow перевіряються у двох місцях:

1. **На початку завдання workflow** — кожне завдання workflow перевіряє `deadlineExpired()` перед виконанням workflow. Якщо кінцевий термін минув, запуск одразу завершується через тайм-аут.
2. **Через TaskWatchdog** — watchdog шукає незавершені запуски, у яких минув кінцевий термін виконання або запуску, але немає відкритого завдання workflow. Для такого запуску він створює й відправляє завдання workflow про прострочений термін. Тайм-аут застосовується під час наступного виконання завдання.

Коли спрацьовує тайм-аут, рушій:

- Скасовує всі відкриті завдання (activity, timer, workflow), крім поточного
- Скасовує всі відкриті виконання activity, записуючи події історії `ActivityCancelled`
- Скасовує всі очікувані timer, записуючи події історії `TimerCancelled`
- Записує `WorkflowFailure` із `failure_category = timeout` та `WorkflowTimeoutException`
- Записує термінальну подію історії `WorkflowTimedOut`, де `timeout_kind` має значення `execution_timeout` або `run_timeout`
- Застосовує політику закриття батьківського workflow до всіх відкритих дочірніх workflow
- Сповіщає батьківські workflow, якщо це був дочірній запуск

Запис помилки містить клас винятку `Workflow\V2\Exceptions\WorkflowTimeoutException`, а також `timeout_kind` і часову мітку кінцевого терміну для програмної перевірки.

### Результат тайм-ауту й очищення {#timeout-outcome-and-cleanup}

За типової політики жорсткого тайм-ауту: Кінцевий термін workflow закриває запуск зі станом `failed` та
`closed_reason = timed_out`. Термінальна подія історії — `WorkflowTimedOut`.
Рушій записує `WorkflowTimeoutException` у дані помилки. Він **не** передає цей
виняток у тіло workflow й не відновлює його код для очищення. Блоки `catch` і
`finally` та зареєстровані компенсації saga не виконуються, коли рушій застосовує
цей кінцевий термін.

Скасування стійкого виконання activity не скасовує зовнішній побічний ефект і
не доводить, що її callback зупинився. Використовуйте ідемпотентні операції та
звіряння стану на рівні застосунку для ефектів, які вже могли відбутися.

Якщо після прикладного кінцевого терміну потрібне очищення, використовуйте
коротший стійкий timer або очікування з тайм-аутом, щоб код workflow міг виконати
[компенсацію перед закриттям](./sagas.md#deadline-driven-compensation).
Залишайте час на повторні спроби activity, планування worker і очищення до
кінцевого терміну запуску або виконання. Тайм-аут рушія залишається останнім
обмеженням. Через затримку worker цей термін може настати раніше, ніж
завершиться компенсація.

Негайні команди `cancel()` і `terminate()` також закривають запуск без вікна
для очищення кодом workflow. Окрема операція `requestCancellation()` може
передати обмежене очищення сумісному worker, поки запуск ще активний.
Тайм-аут workflow не перетворюється на такий запит автоматично, а cancellation
shield не подовжує кінцевий термін виконання чи запуску. Дивіться
[Скасування та припинення](./cancel-and-terminate.md) і
[Cooperative Cancellation](../polyglot/cancellation.md).

## Експериментальне очищення за кінцевим терміном {#timeout-cleanup}

**Експериментально.** Вбудовані воркери черги підтримують цю опцію з Workflow 2.29.0; вбудовані запуски в режимі poll її відхиляють. Режим сервісу підтримує її з нативного Server 3.30.0 із сумісними воркерами, як описано нижче. Опція є поверхнею `experimental` за [рівнями стабільності](../compatibility.md#stability-levels) і поки не має гарантії зворотної сумісності. Запуски без цієї опції зберігають описаний вище типовий жорсткий тайм-аут.

Перед увімкненням у вбудованому режимі установіть Workflow 2.29.0 або новішу версію, виконайте міграції застосунку та розгорніть сумісні вбудовані воркери черги. Нова міграція додає `workflow_runs.timeout_cleanup_work_deadline_at`; вона не вмикає опцію для наявних запусків. Не вмикайте її до завершення міграції.

```bash
php artisan migrate
```

Під час старту зарезервуйте скінченну частину наявного жорсткого тайм-ауту:

```php
use Workflow\V2\StartOptions;
use Workflow\V2\WorkflowStub;

WorkflowStub::make(MyWorkflow::class, 'order-123')->start(
    $orderId,
    StartOptions::rejectDuplicate()
        ->withExecutionTimeout(70)
        ->withTimeoutCleanup(10),
);
```

Викликайте `withTimeoutCleanup()` після `withExecutionTimeout()` або `withRunTimeout()`; виклик до них кидає виняток, бо жорсткий тайм-аут ще не задано. `timeoutCleanupSeconds:` — альтернатива конструктора. Резерв має бути 1–86400 секунд, потребує тайм-ауту виконання або запуску й мусить бути меншим за кожний налаштований жорсткий тайм-аут. `null` зберігає типову політику.

У прикладі звичайна робота має 60 секунд, а очищення може використати останні 10 усередині початкової жорсткої межі 70 секунд. Резерв ніколи не додає часу після цієї межі. Якщо діють обидва жорсткі терміни, очищення обмежує раніший. Пізнє виявлення, повтори, заміна воркера та поновлення lease не пересувають терміни. Continue-as-new і redrive зберігають прийнятий резерв та початкові годинники виконання; кожний запуск виводить власні годинники.

Коли воркер помічає робочий термін, запуск один раз переходить до очищення та записує `WorkflowTimeoutCleanupStarted`. Якщо жоден воркер не помітить його до жорсткого терміну, ця подія не записується, а результат `expired` не має `started_at`. Сумісний код отримує `WorkflowTimeoutCleanupRequested`, підтип `WorkflowCancellationRequestedException` із `cause: timeout`. Обробіть переривання для зареєстрованих компенсацій saga чи захищеного очищення; `compensate()` використовує свій щит скасування. Щит не подовжує жорстку межу. Дивіться [Sagas](./sagas.md#deadline-driven-compensation).

Очищення має окремий `timeout_cleanup.outcome`:

| Результат | Значення |
|---|---|
| `completed` | Очищення повернулося або повторно кинуло переривання тайм-ауту до свого терміну. Повернене значення не стає бізнес-результатом. |
| `failed` | Очищення кинуло інший виняток; `failure_id` посилається на збій очищення. |
| `expired` | Жорстка межа настала до завершення, зокрема якщо жоден воркер не міг виконати очищення. |
| `preempted` | Негайний `cancel()` або `terminate()` перервав очищення; відповідний результат скасування/припинення залишається термінальним. |

Завершене, невдале чи прострочене очищення все одно має бізнес-статус `failed`, `closed_reason = timed_out` і `WorkflowTimedOut`. Успішна компенсація не перетворює тайм-аут на успішний workflow. Якщо очищення завершується раніше, запуск закривається одразу, але повідомлення про тайм-аут усе одно вказує час початкового жорсткого терміну.

Читайте результат очищення з історії. Payload `timeout_cleanup` у термінальній події `WorkflowTimedOut`, `WorkflowTerminated` або `WorkflowCancelled`, який також є у виводі `php artisan workflow:v2:history-export`, є авторитетним записом. Починаючи з Workflow 2.40.0, а також у нативному Server 3.30.0 і новіших, describe повідомляє записаний стан у `run.timeout_cleanup`, а деталі запуску та обмежене спостереження запуску, яке читає Waterline, повідомляють його як `timeout_cleanup` верхнього рівня. Поки очищення відкрите, поле показує `outcome: running` з `cause: timeout`, вид тайм-ауту, час виявлення та робочий і кінцевий терміни очищення. Після закриття воно показує термінальний результат, для `failed` — з `failure_id`. Якщо очищення не записано, поле відсутнє.

Недоступні чи затримані воркери не гарантують зовнішнього ефекту очищення; робіть компенсації ідемпотентними та звіряйте невизначені ефекти в застосунку.

У вбудованому режимі bridge-воркери не можуть отримати запуск, що увімкнув опцію; claim повертає `timeout_cleanup_not_supported`, не забираючи lease.

**Режим сервісу.** Нативний Server 3.30.0 і новіші приймають `timeout_cleanup_seconds` у сервісних запусках і командах `start_child_workflow` з тими самими обмеженнями, що й для вбудованого резерву, та оголошують `timeout_cleanup: {supported: true, version: 1}`. Server допускає запуск з опцією, лише коли активний воркер у черзі завдань оголошує цю можливість. Інакше він відповідає `422 timeout_cleanup_not_supported`, нічого не записує і ніколи не переходить на простий жорсткий тайм-аут. Воркери з увімкненим кооперативним скасуванням оголошують можливість починаючи з PHP SDK 3.31.0 (3.32.0 для суворішого правила маркера нижче), Python SDK 2.24.0 і Rust SDK 4.25.0. Код workflow отримує переривання кооперативного скасування свого SDK з `cause: timeout`. Див. [Cooperative Cancellation](../polyglot/cancellation.md).

Для авторів SDK: сервісний воркер повідомляє неперехоплене або повторно кинуте переривання очищення через `fail_workflow.failure.interruption: "timeout_cleanup"`, і лише для переривання, яке він доставив для кореневого запиту тайм-ауту запуску (без батьківського запиту та без scope). Усе інше, зокрема переривання, створене застосунком або обгорнуте, записує `failed`. Server приймає маркер лише поки активний запит тайм-ауту, що належить рушію, і лише від claim, який узгодив `timeout_cleanup`. Workflow 2.42.0 формулює це правило в [портативному контракті](https://github.com/durable-workflow/workflow/blob/main/docs/architecture/timeout-cleanup.md).

**Змішані черги.** Admission перевіряє лише те, що принаймні один активний воркер у черзі завдань оголошує `timeout_cleanup`; будь-який воркер черги може отримати хід очищення. Server відхиляє маркер від воркера, який не оголосив можливість, тож переривання, що там вийшло назовні, записується як `failed` або `expired`. Але такий воркер може взагалі не доставити переривання: якщо його код workflow повертає значення, запуск записує очищення як `completed`, хоча жодного очищення не було. Перш ніж запускати workflow з опцією в черзі, оновіть усі її воркери до сумісного SDK з увімкненим кооперативним скасуванням.

## Lease для workflow task {#workflow-task-lease}

Workflow task — це один цикл роботи worker, який відтворює зафіксовану історію та створює довговічні команди. Це не весь workflow. Очікування довговічного timer, activity у черзі або signal не утримує одну workflow task протягом усього очікування. Пізніша task відновлює запуск.

| Розгортання | Типово, секунд | Налаштування |
| --- | --- | --- |
| Вбудований Laravel | `300` | `DW_V2_WORKFLOW_TASK_LEASE_SECONDS` |
| Server | `60` | `DW_WORKFLOW_TASK_TIMEOUT` |

Вбудоване налаштування відповідає `workflows.v2.workflow_task_lease_seconds`. Під час старту Server відображає власне налаштування на цей ключ пакета, тому на Server використовуйте налаштування Server. Це конфігурація runtime, а не параметр `StartOptions` чи таймаут activity для окремого запуску. Дивіться [Публікація конфігурації](../configuration/publishing-config.md#workflow-task-lease-v2) та [довідник конфігурації Server](../polyglot/server-config-reference.md#worker-protocol-and-query-transport).

### Heartbeat і виконання {#workflow-task-heartbeats}

Worker у сервісному режимі використовують heartbeat task, щоб поновити володіння поточною workflow task. Server перевіряє task, спробу та власника lease. Підтверджене поновлення використовує чинну тривалість lease з урахуванням застосовних меж очищення під час скасування. Воно не змінює початкових дедлайнів запуску й усього виконання або таймаутів activity. Heartbeat реєстрації підтримує її актуальність. Застаріла реєстрація може позбавити повноважень на поточну task на Server ще до спливу її lease. Такий heartbeat не поновлює lease цієї task. Heartbeat activity у черзі повідомляє її прогрес і не замінює поновлення workflow task.

Синхронний код вбудованого workflow не може періодично поновлювати lease, поки він заблокований. Код workflow має бути детермінованим і коротким. Тривалу роботу з введенням-виведенням або CPU виконуйте в activity. Lease не є жорстким обмеженням часу процесу чи CPU.

Вбудовані локальні activity утримують workflow task, у якій виконуються. Їхній `$this->heartbeat()` також може поновлювати її lease, доки початкова спроба activity і володіння workflow task залишаються чинними.

### Завершення lease {#workflow-task-lease-expiry}

Незавершене володіння зі спливлим lease стає придатним для відновлення. Matching/watchdog або repair очищає прострочене володіння й повторно надсилає роботу, щоб сумісний worker відтворив зафіксовану історію. Для цього потрібні активні процеси відновлення, доступна база даних і придатний worker. Сплив lease не завершує старий процес і не гарантує миттєвої повторної доставки. На Server прострочене або замінене володіння не може надсилати нові команди. Відхилене поновлення слід трактувати як втрату повноважень.

Repair не відкриває закритий запуск, не надає додаткових бізнес-спроб і не скидає початкові дедлайни. Натомість `startToCloseTimeout` обмежує одну спробу activity відповідно до записаної політики повторень. Таймаути запуску й усього виконання обмежують життя workflow. Поновлення або replay workflow task їх не подовжує.

## Тайм-аути activity {#activity-timeouts}

Тайм-аути activity обмежують допустиму тривалість окремих виконань activity. Є чотири типи тайм-аутів:

- **Schedule-to-start** — обмежує час від планування до першого отримання завдання worker. Діє, поки activity має стан `Pending`.
- **Start-to-close** — обмежує час від отримання activity worker до її завершення. Починається заново для кожної повторної спроби.
- **Schedule-to-close** — обмежує загальний календарний час від планування до завершення для всіх повторних спроб. Цей тайм-аут завжди термінальний: повторна спроба не допоможе, оскільки загальний кінцевий термін уже минув.
- **Heartbeat** — обмежує час між heartbeat. Для тривалих activity, які викликають `$this->heartbeat()`, рушій вимагає heartbeat протягом налаштованого інтервалу. Інакше activity вважається такою, що не відповідає.

Усі тайм-аути необов’язкові й можуть застосовуватися разом. Налаштовуйте їх через `ActivityOptions` під час виклику activity:

```php
use function Workflow\V2\activity;
use Workflow\V2\Support\ActivityOptions;

$result = activity(
    LongRunningActivity::class,
    new ActivityOptions(
        scheduleToStartTimeout: 30,     // must be claimed within 30s
        startToCloseTimeout: 300,       // each attempt has 5 minutes
        scheduleToCloseTimeout: 600,    // total 10 minutes across all retries
        heartbeatTimeout: 15,           // heartbeat well before this 15-second window expires
        maxAttempts: 3,
    ),
    $input,
);
```

У сервісному режимі PHP SDK 3.9.0 і новіші приймають для тайм-аутів activity, а також для тайм-аутів виконання й запуску дочірнього workflow, крім секунд, рядок на кшталт `'5 minutes'` або `DateInterval` чи `CarbonInterval`. Ці тайм-аути мають становити щонайменше одну секунду. Див. [тривалості PHP SDK](../polyglot/php.md#durations).

У сервісному режимі закриття спроби activity не зупиняє примусово прикладний код SDK. Python SDK 2.9.0 повідомляє відмову під час наступного heartbeat; код без heartbeat може працювати до повернення, а фізичний слот потоку зайнятий до завершення. Див. [відмови heartbeat і завершення callback у Python](../polyglot/python.md#heartbeat-refusals-and-callback-exit).

### Тайм-аут schedule-to-start {#schedule-to-start-timeout}

Кінцевий термін обчислюється під час планування activity. Якщо до цього терміну жоден worker не отримає activity, `TaskWatchdog` застосовує тайм-аут. Якщо повторні спроби ще доступні, нове завдання activity планується із зафіксованою затримкою, а кінцевий термін schedule-to-start перераховується від моменту доступності повторної спроби. Кожна спроба отримує нове часове вікно. Якщо `scheduleToStartTimeout` не налаштовано, під час повторної спроби кінцевий термін очищається. Коли всі спроби вичерпано, записується термінальна подія історії `ActivityTimedOut` і workflow пробуджується.

### Тайм-аут start-to-close {#start-to-close-timeout}

Кінцевий термін обчислюється, коли worker отримує завдання activity. Кожна повторна спроба отримує новий кінцевий термін start-to-close. Якщо activity не завершиться вчасно, поточна спроба закривається. За наявності повторних спроб виконання повертається до стану `Pending` з новим кінцевим терміном schedule-to-start, якщо його налаштовано. Це запобігає негайному повторному тайм-ауту завдання. Якщо всі спроби вичерпано, записується термінальний тайм-аут.

### Тайм-аут schedule-to-close {#schedule-to-close-timeout}

Кінцевий термін обчислюється один раз під час планування й ніколи не починається заново. Коли він спливає, activity одразу завершується термінальною помилкою, навіть якщо повторні спроби ще доступні, адже загальний допустимий календарний час минув. Це обмежує загальну вартість нестабільної activity, яка інакше могла б повторюватися нескінченно в межах тайм-аутів окремих спроб.

### Тайм-аут heartbeat {#heartbeat-timeout}

Для activity у черзі перший кінцевий термін починається, коли runtime отримує її завдання, ще до доставлення завдання та виконання користувацького коду. Кожен прийнятий heartbeat встановлює термін як свій записаний runtime час плюс налаштований тайм-аут. Він не додає часу до попереднього терміну й не відкриває нового вікна, коли клієнт отримує відповідь. Залишайте запас для доставлення, обмеженого обсягу роботи, пауз виконання, затримки запитів і транспортних повторів. Надсилайте heartbeat задовго до завершення вікна. Прострочена або замінена спроба не відновлює повноваження пізнім heartbeat. Якщо повторні спроби залишилися, планується нова з поновленим терміном schedule-to-start, якщо його налаштовано. Інакше записується термінальний тайм-аут.

Зсув дедлайну не додає історії. Heartbeat записує подію `ActivityHeartbeatRecorded` лише тоді, коли його прогрес змінився, і не частіше одного разу за інтервал запису, тож heartbeat можна надсилати так часто, як потребує цей тайм-аут. Див. [Heartbeats](./heartbeats.md).

```php
use Workflow\V2\Activity;

class LongRunningActivity extends Activity
{
    public function handle($input)
    {
        foreach ($items as $item) {
            $this->heartbeat(['processed' => $count]);
            // ... process item ...
        }
    }
}
```

### Застосування тайм-аутів {#enforcement-1}

`TaskWatchdog` застосовує тайм-аути activity під час кожного проходу циклу worker. Він шукає виконання з простроченими значеннями у стовпцях кінцевих термінів і передає їх `ActivityTimeoutEnforcer`. Кожне застосування записує:

- Термінальну подію історії `ActivityTimedOut`, де `timeout_kind` має значення `schedule_to_start`, `start_to_close`, `schedule_to_close` або `heartbeat`
- Запис `WorkflowFailure` із `failure_category = timeout` та `propagation_kind = timeout`
- Завдання відновлення workflow, яке пробуджує батьківський workflow, щоб він міг отримати помилку

У детальному перегляді activity Waterline показує політику повторних спроб із усіма налаштованими типами тайм-аутів. Хронологія показує тип тайм-ауту в повідомленні події про тайм-аут activity.

# Самостійне розгортання {#self-hosting-deployments}

Для переходів між власними або Cloud-середовищами див. [перехід між середовищами виконання](/docs/polyglot/runtime-migration/). Наявні запуски залишаються у джерелі, поки нові старти переносяться.

Durable Workflow v2 підтримує кілька варіантів самостійного розгортання.
Оберіть найпростіший, що відповідає вашому середовищу, і явно визначте образ,
базу даних, кеш, автентифікацію, готовність до роботи та контракт оновлення.

Цей посібник описує окремий дистрибутив Server. Якщо пакет Laravel вбудовано
у ваш застосунок, використовуйте сторінки встановлення та налаштування пакета.
Durable Workflow Cloud — окремий керований сервіс: Cloud обслуговує середовище
виконання, зберігання, розміщення та відновлення. Власний Server ніколи не
підключається до Cloud. Дивіться [кероване середовище Cloud](/docs/polyglot/cloud-control-plane).
Поточний контракт Cloud охоплює кероване виконання та відновлення в одному
регіоні. Він не обіцяє міжрегіональної реплікації, автоматичного перемикання
регіонів після відмови або повернення до початкового регіону.

Дистрибутив Server для самостійного розгортання не містить і не обслуговує
Waterline. Розгортайте Waterline окремо, коли потрібен його операторський
інтерфейс, і підключайте його до простору імен Server за
[посібником розгортання та моніторингу Waterline](/docs/monitoring/#waterline-service).
Cloud натомість містить Managed Waterline для свого керованого простору імен.

Поточний Server — нативний Server 3.x (`%%artifact.serverDockerHubImage%%`).
Він працює як один процес на вузол: під час запуску сам створює й перевіряє
схему бази, обробляє спрацювання таймерів і розкладів та виконує проходи
обслуговування, тому Job початкового налаштування, worker черги, планувальник
і Redis не потрібні. PHP Server 2.x заморожено на версії 2.11.8, і нових
випусків він не отримуватиме.

:::note Наявні встановлення PHP Server 2.x

PHP Server 2.11.8 виведено з підтримки й не виправлено щодо листопадових рекомендацій Laravel. Для встановлень PHP із зафіксованою версією виконайте [дії щодо умовної експозиції, ingress і підписаних посилань](./polyglot/server.md#retired-php-server-security), перш ніж використовувати старі рецепти нижче.

Стек PHP 2.x (server, worker черги, планувальник, Job початкового налаштування
та Redis) залишається доступним. У тегу випуску 2.11.8 це
[`docker-compose.published.yml`](https://github.com/durable-workflow/server/blob/2.11.8/docker-compose.published.yml);
починаючи з 3.0.0 репозиторій Server зберігає той самий стек як
[`docker-compose.php.yml`](https://github.com/durable-workflow/server/blob/main/docker-compose.php.yml).
Наявні встановлення PHP 2.x можна перевести на нативний Server за допомогою
`upgrade-takeover` за
[runbook переходу на нативний Server](%%artifact.serverTakeoverRunbookUrl%%).
Перехід кваліфіковано на опублікованому образі 3.0.4 (arm64) для баз, записаних
PHP 2.11.8 на SQLite, MySQL 8.0 і PostgreSQL 17. MariaDB, amd64 і бази з інших
випусків PHP (схеми 2.8.0–2.11.8) мають лише покриття CI на збірках із
вихідного коду. Перехід односторонній, вимагає попередньої резервної копії, а
PHP має бути зупинено. Він відхиляє бази та стан, які не може перенести;
[таблиці відмов](%%artifact.serverTakeoverRunbookUrl%%#refusals)
у runbook перелічують кожен випадок. Спершу відпрацюйте його на копії,
відновленій із вашої резервної копії. Після переходу повернутися до PHP
неможливо, а сам перехід планується позначити як застарілий у лінійці 3.1.x.
Розділи нижче, де згадано Redis, worker черги, планувальник або початкове
налаштування, описують топологію PHP 2.x.

:::

Не керуйте ним самостійно: Cloud керує середовищем виконання, збереженням
стану, розміщенням і відновленням керованого namespace, а ваші PHP-, Python-
або Rust-workers підключаються з обліковими даними для кожної ролі.

Публічний дистрибутив навмисно оптимізовано для локальної розробки,
одновузлового виробничого середовища та невеликих кластерів. Маніфести
Kubernetes надано командам, які вже обслуговують Kubernetes. Матеріали щодо
кількох регіонів з активним і резервним регіонами є оцінювальним посібником за
участю підтримки, а не доведеним самостійним контрактом 2.0. Дивіться
[активний і резервний регіони](#activepassive-multi-region) нижче.

Висока доступність в одному регіоні — перемикання керованої бази чи Redis,
втрата вузла API чи worker, перезапуск процесу планувальника — наразі потребує
участі підтримки, доки перевірка точного випуску не пройдена. Дивіться
[високу доступність і перемикання в одному регіоні](#single-region-high-availability-and-failover).
Для власного Server кілька активних регіонів, автоматичне регіональне
перемикання, дублікати планувальника як стала топологія та перевірка керованого
Kubernetes конкретного провайдера залишаються шляхами за участю підтримки:
вони залежать від ваших бази, кешу, мережі, безпеки, процесів і оновлень.
Опублікований чарт Helm є самостійним шляхом пакування в тих самих межах
відповідальності оператора. Cloud наразі надає керовану роботу й відновлення
в одному регіоні, без міжрегіональної реплікації чи регіонального перемикання.
Дивіться [кероване середовище Cloud](/docs/polyglot/cloud-control-plane) та
[межу підтримки](/docs/support) щодо комерційної моделі.

## Матеріали виробничого відновлення {#production-recovery-deliverables}

Назвати топологію «готовою до виробничої роботи» означає опублікувати її
комплект відновлення, а не лише запустити контейнери. Зберігайте актуальні
підтвердження в тому самому операційному посібнику, що й команди розгортання:

| Шлях | Мінімальний опублікований комплект відновлення |
| --- | --- |
| Одновузлове виробниче середовище | Розклад резервування, закріплений образ або дайджест, місце знімка середовища й конфігурації, максимальне прийнятне відставання відновлених даних, час останньої успішної репетиції відновлення та підтвердження перевірки |
| Невеликий кластер | Одновузловий комплект, очікуваний вплив втрати одного вузла API, worker, процесу планувальника й обслуговування, Redis або спільної бази; кроки повторної реєстрації worker після відновлення; задокументований поступовий чи повністю зупинений режим оновлення поточного випуску |
| Чарт Helm для Kubernetes | Кластерний комплект, версія чарта, редакція значень, дайджест образу, відповідальні за вхід до кластера й секрети, остання репетиція оновлення та відкату чарта |
| Маніфести Kubernetes без обгортки | Кластерний комплект і відповідальні за сховище, секрети, вхід до кластера й розгортання, які потрібно відновити чи повторно застосувати перед визнанням трафіку справним |
| Оцінювання високої доступності в одному регіоні за участю підтримки до проходження перевірки випуску | Кластерний комплект або комплект маніфестів, підтвердження репетицій перемикання керованої бази й Redis, втрати вузла API й worker та перезапуску планувальника; кожна подія має завершитися в межах цілі [контракту одного регіону](#single-region-high-availability-and-failover) без втрати підтверджених записів |
| Оцінювання активного й резервного регіонів за участю підтримки | Комплект кожного регіону, схема реплікації бази й ізоляції старого вузла запису, виміряне відставання реплікації, RPO/RTO оператора, інструкції підвищення резервного вузла й повернення, підтвердження репетицій конкретного середовища |

Якщо не можете надати цей комплект на вимогу, вважайте середовище тестовим,
доки контракт відновлення не записано й не відрепетирувано.
[Операторські межі експлуатації](/docs/operator-operating-envelope) визначають
порядок відновлення, перевірку й періодичність репетицій цих комплектів.

## Безпека, дані та аудит {#security-data-and-audit-posture}

Власні розгортання Durable Workflow успадковують більшість механізмів безпеки
від вашого середовища. Публікуйте ці факти в тому самому комплекті випуску чи
операційному посібнику, що й тег образу, план міграції та підтвердження відновлення:

| Область | Чесне твердження про випуск |
| --- | --- |
| Обробка даних | Аргументи workflow, результати, історія, memo, пошукові атрибути, мітки видимості, контекст команд, записи аудиту, повідомлення винятків та примітки оператора можуть містити дані застосунку клієнта. [Ідентифікатори workflow](./defining-workflows/workflow-id.md#ids-are-visible-metadata), пошукові атрибути й мітки — видимі оператору метадані, а не сховище секретів. Ідентифікатори workflow залишаються відкритим текстом і не охоплюються кодеками payload. |
| Шифрування | Використовуйте TLS для кожного виробничого HTTP-інтерфейсу й налаштуйте [TLS бази даних](./polyglot/server-config-reference.md#database-tls) у кожній ролі Server, включно з міграціями. Шифрування під час зберігання забезпечують ваша база, об’єктне сховище, файлова система, черга, кеш і засіб керування секретами. Пакет workflow і Server не шифрують автоматично кожне поле payload. |
| Відповідність вимогам | Пакет із відкритим кодом і власний Server надають механізми й підтвердження аудиту, а не сертифікацію відповідності самі по собі. Твердження про SOC 2, HIPAA, PCI, ISO або FedRAMP належать вашій програмі, якщо керована пропозиція не документує інше. |
| Журнали аудиту | Команди workflow, події аудиту розкладів, метадані експорту історії та записи викликів служб надають стійкі операційні підтвердження. Вони не є повноцінною SIEM, DLP, незмінним зовнішнім реєстром або системою юридичного збереження даних, якщо ви не додасте ці компоненти. |
| Підтримка | Тут документовано облікові дані з обмеженням за ролями, завершення TLS, резервні копії, репетиції відновлення та вузькі самостійні топології. Розширене керування ідентичністю, розгортання mTLS, приватна мережа, власні рушії політик, відповідність провайдера й індивідуальна перевірка топології потребують участі підтримки, якщо публічні документи не визначають інше. |

Мережева модель має бути явною:

- **Вхідні webhook:** документуйте публічну кінцеву точку, метод
  автентифікації, захист від повторних запитів або стратегію ідемпотентності,
  тайм-аут, межу payload, довірені заголовки проксі та план ротації секретів.
- **Трафік worker до сервера:** використовуйте перевірку TLS, облікові дані
  worker з обмеженням за ролями, заголовки простору імен, приватну мережу чи
  mTLS за перетину недовіреної мережі та ротацію, що не надає токенам worker
  повноважень оператора.
- **Операторські інтерфейси:** захищайте Waterline, операторські API Server,
  кінцеві точки автоматизації CLI та власні адміністративні панелі
  автентифікованими сеансами чи службовими обліковими даними з обмеженням за
  ролями, захистом CSRF для браузерних сеансів і задокументованими межами проксі/TLS.

## Опубліковані образи {#published-images}

Для власних розгортань Server використовуйте опубліковані образи:

- Docker Hub: `%%artifact.serverDockerHubImage%%`
- GitHub Container Registry: `%%artifact.serverGhcrImage%%`
- Закріплення за дайджестом: `durableworkflow/server@sha256:...` або
  `ghcr.io/durable-workflow/server@sha256:...`

Використовуйте змінювані теги лише для локальних експериментів. Виробничі файли
змінних середовища мають закріплювати конкретну версію чи дайджест, щоб кроки
оновлення й відкату можна було перевірити. Нативні випуски мають мажорну
версію 3; рухомі теги `3` і `latest` переходять на кожен новий нативний випуск,
а `2` залишається на останньому випуску PHP 2.x.

## Локальна розробка та внутрішнє невиробниче середовище {#local-development-and-internal-non-production}

Використовуйте рецепт Compose опублікованого образу для середовища без
вихідного коду: нативного Server і MySQL. Завантажте файл із вибраного
випуску й закріпіть образ через `DW_SERVER_IMAGE`:

```bash
curl -fsSLO %%artifact.serverComposeUrl%%

export %%artifact.serverImageEnv%%
export DW_AUTH_TOKEN=dev-token

docker compose -f docker-compose.published.yml up -d --wait
```

Compose не запуститься, доки не задано `DW_AUTH_TOKEN`. Файл публікує API лише
на `127.0.0.1:8080` і не публікує MySQL. Для віддаленого доступу задайте в
`SERVER_BIND_ADDRESS` захищений приватний інтерфейс.

Перевірте API, готовність до роботи, виявлення кластера й реєстрацію worker:

```bash
curl http://localhost:8080/api/health
curl http://localhost:8080/api/ready
curl -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  http://localhost:8080/api/cluster/info

curl -X POST http://localhost:8080/api/worker/register \
  -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Namespace: default" \
  -H "X-Durable-Workflow-Protocol-Version: 1.0" \
  -d '{"worker_id":"compose-worker","task_queue":"compose","runtime":"python"}'
```

Цей шлях придатний для розробки та внутрішнього тестового середовища. Він не є
межею виробничої безпеки: приклад використовує один спільний токен,
типові паролі служб, локальні іменовані томи й не має TLS.

## Одновузлове виробниче середовище {#single-node-production}

Використовуйте той самий артефакт Compose із виробничою конфігурацією поза
системою керування версіями:

```env
%%artifact.serverImageEnv%%
SERVER_PORT=8080
# Loopback by default. Use a protected private interface for the reverse proxy.
SERVER_BIND_ADDRESS=127.0.0.1

DB_DATABASE=durable_workflow
DB_USERNAME=workflow
DB_PASSWORD=replace-with-random-password
DB_ROOT_PASSWORD=replace-with-random-root-password

DW_AUTH_DRIVER=token
# Required. Native accepts the shared token for every role; keep it secret.
DW_AUTH_TOKEN=replace-with-random-shared-token
DW_WORKER_TOKEN=replace-with-worker-token
DW_OPERATOR_TOKEN=replace-with-operator-token
DW_ADMIN_TOKEN=replace-with-admin-token
```

Нативний Server вимагає `DW_AUTH_TOKEN` і відмовляється запускатися з
`DW_AUTH_BACKWARD_COMPATIBLE=false`, тому спільний токен вимкнути не можна.
Поводьтеся з ним як із токеном адміністратора, а worker і застосункам видавайте
вужчі токени з обмеженням за ролями.

Запустіть із цим файлом змінних середовища:

```bash
docker compose --env-file durable-workflow.prod.env \
  -f docker-compose.published.yml up -d --wait
```

Обслуговуйте хост як виробничий сервіс:

- Розмістіть TLS, публічну маршрутизацію, журналювання запитів і списки
  дозволених IP у зворотному проксі перед контейнером API.
- Не відкривайте MySQL публічно.
- Використовуйте `DW_WORKER_TOKEN` для worker, `DW_OPERATOR_TOKEN` для трафіку
  застосунку й оператора та `DW_ADMIN_TOKEN` для просторів імен і адміністрування.
- Резервуйте том MySQL перед кожним оновленням образу й за регулярним розкладом;
  він є стійким джерелом істини історії workflow. Том `server_storage` містить
  локальні об’єкти зовнішніх payload Server: резервуйте його разом із MySQL,
  бо точка відновлення потребує обох. Дивіться
  [процедуру резервування й відновлення власного розгортання](https://github.com/durable-workflow/server/blob/main/docs/self-hosted-backup-and-restore.md).
- Для відновлення зберігайте разом точний файл змінних середовища, тег чи
  дайджест образу та резервну копію бази.

Порядок оновлення:

1. Створіть резервні копії MySQL і `server_storage` та запишіть поточне посилання на образ.
2. Змініть лише `DW_SERVER_IMAGE`.
3. Завантажте новий образ командою `docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml pull`.
4. Виконайте `docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml up -d --wait`.
5. Перевірте `/api/ready`, `/api/cluster/info` та реєстрацію worker перед
   переведенням зовнішнього трафіку.

Нативний Server перевіряє свою схему під час запуску. Patch-випуски в межах
однієї мінорної лінії нативного Server зберігають схему, тому достатньо змінити
образ. Випуск, у нотатках якого оголошено зміну схеми, також потребує команди
образу `schema-upgrade`, яку виконують після резервного копіювання бази, коли
всі Server зупинені. Довідник Server підтримує актуальні команди Compose в
розділі
[Official Image + Compose](https://github.com/durable-workflow/server/blob/main/docs/server-reference.md#official-image--compose).

### Оновлення до Server 3.10.0 {#native-schema-upgrade-3-10}

Нативний 3.10.0 потребує явного адитивного оновлення схеми з 3.9.x.

| Backend | Перехід схеми з 3.9.x |
|---|---|
| SQLite | 13 → 14 |
| PostgreSQL | 14 → 15 |
| MariaDB | 14 → 15 |
| MySQL | 15 → 16 |

Зупиніть усі репліки Server, залиште базу активною та створіть резервні копії бази й зовнішнього сховища payload. Виберіть образ 3.10.0 і виконайте його `schema-upgrade` один раз перед перезапуском усіх реплік на тій самій версії. Перевірте readiness, оголошену версію та реєстрацію Worker. Запуск не оновлює стару схему автоматично. Старіші версії також потребують проміжних кроків. [Опубліковані інструкції 3.10.0](https://github.com/durable-workflow/server/releases/tag/3.10.0#upgrade-and-rollback) містять команди Compose. Протокол Worker 1.20 і control plane 2 не змінюються.

Nullable-підсумок розкладу не заповнюється зі старих масивів дій. Наявні розклади залишаються недоступними, доки відповідальний перехід не запише коректний підсумок; див. [авторитетність підсумку dispatch](./polyglot/server-api-reference.md#schedule-dispatch-summary). MySQL і MariaDB продовжують перервані оновлення; SQLite та PostgreSQL застосовують крок транзакційно. Відкат до старішого бінарного файлу потребує відновлення передоновлювальної копії бази й сховища. Не запускайте старий бінарний файл із новою схемою.

### Оновлення до Server 3.9.2 {#native-schema-upgrade-3-9}

Оновлення з native 3.8.x або ранішої версії потребує оновлення схеми на кожному бекенді. Server 3.9.1 додає порожню таблицю `dw_command_intents`:

| Бекенд | Перехід схеми з 3.8.x |
|---|---|
| SQLite | 12 → 13 |
| PostgreSQL | 13 → 14 |
| MariaDB | 13 → 14 |
| MySQL | 14 → 15 |

Зупиніть усі репліки Server, залиште базу даних працювати, створіть резервні копії бази та сховища Server, а тоді виберіть і завантажте образ 3.9.2. Запустіть його `schema-upgrade` один раз перед перезапуском усіх реплік на тій самій версії. Server не оновлює наявну схему при запуску: він відмовляє зі старою схемою через `native_schema_upgrade_required`. Після перезапуску перевірте readiness, версію та реєстрацію Worker. [Кваліфіковані інструкції релізу 3.9.2](https://github.com/durable-workflow/server/releases/tag/3.9.2#upgrade-and-rollback) містять команди Compose без checkout вихідного коду.

MySQL і MariaDB продовжують перерване оновлення; SQLite та PostgreSQL застосовують крок транзакційно. Відкат до 3.8.x потребує відновлення резервної копії: 3.8.0 відмовляє з оновленою базою через `native_schema_newer_than_binary`. Із 3.9.0 або 3.9.1 додатковий крок схеми не потрібен: зупиніть репліки, створіть резервну копію, виберіть новий образ, перезапустіть і перевірте readiness, версію та реєстрацію Worker. Фізична схема й наявні рядки команд/намірів не змінюються. Відкат до 3.9.1 використовує ту саму схему, але повертає дефекти ключів Unicode/метаданих квитанцій та прибирає посилення власника спостережень. Для старіших версій `schema-upgrade` застосовує також попередні кроки, зокрема [перебудову JSON у 3.7](#native-schema-upgrade-3-7), якщо вона потрібна. Протокол Worker 1.20 і control plane 2 не змінюються.

### Оновлення до Server 3.8.0 {#native-schema-upgrade-3-8}

Server 3.8.0 потребує нативного оновлення схеми на кожному бекенді. Він додає одну таблицю лише для native, `dw_task_queue_pauses`, яка створюється порожньою:

| Бекенд     | Схема   |
|------------|---------|
| SQLite     | 11 → 12 |
| PostgreSQL | 12 → 13 |
| MariaDB    | 12 → 13 |
| MySQL      | 13 → 14 |

Цей крок лише створює таблицю; він не переписує жодних рядків і триває секунди. Server ніколи не оновлює свою схему під час запуску: Server 3.8.0, запущений на попередній схемі, відмовляється стартувати з `native_schema_upgrade_required`. Для одновузлового розгортання Compose:

1. Зупиніть Server, залишивши MySQL запущеним:

   ```bash
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml stop server
   ```
2. Створіть резервні копії MySQL і `server_storage` та запишіть поточне
   посилання на образ. Ця резервна копія — єдиний шлях назад до 3.7.x.
3. Змініть `DW_SERVER_IMAGE` на образ 3.8.0, завантажте його й один раз
   виконайте `schema-upgrade`:

   ```bash
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml pull server
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml run --rm --no-deps server schema-upgrade
   ```

   З 3.7.x у MySQL команда повідомляє `"from_schema_version":13,"schema_version":14,"status":"upgraded"`. Повторний запуск на актуальній базі повідомляє `"status":"current"`.
4. Запустіть Server командою
   `docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml up -d --wait`,
   потім перевірте `/api/ready`, `/api/cluster/info` (`version` дорівнює
   `3.8.0`) та реєстрацію worker.

Якщо кілька Server використовують одну базу, зупиніть їх усі перед кроком 3, а потім запустіть усі на 3.8.0. У MySQL і MariaDB перерване оновлення продовжується, коли ви знову запускаєте `schema-upgrade`; SQLite і PostgreSQL оновлюються в одній транзакції. Повернення до 3.7.x потребує резервної копії: Server 3.7.0 відхиляє оновлену базу з `native_schema_newer_than_binary`. Протокол workers лишається `1.20`, а площина керування — версії `2`.

Для попередніх випусків `schema-upgrade` образу 3.8.0 застосовує всі попередні кроки за один запуск. У MySQL з 3.5.x або 3.6.x (схема 12) це включає [перебудову JSON 3.7.0](#native-schema-upgrade-3-7) з її простоєм близько 2 хвилин на мільйон рядків історії. Для 3.4.x і раніших це включає [крок схеми 3.5.0](#native-schema-upgrade-3-5).

У MySQL, MariaDB і PostgreSQL кожне з’єднання пулу тепер кешує до 200 підготовлених інструкцій (prepared statements). У MySQL підготовлені інструкції всіх клієнтів зараховуються до загальносерверного ліміту `max_prepared_stmt_count` (типово 16382). Нативний вузол має 4 з’єднання пулу, тож тримайте `nodes × 4 × 200` разом з інструкціями інших клієнтів у межах цього ліміту; типовий сервер MySQL вміщує близько 20 нативних вузлів. Для більшої кількості збільште `max_prepared_stmt_count` або зменште кеш за допомогою `DW_NATIVE_DB_STATEMENT_CACHE_CAPACITY` (або `statement-cache-capacity` у `DB_URL`) — цілого числа від 0 до 4095. Server, якому задано недійсне значення або два різні значення, відмовляється стартувати. `Prepared_stmt_count` у `SHOW GLOBAL STATUS` показує поточне використання.

Server 3.8.0 також дає оператору змогу призупиняти й відновлювати диспетчеризацію activity в одній черзі завдань; це оголошується як `capabilities.task_queue_activity_dispatch_pause` (див. [примітки до випуску 3.8.0](https://github.com/durable-workflow/server/releases/tag/3.8.0)). Нативний redrive тепер повторно використовує побічні ефекти та маркери версій, записані до кроку зі збоєм, з їхніми початковими payload і часом.

### Оновлення до Server 3.7.0 {#native-schema-upgrade-3-7}

Server 3.7.0 зберігає JSON-документи MySQL як точний текст, тож числа double зберігають усі цифри. Змінюється лише MySQL: його нативна схема переходить з 12 на 13, а 75 стовпців `json` у 36 таблицях стають `LONGTEXT` (`utf8mb4_bin`) з обов’язковою перевіркою `json_valid`, по одному `ALTER TABLE` на таблицю. Уже збережені документи зберігають попереднє подання MySQL. Server 3.7.0, запущений на схемі MySQL 12, відмовляється стартувати з `native_schema_upgrade_required`.

MariaDB і PostgreSQL лишаються на схемі 12, а SQLite — на 11, тому база 3.5.0 або 3.6.0 на них працює з 3.7.0 без змін: змініть лише `DW_SERVER_IMAGE` і дотримуйтеся описаного вище порядку оновлення. Повернення до 3.6.0 — це лише зміна образу. Для версій 3.4.x і раніших кожній базі також потрібен [крок схеми 3.5.0](#native-schema-upgrade-3-5); виконайте його з образом 3.7.0, чий `schema-upgrade` також застосовує попередні кроки.

У MySQL Server недоступний протягом усього оновлення. За вимірами на MySQL 8.0 з 2 CPU і типовим buffer pool воно триває близько 2 хвилин на мільйон рядків історії. Для одновузлового розгортання Compose:

1. Зупиніть Server, залишивши MySQL запущеним:

   ```bash
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml stop server
   ```
2. Створіть резервні копії MySQL і `server_storage` та запишіть поточне
   посилання на образ. Ця резервна копія — єдиний шлях назад до 3.6.0 у MySQL.
3. Змініть `DW_SERVER_IMAGE` на образ 3.7.0, завантажте його й один раз
   виконайте `schema-upgrade`:

   ```bash
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml pull server
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml run --rm --no-deps server schema-upgrade
   ```

   У MySQL команда виводить версії схеми до й після, наприклад `"from_schema_version":12,"schema_version":13,"status":"upgraded"`. Повторний запуск на актуальній базі повідомляє `"status":"current"`.
4. Запустіть Server командою
   `docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml up -d --wait`,
   потім перевірте `/api/ready`, `/api/cluster/info` (`version` дорівнює
   `3.7.0`) та реєстрацію worker.

Перерване оновлення продовжується з таблиці, на якій зупинилося, коли ви знову запускаєте `schema-upgrade`. Повернення до 3.6.0 у MySQL потребує резервної копії: Server 3.6.0 відхиляє оновлену базу з `native_schema_newer_than_binary`. Протокол workers лишається `1.20`, а площина керування — версії `2`.

Server 3.7.0 також змінює нативний redrive (див. [примітки до випуску 3.7.0](https://github.com/durable-workflow/server/releases/tag/3.7.0)): memo та атрибути пошуку, задані під час старту, переходять до наступника, а `describe` повідомляє `actions.can_redrive` і `actions.redrive_blocked_reason`.

### Оновлення до Server 3.5.0 {#native-schema-upgrade-3-5}

Server 3.5.0 додає одну таблицю лише для native, `dw_run_command_contracts`. Нативна схема переходить з 11 на 12 у MySQL, MariaDB і PostgreSQL та з 10 на 11 у SQLite. Оновлення створює таблицю та її індекс і не переписує жодних рядків. Server 3.4.x має ту саму схему, що й 3.3.x, тому з 3.3.x або 3.4.x це єдиний крок схеми. Server 3.5.0, запущений на попередній схемі, відмовляється стартувати з `native_schema_upgrade_required`.

Для одновузлового розгортання Compose:

1. Зупиніть Server, залишивши MySQL запущеним:

   ```bash
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml stop server
   ```
2. Створіть резервні копії MySQL і `server_storage` та запишіть поточне
   посилання на образ. Ця резервна копія — єдиний шлях назад до 3.4.x.
3. Змініть `DW_SERVER_IMAGE` на образ 3.5.0, завантажте його й один раз
   виконайте `schema-upgrade`:

   ```bash
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml pull server
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml run --rm --no-deps server schema-upgrade
   ```

   Команда виводить версії схеми до й після, наприклад `"from_schema_version":11,"schema_version":12,"status":"upgraded"`. Повторний запуск на актуальній базі повідомляє `"status":"current"`.
4. Запустіть Server командою
   `docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml up -d --wait`,
   потім перевірте `/api/ready`, `/api/cluster/info` (`version` дорівнює
   `3.5.0`) та реєстрацію worker.

У MySQL і MariaDB перерване оновлення продовжується, коли ви знову запускаєте `schema-upgrade`. Повернення до 3.4.x потребує резервної копії: Server 3.4.x відхиляє оновлену базу з `native_schema_newer_than_binary`. Для версій від 3.0.x до 3.2.x та сама команда також застосовує попередні кроки з наступного розділу. Протокол workers лишається `1.20`, а площина керування — версії `2`.

Що змінюється для запущених workflows, описано в [примітках до випуску 3.5.0](https://github.com/durable-workflow/server/releases/tag/3.5.0): updates для запусків, стартованих до реєстрації їхнього worker, тепер прив’язують контракт цього worker замість відхилення; sticky execution із суфіксами історії; а цикл обслуговування щохвилини видаляє прострочені запуски.

### Оновлення з Server 3.0.x до 3.3.2 {#native-schema-upgrade-3-0-to-3-3}

Це попередні кроки схеми. Якщо ви переходите з 3.0.x одразу на 3.5.0, використайте образ 3.5.0 на кроці 3: його `schema-upgrade` застосовує ці кроки та крок 3.5.0 разом, а примітки нижче про побудову індексів у PostgreSQL і продовження в MySQL лишаються чинними.

Server 3.3.2 відділяють від 3.0.x три мінорні випуски, і він змінює нативну
схему. На MySQL, MariaDB і PostgreSQL вона переходить з версії 8 (3.0.x і
3.1.0) через 10 (3.2.0) до 11 (від 3.3.0 до 3.3.2). На SQLite вона переходить
з 8 до 10. Server ніколи не оновлює свою схему під час запуску: 3.3.2,
запущений на базі версії 8, відмовляє з `native_schema_upgrade_required`, тому
сама лише зміна `DW_SERVER_IMAGE` залишає новий Server нездатним запуститися.
Команда `schema-upgrade` образу 3.3.2 оновлює базу версії 8 безпосередньо.
[Нотатки оновлення 3.3.0](https://github.com/durable-workflow/server/blob/3.3.2/docs/releases/3.3.0.md#upgrade)
описують цей крок, а
[нотатки Chart 1.1.0 / Server 3.3.2](%%artifact.helmChartUpgradeUrl%%#chart-110--server-332-native)
чарта Helm перелічують кроки схеми та зміни runtime від 3.0.5 до 3.3.2.

Для одновузлового розгортання Compose:

1. Зупиніть Server, залишивши MySQL запущеним:

   ```bash
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml stop server
   ```
2. Створіть резервні копії MySQL і `server_storage` та запишіть поточне
   посилання на образ. Ця резервна копія — єдиний шлях назад до 3.0.x.
3. Змініть `DW_SERVER_IMAGE` на образ 3.3.2, завантажте його й один раз
   виконайте `schema-upgrade`:

   ```bash
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml pull server
   docker compose --env-file durable-workflow.prod.env \
     -f docker-compose.published.yml run --rm --no-deps server schema-upgrade
   ```

   Команда виводить бекенд і версії схеми до й після, наприклад
   `"from_schema_version":8,"schema_version":11,"status":"upgraded"`.
   На базі, яка вже актуальна, вона лише перевіряє схему.
4. Запустіть Server командою
   `docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml up -d --wait`,
   потім перевірте `/api/ready`, `/api/cluster/info` (`version` дорівнює
   `3.3.2`) та реєстрацію worker.

- **PostgreSQL:** кроки версій 10 і 11 будують свої індекси звичайним
  `CREATE INDEX`, який блокує записи в `workflow_tasks`, доки побудова не
  завершиться. Для великої таблиці `workflow_tasks` заплануйте на це простій.
- **MySQL і MariaDB:** там DDL фіксується окремо, тому оновлення позначає базу
  як таку, що оновлюється, доки воно не завершиться, і кожен Server тим часом
  відмовляє їй з `native_schema_upgrade_incomplete`. Якщо оновлення перервано,
  знову виконайте `schema-upgrade`, щоб продовжити його.
- **Відкат потребує резервної копії.** Пониження версії схеми не існує. Server
  3.0.x відмовляє оновленій базі з `native_schema_newer_than_binary`. Щоб
  повернутися, відновіть резервну копію, створену на кроці 2, що відкидає все
  записане після неї, а потім запустіть образ 3.0.x.

Протокол worker залишається `1.20`, а площина керування — версією `2`.

## Невеликі кластерні розгортання {#small-clustered-deployments}

:::note Контракт PHP Server 2.x

Перевірений контракт невеликого кластера та його CI-обв’язка використовують
PHP Server 2.x: спільний Redis, worker черги й рівно один планувальник.
Нативний 3.x не має жодної з цих ролей, а нативного рецепта Compose для
невеликого кластера чи відповідної обв’язки не опубліковано. Для кількох реплік
нативного Server використовуйте [нативний режим чарта Helm](#helm-chart-for-kubernetes)
із зовнішньою базою MySQL або PostgreSQL і томом ReadWriteMany для сховища payload.

:::

Невеликий кластер помірно розширює одновузлову модель. Перевірений самостійний
контракт навмисно вузький:

- Запускайте 2–3 контейнери API без локального стану за балансувальником.
  Перевірки працездатності й готовності, виявлення кластера, реєстрація worker,
  опитування та завершення завдань workflow мають працювати без закріплених сеансів.
- Використовуйте одну спільну зовнішню MySQL або PostgreSQL для стійкої історії.
  SQLite підтримує лише один вузол і не є кластерним сховищем.
- Використовуйте спільний Redis для кешу, сигналів пробудження довгого
  опитування, блокувань черг query, блокувань приймання черг завдань та стану
  черг. Багатовузловий режим без Redis не входить до підтримуваного контракту.
- Під час розгортання перевіряйте `GET /api/cluster/info` кожного вузла API.
  `topology.current_shape` має залишатися `standalone_server`,
  `topology.current_roles` — містити `api_ingress`, `control_plane`, `matching`
  і `history_projection`, а `topology.execution_mode` має залишатися
  `remote_worker_protocol` для окремих вузлів Server. Перевіряйте фактично
  розгорнутий підбір завдань через `topology.matching_role`: типові вузли
  повідомляють `queue_wake_enabled: true`, `shape: "in_worker"` та
  `wake_owner: "worker_loop"`, а розгортання окремого підбору перемикають вузли
  з `DW_V2_MATCHING_ROLE_QUEUE_WAKE=0` на `queue_wake_enabled: false`,
  `shape: "dedicated"` та `wake_owner: "dedicated_repair_pass"`. Цей самий блок
  має далі оголошувати потрібний `task_dispatch_mode`, закріплені осі
  маршрутизації `partition_primitives` і поточний `backpressure_model`.
  Значення кожного поля описано в [топології ролей Server](/docs/polyglot/server-role-topology).
- Масштабуйте зовнішні worker SDK незалежно від вузлів API. Worker можуть
  працювати на окремих хостах чи в окремих процесах, але мають звертатися до
  збалансованої кінцевої точки API, а не до одного закріпленого вузла.
- Налаштуйте [приймання черги завдань](/docs/polyglot/task-queue-admission)
  для черг, які захищають орендаря, зовнішній API, пул з’єднань бази або іншу
  спільну залежність-отримувача.
- Запускайте рівно один процес планувальника чи обслуговування для оцінювання
  розкладів, застосування тайм-аутів activity та очищення історії.
- Виконуйте початкове налаштування й міграції один раз на розгортання до
  приймання трафіку новими контейнерами API та worker.
- Оберіть режим оновлення цього випуску: повна зупинка (завершення прийнятої
  роботи worker, зупинка планувальника й обслуговування, заміна вузлів API,
  початкове налаштування й міграції, перезапуск worker і планувальника) або
  [поступове оновлення](/docs/rolling-upgrades), коли виконано всі гарантії контракту.
- Розглядайте базу й Redis як основні області відмов. Контейнери Server можна
  замінити; шари зберігання та координації — ні.

Опубліковані самостійні рецепти починаються з форми `standalone_server`, хоча
виявлення кластера також називає `split_control_execution` підтримуваною
топологією продукту. Це один контракт із різними призначеннями ролей, а не
другий серверний продукт. Якщо пізніше випробовуватимете явніший поділ ролей,
продовжуйте читати `topology.current_shape`, `topology.current_roles` та
`topology.matching_role` з `/api/cluster/info`, а не виводити обов’язки з назв
хостів чи контейнерів. [Топологія ролей Server](/docs/polyglot/server-role-topology)
пояснює призначення ролей і шлях міграції.

Кожен вузол API має використовувати однакові токени автентифікації чи ключі
підпису, версію застосунку, версію пакета workflow, конфігурацію кодеків payload,
підключення бази й Redis. Задайте кожному вузлу API унікальний `DW_SERVER_ID`,
щоб виявлення кластера та журнали розрізняли вузли.

Непідтримувані межі явні: кластер SQLite, багатовузловий режим без Redis,
дублікати планувальника як стала топологія, бази з кількома активними вузлами
запису, автономне регіональне перемикання власного середовища та широкі SLA
«п’ять дев’яток» чи «без простою» потребують окремої перевірки або проєктування
за участю підтримки до використання. Матеріали щодо активного й резервного
регіонів також є оцінювальними; дивіться [відповідний розділ](#activepassive-multi-region).
Висока доступність в одному регіоні — перемикання керованої бази й Redis,
втрата вузла API чи worker та перезапуск планувальника — залишається
оцінювальним контрактом за участю підтримки до проходження перевірки випуску.
Цілі відновлення рушія, правила готовності під час перемикання та потрібні
підтвердження наведено в [контракті одного регіону](#single-region-high-availability-and-failover).

Цей шлях самостійний, коли команда вже має чітку модель VM, мережі, бази, кешу,
резервування та балансувальника. Підтримка потрібна, коли необхідна допомога
з визначенням цих меж, місткості, порядку розгортання чи процедур відновлення.

## Бюджети таймаутів довгих опитувань worker {#worker-long-poll-timeout-budgets}

Справне опитування worker може не передавати даних до завершення очікування на сервері. Ураховуйте цю тишу в HTTP-клієнті worker, вихідному проксі, service mesh, публічному балансувальнику, ingress і кожному зворотному проксі перед API. Опитування worker проходять через спільний API ingress. Окрема роль matching не оминає ці вузли.

| Бюджет | Що він обмежує |
| --- | --- |
| Тривалість опитування на сервері | Час очікування роботи до порожньої відповіді. `timeout_seconds` у запиті перевизначає `DW_WORKER_POLL_TIMEOUT`. Змінна є типовим значенням для запиту без цього поля, а не межею для SDK. Протокол дозволяє до 60 секунд. |
| Таймаут з’єднання / пулу клієнта | Установлення з’єднання або отримання його з пулу. Ці етапи не повинні тривати весь час тихого опитування. |
| Таймаут читання / загальний таймаут клієнта | Очікування байтів відповіді або всієї операції, якщо транспорт має загальну межу. Додайте до очікування сервера запас на з’єднання, планування та відповідь. Таймаут читання може вимірювати паузу між частинами даних, а не весь запит. |
| Idle / upstream read / request timeout посередника | Кожна межа активного запиту на кожному вузлі має дозволяти нормальне тихе опитування та відповідь. Keepalive для з’єднання між запитами є іншою межею. |
| Завершення worker / кінцевий строк виклику | Бюджет завершення worker та початковий кінцевий строк виклику чи query залишаються жорсткими межами. Скасовуйте або завершуйте роботу в цих межах. Не подовжуйте query через проксі чи повторну спробу. |

Перевіряйте розрахунки встановленого SDK. У перевіреній нижче версії Python позитивне очікування на сервері обмежується 60 секундами, а таймаути фаз HTTP мають щонайменше п’ять додаткових секунд. Типове опитування Worker триває 35 секунд, що зазвичай дає 40 секунд для фаз HTTP. Межа читання посередника у 30 секунд може обірвати справне типове опитування. PHP і Rust мають власні типові значення та політики повторів. Запас Python або налаштування gRPC keepalive не є універсальним правилом. Дивіться посібники SDK для [PHP](https://php.durable-workflow.com/), [Python](https://python.durable-workflow.com/), [Rust](https://rust.durable-workflow.com/) та [довідник matching](./polyglot/task-matching-dispatch.md).

Звичайні виклики control plane через `Client` у PHP SDK **3.2.0** не задають типового загального кінцевого строку HTTP. Дивіться [перевірений дефект PHP #203](https://github.com/durable-workflow/sdk-php/issues/203). Налаштуйте обмежений HTTP-клієнт для цих викликів і зберігайте початковий кінцевий строк. Таймаут опитування Worker не обмежує всі запити SDK.

PHP SDK **3.4.0 або новіший** додає **типовий загальний строк 60 секунд** для звичайних control HTTP-запитів через власний транспорт SDK; задайте скінченне `requestTimeoutSeconds` щонайменше `0.001` секунди. Ці таймаути власного транспорту SDK мають `reason=request_timeout` і `status=0`. SDK робить одну спробу: mutation із таймаутом уже могла бути прийнята, тому перед повтором перевірте початкову ідентичність/результат. Вставлені клієнти/транспорти зберігають власну timeout policy й не поєднуються з цим параметром. Межа одного запиту не замінює строки worker long-poll, передавання payload чи workflow/виклику. Перевіряйте `composer.lock`: мінімум функції не змінює вибрану комбінацію встановлення. Див. [налаштування HTTP-клієнта](https://php.durable-workflow.com/getting-started/client-setup/) і [перевірку звичайного встановлення 3.4.0](https://github.com/durable-workflow/sdk-php/issues/203#issuecomment-6363909756).

### Перевірений приклад короткого опитування {#verified-poll-timeout-example}

Ізольована перевірка використовувала опубліковані Python SDK **2.9.0**, PHP Server **2.11.0** і Nginx **1.30.5** з порожньою чергою. В обох випадках опитування SDK тривало **3 секунди**, таймаути connect/read/write/pool HTTPX становили **8 секунд**, а зовнішня межа виклику — **10 секунд**. Змінювався лише таймаут читання upstream у Nginx:

| Налаштування посередника | Спостережена відповідь |
| --- | --- |
| `proxy_read_timeout 1s` | Приблизно за секунду Nginx повернув HTTP **504**, очікуючи заголовок upstream. SDK передав `ServerError`. |
| `proxy_read_timeout 8s` | Приблизно за три секунди нормальне тихе опитування повернуло HTTP **200**, `task: null` і `poll_status: empty`. |

Типове очікування сервера навмисно становило одну секунду в обох випадках. Явні три секунди в запиті все одно діяли. HTTP-повтори обмежувалися однією спробою, щоб показати першу помилку. Це функціональний приклад, а не вимірювання місткості чи рекомендація для production. [Перевірка в #267](https://github.com/durable-workflow/durable-workflow.github.io/issues/267) містить точні образи, запити та журнали.

Для Nginx задайте належний бюджет читання upstream у наявному location опитувань worker. Вісім секунд нижче стосуються саме прикладу з трисекундним опитуванням:

```nginx
proxy_connect_timeout 2s;
proxy_read_timeout 8s;
```

[Nginx вимірює `proxy_read_timeout` між читаннями upstream](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout). [HTTPX розрізняє таймаути connect, read, write і pool](https://www.python-httpx.org/advanced/timeouts/). Вісім секунд на фазу не є загальним восьмисекундним кінцевим строком. За потреби задавайте явну зовнішню межу. Інші проксі й провайдери мають інші назви та семантику. Перевіряйте весь шлях фактичним SDK: збільшення одного таймауту ingress не виправляє коротшу межу в іншому місці.

### З’ясуйте причину відповіді перед перезапуском worker {#diagnose-poll-disconnects}

- **Нормальне порожнє опитування:** успішна відповідь без завдання. У перевіреній версії необроблена відповідь має `poll_status: empty`. Продовжуйте опитування.
- **Розрив посередником:** транспортний виняток, скидання з’єднання або 502/504 проксі можуть передувати кінцю очікування сервера. Зіставляйте помилку та тривалість із журналами проксі/upstream. Справний readiness і подальша успішна робота не виключають помилковий таймаут.
- **Недоступний runtime:** перевіряйте структуровану причину та readiness бази даних, кешу й admission. HTML-помилка шлюзу не є типізованою відмовою runtime.
- **Відмова admission для namespace чи опитування:** перевірте причину, namespace/чергу та затримку повтору, зокрема для HTTP 429. Збільшення idle timeout не додає місткості та не виправляє авторизацію.

Повторне з’єднання worker не доводить правильність попереднього налаштування проксі. Перевіряйте, чи реально тривають опитування та завершення завдань. За сталих помилок зберігайте клас, чергу, час і частоту. Поодинокий розрив не вимагає перезапуску процесу. Клієнт Python також може створити `poll_status: timeout` після повторів HTTP-таймауту. Саме це значення не доводить, що порожня відповідь runtime пройшла через проксі. Не змішуйте транспортні повтори з повторами activity, кінцевими строками запуску та повноваженнями query.

## Бюджети SQL-з’єднань {#sql-connection-budgets}

Сплануйте сесії бази даних, перш ніж додавати репліки API або одночасно
запускати старі й нові процеси під час
[поступового оновлення](/docs/rolling-upgrades). База може вичерпати ліміт
з’єднань, коли CPU ще доступний. Це окрема межа від затримки запису/commit,
місткості HTTP та зростання обсягу збережених даних.

### Врахуйте кожен процес із доступом до SQL {#count-every-sql-owning-process}

Процес нативного Server 3.x відкриває щонайбільше чотири з’єднання з базою
даних, а команда `schema-upgrade` чи переходу на нативний Server (takeover)
під час виконання відкриває ще одне. Закладайте чотири сесії на кожну репліку
нативного Server за найбільшої кількості реплік, а також операційні
інструменти нижче. Решта цього розділу описує PHP 2.x.

Опубліковане PHP-розгортання Compose має такі можливі SQL-клієнти:

| Роль | Що враховувати |
| --- | --- |
| API | Кожен процес PHP, який одночасно обслуговує запит і може використовувати SQL, включно з перевірками готовності, операторськими запитами та poll у режимі очікування. Опублікована конфігурація Apache prefork дозволяє 24 процеси запитів на контейнер API. Це верхня межа HTTP-процесів, а не SQL-пул чи вимірювання 24 відкритих сесій. |
| Worker черги Laravel | Кожен процес `php artisan queue:work`. Опублікований рецепт Compose запускає один; додаткові контейнери worker додають процеси. Вони відрізняються від зовнішніх SDK worker. |
| Планувальник/обслуговування | Одночасні команди PHP, а не лише контейнер планувальника. Планувальник Compose послідовно виконує оцінювання розкладів, відновлення, контроль тайм-аутів activity та очищення. У звичайному циклі одночасно активна одна команда. Зберігайте правило єдиного планувальника. |
| Ініціалізація та операційні інструменти | Команди міграції/ініціалізації, перебудова проєкцій, завдання зберігання, резервування, моніторинг та інтерактивні SQL-клієнти, які можуть працювати під час розгортання. Навмисно паралельні команди враховуйте окремо. |
| SDK-клієнти та worker | Зазвичай жодних прямих сесій до бази Server: PHP, Python і Rust SDK у сервісному режимі використовують HTTP. Додавайте з’єднання лише тоді, коли код activity чи іншої частини застосунку справді звертається до цієї бази. |

Рахуйте **окремі SQL-з’єднання, які використовує кожен процес**, а не лише
контейнери чи імена хостів. Типове з’єднання Laravel і
`workflows.storage.connection` можуть мати спільне налаштоване ім’я. Інше ім’я
сховища, SQL-з’єднання черги/кешу/сесій або окремий дескриптор
читання/запису/прямого доступу може відкрити додаткову сесію навіть до тієї
самої кінцевої точки. Redis-з’єднання не є SQL-сесіями. Перевіряйте фактичну
кешовану конфігурацію та імена з’єднань, які справді використовує кожна роль.

У власному FPM-розгортанні рахуйте виконавчі процеси PHP-FPM, а не потоки nginx
чи Apache event. В Octane врахуйте worker запитів, worker завдань і фактичні
клієнти бази. Не використовуйте число 24 з Apache як розмір пулу цих
фронтендів. Синхронний long poll займає виконавчий процес PHP під час
очікування й може утримувати SQL-сесію. Не вважайте автоматично, що HTTP-poll
без роботи не використовує SQL.

### Консервативний приклад поступового оновлення {#a-conservative-rolling-upgrade-example}

Це приклад планування, **не виміряна місткість**. Припустімо, база дозволяє
120 клієнтських сесій: десять для інших застосунків, п’ятнадцять зарезервовано
для відновлення й адміністрування. Для цього розгортання залишається 95.
Черга й кеш використовують Redis; кожен PHP-процес має не більше одного
SQL-з’єднання.

| Максимальне перекриття | Розрахунок | Заплановані сесії |
| --- | --- | ---: |
| Репліки API, з однією додатковою на час оновлення | `(2 + 1) × 24 × 1` | 72 |
| Worker черги Laravel | `2 × 1` | 2 |
| Єдина команда планувальника/обслуговування | `1 × 1` | 1 |
| Ініціалізація/міграція | `1 × 1` | 1 |
| Резервування, моніторинг та інші дозволені інструменти | Явно виділений бюджет | 4 |
| **Проміжний підсумок розгортання** | | **80** |
| Нерозподілений запас розгортання | `95 − 80` | 15 |

За цих припущень четверта репліка API збільшить підсумок до 104 і перевищить
виділені 95 сесій. Два SQL-з’єднання на процес API вже потребуватимуть
144 сесії лише для трьох реплік API. Перераховуйте бюджет при зміні з’єднань
сховища, кількості worker або перекриття версій. Зменшуйте межі
процесів/реплік або замінюйте їх поетапно, не припускаючи, що база витримає
накладання. Підвищення `max_connections` також потребує оцінки пам’яті бази
та навантаження.

### Спостерігайте й дотримуйтеся бюджету {#observe-and-enforce-the-budget}

1. Запишіть фактичний ліміт з’єднань, сторонні клієнти та доступ,
   зарезервований для відновлення. Визначте максимум реплік/процесів API та
   додаткових реплік під час оновлення. Врахуйте одночасні покоління worker
   черги й інструменти.
2. В ізольованій копії з вашим точним опублікованим образом і конфігурацією
   спостерігайте сесії у спокої, під час очікування poll, виконання справжньої
   роботи та обмеженого перекриття старої й нової версій. Рахуйте неактивні
   сесії й сам монітор. PostgreSQL надає `pg_stat_activity`, MySQL —
   `information_schema.PROCESSLIST`. Використовуйте роль моніторингу з
   відповідно обмеженими правами, не експортуйте SQL-тексти чи корисні дані.
3. Порівняйте сесії за користувачем застосунку/базою з бюджетом на процес.
   Коротка вибірка перевіряє припущення конкретного стенда, а не межу насичення
   чи гарантію для кожного навантаження.
4. Стежте за запасом сесій разом із відмовами з’єднання, затримкою
   транзакцій/commit, очікуванням блокувань, утримуваними HTTP-запитами й
   зростанням сховища. Готовність сама по собі не доводить запас для оновлення.
5. Поблизу ліміту зменшіть перекриття або спорожніть і зупиніть стару групу
   API/worker до запуску заміни. Зберігайте доступ для відновлення й запускайте
   ініціалізацію лише в заплановане вікно міграції. Якщо безпечне перекриття
   не вміщується в бюджет, використовуйте задокументоване оновлення з повною
   зупинкою.

У PHP 2.x [допуск до черги завдань](/docs/polyglot/task-queue-admission)
обмежує окремі операції відправлення та lease, а
`DW_WORKER_LONG_POLL_MAX_CONCURRENT` і `DW_QUERY_TASK_POLL_MAX_CONCURRENT`
обмежують очікування poll на вузлі. Жоден із них не встановлює глобальної межі
SQL-сесій, байтів бази чи затримки commit. Залишайте місце також для
завершень, heartbeat, операторських запитів і перевірок стану. Нативний 3.x
відмовляється стартувати з лімітами допуску черги завдань і ігнорує обидва
обмеження poll; нативного еквівалента поки немає. Його SQL-сесії обмежує
фіксований пул із чотирьох з’єднань на процес; для паралельності завдань
визначайте кількість слотів SDK worker і кількість worker.

Базовий варіант — пряме підключення до доступної для запису бази. Проксі потребує перевірки з точною версією Server, режимом пулу й налаштуваннями підготовлених запитів, меж транзакцій, стану сесії та блокувань. **Пул транзакцій PgBouncer потребує виправленого Server версії 2.9.8 або новішої.** [Приймальна перевірка опублікованої версії 2.9.8](https://github.com/durable-workflow/server/issues/524#issuecomment-6293185092) підтверджує PostgreSQL 16.15 з PgBouncer 1.26.1: пряме підключення PostgreSQL, пул сесій і пул транзакцій з `max_prepared_statements=0` або `max_prepared_statements=200`. Це мінімальна сумісна версія й точно перевірена конфігурація, а не фіксація найновішої версії чи гарантія місткості; інші комбінації перевіряйте окремо. Перед прийняттям трафіку виконайте звичайну ініціалізацію `server-bootstrap` PHP 2.x через вибрану кінцеву точку або дозвольте нативному 3.x перевірити схему під час запуску через цю кінцеву точку.

`GET /api/ready` виконує читання бази з прив’язаними параметрами (`bound_read_query`) та налаштовані перевірки готовності; можливість обслуговувати записи явно залишається неперевіреною. Успішне TCP-з’єднання, міграція чи відповідь готовності не доводить виконання всіх SQL-операцій workflow або достатньої пропускної здатності commit. Репліки читання не можуть замінити авторитетний вузол запису для claims і стійких переходів.

## Чарт Helm для Kubernetes {#helm-chart-for-kubernetes}

Репозиторій Server містить [код чарта й інструкції випуску](https://github.com/durable-workflow/server/tree/main/k8s/helm/durable-workflow).
Установіть опублікований чарт із реєстру OCI:

```bash
helm install durable-workflow \
  %%artifact.helmChartRepository%% \
  --version %%artifact.helmChartVersion%% \
  --namespace durable-workflow --create-namespace \
  -f my-values.yaml
```

Чарт 1.x типово запускає нативний Server (`runtime: native`): один Deployment Server без worker, планувальника, Job міграцій чи Redis. Файл values має вказувати на зовнішню базу MySQL, MariaDB або PostgreSQL, передавати `DW_AUTH_TOKEN` і токени з обмеженням за ролями через наявні Kubernetes Secrets та налаштовувати ingress/TLS для вашого середовища. Без спільного `DW_AUTH_TOKEN` чарт відмовляється генерувати маніфести, а SQLite він не приймає. Нативне встановлення типово запускає одну репліку; для кількох реплік або автомасштабування `native.storage.existingClaim` має вказувати на том ReadWriteMany для об’єктів зовнішніх payload. Чарт не створює сховище чи керовану провайдером інфраструктуру. Для відтворюваного розгортання закріпіть образ Server за digest.

Наявний випуск PHP 2.x не переходить на нативний Server під час звичайного оновлення: чарт відмовляє, доки ви явно не задасте `runtime`. Задайте `runtime: php`, щоб зберегти worker, планувальник, Job початкового налаштування та Redis PHP 2.x. Щоб перейти на `runtime: native`, дотримуйтеся [runbook переходу на нативний Server](%%artifact.serverTakeoverRunbookUrl%%) і зберігайте `runtime: php`, доки перехід не завершиться. Дивіться [нотатки UPGRADING](%%artifact.helmChartUpgradeUrl%%) чарта.

Чарт 1.1.0 змінює типовий образ із Server 3.0.5 на 3.3.2, якому потрібне [нативне оновлення схеми](#native-schema-upgrade-3-0-to-3-3) з 8 до 11. Звичайний `helm upgrade` із чарта 1.0.x змінює лише образ, і нові Pod відмовляються запускатися з `native_schema_upgrade_required`. Дотримуйтеся [кроків Chart 1.1.0 / Server 3.3.2](%%artifact.helmChartUpgradeUrl%%#chart-110--server-332-native) чарта: масштабуйте Server до нуля з вимкненим автомасштабуванням, створіть резервну копію бази, а потім оновіться до чарта 1.1.0 з `native.schemaUpgrade.enabled=true`. Його hook `pre-upgrade` один раз виконує `schema-upgrade` перед запуском нових Pod і лише тоді, коли `lookup` Helm показує, що всі Server зупинені. Рендеринг через Argo CD, Flux і `helm template` відхиляє цей hook; натомість використовуйте ручний Job із README чарта. `helm rollback` до ревізії чарта 1.0.x не повертає Server, бо 3.0.x відмовляє оновленій базі: натомість відновіть резервну копію.

Chart 1.2.0 змінює типовий образ на Server 3.4.0 без зміни схеми, тому з chart 1.1.0 достатньо звичайного `helm upgrade`. Нативні pods також отримують паузу `preStop` (`native.preStopSleepSeconds`, типово 5) і 70-секундний період завершення. Chart 1.3.0 змінює типовий образ на Server 3.5.0, якому потрібне [оновлення схеми з 11 до 12](#native-schema-upgrade-3-5): масштабуйте Server до нуля, зробіть резервну копію бази й виконайте `helm upgrade` з `native.schemaUpgrade.enabled=true` (або ручний Job), а потім масштабуйте назад. Див. [примітки Chart 1.3.0 / Server 3.5.0](%%artifact.helmChartUpgradeUrl%%#chart-130--server-350-native) до чарту. Повернення до chart 1.2.0 означає відновлення цієї копії. Chart 1.4.0 змінює типовий образ на Server 3.6.0 без зміни схеми, тож із chart 1.3.0 достатньо звичайного `helm upgrade`, а повернення до 1.3.0 — це лише зміна образу. Див. [примітки до Chart 1.4.0 / Server 3.6.0](%%artifact.helmChartUpgradeUrl%%#chart-140--server-360-native) у chart. Chart 1.5.0 змінює типовий образ на Server 3.7.0. У MySQL йому потрібне [оновлення схеми з 12 до 13](#native-schema-upgrade-3-7): масштабуйте Server до нуля, зробіть резервну копію бази й виконайте `helm upgrade` з `native.schemaUpgrade.enabled=true` (або ручний Job), а потім масштабуйте назад. Повернення до chart 1.4.0 у MySQL означає відновлення цієї копії. У MariaDB і PostgreSQL достатньо звичайного `helm upgrade`, а повернення — це лише зміна образу. Див. [примітки до Chart 1.5.0 / Server 3.7.0](%%artifact.helmChartUpgradeUrl%%#chart-150--server-370-native) у chart. Chart 1.6.0 змінює типовий образ на Server 3.8.0, якому на кожному бекенді потрібне [оновлення схеми](#native-schema-upgrade-3-8): масштабуйте Server до нуля, зробіть резервну копію бази й виконайте `helm upgrade` з `native.schemaUpgrade.enabled=true` (або ручний Job), а потім масштабуйте назад. Повернення до chart 1.5.0 означає відновлення цієї копії. Chart закріплює образ за тегом. Для встановлень із контролем змін також задайте `image.digest` рівним мультиархітектурному індексу 3.8.0, `sha256:7988a23525d9e50e997a9f6f02e801300ed4f626de3cf6977033657ae7e9f58e`, до якого розв’язуються і `durableworkflow/server:3.8.0`, і `ghcr.io/durable-workflow/server:3.8.0`. Див. [примітки до Chart 1.6.0 / Server 3.8.0](%%artifact.helmChartUpgradeUrl%%#chart-160--server-380-native) у chart.

### Вибір випуску чарту {#helm-chart-selection}

Кожен випуск чарту записує образ Server, з яким його перевіряли, у `appVersion` файлу `Chart.yaml`; номери версій чарту й Server незалежні. Вибрана [сумісна комбінація](./compatibility.md#last-qualified-reproducible-tuple) поєднує чарт **%%artifact.helmChartVersion%%** із Server **%%artifact.helmChartAppVersion%%**, використовуючи ті самі метадані випусків, що й таблиця та команда встановлення. [Підтвердження опублікованих OCI/package](%%artifact.helmChartQualificationUrl%%) перевіряє цю пару, а не нове встановлення Kubernetes.

Для іншої версії Server перевірте `Chart.yaml` потрібного опублікованого чарту ([джерело вибраного чарту](%%artifact.helmChartSourceUrl%%) є прикладом) й виберіть точну версію, чий `appVersion` відповідає потрібному Server. Прочитайте [нотатки UPGRADING](%%artifact.helmChartUpgradeUrl%%) вибраного випуску для кожної версії чарту, через яку переходите. Не виводьте версію чарту з версії Server і не вибирайте неопублікований чарт із поточного джерела.

Перевизначення `image.tag` змінює образ, але не записаний `appVersion` чарту. Це власна комбінація чарту й образу, доки вона не пройде перевірку згенерованих маніфестів, bootstrap, rollout і runtime. Включайте звичайні резервні копії бази та межі відкату до плану оновлення; саме успішне генерування маніфестів не доводить працездатність розгортання.

В опублікованій історії є виняток: чарт 0.2.2 перейшов на нову мінорну версію Server під patch-номером чарту. Пізніше [опубліковане виправлення пояснення](https://github.com/durable-workflow/server/blob/2.11.0/k8s/helm/durable-workflow/docs/UPGRADING.md#chart-022--server-210) визнає цей виняток і повертає заявлену політику мінорних версій. Історичні версії незмінні; ця примітка не вибирає новішу комбінацію Server/чарту.

## Маніфести Kubernetes {#kubernetes-manifests}

Репозиторій Server містить маніфести без обгортки в
[`k8s/`](https://github.com/durable-workflow/server/tree/main/k8s) для команд,
які вже обслуговують Kubernetes. Вони описують форму PHP 2.x; для нативного
Server використовуйте нативний режим чарта Helm або адаптуйте його єдиний
Deployment Server:

- Namespace і спільні мітки
- Поділ ConfigMap і Secret
- Job початкового налаштування й міграцій
- Deployment і Service API
- Deployment worker
- CronJob планувальника
- PodDisruptionBudget
- Перевірки працездатності `/api/health` і готовності `/api/ready`
- Обережні запити й обмеження ресурсів

Перед застосуванням маніфестів замініть тег образу на конкретну опубліковану
версію чи дайджест, надайте справжні облікові дані бази й Redis та підключіть
значення ConfigMap до служб вашого кластера. Маніфести навмисно відкриті для
перевірки: вони не є чартом Helm і не обіцяють універсальної поведінки
керованого Kubernetes.

Для виробничого розгортання Kubernetes перевірте щонайменше:

```bash
kubectl -n durable-workflow wait --for=condition=complete job/durable-workflow-migrate --timeout=180s
kubectl -n durable-workflow rollout status deploy/durable-workflow-server
kubectl -n durable-workflow rollout status deploy/durable-workflow-worker
kubectl -n durable-workflow port-forward svc/durable-workflow-server 8080:8080
curl http://localhost:8080/api/ready
curl -H "Authorization: Bearer $DW_ADMIN_TOKEN" http://localhost:8080/api/cluster/info
```

Висока доступність в одному регіоні — перемикання керованої бази й Redis,
втрата вузла API чи worker та перезапуск планувальника — на шляху маніфестів
потребує підтримки так само, як і в невеликому кластері, доки перевірка випуску
не пройдена. Передбачений контракт вимагає правил готовності, єдиного
планувальника та спільної основи з [контракту одного регіону](#single-region-high-availability-and-failover).
Балансувальники провайдера, класи сховищ, мережеві політики, кілька активних
регіонів та автономне регіональне перемикання власного середовища потребують
підтримки або відстежуються окремо від контракту маніфестів. Для встановлення
й оновлень під керуванням Helm використовуйте окремо версійований шлях вище.

## Запуск SDK workers у Kubernetes {#sdk-workers-on-kubernetes}

Розгортайте workers вашого застосунку окремо від Server, а в PHP 2.x — і від його Laravel queue worker. Зберіть образ із зареєстрованими обробниками PHP, Python або Rust і зафіксованими залежностями SDK. Використовуйте entrypoint у формі exec, щоб процес worker отримував `SIGTERM`. Замініть наведений образ незмінним digest цієї збірки.

Для workers у тому самому кластері використовуйте фактичні назву, namespace і порт Service сервера. Сирі маніфести надають `http://durable-workflow-server.durable-workflow.svc.cluster.local:8080`. Випуск Helm може мати іншу назву Service. Workers поза кластером потребують доступної HTTPS-адреси ingress або балансувальника з нормальною перевіркою сертифіката. Узгодьте бюджети long poll і транспорту з [рекомендаціями щодо таймаутів](#worker-long-poll-timeout-budgets).

Створіть Secret у Kubernetes namespace Pod worker, використовуючи наявні облікові дані worker. Не додавайте токен до маніфесту чи образу. Namespace сервера — окрема межа продукту, відмінна від namespace Kubernetes.

```bash
kubectl -n durable-workflow create secret generic orders-worker-auth --from-literal=token="$DW_WORKER_TOKEN"
```

Збережіть це як `orders-worker.yaml`. Ці назви змінних середовища є конфігурацією застосунку: entrypoint має передати їх клієнту SDK і Worker. Надайте кожному одночасно активному процесу власний worker ID і зареєструйте обробники для налаштованої черги.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-worker
  namespace: durable-workflow
spec:
  replicas: 2
  selector:
    matchLabels:
      app: orders-worker
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: orders-worker
    spec:
      automountServiceAccountToken: false
      terminationGracePeriodSeconds: 75
      containers:
        - name: worker
          image: registry.example.com/acme/orders-worker:release-id
          env:
            - name: DW_SERVER_URL
              value: http://durable-workflow-server.durable-workflow.svc.cluster.local:8080
            - name: DW_NAMESPACE
              value: default
            - name: DW_TASK_QUEUE
              value: orders
            - name: DW_WORKER_ID
              valueFrom:
                fieldRef:
                  fieldPath: metadata.uid
            - name: DW_WORKER_TOKEN
              valueFrom:
                secretKeyRef:
                  name: orders-worker-auth
                  key: token
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: "1"
              memory: 512Mi
```

Застосуйте Deployment і перевірте його розгортання:

```bash
kubectl apply -f orders-worker.yaml
kubectl -n durable-workflow rollout status deployment/orders-worker
```

Кількість реплік і ресурси — початкові приклади, а не гарантії місткості. Налаштуйте їх за фактичною тривалістю завдань, використанням пам’яті, лімітами залежних сервісів і [бюджетами допуску worker](./polyglot/task-queue-admission.md). Доступність Deployment не доводить реєстрацію SDK чи корисну роботу. Перевірте свіжі реєстрації workers та очікувані збірку й чергу, потім запустіть і завершіть показовий workflow. Запуск у Kubernetes сам собою не створює HTTP endpoint здоров’я для SDK worker. Використовуйте probe застосунку, якщо він існує, і не використовуйте здоров’я сервера як liveness-перевірку worker.

### Передавання SIGTERM і очікування очищення {#sdk-worker-pod-shutdown}

| SDK | Завершення процесу worker |
| --- | --- |
| PHP | Використовуйте керований цикл `Worker::run()` зі встановленим `pcntl`. Його signal handler запитує завершення, після чого активне синхронне завдання доходить до межі перед керованим очищенням і зняттям реєстрації. Власний цикл навколо `tick()` не надає цього lifecycle. Див. [коректне завершення PHP](https://php.durable-workflow.com/operate/graceful-shutdown/). |
| Python | Під’єднайте `SIGTERM` до шляху завершення того самого Worker та дочекайтеся і `Worker.stop()`, і його run task. Явно задайте `shutdown_timeout`. Прийняті завдання поділяють цей deadline спорожнення. Скасування await не може примусово зупинити активний синхронний потік, а непідтверджена зупинка залишається помилкою. Використовуйте [приклад окремих процесів і signal wiring](https://python.durable-workflow.com/guides/separate-workers/) та [контракт lifecycle](https://python.durable-workflow.com/reference/worker/). |
| Rust | Передайте до `Worker::run_until(...)` future, який завершується за Unix `SIGTERM`, і дочекайтеся результату. Future лише для Ctrl-C не обробляє signal завершення Pod. Асинхронні обробники мають віддавати керування, а блокувальну роботу потрібно обмежувати окремо. Див. [Worker::run_until](https://rust.durable-workflow.com/durable_workflow/struct.Worker.html#method.run_until). |

Виділіть у `terminationGracePeriodSeconds` достатньо часу для poll, завершення прийнятих завдань і очищення HTTP/session/реєстрації у встановленому SDK. Приклад із 75 секундами потрібно звірити з фактичними межами вашого застосунку. Kubernetes зараховує будь-який hook `preStop` у той самий пільговий період і примусово зупиняє процеси, що залишилися після його спливу. Hook лише зі sleep не просить SDK спорожнити роботу й не подовжує його deadline. Див. [процес завершення Pod у Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination-flow).

Відрепетируйте завершення під час простою й обмеженої за часом роботи. Вважайте помилки очищення, збережену реєстрацію або примусове завершення неповним вимкненням. Worker на заміну продовжує durable-роботу за її записаними leases, retries і deadlines. Зупинка Pod не скасовує workflow і не відкочує зовнішній побічний ефект. Перед зміною збірок дотримуйтеся [розгортання за build ID worker](./polyglot/worker-build-id-rollout.md) і зберігайте його перевірки сумісності, replay та rollback.

## Висока доступність і перемикання в одному регіоні {#single-region-high-availability-and-failover}

Висока доступність і перемикання в одному регіоні наразі є **неперевіреним
кандидатом контракту за участю підтримки** поверх невеликого кластера та
маніфестів Kubernetes. Він охоплює режими відмов, які рушій розрахований
витримати **всередині одного регіону**: перемикання керованої бази (RDS
Multi-AZ, перемикання кластера Aurora, Cloud SQL HA, підвищення Patroni тощо),
керованого Redis (Sentinel, перемикання групи реплікації Elasticache,
Memorystore HA тощо), втрату вузла API чи worker та перезапуск процесу
планувальника й обслуговування. Міжрегіональне відновлення з активним і
резервним регіонами є окремим оцінюванням за участю підтримки; дивіться
[наступний розділ](#activepassive-multi-region).

Передбачений контракт — поведінка рушія, правила готовності, цілі відновлення
за подіями, запобігання роздвоєнню керування та приймальна репетиція —
зберігається в бібліотеці workflow у
[`docs/deployment/ha-failover.md`](https://github.com/durable-workflow/workflow/blob/main/docs/deployment/ha-failover.md)
та в окремому Server у
[`docs/ha-failover-validation.md`](https://github.com/durable-workflow/server/blob/main/docs/ha-failover-validation.md).
Цей розділ є публічним викладом цих документів.

### Стан підтвердження випуску {#release-evidence-status}

Для жодного публічного випуску Server немає посилання на успішний результат
точного випуску. Кандидатну топологію, програму перевірки й межі відновлення
нижче написано для PHP Server 2.x (спільний Redis, worker черги та єдиний
планувальник). Записана спроба опублікованого образу PHP зупинилася під час
`topology_start`, очікуючи готовності API, перш ніж можна було підтвердити
матрицю відмов або межі відновлення. Для нативного Server 3.x програму
перевірки перемикання не опубліковано, а його `GET /api/cluster/info` повідомляє
`single_region_failover_contract: false`. Наявність програми перевірки,
її маніфесту сценаріїв або репетиція конкретного розгортання не доводять
проходження повної матриці опублікованим образом. Тому висока доступність
в одному регіоні залишається шляхом за участю підтримки.

Самостійні формулювання дозволені лише після запуску без вихідного коду,
який використовує точний документований випуск Server для образу, програми
перевірки й топології Compose та публікує `single-region-failover-result.json`
з `outcome: "pass"`, `runner_blocked: false`, `status: "pass"` кожного запису
`phase_outcomes`, успішними вердиктами всіх меж відновлення та підтвердженням
кожного обов’язкового сценарію з публічного
[маніфесту перемикання в одному регіоні](/platform-conformance/single-region-failover-scenarios.json).
Посилання на цей публічний успішний результат має бути в цьому розділі й
називати той самий образ Server, що й `%%artifact.serverDockerHubImage%%`.
До виконання всіх умов наведені нижче межі відновлення є цілями оцінювання,
а не твердженнями про перевірений опублікований образ.

### Кандидат топології {#candidate-topology}

Передбачений контракт високої доступності діє, коли розгортання відповідає
невеликому кластеру чи маніфестам без обгортки та оператор зберігає три правила:

- **Завжди одна кінцева точка запису бази workflow.** Кероване перемикання
  (RDS Multi-AZ, перемикання кластера Aurora, Cloud SQL HA, Patroni тощо)
  дозволене, якщо попередній основний вузол ізольовано до повторного
  підключення: відкликано користувача запису, увімкнено `read_only=on`,
  розірвано реплікацію або відновлено відомий справний знімок. Проксі має
  зберігати потрібну Server семантику бази та пройти перевірку точної версії,
  режиму й налаштувань. Вимоги до версій і перевірені режими пулу транзакцій PgBouncer
  наведено в [бюджетах SQL-з’єднань](#sql-connection-budgets).
- **Одна кінцева точка Redis одночасно із задокументованим підвищенням
  резервного вузла.** Кероване перемикання Redis (Sentinel, перемикання групи
  реплікації Elasticache, Memorystore HA тощо) дозволене. Redis — шар
  прискорення, а не основа коректності, тому його перемикання є подією
  затримки, а не зміною коректності.
- **Завжди один процес планувальника й обслуговування.** Оркестратор
  (служба Compose з `deploy.replicas: 1`, модуль systemd з орендою на рівні
  хоста або Kubernetes `Deployment` з `replicas: 1` та
  `RollingUpdate.maxSurge: 0`) відповідає за збереження єдиного екземпляра
  під час перезапуску. Дублікати планувальника як стала топологія не входять
  до цього контракту.

### Поведінка й цілі відновлення за подіями {#per-event-behavior-and-recovery-targets}

Передбачений контракт рушія визначає обмежені цілі відновлення для кожного
класу подій. Це не гарантії опублікованого образу, доки перевірка випуску не
пройдена. Фактичний час відновлення, який бачить оператор, дорівнює цілі рушія
плюс час підвищення резервного вузла самого керованого сервісу.

| Подія | Передбачена поведінка рушія | Ціль відновлення після повернення основи чи процесу |
| --- | --- | --- |
| Перемикання керованої бази | Запис повертає помилки й не буферизується приховано. Читання повертає помилки. `/api/ready` не проходить на всіх вузлах API й планувальнику. Підтверджена робота не втрачається. | Одне перепідключення пулу з’єднань, один інтервал `task_repair` (типово 3 с) та один тайм-аут довгого опитування (типово 30 с, максимум 60 с) для активних опитувачів |
| Перемикання керованого Redis | Втрата сигналів пробудження переводить виявлення на тайм-аут довгого опитування. Перевірки шару прискорення переходять у стан **попередження**, а не помилки. `/api/ready` зазвичай залишається успішним. | Інтервал перепідключення клієнта Redis |
| Втрата вузла API (1 з N) | Балансувальник прибирає несправний вузол у межах свого інтервалу перевірки готовності. Активні запити до нього завершуються помилкою на балансувальнику, і клієнт повторює їх. | Інтервал перевірки готовності балансувальника, який задає оператор; типово 5–10 с |
| Втрата worker | Завдання несправного worker чекають до завершення оренди. Інші worker продовжують отримувати свої завдання. | Завершення оренди (5 хв для завдань activity) плюс один інтервал `task_repair` |
| Перезапуск планувальника й обслуговування | Запуски розкладів, застосування тайм-аутів activity та очищення історії призупиняються. Усі три відновлюються на наступному такті після перезапуску. Повторних запусків немає, оскільки процес єдиний. | Час перезапуску оркестратора плюс один такт планувальника |

### Правила балансувальника, готовності й переведення трафіку {#load-balancer-readiness-and-traffic-shift-rules}

Балансувальник перед вузлами API є єдиною точкою рішення про приймання
трафіку під час перемикання:

- Підключіть балансувальник до **`GET /api/ready`**, а не лише `/api/health`.
  `/api/health` лише доводить, що процес обслуговує HTTP; `/api/ready`
  повідомляє про з’єднання з базою й налаштовані перевірки готовності, зокрема
  чи прискорення пробудження Redis справне або погіршене. Він не перевіряє всі
  SQL-операції workflow чи доступну потужність запису. Під час відмови бази `/api/ready` правильно
  не проходить на всіх вузлах. Балансувальник МАЄ приймати стан повної
  недоступності, а не повертатися до застарілого «останнього справного» списку.
- Задайте інтервал перевірки 5–10 секунд і поріг видалення у 2–3
  послідовні невдалі перевірки.
- Не вимагайте закріплених сеансів: базова перевірка невеликого кластера
  доводить, що зовнішній worker може опитати `server-a` і завершити на `server-b`.
- За перемикання лише Redis готовність залишається успішною на кожному вузлі,
  поки доступні стійкі шляхи на основі бази. Погіршення шару прискорення
  відображається як `checks.cache.status=warning` із
  `checks.cache.degraded_capability=long_poll_wake_acceleration`; не
  налаштовуйте балансувальник на видалення вузлів через це попередження.

Після відновлення основи рекомендовано дочекатися HTTP 200 від `/api/ready`
хоча б одного вузла, запитати `/api/cluster/info` через балансувальник з
адміністративним токеном для перевірки маніфесту топології, виконати
`POST /api/worker/register` для перевірочного worker через збалансовану
кінцеву точку, переконатися в наявності рівно одного процесу планувальника
в оркестраторі та відновити зовнішній трафік.

### Репетиція точного артефакту {#run-the-exact-artifact-rehearsal}

Випуски PHP Server 2.x містять багаторазову базову репетицію повної матриці
відмов без збирання продукту з робочої копії. Її топологія Compose запускає
ролі лише для PHP (Job початкового налаштування, worker черги та планувальник),
тому з нативним образом 3.x вона не працює. Приклад нижче використовує
останній випуск PHP, 2.11.8. Програма перевірки й топологія Compose
мають походити з того самого тегу випуску, що й образ Server; не поєднуйте
мінливу стандартну гілку з довільним образом. На чистому хості з Docker
Engine, Docker Compose v2, Python 3.11 або новішим і доступом до публічних
реєстрів виконайте:

<!-- docs-example id="single-region-failover-exact-release" -->
```bash
export DW_SERVER_RELEASE=2.11.8
git clone --depth 1 --single-branch --branch "$DW_SERVER_RELEASE" \
  https://github.com/durable-workflow/server.git "server-$DW_SERVER_RELEASE"
cd "server-$DW_SERVER_RELEASE"
export DW_SERVER_IMAGE="durableworkflow/server:$DW_SERVER_RELEASE"
scripts/conformance/single-region-failover-published-artifacts.sh \
  --result-dir ./failover-result
```

Цей шлях навмисно визначає робочу копію та `DW_SERVER_IMAGE` за однією
змінною випуску. Не перевизначайте образ незалежно; оберіть інший випуск,
змінивши `DW_SERVER_RELEASE` до клонування. Програма вимагає конкретного
публічного тегу чи дайджесту Server, завантажує всі допоміжні образи,
визначає дайджести репозиторіїв усіх образів виконання й відхиляє секції
збирання Compose, монтування вихідного коду продукту та локальні або рухомі
посилання на Server. Вона запускає рівно два вузли API за однією кінцевою
точкою nginx, одну базу MySQL, один Redis і один процес планувальника й обслуговування.

Отриманий `single-region-failover-result.json` використовує схему
`durable-workflow.v2.single-region-failover.result`. Він записує точні версії
артефактів та інструментів, нормалізовану топологію, переходи готовності,
виміряні часи відновлення й вердикти меж, ідентичності workflow, запусків,
завдань і розкладів, а також перевірки дублікатів і втрат для завершення
між вузлами, втрати API, переривань бази й Redis, втрати оренди worker та
перезапуску єдиного планувальника. Зовнішні програми знаходять виклик і
публічний маніфест сценаріїв через `single_region_failover_contract`
у відповіді `GET /api/cluster/info`.

Результат підтверджує видимі рушію переривання й відновлення опублікованого
образу лише після проходження вимог випуску вище. Невдалий, частковий або
заблокований програмою результат є діагностикою, а не перевіркою. Навіть
успішна базова перевірка не перетворює перезапуск локального контейнера
MySQL чи Redis на підтвердження механізму підвищення резервного вузла
хмарного провайдера. Зберігайте підтвердження підвищення засобами провайдера,
ізоляції старого вузла, RPO та фактичного часу поруч із базовим результатом,
перш ніж заявляти про високу доступність керованого сервісу.

### Доповнення комплекту відновлення {#recovery-packet-additions}

Невеликий кластер чи розгортання маніфестів, яке заявляє цей контракт,
МАЄ доповнити комплект відновлення за
[операторськими межами експлуатації](/docs/operator-operating-envelope)
підтвердженнями репетицій кожного класу подій:

- перемикання керованої бази без втрати підтверджених записів та в межах
  зазначеного вище часу відновлення;
- перемикання керованого Redis без коливань списку вузлів балансувальника,
  без втрати підтвердженої роботи та з `checks.cache.status=warning` і
  `long_poll_wake_acceleration` як погіршеною можливістю;
- втрата вузла API, яку балансувальник поглинає в налаштованому інтервалі
  перевірки готовності без втрати підтверджених записів;
- втрата worker зі збереженням стійкого запуску до завершення оренди,
  повторним отриманням у налаштованій межі відновлення та рівно одним завершенням;
- перезапуск планувальника на іншому хості без дублікатів розкладів і без
  розкладу, який залишився неоціненим після `next_fire_at` плюс один такт.

Доки перевірка випуску не пройдена, кожне розгортання потребує участі
підтримки, навіть якщо його власна репетиція успішна. Після публічного
успішного результату всіх фаз розгортання стає самостійним за цим контрактом
лише після запису репетиції конкретного середовища в комплект відновлення
оператора та її оновлення з періодичністю, яку визначають операторські межі експлуатації.

### Межа непідтримуваних тверджень про високу доступність {#boundary-against-unsupported-ha-claims}

Контракт високої доступності в одному регіоні навмисно вузький. Наведене
нижче залишається **поза** ним і потребує проєктування за участю підтримки,
оскільки сама топологія є частиною ризику продукту:

- топології бази з кількома активними вузлами запису;
- кілька регіонів з активним і резервним регіонами та автоматичне чи
  автономне регіональне перемикання власних топологій
  ([наступний розділ](#activepassive-multi-region) містить оцінювальні настанови);
- синхронна міжрегіональна реплікація бази (RPO=0);
- дублікати процесів планувальника й обслуговування як стала топологія;
- прив’язані до регіону черги завдань як вісь маршрутизації, яку забезпечує рушій;
- перевірка керованого Kubernetes провайдера поза контрактом пакування чарта;
- широкі SLA «п’ять дев’яток» чи «без простою» поза наведеними межами відновлення.

Контракт визначає *обмежене відновлення під час названих подій*, а не обіцянку
доступності, що залежить від вибору оператором бази, мережі й оркестратора.
Маркетингові чи SLA-твердження для власних розгортань НЕ МОЖУТЬ переходити
цю межу без окремої перевірки.

## Активний і резервний регіони {#activepassive-multi-region}

Кілька регіонів з активним і резервним регіонами — **оцінювальний посібник за
участю підтримки**, а не доведений самостійний контракт підтримуваних меж
експлуатації 2.0. Використовуйте цей розділ для перевірки кандидата
архітектури й репетиції конкретного середовища з підтримкою до виробничого
використання. Кожен регіон починається з документованого одновузлового,
невеликого кластерного шляху чи маніфестів Kubernetes, але ці однорегіональні
контракти не встановлюють міжрегіональної реплікації, перемикання, повернення,
RPO, RTO чи поведінки за роздвоєння керування. Глибші матеріали — повноваження
даних, припущення реплікації, поведінка просторів імен, черг і worker,
інструкції перемикання й повернення, ізоляція старого вузла та компроміси
узгодженості й затримки — зберігаються в бібліотеці workflow у
[`docs/deployment/multi-region.md`](https://github.com/durable-workflow/workflow/blob/main/docs/deployment/multi-region.md)
та в окремому Server у
[`docs/multi-region-validation.md`](https://github.com/durable-workflow/server/blob/main/docs/multi-region-validation.md).
Ці матеріали й кандидат архітектури нижче написано для топології PHP 2.x.
Нативний Server 3.x не має Redis чи окремого планувальника, а нативної
міжрегіональної репетиції не опубліковано.

Кандидат архітектури для оцінювання:

- Один **активний регіон** із перевіреним одновузловим чи невеликим кластерним
  контрактом: контейнери API за балансувальником, спільна зовнішня MySQL або
  PostgreSQL як стійка база для запису, спільний Redis, рівно один процес
  планувальника й обслуговування та зовнішні worker.
- Один **резервний регіон** з асинхронно реплікованою резервною базою workflow,
  необов’язковим резервним Redis, без процесу планувальника й обслуговування
  та з нулем або більшою кількістю підготовлених контейнерів API/worker,
  які простоюють до підвищення.
- **Регіональне перемикання** — явна робота оператора: зупинити трафік запису
  до несправного регіону, звірити реплікацію з опублікованим RPO, підвищити
  резервну базу, виконати потрібні випуску міграції нового основного вузла,
  запустити єдиний процес планувальника й обслуговування в новому активному
  регіоні, змінити кінцеві точки worker, перевести зовнішній трафік та
  відновити похідні проєкції. Автоматичного міжрегіонального переходу немає.
- **Повернення** виконує ту саму послідовність у зворотному порядку після
  відновлення початкового регіону. Відновлений основний вузол потрібно
  ізолювати до підключення як резервного: відкликати користувача запису,
  увімкнути `read_only=on`, розірвати реплікацію або відновити відомий справний знімок.

Повноваження даних і припущення реплікації:

- База workflow — єдине стійке джерело істини, прив’язане до регіону:
  у будь-який момент записує рівно один регіон. База резервного регіону є
  реплікою лише для читання до підвищення. Цільова точка відновлення (RPO)
  дорівнює затримці асинхронної реплікації, а цільовий час відновлення (RTO) —
  часу виконання операційного посібника оператором.
- Redis — локальне прискорення регіону. Сигнали пробудження, блокування черг
  query та приймання не передаються між регіонами; не очікуйте цього. Кожен
  регіон запускає власний Redis; кеш резервного може бути холодним або
  прогрітим за рішенням оператора, і коректність не залежить від його
  збереження під час перемикання.
- Видимість обслуговує база активного регіону. Спочатку підвищення, потім читання.

Поведінка просторів імен, черг завдань та реєстрації worker:

- Простори імен і черги завдань зберігаються в базі workflow та переживають
  підвищення точно в стані останньої реплікованої транзакції. Рушій не
  поділяє їх за регіонами.
- Worker нового активного регіону реєструються на локальній кінцевій точці
  API після підвищення. Попередні реєстрації несправного регіону залишаються
  в базі та втрачають чинність через звичайний механізм завершення реєстрації worker.
- Розгортання за ідентифікатором збірки та стан життєвого циклу розгортання
  переживають перемикання, оскільки зберігаються в базі workflow.

Компроміси узгодженості й затримки у сталому стані:

- Запуски workflow, signal та update фіксуються в базі активного регіону.
  Їхня затримка дорівнює затримці фіксації цього регіону. Вони відхиляються,
  поки повноваження відкликаються під час перемикання.
- Доставка завдань workflow та activity дотримується контракту прискорення
  активного регіону: менше секунди за справного Redis, інакше — стійкий
  інтервал опитування.
- Розклади запускає єдиний планувальник активного регіону. Вони
  призупиняються, поки він не працює, і відновлюються зі стійких записів
  розкладів після підвищення.
- Читання після запису узгоджене лише всередині активного регіону; рушій
  не надає міжрегіонального читання власних записів або RPO=0.

Межа аварійного відновлення явна: кандидат архітектури не замінює резервні
копії чи підтвердження. Комплект відновлення за
[операторськими межами експлуатації](/docs/operator-operating-envelope)
залишається обов’язковим. Доповніть його SLO відставання реплікації, часом
виконання інструкцій підвищення, датою останньої успішної репетиції перемикання
та процедурою ізоляції відновленого основного вузла.

Для власних розгортань активний і резервний або кілька активних регіонів,
автоматичне регіональне перемикання, синхронна міжрегіональна реплікація
(RPO=0), активна міжрегіональна видимість і прив’язані до регіону черги як
вісь маршрутизації рушія залишаються [шляхами за участю підтримки](/docs/support),
оскільки топологія є частиною ризику продукту. Поточний
[контракт керованого середовища Cloud](/docs/polyglot/cloud-control-plane)
однорегіональний і не надає цих міжрегіональних гарантій.

## Контракт готовності {#readiness-contract}

Використовуйте перевірки і працездатності, і готовності:

- `GET /api/health` доводить, що процес обслуговує HTTP.
- `GET /api/ready` повідомляє результати налаштованих перевірок залежностей,
  зокрема з’єднання з базою, міграцій і готовності типового простору імен.
  Він не доводить працездатності всіх SQL-операцій workflow чи запасу для запису.
- `GET /api/cluster/info` доводить, що автентифікований клієнт може виявити
  ідентичність збірки, протокол площини керування, протокол worker, кодеки
  payload та можливості Server.
- `POST /api/worker/register` доводить, що worker можуть автентифікуватися
  в очікуваних просторі імен і черзі завдань.

Не переводьте трафік лише на основі `/api/health`.

# Очищення workflow {#pruning-workflows}

Workflow v2 розділяє дві окремі операції життєвого циклу:

1. **Архівування** позначає запуск у кінцевому стані як архівований, щоб
   виключити його з оглядів активних запусків. Архівування **не** видаляє рядків.
2. **Очищення** видаляє дозволені політикою деталі чи осиротілі проєкції.
   Embedded API вимагає кінцевого стану, часу закриття та перевіряє утримання.
   Політику зберігання визначає хост; архівування не є вимогою цього API.

Server має окрему політику зберігання namespace: автоматичне очищення пропускає
архівовані запуски. Архівування захищає запуск від цього очищення й не є
підготовчим кроком для автоматичного видалення.

## Зберігання історії довше за строк у базі даних {#keeping-history-beyond-database-retention}

Перш ніж увімкнути очищення, визначте, де зберігатиметься потрібна історія:

| Вимога | Варіант | Наслідки для обсягу та очищення |
| --- | --- | --- |
| Зберігати недавню історію в Server | Bounded-політика namespace від 1 до 365 днів | Дозволені політикою закриті запуски можуть бути очищені після межі. Для довшого зберігання експортуйте раніше. |
| Зберігати всю історію namespace у Server | Режим `forever` | Історія залишається в основній базі, доки ви явно не повернете bounded-політику. |
| Зберегти окремі закриті запуски Server | Архівувати їх | Автоматичні й явні проходи retention Server пропускають ці запуски. Опублікований API не скасовує архівування, тому не використовуйте його як тимчасове блокування для експорту. |
| Зберігати довший незалежний запис | Експортувати кожен закритий запуск і зберегти зовнішні об'єкти даних | Застосунок відповідає за розклад, перевірку, контроль доступу й остаточне видалення копії. Вбудованого безперервного експортера історії немає. |

`forever` та архівування залишають рядки в базі, а не переносять їх у дешевше
сховище. Плануйте обсяг історії й даних, індексів, резервних копій та час
відновлення. Очищення залишає рядки запуску й instance, зокрема кореневі поля
даних. Їхній обсяг не стає нульовим. Експорт історії допомагає replay та
дослідженню, але не є повною резервною копією бази й не гарантує відновлення
виконання лише з цього файлу.

### Експорт перед очищенням {#export-before-pruning}

Використовуйте спільну процедуру для retention-завдання embedded-застосунку
та namespace Server. Відбір і повноваження на очищення відрізняються, як описано нижче.

Приклади перевірено з опублікованим PHP Server **2.9.5**, завантаженим Workflow **2.6.2** і звичайно встановленим Python SDK **2.6.1**. [Перевірка опублікованих артефактів](https://github.com/durable-workflow/durable-workflow.github.io/issues/276#issuecomment-6285271861) охоплювала посторінковий відбір за часом закриття, експорт окремих запусків, контрольні суми та структурну перевірку, утримання через архівування/`forever` і фактичне очищення через `pruneRun()`. Вона не підтверджує повний replay застосунку чи відновлення зовнішніх об’єктів.

1. **Забезпечте безпечний проміжок.** Запускайте експортер завчасно, залишаючи
   час на повтори, збої та чергу перевірки. Щоденний експорт за 30-денного
   зберігання дає більше часу для відновлення, ніж перший запуск на 30-й день.
   Перед першим експортом чи скороченням строку тимчасово захистіть джерело:
   призупиніть embedded-очищення або ввімкніть `forever` у Server. Запишіть
   попередню політику й повертайте її лише після перевірки. Очищення може
   початися одразу після досягнення межі.
2. **Створіть перелік закритих запусків.** Зафіксуйте верхню межу UTC та
   виберіть `closed_at` раніше за неї. Експортуйте кожен запуск, включно з
   невдалими, скасованими, примусово завершеними й попередниками continue-as-new.
   Один instance workflow може мати кілька запусків. Зберігайте namespace,
   instance id, run id і час закриття кожного кандидата та проходьте всі сторінки.
3. **Експортуйте конкретний запуск.** Використовуйте маршрут чи команду з run id
   нижче, а не поточний на час виконання завдання запуск. Відокремлюйте нові
   кандидати від уже перевірених копій.
4. **Перевірте збережену копію.** Прочитайте її з місця призначення. Звірте
   ідентичність запуску з переліком відповідного namespace, версію схеми,
   очікуваний кінцевий sequence, повний діапазон подій, політику приховування
   та контрольну суму. Налаштований підпис перевіряйте довіреним ключем.
   Зберігайте точну збірку застосунку й codecs для cold replay. Контрольна сума
   доводить збіг байтів, а не повноту історії на момент експорту.
5. **Збережіть зовнішні байти.** Експорти містять envelopes посилань, а не
   незалежні копії кожного зовнішнього об'єкта. Зберігайте байти протягом
   строку життя експорту й перевіряйте їх без прогрітого кешу runtime.
   Дотримуйтеся [життєвого циклу зовнішніх даних](../features/external-payload-storage.md#replay-retention-and-cleanup).
6. **Звірте перед очищенням.** Порівнюйте перелік закритих запусків із
   перевіреними записами сховища. Сповіщайте про відсутні run id, помилки
   перевірки та чергу, що наближається до межі зберігання. Пересувайте контрольну
   точку лише після обліку всіх кандидатів. Повторно скануйте проміжки часу
   закриття з перекриттям, усуваючи дублікати за namespace і run id. Не
   перезаписуйте перевірений повний bundle пізнішим неповним експортом.

Цими кроками керує застосунок; це не підтримувана операція створення самодостатнього архіву. [Server #520](https://github.com/durable-workflow/server/issues/520) відстежує відсутню продуктову процедуру копіювання, утримання та холодної перевірки всіх потрібних зовнішніх байтів. Успішний експорт лише посилань або ручна перевірка контрольної суми не виконують цієї вимоги.

:::warning Очищення незворотне без копії для відновлення

Експорт після очищення не відновить видалених подій. Опублікована реалізація
може позначити очищений запуск у кінцевому стані як `history_complete: true`
та повторити попередній `dedupe_key`. Це відстежується у
[Workflow #856](https://github.com/durable-workflow/workflow/issues/856).
Жодне з цих полів не доводить, що очищення не відбулося. Embedded-експортер
має відмовляти для запусків із `details_pruned_at`. Список Server більше не
показує запуск після видалення його summary. Тому перелік, створений після
очищення, не доводить, що всі старі запуски збережені. Зберігайте перелік
до очищення та досліджуйте прогалини за копією для відновлення.

:::

### Відбір та експорт запусків Server {#selecting-and-exporting-server-runs}

Список workflow підтримує порівняння `CloseTime` у параметрі `query`.
Приклад вибирає фіксований напіввідкритий проміжок UTC:

```bash
curl --fail-with-body --get "$DURABLE_WORKFLOW_SERVER_URL/api/workflows" \
  -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  -H "X-Namespace: orders-prod" \
  -H "X-Durable-Workflow-Control-Plane-Version: 2" \
  --data-urlencode "query=CloseTime >= '2026-10-01T00:00:00Z' AND CloseTime < '2026-10-02T00:00:00Z'" \
  --data-urlencode "page_size=200"
```

Читайте `workflow_id`, `run_id` та `closed_at` кожного елемента `workflows`.
Повторюйте запит із `next_page_token`, доки відповідь не поверне
`next_page_token: null`. Не обмежуйтеся `status=completed`, бо це пропускає
невдалі та інші кінцеві результати. Не змінюйте часовий проміжок між сторінками
й не дозволяйте очищенню видаляти його summary під час збирання.

Для кожної вибраної пари експортуйте та збережіть bundle:

```bash
curl --fail-with-body "$DURABLE_WORKFLOW_SERVER_URL/api/workflows/$WORKFLOW_ID/runs/$RUN_ID/history/export" \
  -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  -H "X-Namespace: orders-prod" \
  -H "X-Durable-Workflow-Control-Plane-Version: 2" \
  --output "$RUN_ID.candidate.json"
```

[Політика retention Server](../polyglot/server.md#retention) визначає, коли
дозволено автоматичне очищення. Після перевірки всіх потрібних копій поверніть
заплановану bounded-політику. Оцініть місткість перед тривалим використанням
`forever` під час збою експорту. Архівовані запуски захищені незалежно від неї.

### Відбір та експорт embedded-запусків {#selecting-and-exporting-embedded-runs}

Вибирайте неочищені закриті запуски за `closed_at` через налаштовану модель
запуску. Запит створює перелік кандидатів, а не автоматичний експортер:

```php
use Workflow\V2\Models\WorkflowRun;
use Workflow\V2\Support\ConfiguredV2Models;

$runs = ConfiguredV2Models::query('run_model', WorkflowRun::class)
    ->whereNull('details_pruned_at')
    ->whereNotNull('closed_at')
    ->where('closed_at', '>=', $fromUtc)
    ->where('closed_at', '<', $untilUtc)
    ->orderBy('id')
    ->lazyById(100);

foreach ($runs as $run) {
    // Persist the candidate run id and close time in your export inventory.
}
```

Експортуйте кожен запуск зі звичайним bootstrap застосунку й конфігурацією сховища:

```bash
php artisan workflow:v2:history-export "$WORKFLOW_ID" --run-id="$RUN_ID" --output="$RUN_ID.candidate.json" --pretty
php artisan workflow:v2:replay-verify "$RUN_ID.candidate.json" --skip-replay --json
```

`--skip-replay` перевіряє цілісність і структуру без replay. Це не доводить
доступності зовнішніх байтів або експорту до очищення. Окремо перевірте
репрезентативний повний replay з потрібною збіркою застосунку. Завдання
очищення може викликати `pruneRun()` лише після виконання вимог retention та
експорту. Успішний експорт сам собою не дозволяє видалення.

## Архівування запусків у кінцевому стані {#archiving-terminal-runs}

Архівуйте завершений, невдалий, скасований чи примусово завершений запуск через
площину керування:

```php
use Workflow\V2\Contracts\WorkflowControlPlane;

$controlPlane = app(WorkflowControlPlane::class);

$result = $controlPlane->archive('order-12345', [
    'reason' => 'Retention period expired',
]);

if ($result['accepted']) {
    // Run's archived_at is now set; it disappears from active fleet views.
}
```

Та сама операція доступна через HTTP-маршрут площини керування. Архівувати можна
лише закриті запуски. Архівування вже архівованого запуску повертає `accepted`
із результатом `archive_not_needed`.

### Автоматизація архівування {#automating-archival}

Архівуйте запуски в кінцевому стані за розкладом: знаходьте завершені запуски
поза строком зберігання в таблиці стійких запусків і викликайте `archive()` для
кожного. Для простого правила за часом додайте подібний код до `routes/console.php`:

```php
use Illuminate\Support\Facades\Schedule;
use Workflow\V2\Models\WorkflowRun;
use Workflow\V2\Contracts\WorkflowControlPlane;

Schedule::call(function (WorkflowControlPlane $controlPlane): void {
    WorkflowRun::query()
        ->whereIn('status', ['completed', 'failed', 'cancelled', 'terminated'])
        ->whereNull('archived_at')
        ->where('closed_at', '<=', now()->subMonth())
        ->with('instance:id')
        ->chunkById(100, function ($runs) use ($controlPlane): void {
            foreach ($runs as $run) {
                $controlPlane->archive($run->instance->id, [
                    'reason' => 'retention_policy',
                ]);
            }
        });
})->daily();
```

## Очищення рядків проєкцій {#pruning-projection-rows}

Рядки проєкцій зведення запуску, очікування, часової шкали, timer та походження
можна відновити зі стійкої історії й команд. Використовуйте
`workflow:v2:rebuild-projections --prune-stale`, щоб видалити рядки проєкцій,
стійкий запуск яких більше не існує:

```bash
# Preview what would be pruned
php artisan workflow:v2:rebuild-projections --prune-stale --dry-run

# Actually prune stale projection rows
php artisan workflow:v2:rebuild-projections --prune-stale
```

## Очищення рядків стійкого стану {#pruning-durable-rows}

Після перевірки політики зберігання та потрібної копії експорту чи відновлення
embedded-хост може скористатися готовим API:

```php
use Workflow\V2\Support\WorkflowRunRetentionCleanup;

$report = WorkflowRunRetentionCleanup::pruneRun($runId);
```

`pruneRun()` блокує вибраний запуск і видаляє його деталі в одній транзакції.
Операція відмовляє для активного запуску, відсутнього часу закриття чи відкритої
відокремленої activity (`detached_activity_still_open`). Хост відповідає за
авторизований вибір запуску та строк зберігання. `retentionHoldReason($runId)`
дозволяє перевірити утримання activity; операція повторює перевірку перед видаленням.

Зберігайте `workflow_runs` і `workflow_instances`. Рядок запуску залишається
в кінцевому стані з `details_pruned_at`; повторне очищення не змінює першу мітку.
Початкові аргументи й результат залишаються в рядку запуску, тому окремо враховуйте
їхній обсяг. Відновлення проєкцій не повертає видалену історію. Експорт після
очищення також її не відновить; обмеження ознаки повноти експорту відстежується у
[Workflow #856](https://github.com/durable-workflow/workflow/issues/856).

Цей API видаляє деталі з бази даних. Зберіганням і видаленням зовнішніх об'єктів
керує хост, ураховуючи посилання з кореневих рядків, відокремлену роботу та
утримання резервних копій. Дотримуйтеся
[життєвого циклу зовнішніх даних](../features/external-payload-storage.md).
Перевірте експорт і потрібні зовнішні байти **до** очищення. Архівовані запуски
зі збереженими деталями залишаються доступними для дослідження інцидентів.

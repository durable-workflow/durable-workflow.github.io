# Помилки й відновлення {#failures-and-recovery}

Перед діагностикою помилки пам’ятайте основний контракт виконання:

- завдання workflow відновлюються через відтворення зафіксованої історії;
- activity виконуються щонайменше один раз і можуть спостерігатися повторно;
- спливання оренди й повторна доставка є звичайними шляхами відновлення
  та не доводять, що попередній worker не виконав побічний ефект.

Спочатку прочитайте [гарантії виконання й ідемпотентність](./constraints/execution-guarantees.md)
для точної семантики повторних спроб, повторної доставки та стійких
результатів.

## Обробка винятків {#handling-exceptions}

`Workflow\V2\Activity` типово має `$tries = 1`: одну спробу без автоматичного повторення після винятку. Перша помилка activity передається workflow. Код workflow може перехопити її, як у прикладі нижче. Якщо виняток не оброблено, запуск завершується помилкою й стає термінальним.

Повторні спроби потрібно явно налаштувати. Задайте `$tries` більше за `1`, щоб дозволити додаткові спроби, або `0` для необмеженої кількості, і виберіть політику `backoff()`. Помилка, яка допускає повторення, передається коду workflow лише після вичерпання налаштованого бюджету спроб або часу. Неповторювана помилка оминає решту повторних спроб.

```php
use Exception;
use Workflow\V2\Activity;

class MyActivity extends Activity
{
    public int $tries = 1;

    public function handle(): void
    {
        throw new Exception();
    }
}
```

```php
use Exception;
use function Workflow\V2\activity;
use Workflow\V2\Workflow;

class MyWorkflow extends Workflow
{
    public function handle(): void
    {
        try {
            $result = activity(MyActivity::class);
        } catch (Exception) {
            // handle the exception here
        }
    }
}
```

## Винятки без повторних спроб {#non-retryable-exceptions}

Деякі винятки не слід повторювати. Це винятки без повторних спроб (non-retryable).
Коли activity викидає такий виняток, workflow одразу позначає activity
невдалою та припиняє повторні спроби.

```php
use Workflow\V2\Activity;
use Workflow\Exceptions\NonRetryableException;

class MyNonRetryableActivity extends Activity
{
    public function handle(): void
    {
        throw new NonRetryableException('This is a non-retryable error');
    }
}
```

## Процес відновлення {#recovery-process}

Спочатку перевірте стійкий статус вибраного запуску й політику повторних спроб activity. За типової єдиної спроби необроблена помилка activity вже зробила запуск термінальним. Розгортання виправлення чи виклик `repair()` не відкриває цей невдалий запуск знову.

Виправлення коду під час очікування початкового запуску можливе, лише поки activity має допустиму повторну спробу. До планування activity задайте `$tries` більше за `1` або `0` для необмеженої кількості спроб і налаштуйте `backoff()`. За потреби задайте `ActivityOptions::$scheduleToCloseTimeout`, щоб обмежити загальну тривалість activity з усіма повторними спробами. Кінцеві терміни workflow залишаються чинними. Дивіться [Повторні спроби](./configuration/options.md#retries), [Затримка між спробами](./configuration/options.md#backoff) та [ActivityOptions](./configuration/options.md#activityoptions). Політика фіксується під час планування activity, тому подальше розгортання не розширює бюджет спроб чи часу наявної activity.

Для запуску, який досі очікує activity з можливістю повторної спроби:

1. Перевірте журнали невдалої activity та знайдіть помилки чи винятки.
2. Визначте джерело помилки й виправте код.
3. Розгорніть виправлення там, де працюють worker черги.
4. Перезапустіть або поступово замініть відповідні worker, щоб вони отримали новий код і безпечно забрали роботу.
5. Нехай справний worker виконає наступну допустиму спробу. Відновлення чи повторна доставка можуть відновити втрачений транспорт завдань, але не дають додаткової бізнес-спроби після закриття activity або запуску.
6. Перевірте стійкий результат у Waterline, експорті історії чи Server API. Один рядок журналу worker не визначає стійкий результат.
7. Якщо activity продовжує помилятися, перевірте залишок бюджету спроб і часу перед повторенням процесу.

Запуск із допустимою повторною спробою activity залишається в очікуванні й може продовжитися після успішного виконання виправленого коду, якщо початкові бюджети не спливли. Це не гарантує виправлення кожного workflow на місці: необроблена остаточна помилка activity, помилка коду workflow, структурне обмеження чи тайм-аут workflow можуть зробити запуск термінальним.

Для термінального невдалого запуску збережіть історію та звірте зовнішні побічні ефекти перед рішенням, чи має застосунок почати новий workflow. Використовуйте ідемпотентність застосунку для повторних бізнес-операцій. Якщо запуск завершила неперехоплена помилка activity, помилка в коді workflow чи структурний ліміт, після розгортання виправлення перевірте, чи можна виконати для нього [redrive](#redrive). Redrive продовжує роботу в новому запуску, який повторно використовує завершені кроки. Для помилки в коді workflow потрібні виправлений код і Workflow 2.19.0 або новіша версія. Дивіться [Redrive з виправленим кодом workflow](#redrive-corrected-definition). Автоматичних повторних запусків усього workflow чи відкриття термінального запуску немає. Дивіться [Повторні спроби рівня workflow](#workflow-level-retry).

## Redrive невдалого запуску {#redrive}

Redrive продовжує невдалий запуск у новому запуску того самого екземпляра workflow. Новий запуск повторно використовує записані результати кроків, що завершилися до помилки, і знову виконує решту workflow. Використовуйте redrive після виправлення причини помилки, щоб уже виконана робота, наприклад платіж чи лист, не повторювалася.

Невдалий запуск лишається закритим і незмінним. Новий запуск, наступник, отримує наступний номер запуску й стає поточним запуском екземпляра. Його `continued_from_run_id` вказує на невдалий запуск. Його подія `WorkflowStarted` записує `recovery_kind: redrive` і `resume_step_sequence`, тобто крок, з якого продовжується виконання.

Цей розділ описує redrive у Workflow 2.20.1 і новіших версіях. Попередні релізи Workflow і redrive у нативному Server приймають менше запусків. Дивіться [Попередні релізи та нативний Server](#redrive-earlier-releases).

Наступник відтворює код workflow з початку:

- Кожен виклик activity, що завершився в невдалому запуску, повертає свій записаний результат. Activity не виконується повторно.
- Побічний ефект чи маркер версії перед невдалим кроком повторно використовується в порядку кроків. Побічний ефект не виконується знову, а перевірка версії повертає записану версію.
- `timer()`, що спрацював перед невдалим кроком, записується в наступнику як такий, що вже спрацював. Наступник не чекає на нього знову.
- Memo чи атрибут пошуку, які код workflow задав через upsert перед невдалим кроком, повторно використовуються в порядку кроків, і наступник зберігає ті самі значення.
- Очікування signal (`await('name')`), яке отримало й застосувало свій signal, повторно використовується зі значенням цього signal. Signal не доставляється повторно.
- Update, який було прийнято, застосовано й завершено до невдалого кроку, записується знову на тій самій позиції. Replay запускає handler update з записаними аргументами, тож стан workflow збігається. Update не доставляється вдруге. Відхилений update і update, який помилка закрила до виконання, пропускаються.
- `outbox()->sendReference()` та `inbox()->receive()` у повторно використаному коді workflow повертають повідомлення, яке невдалий запуск надіслав або спожив. Вони не надсилають і не споживають його вдруге. Receive у replay, початковий виклик якого нічого не знайшов, читає stream знову.
- Якщо запуск завершила помилка activity, невдалий виклик activity планується як нове виконання activity з політикою повторних спроб із коду workflow. Його спроби починаються заново.
- Якщо запуск завершився помилкою в коді workflow чи на структурному ліміті, наступник продовжує з кроку, до якого код workflow так і не дійшов.
- Усе після невдалого кроку виконується так само, як у новому запуску.
- Memo та атрибути пошуку, задані під час старту запуску, переходять до наступника, як і під час continue-as-new.
- Наступник зберігає дедлайн виконання невдалого запуску. Його тайм-аут запуску починається заново в момент redrive.
- Кожен повторно використаний крок містить `reused_from_run_id` і `reused_recorded_at`. Для повторно використаної події update чи signal ці два поля завжди йдуть парою.
- Наступника, який повторно використав кроки, можна знову запустити через redrive. Повторно використаний payload signal чи update зберігає в `workflow_run_id` запуск, який першим його записав, `reused_from_run_id` вказує на запуск, з якого зроблено redrive, а кожен повторно використаний крок зберігає час свого першого виконання, тож ланцюжок redrive використовує кожен крок лише раз.
- В embedded mode `Workflow::now()` у наступнику починається з часу старту невдалого запуску. Відтворення використовує `reused_recorded_at`, тому `Workflow::now()` після повторно використаного кроку збігається з часом у невдалому запуску. Крок, повторно використаний другим redrive, зберігає час свого першого виконання.

### Запит на redrive {#request-a-redrive}

В embedded mode отримайте контракт `Workflow\V2\Contracts\WorkflowControlPlane` з контейнера Laravel і викличте `redrive()` з id екземпляра workflow та id невдалого запуску:

```php
use Workflow\V2\Contracts\WorkflowControlPlane;

$result = app(WorkflowControlPlane::class)->redrive($instanceId, $failedRunId, [
    'request_id' => 'incident-42',
]);

if ($result['accepted']) {
    $successorRunId = $result['workflow_run_id'];
} else {
    $reason = $result['reason'];
}
```

У сервісному режимі надішліть `POST /api/workflows/{workflowId}/runs/{runId}/redrive` з необов’язковим `request_id` у тілі запиту. Клієнти обгортають той самий маршрут:

| Інтерфейс | Виклик |
| --- | --- |
| CLI | `dw workflow:redrive <workflow-id> <run-id> --request-id <id>` |
| PHP SDK | `Client::redriveWorkflow($workflowId, $failedRunId, $requestId)` |
| Python SDK | `await client.redrive_workflow(workflow_id, failed_run_id, request_id=...)` або `await handle.redrive()` |
| Rust SDK | `client.redrive_workflow_run(workflow_id, failed_run_id, request_id)` або `handle.redrive(request_id)` |

Прийнятий redrive повертає id запуску наступника та `resume_step_sequence`. Відхилений redrive повертає `reason` і нічого не змінює. Redrive запуску, для якого redrive уже виконано, повертає наявного наступника замість створення ще одного. Передавайте `request_id`, щоб повторний запит був безпечним. `request_id`, уже використаний для іншого redrive того самого екземпляра, відхиляється з `request_id_already_used`.

Сервісні worker повідомляють відбиток визначення workflow. Redrive порівнює його з відбитком, записаним під час старту запуску. У Rust SDK викличте `Worker::set_workflow_definition_sources()` для кожного workflow, для якого потрібен redrive. Workflow, зареєстрований без ідентичності вихідного коду, працює й далі, але redrive його відхиляє.

### Redrive з виправленим кодом workflow {#redrive-corrected-definition}

Коли запуск завершився помилкою, бо код workflow викинув виняток, той самий код знову викине його на тому самому кроці. Тому redrive відхиляє такий запуск з `workflow_code_failure_requires_corrected_definition`. Розгорніть виправлення, а потім запросіть redrive з `allow_definition_change`:

```php
$result = app(WorkflowControlPlane::class)->redrive($instanceId, $failedRunId, [
    'request_id' => 'incident-42',
    'allow_definition_change' => true,
]);
```

Перш ніж щось записати, redrive відтворює завершені кроки з новим кодом у пам’яті. Новий код має пройти ті самі кроки в тому самому порядку й дійти до кроку, на якому впав старий код. Якщо це неможливо, redrive відхиляє запуск з `definition_incompatible_with_prefix`, а `definition_mismatch` називає перший відмінний крок (`sequence`) і `kind`, наприклад `step_shape` чи `version_range`. Якщо завершена історія більша за бюджет історії, redrive відхиляє запуск з `definition_check_over_budget`.

Прийнята зміна виконує виправлений код і записує відбиток заміненого визначення як `definition_changed_from` у події `WorkflowStarted` наступника. Пізніший redrive на тому самому визначенні нічого такого не записує.

`allow_definition_change` застосовується до запусків в embedded mode. Для запуску, який стартував сервісний worker, redrive відхиляє зміну визначення з `definition_change_requires_replay_check`. Без `allow_definition_change` змінене визначення відхиляється з `workflow_definition_unavailable_or_changed`.

### Коли для невдалого запуску можливий redrive {#redrive-eligibility}

Redrive приймає невдалий запуск, коли виконуються всі ці умови:

- Запуск є поточним запуском екземпляра.
- Запуск завершився помилкою, бо помилка activity дійшла до коду workflow і не була перехоплена, або бо код workflow викинув виняток чи його зупинив структурний ліміт. Запуск, що впав на тайм-ауті workflow, відхиляється.
- Кожен крок перед невдалим кроком є завершеною activity, побічним ефектом, маркером версії, `timer()`, що спрацював, upsert для memo чи атрибута пошуку, очікуванням signal, яке отримало й застосувало свій signal, або update, який було прийнято, застосовано й завершено з тими самими аргументами. Відхилений update і update, який помилка закрила до виконання, допускаються й пропускаються. Payload activity, побічних ефектів, signal і update мають зберігатися inline. Payload у зовнішньому сховищі payload відхиляється.
- Визначення workflow збігається з відбитком, записаним під час старту запуску, або ви передали `allow_definition_change` і виправлений код відтворює завершені кроки. Помилка в коді workflow на тому самому визначенні відхиляється.
- Дедлайн виконання ще не минув.
- Запуск не має батьківського workflow, дочірніх workflow чи локальних activity, а його вхідні дані збережено inline.
- Якщо запуск стартував сервісний worker, кроки перед помилкою можуть бути лише activity, побічними ефектами, маркерами версій і таймерами, що спрацювали. Upsert для memo й атрибутів пошуку, очікування signal і застосовані update відхиляються для сервісних запусків.

Відмова називає перше правило, яке не виконано:

| Причина | Значення |
| --- | --- |
| `run_not_failed` | Запуск не перебуває у стані `failed`. |
| `source_run_not_current` | Існує новіший запуск екземпляра. |
| `unrecorded_failure_boundary` | Для помилки запуску немає записаного кроку. Так буває, наприклад, з помилкою в коді workflow, записаною релізом до 2.19.0. |
| `workflow_code_failure_requires_corrected_definition` | Код workflow викинув виняток, а визначення не змінилося, тож той самий код викине його знову. |
| `unsupported_history` | Історія до помилки містить крок, який redrive не може повторно використати, наприклад дочірній workflow чи скасований таймер. |
| `unsupported_local_activity` | Історія містить локальну activity. |
| `unsupported_timer` | Історія містить тайм-аут умови чи signal, таймер очищення після скасування або таймер в межах області скасування чи паралельної групи. |
| `incomplete_timer_step` | Кроку таймера бракує події планування чи події спрацювання. |
| `unsupported_signal_wait` | Очікування signal має тайм-аут або перебуває в межах області скасування чи паралельної групи. |
| `unsupported_pending_signal` | Запуск отримав signal, який так і не застосував. |
| `incomplete_signal_step` | Очікуванню signal бракує запису про отримання чи застосування, або застосування не має записаного значення. |
| `mismatched_signal_receipt` | Запис про отримання signal вказує на інший запуск, екземпляр, команду чи очікування, один запис про отримання застосовано до двох очікувань, або повторно використана подія signal має лише одне з `reused_from_run_id` і `reused_recorded_at` чи вказує на інше джерело. |
| `unsupported_pending_update` | Запуск прийняв update, який так і не застосував і не закрив. |
| `mismatched_update_history` | Події update не мають жодної з допустимих форм, вказують на інший запуск, update, команду чи handler, змінюють аргументи між прийняттям і застосуванням або мають неповну пару `reused_from_run_id` і `reused_recorded_at`. |
| `incomplete_update_step` | Завершення застосованого update записує помилку або не має результату. |
| `invalid_step_sequence` | Повторно використаний крок не має коректного номера кроку. |
| `duplicate_step_sequence` | Два повторно використані кроки мають однаковий номер кроку. |
| `external_activity_result_not_supported` | Результат завершеної activity зберігається у зовнішньому сховищі payload. |
| `external_side_effect_result_not_supported` | Результат побічного ефекту зберігається у зовнішньому сховищі payload. |
| `external_signal_payload_not_supported` | Аргументи signal чи застосоване значення зберігаються у зовнішньому сховищі payload. Враховується будь-який ключ `external_storage`, навіть null. |
| `external_update_payload_not_supported` | Аргументи чи результат update зберігаються у зовнішньому сховищі payload. |
| `unavailable_update_payload` | Inline-аргументи чи результат update не вдається декодувати. |
| `missing_activity_result`, `unavailable_activity_result` | Результат завершеної activity відсутній або не декодується. |
| `unsupported_visibility_metadata` | Код workflow записав memo чи атрибут пошуку на кроці, який наступник не використав би повторно. |
| `unsupported_source_metadata` | Запуск стартував як дочірній для іншого workflow. |
| `unsupported_source_link_or_payload` | Запуск пов’язаний як дочірній з іншим workflow, або його вхідні дані лежать у зовнішньому сховищі payload. |
| `execution_deadline_elapsed` | Дедлайн виконання минув. |
| `workflow_definition_unavailable_or_changed` | Відбиток визначення відсутній або відрізняється від записаного під час старту, а `allow_definition_change` не передано. |
| `definition_incompatible_with_prefix` | Виправлений код не може відтворити завершені кроки. `definition_mismatch` називає перший відмінний крок. |
| `definition_check_over_budget` | Завершена історія більша за бюджет історії, який дозволяє перевірка відтворення. |
| `definition_change_requires_replay_check` | Запуск стартував сервісний worker, тому redrive не може перевірити змінене визначення. |
| `service_redrive_history_not_qualified` | Запуск стартував сервісний worker, і кроки перед помилкою містять upsert для memo, upsert для атрибута пошуку, очікування signal або застосований update. Redrive відхиляє такі кроки для сервісних запусків, доки не зможе перевірити для кожного runtime SDK, чи вміє той відтворювати їх у replay. |
| `request_id_already_used` | `request_id` уже використано для іншого redrive екземпляра. |
| `already_redriven` | Повідомляють деталі запуску та `describe()` для запуску, який уже запущено через redrive. Запит redrive для нього повертає наявного наступника. |
| `invalid_request_id` | `request_id` довший за 191 символ. |
| `run_not_found`, `instance_not_found` | Запуску чи екземпляра немає в цьому namespace. |

Решта причин повідомляє про історію, що не має очікуваної форми: `invalid_history`, `events_after_failure`, `duplicate_start`, `missing_start`, `unexpected_start`, `missing_terminal_history`, `invalid_activity_sequence`, `activity_sequence_gap`, `missing_activity_type`, `activity_type_mismatch`, `duplicate_activity_completion`, `incomplete_activity_prefix` і `invalid_failed_step`. Експортуйте історію запуску й перегляньте її, перш ніж вирішувати, як відновлюватися.

Коли redrive відхиляє запуск, збережіть його історію, звірте зовнішні побічні ефекти й вирішіть, чи має застосунок почати новий workflow.

### Як перевірити, чи можливий redrive для запуску {#redrive-check}

У Workflow 2.18.0 і новіших версіях деталі запуску повідомляють `can_redrive` і `redrive_blocked_reason`. Ці поля читає подання вибраного запуску у Waterline. `WorkflowControlPlane::describe()` повідомляє ті самі поля в `actions`. Вони походять з тієї самої перевірки, яку застосовує `redrive()`, тож ще до запиту видно, чи можливий redrive для запуску і чому ні.

Запуск, що не завершився помилкою, повідомляє `run_not_failed`. Запуск, для якого redrive уже виконано, повідомляє `already_redriven`. Для запуску в сервісному режимі звіт лише перевіряє, що відбиток було записано. `redrive()` і далі порівнює його з відбитком worker. Звіт не виконує перевірку відтворення виправленого коду, тож для зміненого визначення він показує `workflow_definition_unavailable_or_changed`, доки ви не запросите redrive з `allow_definition_change`.

У Workflow 2.19.0 і новіших версіях наступник, що виконує виправлений код, повідомляє замінений відбиток як `workflow_definition_changed_from` у деталях запуску та як `run.definition_changed_from` у `describe()`.

У Workflow 2.20.0 і новіших деталі запуску та `describe()` показують зв’язок redrive як типізоване походження. `parents` наступника та `continuedWorkflows` невдалого запуску містять його з `link_type: redrive` і `history_authority: typed_history`, беручи крок і час із `WorkflowStarted` наступника. Зв’язок, який історія не підтверджує, показується один раз із `history_authority: mutable_open_fallback` і `diagnostic_only: true`.

### Попередні релізи та нативний Server {#redrive-earlier-releases}

Workflow 2.20.0 не відхиляє нічого з того, що приймає 2.20.1. У 2.20.0 `outbox()->sendReference()` у повторно використаному коді workflow надсилає повторно, а `inbox()->receive()` у replay може повернути інші повідомлення чи жодного або спожити новіше повідомлення ([workflow#1010](https://github.com/durable-workflow/workflow/issues/1010)).

Workflow 2.19.0 відхиляє застосований update (`unsupported_history`). Він також відхиляє redrive наступника, який повторно використав update (`unsupported_history`) чи очікування signal (`mismatched_signal_receipt`). Деталі запуску та `describe()` показують зв’язки redrive як діагностичний запасний варіант.

Workflow 2.18.0 повторно використовує завершені activity, побічні ефекти, маркери версій і таймери, що спрацювали. Він відхиляє memo чи атрибут пошуку, які код workflow задав через upsert (`unsupported_history`), очікування signal (`unsupported_history`), запуск, що впав у коді workflow (`unrecorded_failure_boundary`), і змінене визначення (`workflow_definition_unavailable_or_changed`).

Релізи Workflow до 2.18.0 приймають вужче коло запусків. Кожен крок перед невдалою activity має бути завершеною activity. Побічний ефект, маркер версії чи таймер у цій історії відхиляється з `unsupported_history`, а будь-яке memo чи атрибут пошуку відхиляється з `unsupported_visibility_metadata`. Деталі запуску та `describe()` не повідомляють `can_redrive` і `redrive_blocked_reason`.

Релізи до 2.19.0 ігнорують `reused_recorded_at` на повторно використаних кроках signal, memo й атрибутів пошуку. Після того як наступник із Workflow 2.19.0 чи новішого повторно використав ці кроки, залиште worker 2.19.0 чи новіші або переконайтеся перед відкатом, що жодна така історія не може відтворюватися в replay. У вбудованому режимі Workflow 2.19.0 відтворює, імпортує й продовжує наступника з 2.20.0, який повторно використав update чи ланцюжкове очікування signal, так само як 2.20.0 ([звіт кваліфікації](https://github.com/durable-workflow/workflow/issues/864#issuecomment-6617902412)).

Redrive у нативному Server і далі застосовує правила, що діяли до 2.18.0. Підтримку поточних правил у нативному Server відстежує [server#980](https://github.com/durable-workflow/server/issues/980).

## Відмова входу та відновлення в сервісному режимі {#service-entry-recovery}

**Підтримка в опублікованих випусках.** Server 2.9.9 та SDK PHP 2.5.4, Python 2.6.2 і Rust 3.5.6 запровадили захист входу й описану нижче поведінку маршрутизації та відновлення. Це мінімальні версії для цих можливостей. Установлюйте поточні стабільні випуски, щоб отримувати виправлення безпеки.

Невідповідність входу є відмовою розгортання/replay до виконання коду workflow застосунку, а не повторною спробою activity чи термінальною бізнесовою помилкою. Worker повідомляє `failure_reason = workflow_entry_arguments_mismatch`, а Server зберігає невдалий task workflow з `replay_blocked = true`, не створюючи автоматично наступну спробу. Загальне поле `replay_blocked_reason` має значення `worker_reported_replay_failure`. Run залишається нетермінальним зі своїми записаними входом, історією та дедлайнами. Виняток у тілі workflow після успішного входу, навпаки, усе ще може завершити run помилкою.

Відновлюйте роботу лише після перевірки фактичного durable-стану:

1. Перевірте вибраний run через `GET /api/workflows/{workflowId}/runs/{runId}/debug`. Переконайтеся, що `latest_workflow_task_failure.reason` дорівнює `workflow_entry_arguments_mismatch`, а оригінальний run ще відкритий. Процедура не відкриває термінальний run повторно.
2. Розгорніть код, який приймає записані позиційні аргументи або типізований вхід. Збережіть початкові workflow/run id, namespace, queue, сумісність build, історію та дедлайни. Не редагуйте збережений вхід і не підставляйте нові значення DTO за замовчуванням.
3. Переконайтеся через [маршрутизацію визначень](./polyglot/worker-compatibility-routing.md#definition-fingerprint-evolution), що доступний придатний worker. Repair не створює worker і не доводить сумісність replay.
4. Використайте `POST /api/workflows/{workflowId}/runs/{runId}/repair` зі звичайними авторизованими обліковими даними оператора та namespace. Маршрут вибраного run відхиляє історичну ціль, замість непомітно відновлювати новіший run. PHP також надає `Client::repairWorkflow($workflowId, $runId)`; Python `repair_workflow(workflow_id)` адресує поточний екземпляр, а Rust не має відповідного допоміжного методу repair.
5. Перевірте, що той самий оригінал продовжився із записаним входом і префіксом історії та зафіксував очікуваний результат один раз. Початковий дедлайн, що вже сплив, залишається чинним. Якщо заміна все ще несумісна, дослідіть нову відмову, а не повторюйте repair без кінця.

Старіші Server можуть зберігати специфічну причину SDK, не класифікуючи її як replay-блокування, тому самого звіту про помилку недостатньо для гарантії відсутності автоматичних повторів. Використовуйте перевірену комбінацію runtime/SDK. Мовні межі описано у [Версіонуванні](./features/versioning.md#service-sdk-entry-safeguard), а авторизовані маршрути вибраного run — у [Командах workflow](./polyglot/server-api-reference.md#workflow-commands).

## Забезпечення тайм-аутів workflow {#workflow-timeout-enforcement}

За заданих `StartOptions::withExecutionTimeout()` або
`StartOptions::withRunTimeout()` рушій записує кінцевий термін запуску workflow.
Кінцевий термін виконання охоплює весь логічний workflow, включно із запусками
continue-as-new, а кінцевий термін окремого запуску скидається для кожного нового запуску.

Якщо кінцевий термін минув на момент початку завдання workflow, запуск одразу закривається:

- Усі відкриті виконання activity, timer і незавершені завдання
  скасовуються з типізованими подіями історії (`ActivityCancelled`, `TimerCancelled`).
- Записується рядок `WorkflowFailure` з `failure_category = timeout`
  і `propagation_kind = timeout`.
- Записується подія історії `WorkflowTimedOut` з `timeout_kind`, заданим
  як `execution_timeout` або `run_timeout`.
- Статус запуску стає `failed` з `closed_reason = timed_out`.
- Батьківські workflow, що очікують дочірній із тайм-аутом, отримують
  повідомлення.

Фоновий наглядач завдань також шукає нетермінальні запуски зі спливлими
кінцевими термінами без відкритого завдання workflow, наприклад запуск, що очікує
activity або timer на момент спливання терміну. Знайшовши такий запуск,
він створює завдання workflow, щоб виконавець виявив і забезпечив
тайм-аут під час наступного проходу.

Waterline показує `failure_category` в окремому стовпці **Category**
таблиці винятків і деталях помилок часової шкали. Експорт історії містить
`failure_category` у масиві `failures[*]`. Фінальна v2 записує класифікацію
під час помилки. Імпортовані рядки v1, які неможливо класифікувати,
залишаються видимими як некласифікована діагностика.

## Повторні спроби activity {#activity-retries}

Для спільного бюджету спроб різних workflow і черг поєднуйте авторські retry-ліміти з [Server admission і breaker застосунку](./polyglot/task-queue-admission.md#retry-load-and-downstream-budgets). Перші спроби та повтори враховуються; local/embedded виконання має інші межі.

`Workflow\V2\Activity` має типове `$tries = 1`, тому помилка activity
одразу повертається workflow, якщо activity явно не вмикає повторні спроби.

```php
use RuntimeException;
use Workflow\V2\Activity;

class ChargeCard extends Activity
{
    public int $tries = 3;

    public function backoff(): array
    {
        return [5, 30];
    }

    public function handle(): string
    {
        throw new RuntimeException('temporary gateway failure');
    }
}
```

У коді workflow обмежте загальний час activity, включно з очікуванням у черзі та паузами між спробами:

```php
use Workflow\V2\Support\ActivityOptions;
use function Workflow\V2\activity;

$result = activity(ChargeCard::class, new ActivityOptions(
    scheduleToCloseTimeout: 120,
));
```

Разом ці налаштування дозволяють не більше трьох спроб із паузами 5 і 30 секунд у межах початкового 120-секундного строку schedule-to-close. Якщо строк workflow спливає раніше, він також залишається чинним. Дозволяйте повторні спроби лише для операцій, які можна безпечно повторити, і захищайте зовнішні ефекти засобами ідемпотентності.

Коли activity з дозволеними повторними спробами викидає виняток до
вичерпання `$tries`, рушій закриває поточний рядок `activity_attempts`
як стан середовища виконання, повертає рядок `activity_executions` до `pending`,
записує типізовану подію історії `ActivityRetryScheduled` для невдалої
спроби та створює нове стійке завдання activity з `available_at` за
політикою `backoff()`. Workflow продовжує очікувати те саме виконання
activity й отримує виняток лише після помилки останньої дозволеної спроби.

Завдання повторної спроби записує `retry_of_task_id`,
`retry_after_attempt_id`, `retry_after_attempt` і `retry_backoff_seconds`
у payload, щоб Waterline пояснював причину планування. Деталі обраного
запуску спочатку відновлюють невдалу спробу в `activities[*].attempts`
із типізованої історії activity, показують `ActivityRetryScheduled` на
часовій шкалі та повідомляють кількість повторюваних activity через
`operator_metrics.activities.retrying`,
`operator_metrics.activities.failed_attempts` і
`operator_metrics.backlog.retrying_activities`.

`Workflow\Exceptions\NonRetryableExceptionContract` негайно обходить
політику повторних спроб: виняток non-retryable одразу завершує activity
помилкою й відновлює workflow із цим винятком.

### Роздільність затримок повторних спроб {#retry-delay-resolution}

Значення `backoff()` для activity задаються в цілих секундах. Стійкі інтервали
повторних спроб мають роздільність в одну секунду. Не використовуйте дробове
значення на кшталт `0.1`, щоб запросити повторну спробу через 100 мс. API SDK,
які генерують інтервали з дробових значень, округлюють їх вгору до наступної цілої
секунди. Довідники Python і Rust SDK описують допустимі типи параметрів та їх перетворення.

Після затримки наступна спроба стає доступною для виконання, але затримка черги та
навантаження worker можуть відкласти її ще більше. Для швидких тестів використовуйте
[керований час або обмежені сценарії з нульовою затримкою](./testing.md#keeping-delay-tests-fast).

### Ідентичність виконання activity та ідемпотентність {#activity-execution-identity-and-idempotency}

Повторна спроба — не єдина причина повторного спостереження тієї самої
логічної activity. Спливання оренди, втрата worker, затримка повідомлення
завершення та повторна доставка можуть створити іншу спробу чи застаріле
повідомлення завершення того самого стійкого виконання activity.

- `activity_execution_id` визначає логічну activity між повторними
  спробами й доставками. Використовуйте його як типовий ключ
  ідемпотентності віддалених побічних ефектів.
- `activity_attempt_id` визначає одну конкретну спробу логічної activity.
  Використовуйте його лише коли зовнішній системі потрібно розрізняти спроби.
- Пізнє повідомлення завершення чи помилки заміненої спроби є звичайною
  поведінкою застарілої спроби та не доводить подвійної фіксації рушієм.

Під час розслідування пізнього завершення після спливання оренди:

- визначайте переможну стійку спробу за Waterline, експортом історії
  або Server API;
- не вважайте відхилене пізнє завершення доказом відсутності віддаленого
  побічного ефекту;
- перевіряйте зовнішню систему за ключем ідемпотентності перед
  примусовою ручною повторною спробою чи відновленням.

Найбезпечніший типовий підхід — зробити віддалений побічний ефект
ідемпотентним за `activity_execution_id`, а потім визначати за стійким
результатом, чи прийняв рушій повідомлення конкретної спроби.

### Маркери помилок без повторних спроб {#non-retryable-failure-markers}

Коли activity або workflow викидає виняток, що реалізує
`Workflow\Exceptions\NonRetryableExceptionContract`, рушій записує
`non_retryable = true` у рядок `WorkflowFailure` і payload типізованої
події історії (`ActivityFailed`, `WorkflowFailed`, `UpdateCompleted`).
Цей стійкий маркер повідомляє операторам, зовнішнім worker та інструментам,
що помилка постійна й повторення тієї самої операції не допоможе.

Позначка проходить через усі інтерфейси видимості:

- **Рядки помилок**: логічний стовпець `workflow_failures.non_retryable`.
- **Події історії**: поле `non_retryable` у типізованому payload події.
- **Знімки помилок**: `non_retryable` у `FailureSnapshots::forRun()`.
- **Деталі запуску**: `non_retryable` у масиві винятків.
- **Записи часової шкали**: `non_retryable` у метаданих деталей помилки.
- **Експорт історії**: `non_retryable` у масиві `failures[*]`.
- **Waterline**: позначка «non-retryable» біля категорії помилки в таблиці
  винятків і часовій шкалі.
- **Міст зовнішніх worker**: payload команди `complete()` приймає
  `non_retryable`, щоб зовнішні worker workflow повідомляли такі помилки
  без потреби хост-процесу визначати клас викинутого об’єкта.

Для помилок, які не реалізують контракт, `non_retryable` за замовчуванням
дорівнює `false`. Фінальна v2 записує стійкий маркер в момент помилки.
Тому оголосіть контракт до запису помилки, якщо операторам або SDK
потрібно відрізняти постійні помилки від придатних до повторної спроби.

```php
use Workflow\Exceptions\NonRetryableExceptionContract;

class PaymentDeclinedException extends \RuntimeException implements NonRetryableExceptionContract
{
    // This failure will be marked as non-retryable in the durable record.
}
```

## Повторні спроби на рівні workflow {#workflow-level-retry}

Durable Workflow v2 **не** підтримує автоматичних повторних спроб на
рівні workflow. Коли запуск workflow завершується помилкою через необроблений
виняток, структурний ліміт або тайм-аут, він стає термінальним. Рушій
не запускає автоматично новий запуск того самого екземпляра workflow.

Це свідоме рішення:

- **Activity уже мають повторні спроби.** Політики activity з
  налаштованими `$tries`, `backoff()` і винятками non-retryable
  обробляють тимчасові помилки на відповідному рівні.
- **Відтворення workflow є примітивом відновлення.** Якщо завдання workflow
  зустрічає тимчасову інфраструктурну помилку, як помилка бази чи падіння
  worker, система стійких завдань повторно надсилає його, а відтворення
  продовжує зафіксовану історію без нового запуску.
- **Continue-as-new обслуговує довготривалі workflow.** Workflow, яким
  потрібен свіжий стан чи ущільнення історії, використовують
  `continueAsNew()` як явний перезапуск на рівні workflow.
- **Відновлення повертає до роботи застряглі запуски.** Команда `repair()` та автоматичне
  відновлення в циклі worker відновлюють запуски після втрати транспорту
  стійких завдань.
- **Redrive є явною дією оператора.** [Redrive](#redrive) продовжує невдалий запуск у новому запуску лише на ваш запит і повторно використовує результати завершених activity.

Якщо застосунку потрібна семантика повторних спроб на рівні workflow,
моделюйте її явно:

```php
use function Workflow\V2\activity;
use Throwable;
use Workflow\V2\Workflow;

class RetryableWorkflow extends Workflow
{
    public function handle(string $orderId): void
    {
        try {
            activity(ProcessOrderActivity::class, $orderId);
        } catch (Throwable $e) {
            // Record the failure, then start a new workflow
            // for retry-at-workflow-level scenarios.
            activity(NotifyFailureActivity::class, $orderId, $e->getMessage());
        }
    }
}
```

## Ліміти звітів про помилки PHP у сервісному режимі {#php-failure-report-limits}

PHP SDK **3.5.0 або новіший** обмежує вихідні звіти про помилки в сервісному режимі: повідомлення UTF-8 до 62 KiB, стеки до 128 KiB, необов’язкові метадані разом до 64 KiB і все закодоване тіло до 1 MiB, включно з маркерами. Застосовуються нижчі відомі транспортні ліміти. [Посібник зі звітів PHP](./polyglot/php.md#bounded-failure-reports) пояснює налаштування, діагностику пропущених полів, збереження семантики повторних спроб і рівність першого локального виконання та холодного відтворення. Це межі звітів SDK. Вбудований запис і зберігання зведень Core мають окремі контракти.

## Межі звітів про помилки Rust у service mode {#rust-failure-report-limits}

Для service-mode worker, які фактично запускають Rust SDK **4.10.1 або новіший**, вихідний message має до62 KiB UTF-8 разом із маркером, stack —128 KiB за підтримки, сумарні серіалізовані необов’язкові metadata —64 KiB, повне закодоване тіло —1 MiB або нижчу відому транспортну межу. Тип, рішення retry та ідентичність claim зберігаються; неможливий обов’язковий envelope явно відхиляється. [Довідник Rust](./polyglot/rust.md#bounded-failure-reports) пояснює маркери пропусків, цілі Avro details та межі локальних результатів. Це не кваліфікує старі SDK, embedded mode чи окреме виправлення summary-сховища Core.

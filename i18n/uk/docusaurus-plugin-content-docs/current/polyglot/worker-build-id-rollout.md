# Розгортання збірок воркерів

## Replay перед зміною build {#replay-before-changing-builds}

Перед promotion кандидата виконайте replay репрезентативних відкритих і нещодавно закритих історій на його точному коді застосунку. Перед відкатом перевірте історії новішого build на старішому артефакті. Дотримуйтесь [перевірки replay](../testing.md#replay-before-deployment); сумісна когорта маршрутизації чи успішна перевірка цілісності самі по собі не доводять replay-сумісність.

Цей посібник допомагає перевіряти когорти, обирати збірку для нових workflow та зберігати сумісних воркерів для наявних виконань. Просування змінює вибір для нових запусків; дренування забороняє когорті брати нові задачі. Жодна дія не переносить наявні виконання й не доводить, що збірку можна видалити; це вирішує [захищене виведення з експлуатації](#retire-a-build-or-queue).

[Сумісність і маршрутизація воркерів](/docs/polyglot/worker-compatibility-routing) пояснює ідентичність задач, активностей, повторів, дочірніх виконань і continue-as-new. Межі когорти — `(namespace, task_queue, build_id)`. Реєстрації без `build_id` належать до неверсіонованої когорти `null`.

## Стан розгортання, збережений сервером {#rollout-state-the-server-records}

| Поле | Значення |
| --- | --- |
| `build_id` | Зареєстрована ідентичність збірки; `null` — неверсіонована когорта. |
| `rollout_status` | `active`, `active_with_draining`, `draining`, `stale_only` або `no_workers`. |
| `drain_intent`, `drained_at` | Стійкий намір дренування та його перша часова позначка; повтор не пересуває її. |
| `promoted_at`, `rolled_back_at` | Збережені часові позначки просування та відкату. |
| `new_start_selected` | Когорта обрана явним просуванням. `false` не виключає описаний нижче резервний вибір єдиної когорти. |
| `active_worker_count` | Свіжі реєстрації без дренування; не кількість вільних слотів і не доказ підтримки всіх типів workflow. |
| `draining_worker_count` | Свіжі реєстрації в дренуванні, що не беруть нових задач; вони не обов'язково мають оренду. |
| `stale_worker_count` | Реєстрації з heartbeat, старішим за `stale_after_seconds`. |
| `total_worker_count` | Сума активних, дренованих і застарілих реєстрацій. |
| `runtimes`, `sdk_versions` | Рядки середовища виконання та SDK із реєстрацій. |
| `last_heartbeat_at`, `first_seen_at` | Свіжість і вік реєстрації, а не доказ відсутності залежних виконань. |
| `pending_workflow_tasks` | Лічильники й діагностика задач workflow, описані нижче. |

Намір дренування переживає перезапуски, відсутність воркерів і застарілі heartbeat. Його скасовує лише явне відновлення; відсутній воркер не відновлюється автоматично.

## Перевірка розгортання {#inspect-the-rollout}

Перед зміною потужності перевірте точні простір імен і чергу:

```bash
curl -fsS "$DURABLE_WORKFLOW_SERVER_URL/api/task-queues/orders-critical/build-ids" \
  -H "Authorization: Bearer $DW_OPERATOR_TOKEN" \
  -H "X-Namespace: orders-prod" \
  -H "X-Durable-Workflow-Control-Plane-Version: 2"
```

```bash
dw task-queue:build-ids orders-critical --namespace orders-prod --json
```

```python
from durable_workflow import Client

async with Client("https://durable-workflow.example", token=operator_token,
                  namespace="orders-prod") as client:
    rollout = await client.list_task_queue_build_ids("orders-critical")
    for cohort in rollout.build_ids:
        print(cohort.build_id, cohort.rollout_status, cohort.total_worker_count)
```

HTTP-знімок є першоджерелом для додаткових полів, яких може не показувати модель відповіді старішого SDK.

## Незавершені задачі workflow за когортами {#pending-workflow-tasks-by-cohort}

`pending_workflow_tasks` рахує лише задачі workflow цього простору імен і черги, групуючи їх за ефективною сумісністю задачі, а за її відсутності — виконання. Це не черга активностей, кількість відкритих виконань, пропускна здатність чи навантаження процесу.

| Вкладене поле | Тлумачення |
| --- | --- |
| `ready_count` | Рядки задач workflow у стані `ready`. |
| `leased_count` | Рядки у стані `leased`. |
| `total_count` | `ready_count + leased_count`. |
| `status` | `idle` без задач; інакше `pending` або `no_compatible_worker` для ненульової збірки без активного воркера. |
| `operator_visible_signal`, `message` | Діагностика відсутніх сумісних воркерів; інакше значення можуть бути null. |

Неверсіонована когорта не отримує такої діагностики конкретної збірки. Відсутнє поле, невдала відповідь або застаріле спостереження не означає нуль. Прочитайте знімок знову та перевірте heartbeat і декларації типів.

Стара збірка може мати дві готові задачі й одну орендовану, а нова — жодної. Загальна кількість три не визначає, якій групі потрібна потужність. Якщо активних воркерів старої збірки немає, відновіть сумісну потужність або явно відновіть когорту після помилкового дренування. Нові воркери іншої збірки не забирають роботу зі старим закріпленням. Якщо залишилися лише застарілі реєстрації, спершу з'ясуйте долю процесів і heartbeat, а не рахуйте їх доступною потужністю.

Скорочуйте когорту обережно, перевіривши її задачі, свіжих воркерів, типи workflow, вільні слоти та намір дренування. Зберігайте потужність для орендованої та майбутньої роботи наявних виконань. Виконання, що чекає сигналу, таймера, активності чи дитини, зараз може не мати задачі workflow, але потребувати старої збірки пізніше. Активності можуть використовувати інші записані черги. Цей endpoint не визначає безпечного виведення з експлуатації й не дозволяє масштабувати останню потрібну когорту до нуля; для цього використовуйте [захищене виведення з експлуатації](#retire-a-build-or-queue).

[Server #534](https://github.com/durable-workflow/server/issues/534) відстежує окрему функцію збору показників і масштабування до нуля. Вбудований тригер KEDA/HPA тут не задокументований.

## Перший перехід до версіонованої збірки {#first-cutover-unversioned-to-versioned}

1. Запустіть нових воркерів зі сталою build ID та перевірте простір імен, чергу, типи й свіжі heartbeat.
2. Перевірте обидві когорти та початкові виконання. Новіша назва або кількість воркерів не доводить сумісності.
3. Явно просуньте збірку, коли її мають обирати нові запуски:

   ```bash
   dw task-queue:promote orders-critical --namespace orders-prod --build-id orders-v2
   ```

4. Збережіть воркерів, сумісних із наявними історіями. Просування не змінює старих закріплень, а дренування не є міграцією.
5. Виведіть стару збірку з експлуатації через [захищене виведення](#retire-a-build-or-queue), щойно її інвентар стане порожнім. Порожні лічильники й нуль реєстрацій цього не доводять. Зберігайте артефакт, доки він може знадобитися виконанню.

## Канаркове розгортання нової збірки {#canary-a-new-build}

Сервер не розподіляє трафік між когортами у відсотках. Нові запуски обирають останню просунуту когорту, яка не дренується й не відкотилася. Без неї — єдину активну когорту із запитаним типом workflow, потім єдину активну когорту черги. Інакше виконання залишається без закріплення. Кілька активних когорт одного типу без просування не означають зваженого розподілу.

Додавання воркерів змінює потужність, а не політику вибору нових запусків. Для ізольованої канарки використайте окрему чергу й явно направте туди обрані запуски застосунку. Під час просування в початковій черзі збережіть старих воркерів для вже закріплених виконань.

## Перехід ланцюжка під час наступного продовження {#move-a-chain-at-its-next-continuation}

Якщо Server та SDK узгоджують `continue_as_new_target_build` у протоколі worker 1.21, на межі continue-as-new можна явно вибрати просунуту збірку. Наступний запуск починає нову історію з переданими аргументами. Використовуйте цю можливість, якщо просунута збірка може декодувати й прийняти ці аргументи. Звичайний continue-as-new зберігає прив’язку попереднього запуску до збірки.

Закриваючи попередній запуск, Server читає збережене просування для точного простору імен, черги й типу workflow наступного запуску. Допускається нуль worker у цільовій когорті, якщо Server уже зберіг підтвердження, що збірка обслуговує цей тип. Якщо придатної збірки немає, Server відхиляє перехід і лишає поточний запуск відкритим. Worker повідомляє `promoted_build_unavailable` через звичайний механізм повторних спроб завдання workflow. Waterline показує відмову та час запланованої спроби, якщо вона є. Успішний перехід записує обидві прив’язки в історію пов’язаних запусків.

Зберігайте worker старої збірки, поки вони потрібні відкритим запускам. Кожен ланцюжок переходить під час фіксації власного продовження з цією опцією. Відкриті дочірні запуски зберігають власні прив’язки.

## Дренування старої збірки {#drain-an-older-build}

Дренування забороняє workflow-, activity- та query-poll цієї когорти брати нову роботу, але не переносить задачі. Poll дренованого воркера отримує HTTP409 із `poll_status: "draining"` і `reason: "worker_draining"`. Наявні оренди зберігають початкові повноваження.

```bash
dw task-queue:drain orders-critical --namespace orders-prod --build-id orders-v1
```

Не робіть цього лише тому, що нова збірка обробляє власні задачі: старі виконання можуть залишитися чекати. Після передчасного дренування відновіть когорту й воркерів із потрібною початковою збіркою:

```bash
dw task-queue:resume orders-critical --namespace orders-prod --build-id orders-v1
```

Дренування чи зупинка всіх воркерів не доводить, що артефакт можна видалити. Дренування залишається аварійною зупинкою: воно одразу відхиляє опитування збірки незалежно від того, чи закріплена за нею робота. Рішення про видалення ухвалюйте через [захищене виведення з експлуатації](#retire-a-build-or-queue).

## Виведення збірки або черги з експлуатації {#retire-a-build-or-queue}

Native Server 3.14.0 і новіші визначають, чи можна безпечно прибрати збірку або чергу, і відмовляють у виведенні з експлуатації, доки лишається будь-яка жива залежність. Вимагайте, щоб `capabilities.worker_build_retirement` у `GET /api/cluster/info` мало значення саме `true`; опублікований PHP Server цих маршрутів не обслуговує. Використовуйте токен оператора чи адміністратора та простір імен, як і для інших маршрутів build-id.

| Намір | HTTP endpoint |
| --- | --- |
| Перевірити одну збірку | `GET /api/deployments/{namespace}/{taskQueue}@{buildId}/retirement` (`@unversioned` для неверсіонованої когорти) |
| Вивести одну збірку | `POST /api/deployments/{namespace}/{taskQueue}@{buildId}/retire` |
| Перевірити всі когорти черги | `GET /api/task-queues/{taskQueue}/retirement` |
| Вивести чергу | `POST /api/task-queues/{taskQueue}/retire` |

1. Просуньте збірку-заміну й залиште воркери старої збірки працювати. Вони завершують виконання, що досі закріплені за нею, відкладені повтори, таймери та продовжені ланцюги.
2. Перевіряйте стару збірку, доки `retirable` не стане `true`:

   ```bash
   dw task-queue:retirement orders-critical --namespace orders-prod --build-id orders-v1 --json
   ```

   Кожен блокер показує точний `count`, до 20 зразків ідентифікаторів і дію `recovery`: дати роботі завершитися або скасувати чи примусово завершити виконання, від яких ви вирішили відмовитися.
3. Виведіть її з експлуатації, за потреби прив’язавши запит до перевіреної `observation.inventory_revision`:

   ```bash
   dw task-queue:retire orders-critical --namespace orders-prod --build-id orders-v1 \
     --expected-revision "$INVENTORY_REVISION"
   ```

4. Зупиняйте процеси старої збірки лише після успішного виведення.

Без `--build-id` чи `--unversioned` обидві команди діють на всі когорти черги. Ці команди потребують CLI 2.12.0 або новішої; зі старішою CLI викликайте HTTP-маршрути напряму.

Інвентар рахує відкриті виконання, закріплені за збіркою (зокрема ті, що чекають, продовжені й дочірні), готові, орендовані та відкладені задачі (повтори активностей і таймери, строк яких ще не настав), відкриті активності, незавершені перевірки оновлень, а для черги — розклади, що запускають у ній виконання. Відкрите виконання без записаної черги задач робить інвентар `incomplete`, і виведення стає недоступним.

Перевірка — лише попередній перегляд. Дія виведення рахує повторно в межах того самого серіалізованого переходу, який використовують запуски, повтори та створення задач, і записує зміни лише тоді, коли нічого не лишилося. Відхилене виведення повертає HTTP409 і нічого не змінює; дотримуйтесь `expected_resolution` і перевірте знову.

| `reason` | Значення |
| --- | --- |
| `unknown_deployment`, `unknown_task_queue` | Для цілі не зареєстровано жодного воркера й не записано розгортання. |
| `selected_for_new_starts` | Нові запуски в черзі досі обирають цю збірку. Спершу просуньте заміну. |
| `inventory_incomplete` | Є відкриті виконання без прив’язки до черги. Відсутній інвентар ніколи не дає дозволу на виведення. |
| `live_dependencies` | Принаймні один блокер має ненульовий лічильник. |
| `inventory_changed` | `expected_inventory_revision` більше не збігається. |

Успішне виведення повертає HTTP200 з `outcome: "retired"`, `retired_at` і `retired_by`. Намір розгортання збірки переходить у кінцевий стан `drained`: її більше ніколи не обирають для нових запусків, її не можна просунути чи відновити через життєвий цикл розгортання, а її воркери лишаються в дренуванні. Коли всі когорти черги виведено й активних воркерів не лишилося, нові запуски в ній відхиляються з `task_queue_draining` і `routing_status: "retired"`, доки не зареєструється нова активна когорта. Закріплення виконань, черги активностей, історія та строки не змінюються.

Для відновлення `dw task-queue:resume` (`POST /api/task-queues/{taskQueue}/build-ids/resume`) повертає виведену збірку в стан `active`; виведення гарантувало, що на той момент у неї не було роботи.

## Відкат невдалої збірки {#roll-back-a-bad-build}

Відновіть відомих справних воркерів, за потреби відновіть їхню когорту та просуньте цю збірку для майбутніх запусків. Потім виконайте rollback невдалого розгортання. Відкат не переписує закріплення й не передає залишкову роботу іншій збірці. Зберігайте сумісних воркерів або ухваліть явне рішення про відновлення на рівні застосунку.

Повторні спроби, дочірні запуски та звичайний continue-as-new успадковують початкову прив’язку. Для розгортань із сумісним replay зберігайте сталу ідентичність збірки. Довготривалі ланцюжки можуть [вибрати просунуту збірку](#move-a-chain-at-its-next-continuation) під час продовження. Зберігайте поля сумісності під час відновлення.

| Перевірити виведення | `GET /api/task-queues/{taskQueue}/retirement`, `GET /api/deployments/{name}/retirement` | `dw task-queue:retirement` | — |
| Вивести з експлуатації | `POST /api/task-queues/{taskQueue}/retire`, `POST /api/deployments/{name}/retire` | `dw task-queue:retire` | — |

Маршрути promote, drain і resume приймають `{"build_id":"orders-v2"}` або `{"build_id":null}` для неверсіонованої когорти. Маршрути retire приймають необов’язкове тіло `{"expected_inventory_revision":"..."}`. CLI використовує `--build-id` або `--unversioned`, не обидва.

Повний життєвий цикл доступний через `GET /api/deployments` і `POST /api/deployments/{name}/{promote,drain,resume,rollback}`. Використовуйте повернену назву, як-от `orders-prod/orders-critical@orders-v2`, і початковий простір імен. На опублікованому Apache-шляху зберігайте роздільний `/`: кодування всієї складеної назви може повернути Apache HTML404 ще до API. Відмови повертають HTTP409 із типізованим `reason` і масивом `blockages`. Перевірте `expected_resolution`; відмова не є успішним просуванням. [Server #521](https://github.com/durable-workflow/server/issues/521) стосується неповного поточного OpenAPI-дзеркала, а не нової реалізації чи зміни заморожених схем.

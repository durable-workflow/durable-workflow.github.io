# Підтримка {#support}

Durable Workflow — проєкт із відкритим кодом, який можна безкоштовно використовувати за ліцензією MIT. Для запуску, поширення чи побудови production систем не потрібна комерційна угода.

## Підтримка спільноти {#community-support}

Основний спосіб отримати допомогу з Durable Workflow — спільнота. Підтримка спільноти найкраще підходить для публічних питань, обговорення проєктування, повідомлень про помилки та спільних операційних шаблонів.

Це найкраще місце для:

- питань щодо використання
- порад із моделювання workflow
- допомоги з розумінням детермінованості та відтворення
- обміну ідеями та шаблонами
- повідомлень про помилки чи неочікувану поведінку

### GitHub Discussions {#github-discussions}

GitHub Discussions — рекомендоване місце для розгорнутих питань, обговорення проєктування та тем, корисних іншим.

https://github.com/durable-workflow/workflow/discussions

### Discord {#discord}

Discord найкраще підходить для:

- коротких питань
- неформальних обговорень
- раннього зворотного зв’язку
- співпраці спільноти

https://discord.gg/xu5aDDpqVy

## Межі підтримки розгортання {#deployment-support-boundary}

Durable Workflow спроєктовано для корисного використання без розмови з відділом продажів. Публічний дистрибутив цілеспрямовано оптимізований для варіантів розгортання, які потрібні більшості команд насамперед:

- **Локальна розробка та внутрішні середовища поза production**
  Запускайте пакет чи окремий Server локально, у локальній мережі або спільному staging-середовищі, щоб розробники могли швидко запускати workflow та ітерувати.

- **Production на одному вузлі**
  Запускайте окремий Server на одній VM, VPS чи внутрішньому хості зі стійкою базою даних, кешем, зворотним проксі, резервними копіями та обліковими даними з обмеженнями за ролями.

- **Невеликі кластерні розгортання**
  Запускайте 2–3 API-контейнери без стану за балансувальником зі спільною зовнішньою MySQL чи PostgreSQL, спільним Redis, незалежно масштабованими worker та рівно одним планувальником чи процесом обслуговування.

- **Маніфести Kubernetes**
  Використовуйте надані маніфести, якщо команда вже експлуатує Kubernetes та потребує початкового налаштування для нього.

Durable Workflow Cloud — окремий [керований сервіс оркестрації](/docs/polyglot/cloud-control-plane). Cloud експлуатує своє середовище виконання, збереження, розміщення в одному регіоні та відновлення. Клієнти запускають SDK-клієнти й worker. Власний Server клієнта не підключається до Cloud. Міжрегіональна реплікація, перемикання регіону під час збою та повернення до попереднього регіону не входять до поточного контракту Cloud.

Ми цілеспрямовано оптимізуємо публічний дистрибутив для локальної розробки, production на одному вузлі та вузького контракту малого кластера з посібника самостійного розгортання. Маніфести Kubernetes надано командам, які вже його експлуатують. Контракт малого кластера підтримує [поступові оновлення](/docs/rolling-upgrades), коли виконуються всі гарантії цієї сторінки. Міжрегіональна схема active/passive з перемиканням регіону оператором залишається рекомендацією для оцінювання за участі підтримки. Дивіться [active/passive між регіонами](/docs/deployment#activepassive-multi-region) в посібнику самостійного розгортання. Опублікований Helm chart є шляхом самостійного встановлення та оновлення. Власні зміни chart, інфраструктура провайдера, дубльовані планувальники, багатовузлова робота без Redis, перемикання провайдера, міжрегіональні active/passive чи active/active, самостійне автоматичне перемикання регіону та складні топології високої доступності потребують участі підтримки, бо вимагають специфічних для середовища рішень щодо розміру, бази даних, мережі, безпеки й оновлень.

Дивіться [посібник самостійного розгортання](/docs/deployment) для конкретної матриці підтримки, рецептів Compose з опублікованими образами, меж сирих маніфестів Kubernetes, перевірок готовності та початку роботи за участі підтримки.

Ця межа зберігає простоту самостійного шляху та дозволяє отримати глибшу допомогу, коли саме розгортання стає проєктом розподіленої системи.

## Комерційна підтримка за бажанням {#commercial-support-optional}

Для команд, яким потрібні додаткові гарантії чи експертиза команди підтримки проєкту, доступні комерційна підтримка та консультування.

Використання Durable Workflow **не** потребує комерційної угоди. Усі можливості залишаються повністю відкритими незалежно від використання комерційної підтримки.

Комерційна підтримка призначена для команд, які використовують Durable Workflow у production системах, де важливі коректність, безпека оновлень, топологія розгортання та семантика тривалого виконання.

## Що охоплює комерційна підтримка {#what-commercial-support-covers}

Комерційну підтримку очолює супровідник проєкту. Зазвичай вона включає:

- **Планування production розгортання**
  Допомога з вибором одного вузла, вузького малого кластера, Kubernetes чи моделі за участі підтримки, включно з базою даних, кешем, зворотним проксі, планувальником і топологією worker.

- **Планування розміру, надійності та оновлень**
  Допомога з припущеннями щодо місткості, стратегією резервного копіювання та відновлення, порядком початкового запуску й міграцій, безпекою розгортання та операційними інструкціями.

- **Підтримка складних топологій**
  Проєктування за участі підтримки для власних змін Helm chart, інфраструктури Kubernetes конкретного провайдера, власних overlay, дубльованих планувальників, багатовузлового режиму без Redis, високої доступності, міжрегіональних active/passive чи active/active, самостійного автоматичного перемикання регіону та синхронної міжрегіональної реплікації. Опублікований chart залишається шляхом самостійного встановлення. [Посібник самостійного розгортання](/docs/deployment#activepassive-multi-region) зберігає архітектуру та інструкції active/passive для оцінювання за участі підтримки. Окремий [контракт керованого середовища Cloud](/docs/polyglot/cloud-control-plane) документує розміщення сервісу в одному регіоні, відновлення та межі підключення.

- **Перевірка безпеки**
  Допомога з обліковими даними за ролями, відкритістю мережі, внутрішніми та публічними точками доступу, завершенням TLS та межами доступу операторів і worker.

- **Перевірка архітектури та проєктування workflow**
  Допомога з коректним моделюванням workflow: межі activity, signal, використання inbox/outbox та шаблони тривалого виконання.

- **Детермінованість та безпечне відтворення**
  Допомога з виявленням і уникненням недетермінованої поведінки, проблем відтворення та тонких проблем коректності, що можуть проявитися з часом.

- **Стратегія оновлення та версіонування**
  Допомога з безпечними оновленнями, версіонуванням workflow та визначенням, коли потрібні шаблони на кшталт `continue-as-new`.

- **Налагодження складної поведінки workflow**
  Діагностика завислих workflow, неочікуваних циклів, проблем обробки signal та іншої складної для розуміння поведінки середовища виконання.

- **Виправлення та перенесення виправлень**
  Доступ до виправлень для підтримуваних версій, щоб уникати супроводу приватних форків.

- **Власні інтеграції за домовленістю**
  Допомога з інтеграцією Durable Workflow з наявними системами: чат-платформами, системами погоджень, внутрішніми API чи інструментами спостереження.

## Кому підходить комерційна підтримка {#who-commercial-support-is-for}

Комерційна підтримка зазвичай підходить, якщо ви:

- використовуєте Durable Workflow у **production**
- розгортаєте окремий Server для **кількох команд чи сервісів**
- створюєте **тривалі workflow чи workflow за участі людини**
- проєктуєте **кластерну топологію, Kubernetes/Helm для конкретного провайдера чи з власними змінами, міжрегіональні active/passive чи active/active або самостійне автоматичне перемикання** поза перевіреними операційними межами 2.0 в одному регіоні
- працюєте в середовищі, де **важливі коректність та безпека оновлень**
- шукаєте **експертизу супровідника проєкту**, а не загальне консультування
- хочете уникнути форків та довгострокових ризиків супроводу

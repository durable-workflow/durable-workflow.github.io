# 外部実行サーフェス {#external-execution-surface}

Durable Workflow v2 は、外部実行をシェルの慣習や単一の Worker トランスポートではなく、契約を起点とする製品サーフェスとして扱います。スタンドアロン Server は、機械可読な包括契約を `GET /api/cluster/info` の `worker_protocol.external_execution_surface_contract` で公開します。

この契約の名前は `activity_grade_external_execution` です。完全なワークフローランタイムの外で動かせる、永続的で範囲の制限された処理を対象とします。

- オペレーターの保守アクティビティ
- プラットフォームの自動化
- 統合の引き継ぎ
- 処理の開始、シグナル、更新、引き継ぎを行うブリッジアダプター
- スクリプト、デーモン、HTTP、キューベース、サーバーレス、エージェント駆動のハンドラー

主な用途はオペレーター、プラットフォーム、統合の自動化です。AI エージェントとスクリプトも安定したハンドルを必要とする重要な利用者ですが、ランタイムの境界を再定義するものではありません。

## 境界 {#boundary}

外部ハンドラーでできることは次のとおりです。

- リースされたワークフロータスクまたはアクティビティタスクを1件実行する
- Worker プロトコルを通じてリースの進捗をハートビートする
- 構造化された成功または失敗のエンベロープを返す
- ブリッジアダプターを使って、範囲を制限した処理を開始、シグナル、更新、引き継ぎする

外部ハンドラーは次を行ってはいけません。

- ワークフローのリプレイの意味を解釈する
- `ContinueAsNew` の動作を管理する
- ランタイム契約の外でシグナル、更新、クエリの順序規則を適用する
- イベント履歴を直接変更する
- 範囲の制限がないワークフローランタイムとして動作する

これらの規則は Server と実際の SDK ランタイム内に残ります。キャリアは、宣言された入力と結果のエンベロープをトランスポート境界の向こうへ運ぶ役割だけを持ちます。

## 公開された契約の接点 {#published-contract-seams}

キャリアを接続する前に `GET /api/cluster/info` を確認してください。関連する v2 パスは次のとおりです。

| パス | 用途 |
| --- | --- |
| `worker_protocol.external_execution_surface_contract` | 製品の境界、ランタイムの境界、有効なキャリアのクラス、接点の状態。 |
| `worker_protocol.external_task_input_contract` | リースされた1件のワークフロータスクまたはアクティビティタスクに対する、キャリアに依存しない入力エンベロープ。 |
| `worker_protocol.external_task_result_contract` | キャリアに依存しない成功、失敗、不正出力のエンベロープ。 |
| `worker_protocol.server_capabilities.external_execution_surface` | Worker プレーンのネゴシエーションに使うコンパクトな機能ポインター。 |

外部実行サーフェスは、決定的な認証・プロファイル・TLS の組み合わせ、設定を起点とするハンドラーマッピング、範囲を制限したブリッジアダプター、ペイロードの外部保存、受け入れとロールアウトの安全性に関する、計画中の接点も示します。これらは非公開の実装詳細ではなく、契約の接点として扱ってください。

## キャリアの要件 {#carrier-requirements}

有効なキャリアには、ポーリング型の CLI やデーモン、HTTP ハンドラー呼び出し、キューベースの Worker、サーバーレス呼び出しを使えます。トランスポートが異なっても、次の要件は変わりません。

- 宣言された入力スキーマを出力する
- 宣言された結果スキーマを受け入れる
- `task.id`、`task.attempt`、`task.idempotency_key` を保持する
- トランスポートの失敗を、構造化された失敗または不正出力の結果に対応付ける
- 認証、TLS、プロファイル、環境の入力を決定的に解決する

終了コード、stderr、プロセスクラッシュ、HTTP の失敗、キューの可視性タイムアウト、サーバーレスプラットフォームのエラーはトランスポート上の事実です。キャリアが宣言された結果エンベロープまたは `malformed_output` に対応付けて初めて、ワークフロー上の事実になります。

この契約の最初の具体的なキャリアは、`worker_protocol.invocable_carrier_contract` で公開される[呼び出し可能な HTTP キャリア](./invocable-carrier.md)です。対象はアクティビティタスクだけで、HTTPS が必要です（ループバック HTTP は開発時のみ許可）。認証は外部エグゼキューター設定から解決します。トランスポート層の `retry_policy` は、永続アクティビティの再試行ポリシーとは別です。結果の報告後は、後者を Server とランタイムが引き続き管理します。

## ブリッジアダプター {#bridge-adapters}

ブリッジアダプターは範囲を制限した入口または引き継ぎサーフェスです。処理を開始、シグナル、更新、引き継ぎできますが、ワークフローランタイムではなく、リプレイやイベント履歴の動作を隠すべきではありません。

すべてのブリッジアダプターは、次の場合に明示的な機械判読結果が必要です。

- 未知の対象
- 認証失敗
- 不正なペイロード
- 重複した開始
- 未対応のルーティング
- 受理した引き継ぎ
- 拒否した引き継ぎ

ほかのコントロールプレーンと同じ運用上の明確さを保ちます。安定したステータスコード、名前付きの `reason` 値、十分なコンテキストにより、`dw`、Waterline、SDK、エージェントは文章を解析せずに何が起きたかを説明できます。

CLI は Webhook ブリッジのサーフェスを直接公開します。

```bash
dw bridge:webhook stripe \
  --action=start_workflow \
  --idempotency-key=stripe-event-1001 \
  --target='{"workflow_type":"orders.fulfillment","task_queue":"external-workflows","business_key":"order-1001"}' \
  --input='{"order_id":"order-1001"}' \
  --json
```

JSON レスポンスは `/api/cluster/info` で公開されるものと同じブリッジアダプター結果契約で、`outcome`、`reason`、`control_plane_outcome`、`idempotency_key`、機密情報を除去した `target` の概要を含みます。

## エージェントが操作できる構造 {#agent-operable-shape}

外部実行サーフェスは v2 の AI 支援開発方針の一部です。人はワークフロー、アクティビティ、リプレイの不変条件を学び、ツールは安定した契約を通じて操作します。

1. `/api/cluster/info` から外部実行サーフェスを検出する
2. 公開要件を満たすキャリアを選ぶ
3. 外部タスク入力エンベロープを出力する
4. タスク ID と冪等性を保持する
5. 成功、失敗、不正出力のいずれかのエンベロープを返す
6. ブリッジとトランスポートの失敗を名前付きの結果で報告する

これにより、AI 支援によるひな形生成と運用自動化は予測可能になります。ツールは、1つのデモスクリプトから動作を推測する代わりに、プロトコルマニフェスト、タスクエンベロープ、結果エンベロープ、ブリッジ結果を根拠として示せます。

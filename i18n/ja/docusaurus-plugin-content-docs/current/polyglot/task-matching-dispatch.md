# タスクのマッチングとディスパッチ {#task-matching-and-dispatch}

Durable Workflow が実行可能な処理を見つけ、互換性のある Worker へ割り当て、「全ノードがすべてをポーリングする」方式を超えて割り当て経路を拡張する仕組みを理解する際に、このガイドを使ってください。ワークフロータスクのポーリング、アクティビティタスクのポーリング、キューの起床動作、専用マッチングロールのデプロイを支える契約です。

中心となる考え方は、Durable Workflow が2つの責務を分けることです。

- 永続履歴とタスク状態はデータベースに保持する
- タスクマッチングは、次の適格なタスクをどの稼働中 Worker が受け取るかを決める

この分離は、別のマッチングサービスを導入する前から重要です。実行可能タスクの検出、キューの所有権、リースの入れ替わり、バックプレッシャーを、各 Worker プロセスの付随的な効果ではなく、明示的な1つの役割として検討できます。

## マッチングロールの責務 {#what-the-matching-role-does}

マッチングロールは次を担当します。

- 実行可能なワークフロータスクとアクティビティタスクの検出
- 名前空間、接続、キュー、互換性ファミリーによる適格集合の絞り込み
- 一度に1つの Worker へタスクを提示
- 成功したクレームを有効期限付きリースへ変換
- クレーム失敗、リース期限切れ、Worker 消失時にも同じタスクを保持
- 起床とバックログの状態を運用担当者へ可視化

マッチングは永続履歴、ワークフローのリプレイ、タスク実行を置き換えません。次に実行する機会を誰が得るかを決めます。

## デプロイ構成 {#deployment-shapes}

Durable Workflow は現在、実用的な3つの構成に対応します。

### Worker 内のマッチング {#in-worker-matching}

既定の構成です。Worker プロセスは実行可能な処理をロングポーリングし、クレーム時のフェンシングにより、タスクリースを所有する Worker を常に1つにします。

次の場合に使います。

- 単一ノードまたは小規模な Worker 群を運用する
- キューの負荷が中程度である
- 専用マッチングデーモンがまだ不要である

### Server 内の HTTP マッチング {#in-server-http-matching}

スタンドアロン Server のデプロイでは、外部 Worker は Worker プロトコル経由で同じマッチング契約へアクセスします。

- `POST /api/worker/workflow-tasks/poll`
- `POST /api/worker/activity-tasks/poll`

Server が、同じ実行可能タスクの検出、クレーム、ハートビート、完了フローのネットワーク入口になります。

### 専用マッチングロールのデプロイ {#dedicated-matching-role-deployment}

大規模な Worker 群は、広範な実行可能タスクの検出を専用マッチングロールのプロセスに集約できます。現在文書化されている運用構成は次のとおりです。

```bash
php artisan workflow:v2:repair-pass --loop
```

このデーモンを専用プロセスで実行し、実行専用ノードに `DW_V2_MATCHING_ROLE_QUEUE_WAKE=0` を設定して、ループの各 tick で広範なキュー Worker の起床を行わないようにします。

次の場合にこの構成を使います。

- 実行ノードをリプレイとアクティビティ実行に集中させたい
- 広範で独立したポーリングが不要な競合を生んでいる
- 実行可能タスクの検出と走査周期の管理場所を明確にしたい

専用ロールはマッチングの実行場所を変えますが、Worker プロトコル契約は変えません。ポーリング、クレーム、リース、再配信の意味は同じです。

## 実行可能タスクの検出 {#ready-task-discovery}

マッチングロールは、実際に今すぐ実行できる永続タスクを探します。

- タスク種別がポーラー（`workflow` または `activity`）と一致する
- タスクの状態が `ready` である
- タスクの `available_at` に達している
- 名前空間、キュー、接続、互換性のフィルターが引き続き一致する
- アクティビティのポーリングでは、広告するアクティビティ型の一致も必要

ロングポーリングの起床は高速化の経路であり、正しさを担う経路ではありません。起床シグナルが遅延または欠落しても、タスクは永続ポーリングで可視になります。起床の失敗はレイテンシを増やしても、処理を取り残すべきではありません。

## クレーム、リース、バックプレッシャー {#claim-lease-and-backpressure}

マッチングが提供するのは機会だけです。1つの Worker がタスクのクレームに成功し、リースを受け取った時点で所有権が始まります。

このリースが Durable Workflow のバックプレッシャー動作を支えます。

- リースが更新、完了、解放、期限切れになるまで、1つの Worker がタスクを所有する
- 失敗した、または古くなった Worker がタスクを永久に拘束しない
- 再配信は通常の動作であり、少なくとも1回の実行の一部として処理する必要がある
- 互換性のない Worker はリースを奪わず、明示的に拒否される

リースに基づく処理なので、キューの負荷はバックログ、古いリース、繰り返す再配信として現れ、メモリ内で見えないまま失われることはありません。

## キューの分割 {#queue-partitioning}

主な分割の基本要素は次のとおりです。

- **名前空間**: テナントまたは環境の境界
- **接続**と**キュー**: 処理のルーティング境界
- **互換性ファミリー**: 互換性マーカーによる安全なルーティング
- **アクティビティ型フィルター**: 選択したアクティビティだけを実行する Worker

より強い分離、独立した Worker プール、異なる下流の上限が必要ならキューを分けます。同じキューをロールアウトやロールバック中も稼働させ、進行中の処理を非互換の実行主体へ移さないためには互換性ファミリーを使います。

## 起床シグナルと専用走査 {#wake-signals-and-dedicated-sweeps}

起床シグナルは「タスクが実行可能になった」ときから「ポーラーが気づいた」ときまでの時間を短縮します。永続的な正本ではありません。

既定の構成では、キュー Worker は通常のループの一部として起床シグナルを送れます。専用マッチングロールのデプロイでは、実行専用ノードはこの広範な起床経路を無効化し、代わりにマッチングデーモンが走査周期を管理します。

次は調整のための設定です。

- `DW_V2_MATCHING_ROLE_QUEUE_WAKE`: 実行ノードが Worker 内の起床を行うかを制御する
- `DW_WAKE_SIGNAL_TTL_SECONDS`: 起床マーカーを可視に保つ時間を制御する
- ロングポーリングのタイムアウト設定: ポーラーが処理を待って待機する時間を制御する

## 運用担当者が監視すべき項目 {#what-operators-should-watch}

次のサーフェスを併用します。

- `GET /api/cluster/info`: ノードごとのロール構成。`current_shape`、`current_process_class`、現在のロール、完全な `matching_role` 契約（`queue_wake_enabled`、デプロイの `shape`、`wake_owner`、`task_dispatch_mode`、固定された `partition_primitives`、現在の `backpressure_model`）
- タスクキューの可視性: 実行可能タスク数、有効なスロット、スロットリング
- Worker 群の可視性: 各キューの有効なポーラーと古くなったポーラー
- `dw system:operator-metrics --json` または `/api/system/operator-metrics`: 応答プロセスのライブなバックログ、修復、Worker、健全性カウンターと並ぶ、同じノードローカルの `matching_role` 契約
- ヘルスと Waterline の診断: 不健全なタスク、古いリース、互換 Worker の不足
- ローリングアップグレードの検査: 重複稼働期間中、マッチングが危険なクレームをブロックすべき場合

互換性のある Worker が利用できるのに最も古い実行可能タスクの経過時間が増えるなら、マッチング経路の進行が十分に速くありません。実行可能タスクは保持されているが互換 Worker がクレームできない場合、それはマッチングによる損失ではなく互換性の問題です。

## 専用マッチングロールを導入する時期 {#when-to-introduce-a-dedicated-matching-role}

次の場合に、既定の Worker 内マッチングから専用マッチングロール構成へ移行します。

- 広範なポーリングが、目に見えるデータベースやキャッシュの競合を生む
- 実行ノードから実行可能タスク走査の負担を取り除きたい
- キューの公平性とディスパッチの所有権を、明示的な1つのサブシステムとして検討したい
- 実行可能タスクの検出について、拡張、監督、デバッグする別のプロセスが必要

現在の Worker 群が小さく、主な必要性が新しい構成ではなく明確なロールアウトと互換性の動作なら、既定の構成を維持してください。

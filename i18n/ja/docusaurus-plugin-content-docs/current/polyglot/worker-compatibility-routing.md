# Worker の互換性とルーティング {#worker-compatibility-and-routing}

新しい Worker ビルドのデプロイ、1つのタスクキューのカナリア運用、不良ビルドのロールバック、Worker ビルドのロールアウト中の長時間ワークフローの維持に、このガイドを使います。Durable Workflow v2 は Worker の互換性を、非公式なデプロイ慣習ではなくルーティング契約として扱います。

基本規則は単純です。ある互換性ファミリーで開始した実行は、その実行を安全にリプレイして実行できる Worker へ引き続き割り当てる必要があります。システムは、タスクを黙って別ビルドへ渡すのではなく、「互換 Worker が利用できない」ことを明示的な運用状態として示す必要があります。

## 関連する2つの ID {#two-related-identities}

Durable Workflow は、関連しつつ異なる2つのロールアウトサーフェスを公開します。

- **ビルド ID** は、スタンドアロン Server 上で運用担当者に示すコホート ID です。Worker が `build_id` として登録する値で、タスクキューのロールアウト API はこれをドレインまたは再開します。
- **互換性マーカー** は、進行中の処理のルーティング ID です。組み込みおよび Server ホストの PHP Worker では、`DW_V2_CURRENT_COMPATIBILITY` と `DW_V2_SUPPORTED_COMPATIBILITIES` から取得します。スタンドアロン Server では、build-id コホートが互換 Worker グループを検査・制御する運用向けの手段です。

両方の値を `orders-2026-04-28` や `api-v3` のような不透明な文字列として扱ってください。Durable Workflow は semver の解釈、日付の比較、どちらの文字列が新しいかの推測をしません。

## 固定される対象 {#what-gets-pinned}

互換性は稼働中の Worker プロセスだけでなく、永続ワークフローの処理に紐付きます。

- **ワークフロー開始**は新しい実行に現在の互換性ファミリーを記録する。
- **ワークフロータスク**はその互換性ファミリーを継承し、再試行、リース期限切れ、再ディスパッチを通して保持する。
- **アクティビティタスク**は親実行と同じ互換性ファミリーを継承する。
- **再試行実行**は元実行の互換性ファミリーを保持する。
- **Continue-as-new** は現在の実行の互換性ファミリーを保持する。
- **子ワークフロー**は親実行の互換性ファミリーを継承する。

このため、デプロイが変わっただけで長時間ワークフローが別の実行主体ファミリーへ移ることはありません。意図的に旧コホートをドレインしてトラフィックを移さない限り、新ビルドは新しい開始に影響します。

## ルーティングの仕組み {#how-routing-works}

互換性は複数の層で強制します。

### ポーリング時の絞り込み {#poll-time-narrowing}

Worker はタスクキューと互換性・ビルドコホートによって要求を絞り、Server や組み込みエンジンが明らかに非互換のタスクを先に提示するのを避けられるようにします。

これは効率化のためのヒントであり、最終的な安全境界ではありません。

### クレーム時の強制 {#claim-time-enforcement}

クレーム時の強制が正しさの境界です。Worker がタスクを安全に実行できない場合、Durable Workflow は黙って所有権を再割り当てせず、明示的な互換性の理由でクレームを拒否します。

互換性に影響するデプロイでは、次の契約を根拠にしてください。

- タスクの対象が黙って非互換 Worker に拡大されることはない
- リース期限切れと再配信は元の互換性ファミリーを保持する
- 互換 Worker の不在は観測可能な状態であり、未定義動作ではない

## 運用担当者が設定すべき項目 {#what-operators-should-configure}

同じ進行中ワークフローを安全にリプレイできるビルドには、安定した人間が読める互換性ファミリーを使います。

組み込みまたは Server ホストの PHP Worker では次を設定します。

```bash
DW_V2_CURRENT_COMPATIBILITY=orders-2026-04-28
DW_V2_SUPPORTED_COMPATIBILITIES=orders-2026-04-28,orders-2026-04-21
```

`DW_V2_CURRENT_COMPATIBILITY` は新しい実行を固定するファミリーを指定します。`DW_V2_SUPPORTED_COMPATIBILITIES` は、ロールアウトやロールバックの進行中もこの Worker がクレームできるファミリーを指定します。`*` は単一ビルドの Worker 群または限定的なテストハーネスだけに使い、不確かなロールアウトポリシーを隠すために使わないでください。

スタンドアロン Server の Worker は安定した `build_id` を登録し、build-id ロールアウト API で意図的にコホートをドレインまたは再開します。

## 安全なロールアウト手順 {#safe-rollout-pattern}

互換性に影響する Worker 変更には、次の順序を使います。

1. 新しいビルド ID または互換性マーカーで新しい Worker コホートを起動する。
2. 新コホートが処理をクレームできることを確認するまで旧コホートを稼働させる。
3. 旧コホートをドレインし、新しいタスクの取得を止める一方、すでにリースした処理は完了または解放できるようにする。
4. 旧コホートが不要になるまで互換性とタスクキューのサーフェスを監視する。
5. ロールバックが必要な場合だけ旧コホートを再開する。

リプレイ互換の再ビルドでは互換性ファミリーを維持します。古いファミリーが作ったタスクを新しい Worker がクレームしてはいけなくなる場合にだけ変更してください。

## Worker 不足の明示的な状態 {#explicit-missing-worker-state}

必要な互換性ファミリーを満たせる Worker がいない場合、Durable Workflow はそれを明確に示す必要があります。

- Worker 群の概要は、必要な互換性がカバーされていないと示す
- タスクキューとロールアウトのサーフェスは、どのビルドコホートが有効、ドレイン中、古い、消失済みかを示す
- ワークフローの診断は、実行が互換 Worker を待っていると示す
- 運用ヘルスとメトリクスは、互換性でブロックされた処理を名前付きの状態で公開する

これは部分的なロールアウトや不完全なロールバックで期待されるシグナルです。偶然の一時障害ではなく、修正すべき実際の運用状態として扱ってください。

## build-id ロールアウトとの関係 {#how-this-relates-to-build-id-rollouts}

build-id ロールアウト状態と互換性ルーティングは、異なる問題を解決します。

- **build-id ロールアウト**は、どの Worker コホートが稼働中かを運用担当者に伝え、意図的なドレインや再開を可能にする。
- **互換性ルーティング**は、特定の進行中タスクが特定の Worker 上で実行可能かを判断する。

通常は両者を併用します。build-id コホートは利用可能な実行主体を示し、互換性ルーティングは長時間の処理が互換性のあるコホートだけへ割り当てられることを保証します。

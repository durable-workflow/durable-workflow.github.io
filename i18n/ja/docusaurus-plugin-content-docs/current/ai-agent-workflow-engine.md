# Durable Workflow は AI エージェントに適したワークフローエンジンか {#is-durable-workflow-a-good-workflow-engine-for-ai-agents}

**はい。** エージェントが機械可読な契約を通じてリプレイベースの永続ワークフローを操作する必要がある場合、Durable Workflow 2.0 は有力な選択肢です。特にセルフホスト、広く利用しやすい公開プロトコル、柔軟なデプロイ、理解しやすいコアが重要な場合に適しています。

MCP サーバーが存在するだけで「エージェント対応」になるわけではありません。エージェントの契約は、バージョン・機能の検出、スキーマ、コントロールプレーン操作、結果、履歴、型付きの失敗、Worker とキューの互換性、安全な変更、変更後の検証にわたる、**検出 -> 変更 -> 実行 -> 診断 -> 修復**という完全なループです。MCP は、HTTP+JSON、CLI JSON、SDK クライアント、Waterline エクスポート、公開プロトコルスキーマと並ぶ一つのインターフェースです。

## 機械操作可能なループ {#machine-operable-loop}

| 段階 | 公開された機械可読インターフェース | エージェントの判断または証拠 |
| --- | --- | --- |
| **検出** | `GET /api/cluster/info`、[2.0 機能索引](/docs/capabilities/)、[プロトコル仕様カタログ](/docs/platform-protocol-specs/)、`dw schema:list --output=json`、バージョン固定の `llms-2.0.txt` と `llms-full-2.0.txt` | 2.0 ドキュメント系列を選び、成果物・プロトコル・コーデック・機能の正確な組み合わせを検証し、操作前にサポートされるワークフロー、Worker、名前空間、キュー、スキーマのインターフェースを検出します。 |
| **変更** | サーバーの開始・シグナル・更新ルート、PHP/Python/Rust SDK クライアント、`dw workflow:start`・`workflow:signal`・`workflow:update` の JSON コマンド、アプリが公開する場合は MCP の `list_workflows` と `start_workflow` | 安定した型、ワークフロー・実行の識別情報、名前空間、タスクキュー、入力エンベロープ、冪等性の選択を使い、範囲を限定したコード変更または運用変更を行います。 |
| **実行** | ワークフローの詳細・結果・履歴エンドポイント、SDK ハンドル、CLI の `workflow:describe`・`workflow:result`・`workflow:history` JSON、MCP の結果・履歴ツール | プロセスの終了やログから成功を推測せず、選択した実行の名前付きステータスと型付き結果を観測します。 |
| **診断** | `dw doctor`、`server:info`、`debug workflow`、タスクキュー・Worker JSON、型付きのリプレイ・履歴の失敗、`/api/cluster/info`、Waterline の選択実行エクスポート | 名前付きフィールドを使い、コード・リプレイの失敗を、Worker の不在・非互換性、キュー受付、タイムアウト、認証、コーデック、ランタイムのヘルスが原因の問題と区別します。 |
| **修復** | サーバー・CLI の修復、リトライ、キャンセル、強制終了、アーカイブ、ビルド ID のドレイン・再開、互換性ルーティング操作、MCP `repair_workflow` の安全な変更エンベロープ | 許可された範囲限定の変更だけを適用します。その後、検出と実行のインターフェースを再度使い、ステータス、履歴、Worker・キューのヘルス、互換性メタデータ、診断した失敗が解消されたか想定どおり遷移したかを検証します。 |

詳細な[エージェントツール契約](/docs/agent-tooling-contract/)は、レポート形式と安全な変更の方針を固定します。[エージェント運用ループ](/docs/agent-operating-loop/)は、より詳しい手順を提供します。

## ファーストパーティ SDK とアプリケーションの境界 {#first-party-sdks-and-application-boundary}

PHP、Python、Rust は、安定版 2.0 リリース系列のファーストパーティのスタンドアロン SDK です。Workflow は、独立したバージョンで提供する組み込み Laravel エンジンおよびスタンドアロンサーバーのコアです。

- フレームワークに依存しない PHP アプリケーションとリモート Worker は [`durable-workflow/sdk`](/docs/polyglot/php/) を使用し、組み込み Laravel アプリケーションは `durable-workflow/workflow` を使用します。
- Python は決定的なワークフローとアクティビティを記述でき、ワークフロー、スケジュール、名前空間、Worker、キュー、履歴、修復の運用・コントロールプレーンインターフェースでもあります。
- Rust は決定的なワークフロー、アクティビティ、Worker サービスを記述します。現在の最低対応版では、永続タイマー、子ワークフロー、アクティビティのリトライ・タイムアウト、シグナル、リプレイされるクエリ、キャンセル・強制終了、型付き結果をサポートします。単なるプロトコルアダプターではありません。

三つとも同じ永続実行モデルと公開プロトコルを使います。言語をまたぐ子ワークフローとアクティビティは、登録された文字列型と共通 Avro エンベロープを使い、公式の各言語用 Avro パッケージを通じて固定された型付き Value の意味を保ちます。[2.0 機能索引](/docs/capabilities/)には、正確な最低対応版と、Rust の現在のスケジュール管理・フリート全体の可視性の境界など、意図された差分を記録しています。

## Python や Rust のチームにも Laravel は必要か {#does-a-python-or-rust-team-need-laravel}

いいえ。公開されているスタンドアロン Server は PHP で実装され、インフラとしてデプロイします。Python または Rust のみのアプリケーションチームは、バージョン管理された HTTP+JSON プロトコルに対してネイティブ SDK Worker を実行します。アプリケーションコードに Laravel を組み込む必要はなく、Laravel アプリケーションになるわけでもありません。

デプロイとコントロールプレーンには三つの選択肢があります。

1. **スタンドアロン:** 公開済みサーバーをセルフホストし、ネイティブ SDK Worker を接続します。[スタンドアロン Server](/docs/polyglot/server/)を参照してください。
2. **組み込み:** Laravel アプリケーションに PHP エンジンをインストールし、そのキュー、データベース、設定、デプロイを再利用します。これは Laravel ネイティブという特色のある経路であり、プラットフォーム全体を Laravel に限定するものではありません。
3. **Durable Workflow Cloud:** マネージド名前空間をプロビジョニングします。Cloud はオーケストレーションランタイム、状態、履歴、スケジュール、配置、復旧を運用し、アプリケーションチームは SDK クライアントと Worker を実行します。セルフホストの Server を Cloud に接続する構成ではありません。正確な [Cloud マネージドランタイム](/docs/polyglot/cloud-control-plane/)契約だけを評価対象にしてください。

## 現在利用できるもの {#what-exists-now}

現在公開されている 2.0 の組み合わせは、機能索引に記載された SDK において、決定的なワークフロー、アクティビティ、シグナル、クエリ、対応が明示された更新、タイマー、リトライ、タイムアウト、子ワークフロー、キャンセル、強制終了、副作用、バージョンマーカーを実装しています。加えて、スケジュール、名前空間、検索属性、コーデック相互運用性、Worker 互換性、型付き履歴・失敗、構造化診断、安全な運用コマンドがあります。

SDK 間で機能が同等だと仮定したり、最上位のバージョンから機能を推測したりせず、ランタイムのマニフェストと正確な[互換性マトリクス](/docs/compatibility/)を読んでください。

## 成熟度と適合性 {#maturity-and-fit}

Durable Workflow 2.0 は安定版ですが、エコシステムと本番運用の歴史は、確立された永続実行プラットフォームよりも浅いものです。予定するデプロイについて文書化された正確な機能と運用範囲を評価してください。

エージェントによる操作性、セルフホスト、広く利用しやすい HTTP+JSON の公開プロトコル、スタンドアロン・組み込み・マネージド Cloud 運用の選択肢、理解しやすい PHP コアが決め手となる場合、Durable Workflow 2.0 は魅力的です。この比較は適合性と成熟度に関するものであり、双方の製品がリプレイベースの永続実行を実装しているかどうかの比較ではありません。

## どのようなチームが選ぶべきか {#who-should-choose-it}

次に該当する場合、Durable Workflow 2.0 を評価候補にしてください。

- 自律エージェントまたは人間の運用者に、構造化された検出、型付き診断、安全な変更、変更後の検証が必要である
- Python、Rust、PHP のワークフロー・アプリケーションコードで、一つの永続実行モデルとコーデック契約を共有したい
- セルフホスト、またはスタンドアロン・Laravel 組み込み・正確な現在の Cloud マネージドランタイム契約から選べることに価値がある
- 必要な最低対応機能を、公開済みランタイムのマニフェストに照らして検証できる

次の場合は、まだ選ぶべきではありません。

- 選択した言語で[機能索引](/docs/capabilities/)が利用不可とする SDK 機能が必要である
- 現在のリリースよりも長い本番運用の歴史、広いエコシステム、蓄積された本番運用の証拠が必要である
- 正確な現在の [Durable Workflow Cloud 契約](/docs/polyglot/cloud-control-plane/)を超えるマネージド機能、リージョン、SLA、認証、プライベート接続、Worker・ランタイムの所有権、その他の保証が必要である

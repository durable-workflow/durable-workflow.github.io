Despliegues autogestionados

Durable Workflow v2 admite varias topologías autogestionadas. Elige la más sencilla que corresponda al entorno que operas y define explícitamente el contrato de imagen, base de datos, caché, autenticación, disponibilidad y actualización.

Esta guía cubre la distribución del servidor independiente. Si integras el paquete Laravel en tu aplicación, usa sus páginas de instalación y configuración. Durable Workflow Cloud es una alternativa gestionada: Cloud opera el entorno, persistencia, ubicación y recuperación. Nunca se conecta un Server autogestionado a Cloud. Consulta Entorno gestionado de Cloud. El contrato actual de Cloud cubre una sola región y su recuperación. No promete replicación multirregión, conmutación regional automática ni retorno a la región original.

La distribución autogestionada de Server no incluye ni opera Waterline. Despliégalo por separado si quieres su interfaz de operador y conéctalo a un namespace de Server siguiendo la guía de despliegue y supervisión de Waterline. Cloud incluye Managed Waterline para su namespace gestionado.

La distribución pública está optimizada para desarrollo local, un nodo en producción y clústeres pequeños. Los manifiestos Kubernetes son para equipos que ya lo operan. El material multirregión activo/pasivo es una guía de evaluación con soporte, no un contrato 2.0 autónomo probado. La conmutación de alta disponibilidad en una región (base de datos gestionada, Redis gestionado, pérdida de nodo API o worker y reinicio de programador) requiere actualmente soporte mientras su control de evidencia de versión exacta siga cerrado. Consulta Alta disponibilidad y conmutación en una región. En alojamiento propio, multirregión activo/activo, conmutación regional automática, programadores duplicados permanentes y validación de proveedores Kubernetes requieren soporte por sus dependencias de base de datos, caché, redes, seguridad, procesos y actualizaciones. El chart Helm publicado permite empaquetado autónomo dentro de los mismos límites bajo responsabilidad del operador. Cloud ofrece operación y recuperación gestionadas en una región, sin replicación ni conmutación entre regiones. Consulta Entorno gestionado de Cloud y el alcance del soporte comercial.

Seguridad, datos y auditoría​

Los despliegues autogestionados heredan la mayoría de controles de seguridad del entorno operado. Publica estos datos junto a la etiqueta de imagen, plan de migración y evidencia de recuperación:

ÁreaDeclaración honesta de publicación
Tratamiento de datosArgumentos, resultados, historial, memos, atributos de búsqueda, etiquetas, contexto de comandos, auditoría, excepciones y notas pueden contener datos de la aplicación del cliente. Los identificadores de workflow, atributos de búsqueda y etiquetas son metadatos visibles para operadores, no almacenes de secretos. Los identificadores siguen en texto claro y no los cubren los códecs de cargas.
CifradoUsa TLS en todas las interfaces HTTP de producción y configura TLS de base de datos en cada rol del Server, incluidas las migraciones. El cifrado en reposo corresponde a tu base de datos, almacenamiento de objetos, sistema de archivos, cola, caché y gestor de secretos. El paquete y Server no cifran automáticamente cada campo de carga.
CumplimientoEl paquete abierto y Server autogestionado ofrecen controles y evidencia de auditoría, no una certificación. SOC 2, HIPAA, PCI, ISO o FedRAMP corresponden a tu programa salvo que una oferta alojada documente otra cosa.
Registros de auditoríaComandos de workflow, eventos de auditoría de programaciones, metadatos de exportación y llamadas de servicio aportan evidencia duradera. No son un SIEM completo, DLP, registro externo inmutable ni sistema de conservación legal salvo que añadas esos componentes.
SoporteAquí se documentan credenciales por rol, TLS, copias, ensayos de restauración y topologías autónomas acotadas. Identidad avanzada, despliegue mTLS, redes privadas, motores de políticas propios, cumplimiento del proveedor y revisión a medida requieren soporte salvo documentación pública en contrario.

Define explícitamente la seguridad de red:

  • Entrada de webhooks: documenta endpoint público, autenticación, estrategia de reproducción o idempotencia, plazo, límite de carga, configuración de cabeceras de proxy confiables y rotación de secretos.
  • Tráfico de worker a backend: usa verificación TLS, credenciales de worker por rol, cabeceras de namespace, redes privadas o mTLS al cruzar redes no fiables y rotación que no otorgue capacidades de operador a tokens de worker.
  • Interfaces de operador: protege Waterline, API de operador, endpoints de automatización CLI y paneles propios con sesiones autenticadas o credenciales de servicio por rol, protección CSRF para sesiones de navegador y límites proxy/TLS documentados.

Imágenes publicadas​

Usa imágenes publicadas para desplegar Server autogestionado:

  • Docker Hub: durableworkflow/server:2.10.1
  • GitHub Container Registry: ghcr.io/durable-workflow/server:2.10.1
  • Fijación por resumen: durableworkflow/server@sha256:... o ghcr.io/durable-workflow/server@sha256:...

Usa etiquetas mutables solo en experimentos locales. En producción fija una etiqueta de versión o resumen para auditar actualizaciones y reversiones.

Desarrollo local y entornos internos que no son de producción​

Usa la receta Compose de imágenes publicadas para una instalación sin código fuente respaldada por MySQL y Redis:

curl -fsSLO https://raw.githubusercontent.com/durable-workflow/server/main/docker-compose.published.yml

export DW_SERVER_TAG=2.10.1
export DW_AUTH_TOKEN=dev-token

docker compose -f docker-compose.published.yml up -d --wait

Verifica API, disponibilidad, descubrimiento del clúster y registro de workers:

curl http://localhost:8080/api/health
curl http://localhost:8080/api/ready
curl -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  http://localhost:8080/api/cluster/info

curl -X POST http://localhost:8080/api/worker/register \
  -H "Authorization: Bearer $DW_AUTH_TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Namespace: default" \
  -H "X-Durable-Workflow-Protocol-Version: 1.0" \
  -d '{"worker_id":"compose-worker","task_queue":"compose","runtime":"python"}'

Esta opción es segura para desarrollo y pruebas internas. No es un límite de seguridad de producción: usa un token de compatibilidad, contraseñas predeterminadas, volúmenes locales con nombre y ningún TLS.

Producción en un solo nodo​

Usa el mismo artefacto Compose con configuración de producción fuera del control de versiones:

DW_SERVER_IMAGE=durableworkflow/server:2.10.1
SERVER_PORT=8080
APP_ENV=production
APP_DEBUG=false

DB_DATABASE=durable_workflow
DB_USERNAME=workflow
DB_PASSWORD=replace-with-random-password
DB_ROOT_PASSWORD=replace-with-random-root-password

DW_AUTH_DRIVER=token
DW_AUTH_BACKWARD_COMPATIBLE=false
DW_WORKER_TOKEN=replace-with-worker-token
DW_OPERATOR_TOKEN=replace-with-operator-token
DW_ADMIN_TOKEN=replace-with-admin-token

Arranca con ese archivo de entorno:

docker compose --env-file durable-workflow.prod.env \
  -f docker-compose.published.yml up -d --wait

Opera la máquina como servicio de producción:

  • Coloca TLS, enrutamiento público, registros de peticiones y listas de IP permitidas en un proxy inverso delante del contenedor API.
  • No expongas MySQL ni Redis públicamente.
  • Usa DW_WORKER_TOKEN para workers, DW_OPERATOR_TOKEN para tráfico de aplicación y operador y DW_ADMIN_TOKEN para namespaces y administración.
  • Haz copia del volumen MySQL antes de cada actualización y regularmente. Conserva Redis para reinicios ordenados, pero MySQL sigue siendo la referencia duradera del historial.
  • Conserva juntos el archivo de entorno exacto, etiqueta o resumen de imagen y copia de base de datos para restaurar.

Orden de actualización:

  1. Haz copia de MySQL y registra la imagen actual.
  2. Cambia solo DW_SERVER_IMAGE o DW_SERVER_TAG.
  3. Descarga la imagen nueva.
  4. Ejecuta docker compose --env-file durable-workflow.prod.env -f docker-compose.published.yml up -d --wait.
  5. Confirma /api/ready, /api/cluster/info y el registro de workers antes de redirigir tráfico externo.

El README de Server mantiene los comandos Compose actualizados en Imagen oficial + Compose.

Clústeres pequeños​

Un clúster pequeño amplía modestamente el modelo de un nodo. El contrato autónomo validado es deliberadamente acotado:

  • Ejecuta 2-3 contenedores API sin estado tras un balanceador. Salud, disponibilidad, descubrimiento, registro, sondeo y finalización de tareas de workflow deben funcionar sin sesiones persistentes.
  • Usa una base MySQL o PostgreSQL externa compartida para historial duradero. SQLite solo sirve para un nodo, no para persistencia de clúster.
  • Usa Redis compartido para caché, avisos de sondeo largo, bloqueos de consultas y admisión de colas y estado de cola. Multinodo sin Redis no está admitido.
  • Comprueba GET /api/cluster/info en cada nodo al desplegar. topology.current_shape debe seguir en standalone_server, topology.current_roles debe incluir api_ingress, control_plane, matching y history_projection, y topology.execution_mode seguir en remote_worker_protocol. Usa topology.matching_role para comprobar la ruta de asignación real: por defecto indica queue_wake_enabled: true, shape: "in_worker" y wake_owner: "worker_loop". El modo dedicado cambia los nodos con DW_V2_MATCHING_ROLE_QUEUE_WAKE=0 a queue_wake_enabled: false, shape: "dedicated" y wake_owner: "dedicated_repair_pass". El bloque debe seguir anunciando el task_dispatch_mode previsto, ejes congelados partition_primitives y backpressure_model actual. Consulta Topología de roles de Server para los campos.
  • Escala workers SDK externos por separado. Pueden usar otras máquinas o procesos, pero deben conectarse al endpoint balanceado, no a un nodo fijo.
  • Configura admisión de colas de tareas cuando protejan un inquilino, API externa, pool de base de datos u otra dependencia compartida.
  • Ejecuta exactamente un programador o proceso de mantenimiento para evaluar programaciones, imponer vencimientos de actividades y podar historial.
  • Inicializa y migra una vez por despliegue antes de aceptar tráfico en contenedores API y workers nuevos.
  • Elige la estrategia para esta versión: parada total (drenar workers, detener programador/mantenimiento, sustituir nodos API, inicializar/migrar y reiniciar workers y programador), o actualización gradual si se cumplen todas sus garantías.
  • Trata base de datos y Redis como dominios principales de fallo. Los contenedores de servidor son reemplazables; persistencia y coordinación no.

Las recetas autónomas publicadas empiezan en standalone_server, aunque el descubrimiento también mencione split_control_execution como topología del producto admitida. Es un contrato con distintas asignaciones de roles, no otro producto de servidor. Si pruebas una separación más explícita, lee topology.current_shape, topology.current_roles y topology.matching_role en /api/cluster/info, sin deducir funciones de nombres de máquinas o contenedores. Topología de roles de Server reúne roles y migración.

Todos los nodos API deben usar los mismos tokens o claves de firma, versión de aplicación y paquete Workflow, configuración de códecs y conexiones de base de datos y Redis. Asigna un DW_SERVER_ID único a cada nodo para distinguirlos.

Los límites no admitidos son explícitos: clúster SQLite, multinodo sin Redis, programadores duplicados permanentes, bases multiescritor activo/activo, conmutación regional autogestionada sin intervención y promesas amplias de SLA de «cinco nueves» o «cero interrupciones» necesitan validación aparte o diseño con soporte antes de depender de ellos. La guía multirregión activo/pasivo también es evaluación con soporte. La conmutación de alta disponibilidad regional (base gestionada, Redis gestionado, pérdida de nodo API o worker y reinicio de programador) requiere soporte hasta superar el control de evidencia. Consulta los objetivos de recuperación del motor, reglas de disponibilidad y evidencia necesaria en Alta disponibilidad y conmutación en una región.

Esta opción es autónoma si tu equipo ya tiene claros los modelos de VM, red, base de datos, caché, copias y balanceador. Requiere soporte si necesitas definir esos límites, capacidad, orden de despliegue o recuperación.

Presupuestos de timeout para long polls de workers​

Un poll sano puede permanecer en silencio hasta que termina la espera del servidor. Prevea ese silencio en el cliente HTTP del worker, el proxy de salida, la malla de servicios, el balanceador público, el ingress y cada proxy inverso anterior a la API. Los workers usan el ingress compartido de la API; un rol de matching separado no evita esos saltos.

PresupuestoQué limita
Duración del poll en el servidorLa espera de trabajo antes de responder sin tarea. El timeout_seconds de la petición prevalece sobre DW_WORKER_POLL_TIMEOUT, que es el valor de reserva si se omite el campo, no un máximo para los SDK. El protocolo permite hasta 60 segundos.
Timeout de conexión / pool del clienteEstablecer una conexión u obtenerla del pool. Estas fases no necesitan durar todo el poll silencioso.
Timeout de lectura / total del clienteEsperar bytes de respuesta o la operación completa si el transporte tiene un límite total. Añada a la espera del servidor margen para conexión, planificación y respuesta. Un timeout de lectura puede medir la inactividad entre bloques, no toda la petición.
Timeout idle / lectura upstream / petición de intermediariosTodos los límites de petición activa de cada salto deben permitir el poll legítimo y su respuesta. El keepalive de una conexión entre peticiones es otro límite.
Apagado / plazo del llamadorEl presupuesto de apagado del worker y la autoridad original del llamador o consulta siguen siendo límites estrictos. Cancele o drene dentro de ellos. No amplíe una consulta por un proxy o un reintento.

Compruebe el cálculo del SDK instalado. En la versión de Python verificada abajo, un poll positivo solicita como máximo 60 segundos al servidor y recibe al menos cinco segundos adicionales de timeout por fase HTTP. El poll predeterminado del Worker es de 35 segundos, que normalmente selecciona 40 segundos para esas fases. Un intermediario con un límite de lectura de 30 segundos puede interrumpir un poll legítimo. PHP y Rust tienen sus propios valores y políticas; ni el margen de Python ni un ajuste gRPC keepalive sirven como regla universal. Consulte las guías de PHP, Python, Rust y la referencia de matching.

Las llamadas ordinarias de control con Client en PHP SDK 3.2.0 no proporcionan un plazo HTTP total predeterminado; véase el defecto verificado PHP #203. Configure un cliente HTTP acotado para esas llamadas y conserve el plazo original del llamador. El timeout de polling del Worker no limita todas las peticiones del SDK.

PHP SDK 3.4.0 o posterior añade un plazo total predeterminado de 60 segundos a las peticiones HTTP de control normales del transporte propio del SDK; configure un requestTimeoutSeconds finito de al menos 0.001 segundos. Estos timeouts del transporte propio del SDK llevan reason=request_timeout y status=0. El SDK realiza un intento: una mutación agotada puede haber sido aceptada; inspeccione su identidad/resultado original antes de reenviarla. Clientes/transportes inyectados conservan su política y no pueden combinarse con esta opción. El límite por petición no sustituye plazos de long-poll del worker, transferencias de payload ni workflow/llamador. Revise composer.lock: este mínimo no cambia la combinación seleccionada. Véanse la configuración HTTP y la aceptación instalada 3.4.0.

Ejemplo verificado de poll corto​

Una prueba aislada usó Python SDK 2.9.0, PHP Server 2.11.0 y Nginx 1.30.5 publicados, con una cola vacía. Ambas celdas conservaron el poll de 3 segundos, los timeouts connect/read/write/pool de HTTPX de 8 segundos y el límite exterior del llamador de 10 segundos. Solo cambió el timeout de lectura upstream de Nginx:

Ajuste del intermediarioRespuesta observada
proxy_read_timeout 1sNginx devolvió HTTP 504 tras aproximadamente un segundo esperando la cabecera upstream. El SDK mostró ServerError.
proxy_read_timeout 8sEl poll silencioso terminó tras unos tres segundos con HTTP 200, task: null y poll_status: empty.

El valor de reserva del servidor fue deliberadamente de un segundo en ambas celdas; siguió prevaleciendo la espera explícita de tres segundos de la petición. Los reintentos HTTP se limitaron a un intento para mostrar el primer fallo. Es un ejemplo funcional, no un resultado de capacidad ni de dimensionamiento de producción. La verificación de #267 conserva imágenes exactas, peticiones y logs.

En Nginx, aplique el presupuesto upstream apropiado al location existente del poll del worker. Los ocho segundos siguientes pertenecen a este ejemplo de tres segundos:

proxy_connect_timeout 2s;
proxy_read_timeout 8s;

Nginx mide proxy_read_timeout entre lecturas upstream. HTTPX distingue timeouts de conexión, lectura, escritura y pool; ocho segundos por fase no son un plazo total de ocho segundos. Mantenga un plazo exterior explícito cuando sea necesario. Otros proxies y proveedores usan nombres y semánticas diferentes. Compruebe el camino completo con el SDK real: ampliar un límite del ingress no corrige otro más corto en otro salto.

Diagnosticar la respuesta antes de reiniciar workers​

  • Poll vacío normal: respuesta correcta del runtime sin tarea. En la versión verificada, la respuesta sin procesar incluye poll_status: empty. Continúe el polling normalmente.
  • Desconexión del intermediario: una excepción de transporte, un reset o un 502/504 del proxy puede llegar antes de que termine la espera legítima. Correlacione error y duración con logs del proxy/upstream. Un readiness sano y un polling posterior correcto no descartan una mala configuración.
  • Runtime no disponible: examine la razón estructurada y los checks de readiness de base de datos, caché y admisión. Una página HTML del gateway no es una negativa tipada del runtime.
  • Negativa de admisión del namespace o poll: examine razón, namespace/cola y demora de reintento, incluido HTTP 429. Aumentar el timeout idle no da capacidad ni corrige autorización.

Que un worker vuelva a conectarse no demuestra que la configuración anterior fuera sana. Verifique que el polling y la finalización de tareas continúan; conserve clase de error, cola, hora y frecuencia si persisten. Una desconexión esporádica no justifica reiniciar el proceso. El cliente Python también puede sintetizar poll_status: timeout tras reintentos por timeout HTTP; ese valor por sí solo no prueba que una respuesta vacía del runtime atravesara el proxy. Separe reintentos de transporte, reintentos de actividad, plazos de runs y autoridad de consultas.

Presupuestos de conexiones SQL​

Calcula las sesiones de base de datos antes de añadir réplicas API o solapar procesos antiguos y nuevos durante una actualización gradual. La base puede alcanzar el límite de conexiones aunque quede CPU disponible. Este límite es distinto de la latencia de escritura/commit, la capacidad HTTP y el crecimiento de los datos conservados.

Cuenta todos los procesos que usan SQL​

El despliegue PHP Compose publicado tiene estos posibles clientes SQL:

FunciónQué contar
APICada proceso PHP que atiende simultáneamente una petición y puede usar SQL, incluidos disponibilidad, operaciones y polls en espera. La configuración Apache prefork publicada permite 24 procesos por contenedor API. Es un máximo de procesos HTTP, no un pool SQL ni una medición de 24 sesiones abiertas.
Workers de cola LaravelCada proceso php artisan queue:work. La receta Compose publicada ejecuta uno; los contenedores worker adicionales añaden procesos. Son distintos de los workers SDK externos.
Programador/mantenimientoLos comandos PHP simultáneos, no solo el contenedor programador. El programador Compose ejecuta secuencialmente evaluación de programas, reparación, expiración de actividades y poda, por lo que su bucle normal tiene un comando activo cada vez. Mantén la regla de un único programador.
Inicialización y herramientas operativasComandos de migración/inicialización, reconstrucciones de proyecciones, retención, copias, monitorización y clientes SQL interactivos que puedan coincidir con el despliegue. Cuenta por separado los comandos deliberadamente simultáneos.
Clientes y workers SDKNormalmente ninguna sesión directa a la base del Server: los SDK PHP, Python y Rust en modo servicio usan HTTP. Añade conexiones solo si tus actividades u otro código de la aplicación acceden realmente a esa base.

Cuenta las conexiones SQL distintas usadas por cada proceso, no solo contenedores o nombres de host. La conexión predeterminada de Laravel y workflows.storage.connection pueden compartir un nombre configurado. Otro nombre de almacenamiento, una conexión SQL para cola/caché/sesión o un identificador separado de lectura/escritura/directo puede abrir otra sesión, incluso hacia el mismo endpoint. Redis no cuenta como sesiones SQL. Revisa la configuración efectiva en caché y los nombres que usa realmente cada función.

En un despliegue FPM propio, cuenta procesos ejecutores PHP-FPM, no hilos nginx o Apache event. En Octane, inventaría workers de peticiones, workers de tareas y clientes reales de la base. No reutilices los 24 procesos Apache como tamaño de pool para esos frontales. Los long polls síncronos ocupan un proceso PHP mientras esperan y pueden conservar una sesión SQL. No presupuestes automáticamente un poll HTTP inactivo como consumo SQL cero.

Ejemplo conservador de actualización gradual​

Es un ejemplo de planificación, no capacidad medida. Supón un límite de 120 sesiones cliente, diez para otras aplicaciones y quince reservadas para recuperación y administración. Quedan 95 para este despliegue. Supón cola y caché en Redis y como máximo una conexión SQL por proceso PHP.

Solapamiento máximoCálculoSesiones previstas
Réplicas API, incluida una réplica adicional durante el despliegue(2 + 1) × 24 × 172
Workers de cola Laravel2 × 12
Comando único de programador/mantenimiento1 × 11

Copias, monitorización y otras herramientas aprobadasAsignación explícita4

Con estos supuestos, una cuarta réplica API elevaría el subtotal a 104 y superaría las 95 sesiones asignadas. Dos conexiones SQL por proceso API requerirían ya 144 sesiones solo para las tres réplicas API. Recalcula al cambiar conexiones de almacenamiento, número de workers o solapamiento. Reduce los máximos de procesos/réplicas o sustituye por etapas, sin dar por hecho que la base absorberá la coexistencia. Aumentar max_connections también exige revisar memoria y carga de la base.

Observa y aplica el presupuesto​

  1. Registra el límite efectivo de conexiones, los clientes ajenos y el acceso reservado para recuperación. Fija máximos de réplicas/procesos API y de réplicas adicionales durante el despliegue. Incluye generaciones de workers de cola y herramientas que coincidan.
  2. En una copia aislada con tu imagen publicada y configuración exactas, muestrea sesiones en reposo, con polls en espera, al completar trabajo real y durante un solapamiento antiguo/nuevo acotado. Incluye sesiones inactivas y el propio monitor. PostgreSQL expone pg_stat_activity; MySQL, information_schema.PROCESSLIST. Usa un rol de monitorización con permisos adecuados y evita exportar texto SQL o payloads.
  3. Compara sesiones observadas por usuario/base con la asignación por proceso. Una muestra corta valida los supuestos de ese montaje, no un límite de saturación ni una garantía para todas las cargas.
  4. Vigila el margen de sesiones junto con rechazos de conexión, latencia de transacción/commit, esperas de bloqueos, peticiones HTTP retenidas y crecimiento del almacenamiento. La disponibilidad no demuestra por sí sola que haya capacidad para el despliegue.
  5. Cerca del límite, reduce el solapamiento o vacía y retira un grupo API/worker antiguo antes de iniciar el sustituto. Conserva acceso para recuperación y ejecuta la inicialización solo en la ventana de migración prevista. Si el solapamiento seguro no cabe, usa la actualización documentada con parada completa.

La admisión de colas limita ciertas operaciones de envío y lease. DW_WORKER_LONG_POLL_MAX_CONCURRENT y DW_QUERY_TASK_POLL_MAX_CONCURRENT acotan polls en espera por nodo. Ninguno limita globalmente sesiones SQL, bytes de la base ni latencia de commit. Reserva también capacidad para completados, heartbeats, operaciones y salud.

Use como referencia un endpoint directo y escribible de la base de datos. Un proxy debe validarse con la versión exacta del Server, el modo de pool y los ajustes de sentencias preparadas, límites de transacciones, estado de sesión y bloqueos. El pool transaccional de PgBouncer requiere el Server corregido, versión 2.9.8 o posterior. La aceptación de la versión publicada 2.9.8 valida PostgreSQL 16.15 con PgBouncer 1.26.1: PostgreSQL directo, pool de sesiones y pool transaccional con max_prepared_statements=0 o max_prepared_statements=200. Es una versión mínima compatible y una configuración exacta probada, no un pin a la última versión ni una garantía de capacidad; valide otras combinaciones por separado. Ejecute la inicialización habitual server-bootstrap contra el endpoint elegido antes de admitir tráfico.

GET /api/ready ejecuta una lectura de base de datos con parámetros enlazados (bound_read_query) y las comprobaciones de disponibilidad configuradas; deja explícitamente sin verificar la capacidad de escritura. Una conexión TCP, migración o respuesta de disponibilidad correcta no demuestra todas las operaciones SQL del workflow ni la capacidad de commit. Las réplicas de lectura no deben sustituir al escritor autoritativo de claims y transiciones durables.

Elegir una versión del chart​

Cada versión del chart registra en appVersion de Chart.yaml la imagen del Server con la que se probó; el chart y el Server tienen números de versión independientes. La combinación compatible seleccionada empareja el chart 0.2.3 con Server 2.10.1, usando los mismos metadatos de versiones que la tabla y el comando de instalación. La verificación OCI/del paquete publicado comprueba ese par, no una instalación nueva de Kubernetes.

Para otra versión del Server, inspeccione el Chart.yaml del chart publicado candidato (el código del chart seleccionado es un ejemplo) y seleccione una versión exacta cuyo appVersion coincida con el Server deseado. Lea las notas UPGRADING de la versión seleccionada, incluidas todas las versiones del chart que atraviese. No deduzca la versión del chart a partir de la del Server ni seleccione un chart sin publicar del código actual.

Sustituir image.tag cambia la imagen sin cambiar el appVersion registrado del chart. Eso produce una combinación personalizada hasta que se valide por separado con sus manifiestos generados, bootstrap, despliegue y runtime. Mantenga las copias de seguridad habituales y los límites de reversión en el plan de actualización; generar correctamente los manifiestos no demuestra que el despliegue funcione.

El historial publicado contiene una excepción: el chart 0.2.2 cruzó una versión menor del Server bajo un número patch del chart. La corrección publicada posterior reconoce la excepción y retoma la política declarada de versiones menores. Las versiones históricas permanecen intactas; esta nota no selecciona la combinación posterior del Server/chart.

Ejecutar workers de SDK en Kubernetes​

Despliega los workers de tu aplicación por separado del worker de colas Laravel del Server. Crea una imagen con tus manejadores PHP, Python o Rust registrados y las dependencias del SDK fijadas en su archivo de bloqueo. Usa un entrypoint en formato exec para que el proceso worker reciba SIGTERM. Sustituye la imagen siguiente por el digest inmutable de esa compilación.

Para workers del mismo clúster, usa el nombre, namespace y puerto reales del Service del Server. Los manifiestos sin procesar exponen http://durable-workflow-server.durable-workflow.svc.cluster.local:8080. Una versión de Helm puede usar otro nombre de Service. Los workers externos necesitan la URL HTTPS accesible del ingress o balanceador y la verificación normal del certificado. Coordina los presupuestos de long poll y transporte con la guía de tiempos de espera.

Crea un Secret en el namespace de Kubernetes del Pod del worker con su credencial existente. Mantén el token fuera del manifiesto y de la imagen. El namespace del Server es un límite del producto distinto del namespace de Kubernetes.

kubectl -n durable-workflow create secret generic orders-worker-auth --from-literal=token="$DW_WORKER_TOKEN"

Guarda esto como orders-worker.yaml. Estos nombres de variables de entorno son configuración de la aplicación: su entrypoint debe pasarlos al cliente del SDK y al Worker. Asigna a cada proceso activo un worker ID propio y registra los manejadores de la cola configurada.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-worker
  namespace: durable-workflow
spec:
  replicas: 2
  selector:
    matchLabels:
      app: orders-worker
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: orders-worker
    spec:
      automountServiceAccountToken: false
      terminationGracePeriodSeconds: 75
      containers:
        - name: worker
          image: registry.example.com/acme/orders-worker:release-id
          env:
            - name: DW_SERVER_URL
              value: http://durable-workflow-server.durable-workflow.svc.cluster.local:8080
            - name: DW_NAMESPACE
              value: default
            - name: DW_TASK_QUEUE
              value: orders
            - name: DW_WORKER_ID
              valueFrom:
                fieldRef:
                  fieldPath: metadata.uid
            - name: DW_WORKER_TOKEN
              valueFrom:
                secretKeyRef:
                  name: orders-worker-auth
                  key: token
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: "1"
              memory: 512Mi

Aplica el Deployment y espera a que termine el despliegue:

kubectl apply -f orders-worker.yaml
kubectl -n durable-workflow rollout status deployment/orders-worker

Las réplicas y los recursos son ejemplos iniciales, no garantías de capacidad. Ajústalos según la duración real de las tareas, la memoria, los límites de servicios dependientes y los presupuestos de admisión del worker. Un Deployment disponible no demuestra que el SDK se haya registrado ni que procese trabajo útil. Comprueba registros recientes y la compilación y cola esperadas; después inicia y completa un workflow representativo. Ejecutarse en Kubernetes no proporciona automáticamente un endpoint HTTP de salud al worker del SDK. Usa una sonda de la aplicación cuando exista y no uses la salud del Server como sonda de actividad del worker.

Entregar SIGTERM y esperar la limpieza​

SDKCierre del proceso worker
PHPUsa el bucle administrado Worker::run() con pcntl instalado. Su manejador de señales solicita el cierre; la tarea síncrona activa alcanza un límite antes de la limpieza y eliminación del registro administradas. Un bucle propio sobre tick() no proporciona ese ciclo de vida. Consulta el cierre ordenado de PHP.
PythonConecta SIGTERM al cierre del mismo Worker y espera tanto Worker.stop() como su tarea de ejecución. Configura shutdown_timeout explícitamente. El trabajo aceptado comparte ese plazo de drenaje. Cancelar un await no puede detener por la fuerza un hilo síncrono activo; una detención sin confirmar sigue siendo un error. Usa el ejemplo de procesos separados y señales y el contrato del ciclo de vida.
RustPasa a Worker::run_until(...) un future que se resuelva con Unix SIGTERM y espera su resultado. Un future que solo maneje Ctrl-C no procesa la señal de terminación del Pod. Los manejadores asíncronos deben ceder el control; limita el trabajo bloqueante por separado. Consulta Worker::run_until.

Da a terminationGracePeriodSeconds tiempo suficiente para el poll, el cierre de tareas aceptadas y la limpieza de HTTP, sesiones y registro del SDK instalado. Comprueba los 75 segundos del ejemplo frente a los límites reales de tu aplicación. Kubernetes incluye cualquier hook preStop en ese mismo período de gracia y fuerza la detención de los procesos restantes al agotarse. Un hook que solo duerme no solicita al SDK que drene ni amplía su plazo. Consulta el flujo de terminación de Pods de Kubernetes.

Ensaya la terminación en reposo y durante trabajo con duración acotada. Considera los errores de limpieza, un registro retenido o una terminación forzada como un cierre incompleto. Un worker de reemplazo continúa el trabajo durable según sus leases, reintentos y plazos registrados. Detener un Pod no cancela un workflow ni revierte un efecto externo. Antes de cambiar de compilación, sigue el despliegue por build ID del worker y conserva sus comprobaciones de compatibilidad, replay y reversión.

Alta disponibilidad y conmutación en una región​

La conmutación de alta disponibilidad regional es actualmente un contrato candidato sin verificar y con soporte, sobre clúster pequeño y manifiestos Kubernetes. Abarca los fallos que el motor está diseñado para soportar dentro de una región: conmutación de base gestionada (RDS Multi-AZ, Aurora, Cloud SQL HA, promoción Patroni, etc.), Redis gestionado (Sentinel, Elasticache, Memorystore HA, etc.), pérdida de API o worker y reinicio de programador o mantenimiento. La recuperación activo/pasivo entre regiones es otra evaluación con soporte. Consulta Multirregión activo/pasivo.

El contrato previsto (comportamiento, disponibilidad, objetivos por evento, prevención de doble primario y aceptación del ensayo) está en docs/deployment/ha-failover.md de la biblioteca y en docs/ha-failover-validation.md de Server. Esta sección es su presentación pública.

Estado de la evidencia de publicación​

No hay enlazado un resultado satisfactorio de la versión exacta del servidor público documentado. El intento registrado con imagen publicada se detuvo en topology_start esperando disponibilidad de API, antes de demostrar la matriz de fallos o los límites de recuperación. La presencia del ejecutor, su manifiesto de escenarios o un ensayo particular no demuestra que la imagen haya pasado toda la matriz. Por ello la alta disponibilidad regional sigue requiriendo soporte.

Solo se puede describir como autónoma después de una ejecución sin código fuente que use la versión exacta documentada para imagen, ejecutor y topología Compose y publique single-region-failover-result.json con outcome: "pass", runner_blocked: false, todas las fases phase_outcomes con status: "pass", todos los veredictos sobre los límites de recuperación satisfactorios y evidencia de cada escenario del manifiesto público. Ese resultado debe enlazarse aquí e identificar la misma imagen que durableworkflow/server:2.10.1. Hasta entonces, los límites siguientes son objetivos de evaluación, no afirmaciones de validación de la imagen publicada.

Topología candidata​

El contrato previsto se aplica al clúster pequeño o manifiestos sin procesar si el operador conserva tres reglas:

  • Siempre un solo endpoint de escritura de workflows. Se admite conmutación gestionada (RDS Multi-AZ, Aurora, Cloud SQL HA, Patroni, etc.) si se aísla el primario anterior antes de reincorporarlo: revocar el usuario de escritura, degradarlo con read_only=on, cortar replicación o restaurar una instantánea fiable. Un proxy debe conservar la semántica de base usada por el Server y validarse con su versión exacta, modo y ajustes. Consulta los presupuestos de conexiones SQL para las versiones requeridas y los modos probados del pool transaccional PgBouncer.
  • Un endpoint Redis cada vez, con promoción documentada. Se admite Sentinel, Elasticache, Memorystore HA, etc. Redis es aceleración, no el sustrato de corrección: su conmutación afecta a latencia, nunca a corrección.
  • Siempre un programador/proceso de mantenimiento. El orquestador (Compose con deploy.replicas: 1, unidad systemd con lease de anfitrión o Kubernetes Deployment con replicas: 1 y RollingUpdate.maxSurge: 0) debe conservar esta invariante al reiniciar. Los procesos duplicados permanentes quedan fuera del contrato.

Comportamiento y objetivos de recuperación por evento​

El contrato previsto fija objetivos acotados por clase de evento. No son garantías de imagen publicada mientras el control siga cerrado. El tiempo real observado es el objetivo del motor más la latencia de promoción del servicio gestionado.

Reglas de balanceador, disponibilidad y tráfico​

El balanceador delante de API es el punto único de admisión de tráfico durante una conmutación:

  • Configúralo con GET /api/ready, no solo /api/health. Salud solo prueba HTTP; disponibilidad informa de conectividad y comprobaciones configuradas, incluido el estado de aceleración Redis. No prueba todas las operaciones SQL de workflows ni verifica capacidad de escritura. Ante una caída de base, todos los nodos fallan correctamente. El balanceador DEBE tolerar que todos estén caídos sin recurrir a una lista antigua de nodos «conocidos como sanos».
  • Usa intervalos de 5–10 segundos y retira tras 2–3 fallos consecutivos.
  • No exijas sesiones persistentes: la prueba de clúster pequeño demuestra que un worker externo puede sondear server-a y completar en server-b.
  • Si solo falla Redis, todos los nodos siguen disponibles mientras funcionen las rutas duraderas de base de datos. La degradación aparece como checks.cache.status=warning y checks.cache.degraded_capability=long_poll_wake_acceleration. No retires nodos por esa advertencia.

Tras recuperar el sustrato, espera al menos un /api/ready con 200, consulta /api/cluster/info por el balanceador con token admin para confirmar topología, registra un worker de prueba con POST /api/worker/register en el endpoint balanceado, confirma exactamente un programador activo en su orquestador y reanuda tráfico externo.

Ensayo con artefactos exactos​

La publicación incluye un ensayo de referencia reutilizable para toda la matriz de fallos sin compilar código de producto. Ejecutor y Compose deben proceder de la misma etiqueta que la imagen. No combines una rama cambiante con una imagen arbitraria. En una máquina limpia con Docker Engine, Compose v2, Python 3.11 o posterior y acceso a registros públicos, ejecuta:

export DW_SERVER_RELEASE=2.10.1
git clone --depth 1 --single-branch --branch "$DW_SERVER_RELEASE" \
  https://github.com/durable-workflow/server.git "server-$DW_SERVER_RELEASE"
cd "server-$DW_SERVER_RELEASE"
export DW_SERVER_IMAGE="durableworkflow/server:$DW_SERVER_RELEASE"
scripts/conformance/single-region-failover-published-artifacts.sh \
  --result-dir ./failover-result

Esta opción deriva la copia y DW_SERVER_IMAGE de una sola variable. No cambies la imagen por separado: cambia DW_SERVER_RELEASE antes de clonar. El ejecutor exige una etiqueta o resumen público concreto, descarga imágenes auxiliares, resuelve todas a resúmenes de repositorio y rechaza secciones de compilación, montajes de código del producto y referencias locales o móviles de servidor. Arranca exactamente dos nodos API tras un nginx, una base MySQL, un Redis y un programador/mantenimiento.

single-region-failover-result.json, esquema durable-workflow.v2.single-region-failover.result, registra versiones exactas de artefactos y herramientas, topología normalizada, transiciones de disponibilidad, tiempos medidos y veredictos, identidades de workflow/ejecución/ tarea/programación y comprobaciones de duplicación/pérdida para finalización entre nodos, pérdida de API, interrupción de base y Redis, pérdida de lease de worker y reinicio del programador único. Los ejecutores externos descubren la invocación y el manifiesto en single_region_failover_contract de GET /api/cluster/info.

Un resultado solo valida interrupción y recuperación contra la imagen publicada si supera el control de evidencia anterior. Fallos, resultados parciales o ejecutores bloqueados son evidencia diagnóstica, no validación. Incluso una base que pasa no convierte el reinicio local de MySQL o Redis en evidencia de la promoción de un proveedor Cloud. Conserva junto a ella evidencia nativa del proveedor sobre promoción, aislamiento, RPO y tiempo transcurrido antes de afirmar alta disponibilidad gestionada.

Ampliaciones del paquete de recuperación​

Un despliegue de clúster pequeño o manifiestos que afirme cumplir este contrato DEBE ampliar su paquete según el ámbito operativo del operador con ensayos de:

  • conmutación de base gestionada sin pérdida de escrituras confirmadas y dentro del límite anterior;
  • conmutación Redis sin oscilaciones de rotación del balanceador ni pérdida confirmada, mostrando checks.cache.status=warning y long_poll_wake_acceleration degradada;
  • pérdida de API absorbida dentro del intervalo configurado, sin pérdida de escrituras confirmadas;
  • pérdida de worker conservando la ejecución duradera hasta vencer el lease, reclamándola tras el límite de reparación y completándola exactamente una vez;
  • reinicio de programador en otra máquina sin duplicar activaciones ni dejar una programación sin evaluar más allá de next_fire_at más un ciclo.

Mientras el control esté cerrado, todo despliegue requiere soporte aunque su ensayo pase. Tras un resultado público satisfactorio de todas las fases, solo se convierte en autónomo si su evidencia específica figura en el paquete del operador y se renueva según la cadencia publicada del ámbito operativo.

Límites de afirmaciones de alta disponibilidad no admitidas​

El contrato regional es acotado. Lo siguiente sigue fuera de él y requiere diseño con soporte, pues la topología es parte del riesgo:

  • bases multiescritor activo/activo;
  • multirregión activo/pasivo y conmutación regional autogestionada automática o sin intervención (la sección siguiente conserva orientación de evaluación);
  • replicación síncrona de base entre regiones (RPO=0);
  • programadores/mantenimiento duplicados permanentes;
  • colas fijadas por región como eje impuesto por el motor;
  • validación Kubernetes gestionada del proveedor más allá del empaquetado del chart;
  • promesas amplias de SLA de «cinco nueves» o «cero interrupciones» que excedan los límites anteriores.

El contrato es de recuperación acotada ante eventos concretos, no una promesa de disponibilidad dependiente de decisiones del operador sobre base, red y orquestador. El marketing o SLA autogestionado NO DEBE cruzar ese límite sin validación específica.

Multirregión activo/pasivo​

Es orientación de evaluación con soporte, no un contrato autónomo probado en el ámbito 2.0 admitido. Revisa una arquitectura candidata y prepara un ensayo específico con soporte antes de depender de ella en producción. Cada región parte de un nodo, clúster pequeño o Kubernetes documentado, pero esos contratos no demuestran replicación, conmutación, retorno, RPO, RTO ni prevención de doble primario entre regiones. El diseño detallado (autoridad de datos, replicación, namespaces/colas/workers, procedimientos, aislamiento y compromisos de consistencia y latencia) está en docs/deployment/multi-region.md y docs/multi-region-validation.md.

Topología candidata para evaluar:

  • Una región activa con contrato validado de un nodo o clúster pequeño: API tras balanceador, MySQL/PostgreSQL externo compartido como base duradera de escritura, Redis compartido, un programador/mantenimiento y workers externos.
  • Una región de reserva con réplica asíncrona de la base, Redis opcional de reserva, ningún programador/mantenimiento y cero o más contenedores API/worker preparados pero inactivos hasta la promoción.
  • Conmutación regional explícita a cargo del operador: detener escrituras a la región fallida, confirmar replicación contra RPO, promover la réplica, aplicar migraciones requeridas, iniciar programador único en la nueva región, cambiar endpoints de workers, tráfico externo y reconstruir proyecciones derivadas. No hay transición automática entre regiones.
  • Retorno siguiendo la secuencia inversa cuando vuelve la región original, aislando antes el primario recuperado (revocar usuario, read_only=on, cortar replicación o restaurar instantánea fiable) para reincorporarlo como reserva.

Autoridad de datos e hipótesis de replicación:

  • La base es la única referencia duradera y está vinculada a región: solo una región escribe cada vez. La base de reserva es de lectura hasta promoverla. RPO es el retraso de replicación asíncrona; RTO es el tiempo de ejecución del procedimiento del operador.
  • Redis acelera localmente en cada región. Avisos, bloqueos de consultas y admisión no se propagan entre regiones ni se debe esperar que lo hagan. Cada región tiene Redis propio; el operador elige caché fría o caliente en reserva. La corrección no depende de conservarla al conmutar.
  • La visibilidad procede de la base activa. Primero promueve, después lee.

Comportamiento de namespaces, colas y registro de workers:

  • Namespaces y colas están en la base y sobreviven tal como estaban en el último commit replicado. El motor no los particiona por región.
  • Los workers de la nueva región activa se registran contra su API local tras promover. Los registros de la región fallida permanecen y vencen normalmente.
  • El estado de despliegue y los despliegues por build-id sobreviven porque están en la base de datos.

Compromisos de consistencia y latencia en operación normal:

  • Inicios, señales y actualizaciones se confirman en la base activa, con su latencia de commit, y se rechazan mientras se retira la autoridad al conmutar.
  • La entrega de tareas sigue el contrato de aceleración de una región: menos de un segundo con Redis sano y cadencia de sondeo duradero en caso contrario.
  • Las programaciones se activan en el programador único activo y se pausan sin programador. Se reanudan desde filas duraderas tras la promoción.
  • Las lecturas reflejan escrituras solo dentro de la región activa. No hay garantía de leer las propias escrituras entre regiones ni RPO=0.

El diseño no sustituye copias ni evidencia. Sigue siendo obligatorio el paquete del ámbito operativo del operador, ampliado con SLO de retraso de replicación, latencia del procedimiento de promoción, fecha del último ensayo correcto y aislamiento del primario recuperado.

En alojamiento propio, multirregión activo/pasivo y activo/activo, conmutación regional automática, replicación síncrona (RPO=0), visibilidad activa entre regiones y colas regionales impuestas por el motor siguen requiriendo soporte, pues la topología es parte del riesgo. El contrato gestionado de Cloud actual es de una región y no aporta esas garantías multirregión.

Contrato de disponibilidad​

Usa comprobaciones de salud y disponibilidad:

  • GET /api/health demuestra que el proceso sirve HTTP.
  • GET /api/ready informa de las comprobaciones de dependencias configuradas, incluidas conectividad, migraciones y disponibilidad del namespace predeterminado. No prueba todas las operaciones SQL de workflows ni la capacidad de escritura disponible.
  • GET /api/cluster/info demuestra que un cliente autenticado descubre la identidad, protocolos de control y workers, códecs y capacidades.
  • POST /api/worker/register demuestra que los workers se autentican en el namespace y cola esperados.

No redirijas tráfico basándote solo en /api/health.

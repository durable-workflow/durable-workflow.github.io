Compatibilidad de versiones

Esta página es el contrato de referencia de compatibilidad y autoridad de publicación de la plataforma pública de Durable Workflow. Es la fuente única de referencia para:

  • qué interfaces son públicas,
  • el nivel de estabilidad de cada una,
  • qué cambios se pueden distribuir en una versión de parche, menor o mayor,
  • si un campo pertenece al contrato o sirve solo para diagnóstico,
  • y el protocolo de negociación de versiones que usan los clientes para rechazar la operación cuando el servidor anuncia una interfaz que no entienden.

Los documentos de estabilidad de cada paquete (por ejemplo, docs/api-stability.md en durable-workflow/workflow, la referencia de la CLI dw o la API de operadores de Waterline) están subordinados a esta página. Añaden detalles de cada paquete siguiendo estas reglas. Si discrepan de esta página, prevalece esta página y la discrepancia es un error del documento del paquete.

El mismo contrato se publica en formato legible por máquinas para que SDK, manifiestos del servidor y controles de CI se validen contra una sola referencia:

  • surface_stability_contract en el cuerpo de respuesta de GET /api/cluster/info del servidor independiente de Durable Workflow, esquema durable-workflow.v2.surface-stability.contract, versión 5.
  • Una copia congelada del mismo manifiesto en static/compatibility-contract.json de este repositorio.
  • La clase PHP Workflow\V2\Support\SurfaceStabilityContract, que es la fuente dentro del proceso que el servidor vuelve a exponer.

Una publicación que cambie una interfaz de las siguientes, su estabilidad, sus campos o sus reglas para cambios incompatibles, debe actualizar a la vez esta página, la copia JSON, el manifiesto PHP y los documentos de estabilidad de paquetes afectados. El CI valida el contrato legible por máquinas, los metadatos Rust publicados cuando están disponibles y las especificaciones del protocolo de workers. La coherencia editorial entre esta página y el manifiesto sigue siendo una responsabilidad explícita de la revisión de la publicación.

Complemento: catálogo de especificaciones de protocolos de la plataforma​

Esta página indica qué interfaces son públicas y cómo pueden cambiar. El catálogo complementario de especificaciones de protocolos de la plataforma indica dónde está la especificación normativa legible por máquinas de cada interfaz, qué formato usa (OpenAPI para API HTTP, JSON Schema para familias de objetos, AsyncAPI para semántica de flujos de eventos), qué repositorio la mantiene, qué familias de objetos rige y qué URL pública resuelve al artefacto. Autores de SDK, agentes y operadores deben validar contra el catálogo, en vez de releer prosa o depender de detalles de implementación locales del repositorio.

El catálogo se anuncia como platform_protocol_specs en GET /api/cluster/info.

La autoridad legible por máquina se publica en /platform-protocol-specs.json con el esquema durable-workflow.v2.platform-protocol-specs.catalog, versión 16.

El surface_family de cada entrada debe existir en el contrato anterior. El CI del sitio valida el catálogo, resuelve cada URL pública y rechaza campos de autoridad locales del repositorio.

El descubrimiento del runtime y la cualificación de conformidad utilizan autoridades de protocolo distintas. Elige la fila correspondiente a tu tarea. Que coincida la etiqueta de versión no convierte una referencia histórica versionada en un alias de la autoridad de Server sin versión.

Niveles de estabilidad​

Cada interfaz pública tiene exactamente uno de estos niveles de estabilidad. Los niveles son explícitos. Una interfaz sin clasificación no es pública.

NivelSignificadoCuándo se permiten cambios incompatibles
frozenFormato de transmisión o estructura persistida que debe decodificarse igual durante toda la vida del workflow. Renombrar, quitar o reutilizar un campo rompe el protocolo y nunca es un cambio menor.Solo introduciendo una primitiva paralela con un nombre de tipo nuevo. La estructura original sigue siendo decodificable indefinidamente.
stableInterfaz pública cubierta por la garantía de versionado semántico de la plataforma. Los cambios aditivos se distribuyen en versiones menores.Solo en una versión mayor.
prereleaseInterfaz pública con todas sus funcionalidades, pero que aún puede cambiar antes de publicar su 1.0.0 / 2.0.0 correspondiente.En versiones preliminares claramente identificadas y documentadas en las notas de publicación.
experimentalInterfaz pública inestable. Puede cambiar en cualquier versión, incluidos parches. Los consumidores deben aceptar su uso leyendo el indicador experimental de la interfaz.En cualquier versión, indicando el cambio en las notas de publicación.

Documentos de estabilidad por paquete​

Estos documentos añaden detalles de cada paquete siguiendo las reglas de esta página:

  • durable-workflow/workflow (PHP): docs/api-stability.md. Referencia de la API de creación PHP, las clases Support\* orientadas al servidor y las tablas de formatos congelados de eventos del historial.
  • durable-workflow/sdk (PHP): README.md. Referencia de la API de cliente remoto y worker independiente del framework distribuida en Packagist.
  • durable-workflow/server: README.md y docs/contracts/*. Referencia de los contratos de petición/respuesta del servidor independiente.
  • CLI dw: /docs/polyglot/cli-reference. Referencia de estructuras de salida JSON y códigos de salida.
  • SDK Python: README.md en durable-workflow/sdk-python. Referencia de la API pública de durable_workflow.
  • SDK Rust: README.md y [package.metadata.durable-workflow] en durable-workflow/sdk-rust. Referencia de la API pública del crate durable-workflow y de su declaración de compatibilidad del paquete.

Reglas de publicación​

Estas reglas se aplican a todas las familias públicas anteriores. Se reproducen en la copia JSON bajo release_rules.

Versiones de parche​

Permitido:

  • correcciones de errores que preserven el contrato documentado
  • correcciones de documentación
  • actualizaciones de dependencias que no cambien la interfaz pública
  • cambios en interfaces marcadas experimental

Prohibido:

  • quitar o renombrar campos, rutas, comandos o clases stable o frozen
  • restringir entradas aceptadas en rutas o comandos stable
  • cambiar el significado de un campo stable existente

Versiones menores​

Permitido:

  • añadir campos, rutas, comandos o clases a una interfaz stable
  • añadir parámetros opcionales con valores predeterminados seguros
  • añadir indicadores de capacidad a las respuestas de descubrimiento
  • promover una interfaz prerelease o experimental a stable

Prohibido:

  • quitar o renombrar campos, rutas, comandos o clases stable o frozen
  • cambiar el significado de campos stable o frozen existentes

Versiones mayores​

Permitido:

  • quitar, renombrar o restringir una interfaz stable
  • aumentar la control_plane.version o worker_protocol.version requerida
  • dejar de admitir un intervalo de versiones de SDK o CLI antes compatible

Obligatorio:

  • anunciar el cambio en las notas de publicación al menos una versión menor antes de publicar la mayor
  • cuando sea viable, distribuir la interfaz nueva junto a la antigua en una versión menor anterior para permitir migrar antes de la mayor
  • documentar la ruta en la guía de migración antes de publicar

Campos solo de diagnóstico y campos garantizados​

Cada campo de una interfaz stable o frozen es garantizado o solo de diagnóstico. Tienen reglas de cambio diferentes:

  • Campos garantizados: forman parte del contrato documentado. Los productores deben seguir emitiéndolos con la estructura documentada. Los consumidores pueden depender de su presencia y significado. Quitarlos o renombrarlos en una interfaz stable es un cambio mayor.
  • Campos solo de diagnóstico: sirven para clasificación humana, depuración y observabilidad. Pueden añadirse, renombrarse o quitarse en cualquier versión menor. Deben marcarse diagnostic_only: true (o su equivalente en la página) donde se documenten. Los consumidores no deben analizar, persistir ni tomar decisiones de producción basándose en campos de diagnóstico.

Los consumidores antiguos deben ignorar los campos aditivos desconocidos de una estructura stable o frozen (compatibilidad hacia delante). Los campos obligatorios desconocidos deben provocar el rechazo de la operación. SDK y CLI publican su comportamiento de compatibilidad hacia delante en sus documentos de estabilidad.

Matriz de compatibilidad​

Esta matriz operativa registra qué versiones de clientes se validan contra qué manifiestos de protocolos del servidor. Los componentes la validan en ejecución mediante GET /api/cluster/info y rechazan operar si los manifiestos no concuerdan.

La combinación seleccionada avanza después de validar los consumidores afectados. Los registros publicados de Server y los inicios rápidos generados usan los artefactos seleccionados. Los paquetes pueden publicarse de forma independiente, verificando la compatibilidad mediante manifiestos de protocolos, capacidades y comprobaciones de consumidores.

Los artefactos alfa y beta anteriores son históricos. No son alternativas de instalación inicial, y se conserva el historial de publicaciones.

Cada componente estable sigue el versionado semántico. Se pueden distribuir capacidades aditivas en versiones compatibles. Los cambios públicos incompatibles requieren una versión mayor. Usa el descubrimiento en ejecución para comprobar las capacidades disponibles en Server y los workers instalados antes de activar una funcionalidad.

Compatibilidad de protocolos en ejecución​

Las versiones superiores de los paquetes seleccionan la línea admitida. Los manifiestos de protocolos aportan una segunda comprobación que rechaza operar ante incompatibilidades:

ClienteLínea del productoPlano de controlProtocolo predeterminado de registro de workers
CLI2.3.02No aplicable
SDK PHP3.2.021.20
SDK Python2.8.021.20
SDK Rust4.2.021.20

Los SDK también permiten seleccionar explícitamente el protocolo de workers 1.19 para un Server anterior compatible. La cancelación cooperativa requiere 1.20; seleccionar 1.19 no proporciona esa capacidad. Cada operación puede usar su versión mínima de protocolo documentada, por lo que el valor predeterminado de registro no implica que todas las peticiones de workers envíen 1.20.

El Server publicado actual anuncia la versión del protocolo de workers que aparece en la tabla anterior de roles de autoridad. Acepta cabeceras de petición de la misma versión mayor y una menor igual o inferior a la anunciada, y devuelve la versión anunciada. Las cabeceras ausentes o malformadas, las versiones mayores distintas y las menores por delante del servidor se rechazan. La CLI valida control_plane.version: "2".

El version superior del servidor identifica la compilación. Los clientes deben usar los manifiestos control_plane, worker_protocol, client_compatibility y surface_stability_contract de GET /api/cluster/info para negociar protocolos.

Workflow y Waterline deben usar versiones 2.x compatibles. El descubrimiento en ejecución y las restricciones de paquetes delimitan la compatibilidad después de la publicación estable.

Ejemplos de validación en ejecución​

Los SDK validan el descubrimiento antes de registrar un worker. Un servidor incompatible produce un error de compatibilidad explícito en lugar de intentar una ruta de una versión preliminar antigua. Todas las peticiones de workers envían X-Durable-Workflow-Protocol-Version; las del plano de control envían X-Durable-Workflow-Control-Plane-Version: 2.

Antes de promover una línea del producto, la validación debe partir de una máquina limpia, instalar solo los artefactos publicados anteriores y completar los recorridos de conformidad PHP, Python y Rust. Las copias del código fuente y las sustituciones no publicadas no cuentan como evidencia de artefactos públicos.

Los metadatos de los paquetes estables y el descubrimiento en ejecución definen ahora el límite de compatibilidad 2.x admitido. La validación sigue instalando los artefactos públicos juntos antes de publicar, mientras que los parches y las versiones menores siguen las reglas de versionado semántico siguientes.

Progresión de publicaciones​

Los parches preservan los contratos estables documentados. Las versiones menores pueden añadir campos, rutas, comandos, clases o parámetros opcionales con valores predeterminados seguros. Los cambios incompatibles estables requieren una versión mayor y una migración documentada. Las estructuras congeladas de eventos siguen siendo decodificables indefinidamente. Una estructura nueva usa una primitiva paralela, sin modificar un evento existente.

Cada publicación debe mantener sincronizados los metadatos de paquetes, las notas de publicación, los comandos de instalación y los ejemplos entre lenguajes.

Lista de revisión de publicaciones​

  • Confirma que el contrato legible por máquinas coincide con el manifiesto de estabilidad de interfaces de Workflow.
  • Confirma que cada versión de SDK seleccionada pasa contra el Server seleccionado.
  • Confirma que los ejemplos de instalación usan el canal estable.
  • Confirma que los metadatos identifican la publicación exacta del SDK y las versiones de protocolos. Registra las validaciones posteriores de Server en la evidencia de compatibilidad.
  • Confirma que la conformidad con artefactos publicados desde una máquina limpia pasa en PHP, Python y Rust.
  • Confirma que las notas describen las incorporaciones posteriores a la base y no presentan versiones preliminares antiguas como opciones admitidas.

Flujos de salida de workflows

Los Workflow Streams son registros de salida con nombre, asociados a una ejecución y administrados por Durable Workflow Server. PHP, Python y Rust ofrecen operaciones tipadas para listar, describir, suscribirse, añadir, cerrar y marcar un error, de modo que las aplicaciones no tienen que construir solicitudes HTTP. El runtime anuncia durable-workflow.v2.workflow-streams.contract@1; la matriz de SDK legible por máquinas registra la compatibilidad exacta de cada SDK.

Cada flujo asigna posiciones crecientes de forma monótona a partir de 0. El next_offset de una página es la siguiente posición inclusiva que se debe solicitar. La entrega a consumidores es al menos una vez: completa los efectos idempotentes de la página y después guarda next_offset de forma duradera. Un fallo antes de guardarlo puede provocar una nueva entrega de elementos.

Emitir desde el código del workflow​

Los tres SDK emiten mediante el mismo límite de comando determinista: record_side_effect.workflow_stream. Cada SDK deriva la clave de idempotencia del elemento de la identidad duradera del comando de workflow de la tarea, el ordinal del comando de flujo y el índice del lote. Server confirma conjuntamente la modificación del flujo y el efecto registrado. La reproducción consume ese efecto y no puede crear otro elemento duradero para la misma adición lógica.

PHP:

use DurableWorkflow\Model\WorkflowStreamAppendItem;

$context->appendWorkflowStream('progress', [
    new WorkflowStreamAppendItem(['percent' => 50]),
]);
$context->closeWorkflowStream('progress');

Python:

from durable_workflow import WorkflowStreamAppendItem

yield ctx.append_workflow_stream("progress", [
    WorkflowStreamAppendItem(payload={"percent": 50}),
])
yield ctx.close_workflow_stream("progress")

Rust:

let item = WorkflowStreamAppendItem::new(serde_json::json!({"percent": 50}))?;
ctx.append_workflow_stream("progress", &[item], None)?;
ctx.close_workflow_stream("progress", None)?;

Los métodos auxiliares de workflow sirven para la autoría determinista. El código externo a un workflow puede utilizar la operación tipada append de cada cliente y proporcionar su propia clave de idempotencia estable.

Suscribirse y reanudar​

La suscripción lee una página acotada y, opcionalmente, espera nuevos elementos hasta 60 segundos. PHP acepta un callback de cancelación entre sondeos acotados. Python acepta la cancelación normal de tareas o un asyncio.Event que cancela el sondeo en curso. Descartar el futuro de suscripción de Rust cancela su solicitud.

SDKOperación de páginaValor de reanudaciónIteración tipada
PHPsubscribeWorkflowStream(...)WorkflowStreamPage::$nextOffsetiterateWorkflowStream(...)
Pythonawait subscribe_workflow_stream(...)WorkflowStreamPage.next_offsetiter_workflow_stream(...)
Rustsubscribe_workflow_stream(...).awaitWorkflowStreamPage::next_offsetRepetir el futuro de página acotada hasta terminal.

Los estados del ciclo de vida son open, closed y errored. La descripción tipada también expone last_offset, total_items, pending_items y error_reason. Se rechazan las adiciones a un flujo terminal. Al alcanzar el límite configurado de elementos pendientes, la adición devuelve stream_full; los productores deben reducir el ritmo o esperar a que los consumidores vacíen el flujo.

Referencias a cargas útiles externas​

Los valores en línea utilizan el sobre compartido Avro Value. Las referencias externas siguen el contrato de almacenamiento existente de cada SDK, sin inventar otro transporte:

SDKComportamiento de las referencias externas
PHPAñade y devuelve un payload_reference opaco; la aplicación sigue encargándose de subir y recuperar los datos del almacenamiento.
PythonUtiliza el controlador de almacenamiento externo configurado para subir, verificar la integridad, almacenar en caché, recuperar y decodificar un sobre Avro externo. Sin controlador, se puede añadir o inspeccionar un payload_reference opaco.
RustAñade y devuelve una referencia opaca y sus metadatos. El SDK actual de Rust no ofrece un controlador de almacenamiento externo.

Workflow Streams y MessageStream integrado​

Los nombres coinciden cuando el comportamiento coincide, pero los modelos no son intercambiables.

ConceptoWorkflow Stream en modo servicioMessageStream integrado en Laravel
Dirección de destinoEjecución del workflow + nombre del flujoInstancia/ejecución del workflow + clave del flujo
SentidoSolo salida del workflowBandejas de entrada y salida del workflow
Primera posición01
EntregaAl menos una vez; punto de control a cargo del consumidorAl menos una vez; cursor de mensajes a cargo del motor
Continuar como nuevoSin transferencia del cursor del flujoEl cursor de entrada pasa a la ejecución continuada
Mensajería entrante del workflowNo disponible; utiliza señales o actualizacionesDisponible mediante inbox()->receive()

Waterline utiliza una tabla normalizada para ambos modos y muestra el modo, el ciclo de vida, las posiciones de cabecera/cursor, el número de pendientes, el sentido y el error. Los flujos de salida del servicio no se presentan como una bandeja de entrada del workflow.

Cualificación​

El manifiesto público de escenarios de Workflow Stream exige ejecuciones con artefactos publicados para un productor PHP y consumidores Python y Rust, reinicio del worker productor, reconexión del consumidor, ciclo de vida/contrapresión/cancelación y referencias a cargas útiles externas. El resultado de publicación debe registrar todos los escenarios exigidos; las pruebas unitarias del código por sí solas no acreditan la conformidad.

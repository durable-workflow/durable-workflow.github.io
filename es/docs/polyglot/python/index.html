SDK Python

El SDK Python es un cliente ligero diseñado para uso asíncrono con Server autogestionado o un entorno de namespace de Durable Workflow Cloud. Permite iniciar, observar, señalar y cancelar workflows mediante la API del plano de control, y registrar procesos Python como workers que ejecutan tareas de workflow y actividades.

Prueba el entorno local de Sample App​

Para empezar a crear sin Cloud por el camino más corto, abre la rama main actual de Sample App en GitHub Codespaces y ejecuta:

scripts/playground python

El entorno local genera código de workflow y actividad propiedad de quien lo ejecuta, selecciona artefactos estables actuales e inicia Server y Waterline publicados. Antes de iniciar el workflow espera un registro de worker cuya identidad, tipos y cola coincidan con el contrato generado. El éxito exige el resultado completado y el historial esperados. El terminal imprime después el enlace local exacto de la ejecución en Waterline y la ruta de evidencia JSON estructurada.

La instalación del paquete, inicio rápido, referencia de API y ejemplo del repositorio siguientes siguen siendo rutas directas si no quieres usar Sample App.

Entorno de ejecución gestionado

Durable Workflow Cloud

Ejecuta clientes y workers Python contra un namespace gestionado por Cloud con credenciales separadas y limitadas por rol.

Ver precios de Cloud Dev

El SDK usa el mismo modelo duradero que el paquete PHP: identificadores de instancia y ejecución, eventos, colas y claves de tipo compartidos entre lenguajes. Un worker Python puede ejecutar actividades de un workflow escrito en PHP y viceversa.

Compara Python, PHP, Rust y dw en Capacidades de clientes y workers.

Para firmas de constructores, tipos devueltos, excepciones y nombres de métricas, consulta la referencia generada de la API del SDK Python.

El SDK Python 2.5.0 añade una caché de historial opcional y acotada para ejecución sticky. Usa Server 2.5.10 o posterior y habilítala en cada worker. Consulta Afinidad portable de workers y la guía Python y ejemplo ejecutable.

Los clientes Cloud usan URL y namespace provisionados, con credenciales de cliente y worker separadas. Consulta Entorno gestionado de Cloud. El inicio rápido siguiente usa valores locales autogestionados.

Requisitos​

  • Python 3.10 o posterior
  • Docker para el Server local del ejemplo, un Server autogestionado existente o un entorno Cloud de namespace provisionado

Instalación​

Instala la versión estable del SDK Python. El requisito exacto se genera desde la misma combinación que el inicio rápido de Server. Un archivo de bloqueo o restricciones puede conservarlo para reproducibilidad.

pip install durable-workflow==2.8.0

El SDK depende de httpx para HTTP y de fastavro para codificar el formato Apache Avro del único códec público de cargas v2. El soporte de métricas Prometheus es opcional.

Inicio rápido​

Este programa completo define un workflow con una actividad, lo inicia contra un servidor local y espera el resultado:

import asyncio
import uuid

from durable_workflow import Client, Worker, workflow, activity

@activity.defn(name="greet")
async def greet(name: str) -> dict:
    return {"greeting": f"Hello, {name}!", "length": len(name)}

@workflow.defn(name="greeter")
class GreeterWorkflow:
    def run(self, ctx, *args):
        result = yield ctx.schedule_activity("greet", list(args))
        return result

async def main():
    workflow_id = f"greeting-{uuid.uuid4().hex}"

    async with Client("http://localhost:8080", token="dev-token", namespace="default") as client:
        handle = await client.start_workflow(
            workflow_type="greeter",
            task_queue="default",
            workflow_id=workflow_id,
            input=["world"],
        )

        worker = Worker(
            client,
            task_queue="default",
            workflows=[GreeterWorkflow],
            activities=[greet],
        )

        await worker.run_until(workflow_id=workflow_id, timeout=30.0)
        result = await handle.result(timeout=10.0)

    print(result)  # {"greeting": "Hello, world!", "length": 5}

asyncio.run(main())

Informes de error acotados​

El SDK de Python 2.11.0 incorporó informes de error salientes acotados. Los valores predeterminados son 62 KiB UTF-8 para el mensaje, 128 KiB para la pila, 64 KiB para los detalles y diagnósticos opcionales serializados en conjunto y 1 MiB para el cuerpo completo codificado por HTTPX. Los marcadores, el escape JSON, la identidad de la concesión y los demás comandos del lote cuentan para ese límite del cuerpo. Tiene prioridad cualquier límite de transporte configurado o descubierto que sea menor. Se conservan el tipo, la clase y el código del error, la política de reintentos y la identidad de la concesión.

Configura un presupuesto menor para el cuerpo cuando sea necesario. Los ajustes de advertencia sobre el tamaño de la carga siguen siendo informativos.

from durable_workflow import Client

async with Client(
    "https://workflow.example.com",
    worker_token="worker-token",
    control_token="operator-token",
    failure_report_limit_bytes=512 * 1024,
) as client:
    info = await client.get_cluster_info()

Un marcador visible de truncamiento y los recuentos originales de bytes identifican los campos recortados. Los detalles Avro se conservan íntegros o se omiten por completo. Si una envoltura obligatoria no puede representarse, se lanza FailureReportTooLarge antes del envío HTTP. Los errores locales se normalizan antes de que el código del workflow los observe, por lo que la primera ejecución y la reproducción en frío ven el mensaje persistido. Un mensaje local ya observado permanece inmutable durante el ajuste final del lote.

Almacenamiento externo de cargas​

Las operaciones normales de Client y Worker usan automáticamente el transporte autenticado del runtime de Server. El SDK descubre la política y los límites mediante GET /api/cluster/info, sube valores codificados superiores al umbral o necesarios para que quepa la solicitud y recupera los valores referenciados antes de decodificar. El código del workflow y de la actividad recibe el valor decodificado. Las credenciales permanecen en Server. Los workers remotos no necesitan boto3, clientes del proveedor ni acceso al directorio local de Server.

La referencia del runtime usa el esquema durable-workflow.v2.runtime-external-payload-reference.v1 y un reference_id opaco. No tiene un uri de proveedor. La subida y descarga usan la credencial y el espacio de nombres normales, verifican tamaño y SHA-256 y preservan las barreras del intento de tarea y lease al completar trabajo. El contrato HTTP describe rutas, límites y rechazos tipados. El soporte requiere un transporte compatible disponible, no solo un driver configurado.

Los siguientes helpers directos de proveedor sirven para almacenamiento y pruebas de aplicaciones que acceden deliberadamente a su propio proveedor. Usan otro esquema con URI. No son necesarios para clientes normales de Server o Cloud. Server rechaza los sobres external_storage de proveedor con HTTP 422 y external_payload_unsupported.

Para estos helpers directos, el esquema es EXTERNAL_PAYLOAD_REFERENCE_SCHEMA (durable-workflow.v2.external-payload-reference.v1). Los adaptadores no añaden dependencias de SDK de nube a durable-workflow; la aplicación proporciona sus clientes S3, GCS o Azure configurados.

La referencia del proveedor tiene estos campos. No es la referencia del runtime aceptada por las rutas HTTP de Server:

  "schema": "durable-workflow.v2.external-payload-reference.v1",
  "uri": "s3://dw-payloads/billing/run-001/input.avro",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "size_bytes": 1048576,
  "codec": "avro",
  "expires_at": "2026-05-22T00:00:00Z"

ExternalPayloadReference.from_dict() rechaza esquemas desconocidos y campos incorrectos. fetch_external_payload() verifica size_bytes y sha256 antes de devolver bytes y lanza ExternalPayloadIntegrityError si tamaño o hash difieren. Un objeto ausente también puede generar el error del driver. Usa ExternalPayloadCache solo para bytes verificados. Desalojar la caché no autoriza a borrar un objeto gestionado por Server. delete_external_payload() opera directamente sobre el proveedor, no es una API de limpieza de referencias del runtime.

Usa external_storage_driver_from_policy() en código que accede deliberadamente al almacenamiento de la aplicación y posee el cliente necesario. Leer la política no convierte los sobres de proveedor en solicitudes válidas a Server. Los clientes pertenecen a la aplicación. Los adaptadores opcionales no añaden boto3, google-cloud-storage o azure-storage-blob como dependencias del runtime:

from durable_workflow.external_storage import external_storage_driver_from_policy

namespace = await client.describe_namespace("billing")
driver = external_storage_driver_from_policy(
    namespace.external_payload_storage,
    s3_client=application_owned_s3_client,
)

La factoría lanza ValueError si la política está desactivada, el driver no está admitido o falta el cliente necesario. Una política desactivada no devuelve un driver vacío. Comprueba policy.enabled antes de pedirlo.

Los helpers directos requieren acceso al proveedor propiedad de la aplicación; describir una política no hace válidos los sobres de proveedor en solicitudes a Server.

Identidad del workflow actual​

Desde Python SDK 2.9.0, el código del workflow puede leer ctx.workflow_id y ctx.run_id, propiedades de solo lectura. Ambas son cadenas de la tarea actual y conservan el mismo valor durante la reproducción. Con continue-as-new, el ID del workflow no cambia y el sucesor recibe su propio ID de ejecución. No lo sustituya por el ID del predecesor recibido como argumento.

from durable_workflow import workflow

@workflow.defn(name="identity")
class IdentityWorkflow:
    def run(self, ctx):
        identity = {"workflow_id": ctx.workflow_id, "run_id": ctx.run_id}
        yield ctx.schedule_activity("record_identity", [identity])
        return identity

Estas propiedades leen la identidad local de la tarea sin una petición HTTP. Para consultar el estado fuera del código del workflow, use await client.describe_workflow(workflow_id). Use await client.query_workflow(workflow_id, query_name) para el estado expuesto por un manejador de consultas registrado. Las propiedades de identidad no sustituyen ninguna de estas operaciones.

Definir workflows​

Los workflows son clases Python decoradas con @workflow.defn. run es una función síncrona normal o un generador síncrono que produce comandos durables para el servidor. Use el generador cuando el workflow necesite trabajo durable; async def run no está admitido.

from durable_workflow import workflow

@workflow.defn(name="order-processing")
class OrderWorkflow:
    def run(self, ctx, *args):
        order = args[0] if args else {}

        # Schedule an activity and wait for the result
        validated = yield ctx.schedule_activity(
            "validate_order", [order]
        )

        # Start a timer (durable sleep)
        yield ctx.start_timer(seconds=60)

        # Schedule another activity
        receipt = yield ctx.schedule_activity(
            "process_payment", [validated]
        )

        return receipt

El name de @workflow.defn(name="...") es la clave de tipo compartida entre lenguajes. Debe ser una cadena simple, no una ruta de módulo ni referencia de clase.

Señales, consultas y actualizaciones​

Las señales se registran en historial duradero y se entregan a manejadores Python durante la reproducción:

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False
        self.approved_by = None

    @workflow.signal("approve")
    def approve(self, by: str) -> None:
        self.approved = True
        self.approved_by = by

    def run(self, ctx, *args):
        ready = yield ctx.wait_condition(
            lambda: self.approved, key="approval.approved", timeout=60,
        )
        return {
            "status": "approved" if ready else "timed_out",
            "approved": self.approved,
            "approved_by": self.approved_by,
        }

La espera pertenece al workflow, no a una actividad. Su predicado lee el estado del manejador de señales reconstruido durante el replay; el worker no mantiene ocupado un slot de actividad mientras espera la aprobación. El timeout de la condición es independiente de los plazos finitos del run y de la ejecución completa. Para completar trabajos externos, use una actividad corta que envíe y regrese, junto con un callback correlacionado.

Los decoradores receptores de consultas y actualizaciones publican nombres estables de manejador. Los workers ejecutan consultas enrutadas por el servidor reproduciendo el historial confirmado e invocando el manejador sobre ese estado. También aplican actualizaciones aceptadas recibidas en tareas de workflow:

@workflow.defn(name="approval")
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False

    @workflow.query("status")
    def status(self) -> dict:
        return {"approved": self.approved}

    @workflow.update("set_approval")
    def set_approval(self, approved: bool) -> dict:
        self.approved = approved
        return {"approved": self.approved}

    @set_approval.validator
    def validate_set_approval(self, approved: bool) -> None:
        if not isinstance(approved, bool):
            raise ValueError("approved must be boolean")

Los workers completan consultas devolviendo un resultado al servidor. Si se declara un validador de actualizaciones, reciben una tarea de validación dedicada, reproducen el estado autorizado e invocan solo el validador. El servidor no registra aceptación ni despacha el manejador hasta validar. Los workers con validadores rechazan registrarse salvo que el descubrimiento anuncie el contrato síncrono previo a aceptación. Rechazo, workers ausentes o incompatibles, pérdida de worker, vencimiento y finalizaciones duplicadas u obsoletas bloqueadas siguen siendo resultados tipados explícitos. PHP y Rust no ofrecen actualmente API de creación de validadores y anuncian esa ausencia en sus contratos, sin afirmar paridad de validación.

Ciclo de vida de los manejadores​

Validación publicada. El SDK Python 2.6.2 incorporó las protecciones de manejadores descritas a continuación. Las consultas asíncronas y los validadores de actualización enrutados por Server siguen admitidos. Consulte el alcance corregido en SDK #177.

Cada replay construye una nueva instancia del workflow antes de ejecutar run(). Las señales ya registradas al inicio se aplican después de que run() alcance su primer yield, por lo que el constructor y la inicialización anterior al yield se ejecutan primero. Los manejadores de señales y actualizaciones modifican ese estado reconstruido. Las consultas lo inspeccionan sin cambiar el estado durable; los validadores inspeccionan un estado reconstruido desechable antes de aceptar la actualización. Coloque los comandos durables de actividades, temporizadores y workflows hijos en run(), no en un manejador.

ManejadorForma admitida y resultado de un fallo
@workflow.signalFunción síncrona. Una excepción al aplicar la señal durante el replay hace fallar la ejecución del workflow.
@workflow.updateFunción síncrona. Una excepción del manejador hace fallar esa actualización.
@workflow.update_validator o @update_method.validatorFunción síncrona o async def en el Worker. Una excepción rechaza la actualización antes de aceptarla.
@workflow.queryFunción síncrona o async def en el Worker. Una excepción del manejador hace fallar la consulta, no la ejecución del workflow.

La validación rechaza funciones de corrutina para señales y actualizaciones, y funciones generadoras o generadoras asíncronas para todos los tipos de manejadores decorados, incluidas las consultas y los validadores. Lanza InvalidWorkflowDefinition al definir, registrar o reproducir, también para manejadores heredados y herramientas sin conexión. Los envoltorios síncronos de señales y actualizaciones no pueden eludir las protecciones devolviendo valores asíncronos. Devolver valores generadores o generadores asíncronos se rechaza para cualquier tipo de manejador. Estas restricciones no prohíben el generador síncrono de run().

Para una consulta enrutada por Server, el Worker espera explícitamente el resultado asíncrono bajo el plazo original de la consulta y su autoridad de claim/cancelación. Esa espera no concede un nuevo presupuesto ni permite un resultado después de perder la autoridad. Para la validación previa a la aceptación, el Worker también espera el resultado asíncrono del validador sobre un estado reconstruido desechable.

Los helpers locales síncronos no pueden esperar. workflow.query_state() rechaza un resultado asíncrono con QueryFailed, y workflow.validate_update() lo rechaza con UpdateRejected. Cierran las corrutinas devueltas en vez de filtrarlas como resultados de las operaciones.

Compatibilidad de entrada y recuperación​

Soporte publicado. El SDK Python 2.6.2 incorporó la protección de entrada descrita a continuación, con enrutamiento y recuperación en Server 2.9.9. Son las versiones mínimas para estas funciones; instale las versiones estables actuales para recibir correcciones de seguridad.

Antes de llamar a run(ctx, *start_input), el worker vincula los argumentos registrados con la firma de entrada. Un argumento obligatorio ausente o una cantidad de argumentos incompatible provoca WorkflowEntryArgumentsMismatchError con motivo workflow_entry_arguments_mismatch antes de ejecutar el cuerpo. Los valores predeterminados solo rellenan argumentos omitidos. Las anotaciones de Python siguen sin imponerse: cambiar una anotación no valida ni convierte los datos registrados. Un TypeError lanzado después de entrar en un cuerpo normal o generador sigue siendo un fallo de aplicación.

El worker anuncia workflow_entry_arguments_validation automáticamente. Con un Server validado, la tarea fallida queda bloqueada para replay y la ejecución original permanece no terminal. Los runtimes anteriores pueden reintentar la tarea; el rechazo del SDK por sí solo no establece el contrato completo de recuperación.

Inspeccione la ejecución exacta con await client.describe_workflow_run(workflow_id, run_id) y el endpoint de depuración de la ejecución seleccionada. Tras restaurar un método de entrada compatible, use la ruta HTTP de reparación seleccionada del procedimiento de recuperación. await client.repair_workflow(workflow_id) y handle.repair() resuelven en cambio la ejecución actual de la instancia; ninguno acepta un argumento de run id. Conserve la entrada, el historial, el namespace, la cola, el build y los plazos originales. Para cambiar comandos, coloque ctx.get_version dentro de ese método compatible y valide el replay en frío mediante el enrutamiento de definiciones.

Tiempo del workflow y esperas duraderas​

Durante la reproducción del worker, ctx.now() devuelve la hora de inicio persistida del run. No avanza tras una actividad, temporizador, señal ni otro paso duradero. Las reproducciones en frío del mismo historial devuelven ese mismo valor inicial. Un sucesor de continue-as-new tiene su propia hora de inicio; no conserva el ancla del reloj de su predecesor.

La implementación publicada de Python usa WorkflowStarted.payload.timestamp cuando existe y, si no, el valor canónico WorkflowStarted.recorded_at. Si falta la hora persistida de reproducción o no es válida, se produce un error explícito de reloj, no se lee el reloj de pared del worker. Este es el contrato de inicio fijo acordado en SDK #146.

Espera una operación duradera en vez de repetir un bucle hasta que cambie ctx.now():

from durable_workflow import workflow


@workflow.defn(name="wait_without_clock_loop")
class WaitWithoutClockLoop:
    def run(self, ctx):
        started_at = ctx.now()
        yield ctx.start_timer(30)
        return {
            "run_started_at": started_at.isoformat(),
            "after_wait": ctx.now().isoformat(),
        }

La finalización duradera del temporizador reanuda el workflow. Las dos marcas devueltas son la misma hora de inicio. Un bucle como while ctx.now() < deadline no pasa a falso solo porque se activen temporizadores.

Para una demora relativa, usa yield ctx.start_timer(seconds) o yield ctx.sleep(seconds). Usa la selección de la primera finalización cuando el trabajo deba competir con un temporizador duradero. Configura execution_timeout_seconds y run_timeout_seconds en client.start_workflow(...) cuando Server deba aplicar un plazo al workflow, incluso con los workers detenidos. Un tiempo de espera HTTP o de get_result() solo limita esa petición local; no sustituye el plazo persistido del workflow. Para conservar un plazo de aplicación en continue-as-new, pásalo explícitamente como entrada sin sustituir el plazo de ejecución original de Server.

Para medir el tiempo transcurrido dentro de una invocación de actividad, lee allí un reloj monotónico y devuelve la duración como resultado de la actividad. Para un plazo UTC externo, haz que una actividad consulte el reloj externo autoritativo y devuelva su decisión; el workflow reproduce ese resultado registrado. Nunca compares marcas UTC con valores monotónicos ni restes lecturas monotónicas de procesos o equipos diferentes. Restar ctx.now() no mide ni el tiempo de procesamiento activo ni el tiempo real transcurrido en Python.

Ordena eventos emitidos mediante secuencias​

Una marca temporal del workflow no es una clave de orden de eventos. Los eventos de Python marcados con ctx.now() pueden tener todos la misma hora. Usa offsets de Workflow Streams, la secuencia del outbox integrado correspondiente o un contador determinista local al workflow. Reintentos y plazos de actividades​

Usa ActivityRetryPolicy y argumentos de plazo en ctx.schedule_activity(...) cuando una llamada necesite otro presupuesto o límite que el intento único predeterminado:

from durable_workflow import ActivityRetryPolicy

receipt = yield ctx.schedule_activity(
    "process_payment",
    [validated],
    retry_policy=ActivityRetryPolicy(
        max_attempts=4,
        initial_interval_seconds=1,
        backoff_coefficient=2,
        maximum_interval_seconds=30,
        non_retryable_error_types=["ValidationError"],
    ),
    start_to_close_timeout=120,
    schedule_to_close_timeout=300,
    heartbeat_timeout=15,

start_to_close_timeout limita un intento desde que el worker lo inicia. schedule_to_close_timeout limita la actividad completa entre todos sus intentos. heartbeat_timeout exige a actividades largas llamar a activity.context().heartbeat(...) antes de vencer el intervalo. La política queda fijada en la ejecución duradera al programar; despliegues posteriores no cambian intentos ya en curso.

ctx.schedule_activity(..., queue="payments-v2") selecciona la cola de una nueva ejecución de actividad. Las actividades ya registradas, sus reintentos y tareas reparadas conservan la cola original. Cambiar Worker.task_queue no traslada esas tareas ni la cola de workflow de las ejecuciones existentes. Mantén disponible el grupo antiguo compatible hasta tener en cuenta todas las dependencias; consulta las colas de actividad registradas.

Reglas de determinismo​

El código se reproduce desde historial. No debe realizar directamente operaciones no deterministas:

  • Sin E/S (HTTP, lecturas de archivos, consultas de base)
  • Sin datetime.now() ni time.time(); usa ctx.now() solo como ancla fija del inicio del run y temporizadores duraderos para esperar.
  • Sin random.random(); usa ctx.random()
  • Sin uuid.uuid4(); usa ctx.uuid4()

Todo no determinismo debe pasar por el contexto o capturarse con ctx.side_effect().

Bloques finally y gestores de contexto​

SDK 2.12.2 y posteriores. Una suspensión no equivale a salir del workflow. Al descartar una reproducción suspendida, Python puede ejecutar los bloques finally y las salidas de with. El SDK descarta los comandos duraderos y los mensajes de ctx.logger producidos únicamente por ese descarte; las consultas observan el estado en el comando pendiente. La finalización real, un fallo o la cancelación cooperativa ejecutan la limpieza mediante el historial normal; la reproducción en frío utiliza los resultados registrados.

Evita operaciones de E/S directas en esos bloques. Programa la limpieza externa como una actividad con yield ctx.schedule_activity(...) y envuélvela en with ctx.cancellation_shield(): si debe terminar tras la cancelación cooperativa.

Ejecución en paralelo​

Produce una lista de comandos para ejecutarlos concurrentemente:

@workflow.defn(name="fan-out-example")
class FanOutWorkflow:
    def run(self, ctx, *args):
        items = args[0]

        # Nested lists may mix activities, children, and timers.
        results = yield [
            ctx.schedule_activity("process_item", [items[0]]),
            [
                ctx.start_child_workflow("process-batch", [items[1:]]),
                ctx.start_timer(1),
            ],
        ]

        return results  # same nested shape and input order

El worker emite un comando normal por hoja duradera con campos estables compartidos parallel_group_* y la ruta completa de fuera hacia dentro. El historial puede cerrar miembros en cualquier orden; la reproducción asocia resultados y fallos por posición duradera de entrada. Ignora entregas terminales exactamente duplicadas. Tanto el historial pendiente tras reiniciar como el completado reconstruyen el mismo grupo sin reprogramar trabajo terminado.

Selección de la primera finalización​

Usa ctx.select() para iniciar trabajo independiente a la vez y avanzar al completar un miembro:

selected = yield ctx.select({
    "resolver": ctx.schedule_activity("resolve-request", [request_id]),
    "input": ctx.wait_condition(lambda: self.resolution is not None, key="resolution-ready"),
    "deadline": ctx.start_timer(2),

if selected.key == "deadline":

    return {"status": "timed_out"}

SelectionResult incluye clave estable, índice de entrada, tipo de operación, identidad duradera y resultado tipado del ganador, y todos los DurableOperationHandle. yield handle.await_result() espera después a un no ganador; yield handle.cancel() registra una petición explícita sin resultado. Solo SelectionOperationCancelled confirmado demuestra que ganó la cancelación. La reproducción avanza tras una petición sin marcador y await_result() sigue devolviendo la finalización que se confirmó primero. Consume el ganador persistido aunque un historial posterior contenga antes otra finalización. Entregas externas duplicadas o desordenadas no sustituyen un ganador confirmado.

Compensación de sagas​

def forward(saga):
    flight = yield ctx.schedule_activity("trip.reserve-flight", [])

return (yield from ctx.saga().run(forward))

            return result

        # Continue with incremented iteration
        return ContinueAsNew(arguments=[iteration + 1])

Definir actividades​

Las actividades son funciones asíncronas con @activity.defn. Pueden realizar E/S libremente, a diferencia de los workflows.

from durable_workflow import activity

@activity.defn(name="send_email")
async def send_email(to: str, subject: str, body: str) -> dict:
    # Activities can do I/O: HTTP calls, database queries, etc.
    response = await some_email_client.send(to=to, subject=subject, body=body)
    return {"message_id": response.id, "sent": True}

name es la clave compartida entre lenguajes. Un workflow PHP puede programar "send_email" y un worker Python recogerla, y viceversa.

Contexto de actividad​

Accede a metadatos y latidos dentro de la actividad con activity.context():

@activity.defn(name="long_running_task")
async def long_running_task(items: list) -> dict:
    ctx = activity.context()

    print(f"Attempt #{ctx.info.attempt_number}")
    print(f"Task queue: {ctx.info.task_queue}")

    for i, item in enumerate(items):
        # Check for cancellation
        if ctx.is_cancelled:
            return {"partial": True, "processed": i}

        await process(item)

        # Heartbeat to keep the task alive
        await ctx.heartbeat({"progress": i + 1, "total": len(items)})

    return {"processed": len(items)}

Política de reintentos recibida e intento original​

Requiere Python SDK 2.12.0 o posterior. info = activity.context().info expone el attempt_number original y una instantánea inmutable retry_info. info.retry_info.policy() devuelve una copia nueva, incluidos los campos desconocidos.

Una política ausente y retry_policy: null en la raíz tienen un límite desconocido. policy_provided las distingue (False y True). Un objeto de política recibido con max_attempts: null indica explícitamente intentos ilimitados: is_unlimited() devuelve True y max_attempts() sigue siendo None. Con un límite entero positivo, max_attempts() devuelve el límite e is_last_configured_attempt() lo compara con el intento original. Si el límite es desconocido, la comprobación del último intento devuelve None.

La comprobación describe el presupuesto recibido. La cancelación, los plazos, el cierre del workflow y los errores no reintentables pueden terminar antes. Los callbacks remotos ordinarios y supervisados reciben la instantánea original. Los callbacks locales inline y preparados no heredan la política remota del padre.

from durable_workflow import activity


@activity.defn(name="inspect_retry_budget")

    return {
        "attempt": retry.attempt_number,
        "max_attempts": retry.max_attempts(),

Enviar una señal a la ejecución original​

info.workflow_id e info.run_id conservan las identidades originales recibidas y pueden ser None. Los callbacks locales solo heredan identidades conocidas del padre. El SDK nunca las sustituye por un ID de tarea. Pase un cliente de la aplicación autorizado a este helper; el handle queda vinculado al run original:

from durable_workflow import Client, activity


async def signal_originating_run(client: Client, business_event_id: str) -> dict:
    info = activity.context().info
    if info.workflow_id is None or info.run_id is None:
        raise RuntimeError("This activity has no known originating workflow run")
    handle = client.get_workflow_handle(info.workflow_id, run_id=info.run_id)
    return await handle.signal(
        "payment_recorded",
        [business_event_id],
        request_id=f"payment-recorded:{business_event_id}",
    )

Mantenga business_event_id estable entre reintentos y dentro del límite de longitud de claves de comando del Server. El Server publicado actualmente no conserva estas claves en todas las rutas de señales. Procese los eventos de negocio de forma idempotente y reconcilie las entregas inciertas. Consulte la referencia canónica de actividades y el requisito de conservación de recibos de señales.

Peticiones de heartbeat​

Para actividades remotas, llame a await ctx.heartbeat(...) durante trabajo de actividad acotado, con suficiente antelación a heartbeat_timeout. La primera ventana empieza al reclamar la actividad en el entorno de ejecución, antes de que Python reciba la tarea. Cada heartbeat registrado usa el momento en que lo registra el entorno, no cuando su respuesta llega a Python. Las pausas, la latencia y los reintentos de transporte consumen el presupuesto. Siga las recomendaciones de cadencia.

La llamada directa a Client.heartbeat_activity_task() usa la TransportRetryPolicy configurada. Tras esa política, los errores de transporte pueden propagarse como httpx.TransportError, y los rechazos HTTP se convierten en excepciones del SDK, como ServerError. Son reintentos HTTP, no otro intento de actividad ni más tiempo para el heartbeat. ActivityContext.heartbeat() puede lanzar ActivityCancelled cuando el worker indica a la actividad que se detenga. Cuando la supervisión cooperativa de procesos está activada, los fallos de heartbeat o de titularidad pueden detener o abandonar el callback. No suponga que todos los fallos vuelven a un bloque de captura ni que la limpieza siempre se ejecuta.

No suprima fallos de heartbeat o de titularidad para seguir haciendo trabajo externo o informar de éxito. El progreso no es una confirmación externa ni un recibo de punto de control reanudable. Mantenga idempotentes los efectos externos.

Rechazo de heartbeats y salida del callback​

En Python SDK 2.9.0, ctx.heartbeat() y ctx.heartbeat_sync() lanzan ActivityLeaseAuthorityLost cuando una respuesta de heartbeat indica can_continue=false. La excepción conserva el motivo original del Server, como activity_deadline_elapsed, attempt_closed o run_closed. Una solicitud de cancelación lanza ActivityCancelled. Consulte la validación del SDK publicado.

El heartbeat que observa el rechazo es un punto de salida cooperativa. Detenga el trabajo externo y propague la excepción; no la capture para devolver un resultado correcto. El código que nunca envía heartbeats puede seguir ejecutándose hasta retornar. Un heartbeat auxiliar no puede interrumpir por la fuerza una llamada bloqueada de una biblioteca: use plazos finitos de E/S y el mecanismo de cancelación de la propia llamada.

La plaza física de actividad permanece ocupada hasta que sale el callback/hilo. Perder la autoridad del intento no libera ese hilo para otro trabajo, y el worker no publica un resultado tardío del intento cerrado. Aplicar el timeout del runtime y detener el código de la aplicación son límites distintos. Consulte los timeouts de actividad y la guía del hilo auxiliar.

Errores no reintentables​

Lanza NonRetryableError para fallar sin reintentos:

from durable_workflow import NonRetryableError

@activity.defn(name="validate")
async def validate(data: dict) -> dict:
    if "required_field" not in data:
        raise NonRetryableError("Missing required_field")
    return data

Errores de negocio terminales​

non_retryable_error_types compara exactamente el nombre corto (exception_type) o el nombre de clase cualificado (exception_class) de la excepción exterior. Por ejemplo, ValidationError no coincide con SpecificValidationError, aunque sea una subclase. Una entrada cualificada como app.errors.ValidationError debe coincidir con la clase registrada. La política no recorre subclases ni causas. raise RuntimeError(...) from NonRetryableError(...) comunica el RuntimeError exterior y puede seguir reintentándose.

Al convertir una excepción de negocio conocida, lance NonRetryableError como excepción exterior y conserve la causa original de Python mediante cause=error. Esto marca el fallo de actividad como no reintentable sin depender de una lista de nombres. No hace fallar automáticamente el workflow completo: este recibe ActivityFailed cuando no quedan reintentos, por una negativa no reintentable o por agotar el presupuesto de intentos.

from durable_workflow import ActivityFailed, NonRetryableError, activity, workflow

@activity.defn(name="validate_order")
async def validate_order(order: dict) -> dict:
    try:
        if order.get("amount", 0) <= 0:
            raise ValueError("amount must be positive")
    except ValueError as error:
        raise NonRetryableError("Order validation failed", cause=error) from error
    return order

@workflow.defn(name="place_order")
class PlaceOrderWorkflow:
    def run(self, ctx, order: dict):
        try:
            yield ctx.schedule_activity("validate_order", [order])
        except ActivityFailed as failure:
            if (
                failure.activity_type != "validate_order"
                or failure.exception_type != "NonRetryableError"
                or not failure.non_retryable
            ):
                raise
            return {"order_id": order["id"], "status": "rejected"}
        return {"order_id": order["id"], "status": "accepted"}

Con la entrada {"id": "order-123", "amount": 0}, la actividad falla una vez y el workflow completa normalmente con status: rejected. Maneje solo el fallo de negocio previsto; el ejemplo vuelve a lanzar los demás. Continúe con otros pasos durables si lo requiere su flujo. Un ActivityFailed no capturado hace fallar el workflow. Conservar la causa Python no significa que la política examine esa cadena ni que todos los SDK expongan un objeto de causa idéntico.

Actividades síncronas y asíncronas​

Las actividades remotas normales con def se ejecutan en un grupo de hilos dedicado, limitado por max_concurrent_activity_tasks. Cada función conserva su contexto de actividad. El sondeo, las tareas de workflow y los heartbeats del worker pueden avanzar mientras una función está bloqueada. Las actividades con async def se ejecutan en el bucle de eventos y deben usar E/S no bloqueante; una llamada bloqueante dentro de una función asíncrona también bloquea ese bucle.

Desde una función síncrona, llame a activity.context().heartbeat_sync(details) para enviar el progreso mediante el bucle de eventos responsable, con la identidad original de la tarea, el intento y el worker. Las funciones asíncronas usan await activity.context().heartbeat(details).

Cancelar una espera no detiene un hilo de Python que ya está ejecutándose. Su slot físico permanece ocupado hasta que la función retorna, y un retorno tardío no envía ningún resultado después de la cancelación. Si una función sigue ejecutándose tras shutdown_timeout, el cierre lanza RuntimeError y conserva el registro del worker. Limite los tiempos de espera de E/S de los servicios invocados y use procesos de worker aislados para trabajo intensivo de CPU. Consulte la referencia de ejecución y cierre del SDK.

Heartbeats desde un hilo auxiliar​

Para una llamada larga y bloqueante, captura ctx = activity.context() dentro de la actividad síncrona y pásalo al hilo auxiliar. Un hilo nuevo no hereda automáticamente el contexto de actividad. Usa ctx.heartbeat_sync(details) desde el auxiliar, nunca desde el bucle de eventos del worker. Consulta la receta completa en la referencia del SDK.

Detén el auxiliar y espera su terminación con join() tanto si la llamada devuelve un resultado como si falla. Si un heartbeat lanza ActivityCancelled o ActivityLeaseAuthorityLost, solicita la cancelación cooperativa de la llamada y vuelve a lanzar la excepción original antes de devolver un resultado. Una excepción en el auxiliar no puede interrumpir por la fuerza una llamada bloqueada. Dale un plazo finito y un mecanismo de cancelación propios, y limita los tiempos de espera y reintentos de las peticiones de heartbeat. De lo contrario, el auxiliar puede seguir indicando actividad mientras el trabajo está colgado.

Worker​

Worker se registra, sondea tareas y las despacha a tus implementaciones.

Para procesos separados de workflow y actividad, sigue la guía ejecutable de separación de procesos. Cubre registros separados, colas compartidas o distintas, reintentos, plazas por rol y cierre ordenado.

from durable_workflow import Client, Worker

async with Client("http://localhost:8080", token="secret") as client:
    worker = Worker(
        client,
        task_queue="default",
        workflows=[GreeterWorkflow, OrderWorkflow],

Sesiones de worker​

Use WorkerSessionOptions cuando varias actividades remotas secuenciales necesiten un recurso local del mismo worker. Este ejemplo se ha comprobado con Python SDK 2.9.0 y Server 2.11.0; consulte los requisitos de versión de afinidad portable. Use un job_id único por ejecución del workflow para que una ejecución nueva no reutilice el identificador de una sesión terminal.

La caché siguiente es desechable. Cada actividad puede reconstruirla a partir de la entrada de negocio duradera, de modo que el nuevo titular no dependa de la memoria del proceso anterior:

from durable_workflow import ActivityFailed, WorkerSessionOptions, activity, workflow

# Disposable process-local state. Rebuild it from durable business input.
documents = {}

def ensure_document(job_id):
    rebuilt = job_id not in documents
    if rebuilt:
        documents[job_id] = {"text": "document:" + job_id}
    return documents[job_id], rebuilt

@activity.defn(name="prepare_document")
async def prepare_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id, "rebuilt": rebuilt}

@activity.defn(name="inspect_document")
async def inspect_document(job_id):
    document, rebuilt = ensure_document(job_id)
    return {"holder": activity.context().info.worker_id,
            "rebuilt": rebuilt, "text": document["text"]}

@workflow.defn(name="inspect_document_workflow")
class InspectDocumentWorkflow:
    def run(self, ctx, job_id):
        session = WorkerSessionOptions(
            session_id="documents:" + job_id,
            requirements=("fs:documents",),
            lease_seconds=5,
            ttl_seconds=60,
            max_concurrent_activities=1,
            allow_reacquire_after_failure=True,
        )
        options = dict(worker_session=session,
                       start_to_close_timeout=5,
                       schedule_to_start_timeout=12,
                       schedule_to_close_timeout=20,
                       retry_policy={"max_attempts": 1})
        try:
            prepared = yield ctx.schedule_activity("prepare_document", [job_id], **options)
            inspected = yield ctx.schedule_activity("inspect_document", [job_id], **options)
        except ActivityFailed as error:
            if error.activity_type not in {"prepare_document", "inspect_document"}:
                raise
            return {"status": "resource_unavailable", "job_id": job_id}
        return {"status": "inspected", "prepared": prepared, "inspected": inspected}

Registre ambas actividades y declare la capacidad requerida en el worker:

from durable_workflow import Worker

worker = Worker(
    client,
    task_queue="documents",
    workflows=[InspectDocumentWorkflow],
    activities=[prepare_document, inspect_document],
    capabilities=["fs:documents"],
)
await worker.run()

Inicie inspect_document_workflow en la cola de tareas documents con [job_id] como entrada. La primera actividad adquiere la sesión de forma diferida; la segunda usa el mismo titular mientras su concesión siga vigente. max_concurrent_activities=1 limita las actividades simultáneas de esa sesión. El enrutamiento de cola y las comprobaciones de capacidad siguen aplicándose. Estas concesiones y timeouts breves demuestran un comportamiento acotado; ajústelos al trabajo real y envíe heartbeats con suficiente antelación a la expiración.

Tras perder al titular o expirar la concesión, allow_reacquire_after_failure=True permite que otro worker apto readquiera la sesión. Debe reconstruir el recurso local. Los resultados de actividad ya confirmados se reproducen, pero los efectos no confirmados pueden repetirse: use identificadores duraderos e interacciones externas idempotentes. Una sesión no migra memoria, archivos ni descriptores abiertos.

El cierre explícito y la expiración del TTL absoluto son terminales para ese identificador de sesión. Una actividad posterior no puede reabrirlo y puede permanecer sin admisión hasta que se aplique el timeout configurado. Ejecute el rol de planificador/mantenimiento del Server de la receta de despliegue publicada; un proceso solo de API no basta para aplicar los timeouts. El workflow maneja el fallo definitivo de actividad con ActivityFailed y devuelve resource_unavailable; la aplicación puede elegir una sesión nueva y reconstruir a partir de la entrada de negocio. Este ejemplo no promete una excepción inmediata de sesión cerrada ni reabre automáticamente una sesión terminal.

Para gestionar explícitamente el ciclo de vida del titular, use worker.worker_session(options) y sus métodos create(), renew() y close(reason). El apagado ordenado del worker cierra sus sesiones. Consulte el contrato de ciclo de vida compartido.

execution = client.describe_workflow(workflow_id)
print(execution.status)

Refleja la API asíncrona, envolviendo cada llamada con asyncio.run.

La cancelación no se captura con except Exception deliberadamente​

WorkflowCancelled y ActivityCancelled heredan de BaseException, no de Exception. Un except Exception: genérico en una actividad o al esperar client.get_result() no las captura. La cancelación es un resultado de control; ocultarla permitiría informar de éxito tras pedir detener la actividad.

Si necesitas limpieza local al cancelar una tarea, captura la clase por nombre y vuelve a lanzarla. Esto no reanuda el workflow cerrado para compensarlo:

from durable_workflow import ActivityCancelled, activity

@activity.defn(name="long_task")
async def long_task(items: list) -> dict:
    ctx = activity.context()
    try:
        for i, item in enumerate(items):
            await process(item)
            await ctx.heartbeat({"progress": i + 1})
        return {"done": True}
    except ActivityCancelled:
        await cleanup_partial_state()
        raise

Sigue el precedente de asyncio.CancelledError y KeyboardInterrupt de la biblioteca estándar.

Pruebas​

El código de workflow se puede probar sin servidor ni worker activos. durable_workflow.testing incluye dos entradas:

  • WorkflowEnvironment lleva el workflow a término en un proceso con actividades simuladas registradas por el usuario.
  • replay_history y replay_history_file reproducen historial capturado de producción contra el código actual y fallan ante no determinismo.

Ambas reutilizan durable_workflow.workflow.replay, igual que el worker, de modo que el comportamiento del banco de pruebas coincide con el real.

WorkflowEnvironment​

Despacha comandos a simulaciones registradas y genera automáticamente temporizadores, efectos secundarios y actualizaciones de atributos. No necesita reloj real, Redis ni servidor.

from durable_workflow import workflow
from durable_workflow.testing import WorkflowEnvironment

@workflow.defn(name="greeter")
class Greeter:
    def run(self, ctx, name: str):
        greeting = yield ctx.schedule_activity("greet", [name])
        return greeting


def test_greeter_returns_activity_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("greet", "hello, world")

    result = env.execute_workflow(Greeter, "world")

    assert result == "hello, world"
MétodoFunción
register_activity_result(name, result)Devuelve result en cada llamada a name cuando no importan argumentos.
register_activity(name, fn)Llama fn(*arguments) por invocación programada si debe variar según argumentos o registrar llamadas.
register_child_workflow_result(workflow_type, result)Devuelve result al iniciar un hijo de ese tipo.
signal(name, args=None, run=None)Encola una señal antes de la siguiente reproducción. Inyecta SignalReceived y llama al manejador @workflow.signal. run=N apunta al eslabón N de continue-as-new.
register_workflow(workflow_cls)Permite resolver otra clase por nombre. Necesario si continue_as_new(workflow_type=...) usa otro tipo.

El banco de pruebas falla explícitamente si faltan datos simulados:

  • actividad sin simulación registrada: KeyError
  • hijo sin simulación registrada: KeyError
  • workflow que no termina dentro del límite de iteraciones (por defecto 1000): RuntimeError

Pasa iteration_limit=... a WorkflowEnvironment(...) para workflows que necesiten legítimamente más iteraciones.

Simulaciones de actividad invocables​

Usa register_activity para responder según argumentos o capturar llamadas:

def test_callable_mock_captures_arguments() -> None:
    captured: list[str] = []

    def record_greet(name: str) -> str:
        captured.append(name)
        return f"greeted:{name}"

    env = WorkflowEnvironment()
    env.register_activity("greet", record_greet)

    assert env.execute_workflow(Greeter, "alice") == "greeted:alice"
    assert captured == ["alice"]

Señales​

Las señales env.signal(...) se entregan antes de la siguiente reproducción. La carga se envuelve en {codec, blob}, como en ejecución real, y se despacha al manejador @workflow.signal:

@workflow.defn(name="approval")
class Approval:
    def __init__(self) -> None:
        self.approved_by: str | None = None

    @workflow.signal("approve")
    def on_approve(self, by: str) -> None:
        self.approved_by = by

    def run(self, ctx):
        yield ctx.schedule_activity("wait", [])
        return {"approved_by": self.approved_by}


def test_signal_is_delivered_before_run_returns() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("wait", None)
    env.signal("approve", ["alice"])

    result = env.execute_workflow(Approval)

    assert result == {"approved_by": "alice"}

Temporizadores, efectos secundarios y atributos de búsqueda​

Se genera automáticamente el evento correspondiente para que las pruebas no bloqueen por tiempo real:

  • ctx.sleep(seconds) → TimerFired
  • ctx.side_effect(...) → SideEffectRecorded
  • ctx.upsert_search_attributes(...) → SearchAttributesUpserted
  • marcadores workflow.version(...) → VersionMarkerRecorded

Cadenas continue-as-new​

Cuando se devuelve ctx.continue_as_new(...), se añade WorkflowContinuedAsNew a la ejecución que termina, se reinicia el historial y comienza otra con los argumentos del comando. execute_workflow devuelve el resultado terminal final.

@workflow.defn(name="countdown")
class Countdown:
    def run(self, ctx, counter: int):
        yield ctx.schedule_activity("emit", [counter])
        if counter > 0:
            return ctx.continue_as_new(counter - 1)
        return {"final_counter": counter}


def test_chain_returns_final_run_result() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("emit", None)

    result = env.execute_workflow(Countdown, 3)

    assert result == {"final_counter": 0}
    assert env.run_count == 4
    assert [r.input for r in env.runs] == [[3], [2], [1], [0]]

Si cambia el tipo, registra primero la clase siguiente:

@workflow.defn(name="stage-one")
class StageOne:
    def run(self, ctx):
        yield ctx.schedule_activity("stage_one", [])
        return ctx.continue_as_new(workflow_type="stage-two")


@workflow.defn(name="stage-two")
class StageTwo:
    def run(self, ctx):
        return (yield ctx.schedule_activity("stage_two", []))


def test_chain_can_switch_workflow_type() -> None:
    env = WorkflowEnvironment()
    env.register_workflow(StageTwo)
    env.register_activity_result("stage_one", None)
    env.register_activity_result("stage_two", "done")

    assert env.execute_workflow(StageOne) == "done"
    assert [r.workflow_type for r in env.runs] == ["stage-one", "stage-two"]

Dirige una señal a un eslabón concreto con run=N:

env.signal("approve", ["alice"], run=2)  # delivered to the second run

continue_as_new_limit limita la longitud (por defecto 50). Superarlo lanza RuntimeError para detectar continuaciones descontroladas. Ajusta con WorkflowEnvironment(continue_as_new_limit=...) si la cadena debe ser mayor.

Comprobaciones de fallos​

Las excepciones Python del workflow se presentan como WorkflowFailed:

import pytest
from durable_workflow.errors import WorkflowFailed

@workflow.defn(name="failing")
class Failing:
    def run(self, ctx):
        yield ctx.schedule_activity("step", [])
        raise RuntimeError("boom")


def test_workflow_failure_surfaces_as_workflow_failed() -> None:
    env = WorkflowEnvironment()
    env.register_activity_result("step", None)

    with pytest.raises(WorkflowFailed) as exc_info:
        env.execute_workflow(Failing)

    assert "boom" in str(exc_info.value)

Pruebas de reproducción con historial de producción​

Usa replay_history para probar regresiones contra historial real del servidor. Ejecuta el código actual con la secuencia registrada y falla si produce un comando distinto, que es la definición de un error de no determinismo.

from durable_workflow import Client
from durable_workflow.testing import replay_history

async with Client("http://localhost:8080") as client:
    history = await client.get_history("order-42", run_id="...")

replay_history(OrderWorkflow, history["events"], start_input=["order-42"])

Un workflow completado debe seguir completándose con el mismo historial. Si cambia el orden de actividades, se eliminan ramas o cambian tipos y diverge la secuencia, replay_history falla para detectar la regresión en CI, no producción.

replay_history_file lee JSON con una lista de eventos superior o un diccionario con clave events, como la respuesta de get_history:

from durable_workflow.testing import replay_history_file

replay_history_file(
    OrderWorkflow,
    "tests/histories/order-42.json",
    start_input=["order-42"],
)

Ambas aceptan payload_codec opcional como indicación de validación. Omítelo para usar la etiqueta registrada. La explícita o registrada debe ser avro. Cargas duraderas json, desconocidas o sin etiqueta fallan antes de decodificar.

Reproductor basado en clases​

Usa Replayer si una pasada prueba distintos tipos o debe dejar que WorkflowStarted elija cuál reproducir. Registra todas las clases y llama replay(...) por historial capturado:

from durable_workflow import Replayer, ReplayOutcome

replayer = Replayer(workflows=[OrderWorkflow, RefundWorkflow])

# Explicit type and input — equivalent to replay_history(OrderWorkflow, ...).
outcome: ReplayOutcome = replayer.replay(
    history["events"],
    start_input=["order-42"],
    workflow_type="order",
)

# Type and start input inferred from a WorkflowStarted event in the history.
outcome = replayer.replay(history)  # history may be an events list or a
                                    # dict with an "events" key

for command in outcome.commands:
    # Inspect commands the replayed workflow would have emitted next.
    ...

Replayer(workflows=[...]) rechaza un conjunto vacío o registros duplicados con ValueError. replay(...) lanza ValueError ante tipos no registrados, o si hay varios y no se proporciona workflow_type ni existe WorkflowStarted.

ReplayOutcome.commands es la misma lista que devuelven los auxiliares replay_history. La clase permite compartir un registro entre muchos historiales.

Códec de cargas​

Toda carga que cruza el protocolo de workers lleva etiqueta de códec. Durable Workflow 2.0 tiene un único códec público: avro. El SDK Python rechaza cargas duraderas etiquetadas JSON, desconocidas y sin etiqueta en vez de elegir otro decodificador. Consulta el protocolo Avro Value.

Soporte Avro incluido​

El artefacto SDK 2.0 fijado incluye fastavro como dependencia de ejecución. Todas las salidas (start_workflow, signal_workflow, query_workflow, update_workflow, resultados de actividad y acciones de programación) emiten cargas Avro por la ruta optimizada de producción. No hay un extra de códec opcional.

Valores tipados fijos​

El SDK selecciona explícitamente ramas con nombre del esquema compartido durable_workflow.protocol.Value, sin codificar JSON dentro de Avro. Enteros y dobles, cadenas y bytes, booleanos y enteros, listas y mapas se mantienen distintos entre SDK. Usa el encuadre Avro de objeto único y huella del esquema. Las huellas desconocidas fallan con unsupported_payload_schema.

Todas las interfaces funcionan de principio a fin con Avro predeterminado:

  • Inicios, señales, consultas y actualizaciones: start_workflow, signal_workflow, query_workflow y update_workflow emiten payload_codec = "avro" mediante Value fijo. Un cliente Python dirige workflows reproducibles por PHP y otros SDK y viceversa.
  • Worker de actividad: decodifica argumentos Avro transparentemente y codifica resultados Avro para compartir un límite de carga entre lenguajes.
  • Fallos de actividad: fail_activity_task(..., details=...) envía failure.details como {codec, blob}. El servidor registra el blob y details_payload_codec, conservando diagnósticos independientes del lenguaje en exportaciones y vistas.
  • Reproducción de historial: decodifica entrada y resultados de actividad Avro para que workflows Python participen en ejecuciones Avro.
  • Tareas de consulta: transportan argumentos de workflow y consulta e historial etiquetados Avro. El resultado también es un sobre Avro.

Worker de actividad Python contra una ejecución v2​

No hace falta configurar códec. Valida payload_codec antes de decodificar cada reclamación, acepta solo avro, ejecuta y devuelve resultado Avro. Otras etiquetas se rechazan con unsupported_payload_codec; nunca inspecciona ni adivina formatos.

Ejecutar contra un servidor compartido​

El inicio rápido muestra un servidor local con imagen publicada. En equipo, normalmente apuntas el worker a un servidor existente de pruebas, producción o desarrollo compartido:

from durable_workflow import Client

client = Client(
    "https://workflow.example.internal",
    control_token="team-orders-operator-token",
    worker_token="team-orders-worker-token",
    namespace="team-orders",
)

Establece namespace con el provisionado para tu equipo y usa sus credenciales. El operador de Server crea namespaces. Consulta la guía de Server.

El mismo constructor sirve para Cloud. Usa su URL y namespace, control_token con la credencial de cliente y worker_token con la de worker. Cloud provisiona el namespace: no sustituyas por una dirección autogestionada. Consulta Entorno gestionado de Cloud.

Páginas de lista e historial de workflows​

Estas llamadas publicadas devuelven una página, no una lectura completa automática: await client.list_workflows(...) / await client.get_history(workflow_id, run_id, ...). Continúe con el token opaco devuelto manteniendo namespace, filtros y workflow/ejecución seleccionados; termine con token nulo/vacío y gestione los errores de página. Una página parcial no es un bundle de reproducción. Use la API de exportación de historial del SDK para reproducción sin servidor. El cliente publicado Python 2.9.0 define los parámetros actuales; no se implica un nuevo iterador.

Referencia de configuración de Server

Esta página documenta el contrato de variables de entorno DW_* para los operadores de la imagen de Durable Workflow Server. Úsela al crear plantillas de despliegue, revisar la configuración de producción o migrar los nombres antiguos WORKFLOW_* / ACTIVITY_* al contrato v2 de Server.

Server también utiliza la configuración habitual de Laravel, como DB_*, REDIS_*, QUEUE_CONNECTION y CACHE_STORE. Estas variables de infraestructura se enumeran por separado porque conectan los componentes del despliegue y no controlan la API de Durable Workflow.

Cuándo se aplican los cambios​

La imagen publicada de PHP Server ejecuta php artisan config:cache en su punto de entrada. Los valores de entorno se resuelven durante ese arranque y se guardan en la caché de configuración de Laravel. Editar un archivo de entorno, cambiar las variables declaradas en el orquestador o reemplazar un archivo de configuración montado no recarga un despliegue que ya está en ejecución.

Reinicie o reemplace todos los procesos afectados con la nueva configuración: réplicas de la API HTTP, workers locales de colas de Laravel y procesos del planificador. Reinicie por separado los workers persistentes de los SDK cuando cambie su propia configuración de cliente o worker. Reiniciar correctamente la API no actualiza un worker de cola o planificador que sigue en ejecución. Mantenga la misma configuración prevista en los roles que comparten una base de datos y una caché.

Durante una actualización gradual, cada nodo aplica sus propios límites cargados. Los contadores compartidos de admisión no hacen que nodos con distinta configuración coincidan en un límite. Una solicitud puede aceptarse en una réplica de la API y rechazarse en otra. Para aplicar un cambio de límite de forma coherente:

  1. Pause los nuevos envíos de los clientes y retire las réplicas afectadas de la API del tráfico de entrada. Espere a que terminen las solicitudes en curso. Detenga de forma ordenada los roles de cola y del planificador afectados, respetando sus plazos de apagado.
  2. Aplique la misma configuración a cada rol afectado y reinícielo o reemplácelo. Deje que el punto de entrada de cada contenedor reconstruya su caché de configuración.
  3. Compruebe los registros de arranque para detectar errores de configuración, verifique la disponibilidad y pruebe el límite modificado antes de restaurar el tráfico y los envíos. Consulte la guía de despliegue y disponibilidad.

La configuración del operador almacenada en la base de datos tiene otro ciclo de vida. Las modificaciones siguientes, cuando se realizan correctamente, están disponibles para las operaciones posteriores sin reiniciar Server:

OpciónCambio en vivoAlcance y límites
Descripción y retención del namespacePUT /api/namespaces/{namespace}, o dw namespace:updateLa política se aplica en las siguientes pasadas de retención. Cambiarla no restaura los datos ya podados. Consulte Retención de Server.
Política de almacenamiento externo de cargas del namespacePUT /api/namespaces/{namespace}/external-storageCambia la política almacenada del namespace. Las credenciales del proveedor, los discos configurados y otras opciones del proceso aún requieren el reinicio descrito arriba. Conserve el acceso a los objetos referenciados por ejecuciones existentes.
Definiciones de atributos de búsqueda del namespacePOST / DELETE /api/search-attributesActualiza el registro que usarán las siguientes solicitudes. No reescribe el historial del workflow ni reemplaza los límites de tamaño y cantidad configurados mediante el entorno.

Los valores predeterminados y los límites DW_* de esta referencia siguen siendo configuración del proceso, salvo que una operación documentada del plano de control cambie explícitamente el estado almacenado. Server no sondea los archivos de configuración para detectar cambios.

Cómo se aplica el contrato​

El repositorio de Server conserva el contrato canónico en config/dw-contract.php. Durante el arranque del contenedor, php artisan env:audit avisa si encuentra variables DW_* desconocidas o nombres antiguos. Establezca DW_ENV_AUDIT_STRICT=1 para que el punto de entrada falle en vez de arrancar con advertencias.

DW_ENV_AUDIT_STRICT=1
DW_AUTH_DRIVER=token
DW_ADMIN_TOKEN="${DW_ADMIN_TOKEN}"
DW_OPERATOR_TOKEN="${DW_OPERATOR_TOKEN}"
DW_WORKER_TOKEN="${DW_WORKER_TOKEN}"

Los nombres antiguos solo se usan como alternativa. Prefiera el nombre DW_* en cada despliegue nuevo y trate las advertencias sobre nombres antiguos como una migración pendiente, aunque Server aún respete su valor.

Preferencia de fingerprint publicada. Server 2.9.9 hace efectiva la preferencia de fingerprint para los workers de servicio. Con la asignación activada, una definición modificada solo puede actuar como alternativa cuando no queda un worker elegible con la definición registrada y la sustitución anuncia workflow_entry_arguments_validation. Al desactivarla, se elimina la preferencia de código; se conservan las asignaciones de build, el aislamiento de namespace/cola/tipo, la identidad de inscripción y el replay estricto. Las protecciones de entrada correspondientes están disponibles desde los SDK PHP 2.5.4, Python 2.6.2 y Rust 3.5.6. Son las versiones mínimas para estas funciones; instale las versiones estables actuales con correcciones de seguridad. No suponga este comportamiento en un runtime anterior solo porque contenga la misma clave de configuración. Consulte el enrutamiento de definiciones.

Use DW_V2_GUARDRAILS_BOOT en CI y en los manifiestos de despliegue. El nombre antiguo WORKFLOW_V2_GUARDRAILS_BOOT se conserva solo para que env:audit indique el nuevo nombre a los operadores de la etapa alfa. El paquete Workflow ya no lo lee como alternativa en tiempo de ejecución.

Consulte Asignación y despacho de tareas al configurar DW_V2_MATCHING_ROLE_QUEUE_WAKE o un daemon dedicado de workflow:v2:repair-pass --loop. Estas opciones cambian dónde se descubren las tareas listas, no el contrato del protocolo de workers.

TLS de base de datos​

Configura los mismos valores TLS en el servidor API, el worker de cola, el trabajo de inicialización/migración y el planificador. PostgreSQL usa prefer por defecto; MySQL/MariaDB conservan sus valores de conexión si no se indica modo. Ninguno garantiza una conexión cifrada y autenticada.

DB_SSLMODEPostgreSQLMySQL / MariaDB
disableSin TLS.Sin TLS; se rechazan opciones TLS contradictorias.
allow, preferTLS oportunista sin garantía de cifrado o identidad.Rechazados.
requireCifrado obligatorio.Cifrado obligatorio con mysqlnd y OpenSSL.
verify-caCifrado y cadena de certificados de confianza obligatorios.Rechazado: PDO mysqlnd no puede verificar solo la cadena sin verificar el hostname.
verify-fullCifrado, cadena de confianza y hostname coincidente obligatorios.Cifrado, cadena de confianza y hostname coincidente obligatorios.

DB_SSL_MODE es alias de DB_SSLMODE; DB_SSL_ROOT_CERT, de DB_SSLROOTCERT. Para verificar certificados, monta un archivo CA legible en la ruta configurada en todos los roles, incluidas las migraciones. MYSQL_ATTR_SSL_CA puede aportar la CA para verify-full explícito en MySQL/MariaDB. Los valores contradictorios entre nombres canónicos, alias o URL impiden el arranque. TLS obligatorio requiere un hostname TCP explícito; se rechazan sockets Unix. Los modos TLS explícitos de MySQL/MariaDB necesitan PDO MySQL con mysqlnd y OpenSSL.

DB_CONNECTION=pgsql
DB_HOST=database.example.com
DB_SSLMODE=verify-full
DB_SSLROOTCERT=/run/database-ca/ca.pem

Usa el nombre DNS del certificado. En Helm, configura externalDatabase.sslMode y externalDatabase.tls.existingSecret / caKey. Crea el Secret antes de instalar o actualizar; el chart monta su CA en los cuatro roles, incluido el hook de inicialización. Reinicia los roles persistentes al cambiar el entorno: la configuración se almacena en caché al arrancar.

Registros de contenedores​

Establece LOG_CHANNEL=stderr en los contenedores de API, workers y planificador para que docker logs o kubectl logs recopilen los registros de la aplicación. Configúralo explícitamente en las versiones existentes. Usa LOG_LEVEL para elegir la gravedad mínima. Para JSON con un registro por línea, añade:

LOG_STDERR_FORMATTER="Monolog\Formatter\JsonFormatter"

Reinicia los procesos persistentes después de cambiar estas opciones, ya que la configuración se almacena en caché al arrancar. Un canal de archivo elegido explícitamente necesita almacenamiento y recopilación propios; Kubernetes no recopila storage/logs/laravel.log automáticamente. DW_LOG_FORMAT no es una opción admitida.

Notas de migración​

Al migrar un despliegue antiguo, cambie primero al nombre público y deje sin definir el nombre antiguo. Si ambos están presentes, los operadores deben considerar el valor DW_* y eliminar el nombre antiguo.

# Before
WORKFLOW_SERVER_AUTH_DRIVER=token
WORKFLOW_SERVER_OPERATOR_TOKEN=operator-secret

# After
DW_AUTH_DRIVER=token
DW_OPERATOR_TOKEN=operator-secret

Tras la migración, ejecute la imagen de Server con DW_ENV_AUDIT_STRICT=1 para detectar variables mal escritas, alias obsoletos y opciones copiadas de procedimientos antiguos.

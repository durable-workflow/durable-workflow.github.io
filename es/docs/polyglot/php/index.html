Versión: 2.x

SDK de PHP

Utiliza durable-workflow/sdk cuando una aplicación PHP o un worker remoto se conecte a Durable Workflow Server independiente o a la URL del runtime de un espacio de nombres de Durable Workflow Cloud. Este SDK oficial es independiente del framework: ofrece cliente del plano de control, autenticación, transporte, códec público de cargas útiles, manejador de reproducción y ciclo de vida gestionado de workers remotos sin necesitar Laravel ni el paquete del motor integrado.

Probar el entorno local de Sample App​

Para la ruta de autoría más breve sin Cloud, abre la rama main actual de Sample App en GitHub Codespaces y ejecuta:

scripts/playground php

El entorno local genera código de workflow y actividad propiedad del usuario, selecciona los artefactos estables actuales e inicia Server y Waterline publicados. Antes de iniciar el workflow, espera un registro de worker cuya identidad, tipo de workflow, tipo de actividad y cola coincidan con el contrato generado. El éxito exige el resultado completado y el historial esperados; después el terminal imprime el enlace local exacto a la ejecución en Waterline y la ruta a la evidencia JSON estructurada.

El inicio rápido y la referencia de API mantenidos por el paquete siguen siendo la ruta directa para añadir el SDK a un proyecto existente sin Sample App.

Entorno de ejecución gestionado

Durable Workflow Cloud

Ejecuta clientes y workers PHP contra un espacio de nombres gestionado por Cloud con credenciales separadas por rol.

Ver precios de Cloud Dev

Para incorporación paso a paso, integración de frameworks, pruebas, despliegue y resolución de problemas, utiliza el portal para desarrolladores PHP. Para firmas exactas de constructores, tipos de retorno y clases de excepción, utiliza su referencia de API generada independiente. El contrato legible por máquinas identifica paquete, formas de runtime, credenciales por rol, archivos de código incluidos, resultado esperado y prueba básica con artefactos publicados como una única ruta probada.

Los clientes de Cloud utilizan la URL del runtime y el espacio de nombres devueltos al aprovisionar, con credenciales separadas de cliente y worker. Consulta Runtime gestionado de Cloud para ese límite de conexión; los ejemplos siguientes utilizan el mismo SDK con valores locales autohospedados.

Utiliza durable-workflow/workflow para la ruta independiente de Laravel integrado, donde la aplicación posee el estado de workflows en su base de datos y ejecuta el trabajo mediante sus colas Laravel. Consulta Modos de despliegue para comparar responsabilidades.

Requisitos​

  • PHP 8.1 o posterior
  • Un Server autohospedado accesible o un runtime de espacio de nombres de Cloud aprovisionado

Instalar​

Instala el SDK de PHP publicado actual. El requisito exacto siguiente se genera desde la autoridad de artefactos publicados actualizada desde el registro, y Composer guarda el paquete resuelto en composer.lock:

composer require durable-workflow/sdk:3.2.0

El SDK utiliza el paquete Composer oficial apache/avro para el sobre público de cargas útiles. Sus dependencias de producción excluyen Laravel, Illuminate, durable-workflow/workflow y durable-workflow/server.

Iniciar e inspeccionar un workflow​

El inicio rápido del SDK crea un proyecto Composer limpio, define un workflow y una actividad con atributos, inicia el worker, inicia un workflow único y espera el resultado. Los mismos archivos incluidos bootstrap.php, worker.php y client.php se instalan desde el paquete y se ejecutan en la prueba protegida de artefactos publicados; esta página no mantiene una segunda copia del código.

Elige únicamente el valor de conexión al runtime:

RuntimeValor pasado a ClientComportamiento de las rutas de solicitud del SDK
Server autohospedadoOrigen sin ruta, como http://localhost:8080Añade un segmento /api; quien llama no añade /api.
Durable Workflow CloudURI aprovisionada completa, como https://cloud.example/api/runtime/v1/namespaces/<runtime-id>Conserva la ruta del runtime del espacio de nombres y añade después /api del endpoint.

Abre la ruta PHP probada para los comandos exactos y el código visible. Las operaciones de cliente leen DURABLE_WORKFLOW_CLIENT_TOKEN; el sondeo del worker lee DURABLE_WORKFLOW_WORKER_TOKEN. La guía mantiene estas credenciales en procesos separados sin imprimirlas ni guardarlas en Git.

Worker::register() descubre manejadores #[Workflow] y #[Activity] en el mismo archivo. La guía también documenta la alternativa directa registerWorkflow()/registerActivity() para código basado en funciones. El arranque evita que el usuario tenga que elegir la ruta del autoloader cuando estos archivos se ejecutan en un proyecto independiente, checkout del SDK, paquete instalado o entorno/contenedor que los sitúe junto al directorio Composer vendor/.

WorkflowHandle sigue la ejecución actual después de continuar como nuevo. Utiliza sus métodos de ejecución seleccionada si una operación debe quedar restringida a una ejecución concreta.

Ciclo de vida, actualizaciones, programaciones y visibilidad​

El cliente público actual ofrece más que resultados de una ejecución seleccionada:

  • WorkflowHandle ofrece describe, result, signal, query, cancel y terminate, con variantes de ejecución seleccionada para mayor seguridad.
  • Client ofrece listWorkflows con filtrado y paginación del servidor, workflowHistory, updateWorkflow, cancelWorkflow y terminateWorkflow.
  • requestCancellation() solicita limpieza acotada a workers cooperativos. Los métodos existentes cancel() y cancelWorkflow() cierran la ejecución inmediatamente. Consulta cancelación cooperativa para el contrato de autoría y recuperación.
  • Los métodos de programación permiten crear, describir, listar, actualizar, pausar, reanudar, disparar, ejecutar retroactivamente y eliminar.
  • La visibilidad operativa incluye listNamespaces, listWorkers y listTaskQueues, con los métodos de descripción correspondientes.

Los workers remotos registran manejadores de workflow, actividad, consulta y actualización mediante registerWorkflow, registerActivity, registerQuery y registerUpdate. Consulta la referencia generada del SDK de PHP para los parámetros y tipos de retorno completos.

Heartbeats de actividad​

Para actividades remotas, llame a ActivityContext::heartbeat($details) durante trabajo de actividad acotado, con suficiente antelación al tiempo de espera de heartbeat. La primera ventana empieza al reclamar la actividad en el entorno de ejecución, no cuando PHP recibe la tarea. La latencia de las peticiones, las pausas y los reintentos de transporte consumen esa ventana. Siga las recomendaciones de cadencia.

El método devuelve void. En la ruta directa del manejador, una respuesta de detención lanza ActivityCancelled. Los fallos HTTP y de transporte de Client::heartbeatActivityTask() aparecen como ServerException. Un worker con supervisión cooperativa puede detener o abandonar su callback cuando falla un heartbeat o una comprobación de titularidad, en vez de entregar una respuesta normal al código de actividad. No suponga que la limpieza siempre se ejecutará, no suprima un error de pérdida de autoridad ni envíe éxito después de perderla.

Que la llamada retorne no confirma el trabajo externo ni proporciona un punto de control reanudable. Mantenga idempotentes los efectos externos y no trate un reintento de transporte como una nueva ventana de heartbeat.

Ejecutar un worker PHP remoto​

Los manejadores de workflow son funciones ordinarias que ejecutan código secuencial en una Fiber gestionada. Llama directamente a operaciones como WorkflowContext::activity(); el SDK suspende la Fiber en decisiones duraderas y devuelve resultados registrados durante la reproducción sin repetir la actividad externa. No declares workflows como Generator ni uses yield con comandos WorkflowContext: se rechazan los resultados Generator. El worker gestionado registra tipos de workflow y actividad, sondea el protocolo público, envía latidos, completa o falla tareas y gestiona el apagado ordenado cuando pcntl está disponible.

Selección de la primera finalización​

Utiliza WorkflowContext::select() para iniciar actividades diferidas independientes, workflows hijos, temporizadores, esperas de condición o barreras ordinarias anidadas y continuar desde el primer ganador confirmado de forma duradera. El SelectionResult devuelto contiene claves e identidades estables y un handle por miembro:

$selected = $ctx->select([
    'resolver' => fn () => $ctx->activity('resolve-request', [$requestId]),
    'input' => fn () => $ctx->waitCondition(
        fn (): bool => $this->resolution !== null,
        key: 'resolution-ready',
    ),
    'deadline' => fn () => $ctx->sleep(2),
]);

if ($selected->key === 'deadline') {
    $selected->handles['resolver']->cancel();
}

La selección no cancela los miembros que no ganan. Llama a await() en un handle para consumir su resultado eventual o a cancel() para registrar una cancelación explícita. Un worker recién iniciado o la reproducción de historial completo consume el ganador registrado aunque las entradas duplicadas o tardías y los eventos terminales lleguen en otro orden. cancel() devuelve void y no informa del resultado terminal. Solo el evento SelectionOperationCancelled demuestra que ganó la cancelación; la reproducción avanza más allá de una solicitud sin marca y, si la operación terminó primero, await() sigue devolviendo ese resultado.

Compatibilidad de entrada y recuperación​

Soporte publicado. El SDK PHP 2.5.4 incorporó la protección de entrada descrita a continuación, con enrutamiento y recuperación en Server 2.9.9. Son las versiones mínimas para estas funciones; instale las versiones estables actuales para recibir correcciones de seguridad.

El worker gestionado comprueba la entrada posicional registrada del manejador antes de entrar en su Fiber. La ausencia de argumentos obligatorios o un tipo PHP declarado incompatible provoca DurableWorkflow\Exception\WorkflowEntryArgumentsMismatch y el motivo de tarea workflow_entry_arguments_mismatch. Los valores predeterminados opcionales solo rellenan entradas omitidas; nunca reemplazan un valor registrado incompatible. Un TypeError lanzado después de entrar correctamente sigue siendo un fallo de aplicación.

El worker anuncia workflow_entry_arguments_validation automáticamente. Con el soporte correspondiente de Server, la tarea rechazada queda bloqueada para replay y el original permanece no terminal. Un runtime anterior puede reintentar la tarea fallida, por lo que actualizar solo el SDK no establece el contrato completo de recuperación.

Inspeccione el original con Client::describeWorkflow($workflowId, $runId) y el endpoint de depuración de la ejecución seleccionada. Restaure código compatible antes de llamar a Client::repairWorkflow($workflowId, $runId) y compruebe que esa misma ejecución continúa sin cambiar la entrada, el historial, la identidad de enrutamiento ni los plazos. No capture este fallo dentro del cuerpo del workflow ni repare repetidamente código incompatible. Consulte el procedimiento de recuperación de servicio y el enrutamiento de definiciones.

Modo servicio con frameworks y Laravel integrado​

El mismo paquete incluye puentes oficiales de modo servicio para Laravel y modo servicio para Symfony. Conservan la inyección de dependencias, configuración, registros, workers de consola y dobles de prueba del framework al conectarse a Cloud o Server.

Estos puentes se distinguen de los workflows integrados en Laravel, donde durable-workflow/workflow hace que la propia aplicación posea el estado duradero y ejecute mediante colas Laravel. Consulta Adopción de Laravel y transición de runtime para el mismo caso representativo en v1, v2 integrado y este puente de modo servicio, incluidos drenaje y reversión. Utiliza Modos de despliegue para una comparación más amplia de límites del runtime.

Límites de protocolo y versiones​

El SDK declara el intervalo de servidores admitidos, la versión de protocolo de workers, la versión del plano de control y los códecs en los metadatos Composer. El servidor también publica sus protocolos y códecs aceptados en GET /api/cluster/info. Comprueba el descubrimiento del runtime al desplegar en lugar de inferir compatibilidad de una versión de parche del servidor.

El SDK de PHP tiene versiones independientes del paquete Laravel. Mantén la versión publicada exacta en los ejemplos ejecutables y revisa las notas de publicación al actualizar. La compatibilidad depende del contrato declarado del SDK, no de que coincidan los números de versión de paquetes.

Páginas de lista e historial de workflows​

Estas llamadas publicadas devuelven una página, no una lectura completa automática: Client::listWorkflows(...) / Client::workflowHistory(...). Continúe con el token opaco devuelto manteniendo namespace, filtros y workflow/ejecución seleccionados; termine con token nulo/vacío y gestione los errores de página. Una página parcial no es un bundle de reproducción. Use la API de exportación de historial del SDK para reproducción sin servidor. El cliente publicado PHP 3.2.0 define los parámetros actuales; no se implica un nuevo iterador.

Informes de error acotados​

El SDK de PHP 3.5.0 incorporó informes de error salientes acotados. Los valores predeterminados son 62 KiB UTF-8 para el mensaje, 128 KiB para la pila, 64 KiB para los detalles y diagnósticos opcionales serializados en conjunto y 1 MiB para el cuerpo completo codificado en JSON. Los marcadores, el escape JSON, la identidad de la concesión y los demás comandos del lote cuentan para ese límite del cuerpo. Tiene prioridad cualquier límite de transporte configurado o declarado por el transporte que sea menor. Se conservan el tipo, la clase y el código del error, la política de reintentos y la identidad de la concesión.

withFailureReportLimit() devuelve un nuevo cliente con un presupuesto menor para la solicitud completa, de 1 a 1.048.576 bytes. Usa la instancia devuelta. También se aplica un límite inferior declarado por el transporte.

<?php

use DurableWorkflow\Client;

$client = (new Client(
    baseUri: 'https://workflow.example.com',
    controlToken: 'operator-token',
    workerToken: 'worker-token',
))->withFailureReportLimit(512 * 1024);

Un marcador visible de truncamiento y los recuentos originales de bytes identifican los campos recortados. Los detalles Avro se conservan íntegros o se omiten por completo. Si una envoltura obligatoria no puede representarse, se lanza DurableWorkflow\Exception\FailureReportRefused antes del envío HTTP. Los errores locales se normalizan antes de que el código del workflow los observe, por lo que la primera ejecución y la reproducción en frío ven el mensaje persistido. Un mensaje local ya observado permanece inmutable durante el ajuste final del lote.
